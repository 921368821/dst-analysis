## 1. ★★★ 最大风险：判据错被当成「宿主有缺口」
第三/四轮共 **10 次**红灯，**无一是宿主缺口**。反复出现的形态与对策：
- **手工列清单必漏**（sg 方法表 / prefabskin 全局表 / 渲染管理器 / 平台函数 各漏一次）
  ⇒ 改为**源码静态提取**或**单点维护**
- **本运行时的 debug 信息不可靠**：`getinfo(fn,"u").nparams` 与 `getinfo(2,"n").name` **恒 nil**
- **「我装过」≠「现在还在」**：模块会被 `require` 再执行一遍，把全局还原
- **「检查写好了」≠「检查生效过」**：**死代码在干净状态下同样输出 ✔**
  ⇒ 任何新检查必须配一次**反向测试**（造一个它该抓到的情况）
- **字符串在 ≠ 行为在**：审计条目要指向**行为**（如那两行登记/清除语句），不能指向关键词
- **★★★ 三类「假 ✅」——检查通过但什么都没证明**（今天逐条攒出来的，各已有机械守卫）：
  ① **词在 ≠ 行为在**（闸门空转）⇒ 特征串必须指向**行为**，不能指向关键词；
  ② **指向消息文本**（一改措辞就断）⇒ `audit_fixes --quality`：`string` 类必须为 0；
  ③ **自满足**：特征串**只在检查表自己那一条里**⇒「无论行为在不在都通过」，
     它**真的掩盖过一次回归**（我删掉被守护的逻辑后检查一直绿）
     ⇒ `self_satisfying_markers()`。**这三类都只能靠反向测试发现。**
- **★★★ 第四类「假 ✅」：判据可被绕过（「偶然通过」）**（2026-10-16 第 55 轮，P37）
  变异测试报「**没被抓住**」时，要先怀疑**两件事**、别只怀疑一件：
  ① 篡改本身是不是 **no-op**（⇒ 见「一处多改」）；
  ② **判据能不能被绕过** —— 实测：`⑦`「同 key 认回角色」在**身份机制完全失效**时**依然绿**，
     因为 K1 恰好拿到「重启后新连接也会拿到的槽位号」⇒ 靠**巧合**满足了断言。
  ⇒ 修法不是改判据的阈值，而是**让巧合不可能发生**（先开两个占位连接，把 K1 挤到非默认槽位）。
  **功能测试全绿说明不了任何事：判据自己不知道自己被绕过了。**
- **★★★ 第五类：隔离手段把被测的量一起钉死**（2026-10-18，P39）
  为防玩家死掉而 `health:SetInvincible(true)`，结果原版 `hunger.lua` 的
  `DoDelta` 里 `health:IsInvincible()` 会**早退** ⇒ **无敌的玩家饿也饿不着**，
  实测「饥饿恒为 150」看着像**死值**，其实是**我的隔离手段**造成的。
  ⇒ 隔离要挑**不影响被测变量**的手段（这里改成逐拍补血）。
  **凡是「测某个量在变」的判据，先问一句：我的准备动作会不会让它不变。**
- **★★★ 第六类：按「位置/槽位/名字」缓存的数据会活得比主人长**（同日，真缺陷）
  `hub.me_by_slot[槽位]` 在槽位**换主人**（旧角色被回收、槽位分给新连接）之后，
  到下一轮刷新（≤0.27 s）之前仍是**上一个角色**的数据，而且 `ok` 还是 `true`。
  ⇒ 缓存条目必须**自带身份**（`guid`）并在出口对账；换主人时**源头作废**。
  **形态：有字段 ≠ 那个字段说的是你。**
- **★★ 自检用例里**写死**被测系统的当前值 ⇒ 迟早假红**（同日，`verify_plan.py`）
  一条自检写着「项数 31 对得上不得报」，加了一条测试（31→32）之后它立刻假红。
  **假红比漏测更坏**：人一旦习惯「这条偶尔红」，真回归就再也看不见了。
  ⇒ 自检只锁**语义**，数字从实时数据取。
- **★ 「当时值」标记必须与数字**同一行**（跨行不算）** —— `verify_plan.py` 是按行过滤的。
- 杂项：断言用 `__` 开头键被惰性表忽略；`grep PASS` 会匹配 `IMPASSABLE`
- **★★★ 改文件的动作本身也要「行首锚定」**（今天**三次**插坏文件的根因）：
  `s.replace("def main():", 新函数 + "def main():", 1)` 命中的**不是定义**，
  而是**别处字符串/注释里引用的同一个串** ⇒ 整个文件被插坏。
  ⇒ ① 按**行首锚定**（`^def main\(\):`）找；② 判据/审查**只看代码、剥掉注释**；
  ③ 必要时把字面量**拆开**（`'def '+'main'+'():'`）让它不可能被误命中。
  **「按子串找」而不问「这段文本是什么身份」= 今天所有翻车的共同根因。**
- **★★★ `lupa` 里「包装套两层」会静默返回 nil**（2026-10-16 **一天踩了三次**）：
  写了 `q(code)` = `L.eval("(function() " + code + " end)()")`，然后又传进一段
  **自带 `(function() … end)()`** 的代码 ⇒ 外层函数体只剩一个表达式、**没有 return**
  ⇒ Lua 返回 nil ⇒ Python 拿到 `None`。
  症状是 `int(None)` 的 TypeError / `not enough values to unpack` ——
  **看起来像「取不到值」，实际是包装问题**，会把人引向错误的排查方向。
  ⇒ 规矩：一个文件里**只允许一种包装约定**；要混用就分成两个明确的名字
  （本项目现在用 `q`/`qx`、`ev`/`evx`）。
- **★★★ 「想吵，但吵的机制本身坏了」**（2026-10-16 压 §9v.5 时压出来）：
  `rt/server.py` 的 `targets` 出错分支打印 `cid`，而 `cid` 只是**另一个方法的局部变量**
  ⇒ 出错处理自己抛 `NameError`，把真正的 `TimeoutError` **盖住**了。
  这类 bug **跑得再全也测不出来**（只在出错时才走）⇒ 已加静态守卫
  `tools/lint_names.py`（`pyflakes`，**只判「未定义名/语法错误」**，无害提示只列出不判红 ——
  否则守卫会淹没在噪音里；没装 pyflakes 直接判失败，不静默跳过）。
  ★ 另：**未使用的变量往往是一个「空洞」**（我写的 `E3` 里 `before_tw` 赋值了却没断言）——
  静态检查顺手能抓出来。
- **★★★ 跨进程读帧：一律按帧里的 `t` 排空**（2026-10-16 **一天栽了 4 次**）。
  「读一条帧就当最新」永远是错的：socket 里积压的是**按键之前**的旧帧 ⇒
  位置/状态当然不动 ⇒ 把一个**测法问题**误报成 bug（今天在 E8 上就这么误报过一次）。
  正确做法：读到 `t ≥ 目标时刻` 才取最后一次见到的值。
- 流程：修复前问「**先有失败样本吗**」；修完**从同一样本重跑**（缺口是链式的）
- **★★★ 「我量的不是我以为我量的东西」**（2026-10-16 新增，与上面同族但更阴）：
  我写了个探针做「只发一次 act」的实验，但**被测代码自己会在后台重发**
  （`step_one_player` 的待做动作分支每 30 拍 push 一次）⇒ 那次实验实际测的是「每秒一下」，
  而我把读数当成了「一次 push 的结果」，据此改了服务端，**弄红了 2 条判据**。
  ⇒ 规矩：**实验里要数清被调用的次数**（`act_ok` 计数 / 打点），
    不能只看「结果变了没有」；探针必须证明它**真的**在测它声称测的东西。
  ★ 这次抓住我的是**判据**，不是推理 —— 这就是「反向测试」值钱的地方。
- **「查不到」≠「宿主有缺口」**：`§9w.2` 两条「做不了」，查下去一条是**客户端行为错**、
  一条是**诊断错**（我测的方法在原版里根本不存在）。⇒ 下结论前先确认
  **被测的 API 是不是原版真有的**（`grep "function Inventory:"`），别拿自己臆想的接口当基准。

## 4. ★ 引擎语义速查（**只留最容易再犯的**；其余见报告 §4 与各断言的注释）
- **数值型 getter 绝不能返回 nil**（Light `_intensity`、Transform `_x`、`TheInventory:*Count`）
  ——下游多半是算术/比较，nil 会把错误推到很远（今天因此打挂过 3 个入口）
- `AddComponent` 影子闸门 = **查 + 成功添加后登记 + 移除时清除**，三处缺一即**空转**
- **★★★ 07 侧：玩家会在世界开始约 12 s 后掉血致死，死后世界永久停摆**（2026-10-16 查实）。
  逐秒实测：`health 150 → 49.95（6 s）→ 0（12 s）`，随后 `sg=death`，
  **之后 `act` 再也推不动任何动作 —— 但 `push_action` 依旧返回成功**。
  ⇒ 「树砍不倒」「同一脚本三遍结果不同」**全是这个**（§9w.2 的答案）。
  判据侧用 `_pin_player_alive()`（`health:SetInvincible(true)`）钉住这条无关变量；
  `/healthz` 与 `/status` 现在报 `player_alive`/`player_health`（**死必须看得见**）。
  ⚠️ 仍未解：无复活路径；`phase=day` 时却在掉血并进 `hit_darkness`（两个真相源不一致）；
  掉血速率/每刀进度不完全可复现。
- **★★ 「一节拍主人」原则**：`loco:PushAction` **一次 push = 一次敲击**（实测只 push 一次 ⇒
  `workleft` 15→14 就停住）；「连砍」靠**服务端** `ACT_REPEAT`（30 拍 = 1 s）定时重发撑起来
  —— 它是**承重结构**。客户端**只需按下时发一次**；自己也重发会与服务端节拍**叠加**：
  实测砍一棵 15 点的树，客户端重发 ⇒ **21 s / 30 次 push**，只让服务端一节拍 ⇒ **15 s / 15 次**（各 3 遍一致）。
- **带 target 的动作是「到达之后才执行」**：`PushAction` → `GoToEntity`，
  到达距离 = `ARRIVE_STEP + rad(owner) + rad(self)` 再 `max(…, bufferedaction.distance)`。
  `ACTIONS.CHOP.distance = 1.75` ⇒ 1.2 格能砍；`ACTIONS.PICKUP` **没有 distance**
  ⇒ 算出来 ≈0 ⇒ 只有站在物品**正上方**才算到达（0.2 格就捡不到）⇒ push 成功却**静默无反应**。
  ⇒ 用原版自己留的钩子 `bufferedaction.arrivedist` 补（只在两个字段都缺时才补，并**记账**）。
- **★★★ 06 宿主里两处光照桩互相矛盾 ⇒ 白天也被「黑暗」打死**（2026-10-16 查实）：
  `host/01_core.lua:186` 的 `LightWatcher:IsInLight = **true**`（理由「宿主恒为白天」**已过期**，
  挂上世界组件后宿主已有昼夜）与 `host/06_entityscript.lua:189` 的
  `EntityScript:IsInLight = **false**`（理由「无光照系统」）。
  `grue:CheckForStart()` 读的是后者 ⇒ 恒 false ⇒ 永远「在黑暗里」⇒ 5~10 s 后一发
  `GetAttacked(nil, TUNING.GRUEDAMAGE=100.05, nil, "darkness")` ⇒ **玩家 12 s 必死**。
  ⇒ 07 侧代理：`sync_grue_light()` 按**世界昼夜相位**加/撤 `grue:AddImmunity("light")`
  （原版本来就是靠 LightWatcher 的 enterlight/enterdark；**是代理不是等价**：营火旁不挨打做不到）。
  **不改 06**（保真基线），缺陷登记在 §9z。
- **★ `isinstance(True, int)` 是 True** ⇒ 任何 `elif isinstance(v,int)` 的归一化都会**把布尔变成 1/0**。
  `rt/server.py` 的 `Sim.stats()` 里就踩了：`/healthz` 的布尔全成了 `1/0`。
  最刺眼的是这一行**同一个表达式里已经修过一次**（浮点被截断）——
  **「这里修过了」≠「这里没问题了」**。消元顺序必须 **bool 先判**。
- **★★ 玩家死后状态机出不去**（`SGwilson` 的 death 是终态，`GoToState("idle")` 报
  `Left death state.`）⇒ 07 侧的复活只能**换一具身体**（`M.respawn`：移除尸体 + `add_player`），
  死满 3 s 自动做（`auto_respawn`）。**原版是变 ghost，本宿主没有 `SGghost`**。
  ⚠️ 换了身体之后：**客户端必须能认回自己** —— 靠「客户端每 2 s 例行重问 `whoami` + 服务端
  `slot_guid` 对账」，**不靠推送**（推送在负载下不可靠）。且**只在 guid 真变了**时才重置预测。
- **★★★ 对象被换掉 ⇒ 挂在旧对象上的状态没人重建**（今天在**自己的补丁**里又踩了一次）：
  光照代理只在**相位翻转**时动手 ⇒ 复活后的新身体 immunity 表是空的 ⇒ 白天又挨打。
  ⇒ 判据/代理都要**同时认实体**（`dark == last_dark and p == last_grue_entity` 才早退）。
  同类：这个母题今天以「两处桩矛盾」「死代码」「注释理由过期」等形态反复出现。
- C++ 子对象用**代理法**（任何名字都接得住），但**返回布尔的查询必须显式给 false**
- 客户端专属对象**保持 nil** 才忠于原版；`Profile` 要给「设置代理」
- **动作链（07 侧，量出来的）**：一次 `locomotor:PushAction(ba)` = **一次**敲击；
  「连砍」靠**服务端按 `ACT_REPEAT`(30 拍 = 1 s) 定时重发** —— 它是**承重结构**，
  删了会「一次都砍不倒」。反过来说，**任何一次多余的 push 都会把正在飞的那一记顶掉**
  （客户端再叠 0.7 s 一发 ⇒ 效率从 1.0 点/次掉到 0.35）。
  ⇒ 客户端只发一次；服务端负责节拍。
- **玩家与树的物理接触 ≈ 1.2 格**，而**动作有效距离更近**（1.0 格能砍、1.2 格打空）
  ⇒ 「到了就敲、打空等下一拍」这个容忍性必须靠重发提供，不能假设「够得着就一定砍得动」。
- **树倒 = 同一实体的 `workable.action` 从 `CHOP` 变 `DIG`**（`make_stump` 就地改成树桩），
  `workleft` 重置为 1。所以「workleft 卡在 1 不动」是**已倒下**，不是卡住。
  掉落走 `lootdropper:DropLoot`（`log` / `pinecone`）。
- `chop_tree`(onwork) 在宿主里**第一行就返回**（`components.growable == nil`）⇒
  它依赖的 `GetGrowthStages` / `PlayChopSound`（宿主 NIL）**碰不到**。
  `GetBuild` 也是 NIL —— 但 `chop_down_tree` 还没走到那一行就被 `growable` 分支绕开了。
- **原版 `Inventory` 没有 `GetItems`**（真接口：`GetItemInSlot`/`FindItem`/`GetItemsWithTag`/
  `Has`/`GetItemByName`/`GetNumSlots`/`GiveItem`），且这些**在宿主里都能用**。
  「拾取不可用」的旧结论因此作废 —— 缺的是 07 侧没接 PICKUP。
- **引擎不向预制体工厂传参**（三处外部文档一致）⇒ `carnivaldecor_*` 是原版缺陷，**不修**

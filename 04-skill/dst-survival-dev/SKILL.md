# 类饥荒生存游戏开发与 Bug 修复

> 方法论沉淀自《Don't Starve Together》(DST) 的完整 Lua 代码树拆解（821 个组件 / 1594 个预制体 / 261 个状态图 / 444 个地图文件）。
> 本文所有硬约束、Bug 模式与数量级参考都来自对真实源码的核实，不是通用最佳实践的转述。

---

## 一、何时使用本 Skill

**命中以下任一情形即加载本 Skill：**

| 场景 | 具体信号 |
|---|---|
| **搭建/扩展玩法逻辑** | 要新增一种生物、物品、配方、食物、状态效果；要在已有系统上挂新行为 |
| **调生存数值** | 觉得饥饿掉得太快、理智阈值不对、温度手感诡异、难度曲线太陡/太平 |
| **写或改 AI** | 生物不寻路、不攻击、卡在原地、行为抖动、状态切换丢失上下文 |
| **做世界生成** | 要生成地图/关卡/地牢；要保证可通关、要放资源、要控制生成耗时 |
| **做联机** | 多人不同步、客户端看到的状态不对、预测回滚、RPC 被限流、带宽异常 |
| **查 Bug** | 卡顿 / 掉帧、内存持续增长、崩溃、存档读不回来、物品复制或丢失 |
| **写存档兼容** | 改了字段名、加了新组件、要支持旧版本存档迁移 |
| **写模组接口** | 要暴露给第三方扩展点、设计钩子、避免模组互相破坏 |
| **做架构选型** | 正在决定「实体/组件/预制体怎么分层」「谁跑服务端逻辑」「事件怎么设计」 |

**不适用：** 非生存类游戏的通用引擎问题（渲染管线、材质、音频混音）、以及与本体系无关的纯前端/工具链开发。

## 二、核心架构原则（10 条硬约束）

这些是 DST 十年维护沉淀出的不可违背项。每条都写明了**理由**——如果你的方案违反了其中一条，必须能说清为什么这个理由不成立。

### 约束 1：三层严格分工——Prefab 是"如何造"，Component 是"如何表现"

- **Prefab（工厂函数）**只负责：创建实体壳 → 挂原生组件 → 打标签 → 挂行为组件。不写玩法规则。
- **Component（组件）**承载全部行为与状态，**彼此之间没有继承**，通过 `inst.components.xxx` 访问。
- **依据**：DST 的 1594 个预制体里没有任何一个继承另一个预制体；两个共享 `health` + `combat` 的实体行为相似却不需要共同基类。这样才能按预制体自由混搭能力、在运行时增删组件、每个组件小而可测。

**违反后果**：一旦让预制体继承玩法基类，你会得到一棵无法拆解的继承树，加一个"会燃烧的背包"就得新建 6 个子类。

### 约束 2：`SetPristine()` / `ismastersim` 闸门是主从分离的唯一边界

```lua
inst.entity:AddNetwork()          -- 必须在这之前
inst._charge = net_byte(...)      -- 所有 netvar 声明在这之前
inst.entity:SetPristine()         -- 冻结"可同步状态"的快照
if not TheWorld.ismastersim then return inst end   -- 客户端到此为止
-- 以下全部是服务端权威逻辑
```

- **依据**：`SetPristine` 之前添加的一切都会被复制给客户端；之后的不会。一个工厂函数同时描述服务端与客户端的实体，**实体的形状有单一事实来源**，且服务端专用代码有一条显眼的、可 grep 的分界线。

**违反后果**：客户端跑权威逻辑 → 双端各自改状态 → 永久分叉，且这类 bug 极难定位（症状是"偶尔 UI 显示不对"）。

**附加硬约束**：`AddNetwork()` 必须在 `SetPristine()` 之前。DST 的 1905 处调用全部遵守此序。

### 约束 3：状态写入只能通过一个受控入口，禁止裸赋值

数值条的**唯一**写入口是 `DoDelta()`，它按固定顺序执行：闸门 → 钳制 → 边缘触发 → 事件广播 → 积分。

- **依据**：DST 的 `Health:DoDelta`（`health.lua:613`）有七个有序阶段——非致死地板 → `redirect` 钩子 → 无敌判定 → 吸收 → `deltamodifierfn` → 单次伤害下限 → `SetVal`。任何裸赋值都会跳过其中某些阶段。

**违反后果**：`self.currenthealth = 0` 会漏掉死亡检测（`old_health > 0 and current <= 0` 这个跨栏判断）、漏掉 `entity_death` / `death` 事件、漏掉尸体处理。表现为"东西不会死"。

### 约束 4：属性 setter 承载网络同步与副作用，不设"脏标记"

```lua
local Health = Class(function(self, inst) ... end, nil,
    { maxhealth = onmaxhealth, currenthealth = oncurrenthealth, ... })
-- setter 自动把值推到 inst.replica.health 并刷新 HUD
self.currenthealth = 42   -- 一句普通赋值即完成同步 + UI 更新
```

- **依据**：`class.lua` 的 `props` 机制让赋值透明触发副作用。这是保持权威状态与复制状态同步的最干净方式，**不存在"被遗忘的脏标志"**。

**违反后果**：同步与业务逻辑分离后，必然出现某条路径忘了设脏标记，症状是"血量在别人屏幕上不变"。

### 约束 5：事件订阅必须双向记账，销毁时统一解绑

订阅时同时在**数据源**（`event_listeners`）和**监听者**（`event_listening`）登记，销毁时成对摘除。

- **依据**：Lua/C++ 的 GC **不会**帮你断开双向引用。`TheWorld:PushEvent("entity_death", {inst=...})` 的 data 会被监听者闭包捕获，实体逻辑上已死也会被拖住不回收。DST 的 `RemoveAllEventCallbacks`（`entityscript.lua:1232`）是 `Remove()` 能安全执行的前提。

**违反后果**：内存泄漏随游戏时长线性增长；严重时实体被"复活"——`Remove` 后仍收到事件回调，在已销毁对象上执行逻辑。

### 约束 6：所有异步任务必须归属到实体，销毁即自动取消

`DoTaskInTime` / `DoPeriodicTask` / `StartThread` 一律通过实体发起，任务 id 绑定实体 GUID。

- **依据**：`KillThreadsWithID(guid)` 让"死亡即取消"变成自动行为，不需要每个组件手动清理。这是 DST 能在几十万次实体创建/销毁下不泄漏协程的基础。

**违反后果**：这是泄漏重灾区。见 `bug-patterns.md` 的「协程泄漏」与「实体销毁后协程未清理」两条。

### 约束 7：定时器回调不可挂起（不可 `yield`）

周期任务回调内只允许做"本刻能做完"的事；需要长时序逻辑就用 `StartThread` + `Sleep`。

- **依据**：`DoPeriodicTask` 底层是协程，回调里 `yield` 会让任务在下一次 tick 恢复前不再运行——周期漂移；若此时被 `Cancel()`，协程永远不 resume 也不 dead，直接泄漏。

**违反后果**：`DoPeriodicTask(1, fn)` 悄悄变成"1 秒 + fn 的耗时"。且 `Cancel()` 后协程悬空。

### 约束 8：AI 分决策层与执行层，两层都要迟滞

- **决策层**（行为树 / Brain）：决定"做什么"，周期 0.25–1 s。
- **执行层**（状态图 / StateGraph）：决定"怎么做"，`Sleep(0.125)` 级别的转向频率。
- **转向频率 ≥ 决策频率的 3–8 倍**；所有距离判断用**双带**（触发阈值 / 停止阈值）。
- **依据**：DST 的兔子 period=0.25 s（猎物必须反应快），`ChaseAndAttack` 内部 8 Hz 转向。单阈值会在边界抖动（A→B→A→B），视觉刺眼且每帧触发一次寻路请求。

**违反后果**：怪物在判定边界疯狂抽搐；CPU 被无意义的寻路吃掉。

### 约束 9：世界生成必须做后置验收，且失败要结构化报错

五道硬校验：提交成功 → 最小面积 → 连通性（孤立地块 < 5%）→ 必需资源数量 → 存在出生点。任一失败则重试（上限 5 次），仍失败则**结构化返回原因**。

- **依据**：DST 的 `Node:PopulateVoronoi` 里 `if #points_x < pos_needed then return end` 是**静默放弃**，只打 `print`。结果是一张"少了几个洞穴"的地图——玩家不报错，但会遇到"我要找 XX 资源但地图上没有"。

**违反后果**：无法复现的"地图有 bug"工单。静默失败必须留下可查询痕迹（统计表 / 调试面板）并在验收阶段作为警告输出。

### 约束 10：数值常量写成"意图表达式"，不写裸数字

```lua
DAPPERNESS_MED      = 100/(day_time*6)     -- 读作"6 天掉满一条理智槽"
WILSON_HUNGER_RATE  = calories_per_day/total_day_time
STARVE_KILL_TIME    = 120                    -- 这个就该是裸数字（它不是速率）
```

- **依据**：策划看到 `100/(day_time*6)` 立刻知道设计意图，看到 `0.034722` 得心算。更重要的是**改时钟时速率类常量会自动等比缩放**，而裸数字会悄悄失衡——这恰恰暴露了哪些是"玩家感知量"（速率/累积量，应归一化）、哪些是"物理量"（温度、长度，不该归一化）。

**必做**：`day_time`（白天 300 秒）与 `total_day_time`（全循环 480 秒）**必须在代码里显式区分命名**。DST 没做到这点，导致季节变化时数值漂移，是十年维护里必然反复踩过的坑。

## 三、常见开发任务怎么入手

### 任务 A：新增一种生物

| 步骤 | 做什么 | 查哪里 |
|---|---|---|
| 1 | 定参数：血量、速度、攻击、掉落、吃什么 | `references/gameplay-numbers.md` 参数表模板 |
| 2 | 写决策层：脑的行为树，标好 period 与迟滞双带 | 约束 8 |
| 3 | 写执行层：状态图，用生成器而不是复制粘贴 | `references/architecture.md` §7 |
| 4 | 挂组件：`locomotor`（**必须在状态图之前**）→ `health` → `combat` → `brain` | 约束 1 |
| 5 | 依赖声明：把会生成的预制体列进 `deps`，保证资产常驻 | `references/architecture.md` §1 |
| 6 | 加标签（至少 `mob` + 阵营 + 可食性） | §3 标签规范 |
| 7 | 存读档：至少脑的目标状态、`combat.target` 要能在 `LoadPostPass` 还原 | `references/architecture.md` §2 |

**最易踩的坑**：忘了 `locomotor` 必须在 `SetStateGraph()` 之前加（状态图构造时会查询它）；忘了脑的思考相位随机散布（`period * (0.5 + random())`），导致 100 只同种怪同一刻集体重评。

### 任务 B：新增一种食物/物品

1. 建组件（`edible` / `inventoryitem` / `stackable` / `perishable`）而不是往预制体里塞字段
2. 用 `Make*` 打包辅助函数复用原型
3. 数值按"每天需要多少热量 ÷ 每份提供多少"反推
4. 检查腐败乘数：新鲜 1.0 / 变质 0.667 / 腐烂 0.5
5. 交互动词通过 `COMPONENT_ACTIONS` 注册收集器，不要写 switch

### 任务 C：调试"卡顿/掉帧"

按 `references/debugging.md` 的定位流程走。快速自查三问：
1. 是不是协程/定时器数量爆炸？（看活跃协程数）
2. 是不是每帧事件广播过多？（单帧 > 5000 次就该优化）
3. 是不是本该休眠的实体还在 tick？（这是 DST 里 90% 的浪费）

### 任务 D：调试"多人不同步"

按 `references/debugging.md` 的联机排查顺序走。最高频的三个根因：
1. 净字段漏设脏标记（但因为约束 4，这类问题应该已被架构消灭——如果出现了，说明绕过了 setter）
2. `netvar` 声明顺序两侧不一致（模组单边启用）
3. `set_local` 污染导致带宽永久抬高

### 任务 E：调试"存档损坏/读不回来"

1. 先确认是不是 NaN/Inf 写进去了（存档必须是可读文本，直接搜 `=nan` / `1.#QNAN`）
2. 检查有没有字段重命名没写迁移映射
3. 检查组件名大小写（存档字段名 = 组件表的 key）
4. 见 `references/bug-patterns.md` 「存档损坏」系列

### 任务 F：做世界生成

1. 先写"锁—钥匙图"保证可达性（不要靠洪水填充碰运气）
2. Voronoi + Lloyd 松弛做地形，用**网格空间哈希**把最近站点查询降到 O(1)（100 次迭代从 8 秒降到 1 秒内）
3. 散布按 O(胞元点数) 而非 O(面积)
4. 五道后置校验 + 结构化报错
5. 生成跑在**独立离线 VM**，不在游戏主循环里

### 任务 G：设计新系统 / 扩展点

先读 `references/modding-api.md`。核心原则：**不改任何原版代码，只在既有钩子点插入回调**。钩子分两种：贡献函数的（fn 型）和贡献数据的（data 型）。

## 四、Bug 排查决策树

### 4.1 性能问题（卡顿 / 掉帧 / CPU 高）

```
CPU 飙高
├── 主线程帧时间高
│   ├── 协程/定时器数量异常
│   │   ├── 单个实体挂了成百上千个 DoPeriodicTask → 改用 StartThread + Sleep
│   │   └── 全局定时器在每刻触发 → 提高周期 / 合并到统一 tick
│   ├── 事件广播量过大
│   │   ├── 监听者数量过多（一个事件挂了几百个监听者）
│   │   └── 单帧广播 > 5000 次 → 加"脏聚合"或降频到每 N 刻一次
│   ├── 实体数过多且都在 tick
│   │   └── 启用休眠机制（兴趣管理）：离开活动区即停脑、停状态图
│   └── 空间查询过密
│       ├── FindEntities 半径设得过大 → 缩小半径或用分层空间哈希
│       └── 每帧多次同一区域查询 → 缓存一帧
├── 世界生成阶段慢
│   ├── Lloyd 迭代用了暴力 O(P×S) → 改网格空间哈希 O(P+S)
│   ├── 静态布局回溯重试 → 改为"失败即放弃，不回溯"
│   └── 重试代价（maxtries=5 每次全量 GC）→ 结构化报错提前退出
└── 单个模组占满 CPU
    ├── 死循环 → 加指令配额 / 独立 Lua state
    └── 每帧全局扫描 → 检查其 OnUpdate
```

**数量级参考**：DST 单个世界约 3000 个实体，但同时活跃的通常只有 **100–200 个**。休眠机制砍掉 90% 的 AI 开销。**AI 的规模问题从来不是"节点太多"，而是"不该跑的还在跑"。**

### 4.2 联机不同步

```
客户端与服务端表现不一致
├── 状态值本身不同
│   ├── 绕过了属性 setter 直接写字段 → 回到约束 3/4
│   ├── 该组件没注册进 REPLICATABLE_COMPONENTS → 客户端永远看不到
│   ├── netvar 声明顺序两侧不一致（模组单边启用）→ 改用显式字段 ID
│   └── 服务端写了 replica（只读镜像）→ 破坏同步，只允许读
├── 状态对但行为不同
│   ├── 逻辑跑在了客户端（非 ismastersim 侧）
│   ├── 服务端逻辑被条件短路，两端条件结果不同
│   └── pairs 遍历顺序两端不同 → 改用有序遍历 + 确定性 tiebreaker
├── 客户端卡顿/瞬移
│   ├── 缺客户端预测 → 补"预测移动 + 服务器纠正"链路
│   └── 预测与权威逻辑不一致，无回滚带
└── 带宽异常
    ├── set_local 被滥用 → 该字段永久性退化为每次 set 都发
    └── 模组无限抬高全局 RPC 限流 → 每模组独立配额 + 全局硬上限
```

### 4.3 崩溃 / 报错

```
崩溃
├── nil 索引
│   ├── TheWorld 在世界实体创建前被访问
│   ├── 组件在服务端专属分支里被客户端访问
│   └── 模组拦截器返回值可能是 nil（原版"条件为假就什么都不做"是已知 AI 卡住原因）
├── 已销毁对象被访问
│   ├── 协程/事件在实体 Remove 后仍在跑 → 补齐清理（约束 5、6）
│   └── 闭包捕获了已销毁实体 → 检查 SourceModifierList 的 onremove 链
├── 遍历中修改
│   ├── pairs 遍历时回调里 Remove 实体 → 先快照再遍历
│   └── Remove() 重入（组件的 OnRemoveEntity 里又调 Remove）→ 加 is_removing 标志
└── 数值异常
    ├── 除零（min/max 截断差异）
    └── NaN 传播 → 存档写入前必须做 isbadnumber 检查
```

### 4.4 存档问题

```
存档损坏 / 读不回来
├── 含 NaN / Inf
│   ├── 值计算本身产生了 NaN（除零、sqrt 负数）→ 加数值守卫
│   └── NaN 走别的序列化路径绕过了扫描 → 在序列化器里加类型钩子
├── 字段丢失
│   ├── 组件名改了大小写 → 统一小写
│   ├── 字段重命名没写迁移映射 → 写 replace 表
│   ├── 组件被删了但存档里还有 → 用 add_component_if_missing 机制
│   └── 引用实体没解析 → 检查两趟加载（OnLoad 存 GUID，LoadPostPass 换实体）
└── 读档后状态错乱
    ├── setter 在读档时被守卫条件挡掉（标签没更新）
    └── setter 依赖的字段还没被恢复（顺序耦合）→ 显式的"更新标签"方法
```

### 4.5 AI 异常

```
AI 不动 / 行为奇怪
├── 站在原地什么都不做
│   ├── ActionHandler 的 condition 为假 → 动作没被接受但 locomotor 已到位（已知卡住原因）
│   └── 目标不可达 → 检查寻路
├── 莫名停下
│   ├── PriorityNode 的 EventNode 抢占时 Reset 了正在跑的子节点 → 状态丢失
│   └── statemem 在 GoToState 时被清空 → 跨状态用 sg.mem
├── 抖动 / 抽搐
│   └── 单阈值判定 → 改双带迟滞（约束 8）
├── 追着打不到
│   └── 落空也计入攻击次数并重置追击计时 → 这是可调参数而非 bug
└── 跟不上 / 转向迟钝
    └── 转向频率 < 决策频率 3 倍 → 提高转向频率
```

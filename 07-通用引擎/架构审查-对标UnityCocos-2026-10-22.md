# 架构审查：它能不能成为"真正的引擎"（对标 Unity / Cocos）

> 审查对象：`07-通用引擎`（实时层）+ `06-引擎复刻`（宿主）+ `02-注释源码`（内容层）
> 审查方式：读代码 + 实测量级 + 对照既有 `Unity对标审查与路线图-2026-10-21.md` 复核
> 审查日期：2026-10-22　审查人：AI（基于仓库内可复核的证据，不采信文档自述）
> 结论口径：**分两套分打**——"运行时内核"与"引擎产品"是两种东西，混在一起打分只会得出错误结论

---

## §0 一页结论（先看这一段）

**一句话**：它现在能**跑**一个世界，但还不能**生产**一个世界。

| 角色 | 得分 | 依据 |
|---|---|---|
| **运行时内核**（模拟 / 确定性 / 网络 / 动画） | **67 / 100** | 6 项加权：实体组件 3/4 · 确定性 4/4 · 动画 3/4 · 物理 1/4 · 网络 3/4 · 调试 2/4 |
| **引擎产品**（渲染管线 / 资产 / 编辑器 / 构建 / 平台） | **20 / 100** | 10 项加权：RHI 1 · 材质 0 · 2D批 2 · 光照 1 · 相机 1 · 3D 0 · 资产 1 · 编辑器 1 · 构建 0 · 平台 1（各 /4） |
| **生态**（SDK / 扩展 / 包管理） | **13 / 100** | 脚本对外能力 1 · 扩展点 0.5 · 生态 0（各 /4） |

**三句话**：

1. **缺的不是 20 个功能，是 4 个层**：平台抽象层、资产管线、构建发布、编辑器框架。
   前三个当前是 **0 行代码**；第四个是 432 行"寄生在运行中世界上的面板"。
2. **最值钱的资产不是引擎，是"引擎工程能力"**：确定性 tick + 逐 tick 回放校验 +
   274 条判据 + 协议 schema 单一来源 + 命令栈/原子场景导入。这些在 Unity/Cocos 项目里
   都少见，**不要为了"像 Unity"而丢掉它们**。
3. **最贵的负债是三层语言三套数据模型**（Lua 世界 / Python 编排 / JS 表现）：
   任何新能力都要改三处。今天加的 `pr`（腐烂进度）字段就是三处手改（rt_boot / sim.py / client.html）
   ——这不是风格问题，是**边际成本**问题，也是"引擎 API 面不统一"的根。

**需要你拍板的一个决策**（其它都是执行）：

- **目标形态 A（Unity 式）**：native 内核 + 多后端 + 多平台导出。
  代价：换内核语言、重写全部表现层，现有 32.6k 行运行时约 **30%** 可迁移；
  单人/小队**不可达**（既有路线图里 M8 多平台 10.5 人月已标"不建议"，我同意）。
- **目标形态 B（Cocos Creator 式，推荐）**：**Web-first、编辑器驱动、2.5D**。
  代价：放弃 3D/主机/原生；收益：现有客户端、协议、Lua 内容层、判据基座**全部可保留**，
  单人可按季度推进。**本文的建议是 B。**

## §1 打分口径（先说清怎么打分，便于反驳）

### 1.1 成熟度级别

| 级别 | 含义 | 判据 |
|---|---|---|
| **L0** | 无 | 没有代码，或只有注释/TODO |
| **L1** | 原型 | 能演示一个场景，换个人/换个项目就用不了 |
| **L2** | 可用 | 单项目能靠它交付，但缺工具、缺边界、缺文档 |
| **L3** | 成熟 | 有工具链、有明确边界、有回归测试，能被第二个人接手 |
| **L4** | 平台级 | 能被**第三方**依赖：有稳定 API、有版本策略、有生态 |

### 1.2 为什么打两个分

Unity/Cocos 之所以是"引擎"，不是因为它们能跑世界（很多游戏框架都能），
而是因为它们在**世界之外**还提供四样东西：

```
   ① 平台抽象（同一份内容跑到不同设备）
   ② 资产身份与管线（美术改图不用改代码）
   ③ 构建发布（非开发者也能拿到可运行产物）
   ④ 编辑器（内容生产的主要界面，且与运行时隔离）
```

**这四样当前全部缺失或只有壳**。所以"运行时 67 + 产品 20"不是自相矛盾，
而是精确描述了现状：**内核是真的，产品是空的。**

### 2.2 分层与依赖方向（读代码确认）

```
浏览器（单页）                                    Python 进程
┌──────────────────────────────┐   WS(二进制 v3)  ┌──────────────────────────────┐
│ client.html 2,141 行          │◄────────────────►│ server.py   HTTP + WS        │

│  ├ DOM HUD（1 行文本）         │                  │        └ sim.py  lupa 嵌入     │
│  └ DOM 编辑器（432 行）        │                  │           └ rt_boot.lua 3.5k │
└──────────────────────────────┘                  │              └ host/ 46k Lua  │
                                                   │                 └ DST 脚本 1.5M│
                                                   └──────────────────────────────┘
```

依赖方向是干净的（JS 不碰 Lua，Lua 不碰网络），**这是优点**。
但反过来看：**一次绘制要跨 4 个渲染表面**（WebGL 精灵 / Canvas2D 地形 / DOM HUD / DOM 编辑器），
它们之间没有任何合成抽象——每个新表现能力都要在 4 处分别决定"我算哪一层"。

### 2.3 关键实现事实（逐条可复核）

| 事实 | 证据 |
|---|---|
| 渲染是 **WebGL1 + 单一硬编码 sprite 着色器** | `render_batch.js:249-262` 顶点属性只有 `a_pos/a_uv`（**没有 color/tint/z**），uniform 只有 `u_res/u_tex` |
| 相机是**CPU 投影的 2D 平移缩放**，着色器里无矩阵 | `render_batch.js:254` `clip = a_pos/u_res*2-1` |
| 无 tint / 无旋转 / 无遮罩 / 无九宫格 | 顶点格式仅 pos+uv，CPU 侧生成轴对齐四边形 |
| 光照 = **一层 `rgba` 覆盖**，无光照管线 | `client.html:1222-1229` `darkA` + `fillStyle` |
| 物理 = **293 行运动积分**，碰撞是 07 侧给玩家写的**扫掠圆 CCD** | `host/11_physics.lua`（293 行，仅 `_integrate`）；`rt_boot.lua:1472-1520` 线段-圆求交 |
| 无宽相 / 无窄相 / 无关节 / 无射线查询 | 计划里 F1◐ F2○ F3○ F4◐ |
| 场景 = **TSV 文本**（`prefab\tx\tz[\toverrides]`），无嵌套层级 | `rt_boot.lua` `M.scene_export/import` |
| 资产**无 GUID、无 importer、无依赖图**；场景靠 prefab 名字符串引用 | 全仓无 `.meta`、无 assetDB |
| 新增可摆放内容 = **写 Lua prefab**，不是拖资产 | `Core.Prefabs` 注册表 + DST prefab 约定 |
| 编辑器 = 同一进程、同一世界上的 DOM 面板；撤销栈覆盖 **5 个动词** | `client.html:1499-1930`（432 行）；`commands.py` move/spawn/remove/scene_import/scene_clear |

| 网络 = **全量快照/帧**，无 AOI；地形只发一次（128×128 ≈ 40 KB） | `protocol.md:24`；`grep AOI` 0 命中 |
| 协议有**单一来源 schema**（v3 fix16），py/js 双侧生成 | `protocol.schema.json` + `gen-protocol-schema.mjs`（闸门 ⑥ 校验） |
| 构建发布 = `start.sh/stop.sh/*.bat` + `pack_atlas.py`（289 行） | `deploy/` 下**没有**打包、清单、版本、签名 |
| 平台分支在运行时里**几乎是 0**（`os.name` 只出现在 tests） | `grep os.name rt/*.py` → 0；`taskkill` 仅出现在注释 |
| 无 CI 配置 | 仓库无 `.github/`；闸门靠本地 `pre-commit.sh`（12 步） |
| 帧率**有判据但只是下界** | `F3`：6/50/400 实体"乐观下界 ≥55 fps"，实现在 `perf_lib.measure()` —— **Node 沙箱里对 draw 路径的 CPU 计时**（无 GPU、无浏览器合成、无 HUD/DOM 成本） |
| 真实设备帧率**无测量** | 无 headless Chromium + GPU 的测量管道；`/healthz` 也没有客户端帧率上报 |
| 完成度：102 模块 / 57.2 人月；● 35(20.4) · ◐ 35(21.3) · ○ 32(15.5) | 计划表逐行统计；P0 完成 17.1/33.0（52%） |

## §4 符合项（这些要保住，不要在重构里丢掉）

1. **确定性优先的运行时**：`seed` 播到 Lua 全局 RNG（E30）、帧序=深度序（E24）、
   场景导出字节确定（E22）、存档三次采集 sha256 相同（E20）。
   → 这是"引擎"最难的属性之一，Unity 项目里通常靠额外工程才能拿到。
2. **逐 tick 回放校验**：录像 → 回放 → 逐 tick 比 hash，且能挺过 `taskkill /F`（B21）。
   → 引擎级的能力，直接对应"崩溃可复现"。
3. **274 条判据 + 12 步提交闸门 + 变异验证**：判据不是"点一遍看看"，是有反向用例、
   有变异能证伪的。跨语言边界（Python↔Lua↔JS）也有判据（E32/F37/F41）。
   → 绝大多数自研引擎在第 3 年才补这块。
   ★ 其中 `F3`（6/50/400 实体绘制帧率"乐观下界 ≥55 fps"）已经把"性能可测"这件事
   起了个头——虽然它在 Node 沙箱里（无 GPU/无合成），是**下界**而非真实帧率（见 §5.7）。
4. **协议单一来源**：`protocol.schema.json` → 双侧生成 → 闸门校验一致性（v3 fix16）。
   → 这是"引擎 API 面"的正确做法，应该推广到场景/存档/HUD 字段（见 §8 Phase 0）。
5. **权威服务器 + 客户端预测 + 会话认领**：断线重连拿回同一角色（D1）、
   大误差立刻吸附（P5）、宽限期真回收（D2）。→ 多人这块比 Cocos 默认方案强。
6. **内容层是真的**：821 组件 / 1,594 prefab / 191 brain / 261 stategraph 真跑，
   而不是"接口占位"。→ 这让"玩法深度"不是问题；反过来也说明**引擎的通用性不是这张牌**。
7. **原子编辑原语**：场景导入=一步撤销（C3b）、删父摘子（C2）、存档两遍绑定+回读（E40）。
   → 这些是编辑器内核真正难的部分，已经有正确形状。
8. **失败可见化**：`ComponentErrors`/`PhysicsErrors`/`NoteStub`/`NoteGap`/`/healthz` 计数，
   并有判据读它们（E37 还带阳性对照）。→ 这一点比多数商业引擎的默认状态好。
9. **代码分层纪律**：JS 不碰 Lua、Lua 不碰网络、Python 只做编排；依赖单向。
   → 重构时唯一需要保留的"骨架"。

## §5 不足项（按层，逐条说"为什么是结构性的"）

### 5.1 平台抽象层缺失（L0）

- 渲染直接用 `gl`；音频直接用 `AudioContext`；输入直接用 DOM 事件；文件直接用 Python `open`。
- **不是"少写了几个接口"**：因为没有接口，所以"换一个平台"= 重写表现层；
  也因为没有接口，**测试只能跑在浏览器桩上**（`perf_lib.js` 里那套 DOM 桩就是这么来的）。
- 后果：跨平台、移动端、云端渲染、录制回放（离屏）全部被这一层卡住。

### 5.2 资产没有身份（L0）

- 场景引用的是 **prefab 名字符串**；贴图引用的是 **atlas 内 build 名**；没有 `.meta`、没有 GUID。
- **后果是链条式的**：不能重命名（引用会断）、不能增量导入、不能算依赖、不能分包、
  不能做"这个贴图被哪些 prefab 用"、不能做资源版本迁移。
- 这解释了一个看起来很奇怪的现象：**"保存场景"能字节确定，但"替换一张图"却要改代码**。

### 5.3 构建发布缺失（L0）

- `deploy/` 只有启停脚本。运行 = Python 3.13 + lupa + 仓库目录 + DST 资产。
- **后果**：交付对象只能是"能跑 Python 的开发者"；"开发时能跑 = 发布能跑"这个前提
  从未被验证过（既没有产物，也就没有"发布态"这回事）。

### 5.4 编辑器不是工具，是面板（L1）

- 432 行，寄生在**正在运行的世界**上：没有编辑态/运行态隔离（PIE），改坏就是改坏。
- 只有 5 个动词进撤销栈；没有资产浏览器、没有 Prefab Mode、没有多选、没有 Gizmo
  （只有"聚焦"）、没有 Profiler。
- **后果**：内容生产的主要界面不存在 → 所有内容生产都退回"写 Lua / 改文本"。

### 5.5 三层语言三套模型（结构性成本）

- 新能力要动三处：Lua（世界真相）→ Python（跨语言转换）→ JS（表现）。
- 证据：`pr`（腐烂进度）字段在 B33 里改了三处，且其中一处（`sim.py` 只挑 p/n）
  差点把新字段**静默丢掉**。
- **后果**：每个功能都付三倍成本；而"忘记改第三处"是静默的（不报错）。

### 5.6 通用性天花板：深度耦合 DST 的数据模型

- prefab / components / animstate / stategraph / TUNING / `TheWorld.state` 全是 DST 的形状。
- 这不是 bug，是**当初的定位**（跑原版脚本）。但它决定了：这个引擎**不能**变成
  "通用引擎"，只能变成"能生产 DST 式 2.5D 游戏的引擎"。
- **必须明确写进定位**，否则每次讨论"要不要支持 3D/骨骼/自定义渲染"都会跑偏。

### 5.7 单线程 lupa 的性能天花板

- 模拟 = 一个 Python 线程 + 一个 Lua VM（lupa）；30 Hz 固定 tick；无 Job/无分帧/无分区。
- 实测：206 实体 step 0.86 ms（E26）→ 单核实测余量约 38 倍，**约 2,000~5,000 实体上限**。
- **后果**：能做"小而深"的世界，不能做"大而广"的世界。
  客户端帧率**只有下界判据**（`F3` 在 Node 沙箱里量 draw 路径，无 GPU/无合成），
  真实设备帧率**没有被测量过** —— 既有对标文档也承认这一点，本文复核后仍成立。

### 5.8 无热重载 / 无脚本沙箱 / 无对外 SDK（L1）

- 改 Lua 要重启（≈4 s）；没有 `modmain` 式入口；没有对外 API 文档；没有示例工程。
- **后果**：第三方（美术/策划/外部开发者）无法参与；"引擎"的生态面为 0。

### 5.9 内容生产仍是"写代码"

- 新增一个可摆放对象 = 写 `prefab` Lua 函数并注册；新增一种交互 = 写组件。
- 与 Unity/Cocos 的"资产驱动"正好相反。这是 §5.2/§5.4 的直接后果，也是**最大的一道坎**。

### 5.10 版权与合规边界（必须在定位里写明）

- 内容层 153 万行来自 DST；`pack_atlas.py` 只解决了**贴图**的替换。
- 现实含义：**这是一套"学习/研究复刻 + 自研运行时"的组合**，不是可直接发布的商业引擎。
  任何"对外发布"的路线，都必须先回答"行为脚本从哪来"。

### 5.11 判据基座同时是资产和负债

- 274 条判据 + 12 步闸门，让重构"一动就红一片"。
- **后果**：架构重构的**表观成本**被测试放大 3~5 倍。缓解方式不是删判据，
  而是**先立接口再搬家**（§8 Phase 0），让判据守"行为"而不是守"实现位置"。

## §6 风险登记（触发条件 → 后果 → 缓解）

| # | 风险 | 触发条件 | 后果 | 缓解 |
|---|---|---|---|---|
| **R1** | 定位漂移：按"通用引擎"的期待继续加功能 | 继续做 3D/多平台/自定义渲染 | 永远做不完，且现有优势（确定性/判据）被摊薄 | **写死定位**：Web-first 2.5D 编辑器驱动；3D/主机**明确不做** |
| **R2** | 版权边界被忽略 | 打算"发布给别人玩" | 内容层不可分发；返工或法务风险 | 定位写清；发布路线必须先有"自产内容层"方案 |
| **R3** | 三层语言成本 | 每个新功能都改三处 | 边际成本 3×；"忘改第三处"静默失败 | Phase 0 的**字段单一来源**（schema 生成三侧） |
| **R4** | 重构被判据放大 | 尝试把 client.html 拆模块 | 大范围红，重构半途而废 | 先立接口再搬家；判据只改"引用路径"不改"断言" |
| **R5** | 单线程天花板 | 世界实体数上到数千 | 掉帧/卡顿，且无 Job 系统可救 | 明确"小而深"；需要时先做**分区/休眠/增量快照**（已有休眠基础） |
| **R6** | 性能结论无证据 | 有人问"多少帧" | 只能给"感觉"或给一个沙箱下界 | `F3` 已有下界判据；缺的是**真实浏览器**测量（headless Chromium + GPU）并把这些数字列进闸门 |
| **R7** | 平台路径单一 | 需要 Linux/mac/移动 | 无法交付 | Phase 2 的构建产物先做"同机可复现"，再谈跨平台 |

## §7 结论性判断

**判断一（能力）**：作为"能跑 DST 式 2.5D 游戏的运行时"，它已经是**可用的垂直切片**；
作为"Unity/Cocos 意义上的引擎"，它**还不是**——缺的是四个层，不是二十个功能。

**判断二（路径）**：现有栈（Python+Lua+浏览器）如果继续沿着"Unity 式"走，是死路
（换内核语言 + 重写表现层 + 多平台导出，单人不可达）；如果沿着"**Cocos Creator 式**"走，
是**可行且顺**的——因为客户端已经是 Web、协议已有、内容层可复用、判据基座可复用。

**判断三（价值）**：这个项目最稀缺的不是"又一个引擎"，而是**"引擎工程能力"**：
确定性、回放、274 判据、变异验证、协议单源、失败可见化。这些是**换不来**的，
而"资产管线""编辑器""构建发布"是**买得到/抄得到**的工程。

**判断四（门槛）**：我给出"可称为引擎产品"的六条硬门槛，当前 **0/6**：

| # | 硬门槛 | 现状 |
|---|---|---|
| 1 | 非开发者能在自己机器上双击运行一个 build 产物（无 Python、无源码） | ✘ 无产物 |
| 2 | 美术能替换贴图/动画而不改一行代码 | ✘ 无资产身份 |
| 3 | 新增一个可摆放对象不需要写 Lua | ✘ 内容=代码 |
| 4 | 编辑态与运行态隔离（PIE），误操作可回退 | ✘ 面板寄生运行时 |
| 5 | 有版本化资源清单 + 可回滚的增量构建 | ✘ |
| 6 | 有对外脚本 API 文档 + 示例工程（三方 1 天做出可玩原型） | ✘ |

> 这六条不是"锦上添花"，而是**"引擎"与"能跑的引擎内核"的分界线**。
> 达到 6/6，才谈得上"类似 Unity/Cocos"；达到 4/6，已经是"可用的自研引擎"。

## §8 主要改进方向

> 既有 `Unity对标审查与路线图-2026-10-21.md` 的 M1~M8 方向是对的，**本文不推翻**。
> 本文补三件它没写死的：**(a) 先做字段单一来源（否则后面每步都改三处）；
> (b) 把"六条硬门槛"变成验收闸门；(c) PIE 隔离必须早做，不能等编辑器做大再补。**

### Phase 0 · 冻结架构，立五个接口（2~3 周）

**做什么**

1. 抽出 5 个接口（**只抽接口，不改行为**）：
   `IRenderer`（draw(cmdList) / 纹理句柄 / 相机参数）、`IAudio`（play/stop/音量/总线）、
   `IPhysics`（query/move/sweep）、`IAssetDB`（resolve(guid) / list(type)）、
   `IScriptHost`（call / subscribe / 错误上报）。
2. **字段单一来源**：把"场景行 / 存档记录 / HUD item / 帧实体"四处字段表收成一份
   `data.schema.json`，生成 Lua/Python/JS 三侧（照抄 `protocol.schema.json` 的做法）。
3. 把 `client.html` 按接口切成模块（`render/`、`hud/`、`editor/`、`net/`），
   **每切一刀跑一次全量**（94+41+55），红了就回退这一刀。

**出口判据（可机器验证）**

- `grep` 同一个字段名在 Lua/Python/JS 里**只出现一次定义**（生成物除外）；
- `client.html` < 400 行（纯装配）；渲染/编辑器/HUD 各自有独立文件；
- 274 条判据全绿，**且没有一条断言被改过**（只允许改 import 路径）。

### Phase 1 · 资产管线 MVP + 编辑器能"拖"（6~8 周）

**做什么**

1. `.meta` + GUID：每个资产（贴图/atlas/anim/场景/prefab）有稳定 id；场景引用 **GUID 而非名字**。
2. Importer 注册表：PNG/atlas/anim 三个 importer 起手；产物进 `ArtifactCache`（内容 hash 命名）。
3. 依赖图 + 增量导入：改一张 PNG → 只重建受影响的 build 与 bundle。
4. 编辑器：**资产浏览器 + 拖进视口 + 选中/多选 + Gizmo（移动/旋转）+ Prefab Mode**。
5. **PIE 隔离**：编辑态世界 = 一个可回滚的快照分支；"Play" = fork，"Stop" = 丢弃。

**出口判据**

- 硬门槛 2（美术换图不改代码）✔：替换 PNG → `build` → 场景里生效，**零 Lua 改动**；
- 硬门槛 3（新增可摆放对象不写 Lua）✔：从资产浏览器拖一个新 prefab 进场景并存盘；
- 硬门槛 4（PIE）✔：Play 中改世界 → Stop → 世界**逐字节**回到 Play 前（用现有 E22 文本比）。

### Phase 2 · 构建发布（8~10 周）

**做什么**

1. 一键 build：静态客户端（含资源包）+ 服务端（打包为单文件）+ `manifest.json`（版本/内容 hash）。
2. 资源清单与版本：bundle 级 hash，可回滚；启动时校验清单。
3. 发布态与开发态分离：同一份代码，用 `--release` 切换资源来源（本地/CDN）。
4. 把 **真实客户端帧率** 接进闸门：`F3` 目前只是 Node 沙箱的下界，补一条
   **headless Chromium + 真 GPU** 的测量（同一台机器、同一份场景、可复现），
   并让 `/healthz` 上报客户端 `fps`（每 5 s 一次），给"多少帧"一个可复核的数字。

**出口判据**

- 硬门槛 1（双击运行）✔：产物目录在没有 Python 的机器上能跑（先同机验证，再谈跨平台）；
- 硬门槛 5（清单+增量）✔：改一张图 → 只有一个 bundle 的 hash 变；回滚可用。

### Phase 3 · 内容生产闭环（按需，8~12 周）

1. **可视化定义 prefab**（不写 Lua）：组件挂载 + 数值编辑 + 保存为资产。
2. 脚本 API（对外）：`World` / `Entity` / `Component` / `Event` 四类，**有文档 + 示例工程**。
3. 调试工具：帧调试器（冻结一帧看 draw list）、时间轴（tick 与事件）、内存/实体计数。

**出口判据**：硬门槛 6（三方 1 天做原型）✔。

### 明确"不做"清单（写进 README，防止漂移）

- ❌ 3D / 骨骼 / PBR / 后处理链（除非定位改成 3D，那要重开一份评估）
- ❌ 原生导出 / 主机 / 移动端原生（Web 移动端可做，原生不做）
- ❌ 自研 IDE / Shader Graph / Package Manager
- ❌ 通用 mod 平台（与现有定位冲突，收益不成比例）
- ❌ 把 Lua 换成 C#/TS（内容层 1.5M 行是最大资产，换语言=丢掉它）

### 与既有路线图的对应

| 本文 | 既有 M1~M8 | 差异 |
|---|---|---|
| Phase 0 | （无） | **新增**：接口抽象 + 字段单一来源，是后面所有阶段的降本项 |
| Phase 1 | M1 编辑器内核 + M2 资产管线 | 合并推进；**PIE 提前**（原路线图放在 M1，本文要求 Phase 1 就必须生效） |
| Phase 2 | M5 构建发布 + M3 渲染升级的一小部分 | 先要"能交付"，再要"更好看" |
| Phase 3 | M6 生态 + M3/M4 剩余 | 内容生产闭环 |
| — | M7 规模、M8 多平台 | **维持"不建议"**（与既有结论一致） |

## §10 最终回答（把话说完）

> **问**：现有架构与系统设计是否满足构建 Unity/Cocos 类引擎的要求？
>
> **答**：**作为运行时内核，基本满足（67/100），且有两个维度超过对标项（确定性与网络）。
> 作为引擎产品，不满足（20/100）——缺的是平台抽象、资产管线、构建发布、编辑器框架这四层，
> 而不是功能清单上的若干项。**
>
> **如果要继续走**：选 Web-first 2.5D（Cocos Creator 形态），按 Phase 0→1→2 推进，
> 用本文的**六条硬门槛**当验收闸门；**不要**碰 3D/原生/多平台。
>
> **如果目标必须是 Unity 式**：那要换内核语言并重写表现层，现有 32.6k 行运行时约 30% 可迁移，
> 这已经不是"改进"，是"重开"——需要先做一个明确的立项决策，而不是继续在现有结构上加功能。

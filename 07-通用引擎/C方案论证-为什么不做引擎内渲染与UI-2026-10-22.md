# C 方案论证：为什么"引擎内渲染/UI"不该做

> 被论证的方案（下称 **C**）：把表现层从浏览器搬回引擎侧 —— 即"引擎内渲染 + 引擎内 UI 绘制"，
> 使画面与原版《饥荒》同构（可直接吃 `data/anim/*.zip` 并按原版 widget 语义绘制）。
> 论证方式：先把 C 拆开（不拆会得出错结论）→ 逐项算适配成本 / 性能 / 维护 → 对定位 → 条件反转检验
> 日期：2026-10-22　结论在第 §0 与 §6，其余是依据

---

## §0 结论

**不做 C。** 三条判据（每条都能落到本仓库的证据上）：

| 判据 | 结论 | 量级 |
|---|---|---|
| **适配成本** | C 要求重建**文字/字形系统**（现在两种文字都借浏览器字体栈）、widget 布局→绘制、输入焦点、合成顺序；这些不是"移植"，是"从零再写一遍表现层" | **6~12 人月** |
| **性能** | 三条实现路径（服务端离屏 / 本地原生壳 / 同进程）**都要改变交付形态**；收益只是"更像原版"，而当前瓶颈不在画面 | 服务端离屏 ≈ 云游戏延迟；本地壳 = 多平台打包 |
| **定位** | 本项目的差异化是 **确定性 / 回放 / 274 判据 / Web 直达 / 零构建迭代**；C 直接毁掉后两条，且**不产生六条硬门槛中的任何一条** | 机会成本 = 编辑器 + 资产管线整轮（7.5 人月） |

**一句话**：C 的代价 ≈ 把"让它成为引擎的那两件事（编辑器内核 + 资产管线）"整整推后一轮，
换来的只是"画面更像原版"——而**原版画面从来不是这个项目的短板，编辑器与资产才是**。

---

## §1 先把 C 拆开：它是三个完全不同的方案

混着说"C 做不做"是没法论证的，因为三种形态的成本差 5 倍以上：

| 形态 | 做法 | 交付形态 | 最小成本 | 结论 |
|---|---|---|---|---|
| **C1 · 服务端离屏渲染** | 服务端出图，客户端只显示视频/位图 | 变成云游戏 | GPU 服务端 + 编码 + 会话扇出，**3~6 人月**起 | ✘ 对 2.5D 小游戏是负收益 |
| **C2 · 本地原生壳** | 引擎内 renderer + 原生窗口（Electron/自绘窗口），浏览器只当容器 | 变成桌面 App | 每平台 **3~6 人月**（打包/签名/驱动矩阵） | ✘ 除非"必须原生发行"，那时该放弃的是 Web-first |
| **C3 · 引擎内 UI 绘制** | 用 widget 语义自己画 UI（含文字） | UI 与原版同构 | 文字/字形/布局/焦点 **3~4 人月** | ✘ 仓库里没有任何字形系统，从零 |

**真正被推荐"不做"的是 C 整体**；但如果将来只做其中一项，**C3 是最不该做的**（见 §2.1）。

## §2 适配成本：现状是"三个表面 + 两条文字路"，C 要把它们全换成自己的

### 2.1 现在的表现层长什么样（实测）

```
#cv（2D canvas）
 ├─ 地形：drawImage(cv2 离屏瓦片图)          ← client.html:1192-1208
 ├─ 精灵：drawImage(glc)  ← WebGL 批渲染结果  ← client.html:354（合成到 2D 画布）
 ├─ 暗度：fillStyle rgba + fillRect          ← client.html:1229
 └─ 世界内标签：ctx.fillText(...)            ← client.html:1388/1393/1417/1762
#hud / #ed（DOM）
 └─ 面板文字与控件：浏览器排版 + 浏览器字体栈  ← 全部 CSS
```

- **文字有两条路，但都不是引擎自己的**：面板走 DOM（浏览器排版 + 字体栈），
  世界内标签走 `ctx.fillText`（**仍依赖浏览器字体栈**）。
  → C 一旦"引擎自己出画面"，这两条都得换成**自己的位图字体 / 字形缓存**。
  中文字形是几千个（`CJK` 常用 3,500+，全量 2 万+），这是**一个从零开始的子系统**，
  而且在 2.5D 缩放/像素对齐下还要处理 hinting 与 mipmap —— 这不是"顺手做掉"。
- **合成顺序是隐式的**：地形 → 精灵（WebGL 结果贴回 2D 画布）→ 暗度 → 标签。
  这条顺序只存在于 `client.html` 的调用次序里（`drawTerrain` → 批渲染 → `darkA` → 标签），
  **没有一层抽象**。C 要复刻它，就得先把它显式化（RenderGraph），否则两台实现的层序会漂移。

### 2.2 需要"映射"还是"重写"（逐项）

| 子系统 | 现状 | C 的做法 | 性质 |
|---|---|---|---|
| 精灵/图集/深度序 | WebGL1 单 shader（`a_pos/a_uv`），深度序由服务端排（E24） | 引擎内 GL 渲染 | **重写**（但**有一半资产**：`10_animstate.lua` 已有 `GetDrawList`） |
| 动画 draw list | 已有（`06/10_animstate.lua:14` `GetDrawList()` 返回符号+UV+变换） | 直接复用 | **可复用** ✔ |
| 地形 | 服务端发 128×128 瓦片，客户端一次性光栅成离屏图 | 引擎内瓦片渲染 | 重写（简单，1~2 周） |
| 暗度/光照 | 一层 `rgba` 覆盖 | 引擎内光照 | 重写（且要决定是否做真光照） |
| 文字 | DOM + `fillText` | 位图字体 + 字形缓存 | **从零**（CJK 是硬骨头） |
| UI 控件 | DOM（按钮/输入框/文本域/下拉框） | widget 绘制 + 命中测试 + 输入法 | **从零**（IME/光标/选区是最难的部分） |
| 输入 | DOM 事件 + 指针事件 | 引擎窗口输入 + 焦点模型 | 重写（含"谁有焦点"） |
| 音频 | WebAudio 程序合成（235 行） | 引擎音频 | 重写（且我们没有音频资产） |

**9 项里只有 1 项可直接复用。** 这就是"适配"的真实含义：不是把现有代码挪个地方，
而是**再实现一遍**，而且要与现有那一遍**行为等价**（否则两套画面不一致，用户立刻看出来）。

### 2.3 一个具体的成本样本：中文

`client.html` 里 6 处 `fillText` 画的都是**中文标签**（"动作"、实体名、编辑器标签）。
换到引擎内绘制，最小的可行方案也要：

1. 字体文件 → 图集（含 CJK 子集化，否则 20 MB 字体）；
2. 字形缓存 + LRU + 按需上传纹理；
3. 排版（断行、对齐、字号缩放）；
4. 输入法（中文输入：候选窗、组合串、光标）—— 如果 UI 要可编辑文本的话。

**这一条本身就是 1~2 人月**，而它产出的东西和浏览器现成的排版比，**更差**。

### 2.4 反过来的账：把 Web-first 拉成"标准引擎"要付哪些适配成本

这一节回答"Web-first 与标准引擎之间的适配成本"——它其实是 **C 的隐含成本**：
C 一旦成立，就等于承诺"这套东西要能当标准引擎用"，于是下面每一项都要补。

| 维度 | Web-first 现状 | 标准引擎要求 | 适配成本 |
|---|---|---|---|
| 渲染 | WebGL1 + 单 shader | RHI 抽象 + 多后端（D3D/Metal/Vulkan/GL/WebGPU） | **每后端 ~3 人月**，且抽象层先要 1~2 |
| 线程/内存 | 单线程 + JS GC（服务端 Python 单线程） | Job 系统 + 可控内存 + 无 GC 峰值 | 需 wasm/worker 或原生内核，**重写级** |
| 文件/IO | 浏览器沙箱 + 静态资源 | 原生 FS + 增量包 + 热更新 | 1~2 人月 |
| 输入 | DOM 事件 + 指针 | 原生输入 + 手柄 + 焦点/IME | 与 §2.2 的输入项重叠，1~2 人月 |
| 音频 | WebAudio（程序合成） | 原生混音 + 3D + 总线 | 1~2 人月 |
| 分发 | 发链接 | 安装包/签名/商店/自动更新 | 3~6 人月（每平台） |
| 调试 | DevTools + `/healthz` | 原生 profiler / 帧调试器 | 2~3 人月 |

**合计：把 Web-first 拉成"能当标准引擎用"，是一个 15~25 人月的工程**（不含内容与工具链）。
C 只是这张表里的**第一行**。所以"C 要不要做"从来不是"加个渲染器"的问题，
而是"要不要用 15~25 人月换赛道"的问题。

## §3 性能：三条路径都要付"交付形态"的代价

### 3.1 先看现在的性能余量（实测，不是估计）

- 服务端：206 实体 `step` = **0.86 ms**（E26），30 Hz 预算 **33 ms** ⇒ 余量约 38 倍；
- 客户端：`F3`（6/50/400 实体）在 Node 沙箱里量 draw 路径，**乐观下界 ≥55 fps**（这是下界，不是真机）。

**结论**：**性能不是当前的瓶颈**。既然如此，任何"为了性能而搬渲染"的论证都不成立；
C 只能靠"画面一致性"来立论，而那是 §5 的定位问题。

### 3.2 C1（服务端离屏）的账

估算（**公式给出，不是实测**）：400 个精灵 × 1 quad × 4 顶点 × (2 pos + 2 uv) × 4 B = **25.6 KB/帧**，
30 Hz ⇒ **≈ 750 KB/s/客户端**，加标签与 UI 后 ≈ 1 MB/s。
这比现在的"二进制实体状态帧"高一个量级；再叠上编码与网络抖动 ⇒ **输入到画面的延迟**从"本机 1 帧"
变成"云游戏级"。对 2.5D 小游戏，这是纯亏。

### 3.3 C2（本地原生壳）的账

- 要解决：打包、签名、自动更新、每平台 GPU 驱动矩阵、崩溃上报 —— 这些正是
  **"构建发布 = L0"** 的那个洞（上一份审查 §5.3），C2 会把洞撕得更大；
- 代价：**丢掉"发个链接就能玩"**，这是本项目唯一的分发优势；
- 收益：画面与原版一致 —— 但只有"原版复刻"这个目标才需要它。

### 3.4 C3（同进程渲染）的账

- 服务端进程要 GPU 上下文 ⇒ 无头服务器（CI、容器）没有；判据（274 条）全都跑在无 GPU 环境，
  **C3 会立刻制造"判据跑不了"的问题**；
- 或者渲染回客户端 —— 那就不是"引擎内"，而是 C2。

**三条路径，没有一条能在"不改交付形态"的前提下成立。**

## §4 维护负担：双表现栈 = 2× 实现 + 2× 判据 + 一套新的基础设施

| 项 | 现在 | 做 C 之后 |
|---|---|---|
| 表现实现 | 1 套（`#cv` + `glc` + DOM，约 2,900 行） | **2 套**（浏览器 + 引擎内），且必须**行为等价** |
| 判据 | 41 条客户端判据（Node + DOM 桩） | 引擎内渲染需要**另一套**判据（离屏 GL / golden image） |
| 视觉回归 | 无（靠数值断言） | golden image 对比 —— **业界公认易 flaky**（字体/驱动/抗锯齿差异），且要维护基线图 |
| 每加一个表现特性 | 改 1 处 + 1 条判据 | 改 2 处 + 2 条判据 + 1 张基线图 |
| 缺陷面 | 1 套 | 2 套，且"只在一套上复现"的 bug 最难查 |

274 条判据已经把"重构成本"放大过一轮（上一份审查 §5.11）。**再加一套表现栈，等于把这个放大系数乘 2。**

## §5 定位契合度：C 毁掉的是差异化，换来的是"更像原版"

本项目的差异化（上一份审查 §4）：

1. 确定性 tick + 逐 tick 回放；
2. 274 条判据 + 闸门 + 变异验证；
3. 协议单一来源；
4. **Web 直达**（发链接即玩，零安装）；
5. **零构建迭代**（改完刷新，没有编译期）。

C 与 4、5 直接冲突：

| 差异化 | C 的影响 |
|---|---|
| Web 直达 | C2/C1 之后不再是"发链接"；C3 让判据跑不了 |
| 零构建迭代 | 引擎内渲染 = 原生构建，改一行要编译（秒级变分钟级） |
| 判据基座 | 新表现栈要新基础设施，且**无法在无 GPU 环境跑** |
| 确定性/回放 | 不受影响（但也不受益） |

而且 C **不解决当前真正的瓶颈**：

- 编辑器 = L1（432 行面板，寄生在运行中世界）；
- 资产管线 = L1（无 `.meta`/GUID/importer）；
- 构建发布 = L0。

**六条硬门槛（上一份审查 §7）里，C 能推进 0 条。** 它推进的是一条"画面一致性"，
而这条不在门槛清单里 —— 因为它是"复刻器"的目标，不是"引擎"的目标。

## §6 条件反转检验：如果目标是"标准引擎"呢？

用户的问题里有一个必须正面回答的条件句。我的回答分两半：

### 6.1 Web-first 对"标准引擎"是不是最优？——**不是最优，是"受限最优"**

- 在 Unity/Cocos 的口径下（多后端、原生壳、多平台发行），Web-first **不是最优**：
  标准引擎的标配是 RHI（D3D/Metal/Vulkan/GL/WebGPU）+ 原生平台服务 + 主机/移动工具链，
  浏览器只是其中一个后端。
- Web-first 只在**一组约束**下才是最优：单人/小队、2.5D、内容层已存在、需要浏览器分发、
  需要零构建迭代。**这组约束恰好就是本项目的现状。**
- 反例要说清：**Cocos Creator 是 Web-first，同时是标准引擎** —— 但它做成 C 的方式是
  **"替换 + 多后端（GFX）+ 原生壳（JSB）"**，是年级别的工程，不是"在 Web 上叠一层"。
  ⇒ 它的存在恰恰证明：**C 是替换，不是叠加。**

### 6.2 那么该放弃的是什么？——**放弃"Web-first 上叠加 C"这个方案**

这是本文的核心判断，写成一句可引用的话：

> **渲染所有权只能有一个。** 要么浏览器（Web-first），要么引擎（C）。
> **两者同时存在 = 两条表现栈都要维护，且都不完整**（UI 仍走 DOM 就不算 C；UI 也重写就不是叠加而是替换）。

于是：

- **若保留 Web-first 为主路径**（本文推荐）⇒ **放弃 C**，并把"能直接吃原版 resources 且画面一致"
  从目标里删掉。这是自洽的。
- **若目标是标准引擎** ⇒ Web-first 不是最优 ⇒ **放弃的应该是"Web-first 作为主路径"**，
  把 WebGL/WebGPU 降级为**一个后端**，另建 RHI + 原生壳 + 构建发布。
  此时 C 不再是一个"要不要做的附加项"，而是**新赛道的地基**——它会自然发生（被替换，而不是被叠加）。
- **唯一不成立的是第三种**：既保 Web-first 为主路径，又做 C。那不是"两条腿走路"，
  是**两条腿各走一边**：交付承诺翻倍、维护翻倍、定位模糊，而且最终一定有一边荒废。

**所以"建议不做 C"这个结论的准确表述是**：在"锁定 Web-first 为主路径"的前提下不做 C；
**若前提翻转，结论翻转的对象是赛道，不是叠加层。** 两者都自洽，中间态不自洽。

## §7 成本量化：C 换掉了什么

| 项 | 人月 | 说明 |
|---|---|---|
| C2 本地原生壳（1 个平台） | 3~6 | 打包/签名/驱动/崩溃上报 |
| C3 文字 + UI 绘制（含 CJK） | 3~4 | 字形缓存/排版/IME |
| 2D 精灵渲染 + 图集 + 深度 | 1~2 | 有 `GetDrawList` 可复用，成本最低的一项 |
| 多后端（每个额外后端） | 3 | 若要"标准引擎" |
| 视觉回归基础设施 | 1~2 | golden image + 基线维护 |
| **最小可行合计** | **6~12** | 不含多后端 |

对照**同一份计划里真正的瓶颈**：

| 真正能推进门槛的项 | 人月 |
|---|---|
| M1 编辑器内核 v2 | 4.0 |
| M2 资产管线 | 3.5 |
| **合计** | **7.5** |

**即：C 的最小成本 ≈ 编辑器 + 资产管线整轮。** 而后者能把六条硬门槛从 0/6 推到 3/6，
C 把它推到 0/6（一条都不推进）。

## §8 什么情况下应该重启这个评估（5 条可观测条件）

不做 C 不是永久决定，但**重启需要触发条件**，否则会每季度重开一次讨论：

1. **要原生发行**：出现"必须在 Steam/主机/移动原生上架"的硬需求；
2. **要 3D/骨骼**：现有 2.5D 精灵栈无法表达（这条同时会推翻 Web-first 的定位）；
3. **客户要求像素级复刻原版 UI**（不是"像"，是"逐像素一致"）；
4. **团队 ≥3 人且有图形工程师**：否则 C 会拖死主线；
5. **Web 端触达不再是需求**（比如产品形态变成"卖引擎授权"而不是"卖游戏/工具"）。

任一条成立 ⇒ 按 §6.2 走"换赛道"，**不是**"加一层"。

---

## §9 结论复述

1. **不做 C**（引擎内渲染/UI）。三理由：适配成本 6~12 人月且只有 1/9 子系统可复用；
   三条实现路径都要改交付形态而性能本就不是瓶颈；它毁掉 Web 直达与零构建迭代这两条差异化，
   且推进六条硬门槛 **0 条**。
2. **C3（引擎内 UI）最不该做**：仓库里没有任何字形系统，中文 IME 更难，产出还不如浏览器排版。
3. **"不做 C"成立的前提是"Web-first 是主路径"**。若目标是标准引擎，Web-first 不是最优，
   此时该放弃的是 **Web-first 作为主路径**（把 Web 后端化），而不是在 Web 上叠 C。
4. **唯一必须禁止的是 hybrid**：Web-first + 引擎内渲染并存 = 两条表现栈、双倍维护、
   交付承诺翻倍、定位模糊。渲染所有权只能有一个。

# 原版饥荒引擎是怎么实现的，以及"靠拢"该靠哪一层

> 依据：`02-注释源码`（1,534,360 行 Lua，含 `update.lua` / `entityscript.lua` / `mainfunctions.lua`）、  
> `06-引擎复刻/host`（46,099 行，逆向出的引擎层）、`ZipAnim解析报告` / `AnimState接入报告` / `UI层修复报告`  
> 日期：2026-10-22　口径：**只写能在仓库里指到文件:行的结论**，不写"大概是这样"



---

## §0 一句话结论

原版《饥荒》= **一个 C++ 引擎**（`TheSim` / `TheNet` / `TheFrontEnd` / `AnimState` / 私有资产格式）  
**+ 153 万行 Lua 游戏层**，两者在**同一个进程**里，Lua 每帧被引擎回调一次 `Update(dt)`。

它的价值**不在 C++ 这门语言**，而在四个语义：

| # | 语义                                                                 | 为什么值钱                       |
| - | ------------------------------------------------------------------ | --------------------------- |
| 1 | **双时间基的 tick 泵**（组件用 `dt`，状态图/大脑/调度器用 **tick 编号**）                 | 让"跳时间/追帧/回放"成为可能，而不是靠 dt 累加 |
| 2 | **休眠 + 延迟停**（`IsAsleep` 摘除更新、`StopUpdatingComponent_Deferred`）     | 上万实体能跑得动，且不会在遍历中改表          |
| 3 | **复制分层**（`netvars` 脏标记 / `classified` 旁观者状态 / `replica` 客户端镜像）     | 服务端权威 + 客户端表现分离，且**只发变化**   |
| 4 | **资产格式**（`atlas-N.tex` KTEX + `build.bin` + `anim.bin`，3522 个 zip） | 动画是数据驱动的，不是代码驱动的            |

**我们已经复刻了第 1、2 项的"游戏层"部分**（因为跑的就是同一份 Lua），  
**没复刻的是引擎层语义**。所以"靠拢"的正确做法是：**补语义，不换语言**。

## §1 原版的两层：谁在干什么（有证据）

### 1.1 分工表

> **一句话读法**：原版的 C++ 提供"世界的物理与呈现器官"，Lua 提供"世界的规则与内容"。  
> 我们现在的 `host/` 是**用 Lua 冒充这些器官**（46k 行），`rt/` 是**用浏览器冒充呈现**。

### 1.2 原版每帧泵的确切顺序（`update.lua:231-305`，逐行抄出）

```
Update(dt):
  ① HandleClassInstanceTracking()  CheckDemoTimeout()
  ② assert(not TheNet:IsServerPaused())          ← 暂停是**服务端状态**，不是客户端开关
  ③ tick = TheSim:GetTick()
     if tick <= last_tick_seen then return end   ← **幂等保护**（"Saw this before"）
  ④ for i = last_tick_seen+1 .. tick: RunScheduler(i)      ← 协程调度，按 **tick 编号**
  ⑤ if SimShuttingDown then return end
  ⑥ StaticComponentUpdates[k](dt)                          ← 静态组件，**每帧一次**（与实体数无关）
  ⑦ for ent in UpdatingEnts:
        for cmp in ent.updatecomponents:
            if cmp.OnUpdate and not StopUpdatingComponents[cmp] then cmp:OnUpdate(dt)   ← 用 **dt**
  ⑧ NewUpdatingEnts → UpdatingEnts 合并；StopUpdatingComponents → StopUpdatingComponent_Deferred
  ⑨ for i = last_tick_seen+1 .. tick: SGManager:Update(i); BrainManager:Update(i)   ← 按 **tick 编号**
  ⑩ last_tick_seen = tick
```

**四点设计意图**（读代码能看出来的，不是猜的）：

1. **双时间基**：组件吃 `dt`（跟真实帧率），状态图/大脑/协程吃 `tick`（跟逻辑拍）。  
   → 于是"一次跳 600 秒"可以用 `LongUpdate` 一次性结算，而不用跑 18,000 次 `OnUpdate`。
2. **幂等保护**（③）：同一 tick 被回调两次直接返回。这是引擎回调频率与逻辑拍解耦后的安全阀。
3. **延迟停**（⑧）：`StopUpdatingComponent` 在 `OnUpdate` 里被调用时**不能立刻改表**（正在遍历），  
   于是记进 `StopUpdatingComponents`，本拍末尾统一处理 —— 这就是我们缺的那条。
4. **静态组件**（⑥）：不挂在实体上、全工程只有几份的更新（如 `ambientlighting` 的世界级计时），  
   每帧跑一次，不随实体数增长。

### 1.3 `LongUpdate` 是"跳时间"的唯一正门

```lua
function LongUpdate(dt, ignore_player)          -- update.lua:308
    for k, v in pairs(StaticComponentLongUpdates) do v(dt) end
    ...  遍历实体，对每个组件调 v:LongUpdate(dt)     -- 不是 N 次 OnUpdate
```

用途（原版注释写明）：**跳过夜晚、从洞穴回来、离线时间的补偿**。  
它是"世界时间可以跳"的能力基础 —— 也是**读档时间快进**该走的门。

## §3 向原版靠拢：分三层，先做 A

> 原则：**靠拢的是语义，不是语言。** 原版是 C++ 不代表我们要写 C++；  
> 它是"同一进程、引擎管器官、Lua 管规则"，这一点我们已经在结构上做到了（Python 当代替品）。

### A 层 · 语义对齐（不换技术栈，1~2 周，可判据化）

这 4 条都能写成机器判据，且**每条都对应一个"现在会静默错"的场景**。

> ★ 原本还有第 5 条"A5 暂停要是服务端状态"，**复核后删掉**：  
> 我们已经是了 —— `hub.is_paused()` 是服务端状态，且 `loops.py:501-521` 在暂停时  
> **不调 `sim.step()`**（只是按 ~10 Hz 继续发帧，并在帧里如实标 `paused: true`）。  
> 这条与 `update.lua:238` 的 `assert(not TheNet:IsServerPaused())` 语义一致。

| #      | 动作                                                                          | 为什么现在会错                                                                    | 建议判据                                                                                                |
| ------ | --------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **A1** | 把 `Step()` 改成 `Update(dt)` 入口：tick 去重 + 按 tick **追帧**（`for i=last+1..tick`） | 现在 `TheSim.tick += 1` 后就跑一次；若将来做跳时间/暂停恢复，调度器与 SG/Brain 会**漏拍**（丢事件、AI 卡一拍） | `E42` 一次 `Update` 只推进一个 tick 且 `RunScheduler` 收到恰好下一拍；`E43` 手工把 tick 跳 +3 ⇒ 调度器/SG/Brain 各跑 **3** 次 |
| **A2** | 补 `StopUpdatingComponent_Deferred` 的真语义（记进集合、本拍末尾统一停）                       | 现在"立即停"在 `OnUpdate` 里调用会**改正在遍历的表**；当前靠"先取快照"绕过，但语义不等价（本拍剩下的组件仍会跑）         | `E44` 在 `OnUpdate` 里 `Stop` 自己 ⇒ 本拍**跑完**、下一拍**不跑**；且不会漏跑同实体其它组件                                    |
| **A3** | 补 `StaticComponentUpdates`（全局注册表 + 每帧一次）                                    | 现在世界级更新只能挂在某个实体上，随实体休眠而**停更**（E37 里 `clock.lua` 就是这类）                      | `E45` 注册一个静态更新 ⇒ 每帧恰好 1 次，且**与实体数无关**；实体全休眠时仍跑                                                      |
| **A4** | 实现 `LongUpdate(dt)`（组件走 `LongUpdate`、不走 N 次 `OnUpdate`）                     | 现在跳时间是 no-op ⇒ 跳过的时段里**腐烂不推进、计时器不结算**（E36 的腐烂、G3 的计时器都会漏）                  | `E46` 跳 600 s ⇒ `OnUpdate` 0 次、`LongUpdate` 1 次，且腐烂/计时按 600 s 结算                                    |

> A1~A4 做完（暂停已天然对齐），就可以对外说一句准确的话：**"tick 语义与原版同构"**。  
> 这比"我们又加了多少功能"值钱得多，因为它是**后续所有能力的地基**。

### B 层 · 结构对齐（1~2 月）

| #      | 动作                                                                                                                                                            | 收益                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **B1** | 把 `host/` 里"冒充引擎"的能力收成 **5 个 C 边界接口**：`ISimQuery`（FindEntities/光照/温度/时间）、`INet`（netvars/classified/RPC）、`IAnim`（state → draw list）、`IAudio`、`IPersist`（存档 IO） | Lua 侧只剩游戏规则（与原版同构）；接口后面可以换实现（Lua→C/Rust/WASM）而不动游戏层 |
| **B2** | `classified` 的**生命周期**对齐：跟随父实体创建/销毁、只在"有人看"时同步                                                                                                                | 现在 classified 是开机造一批；原版是按需。这条直接影响多人与流量              |
| **B3** | 休眠语义补全：入睡时从 `UpdatingEnts` **摘除**、`StartUpdatingComponent` 在 awake 时才注册                                                                                       | 现在靠"每拍查 `IsAsleep`"过滤，是 O(n) 检查；原版是 O(1) 不在表里       |

### C 层 · 表现层对齐（3~6 月，**建议不做**）

原版的渲染、UI 绘制、光照、shader 全在引擎侧。要对齐只有两条路：

- **C1**：把渲染搬回"引擎侧"（本地原生进程 / 服务端离屏）→ 与 Web-first 定位冲突，且要重写全部表现层；
- **C2**：复刻 `widgets/` 的绘制语义（Lua 布局 + 引擎画）→ 能在浏览器里跑，但要自己实现一整套 widget 渲染器。

**结论**：C 层只在"目标改成『能直接吃原版 `resources.zip` 并保证画面一致』"时才值得做；  
否则做到 B 层就够，剩下的用 Web 表现层替代（并**明确写进定位**）。

## §4 明确**不要**抄的部分（负面对标）

| 原版做法                                                 | 为什么不抄                                                           |
| ---------------------------------------------------- | --------------------------------------------------------------- |
| 私有资产格式（KTEX/DXT5/私有 `build.bin`/`anim.bin`）当**对外格式** | 我们已解码（`ZipAnim解析报告.md`），但对外应转 **PNG + JSON**；否则任何美术工具都进不来       |

## §6 靠拢到什么程度算"够"？（三档目标，别混）

| 档        | 含义                                                 | 需要               | 建议                   |
| -------- | -------------------------------------------------- | ---------------- | -------------------- |
| **语义级**  | tick/休眠/复制/存档的**行为**与原版同构，但实现是自己的                  | A 层（6~8 周）       | **推荐做到这里**           |
| **结构级**  | 引擎与游戏层的**边界**与原版同构（Lua 只写规则）                       | A + B（2~3 月）     | **推荐做到这里**           |
| **二进制级** | 能直接吃原版 `data/anim/*.zip` + `scripts.zip` 且**画面一致** | A + B + C（6~9 月） | **不建议**（除非目标改成"复刻器"） |

三档的差别不在"工作量"，而在**你要不要保留"自己的表现层"**：

- 语义级 / 结构级：表现层是**我们的**（Web），原版只提供**语义参照**；
- 二进制级：表现层必须**也是原版的**（引擎内渲染 + widget 绘制），Web-first 定位随之作废。

## §7 结论

1. **原版引擎的骨架不是"很多 C++ 类"，而是四个语义**：双时间基 tick 泵、休眠与延迟停、  
   复制分层、资产格式。前三个我们已经复刻了一半，缺的正好是"引擎侧那一半"。
2. **我们与它的最大结构差异不在语言**，而在"器官归属"：原版引擎管世界与呈现，Lua 管规则；  
   我们现在是 **Lua 冒充器官 + 浏览器冒充呈现**。`host/` 的 46k 行就是这个"冒充"的证据。
3. **靠拢的正确顺序是 A→B，不是换语言**。A 层 6~8 周就能拿到"tick 语义与原版同构"这句  
   可以写进文档、也能被判据验证的话；而这 4 条恰好覆盖了现在会**静默错**的 4 个场景

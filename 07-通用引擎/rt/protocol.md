# rt 线协议（P1 定 / P5 增补二进制版）

> 目标：**省带宽**。JSON 版好调试，二进制版省流量；两者**语义必须一致**
> （同一份快照，两种编码解出来的对象要逐字段相同 —— 这条有测试守着）。

## 1. 传输层

- HTTP + WebSocket **同端口**（默认 8765）。

HTTP 侧除静态文件外有三个接口：

| 路径 | 内容 |
|---|---|
| `GET /status` | 人看的状态页（tick / 实体数 / **昼夜·季节·温度** / 世界组件 5/5 / **模型版本** / **玩家存活+血量 · 各玩家槽位 · 复活次数 · 光源（火）**） |
| `GET /healthz` | JSON：`{ok, stats, world, clients, player_count, dropped_bad_frames, frames_sent}`；`stats.boot` = **模型版本**（如 `rt_boot/7`，与 `rt_boot.lua` 的字面量逐字一致，由 B6 核对）。★ `stats.players[<槽位>]` 现含 `alive` / `health` / `guid` / **`in_light`** / **`light_r`**（P38）/ **`hunger`** / **`sanity`**（P39）；另有 `stats.player_light` = 开着随身光源的槽位数。⚠️ 顶层那个是**在线人数**（int），按槽位的表在 `stats.players` —— 它以前也叫 `players`，同一个 JSON 里两个同名不同物的字段（P39 的判据就是照直觉写错了一次），现已改名 `player_count` |
| `GET /respawn?slot=N` | 请求复活某个槽位的玩家（与 `/pause` 同族的「从外部控制世界」入口）。⚠️ 只是**请求**：真正复活在模拟线程里做，结果看 `/healthz` 的 `player_alive`/`respawns` |
| `GET /debug/kill?slot=N` | **调试击杀**（把该槽位玩家血量扣光）。⚠️ **默认不存在**，必须 `--allow-debug`；返回 404 就是没开 |
| `GET /save` | **立即存档**（P37）。入队给模拟线程，**写完才回 200**（`{ok, n, sz, path}`）——与 `/pause` `/respawn` 同族的「从外部控制世界」，但它是**同步**的。`stop.sh` 在 `taskkill //F`（硬杀）之前先请求它，所以不会丢最后 30 s（含刚认领的会话身份）。⚠️ 服务端没带 `--save-file` 时回 500 + `error` |
| `GET /light?slot=N&r=R` | 给某个槽位开/关**随身光源**（P38，07 侧的**代理**）。`r=0` / 缺省 = 关。**异步**入队（下一次光照同步 ≤0.3 s 生效）；结果看 `/healthz` 的 `players[slot].in_light`。⚠️ 原版靠火把的 `light` 组件，本宿主的 `torch`/`lantern` **没有**该组件 ⇒ 只能这样代理；**默认关** |
| `GET /terrain` | **地形瓦片表**（开局拉一次）：`{w,h,tile,tiles[],names{}}`；`tiles` 是扁平数组（索引 `cy*w+cx`），`names` 是 `瓦片id → 地形名` |

> `/terrain` 走的是 JSON 而不是二进制帧协议：**它不在帧流里**，一次性、可缓存
> （`Cache-Control: max-age=3600`），而且人应该能直接打开看。
> 128×128 = 16384 个瓦片 ≈ 40 KB。**地形不变，所以只发一次**；
> 真要每帧发是 ≈1.2 MB/s（见 `开发计划.md` §9l.2 的取舍表）。
- 客户端→服务端：JSON 文本帧 `{"k":"right","v":1}`（也支持 `{"keys":{...}}`）。
  未知字段**忽略不崩**（前向兼容）。
  ⚠️ 每条输入都**归因到发起它的连接**（槽位）：4 个客户端 = 4 个角色，
  谁按的键只动谁的角色（判据：`tests/test_rt.py` 的 `B26`、`test_stress.py` 的 `C5`）。
  ★ **`k` 只有四个值**：`up` / `down` / `left` / `right`（斜向 = 两个键同按，引擎按 45° 归一）。
  **触屏（P23）没有新增任何协议**：摇杆按下时算出的方向**走的就是这四个键**，
  与键盘发出的帧除 `seq` 外逐字节相同（判据：`F20`）——
  面板只调客户端里那个唯一的 `setKey()`，不自己发帧。
- **控制指令**走另一条路：`{"cmd":"pause","v":1|0}`、`{"cmd":"ping","v":序号}`、
  `{"cmd":"whoami"}`、`{"cmd":"targets"}`、`{"cmd":"me"}`、`{"cmd":"act","v":实体guid}`、`{"cmd":"unact"}`。
  ⚠️ 不能塞进 `k` 那条路 —— `k` 会被**原样**当成输入键名进输入层，于是 `cmd` 会变成一个
  叫 `"cmd"` 的按键（不报错，但 `TheInput` 里会多出个怪键名，查起来很费劲）。
  未知 `cmd` **计数并打印**，不静默。
- **「我是谁」是客户端主动问的**（拉取，不是推送）：
  客户端连上发 `{"cmd":"whoami"}` → 服务端回 `{"you":<实体guid>|null,"slot":n}`。
  `null` 表示「这个连接的角色还在建（它在模拟线程里异步生成）」，客户端**退避重试**。
  ★ 为什么是拉取：早先是**推送**（模拟线程投递、处理线程取走发送），
  实测在负载下（4 客户端 + 646 实体）处理线程会被 GIL 饿到，`you` 有时十几秒都发不出去 ——
  而客户端没有它就不知道自己是谁。**拉取把时序依赖彻底去掉了。**
- 服务端→客户端：默认 **JSON 文本帧**；带 `?bin=1` 连 `/ws` 时改发**二进制帧**。
  ⚠️ **二进制模式下控制消息（whoami 应答 / pong）仍然是文本帧**（客户端按 JSON 解），
  只有**快照**是二进制 ⇒ 任何「读下一条消息就当快照」的实现都必须**跳过控制消息**。

- **交互（P22）**：`{"cmd":"targets"}` → 服务端回
  `{"targets":[{"id":…,"p":…,"x":…,"z":…,"a":"CHOP"},…],"last_act":{…}}`
  （**按距离升序**，最多 12 个；`a` 是**引擎自己声明的动作名**，不是客户端猜的）。
  `{"cmd":"act","v":<guid>}` → 对该目标做它的动作（太远则**先走过去**）；
  `{"cmd":"unact"}` → 取消「一直做」。
  ⚠️ 这三个也是**控制消息**（不是快照）—— 同样必须跳过，不能当帧用。
  ★ **「选中哪个目标」由客户端决定**（点击/点按屏幕上的某个目标 ⇒ 按 **guid** 记住它），
     服务端只认 `v` 里的 guid ⇒ **协议没有因此变化**。列表每 0.5 s 刷一次，
     选中要**按 guid 保持**（按下标保持会在列表变化时指到别的东西上）；
     目标消失才退回最近的那个。（判据：`F29`。）
  ★★ **`act` 的语义（2026-10-16 量清）**：它把动作**压进** locomotor 一次，
     而**一次 push 只等于一次敲击**（实测：只 push 一次 ⇒ `workleft` 15→14 就停住）。
     真正的「连砍」由**服务端**按固定节拍（`ACT_REPEAT` = 30 拍 = 1 s）**重复 push** 提供。
     ⇒ 客户端**只需要在按下时发一条** `act`，**不要自己重发**：
       每条 `act` 都会把服务端的下一拍**重置为「立刻」**，两个节拍**叠加**、
       多出那些 push 是在上一记还没落地时打的。实测（玩家钉成不死，各 3 遍，砍一棵 15 点的树）：
         · 客户端每 0.7 s 重发 + 服务端 1 s 节拍 ⇒ **21 s / 30 次 push**（0.5 点/次）
         · 只让服务端按 1 s 节拍（客户端只发一次）⇒ **15 s / 15 次 push**（1.0 点/次）
       （判据：`F18` 按住 3 s 仍只发 1 条；`E2` 一次 act 必须能砍倒并掉出 `log`。）

- **自身状态（P39）**：`{"cmd":"me"}` → 服务端回
  `{"me":{"ok":true,"slot":n,"health":…,"maxhealth":…,"hunger":…,"maxhunger":…,
  "sanity":…,"maxsanity":…,"items":[{"p":"log","n":2},…],"total":n}}`。
  `items` 按 prefab **聚合**、按数量**降序**（同数量按名字，保证顺序稳定）；
  `total` 是件数总和。槽位不存在 ⇒ `{"ok":false,"why":"…"}`，**不带**一串 0
  （0 血会被读成「快死了」，而事实是「这个人不存在」）。
  ⚠️ 也是**控制消息**，客户端必须先判 `me` 再决定要不要当快照 —— 否则画面会空一帧。
  ★ 与 `targets` **同一种模式**（客户端定时**拉取**，服务端不推送），
    同节拍（`actPoll` 里 0.5 s 一次）。为什么不用推送：见 §1 「我是谁」那段，
    推送在负载下会被 GIL 饿到。
  ★ 服务端在**模拟线程**里按节拍算这张表 ⇒ 刚连上可能回 `{"ok":false,"why":"还没算出来（稍后再问）"}`，
    客户端重问即可（判据 `E10` 就是「问到 ok 为止」）。
  ★ 判据：`E10`（进程内四段 + 跨进程与 `/healthz` 对账）、`F32`（上屏文案 / 缺数据显示 `—` / 不染 NaN / 0.5 s 只发一条）。

## 2. JSON 帧（v1）

```json
{"t":3.0,"tick":90,"n":6,"iseq":42,
 "ents":[{"id":4,"x":11.8,"z":0.0,"p":"wilson","a":"walk","bld":"wilson","fr":2,"f":0.0}],
 "player":{"id":4,"x":11.8,"z":0.0},
 "world":{"phase":"day","season":"autumn","isday":true,"isdusk":false,"isnight":false,
          "temperature":22}}
```

| 字段 | 含义 |
|---|---|
| `t` | 世界时间（秒，float） |
| `tick` | 已推进 tick 数 |
| `n` | 本帧实体数 |
| `iseq` | 输入序号（客户端可用于判断「我的输入被吃到了没」） |
| `ents[]` | `id` guid · `x/z` 世界坐标 · `p` prefab · `a` 动画名 · `bld` build 名 · `fr` 帧号 · `f` 朝向角 |
| `player` | 玩家实体的 id/x/z（没有玩家时为缺省） |
| `world` | **世界环境**（v3 新增）：`phase` 昼夜相位 · `season` 季节 · `isday/isdusk/isnight` 三态布尔 · `temperature` 温度（℃）。可能整个字段缺失（世界组件尚未就绪），客户端必须能兜底 |

> `world` 的值**全部来自 `TheWorld.state`** —— 那是原版 worldstate 组件对
> clock / seasons / worldtemperature 的 netvar 的实时镜像，不是宿主硬编码。
> 所以「同一局里它随时间变化」本身就证明世界组件在跑。

## 3. 二进制帧（v3，P5 建 / 世界环境块 v3 追加）

布局（一切整数小端；变长用 LEB128）：

```
偏移  长度   内容
0     2      魔数 'R''T'（0x52 0x54）
2     1      版本 = 3
3     1      标志位：bit0=含 player，bit1=含 ents，bit2=含 world，bit3=**世界已暂停**
4     varint tick
      float32 t
      varint n
      varint iseq
      varint dict_len           —— 本帧新增的字符串（prefab/anim/build）
      [dict_len × (varint len + bytes)]
      varint player_id          （仅 bit0）
      int16 player_x            （1/16 格为单位）
      int16 player_z
      [n × 实体]：
         varint id              （delta 编码：首个子从 0 起，后续为差值）
         int16  x               （1/16 格）
         int16  z
         varint p_idx           （字符串字典索引；0 = 空）
         varint a_idx
         varint bld_idx
         varint fr
         int16  f               （朝向角，1/16 度）
      [世界环境块]             （仅 bit2，**帧尾**）：
         uint8  phase           （0=day 1=dusk 2=night，255=未知）
         uint8  season          （0=autumn 1=winter 2=spring 3=summer，255=未知）
         uint8  昼夜三态位       （bit0=isday bit1=isdusk bit2=isnight）
         int16  temperature     （℃ × 16）
```

> ★ **世界环境块为什么放帧尾**：这是**追加**式改动，前面每个字段的偏移一个都不动。
>
> ★ 帧里的 `player` 字段仍然只表示**槽位 0**（开机那个默认角色），它是**向后兼容**用的；
>   「我」是谁要看 `whoami` 的应答（§1）。只连一个客户端时两者刚好同指一个角色。
>   出问题时能一眼看出是「多了个尾巴」而不是「老字段被挪了位」。
> ★ **bit3（暂停）零字节成本**：借 `flags` 里一个没用的位。客户端**必须**知道这件事 ——
>   否则世界停住时它只能靠「`t` 不涨」去猜，而「`t` 不涨」和「网络卡了」长得**一模一样**。
> ★ `phase`/`season` 用**序数**而不是字符串：省字典，且两边枚举顺序写死
>   （Python `protocol_bin.PHASES/SEASONS` ⇄ JS `ProtocolBin.PHASES/SEASONS`）。
>   顺序不一致正是最容易「服务端发 day、客户端解成 night」的地方 —— 有 parity 测试逐帧对。

**字典**：每帧自带一张「本帧新出现的字符串」表，客户端把它并进自己的
**连接级字典**（跨帧累积）。所以重复的 prefab/anim/build 名**每帧只花 1 个 varint**。

**定点**：坐标 1/16 格（±2048 格范围）、朝向 1/16 度 —— 对一款 128×128 格的世界够用，
且比 float 省一半。若将来世界变大，把版本号 +1 换 int32 即可（**兼容起见必须升版本**）。

## 4. 为什么两条编码并存

JSON 版留在默认路径：**出问题时能直接肉眼读帧**。二进制版是优化，
不是替代。判据：同一快照两种编码解出来必须**逐字段一致**（`tests/test_protocol.js`）。

## 5. 控制指令（`{"cmd": ...}`）—— **这是替代，不是 RPC**

全仓 `GetRPC` **0 处**。原版靠 `SendRPCToServer / SendRPCToClient` 做「客户端调用服务端函数」，
本工程**没有**这条通道，而是用 WS 上的 JSON 控制消息**替代**。写清楚这件事，
是因为二者**长得像但不等价** —— 把它当 RPC 用会在下面三处吃亏：

| 差异 | RPC | 本工程的控制消息 |
|---|---|---|
| 请求/响应配对 | 有（返回值直接回到调用点） | **只有拉取式命令有回包**（`whoami` / `me` / `targets`）；`act`/`unact`/`pause` 是**单向**的，结果要另一次拉取才知道 |
| 超时 / 重试 | 框架负责 | **没有**。发出去就不管了；丢了只能靠下一次轮询补上 |
| 版本协商 | 有 | **没有**。服务端只认命令名，不认参数版本；参数形状变了客户端会静默不生效 |

> 一句话：**控制消息是「通知」，不是「调用」**。需要「调用」语义时，
> 走下面的第 6 节契约，别在第 5 节上加戏。

### 5.1 命令表（机器生成，勿手改）

<!-- PROTOCOL-CMDS:BEGIN 本块由 tools/check_protocol.py 生成，勿手改 -->

| 命令 | 服务端分发 | 客户端发送 | 回包 | 说明 |
|---|---|---|---|---|
| `act` | ✔ | ✔ | 无（单向） | 对目标施放动作（**单向**，结果靠下一次 `targets` 带回） |
| `me` | ✔ | ✔ | 有 | 自身状态（血/饿/理智/背包），与 `targets` 同一次 HUD 刷新拉取 |
| `pause` | ✔ | ✔ | — | 暂停/恢复模拟（控制类，直接改 hub 状态，不进 `cmds` 队列） |
| `ping` | ✔ | ✔ | 无（单向） | 应用层心跳（浏览器不暴露 WS 的 ping/pong 帧） |
| `targets` | ✔ | ✔ | 有 | 附近可交互目标 + 最近一次动作结果 |
| `unact` | ✔ | ✔ | 无（单向） | 松开时取消持续动作（**单向**） |
| `whoami` | ✔ | ✔ | 有 | 问「我是谁」；服务端**就地应答**（不经过模拟线程）。玩家还没建出来时回 `null` |

> `回包` 列：`有` = 服务端会回一条带结果的消息；`无` = 只排队执行，不回答（要结果就再发一次拉取命令）。

<!-- PROTOCOL-CMDS:END -->

三列必须**同时**一致：`服务端分发` 从 `rt/server.py` 提取、`客户端发送` 从 `rt/client.html` 提取、
`协议文档` 是本块。任一列多一个或少一个，`tools/check_protocol.py` 就退出 1 ——
这条判据防的是本工程反复出现过的那类事故：**声明在、消费不在**（词在 ≠ 行为在）。

## 6. 最小双向调用契约（**尚未实现**，只是契约）

如果将来真要补 RPC，先按这个契约做，别各写一套：

```jsonc
// 客户端 → 服务端
{"rpc": 1, "id": 17, "m": "spawn", "a": {"prefab": "log", "x": 3, "z": 4}}

// 服务端 → 客户端（成功）
{"rpc": 1, "id": 17, "ok": true, "r": {"guid": 42}}

// 服务端 → 客户端（失败）
{"rpc": 1, "id": 17, "ok": false, "e": {"code": "bad_args", "msg": "prefab 未知: lgo"}}
```

| 约定 | 内容 | 为什么 |
|---|---|---|
| `id` | 客户端单调递增，服务端**原样回** | 没有它就无法把回包对到调用点 |
| 超时 | 60 s 未回即失败（客户端自己判） | 本工程的服务端可能正忙在模拟线程里，不设超时会永久挂住 |
| 幂等 | 同 `id` 重发必须**只生效一次** | 超时重试是常态；不幂等就会出现「点一次、造两个」 |
| 错误码 | `bad_method` / `bad_args` / `busy` / `denied` / `internal` | 只有分类才能让客户端决定「重试还是提示」 |
| 执行线程 | **必须**进 `hub.cmds`，不得在处理线程直接碰 Lua | 唯一的硬约束，见 `rt_boot.lua` 顶部注释 |

**为什么先不定实现**：现在 7 条控制消息里只有 3 条需要回包，且都是拉取式；
贸然补一套 RPC 会同时增加「两套语义并存」的混乱。等真正出现「必须远程调用并有返回值」
的需求（例如 Mod 加载、玩家管理后台）再落地。

# 引擎开发计划：从零到「能开发 2.5D 游戏」（饥荒风格）

> **本文回答三个问题**：要做什么（全量模块清单，102 项）· 按什么顺序做（硬依赖 / 可并行 / 关键路径）· 每一步怎么算做完（会红的判据）。
> **第一阶段目标**：S0~S4 结束时，能用它做出一个 30 分钟可通关的《单夜生存》小游戏，且**不改引擎源码**。
>
> 人月是工程判断（不确定度 **±40%**），不是报价。每个数字都能在 §3 的表里逐行加出来 —— `tools/check_engine_plan.py` 会核这件事。

---

## 0. 怎么读这份计划

### 0.1 三句话定位

1. **§3 是清单**：13 个域 / 102 个模块。判定"不得遗漏"的方法不是凭感觉，而是**反查**：§2.2 把《饥荒》的 12 类玩法能力逐条映射到模块，任何一个能力映射不到模块，就是漏了。
2. **§4 是顺序**：区分三种关系 —— **硬依赖**（前者的产物是后者的输入，不能并行）、**软依赖**（接口先定就能并行，用 mock 顶上）、**无依赖**（随便排）。
3. **§5 是分期**：S0~S7，每期都有"退出判据"，判据必须**能变红**（本项目已有 17 次提交专门修"检查看起来在跑其实没牙"，纪律沿用）。

### 0.2 三列数字的口径

| 列 | 含义 | 用途 |
|---|---|---|
| **从零（人月）** | 空白仓库起、自研全部代码的估算 | 回答"如果重来要多久"、给别人照做的参考 |
| **现状** | ● 已有 / ◐ 部分 / ○ 无（对 `07-通用引擎` 实测） | 回答"我们站在哪" |
| **剩余（人月）** | 从零 × (1 − 完成度) | 回答"还要多久"（§7.1 按域汇总） |

**为什么不只给一列**：只给"从零"会让人以为还要 57 人月（实际上本项目已投约 29 人月）；
只给"剩余"会让计划失去可移植性（别人无法照做）。两列并存，差额就是"已有资产"的账面价值。

## 1. 目标与验收

### 1.1 三级目标（每一级都有机械判据）

| 级别 | 定义 | 谁用 | 从零人月 | 退出判据 |
|---|---|---|---|---|
| **G1 能开发简单游戏** | 30 分钟小游戏可通关，**不改引擎源码** | 你自己 / 2~3 人小队 | **39.6** | §1.2 八条全过 |
| **G2 第三方可用** | 别人 clone 后能建自己的场景、加自己的物品、打包发布 | 外部开发者 | **49.2** | §5 S5 的 AC5.x |
| **G3 垂直域商业级** | 2D 生存类可上线运营（遥测 / 回滚 / 沙箱 / 单平台 Web） | 商业项目 | **54.3** | §11 十二条 |
| （G4 通用引擎） | 多管线 / 多平台 / 资产商店 | —— | 200+ | **不建议**，理由见对标报告 §5.2 |

### 1.2 第一阶段的机械定义：《单夜生存》

"能开发简单游戏"是一句形容词，不可验收。把它翻译成一个**具体的小游戏规格**，每条都能自动判：

| # | 剧本 | 玩家动作 | 判据（必须能红） | 反向验证 |
|---|---|---|---|---|
| P1 | 出生与移动 | WASD 在 128×128 岛上跑动 | 8 方向位移逐向对位（±0.01）；撞树不穿透 | 关掉地形碰撞 ⇒ 穿树 |
| P2 | 采集 | 点树 → 自动走近 → 砍 3 下 → 掉 2 木头 | `workleft` 5→1→掉落→**捡起进背包**（槽 1 数量 +2） | 把 `workleft` 初始值写 0 ⇒ 必须红 |
| P3 | 合成 | 2 木头 + 1 草 → 营火 | 材料够时按钮可点、产物进背包；不够时**禁用且给出原因**（缺哪个、缺几个） | 材料不足仍能造 ⇒ 红 |
| P4 | 装备与工具 | 造斧头 → 装备到 `hands` → 砍树变快 | 同一棵树：空手 6 下 / 持斧 3 下（`workleft` 消耗率 1 vs 2） | 装备槽不生效 ⇒ 红 |
| P5 | 战斗 | 蜘蛛追你 → 你打它 → 它掉血 → 死后掉肉 | 追击 ≤3 s 内进入攻击距离；**它会反击**且玩家血量下降 >0；尸体可捡 | 摘掉 `targetfn` ⇒ 单向战斗 |
| P6 | 昼夜 | 撑过一夜 | 一天 8 分钟（day/dusk/night 三段）；夜里离火 ≤7 格不掉血、>7 格掉血 | 把光照代理关掉 ⇒ 火边也掉血 |
| P7 | 存档 | 退出重进 | 位置 / 背包 / 世界时间 / **已砍倒的树** 四项一致；两次保存的 `sha256` 相同 | 只存玩家不存世界 ⇒ 树复活 |
| P8 | 死亡 | 血归零 | 3 s 后复活，背包掉一半（地面可捡回），`respawns` +1 | 不复活 ⇒ 世界停摆 |

> **这八条是 S0~S4 的验收总纲**。每个阶段的退出判据都是它的子集 —— 不允许出现"阶段通过了但剧本跑不通"。

### 1.3 明确不做（产品决策，不是遗漏）

| 不做 | 为什么 | 真要做的前置 |
|---|---|---|
| 3D 渲染管线（HDRP/PBR/全局光） | 2.5D 生存类不需要；成本 ≥8 人月且换不来差异化 | 决定做 3D 游戏 |
| 主机 / 移动原生 | 平台数线性增加维护成本；Web 分发边际成本最低 | 有发行合同 |
| Shader Graph（节点编辑器） | 手写 GLSL + 材质注册表够用 | 有非程序员要写 shader |
| 原版饥荒 UI 全量（183 widget / 63 screen） | 与玩法无关，只影响观感 | 要"看起来像原版" |
| 自研 3D 物理 | 玩法平面是 XZ 二维，3D 是另一个产品 | 做 3D 游戏 |
| 资产交易市场 | 需要供给方生态，不是工程问题 | 有 100+ 第三方开发者 |

## 2. 基准：饥荒到底需要引擎提供什么

### 2.1 先破除三个误解（这三条决定了架构，错了要重写）

| 误解 | 事实 | 后果 |
|---|---|---|
| "饥荒是 2D 游戏" | **3D 场景 + 2D 精灵**。世界是 `(x, y, z)`，精灵是面向相机的 billboard quad，遮挡靠**深度缓冲** | 若按纯 2D 做，树/角色/建筑的遮挡关系无解（只能手工排 z-index，加一个物体就要改一片） |
| "2.5D = 等距菱形瓦片（isometric）" | 饥荒地面是**方形网格**，相机是**固定俯角的透视/弱透视**，不是 45° 菱形投影 | 若按 isometric 做，美术资源全是菱形，与原版资源不兼容 |
| "精灵贴在屏幕上" | 精灵在 3D 空间里有位置，锚点在**脚底**，永远正对相机 | 锚点错了 ⇒ 角色"浮空"或"陷地"，且遮挡判断全错 |

### 2.2 坐标与空间模型（引擎必须提供的）

| 维度 | 饥荒的做法 | 引擎的对应实现 |
|---|---|---|
| 世界坐标 | `(x, y, z)`，y 是高度 | `Transform {x,y,z}` + `rotY` + `scale`；**玩法只读写 x/z**，y 留给跳跃/飞行/悬浮物 |
| 朝向 | 8 向移动，4 向动画 + 水平翻转 | `facing` 取 `atan2` 量化到 8 档；渲染取 4 档 + `flipX` |
| 相机 | 固定俯角 ≈45°，可 45° 步进旋转，滚轮缩放 | 相机 rig：`pitch` 锁定 `[35°, 55°]`、`yaw` 吸附 45° 步进、`distance` 对数缩放 |
| 地面 | 方形瓦片，每格 **4×4 顶点**做颜色混合 | 地形网格 + 顶点色 + 8 种地形材质索引 |
| 遮挡 | 深度缓冲（真 3D） | 主路径：深度缓冲；兜底路径：按脚底 `z` 排序（两路径必须逐对象一致，见 §6.1） |
| 高度玩法 | 极少数（飞行、投掷） | y 轴只参与渲染与命中判定，**不参与寻路** |

### 2.3 玩法能力 → 模块映射（"不得遗漏"的检验表）

| # | 饥荒的能力 | 需要的引擎模块 | 缺了会怎样 |
|---|---|---|---|
| 1 | 生物群系世界生成 | G14 世界生成 · D6 地形瓦片 · C4 场景格式 · F6 地形碰撞 | 只能手摆地图，做不出"每局不同" |
| 2 | 昼夜 / 季节 / 温度 | G13 世界规则 · D7 光照 · H4 自适应音乐 | 生存压力消失，游戏没有节奏 |
| 3 | 采集 / 工作 | G12 采集 · G4 动作系统 · G5 交互目标 | 只能走路，不能改变世界 |
| 4 | 背包 / 装备 | G8 背包 · G9 物品定义 · D13 UI | 捡不起来，也穿不上 |
| 5 | 合成 / 科技树 | G10 合成 · G9 · G8 | 没有进度感，30 分钟就腻 |
| 6 | 建造 / 放置 | G11 建造 · F1 碰撞体 · J5 Gizmo（可选） | 不能改造世界 |
| 7 | 战斗 / 仇恨 | G6 战斗 · G7 AI · F4 射线 · G2 属性 | 单方面清场（**本项目当前状态**） |
| 8 | 农业 / 烹饪 / 腐烂 | G16 · G9（perishable/edible） · G3 计时器 | 食物系统只剩"捡了就吃" |
| 9 | 死亡 / 复活 | G18 · G17 存档 · G2 | 死一次世界停摆 |
| 10 | 存档 / 回放 | G17 · C7 序列化 · A7 确定性 | 关掉就归零，也没法查回归 |
| 11 | 洞穴 / 多层世界 | C3 场景加载 · C8 分区 · K6 分片（多人时） | 只有一层平面世界 |
| 12 | 多人协作 | K1~K5 · B4 传输 · G8 同步 | 只能单人 |

### 2.4 Unity 的 24 个模块，哪些照抄、哪些改造、哪些永远不做

| 处理 | 模块 | 说明 |
|---|---|---|
| **照抄语义** | 对象模型 / 序列化 / Prefab / 动画状态机 / 输入映射 / 编辑器内核 / 资产管线 / 测试框架 | 这些是"引擎"的通用骨架，语义照抄能降低学习成本 |
| **改造为 2.5D** | 渲染（SRP → 2.5D 管线）、物理（PhysX → 2D 平面 + 高度分离）、2D（Sprite Atlas → billboard 图集）、导航（NavMesh → 瓦片 A*） | 直接用 3D 方案会让成本翻倍且手感不对 |
| **降级或不做** | HDRP/URP 多管线、光照烘焙、Timeline、Animation Rigging、XR、主机平台、Addressables 远程 CDN | 见 §1.3 |

### 3.2 逐域要点（为什么这么切，以及最容易漏的坑）

#### A 基础层（7 项 / 2.4 人月）
**要点**：这一层是"改一次全线返工"的地方，所以先做且要做对。三个不可省的细节：
- **定点数**：网络同步与回放必须定点（1/1000 单位），浮点在不同 JS 引擎/CPU 上会有末位差异 ⇒ 回放对不上。
- **确定性随机**：每个实体一条独立随机流（种子 = 世界种子 + guid 哈希），否则"多生成一个实体"会改变全世界的随机序列。
- **单写者原则**：只有模拟线程能碰 Lua 状态；跨线程只传不可变快照。违反它的 bug 表现为"偶发数据错乱"，极难查。

**容易漏的**：`A6` 的环形日志缓冲 —— 没有它，线上崩溃只能看到最后一行。

#### B 平台层（6 项 / 3.2 人月）
**要点**：平台层要做的是"把不确定挡在外面"。`B3` 的**原子写**（临时文件 + rename）与**坏档隔离**（改名留证，不覆盖）是两条用血换来的规则：坏档被自动存档覆盖后，证据就没了。
**容易漏的**：`B1` 的"页面隐藏时降频" —— 不做会让后台标签页吃掉 CPU，笔记本发烫。

#### C 对象与场景（8 项 / 5.8 人月）
**要点**：`C1` 的 **Entity / Asset 分离**是整个架构的地基：Entity 有 guid、可变、进存档；Asset 不可变、按 GUID 引用、可被多实例共享。搞混了就会出现"改一个实例，所有同类都变"。
`C4` 场景格式与 `C5` Prefab 是两个不同的东西：场景存**实例**（含覆盖），Prefab 存**模板**（含默认值）。
**容易漏的**：`C2` 删父节点时子树怎么处理（必须明确：级联删 or 提升到根，二选一写进 schema）。

#### D 渲染（11 项 / 6.6 人月）
**要点**：2.5D 的核心不是"画精灵"，是**排序**。`D5` 必须给出两条路径（深度缓冲 / y-sort）且**逐对象一致**，否则 WebGL 与 Canvas 兜底会看到不同的遮挡关系。
`D7` 光照不要做通用光照模型：2.5D 生存类只需要"环境光 × 点光累加"，乘法 + 加法两张贴图就够。
**容易漏的**：`D1` 的 DrawList 若只带屏幕坐标，后面做缩放/旋转/Gizmo 全部要重写 —— 必须带世界变换。

#### E 动画（5 项 / 2.6 人月）
**要点**：`E3` 动画事件必须**服务端也收到**。只在客户端播放的"命中帧"会导致：动画上打中了，服务端判定没打中（或反之），这是最常见的"手感不对"根因。
**容易漏的**：`E1` 的 `animover` 是动作结束的唯一可靠信号；用固定时长猜结束，会在低帧率下错位。

#### F 物理与空间（7 项 / 3.4 人月）
**要点**：这个域**只做 2D**（XZ 平面）。宽相用空间哈希（格 4 单位）足够，不需要四叉树。
`F3` 的解算顺序要固定（按 guid 排序），否则同一次碰撞在不同机器上推出不同结果 ⇒ 回放分叉。
**容易漏的**：`F6` 地形碰撞与 `F7` 寻路必须**共用同一张可走性表**，两份表一定会漂。

#### G 玩法框架（18 项 / 12.2 人月）
**要点**：这是最大的一块，也是"引擎"与"游戏"的分界模糊处。切分原则：**能被两个以上游戏复用的进引擎，只服务一个游戏的进项目层**。
按此原则，`G1~G7`（组件/属性/动作/交互/战斗/AI）、`G8~G10`（物品/背包/合成）、`G12`（采集）、`G13`（世界规则）、`G17`（存档）进引擎；具体有哪些怪、哪些配方，进项目层（数据，不是代码）。
**容易漏的**：`G4` 的**动作锁**。不做动作锁，玩家能在攻击中移动、在采集时转身，手感立刻散架。

#### H 音频（4 项 / 1.4 人月）
**要点**：先做"能出声"，再做"好听"。`H1` 必须处理浏览器的用户手势解锁（否则自动播放被静默拒绝，表现为"没声音但也没报错"）。
**容易漏的**：`H2` 的听者是相机不是角色 —— 相机旋转时声像要跟着变。

#### I 脚本与扩展（6 项 / 3.4 人月）
**要点**：脚本层是"给别人的手"，`I2` 的 API 表一旦发布就要守兼容；`I3` 的 schema 是检查器、文档、校验三处的单一真源（避免"文档写的能力不存在"）。
**容易漏的**：`I1` 的 table ↔ dict 转换边界。跨语言每次调用都有成本，批量数据要压成字符串/扁平数组传（本项目实测：逐条迭代 table 是几千次调用）。

#### J 工具链（14 项 / 8.4 人月）
**要点**：工具链决定"别人能不能用"。`J2` 命令栈是**所有编辑功能的地基**（撤销、多选、Prefab 覆盖、PIE 全依赖它），必须第一个做。
`J1` 有个硬约束：**编辑器与运行时共用同一套渲染与 CSS**。同一个东西两份实现，本项目已经栽过三次。
**容易漏的**：`J10` PIE 的隔离。PIE 里改的东西必须只存在于内存，退出后资产字节不变。

#### K 网络（6 项 / 3.6 人月）
**要点**：`K2` 权威模型不能省 —— 客户端预测（`K3`）是体验优化，不是正确性来源。
**容易漏的**：`K4` AOI 不做的话，带宽随实体数线性增长（本项目实测 640 实体时已 129 KB/s/客户端）。

#### L 发布与运营（5 项 / 2.0 人月）
**要点**：`L2` 版本硬闸（不一致就拒绝进服）比"能进但乱码"好一万倍。
**容易漏的**：`L5` 合规里的**素材版权清单** —— 用原版美术发布是法律风险，不是技术问题。

#### M 文档与生态（5 项 / 2.2 人月）
**要点**：`M1` 从 schema 自动生成文档，是为了消灭"文档漂移"这一类问题（本项目已抓出 4 处）。
**容易漏的**：`M2` 示例工程必须**只用公开 API**，否则示例会变成"改引擎源码才能跑"的反面教材。

## 4. 优先级与依赖

### 4.1 优先级判据（可判定，不靠感觉）

| 级别 | 判据（满足任一即归此级） | 例 |
|---|---|---|
| **P0** | 缺了《单夜生存》八条剧本中的任意一条跑不通 | 场景格式、动作系统、背包、合成 |
| **P1** | 缺了"外部开发者能做出自己的游戏"或"能上线"不成立 | 编辑器内核、资产管线、构建、版本闸 |
| **P2** | 缺了只是"不够好"，不影响能否做出来 | 粒子、动画混合、热重载、多平台 |
| **P3** | 明确不做（§1.3 有理由） | 社区运营、资产交易 |

> **为什么不用"重要性"排序**：重要性是主观的，会导致"渲染很重要所以先做渲染"。而按上面这把尺子，
> 渲染只到 P1（缺了画面难看但游戏能跑通），**场景格式才是 P0**（缺了整个游戏存不下来）。
> 本项目 42.8 分里最刺眼的一项就是"编辑器内核 1.5/5"，它不是"不够漂亮"，是"别人用不了"。

### 4.3 软依赖（接口先定，用桩并行）

这五处**看起来必须串行，其实可以并行**，前提是**先把接口写死（含空实现）再分头做**：

| 软依赖 | 接口先定成什么 | 并行后果（可接受） |
|---|---|---|
| G 域 ↔ F 域 | `raycast(o,d,mask)` / `overlap(aabb,layer)` / `isWalkable(tile)` | F 未完成时 G 用"永远命中最近目标""地形恒可走"的桩，判据先写、后接真实现 |
| E 域 ↔ G 域 | `play(anim)` / `onAnimEvent(name,cb)` | 动画未接时动作按固定时长结束（**必须登记为临时行为**，否则会变成永久 bug） |
| D 域 ↔ C 域 | `DrawList.push(quad)` | 场景有数据、渲染还没好时先导出 DrawList 做离线校验（本项目已有先例：`drawcmd.json`） |
| J 域 ↔ C 域 | 场景读写 API `load/save/diff` | 编辑器 UI 可以先对着"假场景"做，等 C4 就绪再接 |
| K 域 ↔ G 域 | 快照 schema（组件 → 字段表） | 网络层可先用"单机 loopback 传输"验协议，不依赖真服务端 |

> **软依赖的纪律**：每处桩必须有一条判据证明"接上真实现后行为变了"。否则桩会变成永久实现 ——
> 本项目 `perf_client.js` 的 5927 fps 就是这么来的（桩化 canvas 的 `fillRect` 是空操作）。

### 4.4 三条泳道 + 八个波次

**为什么分泳道**：并行不是"人多就行"，而是"改的文件不重叠"。本项目的运行时（`rt/`）、工具链（`tools/`+编辑器面板）、服务（`server/网络`）天然是三块。

```
泳道 R（Runtime，主链）  A → C → D → E → F → G ──────────→ K
泳道 T（Toolchain）            └→ C4 → J2 → J1..J14 ──→ L
泳道 S（Service/Eco）  B4 ────────────────────────────→ K → L → M
        W1   W2    W3    W4    W5    W6    W7    W8
```

| 波次 | 阶段 | 泳道 R | 泳道 T | 泳道 S | 可并行人数 |
|---|---|---|---|---|---|
| W1 | S0 | A1~A7 | — | B1,B3,B5 | 2（A 域 / B 域） |
| W2 | S1 | C1~C8 | （C4 完成后起 J2） | B2,B4,B6 | 2~3 |
| W3 | S2 | D2,D5~D11 · E1~E5 · G1~G3 | J2 | H1~H3 | **3** |
| W4 | S3 | F1~F7 · G4~G7,G9,G12 | J3,J4 | — | **2~3** |
| W5 | S4 | G8,G10,G11 ∥ G13~G16 · G17,G18 · I1~I3 · H4 | J5,J6 | — | **3**（物品线 / 世界线 / 脚本线） |
| W6 | S5 | （修缺陷） | J1,J7~J14 · I4,I5 | K1,K2（提前起） | **2~3** |
| W7 | S6 | K3~K5 | J12 | L1~L5 · I6 | 2 |
| W8 | S7 | K6 | M1~M4 | M5 | 1~2 |

**W5 是并行度最高的一波**，因为 S4 内部有两条几乎独立的子链：

```
物品线： G9 ──→ G8 ──→ G10 ──→ G11
                              ╲
世界线： G13 ─→ G14 ─→ G15 ─→ G16（烹饪要物品，在此交汇）
```

### 4.6 依赖的常见错误（本项目踩过的）

| 错误 | 表现 | 正确做法 |
|---|---|---|
| 把"接口依赖"当"实现依赖" | 等对方全部做完才开工，串行化 | 先定接口 + 桩，判据先写（§4.3） |
| 把"数据依赖"当"代码依赖" | 为了"能生成蜘蛛"去改引擎源码 | 数据（prefab/配方）与引擎分离，加内容不改代码 |
| 循环依赖 | A 要 B 的字段，B 要 A 的事件 | 引入事件总线（A4）或中介组件，禁止双向直接引用 |
| 阶段内依赖倒挂 | S3 的模块依赖 S4 的模块 | 本文所有依赖都满足"被依赖者的阶段 ≤ 依赖者的阶段"（脚本会核） |

## 5. 分阶段计划（S0~S7）

> 每阶段的"退出判据"都要求**至少一条反向验证**（把实现改坏，判据必须红）。
> 没有反向验证的判据按"未验证"计，不算通过 —— 这是本项目 §1.1 的分级尺子。

### S0 · 地基（3.4 人月）｜无前置
**目标**：一个能启动、能跑固定 tick、能确定性回放、能报错的空壳。

| 交付 | 内容 |
|---|---|
| 主循环 | 30 Hz 固定步长 + 可变帧渲染；追帧上限 5；暂停语义 |
| 确定性 | 种子 PRNG（每实体独立流）+ tick 指纹（CRC32）+ 输入日志 |
| 平台 | 窗口/画布生命周期、原子写、路径白名单、坏档隔离 |
| 并发 | 模拟线程单写者；跨线程只传不可变快照 |
| 可观测 | 分级日志 + 环形缓冲 + 端点耗时 |

**退出判据**：
| # | 判据 | 反向 |
|---|---|---|
| AC0.1 | 同一份输入日志跑 3 次，逐 tick 指纹全同 | 把 PRNG 换成 `Math.random` ⇒ 三条指纹不一致 |
| AC0.2 | 1000 次原子写，中途 kill 进程，文件要么是旧版要么是新版（无半截） | 直接覆盖写 ⇒ 抓到半截 JSON |
| AC0.3 | 坏档被重命名为 `.bad.N` 且**不被自动存档覆盖** | 跳过隔离 ⇒ 30 s 后证据消失 |
| AC0.4 | 模拟线程外的写操作必须抛（debug 断言） | 去掉断言 ⇒ 并发用例不报错 |

### S1 · 运行时骨架（10.1 人月）｜依赖 S0
**目标**：一个精灵能在 3D 坐标平面上被画出来，并有场景资产可存可读。

| 交付 | 内容 |
|---|---|
| 对象模型 | Entity/Asset 分离、组件注册表、生命周期 |
| 场景 | `.scene.json` v1（节点/地形/环境）、保存加载往返 |
| Prefab | 模板 + 实例覆盖 + revert |
| 渲染初版 | DrawList、WebGL2/Canvas2D 双后端、图集、billboard |
| 平台 | 输入抽象、WS 传输、Web 适配 |

**退出判据**：
| # | 判据 | 反向 |
|---|---|---|
| AC1.1 | 100 个对象的场景：保存→加载→保存，两次 `sha256` **逐字节相同** | 序列化时按哈希表顺序输出 ⇒ 两次不同 |
| AC1.2 | 改实例 A 的覆盖字段，实例 B 与 prefab 默认值都不变；`revert` 后 A 与默认值一致 | 覆盖写回 prefab 源 ⇒ B 也变 |
| AC1.3 | 同一场景 WebGL 与 Canvas 的 DrawList **逐顶点逐 UV 一致**（误差 ≤1e-4） | 改一条 UV ⇒ 两条路径分叉 |
| AC1.4 | 删除父节点后，子节点要么全删要么提升到根（按 schema 声明），**不出现悬空 parent** | 只删父 ⇒ 子节点 guid 指向不存在的父 |

### S2 · 表现层（10.0 人月）｜依赖 S1
**目标**：看得对（遮挡正确）、动得对（状态机）、听得见（有声音）、属性可改。

| 交付 | 内容 |
|---|---|
| 2.5D 渲染 | 相机 rig、深度排序双路径、地形瓦片、光照、阴影、粒子、材质、合批 |
| 动画 | 帧动画、状态机、动画事件（服务端也收到）、混合、换装 |
| 音频 | WebAudio 后端、空间音源、总线 |
| 玩法基座 | 组件生命周期、属性 + 修饰器、定时器/Buff |

**退出判据**：
| # | 判据 | 反向 |
|---|---|---|
| AC2.1 | 角色走到树后 ⇒ 被遮挡；走到树前 ⇒ 遮挡树。**两条渲染路径结论相同** | 关掉深度写 ⇒ Canvas 路径遮挡反转 |
| AC2.2 | 攻击动画的"命中帧"事件在**服务端**日志里出现，且时间戳与客户端同一 tick | 只在客户端派发 ⇒ 服务端无记录 |
| AC2.3 | 点光源 0/1/8 三档，同一点像素亮度单调递增；8 光源无 NaN | 光照恒 1.0 ⇒ 三档亮度相同 |

| AC2.5 | 属性修饰器：基础 100 + 10% + 20 ⇒ 130（顺序无关）；下限钳位生效 | 改成加法 ⇒ 130 vs 120 差异被抓 |

### S3 · 玩法核心（7.6 人月）｜依赖 S2
**目标**：能打、能采、能走位、能被打（对等战斗）。

| 交付 | 内容 |
|---|---|
| 物理 | 碰撞体/层、空间哈希宽相、圆-圆/圆-AABB 解算、射线、触发区、地形碰撞、A* 寻路 |
| 动作与交互 | `BufferedAction` 队列、动作锁、20 格目标枚举、选中高亮 |
| 战斗与 AI | 攻击三段时间轴、伤害/护甲、受击硬直、死亡掉落；感知/仇恨/追击/反击 |
| 物品与采集 | 物品组件族、`workable` 采集、工具效率 |

**退出判据**：
| # | 判据 | 反向 |
|---|---|---|
| AC3.1 | 两个生物相向走 300 tick，重叠面积 = 0；位置抖动 < 0.01/tick | 关掉解算 ⇒ 完全重叠 |
| AC3.2 | 32 层逐层 raycast，命中集合与预期**逐位相同** | 忽略 mask ⇒ 全部层都命中 |
| AC3.3 | 攻击中按移动键：位移 = 0（动作锁生效）；动作结束后可移动 | 去掉动作锁 ⇒ 边打边跑 |
| AC3.4 | spider 被攻击后 ≤3 s 转身并造成 ≥1 次伤害，玩家血量下降 >0 | 摘掉 `targetfn` ⇒ 玩家血量不变 |

### S4 · 世界与存档（8.5 人月）｜依赖 S3
**目标**：世界会自己运转（昼夜/季节/再生），能存能读，能死能活 —— **G1 达成**。

| 音频 | 自适应音乐（昼夜/战斗切换，依赖 G13） |

**退出判据**：**《单夜生存》P1~P8 八条全过**，另加：

|---|---|---|

## 6. 关键子系统设计要点

> 这一节不是"模块清单的复述"，而是**四个最容易做错的地方**的具体方案。
> 每个方案都给出"判据"——因为方案本身也是主张，也要能被反驳。

### 6.1 2.5D 场景与渲染

#### 6.1.1 坐标与投影（先定死，后面 80% 的 bug 来自这里）

```
世界（右手，y 向上）        相机（固定 pitch≈45°，yaw 步进 45°）
   y ↑ 高度（只影响渲染/命中，不参与寻路）
     │
     │      z（进深）
     └────────→ x
玩法平面 = XZ。所有距离、寻路、碰撞都在 XZ 上算；y 只用于：
  ① 精灵的脚底锚点 → 决定遮挡顺序
  ② 投掷/飞行物的抛物线（可选）
  ③ 悬浮物的视觉高度（不参与碰撞）
```

**为什么不用等距（isometric）**：等距是把 3D 压成 2D 菱形，代价是"高度"变成纯视觉偏移，
遮挡必须靠手工排序；而饥荒式的"3D 坐标 + 深度缓冲"让遮挡自动正确。代价是需要真 3D 投影矩阵 ——
但 WebGL 本来就提供，成本几乎为零。

#### 6.1.2 排序：两条路径，一个结论

| 路径 | 何时用 | 怎么排 | 风险 |
|---|---|---|---|
| **A 深度缓冲** | WebGL2 可用（默认） | 精灵 quad 写入 `gl_Position.z`（按脚底世界 z 映射） | z-fighting（同 z 的物体闪烁） |
| **B y-sort** | Canvas2D 兜底 / 无深度缓冲 | 按脚底 `z` 降序绘制（远的先画） | 交叉物体无法正确排序（如长桌斜穿） |

**一致性策略**：
- 排序键统一为 `(footZ, -layerPriority, guidHash)` —— 三级键保证**全序**（同 z 也稳定）。
- B 路径的排序结果，必须与 A 路径的"可见性判定"逐对象一致：判据是**随机摆 200 个物体 + 随机相机，
  两条路径输出的"谁遮谁"矩阵完全相同**（不是"看起来差不多"）。
- 已知无解的情况（长物体斜穿）**如实登记为限制**，不假装解决：B 路径下禁止使用跨多格的长装饰物。

#### 6.1.3 相机

```js
// 参数区间（越界即夹紧，不报错）
pitch  ∈ [35°, 55°]   // 默认 45°，不允许玩家改出这个区间（改了就露底）
yaw    ∈ {0, 45, 90, ...}  // 吸附步进：连续旋转会让瓦片接缝闪烁
zoom   ∈ [0.5, 4] 且按 2^0.25 步进  // 对数缩放，保证每档缩放比例一致
target = 角色位置 + 速度前导(0.3 s)  // 前导让"往哪跑"看得见更多
死区   = 屏幕 8% 的圆        // 小位移不晃镜头
```

**平移边界**：相机可视矩形必须被"世界包围盒 + 一圈留白"包含；越界时夹紧而不是露底色。
（本项目曾把"岛边露底色"误判为渲染 bug —— 技术正确≠体验没错，边界夹紧是体验问题。）

#### 6.1.4 地形

- 方形瓦片，每格 **4×4 顶点**（用于边缘颜色混合，避免棋盘感）。
- 8 种地形用一个 `Uint8Array` 存索引（128×128 = 16 KB），整张一次性上传 VBO。
- 地形高度**恒为 0**（生存类不需要起伏）；要起伏时用"装饰物 + 阻挡"表达，不引入高度场。
- 地形与 `F6` 碰撞、`F7` 寻路**共用同一张"可走性表"**（一位一个瓦片），禁止三份。

### 6.2 角色控制

#### 6.2.1 数据流（谁说了算）

```
输入采样(60Hz) → 本地预测(立即移动) → 上行 {seq, dir, actions}
                                          ↓
服务端 tick(30Hz)：校验 → 移动 → 碰撞 → 结算 → 下行 {seq, pos, state}
                                          ↓
客户端：|pos - predict| < 0.5  ⇒ 插值收敛
        |pos - predict| ≥ 0.5  ⇒ 一步吸附（并计数，计数异常 = 作弊或 bug）
```

**三条硬规则**：
1. **服务端权威**：客户端从不决定"打中了没"，只决定"我想打谁"。
2. **预测只为手感**：预测错了一定要能校正回来（吸附 + 计数），不能"错了就将错就错"。
3. **输入与表现分离**：输入产生"意图"（方向 + 动作），不产生位移；位移由移动系统算。

#### 6.2.2 移动与朝向

| 项 | 规则 |
|---|---|
| 速度 | 基础 6 单位/s；修饰器乘算（Buff/地形/负重） |
| 8 向 | 输入向量量化为 8 档；斜向速度归一化（否则斜着走快 41%） |
| 朝向 | `facing = quantize(atan2(dz, dx), 8)`；**朝向与移动解耦**（采集时面向目标，可以侧身走） |
| 动画 | 8 向 → 4 个 build 方向 + 水平翻转；`flipX` 只影响 uv，不影响逻辑 |
| 碰撞 | 沿移动方向两点采样（脚部 + 前方 0.3 单位），防"贴角穿墙" |

#### 6.2.3 动作锁（最容易漏，漏了手感立刻散）

```
状态：idle ⇄ moving
       idle/moving --(有 BufferedAction)--> acting --(完成/打断)--> idle
acting 期间：
  · 移动输入被**排队**而不是丢弃（松开后不补，但动作结束若仍按着则继续走）
  · 不能开始第二个动作（除非新动作 priority 更高，如"被打断"）
  · 受击 ⇒ 立即打断（除非动作标记 uninterruptible）
```

**判据**：攻击中按移动键，位移必须为 0；动作结束的那一 tick 位移恢复。

#### 6.2.4 攻击的三段时间轴

```
前摇(windup) → 命中帧(hit) → 后摇(recovery) → 冷却(cooldown)
 0.20s          0.35s          0.55s           0.80s（从命中帧起算）
```
- 命中判定在**命中帧**（动画事件），不是在按键时 —— 否则"隔空打牛"。
- 后摇期间不能移动（动作锁），但可以被受击打断。
- 冷却独立于动作：冷却未完，动作可以开始但结算为"空挥"（必须报原因）。

### 6.3 资源与合成（饥荒的核心循环）

#### 6.3.1 物品 = prefab + 组件组合

| 组件 | 字段 | 作用 |
|---|---|---|
| `stackable` | `maxstack` | 可堆叠上限（木头 20 / 石头 40） |
| `perishable` | `perishtime`, `temperature_rate` | 新鲜度 1→0；冰箱降低速率；归零变腐烂物 |
| `finiteuses` | `uses`, `onfinished` | 耐久（斧头 100 次）；归零销毁或变废品 |
| `edible` | `hunger`, `health`, `sanity`, `foodtype` | 食用效果；生/熟不同 |
| `fuel` | `fuelvalue` | 可作燃料（营火续命） |
| `weapon` | `damage`, `range` | 武器伤害 |
| `armor` | `absorb`, `durability` | 护甲吸收百分比 |
| `tool` | `action`, `efficiency` | 工具效率（斧头砍树 -2 workleft/次） |
| `container` | `slots`, `type` | 容器（箱子/背包） |

**关键设计**：物品的"是什么"由组件决定，不由 `if name == "axe"` 决定。加新物品 = 加一个数据文件，不改代码。

#### 6.3.2 背包

```
itemslots[1..maxslots]   // 稀疏数组：可能只有 [1] 和 [7] 有值
equipslots{ hands, head, body, beard }   // 4 个字符串键
activeitem               // 手上正在用的（不等于装备）
```
- **满包时物品仍能拿在手上**（`maxslots > 0` 时允许），这是原版行为，也是"背包管理"手感的一部分。
- 堆叠合并规则：先填未满的同类堆，再占空槽；顺序必须确定（否则存档往返后物品位置变）。

#### 6.3.3 配方与科技

```
Recipe {
  name, ingredients:[{item, count}], tab, tech, builder, station, product
}
```

**可用性四问**（顺序固定，返回第一个失败原因，UI 直接显示）：
1. **材料够吗** → 缺哪个、缺几个
2. **科技够吗** → 需要什么等级（SCIENCE_ONE/TWO/THREE、MAGIC_TWO/THREE…），当前等级
3. **站台近吗** → 需要邻近什么建筑（`TECH` 标签），距离多少
4. **产物放得下吗** → 背包有空位 / 手上能拿

> **科技是"等级"不是"解锁列表"**：`TechTree` 记录"我在 SCIENCE 有 2 级"，
> 配方只需 `SCIENCE ≤ 2` 即可。这样加 100 个配方不用维护 100 条解锁关系。

#### 6.3.4 制作 UI 的状态机

```
打开 → 选页签(tab) → 列出该页签全部配方
        ├─ 可制作：高亮 + 图标
        ├─ 材料不足：灰显 + 悬停显示缺什么
        └─ 科技不足：锁形图标 + 显示所需站台
制作 → 二次确认（可选）→ 扣材料 → 产物入包 → **失败必须回滚材料**
```
**判据**：材料不足时的制作请求，服务端必须拒绝（不能只靠 UI 灰按钮 —— 改包就能造）。

#### 6.3.5 腐烂与烹饪

```
新鲜度 1.0 ──(perishtime)──→ 0.5（变质，可吃但效果减半）──→ 0（腐烂物）
冰箱：rate × 0.25；夏天 × 1.5；背包里 × 1.0
烹饪锅：4 格 + 按"优先级最高的匹配配方"产出；失败产出"湿哒哒的一坨"
```
**判据**：同一物品在冰箱/背包里各放 60 s，新鲜度差值符合速率比（±5%）。

### 6.4 世界规则与世界生成

#### 6.4.1 时间轴（一切生存压力的来源）

```
一天 = 480 s，按季节分配三段：
  秋: day 250 / dusk 180 / night 60      （本项目实测值）
  冬: day 180 / dusk 120 / night 180     （夜更长 ⇒ 更难）
季节：20 天/季 × 4 季；温度曲线按季节 + 昼夜相位插值
```
- `worldstate` 是**单例**，所有系统只读它；写入只能通过 `AdvanceTime(dt)`。
- 规则必须可存档：`{day, phase, season, temperature, moonphase}`，缺一不可。

#### 6.4.2 世界生成

```
群系图（房间节点 + 边） → 任务（每房间放什么/放多少） → 连通性校验 → 实体实例化
```
- **同种子必须同世界**：判据是"生成两次的 (地形 + 实体 guid/坐标) 指纹相同"。
- 连通性校验：从出生点做一次 BFS，所有"必达房间"必须可达；不可达则重生成（有次数上限）。
- 资源密度用"每房间配额"，不用"全局随机撒" —— 否则会出现一片空草原。

#### 6.4.3 资源再生

```
砍倒的树 → 登记 (prefab, x, z, respawnAt) → 到期且玩家距离 > 20 → 重生
上限：每区域密度 ≤ N；总量 ≤ M（防内存膨胀）
```
**判据**：砍 10 棵，等 3 天，重生 10 棵（±1）；玩家站在原地的树**不重生**（防刷脸）。

### 6.5 编辑器内核（决定"别人能不能用"）

#### 6.5.1 命令模式（一切编辑的唯一入口）

```
Command {
  do(): void        // 执行
  undo(): void      // 精确逆操作
  merge(other): bool // 连续同类操作合并（拖动时不要产生 300 条命令）
  serialize(): json  // 可存进撤销栈、可跨会话恢复
}
```
**纪律**：任何编辑动作**只能**通过 `exec(cmd)` 改状态。直接改字段的代码一律视为 bug
（因为撤销栈会与真实状态失配，而且失配是静默的）。

#### 6.5.2 schema 驱动的检查器

```
组件声明 → 字段表 → 检查器自动生成控件 → 同时用于：校验 / 文档 / 默认值 / 序列化
```
**一处声明，四处消费**。手写表单是本项目最容易产生"文档与实现不一致"的地方（已抓 4 处）。

#### 6.5.3 PIE 的隔离

```
进入：场景快照（内存）→ 启动运行时 → 标记 dirty
退出：丢弃运行时 → 从快照恢复 → 场景文件 sha256 必须不变
```
**判据**：PIE 里杀 3 个实体 + 改天气，退出后场景文件字节不变。

### 6.6 确定性与存档

| 层 | 要求 | 判据 |
|---|---|---|
| 随机 | 种子化、每实体独立流 | 同种子两次运行指纹相同 |
| 浮点 | 关键量用定点（1/1000） | 两平台/两浏览器结果相同 |
| 顺序 | 遍历顺序确定（按 guid 排序，不用哈希表顺序） | 同场景两次 tick 指纹相同 |
| 并发 | 单写者 | 跨线程写必须抛 |
| 存档 | 组件自述 + 原子写 + 版本迁移 | 存档往返 `sha256` 相同；v1→v2 字段不丢 |
| 回放 | 输入日志逐 tick 比对 | 改一个字节必须被抓到并定位到 tick |

## 附录 A · 术语

| 术语 | 含义 |
|---|---|

| 恒绿判据 | 任何情况下都不会失败的检查（等于没有检查） |
| 硬/软依赖 | 硬：产物是输入；软：接口定了就能并行 |

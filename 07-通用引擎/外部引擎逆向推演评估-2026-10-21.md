# 外部引擎逆向推演评估：要不要装 Unity / Cocos

> 日期：2026-10-21　｜　结论类型：**不采纳**（有条件保留）　｜　决策有效期：到 M2 结束前重审
> 关联：`Unity对标审查与路线图-2026-10-21.md`（差距 42.8/100）、`引擎开发计划-从零到2.5D-2026-10-21.md`（剩余 28.3 人月）

---

## §0 结论先说

**不建议把"下载安装 Unity / Cocos 并做逆向推演"作为加速手段纳入开发计划。**

不是因为"没必要看别人怎么做"，而是因为**性价比差、且其中一条路有法务红线**。拆成三句话：

| 候选 | 结论 | 一句话理由 |
|---|---|---|
| **Unity 编辑器** | **不装** | 条款明文禁止逆向（§4.1）；C# 栈与本项目零交集（§2.1）；它公开的那部分源码**不装也能读**（§5 已实测） |
| **Cocos Creator 编辑器** | **不装** | 引擎 MIT 但编辑器闭源；且有更省事的读法（§3.2） |
| **Godot** | **可选装，但先读源码** | MIT + 编辑器全开源 + 有零安装的 Web 版；是四个候选里唯一"装也划算"的 |
| **饥荒（DST）源码** | **已在手，应作为主要对标源** | 4030 文件 / 153 万行 / 821 component，**同语言、同运行时、能直接跑**（§2.4） |

**替代做法**：把"逆向推演"降级为「**读公开源码 + 写对照笔记 + 落到设计决策**」，预算上限 **3 人日**（占剩余工程量的 0.5%），且必须在 M1-1 启动前用完、不得变成常设活动。

理由不是"省钱"，而是本项目唯一被验证有效的知识获取方式就是这一种：§9aq 的 12 条结论全部来自读 DST 源码；而"我试过 Unity"这类产出在本仓库历史里**一件都没留下**。

## §1 先把问题问准：什么叫"加快"

"加快开发进度"是个感觉词，必须先换成可判的东西。本文采用：

> **加快 = 单位人日产出的「可验证产物」变多。**

"可验证产物"指：能进仓库、能被后人查、能被判据核的东西 —— 一段接口定义、一张对照表、一条写进计划的结论。
反面就是"我看过了""大概是这样"，它随时间衰减到零，且无法被审计。

用这把尺子量本项目的真实历史：

| 知识获取方式 | 实际产出 | 是否进仓 |
|---|---|---|
| 读 DST 源码 `scripts/components/*` | §9aq 12 条结论（背包槽位、科技等级、昼夜相位、季节时长…） | ✅ 进开发计划 |
| 读 DST `actions.lua:4902` | 推翻"ATTACK 依赖动画事件"的错误前提 | ✅ 改动 `rt_boot.lua` |
| 读 `Unity对标审查与路线图` | 24 模块差距表、42.8 分、M1~M8 | ✅ 两轮计划都依赖它 |
| 装引擎跑示例工程观察行为 | —— | ❌ 历史上零次 |

所以问题不是"Unity 值不值得学"，而是"**学它的哪一层，用哪种介质**"。

## §2 现状事实（四项实测）

### 2.1 技术栈与 Unity 零交集

```
7-通用引擎/rt/*.py   → Python 3.13（服务端：http_api / sim / loops / ws / protocol_bin）
7-通用引擎/rt/*.lua  → Lua 5.x（DST 运行时 + rt_boot 胶水）
7-通用引擎/rt/*.js   → 浏览器客户端（无框架、无构建链）
find . -name "*.cs" -o -name "*.sln" -o -name "*.unity"  → 空
```

**零 C# 依赖、零 .NET 运行时、零引擎资产格式。** 这是实测结果，不是印象。

Unity 编辑器内核 = C# + C++（C++ 部分完全闭源）。C# 那部分即使读懂了，迁移到本项目要**翻译两次**：C# → Python（服务端权威逻辑）、C# → 浏览器 JS（编辑器 UI）。而 Unity 编辑器 UI 建立在 IMGUI / UI Toolkit 上，浏览器里没有对应物，翻译损耗接近 100%。

### 2.2 剩余工程量与最大短板

- 剩余 **28.3 人月**（13 域 / 102 模块，从零 57.2，已投入折算 28.9）
- 对标加权 **42.8/100**，四维：功能 45.8 / 性能 50.0 / 工具链 46.3 / 生态 19.3
- 最刺眼单点：**编辑器内核 1.5/5**

### 2.3 关键路径是"定契约"，不是"抄界面"

下一批要做的 M1-1（命令栈）+ M1-3（schema 检查器）合计 1.6 人月，它们解决的是：

- 一次改动怎么被**完整描述**（do + undo 两半）
- 描述怎么**合并**（连续拖拽 60 帧应该是一步撤销）
- 描述怎么**跨进程**（客户端发命令 → 服务端权威执行 → 客户端校正）

这三件事的产出是**接口与语义**，不是像素。而"抄界面"抄不到接口语义 —— 抄到的只是"Inspector 长这样"，这对 1.5/5 这个分数毫无帮助。

### 2.4 最好的逆向素材已经在仓库里

```
02-注释源码/scripts/**.lua   4030 个文件
                             1,534,360 行
scripts/components/          821 个组件
```

关键差别：**这是同一门语言（Lua）、同一个运行时（我们真的在跑它）、同一类玩法（饥荒风格）**。
在它上面做逆向，结论能当场用 `rt_boot` 跑一遍验证；
在 Unity 上做逆向，结论要跨越语言与架构才能落地，落地时大概率已经变形。

## §3 四个候选逐个评估

### 3.1 Unity — 收益中、风险高、成本高 → **不装**

**潜在收益（真实存在的部分）**

1. 编辑器内核的**交互契约**：Inspector 的属性绘制注册、Prefab 覆盖的显示与回退、Scene 视图的 Gizmo 拾取优先级。这三件正好卡在 1.5/5 上。
2. 2.5D 相关：Unity 没有原生 2.5D，但 `Sprite Renderer` 的 `Sorting Layer / Order in Layer` 与 URP 的透明排序，是"双路径排序"的一种成熟取舍。
3. 团队认知校准：让"Unity 级"这个目标有具体形状。

**风险**

| 风险 | 具体表现 |
|---|---|
| **法务（红线）** | ToS 17.3.1 明文禁止反编译/逆向，见 §4.1。**"逆向推演"这个词在 Unity 语境下本身就是被禁止的行为类别** |
| 抽象误移植 | Unity 的 `GameObject/Component` 是 C++ RAII + 托管 GC 的产物。把 `Update/FixedUpdate` 生命周期搬进本项目会**直接重现已踩过的坑**：本项目 `push_action` 是异步的，当场读血量差永远为 0（见 §9ch 记录） |
| 时间成本 | 下载 + 激活 + 建工程 + 观察记录，估算 2~4 小时/次（未实测），产出不可进仓 |
| 诱导过度设计 | 看到 `SerializedProperty` 的反射机制，很容易想在自己的引擎里也做一层 —— 但我们的实体是 Lua table + JSON，**没有需要反射的类型系统** |

**成本**：安装包与平台模块通常为数 GB 级（未在本机实测），外加许可证激活流程。

**结论**：需要它的**知识**，不需要它的**软件**。它公开的那部分源码足够（§5）。

### 3.2 Cocos Creator — 收益低-中、风险低、成本中 → **不装，但读引擎源码**

**事实**：`cocos/cocos-engine` 是 MIT（TypeScript 34.5% + C++ 51.2%）；**Cocos Creator 编辑器本体闭源**。
Cocos 4（2025-12 公告）宣布把编辑器核心能力 Headless 化、CLI 化并纳入 MIT 仓库 —— 按公告属**进行中**，尚未成为可直接引用的稳定参考。

**它对本项目的独特价值**：客户端的语言同源（TypeScript/JS）。如果想看"浏览器里怎么组织节点树 + 渲染排序 + 资源加载"，Cocos 引擎源码的迁移成本比 Unity 低一个数量级。

**但**：我们客户端是**无框架、无构建链**的单文件 JS（`rt/client.html`），引入 Cocos 的组件系统等于换掉现有客户端。这个交易的收益是负数。

**结论**：装编辑器无价值；**需要时读 `cocos-engine` 的 2D 渲染与节点树源码**即可，MIT 允许读也允许借鉴实现思路（MIT 允许更多，但仍建议只借鉴思路、不复制代码，保持本仓库许可清晰）。

### 3.3 Godot — 收益中-高、风险低、成本低 → **唯一"装也划算"的，但先读**

**事实**：

- 引擎 **MIT**，且**编辑器本身也是 Godot 游戏**（`editor/` 目录全开源）—— 这是它能回答"编辑器内核怎么实现"的根本原因
- 有 **Web Editor**（`editor.godotengine.org`），浏览器直接跑，**零安装**
- `UndoRedo` 的设计对 M1-1 直接可用（§5 已抓到完整接口）

**为什么它的参考价值反而高于 Unity（对"编辑器内核"这一项）**：
Unity 的编辑器 UI 层是 C#（可读）但底层是闭源 C++；Godot 的编辑器从 Inspector 到 UndoRedo 到场景序列化**全在同一棵 MIT 源码树里**，可以一路读到底。

**成本**：下载约百 MB 级（未实测）；Web 版零成本。

**结论**：**先读源码，需要看动态行为时再装**。装的话它是唯一候选。

### 3.4 饥荒（DST）源码 — 收益高、风险低、成本已在沉没 → **提为主对标源**

**已付成本**：已在仓库（`02-注释源码`），已注释，已在用。

**它对"2.5D + 饥荒风格"的覆盖度是 Unity 比不了的**：

| 我们要的东西 | Unity 能给 | DST 源码能给 |
|---|---|---|
| 2.5D 场景排序 | 通用方案（需自己裁剪） | 目标形态本身（`scml` / `animstate` / 深度排序） |
| 角色控制手感 | 需自己调参 | 实际参数（`tuning.lua`） |
| 物品 / 合成 / 科技 | 无（要自己设计） | 完整实现（821 个 component） |
| 世界生成 / 季节 / 昼夜 | 无 | 完整实现 |
| 语言 ↔ 运行时 | 跨语言 | **同语言同运行时** |

**结论**：这是本项目**唯一应该大规模投入的逆向对象**，而且投入方式已经验证有效（读 → 结论 → 进计划 → 写判据）。

## §4 法务：这一节决定"能不能做"，不是"值不值得做"

### 4.1 Unity 服务条款 17.3.1（中文版原文）

> 您知悉并同意，软件的各个部分（包括但不限于源代码及各个模块或程序的特定设计和结构）属于机密信息……据此，**您同意不对软件进行全部或部分反汇编、反编译、修改或逆向工程**，且不会允许或授权第三方进行该等行为……
>
> 尽管上文规定禁止实施反编译，但您可以**仅出于检查 Unity 通用语言基础架构（CLI）程序集功能的目的**对其进行反编译，以便理解或改进您的项目或软件的任何编辑器扩展性能。

英文版第 (e) 条更宽，禁止的是：

> Engage in any **decompiling, disassembling or other reverse engineering** or otherwise attempting to **discover, learn or study the structure or organization, underlying algorithms or other internals, protocols, data structures** or other externals, or the source code of the Offerings…

**注意最后这半句**：禁止的不只是"反编译"这个动作，还包括"试图了解/研究其内部结构、算法、协议、数据结构"。**"逆向推演"字面上就是这一条。**

唯一例外（反编译 CLI 程序集）的限定用途是"理解或改进**你的项目**或**你的编辑器扩展**的性能"。我们不是在做 Unity 编辑器扩展，**这个例外不适用于本项目**。

### 4.2 但"对标"不等于"逆向"——这条边界必须说清

条款限制的是**对 Unity 软件本体**（二进制、源码、内部结构）的行为，不是限制"独立开发一个引擎"。因此以下三类行为是安全的：

| 行为 | 是否安全 | 依据 |
|---|---|---|
| 读 Unity **公开文档**、教程、官方博客，整理模块清单 | ✅ 安全 | 公开资料 |
| 读 **UnityCsReference**（官方公开的 C# 参考源码） | ✅ 安全，**有限制** | Reference-Only 许可：可读、**不可修改、不可再分发** |
| 反编译 Unity 编辑器二进制 / 抓它的内部协议与数据结构 | ❌ **禁止** | 17.3.1 + (e) |

还有一条容易被忽略的 (o)/(p)：不得"开发、分发与 Offering 相似或竞争的产品"或"复制其任何 ideas/features/functions/graphics"。
**解读边界**：这是对"**用 Unity 软件去开发竞品**"的限制；独立开发引擎、参考公开资料做功能对标，不落入该条。但这条的存在进一步说明：**不要把 Unity 的东西搬进代码**，只提炼抽象与契约。

### 4.3 落地到本项目的三条硬规矩

1. **不做任何 Unity 二进制反编译**。需要接口信息，读 `UnityCsReference`。
2. **Reference-Only 的代码一行都不进本仓库**。只允许产出"接口签名 + 语义描述 + 我们自己的实现"。
3. **法务风险不进计划估算**。凡是"收益依赖法律灰区"的加速手段，一律视为不可用 —— 它省下的时间是借来的，还的时候是项目级的。

## §5 实证：1 分钟 vs 数小时

本节的目的是把"读源码够不够用"从观点变成实验。

### 5.1 实验

| 项 | 内容 |
|---|---|
| 动作 | 两次 HTTP 读取：`UnityCsReference/Editor/Mono/Undo/Undo.bindings.cs`（19 KB）、`godot/core/object/undo_redo.h` |
| 耗时 | 实测约 1 分钟（含两次请求与整理） |
| 产出 | 两套撤销系统的完整公开接口面 + 分组语义 |
| 对照成本 | 装 Unity 观察同样信息：估算 2~4 小时（下载/激活/建工程/观察），**且拿不到分组语义的内部约定** |

### 5.2 拿到的东西（节选，均为原始接口）

**Unity `Undo`**（记录模式 + 分组）

```
RecordObject(Object, string name)                    // 记录被改前的属性差异（diff）
RegisterCompleteObjectUndo(Object, string name)      // 记录完整快照（重）
RegisterCreatedObjectUndo(Object, string name)       // 标记"新建"，撤销时销毁；对 Transform 抛 ArgumentException
IncrementCurrentGroup()  GetCurrentGroup()  SetCurrentGroupName(string)
CollapseUndoOperations(int groupIndex)               // 把该组起的多次操作折叠成一步
RevertAllInCurrentGroup()  RevertAllDownToGroup(int)
undoRedoEvent(UndoRedoInfo{ undoName, undoGroup, isRedo })
isProcessing { get; }
```

**Godot `UndoRedo`**（操作序列 + 合并模式）

```cpp
enum MergeMode { MERGE_DISABLE, MERGE_ENDS, MERGE_ALL };

void create_action(name, MergeMode, bool backward_undo_ops);
void add_do_method(Callable);      void add_undo_method(Callable);
void add_do_property(Object*, StringName, Variant);
void add_undo_property(Object*, StringName, Variant);
void add_do_reference(Object*);    void add_undo_reference(Object*);
void commit_action(bool execute = true);
bool undo(); bool redo();
uint64_t get_version() const;       void set_max_steps(int);
```

内部结构：`Action { String name; List<Operation> do_ops; List<Operation> undo_ops; uint64_t last_tick; }`

### 5.3 由此得到三个设计决策（这才是有价值的部分）

**决策 1：采用 Godot 的"操作序列"形态，不采用 Unity 的"先登记后修改"形态。**

理由是本项目的 `push_action` **本来就是"描述一条操作"**（`{type, target, args}` → 发往服务端）。
Godot 的 `add_do_method / add_undo_method` 与它同构，只差一个 `undo_ops` 和一次 `commit`；
Unity 的 `RecordObject` 要求"先把对象状态登记进撤销栈，再改对象"，在没有编辑器帧、且改动要过服务端的架构里无法照搬。

**这不是"抄 Godot"，是我们的架构选择了它：命令已经是既成事实，撤销只是给它补上另一半。**

**决策 2：合并策略挂在"操作类型"上，不挂在"编辑器帧"上。**

Unity 用 `IncrementCurrentGroup()`（由编辑器帧驱动）+ `CollapseUndoOperations`（事后折叠）。
浏览器里没有"编辑器帧"这个概念（拖拽是一次 pointermove 流，松手才结束），所以选 Godot 的 `MergeMode`：
`MERGE_DISABLE`（离散操作）/ `MERGE_ENDS`（连续拖拽，只合并首尾）/ `MERGE_ALL`（滑动条类，全合并）。

**决策 3：撤销栈记录"实体级完整快照"，不做字段级 diff。**

这条**必须用我们自己的数字定**，不能抄。实测当前存档：

```
deploy/logs/world-8799.json     35 实体 / 8,347 B（全部实体）
单实体平均 238 B   最大 850 B   字段：y x z rot guid prefab components
```

推算：30 步撤销栈 × 单实体 238 B ≈ **7 KB**（只记被改动的实体）。
即使世界涨到 400 实体，单步也只记"这一次改的那几个"，成本仍是 KB 级。

所以：**没有理由为了省空间去实现字段级 diff** —— 而 diff 恰恰是最容易漏字段、最容易出"撤销后属性没回去"的地方（Unity 也为此提供了 `RegisterCompleteObjectUndo` 这个"全快照"逃生门）。

这条decision 的价值在于：**它是本项目的实测数字推出来的，不是抄来的**。如果哪天真抄了 Unity 的 diff 模式，反而会引入一个我们不存在的性能问题。

## §7 明确建议

### 建议 1：不装 Unity、不装 Cocos Creator。写入计划，不再讨论。

"不再讨论"很重要 —— 这类问题每次卡壳都会被重新提一次，每次都要重新论证。本次给的是**可引用的否决理由**（法务 + 技术栈 + 机会成本），下次直接引用。

- 产物形式：`参考源登记表`（§8），每条必须写"提炼出的结论"与"落到哪个决策"

## §9 什么情况下这个决定应该重审

提前写清重审触发条件，避免"因为当时这么定的"变成教条：

1. **M3 渲染阶段**需要"正确画面"做视觉对照，且 DST 源码不足以判定某效果（例如光照/透明排序的边界情况）→ 装 Godot 做一次性对照。
2. **M2 编辑器 UI 出现"我们不知道业界怎么处理"的具体交互**（如多选 Inspector 的混合值显示）→ 读 Godot 编辑器源码；仍无法判定才考虑装。
3. **项目目标从"能开发简单游戏"升到"第三方可用"（G2）**，且需要说服外部开发者 → 此时需要"与成熟引擎的对照材料"，可重新评估取证预算。
4. 若将来出现 **Godot 无法覆盖而 Unity 独有的能力**（如特定平台的资产管线），且该能力进了关键路径 → 单独评估，但法务结论（§4）不变。

**不在重审范围**：Unity 二进制的反编译。这条不因任何工程理由改变。

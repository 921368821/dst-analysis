# 联机就绪改造：勘察结论与四批计划（批146）

> 目的：为「单人 + 好友联机（主机权威）」打地基，并为后续交接、专用服、公共局留位置。
> **判据不是「代码里有没有这个类」，而是「四条假设成不成立」**——假设破了，后面每一步都要重构。

## 1 · 四条假设的实测现状

| # | 假设 | 实测证据 | 判定 |
|---|---|---|---|
| 1 | 权威不假设自己有本地玩家 | `PlayerController` 是普通模块，`poll` 是注入的 `InputSnapshot` 来源 | ✅ 结构未锁死（但**尚无权威概念**） |
| 2 | 实体身份与连接解耦 | `NodeRecord.id` 进快照；`loadScene` 用 `spawnImmediate(…, r.id)` 原样还原 | ✅ id 稳定；❌ **没有任何所有权字段** |
| 3 | 任意 tick 可导出完整快照 | `saveScene(scene)` 是纯函数（不读时间、不持状态），带 `format` 版本号 | ✅ 能力已具备；❌ 缺「任意 tick 往返一致」的判据 |
| 4 | 不假设进程内只有一个世界 | 全仓 `export const world` / 单例 getter 零命中 | ✅ 满足 |

结论：四条里 **两条已满足、一条只差判据、一条（所有权）为零**。这意味着不需要为联机重构仿真层，只需要补上缺的两小块。

## 2 · 真正的关键缺口不在四条假设里

**全仓 `grep -i intent` 零命中。** 玩家与 AI 现在走两条并行路径，各自有独立的执行点：

| 角色 | 决策产出 | 执行落点 | 单位 |
|---|---|---|---|
| 玩家 | `directionFromMap(map, snap) → {dx, dz}` | `player-controller` 内部算位移 | 方向向量 |
| AI | `MobBrain` 的 `Decision.cell`（目标格） | `ai/move.ts:308` 直接 `node.setLocalPosition` | 目标格 |

两套单位、两个执行点。**这就是「玩家与 AI 逻辑复用」没实现的具体形态**，也是为什么现在补最便宜：再往上长分支，两条路径的差异会渗进更多模块。

## 3 · Intent 层最小切片（批147 的设计）

### 3.1 只做移动，不做动作

动作（攻击 / 使用 / 拾取）牵扯 combat、inventory、crafting 三块，面太宽。**先只归一「移动」一种意图**，把结构立起来；动作意图沿用同一形状，后续按同一模板加，不需要重新设计。

### 3.2 意图只是数据

```text
Intent = { kind: "move.dir",  dx, dz }        // 方向型：键盘 / 摇杆
       | { kind: "move.cell", cell }          // 目标型：AI / 点击移动 / 寻路
```

- 不带执行逻辑、不带引用、可序列化 —— 这三条决定了它能同时服务于联机（要发网络）、回放（要存盘）、AI 训练（要采样）。
- **谁能产意图**由 `IntentSource` 接口描述：`produce(tick) → Intent | null`。实现有四个：玩家、AI、回放、脚本 Bot。

### 3.3 执行点归一到两个纯函数

不是新建一个"执行器模块"（那会引入新的生命周期与顺序问题），而是把「意图 → 位移」这一步抽成两个纯函数，玩家与 AI 都调用它们：

| 纯函数 | 输入 | 输出 |
|---|---|---|
| `dirStep(intent, speed, dt)` | 方向意图 | 位移向量（含对角线归一化） |
| `cellStep(intent, grid, from, path, cursor, speed, dt)` | 目标格意图 + 当前寻路状态 | 位移向量 + 新游标 |

**为什么是纯函数而不是模块**：纯函数可以被判据直接打、被变异直接打、不参与调度顺序、不持有状态。2570 条现有判据全部保留，行为等价性由它们守着——一旦抽错，立刻红。

### 3.4 判据（批147 的验收）

| 判据 | 抓什么 |
|---|---|
| 方向意图在两个不同起点产出同一位移 | 玩家与 AI 走同一段代码 |
| 目标格意图在等价网格上产出同一路径首步 | 同上 |
| 越界 / 不可走的意图被同一处拒绝 | 「拒绝」只有一份，不会一边拒绝一边放行 |
| 旧路径全绿（现有判据不删不改） | 抽取是等价的，不是重写 |

### 3.5 变异（批147 的验收）

- 删掉对角线归一化 → 「斜着走快 41%」那条判据必须红。
- 把 `cellStep` 的不可走校验删掉 → 「越界被拒绝」必须红。
- 让 AI 侧绕过纯函数直写位置 → 判据 2 必须红。

### 7.1 一个需要拍板的冲突：寻路状态要不要进快照

`ai/move.ts` 的 `Mover` 把 `path` / `cursor` / `goalCell` / `arrived` 全部排除在 schema 之外，注释给的理由是：

> 路径是「从当前局面推出来的」，存档再读回来时局面已经变了；把它存进去反而会让读档后的第一 tick 沿一条过期的路走。

**这个理由在存档语义下成立，在回滚语义下不成立。**

| 语义 | 局面是否一致 | 路径是「过期的」还是「必须一致的」 |
|---|---|---|
| 存档 / 读档（新会话） | 不一致（世界可能已推进） | 过期 ⇒ 重算才对 |
| 回滚到 tick N（同一会话） | 完全一致 | **必须一致** ⇒ 重算可能分叉 |

两条路，代价不同：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 模式参数** | `saveScene(scene, { mode: "rollback" })` 时把寻路状态也导出去 | 快照多一个维度；每种组件都要区分「可持久」与「须回滚一致」两类字段 |
| **B. 保证重算确定性** | 回滚后允许重算，靠「同局面 + 同种子 ⇒ 同路径」保证一致 | 寻路必须完全确定（无浮点累积、无缓存顺序依赖），要单独验证；一处不确定就整体失效 |

批148 的判据守的是存档模式的默认行为，当时没有替你做选择。**批151 定了：选 A。**
理由不是「哪个更好写」，而是 **B 的前提现在不成立**：

| 维度 | A · 模式参数 | B · 重算确定性 |
|---|---|---|
| 专业性 | 商业引擎与回滚网络代码（GGPO 一类）默认「快照全量状态」，从不假设重算一致 | 只在确定性锁步（RTS / 格斗）里用；代价是整个数值层改定点、迭代序全部固定 |
| 可扩展性 | 哪一类状态要进回滚，就在**那个组件**的清单里加一个名字；验证单元就是那个组件 | 每新增一处浮点、一处 `Map/Set` 遍历、一处缓存，全局假设就被打破；失效是**静默**的（世界悄悄分叉，找不到证据） |
| 对后续开发 | 编辑器撤销、回放、联机回滚、AI 采样共用同一份「快照 + 还原」能力 | 只对锁步有用；其余场景仍要另做一套快照 |

决定性的一条：本仓库的仿真层**到处是浮点**（`Math.hypot`、位移累加、`Vector2`），迭代序依赖 `Map/Set`。
要让 B 成立，得先把数值层换成定点并固定所有迭代顺序 —— 那是重写，不是选型。
而 A 的默认模式行为**逐字节不变**，成本只有一处参数透传。

### 7.2 方案 A 的落地形态（批151）

| 落点 | 内容 |
|---|---|
| `ComponentSchema.rollback` | 只写**字段名**，不写 `FieldType`：这些是运行期状态，编辑器不编辑、资产不进管线 ⇒ 类型信息没有消费者 |
| `Component.save(opts)` | 只有 `mode === "rollback"` 才额外导出清单里的字段；默认模式与之前逐字节相同 |
| `Component.load` | **不需要模式**：快照里有就还原、没有就保持出生值 ⇒ 存档快照读回来路径是空的，是自然结果 |

| `Mover.schema.rollback` | 七个：`path` / `cursor` / `goalCell` / `arrived` / `failCell` / `retryTick` / `stuckTicks`（后三个是**历史**，不是局面的函数） |

判据 5 条（`snapshot-any-tick.test.ts`）：模式真的切换了行为 / 还原逐字段相等（含路径内容）/
导出仍是纯的 / 存档侧没被污染 / **声明不许漏**（反射求差集）。
变异 M894–M898 全部被抓住，其中 M897 与 M898 是两类不同的漏法：**清单漏字段**与**接线漏透传**。

## 9 · AI 的两条线（2026-10-30 定范围）

用户明确：AI 包含两方面 —— ① 给角色设置 AI 逻辑；② 后期本引擎可以接入 AI 开发游戏。
两者不是一件事，依赖方向是**单向**的。

| 线 | 是什么 | 现在有什么 | 缺口 | 排期 |
|---|---|---|---|---|
| ① 角色 AI 逻辑 | NPC 的决策：追击 / 逃跑 / 采集 / 选目标 | `MobBrain`（决策 → 目标格）+ 批147 的 `IntentSource` 接口 | 只有一种手写决策器；没有行为树 / 状态机 / 效用的可组合层；没有可视化调试 | P3（P2 之后） |
| ② AI 辅助开发 | 用模型生成关卡 / 资产 / 脚本，或作为「另一个作者」进编辑器 | 资产管线、编辑器会话、脚本运行时、快照**全是纯数据** | 没有「给模型的稳定入口」：schema 描述 + 校验 + 失败可回滚 | 线一之后 |

**为什么顺序不能反过来**：② 要的是「机器能安全地写游戏」，前提是每一处改动都是**纯数据、可校验、可回滚**。
线一（把决策变成可序列化的 `Intent`）正在把 AI 相关的一切变成数据；先做 ② 只会得到一堆
「模型改了但没人能证明它改对了」的东西。

### 9.1 专业引擎的 AI 是怎么实现的（对照）

| 层 | 主流做法 | 为什么主流选它 | 本引擎的对应物 |
|---|---|---|---|
| 决策 | 行为树（UE / Unity Behavior）或效用 AI（Sims；饥荒是 brain + behaviour tree） | 行为树能被非程序编辑；效用 AI 能表达「哪件事更值得做」 | `ai/behavior.ts`（`Board` + `AiAgent` + `AiModule`，树是**纯数据**）**已存在，但没接到怪身上**；怪走 `MobBrain`（手写决策器） |
| 执行 | 决策只产出「意图」，由统一的移动 / 动作执行点落地 | 决策与执行解耦才能复用（玩家 / AI / 回放同一套） | 批147 的 `Intent` + `dirStep` / `cellStep` ✓ |
| 感知 | 黑板（blackboard）每拍刷新「世界事实」，决策只读黑板 | 决策不直接读世界，才能被测试、被回放、被快照 | `ai/perception.ts`（视野 / 记忆 TTL / 排序）✓（产出 `Sensed[]`）；但**决策仍直接读 scene** ⇒ 批153 补了 `MobFacts` |
| 调试 | 可视化当前跑的是哪个节点 + 黑板内容 | 没有它，AI bug 只能靠猜 | `AiModule.board(agentId)` 能读黑板；**当前跑到哪个节点没暴露** ⇒ 仍缺（批153 给了 `reason` 与 `MobBrain.facts()`，是第一块） |

> **⚠️ 更正（批153 实测）**：本表上一版写「感知层缺、决策层只有雏形」，那是凭
> `MobBrain.decide` 直接读 scene 的印象写的，**与仓库实际不符** —— `ai/perception.ts`、
> `ai/targeting.ts`、`ai/behavior.ts`、`ai/team.ts` 都在，且都有判据。
> 真实的缺口是**接线与分界**，不是「没有这几层」：
> ① 行为树没有被任何玩法使用（只有 `ai-module.test.ts` 在测它）；
> ② 感知产出的是 `Sensed[]`，而决策**绕过它直接读场景**，所以决策无法脱离场景测试/回放；
> ③ 调试层没有「当前节点」与「为什么这么决定」。
> 教训与 `MEMORY.md` A14 同源：**判断「缺什么」要先 grep 再下结论**，
> 凭一处调用点的印象概括整层，会把「已经有的东西」也列进待办。

这条对照的用处是把「我们差在哪」说具体：**执行层对齐（批147）、感知能力有（batch 5x）、
分界与接线上缺（批153 补了分界，接线是 P3 的下一块）**。
顺序是固定的 —— 先让决策只读黑板（纯数据），才谈得上行为树接线，也才谈得上可视化调试。

### 9.2 批153 落地：`MobFacts`（感知 → 决策的分界线）

| 文件 | 内容 |
|---|---|
| `src/extensions/mobs/mob-facts.ts` | `MobFacts` / `MobCandidate` / `MobGrudge` / `Decision`（带 `reason`）、`mix32`、`wanderTarget`、`chooseFromFacts` |
| `src/extensions/mobs/mob-brain.ts` | `decide` = `sense`（读世界 → facts）+ `chooseFromFacts`（纯）；新增 `facts(agentId)` 供面板 |
| `tests/extensions/mob-facts.test.ts` | 11 条（含两条**手写黑板**的判据） |
| 变异 | M908–M913 六条全部被抓住 |

**为什么决策函数签名里不许有 `Scene`**：那是「决策偷读世界」这件事的**类型级**阻止，
不是纪律。只要签名里有它，将来总会有一次「顺手读一下朝向」；而那句一写，
回放重算、行为树接线、调试面板就都得各自再抄一遍读世界的代码。

**手写黑板是本批最有用的一招**：有两类局面世界造不出来（有仇人时感知被跳过 ⇒ 永远没有
「既有仇人又有可见候选」的黑板；`selfCell = -1` 时漫游格也是 -1），而它们正是优先级的边界。
纯数据 ⇒ 判据可以**直接造**这些局面，不必再为了测一条 `if` 把世界摆成半不可能的形状。

**一处等价变异的诚实记录**：`wanderTarget` 的 `selfCell < 0` 检查在当前网格下不可观察
（`cellZ(-1) = 0`，而 `isWalkable` 要求 `cz > 0`，六个候选全不可走 ⇒ 仍返回 -1）。
保留检查（防御性），不为它造变异条目。

```
  check   能找到自己（selfCell >= 0）—— 否则整棵树失败 ⇒ 这一拍没有决定
  selector 主体
    sequence 敌对            ← 只有挂了攻击组件的生物才追
      check 凶不凶
      selector 挑目标
        sequence 记仇 → check 有仇人 → do 追仇人
        sequence 看见 → check 看得见 → do 追最近的
    sequence 漫游
      check 有漫游格（-1 = 孤岛 / 界外）
      do 漫游
```

四个 kind 全用上，**没有为这棵树新增任何原语**。op 名是玩法词汇（`mob.hasGrudge`）而不是
通用原语（`num.gt`）：后者会把树撑到二十个节点，而「记仇优先」这种语义消失在键名里。

**三条契约，每条都对应一个静默 bug：**

| 契约 | 破掉之后的症状 |
|---|---|
| 黑板只放数字，`MobFacts → Board` 只映射一次 | 树能直接摸 `facts.visible[3]` ⇒ 存不了档、进不了指纹、编辑器导不出 |
| 每拍先 `clear()` 再全量写 | 一块板服务全部生物 ⇒ B 继承 A 的仇人（「一群怪围着同一具尸体」） |
| 树必须瞬时（`memorySize() === 0`） | 决定带上不在快照里的历史 ⇒ 回滚到 tick N 之后行为分叉 |

**规范与编译产物**：`chooseFromFacts` 留在 `mob-facts.ts`，身份是**语义规范**；树是它的编译产物。
判据拿 48 组事实逐条对账两者。这不是两份实现 —— 没有对照，就分不清「树被改坏」与
「规范被改坏」，而两者都只表现为「这只怪的行为有点怪」。

在那之前，树还只是代码里的一个常量。

### 11.1 为什么是 `AssetId`，不是内联 JSON

| 方案 | 好处 | 代价 |
|---|---|---|
| **资产引用（选中）** | 场景只存一个字符串 ⇒ 不动序列化 / 零值 / 编辑器控件；一份树被一群怪共享（改一处全群生效）；资产系统能算「谁用了它」 | 运行期要一次 id → 树的**同步**解析（资产装载是异步的） |
| 内联 JSON | 一处改一处，无需解析 | 每只怪存一份（「调所有猎狗」要逐只改）；存档随生物数量膨胀；编辑器要一个嵌套对象控件 |

`TreeLibrary` 就是为了付掉那个代价而存在的：**只管「id → 已校验的树」，不管 IO**。
谁来把内容送进来是导入器 / 编辑器 / 宿主启动时的事 —— 都有一个明确的时刻，
而「每拍去磁盘找一下」不该是决策路径的一部分。

### 11.2 五个决定（每条对应一个静默 bug）

| 决定 | 破掉之后的症状 |
|---|---|
| 序列化规范化（键序固定 / 末尾换行） | 同内容的树在两个文件里 diff 出无关改动，`sourceHash` 每次都变 ⇒ 每次重导入 |
| 校验只有一份（`AiAgent.create`），版本闸门拒绝更新的格式 | 编辑器里看着没问题，进游戏第一拍就抛 / 新字段被静默丢掉 |
| `put` 是校验点，**失败不改 `revision`** | 坏配置进了库（世界里跑着一棵坏树）/ 一次坏配置让所有怪白白重编译一遍 |
| `revision` 让缓存整批作废 | 编辑器里改了树，要重启进程才生效 —— 而人会以为是「改错了」 |
| 缺 id 不抛 + 三件套（计数 / 名单 / 面板） | 「配了树但没生效」与「没配」在面板上一模一样，世界看起来完全正常 |

另外两条边界：
- **模板写了 `tree` 但 `mobs.ai` 没注册 ⇒ 硬失败**（`MOB.SPAWN_FAILED` 里点名类型）。
  静默用默认树等于「配了不生效」，那是最难查的一类。
- **模板没写 `tree` ⇒ 不挂组件**。给每只都挂一个空值组件的话，存档里会多出一条
  `{"type":"mobs.ai","tree":""}`，而它表达的信息是零。

### 11.3 判据与变异（怎么分辨「真接上了」）

四条地基见 `PROGRESS.md` 批155 条目。这里只记一条方法论：

> **同一个世界里两只怪走不同的树、给出不同的决定** —— 这是「按实体选树」唯一的分辨手段。

### 12.1 为什么身份是「路径」，不是哈希

`core/asset` 的 `stableIdFromPath` 已经把路径变成过 id（FNV-1a → `p1abc123`）。这里**故意不那样做**：

|---|---|---|
| 哈希（`p1abc123`） | 与 `AssetMeta` 的身份体系一致；路径可随便改 | 组件字段里没人读得懂 —— 而编辑器对这个字段给的是**文本框**，不是资产选择器 |
| **路径（`ai/hound`）** | 看一眼组件就知道是哪个文件；改错时 `miss ai/hound` 直接指出文件名 | 改路径 = 换 id（引用会以 `missing` 被数出来，不是静默失效） |

选路径的理由只有一条，但它是决定性的：**「策划能改 AI」的前提是这个字符串人能读写**。
代价用批155 的三件套兜住（`treeFallbacks` / `missingTrees` / 面板 `miss <id>`）。

### 12.2 四个决定（每条对应一个静默 bug）

| 决定 | 不做会怎样 |
|---|---|
| **一个坏文件不阻断整批**，失败进报告并**带路径** | 「任何失败就整体失败」听着正当，但策划存了个半成品 ⇒ 五棵树全不装 ⇒ 所有生物退回内置树，症状是「怪突然都变笨了」 |
| **同一批撞 id ⇒ 后者失败、先到的保留** | 静默覆盖的症状是「我改的那棵没生效」（生效的是另一只文件），而两棵树都合法、都能跑 |
| **跨批次重复不算错**（那是热重载） | 判重判到跨批次 ⇒ 编辑器每保存一次就报一次假错 |
| **HUD 两格数：`ai n/m`** | 只写 `n` ⇒「一棵没装上」与「一棵没配」都是 `0`；只写 `m` ⇒ `0` 既是「全对」也是「没有树」 |

## 13 · 批157：树的可视化编辑（编辑器里的最后一段）

批155 把树做成资产，批156 让宿主把文件装进库 —— 但**改树的方式仍然是打开 JSON 敲文本**。
这一批在编辑器里盖一块树面板：点资产列表里的一份 `.tree.json` 就出来，行可点、可加、可删、可拖、
可改 `op`，顶部一行说清「现在装不装得上」。

### 13.1 编辑与装载是两条相反的规矩

| 场景 | 规矩 | 理由 |
|---|---|---|
| 装载（`tree-asset` / `tree-library`） | **硬失败**：坏树进不了库 | 一只怪第 500 拍才炸，比打开就说不行贵得多 |
| 编辑（`tree-edit` / 面板） | **不拦**：随便放，红字说不行 | 「加一个 selector 再往里放分支」必然经过「空容器」那一瞬 —— 每步硬校验的话这个动作做不出来 |

所以结构操作（增 / 删 / 移 / 改字段）**只管结构**，合法性交给 `treeIssue`（它只是 `checkTree` 的
一次投影 + 把 `detail.path` 映射回下标路径），而**导出**那一刻才重新硬校验一次。

### 13.2 「错误要带位置」是一条契约，不是巧合

`treeIssue` 靠字符串相等把校验器的报错对到面板的某一行上，于是「每个校验错误都带 `detail.path`」
成了一条跨模块约定。这一批**当场发现它并不成立**：重复 id 那条错只带 `detail.id` ——
于是最隐蔽的一类错（两个节点共用一份记忆）在面板上是「树坏了，但没有任何一行变红」。
修法是给那条错误补 `path`，并加一条判据：**六个坏样本的错都必须带位置，且消息以那个位置串开头**。

### 13.3 拖拽的两种错法，以及为什么按内容验

| 做法 | 结果 |
|---|---|
| 先摘源、再按**原来的**目标下标插入 | 源在目标左边时静默落错位置（不报错、行数不变） |
| 先摘源、再按**目标父的引用**插入 | 摘节点会重建它到根的那条链，而「同父换序」的目标父正好在那条链上 ⇒ 找不到 |

本批采用「摘掉源之后修正下标」（`pathAfterRemoval`，只有「同父且排在源之后」减一）。
判据看**内容**：把 `mob.roam` 拖进 `mob.pick` 之后，`pick.kids=3`、`sight.kids=2`、`body.kids=1` ——
行数在三种（对的、落错分支的、没动的）情形下都一样。

### 14.1 真实缺口不是「AI 不会打」

`combat-module` 早就会按决策给的目标出手。缺的是三件别的事：

| 缺口 | 具体形态 | 后果 |
|---|---|---|
| 两条路 | 玩家在宿主里自己调 `attack()`、AI 在模块里自己调 | 友伤 / 射程 / 失败分类 / 文案各有一份 |
| 一个字 | 决策只有 `hunt` / `wander`，「走过去」与「够得着，打」分不开 | 树无法表达「停下来打」 |
| 没有回声 | 树知道自己想打谁，不知道上一次打没打成 | 「打不到就换目标」写不出来 |

### 14.2 三态判定

| 判定 | 含义 | 例子 | 决策层该做什么 |
|---|---|---|---|
| `ok` | 世界真的变了 | 掉血 / 进包 / 吃饱 | 继续 |
| `retry` | 这一拍不成，下一拍**可能**成 | 射程不够、冷却没好、暂时饱着、背包满 | 保持目标 |
| `fatal` | 这条路走不通 | 目标死了 / 不存在、没有攻击组件、配置坏了 | 换目标或换计划 |

布尔判定会把前两行压成同一个 false —— 于是树只剩「全都放弃」或「全都不放弃」（抱着尸体走）。

**未知错误码一律 `fatal`**：默认值必须选"症状能被看见"的那一侧。未知码 retry 会让一个配置写错
变成"每拍重试、世界毫无变化、CPU 打满"，症状只是"有点卡"。

### 14.3 结果回报的单向通道

```
combat-module（每次尝试，成功与失败都报）
      → MobBrain.noteOutcome（带 tick）
      → 下一拍的 MobFacts（只认紧邻的上一拍）
      → 黑板 last.verdict / last.target
      → 树（`mob.lastFailed`）
```

- **只认紧邻的上一拍**：读档 / 回滚之后 tick 会跳，陈旧结果比没有结果更坏。
- **默认树不挂这个 op**：开的是能力，不是玩法 —— 既有行为逐字节不变。

### 15.1 协议：两种消息，六个拒绝码

| 消息 | 方向 | 字段 |
|---|---|---|
| `join` | 客户端 → 主机 | `protocolVersion` / `name` / `ticket?`（信封的 `from` 由传输盖章） |

| `join-reply`（拒绝） | 主机 → 客户端 | `to` / `reason` / `detail?`（版本不符时带 `{ host, client }`） |

| 拒绝码 | 含义 | 客户端该做什么 |
|---|---|---|
| `version-old` | **你**比对方旧 | 更新客户端 |

| `behind` | 主机还没有世界 | 可重试 |

**收下与拒绝是判别联合**（`accepted` 收窄）：被拒时类型上就没有 `playerId` / `json`。
判据在**运行时**再验一遍（`playerId` 不在回复里），因为网络数据可以是任何形状。

### 15.2 座位号与端点号是两件事

```
PeerId    「这根线是几号口」  ← 传输决定，重连一次换一个
PlayerId  「你是几号玩家」    ← 主机的握手盖章，掉线重连不变
```

两者今天在环回里都是 0/1，所以「合并成一个数字」看起来毫无代价 —— 而那样一来，
「重连后你还是你」就退化成「重连后你拿到了同一个端口」，且所有归属判据照样全绿。
`session.playerOf` 是这个转换点：主机侧来自 `room.playerOf`，客户端侧来自
`() => joiner.playerId()` —— **两端的来源不同，但都必须来自握手**。

### 16.1 口径：什么算变化量

| 决定 | 理由 | 破掉之后的症状 |
|---|---|---|
| 比的是**序列化之后的记录** | 运行时对象有量化尾巴、`undefined` 键、临时量 | 增量永远非空，带宽优化归零，日志只说「优化没效果」 |
| 节点身份 `id`，组件身份 `type` | 一个节点上同类型只挂一个 | 同一组件被拆成两条、合并时互相覆盖 |
| 十个顶层字段各自独立 | 移动只发 `x` / `y` | 一条字段表漏项 ⇒ 那个字段永远停在旧值，其余九个都对 |
| 组件整块重发 | 组件数据只有几十字节，而字段级要多表达「删键」 | 多了两种编码形式、少了两分带宽 |
| 删除显式列 `removed` | 增量是稀疏的 | 「没出现」被当删除 ⇒ 场上没动的东西全被清空 |
| 空增量照发 | `seq` / `tick` 是「世界停在第几拍」的证据 | 省下的几十字节会变成诊断里的一次假丢包 |

### 17.0 先把「定点化」这笔账量出来

预测成立的前提是一句话：**同 tick、同输入 ⇒ 同结果**。这句话要跨机器成立，缺的不是「定点化」，
而是几处**实现未定义**的运算。按仿真路径逐个量化（`src/` 全域 grep，数字是调用点数）：

| 运算 | 全仓 | 其中落在这条路上 | 在不在账上 |
|---|---|---|---|
| `+ - * /` | — | 全部 | **不在**。IEEE-754 双精度对这四个是逐位规定的，任何平台一致 |
| `Math.sqrt` | 16 | 3 | **不在**。与 `+ - * /` 同属「被标准规定到位」的那一类 |
| `Math.hypot` | ~~12~~ 1 | ~~11~~ 0 | **不在**（批162 收口）。全仓只剩 1 处（`editor-entry` 的拖拽阈值，不进仿真）。12 处换成 `foundation/math/scalar.ts` 的 `planeLen(dx, dz)` = `sqrt(dx²+dz²)`，由 `tools/determinism-scan.mjs` 守着不许回来。实测：`dirStep` 的定义域（9 组方向向量）上两者**逐位相同** ⇒ 换掉不改变任何位置判据；范围外 20 万组有 **39.03%** 差 1 ulp |
| `Math.cos` / `sin` | 5 / 4 | 2（`Affine2.fromTrs`） | **在**。未定义。`rot = 0` 时 `cos=1 / sin=0` 是精确的，所以**今天不出事**；一旦有节点真的转起来，世界坐标就不再可复现 |
| `Math.atan2` | 1 | 1（`motion/facing.ts`） | **在**。未定义。朝向目前只影响表现、不进物理 —— 这条边界要守住，它是一条**约定**而不是一道闸门 |
| `Math.pow` | 7 | 0 | 不在。全在缓动（`tween/easing`）、JPEG 解码、`roundTo` 里 |
| 随机数 | 0（`Math.random` 只出现在注释里） | 0 | 不在。仿真用 `foundation/random.ts` 的 `XorShift128`（同种子同序列） |

**结论：这笔账不是「重写数值层」。** 要让整个仿真层只剩 IEEE 精确运算，需要的是
11 处 `hypot → sqrt`，加一条「节点旋转不进物理」的约束（`atan2` 那条同理）。
11 处已在批162 收口（→ §18）；**实测代价比预估还小：2786 条判据一条都没变**，因为
`dirStep` 的定义域上 `hypot` 与 `sqrt(dx²+dz²)` 本来就逐位相同 —— 改的不是今天的数，
是换宿主之后的数。剩下的是那条**约定**（旋转 / `atan2` 不进物理），它需要一道闸门而不是一次替换。

所以这一批只做窄口：预测**移动**。打斗 / 拾取 / AI 决策不预测 —— 它们读背包、读随机数流、
读每拍缓存（`Map` 迭代序 + 上几拍的决策），预测它们等于猜；猜错的代价不是「抖一下」，
而是「客户端显示我把怪打死了、主机显示没有」。

### 17.1 重放的边界由主机说：收据，不是 tick，也不是 RTT

客户端在两次快照之间攒了 N 步预测。快照落地后要回答：「这 N 步里哪些主机已经算过了？」
算过了还重放 ⇒ 多走；没算过就不放 ⇒ 少走。两种都是位置漂移，而漂移的观感是「人物在滑」，
日志里什么都看不出来。

两种「猜」都不能用：

| 猜法 | 为什么不行 |
|---|---|
| 「快照是第 T 拍，本地 tick ≤ T 的就算算过了」 | 要求两端共用同一个 tick 时钟。客户端中途加入时从 0 开始数，主机已经在第 1000 拍 |
| 「按往返时延估」 | 估错一次就永久偏，而且没法自证（没有任何一个数能反驳它） |

所以主机在**每份**广播里带一张收据：每个实体「处理到发送方第几条意图」（`AckEntry.seq`）。
`seq` 是发送方自己的，与时钟无关。「处理」包含三种结局 —— 执行、被拒、队列满被丢，
三种都要报：漏掉任何一种，那条意图就永远留在客户端的待重放表里，一拍一步地重复应用。

`noteProcessed` 只前移、不回退：真实的传输会让旧的意图晚到（重传、多路复用）。

### 17.2 四个决定

| 决定 | 破掉之后的症状 |
|---|---|
| 重放**覆盖**（从主机坐标重新加），不是累加 | 累加在**无积压时两种算法算出来的数一模一样** —— 一有积压就是双倍位移，而所有「终态一致」的判据都是绿的 |
| 重放只能在 `loadScene` **之后** | 放在之前：整场替换把重放结果盖掉，预测只生效一瞬；终态判据仍然全绿（下一次重放又对了） |
| 发不出去就**不**预测 | 预测的是「主机将会做的事」，不是「我想做的事」。发了没到还本地走一步，那一步的收据永远等不到，玩家看到「松手了人还在滑」 |
| 预测过**同一道归属检查**（读快照带过来的 `owner`） | 不是我的角色也本地先走，主机每拍都按 `not-owner` 拒 ⇒ 橡皮筋，而拒绝计数在涨、看起来像有人在抢角色 |

上限（`maxPredictSteps`，缺省 32）不是为了省内存，是为了**有界**：收据断了（主机不发 / 版本不匹配 / bug）时，
领先量被卡在「上限 + 1 步」（那 +1 是本拍刚产生、还没被任何一份快照重放过的那一步），与跑了多少拍无关。

### 17.4 判据与变异

判据 14 条（`tests/extensions/net-predict.test.ts`），核心是两条**互为对照**的：

- **客户端第 t 拍的位置 == 主机第 t + 延迟 拍的位置**，逐拍比。预测的全部承诺就是这一条：
  不是「算得差不多」，而是「提前看到主机将来会算出的那个数」。
- **不预测时两拍之间动都不动**。没有这条，「有位移」在预测根本没接上时也可能成立（快照推进也算位移）。

延迟取 2 拍是刻意的：延迟 0 时环回会让主机在**同一拍**收到意图，「客户端领先主机」这件事
根本观察不到 —— 判据全绿，而线上（RTT 几十毫秒）完全是另一回事。

变异 11 条（M1019–M1029）。两条在第一次跑的时候没被抓住，都不是「判据不够严」：

- **M1025 是等价变异**。第一版靶的是「主机也建一个预测器」，而 `predict` 只有一个调用点
  （`sendIntent`，只有客户端走），主机根本不经过它 ⇒ 建不建对象都观察不到。
  改成「默认值被翻成 `false`」（`opts.predict !== false` → `opts.predict === true`）—— 那条一改，
  不传 `predict` 的客户端就退化成「只在快照到达时动」，判据立刻红。
- **M1026 的语料选错了**。第一版用「客户端去推别人的角色」，可那个场景里客户端因为归属检查
  **根本不预测**，待重放表压根没涨 —— 删掉收据那一行也什么都没变。
  换成「座位号在主机那边变了（重连换号）」：客户端按自己那份归属一直预测，主机一直按 `not-owner` 拒，
  40 拍（> 上限 32）之后表就涨到上限开始丢。这是「客户端预测了、主机拒了」唯一能**持续**的情形。

## 18 · 批162：`hypot → sqrt` 与确定性闸门

### 18.0 这一批的难点不是改 12 处，是「判据没地方长」

想给「仿真层不许再用 `Math.hypot`」写一条**行为**判据，写完才发现它永远不会红：
把 `planeLen` 改回 `Math.hypot`，位置判据全绿。原因见 §17.0 —— `dirStep` 的定义域只有
9 组方向向量，那 9 组上两者逐位相同。分叉只在定义域之外发生（39.03% 的输入差 1 ulp），
而 CI 永远跑在同一个引擎上、同一批浮点上。

**一条永远不会红的判据不是判据。** 所以这条约束只能长在**源码**上：

| 机制 | 挡什么 |
|---|---|
| 扫描 `src/` 全域（218 文件 / 62246 行） | 新写的 `Math.hypot` / `Math.random` |
| 每条规则登记「今天应命中几处」 | 规则失效（正则写错 ⇒ 永远 0 命中 ⇒ 与仓库干净一模一样） |
| 白名单精确到「文件 × 规则」 | 一处豁免扩散成整个目录免疫 |
| 陈旧白名单也红 | 文件改名 / 那段代码被删之后，白名单静默失效、还在替未来的违规打掩护 |
| 扫描规模下限（200 文件 / 40000 行） | 路径写错时得到「0 文件 0 违规」—— 最危险的一种绿 |
| `--selftest`（8 条合成语料） | 扫描器自己失效 |

### 18.1 注释行：改过一次，方向是「不吵」

第一版「宁严勿漏，注释里的调用也算」，当场两条假红：`foundation/random.ts` 与
`worldgen.ts` 的文件头都写着「★ 为什么不能用 `Math.random()`」—— 那是**正确的文档**。
判红之后只能加白名单，而白名单一多，人就会「红了就加一条」，闸门被训练成噪音。

所以改成**行级**判断：行首是注释标记 ⇒ 跳过；行首是代码 ⇒ 照样判
（`const d = Math.hypot(a,b); // 旧写法` 仍然红 —— 注释不能当后门）。

不剥整段注释，是因为那要解析字符串：本仓库有一堆内嵌 Lua 源码与 JSON，字符串里的 `//`
会被当成注释，那是一个会**静默吃掉代码**的解析器。行级判断最坏情况是「多行块注释中间的一行」
被误判成代码（红一下，人看一眼），永远不会出现「代码被吃掉一段所以闸门全绿」。

### 18.2 做了哪 12 处、为什么不做第 13 处

| 位置 | 处数 | 这一处为什么危险 |
|---|---|---|
| `extensions/motion/intent.ts` | 1 | 对角线归一化的分母 —— 斜着走 41% 快，而所有位置判据都会过 |
| `extensions/net/predict.ts` | 1 | 预测与主机必须逐位一致，这里是唯一的误差度量 |
| `extensions/ai/move.ts` | 2 | 夹到接触点时的步长、实际位移 |
| `extensions/nav/move-along.ts` | 2 | 逐格推进的距离、路径总长 |
| `extensions/physics/sweep.ts` | 4 | 接触法线、剩余位移、滑动终止条件（`< skin`） |
| `extensions/physics/physics.ts` | 1 | 扫掠候选集的半径 |
| `host/demo-game.ts` | 1 | 找最近尸体（代码里已经写着「同距离取小 cell：回放依赖确定性」） |
| `editor-entry.ts` | **不换** | 拖拽阈值，只在编辑器交互里跑，不进仿真 / 回放 / 存档 |

落成**一个** `planeLen(dx, dz)`，不是 12 份复制粘贴：复制的那天，改定义域（加溢出保护）
的人只会改到他眼前那几份。

### 18.3 实测

| 项 | 数字 |
|---|---|
| 换掉 12 处之后，判据 | 2786 条**全绿，一条期望值都没改** |
| `dirStep` 定义域（9 组方向向量）上 `hypot` vs `planeLen` | 9/9 **逐位相同** |
| 定义域之外的任意浮点 | 39.03% 差 1 ulp（上一批实测，20 万组） |
| 闸门耗时 | 0.1 秒（218 文件 / 62246 行，`--fast` 档也跑） |

### 18.4 已知边界

`planeLen` **没有溢出保护**：`|dx| > 1.34e154` 时 `dx*dx` 溢出成 `Infinity`（`hypot` 不溢出）。
游戏坐标是「格数 × 格宽」量级，离这个边界一百多个数量级。这条写进了函数注释，也写成了一条
判据（`planeLen(1e200, 1e200) === Infinity` 且 `hypot` 有限）—— 边界是**已知且被记录**的
取舍，不是没想过的漏洞。

## 19 · 批163：`?net=host` / `?net=client` —— 预测第一次跑在游戏里

### 19.1 怎么玩：两个标签页就是一场对局

| 标签页 | URL | 这一端做什么 |
|---|---|---|
| 主机 | `index.html?net=host` | 权威：执行远端意图、每拍广播快照、按收据回 `acks` |
| 客户端 | `index.html?net=client&room=engine08` | 只发意图、本地预测移动、按收据重放 |

- `&room=` 缺省 `engine08`；字符集 `[A-Za-z0-9._-]{1,64}`，不合法**退回缺省并在理由里说明**
  （房间名错了的症状只是「连不上」，不写清楚就查不出来）；
- ~~`&seat=` 覆盖「本端声称的座位号」（0..31）~~ —— **批164 删了**（见 §20）：座位只能由握手分配。
  这一行留着是为了让「它曾经存在过、并且是被拆掉的」有处可查 —— 缺口表里划掉的东西也要留痕；
- 不带参数 / `?net=` / `?net=off` / `?net=0` 都是单机；**不认识的值退回单机，但理由里写着它**
  （`?net=cleint` 静默退回时，症状是「我明明加了参数，怎么还是单机」）；
- 端点号 `PeerId` 与座位号 `PlayerId` 仍然是两个字段（批159 立的规矩），退化只发生在调用方。

### 19.2 为什么不是先写一台服务器

这一批要回答的不是「运营服怎么搭」，而是「**两个页面能不能一起玩**」。`BroadcastChannel`
是浏览器原生的同源广播：不起进程、不占端口、不用证书，测完关掉标签页什么都不留。

代价写在文件头上，不留在对话里：**只在同一台机器、同一个浏览器进程内成立**。
跨机器仍然要 Steamworks（datagram）或 WebSocket —— 而那一天的改动只发生在
`extensions/net/broadcast-transport.ts`，因为上层（`session` / `predict` / `join`）只认 `Transport`。

### 19.3 它与环回的三个差别，每一条都改变了行为

| 差别 | 环回的样子 | 真通道的样子 | 这一批怎么处理 |
|---|---|---|---|
| 到达时刻 | 发送时就决定「第 N 拍送到」 | 收到的那一刻本端跑到第几拍是实现细节 | 定义为「**上一次 `receive()` 的 tick**」：这一拍之后收到的，下一拍才可见 |
| 消息身份 | 同一个对象原样交过去 | 过**结构化克隆**，不报错地丢东西 | 收到的东西过形状校验，不能 `as NetMessage`；不过校验记进 `malformed` |
| 自发自收 | 「发给对端」是显式算出来的 | 通道保证自己发的自己收不到 | 直接依赖，不另写过滤 |

「假装它按时到了」是最省事也最坏的一种：客户端会在收到快照的**同一拍**就用它，
而真实网络里那一刻它还在一段 JSON 里。判据把消息自称的 `tick` 写成 999、本端只跑到第 3 拍，
仍然必须在第 3 拍取得到（M1047 咬住这一条）。

`malformed` 与 `unknownKinds` 分开数：前者是「链路/通道名被别的东西污染了」，后者是
「对面是另一个版本」。混在一个数里，`{"chrome.extension": …}` 这类无关广播会把
「版本不一致」这条**唯一线索**淹掉 —— 诊断信号的纯度比票数重要。

### 19.4 「URL 参数 → 行为」抽成纯函数（`host/net-mode.ts`）

不写在组合根里，理由不是洁癖：`demo-game.ts` 是三千多行的组合根，里面任何一行判断都只能靠
「打开浏览器看一眼」验证，而这三件事**每一个错了都表现为画面正常**：

| 决策 | 错了会怎样 | 判据落在 |
|---|---|---|
| `parseNetMode`：角色 / 房间 / 座位 | 客户端输入被拒，角色纹丝不动（看起来像网络断了） | 13 条（含大小写、非法值、座位号两类越界） |
| `localDriveOf` + `drive` 开关 | 控制器与会话同时改位置 ⇒ 每拍走两步（看起来像「跑得特别快」） | 2 条：位置一点没动 ∧ poll/snapshot/driven 都正常 |
| `pickLocalEntity` | 拥有两个角色的人控制错那个（单机下永远只有一个，看不见） | 由 `ownedBy` 的升序契约承担（4 条） |
| `planNetWiring` | 预测没开 ⇒ 画面一顿一顿（看起来像帧率问题） | 3 条 |

★ `drive: false` **不是「联机时不建控制器模块」**：不建模块的话输入根本没人 `poll()`，
而 `poll()` 会消费按下边缘 —— 别处补一次 poll 就把「刚按下」吞掉（M168 那个 bug 的写法）。
所以模块照建、照 poll、`snapshot` 照更新（会话的 `local` 回调读的就是它），只是不落位置。

★ `onWorldLoaded` 在 `loadScene` **成功之后**才回调：整场替换会让宿主持着的 `heroId` 全部悬空
（相机钉在已删除的节点上、按键没反应）；而失败的 `loadScene` 世界一个字节都没动
（它在 `scene.clear()` 之前就返回了），那时改宿主的 id 反而把好的改坏。

## 20 · 批164：座位表（座位只能由握手给，两个窗口不再同控一个角色）

### 20.1 这一批拆掉的那条捷径

批163 能让两个标签页一起动，但那是「**两个窗口同控一个角色**」：世界里只有一个玩家实体，
两端都把自己当成它。根因不在世界生成，而在 `host/net-mode.ts` 里的 `?seat=` 与 `NetMode.assumedSeat`
—— **宿主可以自称我是谁**。这一批把它整条删掉：

| 删掉的东西 | 为什么它必须消失 |
|---|---|
| `?seat=` 与 `NetMode.assumedSeat` | 座位号只有握手能给。留着它就是「客户端自己报一个数字」，而那个数字错了的症状是按键不动（看起来像断网） |
| `NetWiring.playerOf` | 座位映射是**运行期**才知道的（主机 `room.playerOf(peer)`、客户端 `joiner.playerId()`）。URL 解析那一刻算出来的常量，在重连之后必然与事实不符 |

`planNetWiring` 现在只剩一件事：**位置由谁改**（`driveController`）。
判据用 `Object.hasOwn(m, "assumedSeat") === false` 钉接口形状 —— 用 `in` 的话 `undefined` 也算「有」。

### 20.2 一条链路的四段

| 段 | 落点 | 判据读什么 |
|---|---|---|
| ① 选一格 | `worldgen.pickJoinCell` | 独立重算 BFS 距离后比**最小值**；`taken` / `free` 各一条；平局取格号最小（先证明这张图**真有平局**，否则那条判据恒真） |
| ② 造一个人 | `worldgen.spawnPlayerAt` | 坐标是格子中心（定点恒等式）、三样组件齐全（精灵 / `world.player` / `game.controller`）、允许第二个而 `spawnPlayer` 仍只许一个、不可通行与越界**报错且不建节点** |
| ③ 座位 → 实体 | `host/seat-table.ts` | `join` 幂等（同一实体）、`release` **只**交还 `AUTHORITY` 不删实体、占用格从场景收集（含开局那位）、实体被销毁后重造（不返回死 id） |
| ④ 握手经过会话 | `net/session.ts` 的 `adopt` + `onJoinRequest` / `onJoinReply` | 客户端装完世界后下一份增量必然 `desyncs >= 1` ∧ `resyncsSent >= 1`；主机调 `adopt` 记违规；没接钩子时 `join` 记违规（不是静默丢弃） |

★ `pickJoinCell` 与 `pickSpawn` 的目标函数**相反**（一个要「离队友最近」，一个要「最宽敞」），
所以是两份实现而不是一个参数：写成一个函数加开关的话，那个开关本身没有任何判据能看见。

★ 握手消息**必须经过会话**：`transport.receive` 是**消费式**的，宿主与会话各读一次会互相吃掉消息。

★ `adopt` 之后 `baseSnap = null` / `baseSeq = -1` 是**故意**让一次重同步发生：
握手回复里那份世界不在序号链上（主机为这个座位现拍的），链从这里重新开始由主机说了算。

## 22 · 批166：拾荒者（AI 的「捡」与「吃」，走模板选择而不是默认接管）

### 22.1 这一批解决的问题

`actions/intent.ts` 的三个动词里，`attack` 有 AI 在跑，`pickup` / `use` 只有玩家按得动。
生物只有「追」与「游」两种行为。缺的不是执行器，是**决策侧的两组事实**。

### 22.2 为什么不是给所有生物挂背包（会改行为的岔路）

`mob-world.ts` ② 的语义：猎狗打死兔子 ⇒ 猎狗没有背包 ⇒ `LOOT.NO_OWNER` ⇒
计入 `lootNoRecipient`，**与「包满了」（`lootLost`）分开**。
给所有生物挂背包会把它悄悄改掉（肉进猎狗的包、`lootNoRecipient` 归零），
而所有计数都自洽 —— 只有那一条判据会红。

于是能力做在模板上：

| 模板字段 | 不给 | 给了 |
|---|---|---|
| `carry: {stacks, stack}` | 不挂 `game.inventory`；战利品按老路走（`LOOT.NO_OWNER`） | 挂背包；拾取与战利品都进它自己的包 |
| `hunger: max` | 不挂 `game.hunger`；永不饿 | 挂饱食；低于阈值就吃包里的东西 |

★ 两个字段分开：会饿不代表会捡（原地挨饿的怪），会捡也不代表会饿（一口箱子）。

### 22.3 四段形状

| 段 | 文件 | 内容 |
|---|---|---|
| 事实 | `mob-brain.ts` | `hungry` / `hungerPct` / `foodKind` / `forageCell` / `forageNode`（**全部可选**） |
| 决策 | `mob-tree.ts` | 四个黑板键、两个输出码（`OUT_FORAGE` / `OUT_EAT`）、五个 op；默认树：吃 > 追 > 捡 > 漫游 |
| 执行 | `mob-forage.ts`（新） | `forageIntentOf`（纯函数）+ `runForagePass`（一趟遍历 → `executeIntent`） |
| 装配 | `spawn-mob.ts` / `mob-template.ts` | 条件挂两个组件；`null` / `0` 也认作缺省（见 22.4） |

四个刻意的决定：① 新事实全部可选 ⇒ 老世界行为逐字节不变；
② 阈值（`hungryBelowPercent`，默认 50）在感知层求值，不编进树；
③ 板上只记「有吃的吗」，「吃哪一种」由 `boardToDecision(board, facts)` 取事实 ——
板仍然只放数字；④ 拾取半径（1.2）≠ 看得见多远（`forageRadius`，默认 6）。

# UI 图集合页：改动面与取舍（方案，未实施）

> 这份文档回答一个问题：**把「字形页 / 皮肤页 / 中文页」合成一张图集，值不值得现在做。**
> 结论在 §6：技术上可行、改动面 6 处、约 1 个批次；但按批143 写死的触发条件，**现在不满足**。

## 1 · 现状：段数不是常数，是内容相关量

批145 实测（`tools/browser-selftest.mjs` 里那条「UI 真的画在当前帧」的 `draw=` 字段）：

| 状态 | draw 段数 | quad | 字形 |
|---|---|---|---|
| 背包关（HUD 三行 + 提示条） | **4** | 174 | 154 |
| 背包开（+ 面板底板与 9 行） | **13** | 311 | 246 |

批143 记的是「HUD+背包 15 段」—— 那个数**已经漂了**（内容变过一次）。这本身就是「别拿它当闸门」的证据：
段数跟着 UI 内容走，拿它设常数上限，内容一改就误报。

## 2 · 15（现在 13）段是怎么来的

- UI 有三张纹理页：`hud-ui.ts:536` 传 `[fontPage, skinPage, cjkPage]` ⇒ 页号 0 / 1 / 2。
- 页号的来源三处：字形用 `.fnt` 的 `page=0` + `pageBase`（`font.ts:272`）、
  皮肤帧用 `buildSkin(json, 1)`（`hud-ui.ts:241`）、中文用 `pageBase: 2`（`demo-game.ts:765`）。
- `batch2d.ts:191-203`：排序后**只在 `atlas` 变化处开新段**。
- UI 的 `order` 逐元素递增，页号在 0/1/2 之间来回切 ⇒ 十几次切换。

## 3 · 合页后必然是 1 段（不是估计）

排序键是 `layer → sortZ → order → atlas → nodeId`（`batch2d.ts:161-172`），`atlas` 排在 `order` **之后**，
所以同页的 quad **不会被 order 打散**；`it.atlas !== lastAtlas` 一次都不成立 ⇒ runs 只有 1 段。
机制侧已有判据：`ui-module.test.ts` 的「全在同一页 ⇒ 1 段」。

## 4 · 改动面（6 处，逐处可枚举）

### 4.1 `tools/make-ui-assets.mjs`（主要工作量）
- 三张图合成一张 `ui-atlas.png`：中文（1024×2092）在 (0,0)、5×7 字体（128×46）在 (0,2092)、
  皮肤（64×16）在 (0,2138) ⇒ 总计 **1024×2154**。
- `buildFnt` 加 `yOffset`：字体每个 `char` 的 `y` 加 2092；`common scaleW/scaleH` 传合成图尺寸。
- `buildSkinJson`：`image` 改 `ui-atlas.png`，四块补丁的 v 坐标加 2138。
- `build()` 的 `files` 从 6 个变 4 个：`ui-atlas.png` + `ui-font.fnt` + `ui-font-cjk.fnt` + `ui-skin.json`。
- ⚠ `--check` **不会发现孤儿文件**（`main()` 只比对清单里的名字）。换名后必须手动删掉
  `web/assets/ui-font.png` / `ui-font-cjk.png` / `ui-skin.png`，否则它们躺在磁盘上没人管。
  可选顺带修：让 `--check` 也扫 `OUT` 下不在清单里的 `ui-*.png`。

### 4.2 `build.config.json`
- 第 64-69 行：删 3 个 png、加 1 个 `ui-atlas.png`。

### 4.3 `src/host/demo-game.ts`
- `UI_FILES` / `UI_CJK_FILES`（507 / 516 行）合并，只读 `ui-atlas.png` 一次。
- `bakeUi`（723-779 行）：解 1 张图；`fontPage` / `skinPage` / `cjkPage` 都指向同一份 pixels。
- `pageBase: 2` → `0`（765 行）。

### 4.4 `src/host/hud-ui.ts`
- `buildSkin(opts.skinJson, 1)` → `0`（241 行）。
- `pageSources` 从 2-3 张降到 1 张（536 行）。

（只有这一处用 `buildSkin` 与 `pageSources`；编辑器不走 UI 页 —— 已 grep 确认。）

### 4.5 判据
- **新增**（浏览器端）：「HUD 稳态 + 背包打开时 `ui.lastFrame().drawCalls === 1`」。
  用 **1** 而不是「≤ 13」：1 是「所有 UI 同页」的必然结果，不是内容相关的魔数；
  多面板同屏仍是 1；哪天加了第二页它会红，那时再决定。
- **保留** `ui-module.test.ts` 的「皮肤与字体不同页 ⇒ 必须切 2 段」（守机制，不能删）。
- 像素判据（背包行两种颜色）不受影响：它走的是设计坐标 → 屏幕，与页号无关。

### 4.6 变异
- `buildSkin(json, 0)` → `1`：段数回 2+（浏览器判据抓）。
- `pageBase: 0` → `2`：中文另开一页（同上）。
- `ui-skin.json` 的 `image` 指回不存在的文件名：整段被跳过（`ui-module.ts:241` 有一条 warn）。

## 5 · 风险

| 风险 | 评估 |
|---|---|
| NPOT 纹理 1024×2154 | 已有先例：中文图就是 1024×2092；`Nearest` + `Clamp` + 无 mipmap |
| 显存 | 8.8MB vs 现在约 8.5MB（+0.3MB），几乎不变 |
| `--check` 逐字节基线 | 一次性重生成并提交新 PNG（二进制），之后照旧可核 |
| 编辑器派生名撞车 | 反而缓解：少一个 `ui-font.png`（`asset-list.ts:192` 那条撞车少一半） |
| 回滚 | 低：生成器与 4 处接线各自独立，一个提交可 revert |

## 6 · 结论与建议

**不现在做**，除非满足两条之一：①出现低端机目标；②UI 涨到多面板同屏。

理由不是"麻烦"，而是三件事：
1. **收益在桌面端不可观察**：4~13 次 draw call 对桌面 GPU 是噪声；收益只在低端机 / 移动端。
2. **这次要动资产基线**：PNG 逐字节、`build.config.json`、装载路径、孤儿文件 —— 属于
   「改完要有人重新看一遍图」的改动，风险立即可见，收益要等到有低端机才被看见。
3. **段数不是常数**（§1 已经证明它会漂），所以"降到个位数"不是一个能被长期守住的目标；
   真正的目标应该是**「1 段」这个结构性事实**（§3），而它只有合页才能拿到。

如果决定做：按 4.1 → 4.4 的顺序推进，先出生成器改动 + 一张新旧对照（同一场景的段数实测），
再动宿主接线；判据与变异同批跟上。

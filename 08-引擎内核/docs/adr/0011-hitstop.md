# ADR-0011 · 顿帧（hitstop）：冻结是调度器的第三条时间通道，不借 `paused` 也不借 `timeScale`

- **状态**：已采纳（由 `tests/core/scheduler.test.ts` 11 条冻结判据 + `tests/extensions/combat-hitstop.test.ts` 8 条强制；变异 M303–M312 证明判据不空转，其中 M312 只能靠浏览器判据抓）
- **日期**：2026-10-25
- **背景**：P0-2 第一批（批72）交付了补间纯函数，并明确"等第一批消费者来定义跨帧状态位"。
  用户选定的第一个消费者是**战斗 hitstop**：它比 UI 过渡更独立（不依赖 `UiNode` 状态位），
  且能立刻在真实战斗里看见效果。

## 决策

### ① 冻结算子加在 `FixedStepScheduler`（L2），不加在 combat 扩展里

`FixedStepScheduler` 的文件头自称"整个引擎的时间唯一真相"。顿帧改的是
**时间本身推进不推进**，不是某个组件的属性 —— 它就该待在时间真相里。
放在 L4 的后果：宿主得自己决定"哪些帧不喂给 `app.frame()`"，
于是出现**第二条帧路径**，而 `GameApp.frame()` 的注释明确禁止这件事
（"这是唯一的帧入口：外部都只能通过它驱动，否则有两条帧路径就必然有一条被忘记维护"）。

### ② 冻结是**独立通道**，与 `paused` / `timeScale` 平级

三条通道回答三个不同的问题：

| 通道 | 谁在说话 | 恢复时 |
|---|---|---|
| `paused` | 用户（编辑器暂停、玩家按暂停） | 清累积，被明确解除 |
| `timeScale` | 玩法刻度（慢动作/加速） | 一直在生效 |
| `freeze` | 特效（hitstop） | 自己到期 |

**为什么冻结不能借 `paused`**：顿帧到期时要写 `paused = false`，
而那是"恢复用户的运行"。玩家在顿帧期间手动暂停，顿帧一到就会把他的暂停
解除掉 —— 而"暂停被谁解除"在画面上完全看不出来。共用一个布尔还会让
"用户暂停了几秒"和"顿帧冻了几帧"在统计上变成同一个数
（`SchedulerStats.paused` 会被两者同时污染）。

**为什么冻结不能借 `timeScale`**：setter 把 0 夹到 0.01，世界只是**变慢**，
tick 照走 —— AI 照决策、冷却照消耗。顿帧要的是 tick **不走**。

两条组合规则写成判据（M307 钉住顺序）：暂停期间冻结**不消耗**
（暂停时时间不算）；冻结到期**不碰** `paused` 位。

### ③ 时长按逻辑步指定、按真实时间消耗

`freeze(ticks)` 收的是步数；`advance()` 里按 `fixedDt` 收真实时间。
这样 60Hz 与 144Hz 上冻得**一样久**。

按帧数消耗（每帧 `-1`）是最顺手的错法，在 60Hz 上看不出任何问题 ——
只有把两种帧率放在一起比才暴露（M304 钉住）。这与 `feedback.ts` 的
"闪烁按 tick 计"、`attack.ts` 的"冷却按 tick 计"是同一条纪律：
**游戏feel 的时长不跟着刷新率变**。

到期时剩余的真实时间**丢弃**（不补跑、不留给下一次冻结）——
与 `paused` 恢复同一条纪律。补跑会让"顿帧结束后的第一帧"突然多跑几步，
留给下次会让连击时第二下顿帧莫名短一截（M305 钉住）。

### ④ `stepTo` / `stepOnce` 旁路冻结

它们是逻辑跳转（编辑器"运行到此处"、回放快进），不消耗真实时间。
跳完之后剩余冻结照旧按真实时间收。

### ⑤ 触发点在宿主的 `onHit`，策略是函数

`combat/hitstop.ts` 只做三件事：**校验策略返回值**（非负整数，
非法值拒绝并入账 `rejected`，不夹取）、**记账**（triggers / extended /
skipped / rejected）、**转调** `scheduler.freeze()`。

策略写成 `(info: HitInfo) => number` 而不是 `{ ticks, onlyKills }` 枚举：
"什么命中值得冻"是玩法判断。演示页的取舍（玩家命中 3 步、击杀 12 步、
**怪打玩家不冻** —— 群战里每个怪都冻会让画面一帧一停）写死在宿主里，
而冻结本身不报错，只是手感变怪，所以这条必须显式。

`showHit` 收**完整的** `HitInfo`（含 `before`/`after`/`overkill`），
不收裁剪版：策略要按 overkill 判断"这一下有多重"时，裁剪版只能给它一个
看起来完全正常的 0。这是批65"回调少给一个参数，调用方就得猜"的同款防御。

## 后果

**得到的**：
- 顿帧与暂停/慢动作可以同时成立且互不干扰；
- 帧率无关、可回放（同一帧序列 ⇒ 同一组 tick）；
- 读档（`resetTo`）自动清冻结 —— 瞬态不跨存档。

**付不起的**（记入缺口）：
- **没有 UI 过渡动画的消费者**。`TweenPlayer` 组件与属性轨道仍然不做：
  hitstop 证明了"跨帧状态位挂在调度器上"这一种形态，但 UI 过渡需要的是
  `UiNode` 上的状态位（与 `SpriteAnimator.timeMs` 共存），那是**另一种**形态，
  仍然要等它的消费者来定义，不能从 hitstop 类推。
- 冻结期间输入不被消费（动作分发在 `onStep` 里）。经典 hitstop 就是这样
  （那几帧的输入被"吞"），但严格来说它改变了输入延迟的分布。

## 判据与变异

| 层 | 判据 | 变异 |
|---|---|---|
| 调度器 | 11 条（`tests/core/scheduler.test.ts`） | M303–M309 |
| 顿帧层 | 8 条（`tests/extensions/combat-hitstop.test.ts`） | M310–M311 |
| 浏览器 | 2 条（命中冻住 / 冻结期间画面在走） | M312 |

浏览器那两条的靶子是**接线**（`showHit` 有没有调 trigger、
冻结有没有真的拦住推进），Node 侧证不到 —— 已用两类手工变异验证过：
断开 trigger ⇒ "打完没冻住"；冻结不拦推进 ⇒ "冻结中 tick 84→85（应不动）"。

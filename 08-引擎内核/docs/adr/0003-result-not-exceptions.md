# ADR-0003 · 可预期失败用 Result，不用异常

- **状态**：已采纳
- **日期**：2026-10-22

## 背景

引擎里绝大多数"失败"都是**预期内**的：
资源不存在、后端不支持某个特性、着色器编译失败、纹理超过硬件上限、网络断开、场景名不合法。

上一代引擎的做法是"用异常 + 兜底 catch"，结果是两个具体的事故：
- `pcall(cmp.OnUpdate)` 把组件异常吞进一张表，而**没有任何判据读过那张表** ⇒
  组件 bug 从此没有症状（玩家只看到"某个东西不动了"，日志里什么都没有）。
- 场景导出/导入的失败原因被客户端翻译成"操作失败"，丢掉了"第 3 行格式不对"这种可操作信息。

## 决策

**边界写死**：

| 情况 | 用什么 |
|---|---|
| 可预期失败（IO、后端能力、编译、校验） | `Result<T, EngineError>` |
| 程序错误（不变量被破坏、API 误用） | `throw` |
| 边界处（插件 / 脚本 / 第三方解码器） | `trap(() => ...)` 转成 `Result` |

`EngineError` 带**稳定机器码**（`GFX.SHADER_COMPILE` / `ASSET.DEPENDENCY_CYCLE` / …），
判据断言 `code`，而不是断言文案（文案会改，code 不会）。

## 后果

### 正面

- 失败**必须**被处理：TypeScript 的 `Result` 是联合类型，不检查 `ok` 就拿不到 `value`。
- 降级路径写在正常代码里（`if (!r.ok) 用低精度纹理`），而不是写在 `catch` 里。
- 错误分类可被断言：`ASSET.DEPENDENCY_CYCLE` 与 `ASSET.DEPENDENCY_FAILED` 是两个不同的 `code`，
  处置完全不同（前者改依赖图，后者补资源）。

### 负面

- 代码更啰嗦（每处都要 `if (!r.ok)`）。
  **缓解**：`unwrapOr` / `mapOk` / `andThen`；并且在**确实不会失败**的地方（纯计算）不返回 `Result`。
- 不能"一路往上抛"然后在一处处理。
  **缓解**：模块的 `init` 返回 `Result`，`ModuleRegistry` 统一收集并回滚 ——
  这就是"一处处理"的正确形态（在生命周期边界，而不是在随机某处）。

## 被否的方案

- **全用异常**：降级路径会写进 `catch`，而实际工程里没人写全；
  另外热路径上 `throw` 很贵。
- **全用 `null`**：丢失原因，而且 `null` 会被当成"值不存在"而不是"操作失败"。
- **`Result` 里只放字符串**：无法按类别断言，错误处理退化成字符串匹配。

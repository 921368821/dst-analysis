# ADR-0004 · 结构性修改必须走命令队列

- **状态**：已采纳
- **日期**：2026-10-22

## 背景

组件更新期间增删节点/组件会破坏正在进行的遍历：
跳过元素、重复执行、访问已释放对象。

上一代引擎的对策是"遍历前先取快照"：

```lua
local list = {}
for _, c in pairs(self.updatecomponents) do list[#list+1] = c end
for _, c in ipairs(list) do c:OnUpdate(dt) end
```

这**只把问题挪到别处**：快照里的组件可能已经被删，仍会被调一次；
而且"OnUpdate 里停自己"的语义依赖"快照 vs 实时"的微妙差别，没有人能说清。

原版饥荒在同一个位置有一个专门的机制：`StopUpdatingComponents`（延迟停）——
注释写着"不能在遍历中改正在遍历的表，记下来本拍末尾统一处理"。
这是**同一个洞察**，只解决了一个动作（停）。

## 决策

**所有结构性修改走队列，在帧边界的 `flush()` 里执行**：

```ts
scene.spawn(name, parent);        // 入队，返回 Node（尚未挂到树）
scene.destroy(nodeId);            // 入队
scene.attach(nodeId, () => c);    // 入队
scene.enqueue(() => {...}, "x");  // 任意回调也入队（顺序确定）

scene.step(tick, dt):
  flush()          // 上一步积累的命令
  逐类型更新组件
  flush()          // 本步 update 里投递的命令
```

`flush()` 用**队列置换**（取出整队，换空队）而不是边遍历边 `shift`：
命令里可能再投递命令，置换保证本帧不会无限膨胀且顺序严格按投递序。

`spawn` 返回的 `Node` 在 `flush` 前**查不到**（`scene.find(id) === undefined`）——
这是刻意的：让"先查后建"的代码立刻暴露问题，而不是拿到半成品。

## 后果

### 正面

- 遍历期间结构不变 ⇒ 不需要快照，也不需要"延迟停"特例。
- 命令是**可序列化的**（kind + 载荷）⇒ 这是"撤销/重做"与"回放"的落点，
  而不是额外工作量。
- 顺序确定（投递序），满足确定性要求。

### 负面

- `spawn` 之后不能立刻用（必须等 `flush` 或 `step`）。
  **缓解**：提供 `spawnImmediate`（明确命名"立即"），用于加载与编辑器；
  游戏逻辑里用 `spawn`。
- 一处 `flush` 失败的语义要定义清楚：当前是"该条命令抛错会中断本次 flush 的剩余命令"。
  这是已知的粗糙点（未实现"单条失败跳过并记录"），已在 §11.3 风险里登记。

## 被否的方案

- **快照遍历**：跳过元素与"调用已删组件"两个问题都没解决，只是变得更难推理。
- **延迟停（只解决一个动作）**：这是原版的做法，但只覆盖"停组件"，
  "删节点 / 加节点 / 换父"仍然要各自想办法。

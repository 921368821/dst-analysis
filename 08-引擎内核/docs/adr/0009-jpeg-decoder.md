# ADR-0009 · JPEG：自写全格式解码器（13 个 SOF / 8·12 位 / 算术 / 无损 / 分层）

- **状态**：已采纳（`tests/extensions/jpeg.test.ts` 94 条 + `tests/extensions/jpeg-modes.test.ts` 34 条
  强制；变异 M14–M24 共 11 条证明判据不空转）
- **日期**：2026-10-22 立项 · 2026-10-23 补齐 12 bit / 算术 / 无损 / 分层
- **取代**：§11.2 旧口径"JPEG 明确不支持"（连同 README 里那句"见 §11.2"）

## 背景

旧口径把 JPEG 列为"明确不支持"，理由只有一句："需要完整 DCT 解码器，成本高"。
这条理由站不住，因为它把**成本**说成了**边界**：

- JPEG 是本项目外部素材里最常见的位图格式之一（手机截图、实拍贴图、外包交付）；
- 让宿主（浏览器 / 系统）去解，等于把"画面对不对"交给一个不参与判据的实现 ——
  与 `png.ts` 存在的理由（headless 与浏览器必须看到同一份像素）直接冲突；
- 一旦某个入口走了 `createImageBitmap`，颜色空间与预乘 alpha 就与导入期不一致，
  症状是"编辑器里对、游戏里偏色"，而且**任何一条判据都测不出来**。

第一版（2026-10-22）只做了 SOF0/1/2，把 SOF3/5–7/9–15、12 bit、分层明确拒绝。
那一版的问题是"拒绝得很清楚，但素材里真的会出现"：DICOM 导出的 16 位无损、
扫描件里的算术编码、老设备产的分层文件，全都在门外。

## 决策

### ① 13 个 SOF 全部实现，不留"明确不支持"

| SOF | 过程 | 熵编码 | 状态 |
|---|---|---|---|
| 0xC0 / 0xC1 | 基线 / 扩展顺序 | Huffman | 实现 |
| 0xC2 | 渐进 | Huffman | 实现 |
| 0xC3 | 无损 | Huffman（DPCM 预测器 P1–P7） | 实现 |
| 0xC5 / 0xC6 / 0xC7 | 差分顺序 / 差分渐进 / 差分无损 | Huffman | 实现 |
| 0xC9 / 0xCA / 0xCB | 扩展顺序 / 渐进 / 无损 | 算术（QM） | 实现 |
| 0xCD / 0xCE / 0xCF | 差分顺序 / 差分渐进 / 差分无损 | 算术 | 实现 |

精度：DCT 类 8 或 12；无损类 2..16。分量：1（灰度）/ 3（YCbCr 或 RGB）/ 4（CMYK / YCCK）。
仍然拒绝并点名的只剩"结构上不可能支持"的：精度越界、分量数不在 1/3/4、
帧尺寸超过 DHP、分量数/精度与参考帧不符、DHP 的量化表选择器非 0、EXP 越界或位置非法。

**关键决定：判据只有一份。** 过程与精度的支持规则写在 `jpeg/frame.ts` 的
`checkProcessSupport()`，**导入器不重写一遍**而是调用它。
这条是被真实事故逼出来的：解码器补齐 SOF9–15 之后，`textureImporter` 里那张手写的
"不支持的 SOF"表没跟着改，于是"解码器能解、导入器在门口拦下"，
下游永远吃不到新能力 —— 而两边的测试**各自都是绿的**。
两处规则、各自自洽，比单点 bug 更坏：它让两边的绿灯同时失去意义。

### ② 12 bit：默认输出 8 位，全精度在 `pixels16`

输出契约是 RGBA8（与图集、GPU 上传路径一致），所以 12 位不是"解成 12 位就完事"：

- 默认 `pixels` 是 8 位：`round(pixels16 / 257)`；
- `keep16: true` 时额外给 `pixels16`（满 16 位量程，`round(v * 65535 / maxval)`）；
- `bitDepth` 报**源精度**（12），与 PNG 16 位同一条口径（PNG 也是 bitDepth=16 + pixels 为 8 位）；
- 不产 16 位视图时 `pixels16 === undefined`，调用方据此决定要不要付这份内存。

12→8 的取整口径**没有外部金标**（Pillow 是 8 位构建，imagecodecs 没有 jpeg12），
所以判据只能是内部的：`pixels[i] === round(pixels16[i] / 257)` 这条恒等式对任何位深成立，
把"两条独立的降采样路径"压成一条 —— 只要 `pixels` 由 `pixels16` 派生，"取整口径"就只有一处。

### ③ 算术编码：QM 状态机 + 条件模型，证据是"libjpeg 解我们的流"

T.81 Annex D 的 QM 解码器（113 状态 + 固定 0.5 桶 113）与 F.1.4/F.1.5 的条件模型：
DC 每表 64 桶、AC 每表 256 桶（每频点 3 桶）、`fixed_bin` 用于符号/精修位。
DAC 未出现时按规范默认值 L=0/U=1/K=5 建桶。

**这里踩过一个很贵的坑，值得完整记下来：**

`Next_Index_LPS` 表里每个状态还带一个 **Switch_MPS 位（bit 7）**，共 10 个状态
（0,14,36,64,80,88,95,105,110,112）。第一版把表当裸索引抄进来，漏了这个位。
症状：**DC 全对、块首 AC 幅值偏小、其余系数全 0**，而位流位置依然"合法"（不越界、不撞标记）。
原因是 AC 量值编码图（F.23）会把**同一个桶连续用两次**，
第二次决策于是把已经判成 LPS 的符号又当 MPS 解出来。

定位手法（比结论更有用）：
1. 先用一份独立抄写的编码器 + 我们的解码器做**位级回环**（5000 / 8000 bin 全对）
   ⇒ 排除 QM 层，问题在条件模型；
2. 给编码器加 `arithTrace` 钩子，把"编码端打算写的 (桶号, 位值)"与
   "解码端实际读的 (桶号, 位值)"逐项对齐 ⇒ 第一处分歧在第 16–17 个 bin；
3. 打印状态字节：编码后仓库是 129、独立抄本是 1 ⇒ **差在 bit 7** ⇒ 回到 `jaricom.c` 的
   `V(索引, Qe, Next_LPS, Next_MPS, Switch)` 重抄整张表。

这条经验现在被钉成判据：`tests/extensions/jpeg-modes.test.ts` 里
"测试端编码器 vs 生产端解码器，5000 个 bin 逐位一致"，
以及 `QM_SWITCH_STATES` 的内容断言（变异 M19 会同时打红 8 条）。

### ④ 无损：DPCM 预测器 + 模 2^P 回绕

Annex H 的 7 个预测器（P1 Ra / P2 Rb / P3 Rc / P4 Ra+Rb−Rc / P5 Ra+((Rb−Rc)>>1) /
P6 Rb+((Ra−Rc)>>1) / P7 (Ra+Rb)>>1），**不钳位**：
`sample = (pred + diff) & 0xFFFF`（liblj92 的 SOS 用 `Ss=6`，即 P6）。
区间首行首样本用 `2^(P-Pt-1)` 作为预测起点。

**证据**：`imagecodecs.ljpeg`（liblj92）编码 8/12/16 位 SOF3，我们解码后**逐样本相等**
（max = 0）。8 位还有第三路对照：Pillow 也解同一份文件，三者一致 —— 两个独立外部实现同解，
这条比"和某一个实现接近"强得多。12/16 位只有 liblj92 一个参照（Pillow 是 8 位构建），
这一点写进 manifest 的 `note`，不冒充"多实现交叉验证"。

### ⑤ 分层 / 多帧：DHP + EXP + 差分帧，语义按原文而不是"看起来合理"

文件结构 `SOI DHP SOF SOS SOF SOS EOI`。三条语义经过了三次纠错，每次都是被规范原文推翻的：

| 最初写的 | 原文 | 改成 |
|---|---|---|
| 一律 `sample − 2^(P-1) + ref` | J.1.1：无损没有电平位移 | 无损不减，且按 **mod 2^P** 回绕 |
| 有损在**系数域**把参考 DC 加回去 | "differences between **source input components** and reference components" | 样本域相加（反量化 + IDCT 之后） |
| EXP 作用于**前**一帧 | B.3.3：EXP "apply only to the next frame header" | `pendingExp` 挂到**下一个** SOF；DHP 按 B.3.2 解析完成态几何 |

另外两条来自 B.3.2 / B.2.4.5 的硬约束，现在都是拒绝路径而不是"尽力而为"：
DHP 的量化表选择器必须为 0、DHP 只能出现在第一帧之前、EXP 必须在 DHP 之后、
EXP 之后必须有帧头、各帧不得超出 DHP 声明的完成态尺寸、各帧精度必须等于 DHP。

**上采样相位是本实现的选择，必须如实标注**：J.1.1.2 只给了"双线性"和示意图，
没给可执行的取整规则。本实现取"参考样本 i 位于它覆盖的 2×2 输出块中心"，
权重 3:1、`floor((v+8)/16)`、边界两侧钳位。编码器（`tests/tools/jpeg-encode.ts`）
用**同一份规则的独立实现**，所以无损分层回环能逐位相等；
但"真实文件是否也用这个相位"无法证明 —— 没有第三方解码器能对照。

> 同一段代码里还有一个真实缺陷值得记：双线性只钳上界（`Math.min(sh-1, y)`）时，
> `y = -1` 会读到 `undefined`，`NaN` 落进 `Uint16Array` 变成 0，第一行/第一列整片变黑。
> 而**修之前无损分层回环一直"通过"**，因为编码器那份实现有同一个 bug。
> 教训：自洽回环只能证明"两侧一致"，不能证明"规则正确"。

### ⑥ 判据：能拿外部金标就拿，拿不到就换成"更强的内部不变量"

| 能力 | 外部金标 | 没有外部实现时用什么 |
|---|---|---|
| 8 位 SOF0/1/2 | Pillow(libjpeg-turbo) 编 + 解，17 例，容差实测；另有 1420 例网格扫描（⑥-e）与 6 例**自产哈夫曼流由 libjpeg 解**（管编码器合规） | — |
| 8 位 SOF9/10（算术） | **反向**：我们编码 → libjpeg 解，6 例；金标就是 libjpeg 对同一文件的解码结果 | — |
| 8/12/16 位 SOF3（无损） | liblj92 编 + 解，逐样本相等；8 位另有 Pillow 第三路对照 | — |
| SOF3 精度 9/10/11/13/14/15 | liblj92 编 + 解，**逐位相等**（`manifest.wide` 里 9..16 各一张） | — |
| Pt 点变换 0..7（8 位）/ 8..11（12 位） | 无（libjpeg 的无损编码器不暴露 Pt） | 精确等于 `(源 >> Pt) << Pt` 的逐样本等式；预测初值 `2^(P-Pt-1)` 由 M30 变异守住 |
| 4 分量 CMYK（transform=0） | **反向**：我们编码 → libjpeg 解，`cmyk-baseline` / `cmyk-arith` 两例，实测 max=1 | — |
| 4 分量 YCCK（transform=2） | **反向**：同上，`ycck-baseline` / `ycck-arith`，实测 max=2 | — |
| SOF11（算术无损） | 无（libjpeg 直接 `JERR_ARITH_NOTIMPL`） | **手写最小流**（⑥-j）：SOI·SOF11·SOS·QM 熵·EOI 骨架手写、期望像素手算，覆盖 Pt=0/2/4 与 12 位；接缝（初值随 Pt 缩小、`<<Pt` 还原）由 M54 守住。**非零差分的上下文转移仍只有自产回环** |
| SOF5/6/7、13/14/15（分层） | 无（libjpeg 已移除 `hier_code`，ffmpeg 不解析 DHP） | **手写最小流**（字节手写、期望像素手算，⑥-h）：4 条，覆盖 mod 2^P、电平位移、缺 EXP、1×1 参考帧放大；另有自产语料无损分层逐位回环（max=0，含 SOF15）+ 有损分层四变体跨模式逐字节一致 + 6 条结构拒绝 |
| 12 位 DCT | **ffmpeg 7.1 的 mjpeg 解码器**（独立实现，认 P=12），12 例语料，灰度差 0..2 级、RGB 差 4 级（⑥-g） | 跨精度锚定（8 位 Pillow 金标 → 12 位编码 → 解回落回同一批像素，q100 实测 ≤1）+ 四种有损过程跨模式逐字节一致 + 12 位高反差 DC 类别 15 用例 |

表里"我们编码 → libjpeg 解"这一向最初只有算术语料，因为算术 JPEG 没有第三方编码器。
后来补了 6 个**哈夫曼**自产语料（`selfenc-444/420/422/prog-420/rst-420/gray`），理由不是"凑数"：
Pillow 编的那 17 例只证明**我们能解别人的流**，而"别人能解我们的流"是另一件事，
它管的才是**编码器合规** —— 采样因子写错、右边界填充方式不同、扫描脚本不合法，
这些都会在 libjpeg 那边炸掉或解歪，而**我们自己的解码器看不出来**（它会老实按我们写的东西解）。
文件清单由生成器产出（`_selfenc.json`）而不是两边各抄一份，且每个新名字必须在阈值策略表里出现，
否则生成直接失败 —— "生成了但没人判"这类空转不会悄悄发生。

### ⑥-b 未验证分支（逐条写清，别让"13 个 SOF 全实现"被读成"13 个 SOF 全测过"）

| 分支 | 状态 | 为什么没语料 |
|---|---|---|
| 4 分量 × 算术 / 无损 / 分层 | 算术有外部金标；无损与分层只有自洽回环 | Pillow 只能产 baseline CMYK，`liblj92` 只做单分量，imagecodecs 的 `jpeg8_encode` 拒收 4 通道输入。所以 4 分量的**算术**能靠 libjpeg 反向验证，**无损/分层**只能靠"多次回环 + K 端点"（K=0 全黑、K=maxval 直通）自证 |
| 无损精度 2..7 | **没有任何外部实现能产这种流** | `liblj92` 的 `bitspersample` 只接受 8..16（2..7 直接 `invalid bitspersample`），libjpeg 的 8 位构建只能解 8 位。9..16 已逐个用 liblj92 逐位验证 |
| DNL（SOF 里 height=0，高度写在后继 DNL 段） | **明确拒绝**并点名 | 极少见；拒绝比"解出 0 行"安全 |

已实测覆盖的 SOF：C0/C1/C2（8/12 位、灰度/RGB/4 分量、4:2:0/4:4:4）、C3（8/12/16 位、4 分量无损）、
C5/C7（8/12 位、灰度/RGB）、C6/CE（8/12 位、灰度/RGB，帧1 差分渐进）、
C9/CA/CB（8/12 位、灰度/RGB、4 分量、DAC、重启）、CD/CF（8/12 位、灰度/RGB、4 分量）。
**13 个 SOF 全部有跑通的编码→解码回环**，其中 11 个还有外部金标或反向金标。

**这句话现在已经可执行**（`13 个 SOF：每一个都有一份真实文件能解出来`）：
一张 13 行的矩阵把「标记 → 编码模式 → 期望 `d.jpeg.sof`」写死，逐个编码再解码，
最后断言**标记集合本身**等于 `{C0,C1,C2,C3,C5,C6,C7,C9,CA,CB,CD,CE,CF}`，且行数正好 13。
之前的状态是"每个模式各自断言自己的 SOF"——**没有任何一条判据保证 13 个都被覆盖**，
删掉一个模式或把某个标记写错，其余用例照样绿。现在少一个红、多一个（不该放行的标记被放行）也红。
同批还有一条反向的：`0xC4/0xC8/0xCC/0xDC/0xDD` 不是 SOF，支持判据必须拒绝；
精度边界（DCT 只 8/12、无损 2..16）也在这里钉住。

> SOF6/SOF14 原先是"代码路径存在、零用例"的那两条。补测试时暴露的真问题是
> **编码端**的：分层分支在进入渐进路径前无条件写了一个 `(Ss=0, Se=63, Ah=0, Al=0)` 的 SOS，
> 解码端于是把后面四趟数据当一趟顺序扫描读，报 `DC 扫描（Ss=0）必须 Se=0`。
> 也就是说这两条分支从写下来那天起就没跑通过 —— "零用例"和"零验证"在这个仓库里是同一件事。

> 4 分量 YCCK 是同一类问题的第二个实例，而且更隐蔽：解码器少做一次反相
> （Y/Cb/Cr 编码的是**墨量**，不是反相 CMY 本身），症状是**整幅反相**、白变成黑，
> 但"我们编码 → 我们解码"的回环 **max=0 全绿**，因为编码端一起错。
> 抓住它的是 libjpeg：同一张图按"YCC 编码反相值"写，libjpeg 解出反相图（max=255）；
> 按"YCC 编码墨量"写，与 transform=0 的 RGB 差 ≤2。这条经验写死在这里：
> **回环只能证明"对称"，不能证明"正确"；凡是与颜色空间/约定有关的量，必须有一个外部判据。**

"没有外部金标"不等于"没验证"，但必须**说清验证的是哪件事**。
上表最后一列的每一条都在回答"如果这里错了，哪个断言会红"。

四个有损过程（baseline / 渐进 / 算术顺序 / 算术渐进）解出**逐字节相同**的像素，
是本 ADR 里最硬的一条内部判据：量化表与 DCT 相同 ⇒ 系数必须相同 ⇒ 重建必须相同。
它对熵解码错位、统计区建错、渐进精修状态机错都敏感，而且**没有容差**。

### ⑥-c 拒绝路径审计：94 条 `fail()` 里 87 条被真实触发，7 条写清为什么没有

解码器有 94 条拒绝理由。**没被触发过的拒绝理由等于没有判据** —— 它既可能是死代码，
也可能是边界写错（`>` 写成 `>=`）而没人发现。`tools/audit-error-paths.py` 的做法是
给 `fail()` 临时插埋点（仍然 throw，不改控制流），原样跑一遍全量判据，再按
"错误码 + 消息模板前缀"对回源码里的调用点。

结果：**87 / 94**。剩下 7 条逐条定性如下 —— 三种不同的"没有证据"，不能混为一谈：

| 位置 | 定性 | 理由 |
|---|---|---|
| `bits.ts` DHT 查表越界 | **不可达（构造器不变量保证）** | `at = valptr[len] + code - mincode[len]`，而 `valptr[len] + counts[len] ≤ values.length`，且 `code - mincode[len] < counts[len]`，所以 `values[at]` 恒有值。保留它是为了让 `values[at]` 在 `noUncheckedIndexedAccess` 下完成类型收窄 |
| `hierarchy.ts` 找不到分量 N 的参考分量 | **不可达（被前一道检查蕴含）** | `addReferencePlanes()` 先调 `checkPairing()` 要求两帧分量数相等，再逐分量配对；数相等 ⇒ `prev.components[ci]` 必然存在。同上，保留是为了类型收窄 |
| `parse.ts` 没有找到 SOS 扫描 | **不可达（被前一道检查蕴含）** | `finishFrame()` 对任何 `scanCount === 0` 的帧都先报"第 N 帧没有任何扫描"，所以走到文件级统计时 `scanCount` 不可能是 0 |
| `scan-arith.ts` AC 幅度类别溢出（顺序式 / 渐进首扫，两处） | **可构造性极低（保留为深度防御）** | 需要 QM 在同一上下文序列上连续吐出 15 个 LPS。实测：256 种常量填充全覆盖、随机 16..64 字节填充 40 万次，均未命中；只有 **DC** 那条能被 `FF 00` 填充命中（已写成判据） |
| `scan-arith.ts` 渐进 AC / 精修越过谱段末端（两处） | **可构造性极低（同上）** | 需要连续 63 次 MPS 决策，任何可控填充都只能在前几次就转成"EOB"或"落值"，随机搜索同样未命中 |

前三条是**语义重复**：它们保护的不变量已由调用方保证，作用退化为类型收窄。
真正要防的是"将来有人改了调用方的顺序" —— 所以没有删除，而是登记在此，
并在 `jpeg-modes.test.ts` 里用**直接构造/直接调用**的契约判据钉住其中两条
（`new HuffTable(counts, values)` 计数不符必须抛、`predictLossless(0|8, …)` 必须抛）。
后四条是**概率上够不到的深度防御**，写在这里是为了不让"87/94"被读成"94 条都对"。

> 这一节的结论本身也是判据：改完任何一条 `fail()` 都应该重跑一次审计工具。
> 数字下降说明有检查退化成死代码，数字虚高则说明有断言在"随便坏掉就算过"。

3. **不可达的防御 → 留着但登记**：上表后 6 行。

**闸门本身也返工过一次（写下来是因为这类返工很容易被当成"噪音"绕过）**：
第一版 `tools/coverage-gate.mjs` 的白名单直接写行号（`"178-180"`）。它在 ⑥-e 那轮

### ⑥-e 大规模差分扫描：1420 例网格（不是新判据，是"容差到底有多紧"的实测）

17 个固定语料的容差是**从这 17 个用例自身实测出来的**。样本少的时候，
"阈值够用"可能只是"恰好没踩到长尾"。长尾才是真问题：
容差写 4 而某个角落差 40，说明那条路径根本没被固定语料覆盖。

工具是两个文件，一产包一比对（金标仍由 Pillow 解出来）：

```
python tools/jpeg-diff-sweep.py --out .cache/jpeg-sweep     # 要 Pillow/numpy
node --experimental-transform-types tools/jpeg-diff-sweep.mjs .cache/jpeg-sweep
```

| 维度 | 取值 |
|---|---|
| 通道结构 | RGB / `L`（1 分量）/ `CMYK`（4 分量，libjpeg 按 YCCK 编）；后两者另有渐进 × 重启 × q=1/100 的叠加网格 |
| 内容 | smooth（低频）/ edges（硬边 + 1px 斜线）/ noise（全频）/ ramp（逐像素斜坡） |
| 尺寸 | 1×1、17×9、37×23、64×48、129×97、256×192；边角 1×64、64×1、3×97、97×3 |
| 子采样 | 4:4:4 / 4:2:2 / 4:2:0 |
| 质量 | 30 / 60 / 80 / 95；边角 q=1、q=100（量化表两端） |
| 扫描结构 | 顺序 / 渐进 |
| 重启 | 无 / 每行 / 每块 1·3·7（块间隔不对齐 MCU 行） |

合计 **1420 例**。修复后结果：

| 分组 | n | max | p99 | 中位 | mean 峰值 | 有差异的样本占比 |
|---|---|---|---|---|---|---|
| `L`（1 分量） | 128 | **1** | 1 | 1 | 0.020 | 0.9% |
| `CMYK`（4 分量） | 272 | **2** | 2 | 1 | 0.245 | 7.1% |
| `RGB` | 1020 | **3** | 3 | 2 | 0.351 | 16.3% |
| 4:4:4 | 532 | 3 | 3 | 2 | 0.046 | 1.4% |
| 4:2:2 | 404 | 3 | 3 | 2 | 0.351 | 20.5% |
| 4:2:0 | 484 | 3 | 3 | 2 | 0.291 | 20.4% |

怎么读这三个数：

- **4:4:4 只剩 0.046 的平均差、1.6% 的样本不同** —— 这一支没有任何上采样，
  剩下的差就是 IDCT 取整（libjpeg 走整数 ISLOW，我们走另一条路径）。
- **4:2:2/4:2:0 有 ~20% 的样本不同，但幅度仍 ≤3** —— 这是三角上采样的
  **定点 vs 浮点**差别：libjpeg 用 `(3a+b+1)>>2` 与 `(3a+b+2)>>2` 两个**不同偏置**
  （奇偶列各一个），我们算浮点再四舍五入。样本占比高不代表错得多，幅度才是。
- **灰度只有 1 级差** —— 没有色度上采样、也没有 YCbCr→RGB 放大量，
  这条反过来证明上一句的解释成立（如果差值来自 IDCT 以外的东西，灰度不会这么小）。

**它抓到的真缺陷，也是它存在的理由**：3×97 的 4:2:0 图整列差 **40 级**（mean 10）。
根因是 libjpeg 的 `jinit_upsampler` 只在 `downsampled_width > 2` 时才启用
h2v1/h2v2 **fancy** 上采样，否则退回复制（`h2v1_upsample` / `h2v2_upsample`），
我们无条件走三角 —— 三角会把最后一个色度样本和它的左邻混在一起，复制则原样铺开。

修复时又踩了一次**对称坑**：第一版按轴判断（"某轴样本 ≤2 就复制"），
3×97 修好了，97×3 立刻从差 2 变成差 **30**。因为 h2v2 的 fancy 条件**只看宽**，
纵向再小也照样三角。正确规则是按分量：`h2v1` 看宽、`h1v2` 看高、`h2v2` 只看宽。
两条方向各补一张语料（`narrow-420`/`narrow-422` 与 `flat-420`）与两条变异（M48/M49），
删掉任一半都会立刻变红 —— 只修一个方向的补丁活不过下一次运行。

**比较器自检**：先把我们的输出整体 `+8` 再比一遍，报告的峰值必须抬到 ≥8（实测 11）。
没这一步，一个"永远报 0"的比较器（索引错位、只比了第一个像素、两边读了同一份缓冲）
也能印出一张漂亮的分布表，而表上每个数字都是假的。

**为什么不进 CI**：要 Pillow/numpy，且 1420 份未压缩金标合计 22.9 MB，不适合进仓库。
固定 17 例负责"每次都判"，网格扫描负责"按需测分布"，两者不重复。

### ⑥-f 12 位 DCT：先把这条路径锚到有金标的那条上（当时以为找不到外部实现）

写这一节时的判断是"12 位 DCT 是全项目唯一**找不到任何外部实现**的地方"（Pillow 是 8 位构建，
liblj92 只管无损，libjpeg-turbo 的 12 位构建不是任何一个 pip 包会带的东西）。这个判断
**半天之后就被推翻了**，见 ⑥-g —— 但这一节没有删，因为它是 12 位的**第一根柱子**，
而且它抓住的错与 ⑥-g 不完全重合：跨精度锚定能抓住"12 位往返整体偏掉"，
⑥-g 能抓住"编码器与解码器同错"，两者是不同方向的。

不假装有金标的做法：**把 12 位路径钉在 8 位金标的像素上**。

| 步骤 | 数据 | 谁保证它是真的 |
|---|---|---|
| 1 | 取 `smooth-444` / `edges-444` 的 **Pillow 金标像素**当源 | libjpeg-turbo（外部） |
| 2 | 8 位 → 12 位：`v*16 + 8`，再用**我们的编码器**编成 SOF1 / precision=12 / q=100 | 这一步是我们的，但它是**编码**，误差只会让结果更差，不会让判据更松 |
| 3 | 用**我们的解码器**解回来，降到 8 位 | 待验证的那条路径 |
| 4 | 必须落回步骤 1 的同一批像素（实测 q100 差 ≤1，判据卡 ≤1） | 外部金标兜底 |

能抓住的是"只在 12 位才犯"的错：电平位移写成 128（M50）、量程钳到 255、
`toFull16` 的比例写错、12 位分支少乘系数。8 位金标对这些**完全免疫**——
`1<<(8-1)` 正好就是 128，写死和不写死一模一样。抓不住的是与 8 位**共享**的规范误读，
那部分由 8 位金标负责；而"编码器与解码器对 12 位同错"这一类，要靠 ⑥-g 的第三方解码器。

**为什么用 q=100**：量化表全 1 时 DCT 往返近乎无损，判据量的就只剩缩放/位移/钳位这一层，
不会把量化误差混进来当作"容忍度"。用低质量反而会让这条判据失去分辨力。

### ⑥-g 12 位 DCT 的外部金标：ffmpeg（把 ⑥-f 的缺口补上）

**怎么找到的**：`djpeg/cjpeg/magick/convert/vips` 在 PATH 里都没有，但 `pip install imageio-ffmpeg`
带一个静态 ffmpeg 7.1，而它的 `mjpeg` 解码器**是独立实现**（不基于 libjpeg）并且认 12 位。
拿我们 12 位的流喂进去，ffmpeg 自己报 `gray16le(12 bpc, pc, bt470bg, progressive)` ——
它读懂了 P=12，不是"当成 8 位凑合解"。

于是 12 位第一次有了**两路互相独立的见证**：

```
源样本 ──我们的编码器──▶ .jpg ──我们的解码器──▶ 像素A
                           └────ffmpeg 解码───▶ 像素B（金标）
```

| 比较 | 实测 | 说明 |
|---|---|---|
| 像素B vs 源 | 0..2 级 | 编码器把源**正确写进了合规流**（第三方照着规范解，能解回源） |
| 像素A vs 像素B | 0..1 级 | 解码器与第三方理解一致 |

这一组的关键不在"多了一组语料"，而在**见证者换了人**：⑥-f 的见证者里 12 位那一段
编解码全是我们自己的实现，两边同错就永远绿；ffmpeg 不会跟着我们的错误理解走。
变异 **M51**（与 M50 同一个电平位移错，但判据换成 ffmpeg 金标那条）被独立抓住 ——
这是"外部参照真的参与判定"的证据，不是"加了一堆文件只有我们自己那条在起作用"。

**语料 12 例**（`tests/fixtures/jpeg/ff/`，119 KiB）：灰度 8/12 位 ×
{baseline, progressive, restart(3), lossless} + 奇数尺寸（37×23）+ RGB 4:4:4 两例。
都是 q=100，理由同 ⑥-f。

**四个口径坑（都踩过，都写进生成器注释了）**

1. **缩放口径**：同一个 `gray16le` 输出，8 位时 ffmpeg 给 `v*257`（满量程），
   12 位时给 `v<<4`（位对齐，上沿 65520）—— 两种映射。直接相减就是"满量程 vs 位对齐"
   混在一起，差多少都说明不了问题。最后改成**灰度用原生位打包**（`gray` / `gray12le`，
   落盘值就是原生样本值，不经缩放），RGB 因为只有 `rgb48le` 满量程格式，才用
   `round(v * maxval / 65535)` 反算。**"先换到同一精度域再比"是这类跨实现比对的第一条纪律。**
2. **4:2:0 不能用**：色度上采样在 ffmpeg 侧归 swscale，不在 mjpeg 解码器里。
   12 位 4:2:0 两边差 177 级 —— 那个数字测的是"libjpeg 的 fancy 三角 vs swscale"，
   与我们的解码器无关。所以这组语料一律 4:4:4。
3. **内容不能放 Nyquist**：第一版右半区写成逐像素 `0/max` 交替，旁边还有一条 4095→0 的阶跃，
   8×8 块里全是极端系数，重建是强 Gibbs 振铃。两个 IDCT 在振铃上取整不同，
   12 位实测第 18 列差 118 级 —— **那不是谁错了，是"两个 IDCT 在不可表示的内容上本来就会分岔"**。
   判据只能比"能说明问题的量"，所以退到 8 像素宽的块级方波。
4. **源样本可能越界**：奇数宽时 `w/2` 是 18.5，斜坡公式算出 4212 > 4095 ——
   **我自己造了一份超量程的源**，两端各自钳位后"金标 vs 源"看起来差 118 级。
   这个错是被生成器的**生成时自检**当场挡住的（`maxDiffGoldVsSource > tolerance` 直接非 0 退出）。
   顺带说明自检的位置很重要：如果只在判据里比，看到的是"解码器有问题"的错误指向。

**反退化**：金标整体抬 `容差+1` 级后判据必须变红；12 位金标必须 > 255（否则是把 12 位数据存成了 8 位）；
金标最大值必须 ≤ 位深量程、动态范围必须 > 半量程（挡住"全 0 金标"）；
清单里的 `maxDiffGoldVsSource` 必须等于实测值（挡住"写死一个好数字"）。
另有一条**反替换**核查：不能要求每例都差非 0（8 位 + 温和内容时两个 IDCT 恰好一致是正常的，
实测 `gray8-odd` 就是 0），但要求"至少有一例非 0，且 12 位里至少一例非 0" ——
否则金标极可能被换成了我们自己的解码输出。

**为什么这组进仓库，而 ⑥-e 的 1420 例网格不进**：网格的未压缩金标 22.9 MB，这组 119 KiB；
而且这组覆盖的是**唯一没有外部参照**的那条路径，值得每次 CI 都读一遍。
**判据本身不依赖 ffmpeg**（只读落盘字节），所以 CI 不需要装 ffmpeg；
只有重新生成/校验（`python tools/jpeg-ffmpeg-gold.py [--check]`）才需要。

**这组仍然证明不了的**：ffmpeg 与 libjpeg 都可能对某个细节同样偏离 T.81；
它覆盖不到算术编码（ffmpeg 不支持）与分层（ffmpeg 不解析 DHP），
这两块在 ADR 里仍标为"只有内部一致性 + 构造性判据"。缺口缩小了，但没有归零。

**另外两条试过但走不通的路（记下来，免得下次重试）**

1. **4 分量 CMYK/YCCK 拿不到 ffmpeg 的第三方意见**：把 `cmyk*-t0/t2` 喂给 ffmpeg，
   它把 4 分量解释成 `gbrap`（t0）或 `yuva444p`（t2）—— 也就是 RGB+alpha / YUV+alpha，
   **根本不是 Adobe 的 CMYK 语义**。它解出来的东西与"CMYK 反相 + K 乘法"没有可比性。
   所以 4 分量仍然只有 libjpeg 的反向金标（我们编码 → libjpeg 解），见 ⑥ 表。
2. **ffmpeg 不能当 12 位的编码器**：`-pix_fmt gray12le -c:v mjpeg` 会被它降成
   `yuvj444p`（8 位）再编码，产出的 SOF 是 P=8。所以 12 位这条路只能是
   "我们编码 → ffmpeg 解码"这一个方向，反方向（外部编码器产 12 位流给我们解）做不到。

### ⑥-h 分层：字节手写、期望手算（解决"自产回环证明不了规范理解"）

分层是唯一既没有第三方实现、又没有第三方语料的一块。在此之前它的**全部**判据都是
"我们的编码器产流 → 我们的解码器解"。这类判据的死角很具体：

- 差分合成该按 `mod 2^P` 还是 `clamp`；
- 有损差分帧的差图在合成时该不该减回 `2^(P-1)`；
- 没有 EXP 段时放大比例从哪儿来。

只要编码器和解码器**同错**，回环就永远逐位相等 —— 而这三条恰好是最容易"两边一起想歪"的。

做法：`tests/extensions/jpeg-handwritten.test.ts` 里四条**固定字节序列**，
编码器完全不参与；期望像素是手算常量。每个字节对应哪个字段都写在注释里，可以逐字节核对。

| 场景 | 手写的账 | 期望 | 写错时的结果 |
|---|---|---|---|
| 无损，参考帧 2×2 全 128，差分差全 0 | `(128 + 128) mod 256` | **0** | 钳位 → 255；忘掉参考帧 → 128 |
| 有损，两帧系数全 0 | `128 - 128 + 128` | **128** | 忘掉减位移 → 255；少加参考帧 → 0 |
| 同第一条但不写 EXP | 比例来自几何，与 EXP 无关 | **0** | 崩 / 当 1 倍 → 128 |
| 无损，参考帧 1×1 = 200 | `(200 + 128) mod 256`，1×1 放大后仍是常数 | **72** | 边缘按缺失邻居插值 → 边缘 ≠ 72 |

**为什么第四条特意用常数参考帧**：上采样相位（9:3:3:1 的 1/4 偏移）是**本实现的选择** ——
规范只给了图 J.2，没给可执行的取整规则，也没有第三方能验证。常数平面与相位无关，
所以这条能测"放大不产生波纹 + mod 加法"，而不会把"我们的相位"当成"规范的要求"写进期望值。
**这条判据的价值边界必须写清**：它没有、也不可能证明相位选对了。

**字节数断言**：每个流的总长度也断言了（94 / 88 / 184 / 95）。第一版我把场景 D 的长度
手算成 105（把 DHT 的 L 字段算重），断言当场报 95≠105 —— 手算也会错，
所以手算的结论必须落成断言让机器每次复核，而不是留在注释里。

**分辨力由变异证明**：M52（取模改钳位）被 3 条判据抓住，M53（不减回电平位移）被 1 条抓住。
两者在**自产语料的回环里都是绿的** —— 这正是这一组存在的理由。
顺带记一个自己踩的坑：M52 第一版写成 `clampSample(sum & maxval, maxval)`，
取模还留着、钳位对已取模的值无效，是个**等价变异**，跑出来"没被抓住"。
教训：变异体没被抓住时，先怀疑变异体是否真的改变了语义，再怀疑判据。

**成本与取舍**：每加一个场景都要手算一遍，且手算错误率不低（上面就错了一次）。
所以只挑了"最可能两边同错"的四条语义，没有把分层的所有路径都手写一遍 ——
剩下的靠自产语料的一致性判据，证据等级低一档，但补的是不同的东西（覆盖面）。


### ⑥-i 坏输入的取样方式：等距抽样会系统性漏掉段头

"任意单字节篡改都要返回 Result"这条判据只有一个断言语义，但它**怎么挑篡改位置**决定了它到底覆盖了什么。
早期用的是**等距抽样**（按文件长度均分 ~160 个位置）。这在真实 JPEG 上有个结构性偏差：
熵数据占 80%~95% 的字节，于是绝大多数位置落在熵数据里，
而段长、表号、采样因子、谱段边界、重启计数、EXP 因子这些**只有 1~3 个字节**的字段
只能靠"恰好抽到"才被覆盖 —— 它们恰恰是一改就决定"能不能解"的东西。

现在改成**按段结构取样**（`tests/extensions/jpeg-fuzz.test.ts`）：先把文件切成标记段
（测试端自己的走查器，不借解码器的 `splitEntropy` —— 用被测实现准备测试输入，
"解析器漏了什么"就永远测不出来），短段全取、熵段取 30 个，最后断言
**17 类标记段每一类都真的被篡改过**，以及**每份种子至少贡献 50 个样本**
（防止"加了种子但取样器没走到它"）。

种子同时从 8 份扩到 14 份，补的 6 类正是最近几轮才修过的路径：12 位 baseline / 12 位 4:2:0 /
12 位渐进+重启 / 12 位算术渐进 / YCCK（transform=2）/ 窄图 3×97 4:2:0。
**旧种子表里一份 12 位都没有** —— 也就是说"12 位的坏输入路径从没被扫过"。

两个耗时教训，都记在判据的注释里：

1. **不限 `maxPixels` 会让 fuzz 变成性能判据**：篡改 SOF 的宽高字段会造出"合法但巨大"的声明
   （`0x7FFF × 24` = 78 万像素），默认上限 64M 直接放行，于是每个这样的样本都老老实实解 78 万像素 ——
   整条判据 13.7 秒，其中 11 秒花在"解一张被篡改成大图的坏文件"上，对鲁棒性没有任何增量。
   限到 65536 后 0.78 秒（种子最大 960 像素，不受影响）。
2. **取样器本身要自检**：它要是把 SOS 之后的熵段算错，"每类段都被打到"就会退化成
   "每类段都被跳过"，而断言照样绿。所以另有一条判据用已知结构的文件走一遍：
   首段必须是 SOI、末段必须是 EOI、段之间不能有空洞、熵段不能为空、DQT 的总长必须是 69。

### ⑥-j SOF11（算术无损）：手写骨架，补的是"接缝"而不是整条通路

SOF11 是证据最薄的一格：libjpeg 对 `lossless && arith` 直接 `JERR_ARITH_NOTIMPL`，
ffmpeg 根本不解算术，liblj92 只管 Huffman 无损。此前的依据是**组合可信**——
算术引擎被 SOF9/SOF10 对着 libjpeg 验过、无损预测被 SOF3 对着 liblj92 验过，拼起来应该对。

但"两块各自对"不等于"**接缝**对"。SOF11 的接缝有两处，而且都只在特定输入下才暴露：

1. 预测初值必须随点变换缩小：`initial = 2^(P-Pt-1)`；
2. 重建必须把 Pt 左移回来：`sample << Pt`。

`Pt = 0` 时两条都**完全等价于写错**（`2^(P-1)` 就是 `2^(P-0-1)`，左移 0 位等于没移），
所以自产回环在 Pt=0 下永远是绿的 —— 这也是为什么它藏了这么久。

做法与 ⑥-h 同构：段结构手写（`SOI · SOF11 · SOS · QM 熵数据 · EOI`），
熵数据由**测试端的 QM 编码器**产（独立实现，在 SOF9/10 上被 libjpeg 验过），
期望像素手算。所有样本的差分取 0（每个样本 1 个 MPS bin），于是重建只由初值决定：

    sample = 2^(P-Pt-1) << Pt = 2^(P-1)   ⇒ 8 位恒 128、12 位恒 2048

| 变体 | 期望 | 写错时 |
|---|---|---|
| 8 位 Pt=0 | 128 | 精度写死 → 128（恰好对，无分辨力） |
| 8 位 Pt=2 | 128 | 初值不随 Pt 缩小 → 512 钳到 255；忘左移 → 32 |
| 8 位 Pt=4 | 128 | 同上 |
| 12 位 Pt=0 | 2048（8 位输出仍是 128） | 初值写死 128 → 2048 变成 128 |

变异 **M54**（`initial = 1 << (precision - 1)`）被 Pt=2 那条独立抓住 ——
在 Pt=0 下它是等价变异，这也是它此前一直活着的原因。

**一条被现实推翻的断言**：我本来写"样本更多的流必须更长"，跑出来是**相等**。
实测 1024 个全 MPS bin 压成 **1 字节**、4096 个才 2 字节 —— 算术编码对全 MPS 的压缩率就是这么极端。
改成"压缩率不得随 bin 数线性增长"之后，这条反而变成了**"QM 真的是算术编码"**的判据：
一个"一位一码"的哈夫曼式实现会线性增长，立刻红。

**仍然证明不了的**：非零差分的上下文转移（图 F.23/F.24 的幅度树与 `nextCtx` 选择）。
那一段只有"测试端 QM 编码器 ↔ 生产端 QM 解码器"的回环，而那不是第三方。
⑥-j 补的是接缝，不是整条 SOF11 通路 —— 这个区别要留着，别被"SOF11 也有手写流了"盖过去。

### ⑦ 结构性决定（都来自踩过的坑）

**(a) 熵编码段先按 RST 切分，再逐区间建位读取器。**
"单一位流 + 读着遇到标记就跳过"是这类解码器最常见的错源：缓冲里已经预读了几位，
标记位置对不上，于是错位一位、整幅变噪点，**而且不抛错**。

**(b) 渐进式 AC 精修写成显式状态机（0/1/2/3/4）。**
第一版用循环写，把 EOBRUN 记成 `(1<<r) - 1 + receive(r)`。`r=0`（本块即 EOB）时得到 0
⇒ 本块剩余非零系数的修正位一个都没读 ⇒ 位流错位。灰度渐进图因此整片花（单通道差 28）。

**(c) DC 差分类别上限随精度走**（T.81 Table F.1：8 位 ≤ 11、12 位 ≤ 15）。
写死 11 时，12 位**彩色**图必然误判成坏文件，而 12 位灰度因为色块平缓恰好不触发 ——
又是"只在特定输入下错"。变异 M22 一开始**没被抓住**，因为没有一张 12 位素材的
块间 DC 差超过 2047；于是补了一张"相邻 8×8 块在 0/4095 之间跳变、quality=100"的用例
（DC 类别 15）。**修法不是放宽判据，是造出会跨过边界的输入。**

### ⑧ 下游真的被消费

`textureImporter`（`.jpg/.jpeg`，只读 SOF，过程/精度判据来自解码器）→
`decodeImage`（按魔数分发）→ `browser-entry` 烘焙 → `buildAtlasFromSources` → `createTexture`。
导入产物现在带 `format: "jpeg"`、`bitDepth`（源精度）与 `process`（"SOF9 扩展顺序（算术）"），
判据断言算术/无损/12/16 位文件都能**走完整导入链进资产库** —— 而不只是"解码器函数能返回像素"。

分层文件还额外带 `hierarchical: true`，并且**宽高取的是 DHP 声明的完成态几何**，
不是第一帧的参考帧尺寸。这条是补测试时才发现的真缺陷：

> 导入器做的是"轻量扫头"（只走到第一个 SOF，不触碰熵数据）。而分层文件按 B.3.1
> 第一帧就是 **1/2 分辨率的参考帧**，于是 40×24 的图被报成 20×12 —— 解码器解出来
> 是 40×24，元数据却是 20×12。任何"像素层"判据都不会红（像素是对的），
> 只有"元数据尺寸必须等于解码尺寸"这一条能抓住。M40 把这个缺陷注回去，确认判据会红。
>
> 同一处顺带修掉了过程名的语义：原先报 `SOF1 扩展顺序（Huffman）`（参考帧的标记），
> 让元数据看起来像"这是一张普通顺序图"。现在报
> `分层（DHP + 差分帧，参考帧 SOF0 …）` —— 并明说"参考帧"，因为轻量扫头看不到
> 熵数据之后的差分帧，报"末帧"是假的。

## 后果

**好的**：

- 浏览器与 headless 走同一份实现，13 个 SOF、8/12 位、算术、无损、分层全部同一口径；
- 不支持的情形仍然在**导入期**就失败并点名（有路径、有文件名、说清是哪种过程），
  且判据只有一份，不会再出现"解码器能解、导入器拦下"；
- 容差、金标 sha256、截断语义、精度上报全部是显式数据；
- **40 组变异校验**覆盖到本轮 8 个真实缺陷（NLPS、双线性钳位、无损取模、DC 上限、
  精度规则、EXP 位置、YCCK 反相、分层元数据尺寸），每条都确认"改坏了哪条判据会红"；
- 94 条拒绝理由里 **87 条**被真实触发（`tools/audit-error-paths.py`），
  剩下 7 条在 ⑥-c 逐条定性 —— "有检查"和"检查有证据"是两件事。

**代价（写清楚，别当它免费）**：

- 自养代码从约 1200 行涨到 **2863 行**（`jpeg/` 目录 14 个文件，含 104 行公开契约），
  边界情形（奇数尺寸、1×1、非常规采样因子、分层几何）都要自己兜；
- 我们与 libjpeg 之间**必然**存在 ≤6 的单通道差（IDCT 精度 + 上采样实现不同），
  逐字节一致的强判据在"我们 vs 其他实现"上永远拿不到；
- **分层与 SOF11 没有外部实现可对照**，正确性依赖"自洽回环 + 结构校验"，
  对"编解码两侧同一种理解错误"无能为力 —— 这是这份实现最大的证据缺口；
- 上采样相位、上采样取整都是本实现的选择（规范没给可执行规则）；
- 分层有损的质量比同参数非分层基线差一档（实测 max 约为基线的 1.5–2 倍），
  这是"半分辨率参考帧 + 双线性放大"的必然代价，不是 bug。

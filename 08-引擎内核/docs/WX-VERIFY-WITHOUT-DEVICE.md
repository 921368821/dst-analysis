# 无设备条件下的 wx 真机验证：证据分级与替代手段

> 这份文件回答一件事：`docs/WX-DEVICE-CHECKLIST.md` 的 22 条观察项，在**没有设备、
> 没有 appid** 的前提下，各自还能得出什么强度的结论，以及怎么把「只能等设备」的部分压到最小。
>
> 它不是清单的替代品 —— 它是清单的**说明书**：哪 12 条现在就能断言，哪 5 条只能取数，
> 哪 3 条离开设备就只能是「未验」，还有哪 1 条根本不是「待验」而是「没接线」。

## 0 · 结论

1. **22 条观察项里，12 条现在就能断言**（不变量已吸收真机差异，且有判据守着）、
   **5 条只有设备能取数**（帧率、首进耗时等标量）、**3 条离开设备只能是「未验」**（低内存、断网、写失败提示），
   **1 条是已知未接线**（安全区），**1 条是被误记成「待验」的可判定缺口**（`main` 无幂等守卫）。
2. **清单第 0 节把模拟器的能力说反了**：它写「停在模拟器，第 1–2 组能看，3–4 组看不了」，
   而实际上**第 1 组（启动）与第 3 组（触摸布局）是模拟器最有价值的**，**第 2 组（帧源）在模拟器上恰恰最不可信**
   —— 模拟器的 rAF 是桌面浏览器的节拍，不是手机的 vsync。
3. **「缺设备」与「缺凭据」不是两个并列阻塞，是一条级联**：没有开发者工具 ⇒ 连模拟器都没有；
   有工具无 appid ⇒ 能跑模拟器、不能真机预览；有 appid 无设备 ⇒ 仍然不能真机预览（预览要扫码到手机）。
   所以解阻塞的顺序是固定的，而**无设备阶段该做的不是「等」，是把 B/C 两类的条目数压小**。

## 1 · 22 条观察项的证据分级

定级口径（三类，互斥）：

| 级 | 含义 | 无设备时允许写的结论 |
|---|---|---|
| **A** | 真机差异已被**下游不变量吸收**，且有判据 | 「已断言」，可直接当验收通过 |
| **B** | 需要一个**设备上才有的标量**（帧率、耗时、字节数） | 「不掌握」，**必须留空**，不许填估计值 |
| **C** | 需要一次**设备上的经验观察**（闪退、断网、系统弹窗文案） | 「未验」，不许写「应该没问题」 |

### 1.1 启动（5 条）

| # | 条目 | 级 | 现在由什么守着 / 为什么 |
|---|---|---|---|
| 1.1 | 冷启动无「启动失败」弹窗 | **B** | 失败**要说出来**这一半已判（`tests/host/wx-entry.test.ts` 8 条含「缺触摸点名 `WX.NO_TOUCH`」）；「意外失败」那一半只能在设备上看 |
| 1.2 | 控制台有 `EngineWx` 字样 | **A** | CI 第 11 步已排除空壳产物（体积下限 + 打包扫描），入口符号缺失会先在那里红 |
| 1.3 | 断网冷启动有明确弹窗 | **C** | 断网下资源加载失败的路径无法在 Node 里重现 |
| 1.4 | 切后台 5 分钟不重复初始化 | **A-** | 见 §2.4：`main()` 无幂等守卫，这条是**可判定缺口**，不是待验项 |
| 1.5 | 低内存机型反复进出不闪退 | **C** | 需要真实 GC 压力 |

### 1.2 帧源（4 条）

| # | 条目 | 级 | 依据 |
|---|---|---|---|
| 2.1 | FPS 稳定 55–60 | **B** | 模拟器的 rAF 不可信；只能真机取中位数 |
| 2.2 | 切后台回来第一帧 dt 被钳住 | **A** | `scheduler.ts:162` 钳 `maxFrameDt`；`tests/core/scheduler.test.ts:33` 一次喂 **600 秒**（10 分钟）断言只跑 ≤ 8 步 |
| 2.3 | 10 分钟无累积漂移 | **A** | `scheduler.ts:166-176` 超预算的步**丢弃并记账**（`_dropped`），`tests/core/scheduler.test.ts:23` 断言「只跑 maxSteps 步、其余丢弃不静默」 |
| 2.4 | 来电中断后时间不跳变 | **A** | 同 2.2；且 `tick.ts:106-114` 的 dt 由注入时钟算、**绝不读 rAF 回调参数**（真机那个参数可能是 `undefined`） |

**2.3 的期望值写法要改**：清单写「逻辑步数与墙钟大致成比例」，而实现的承诺是
「**tick 单调、无累积漂移，掉帧的时间被丢弃并记账**」—— 这两件事在长时间掉帧时**不相等**。
照清单的原话去验，会把「正确地丢弃了时间」判成不一致。

### 1.3 触摸（5 条）

| # | 条目 | 级 | 依据 |
|---|---|---|---|
| 3.1 | 点右上角按钮命中 | **A-** | 换算层有判据（`wx.test.ts` 43 条含「少乘一个像素比就按哪里都不中」）；真机只剩「`clientX` 的单位/原点」这一个契约假设 |
| 3.2 | 点左下角按钮命中 | **A-** | 同上；键位按短边成比例布局，已有「分辨率变了布局跟着变且不重叠」的判据 |
| 3.3 | 两指同时按不串号、不丢 | **A** | 多点并集 + 「只给 `changedTouches` 的老实现也能跑」两条判据 |
| 3.4 | 按住拖出屏幕再回来不卡住 | **A** | `input.ts:153` 订阅了 `onTouchCancel`，`input.ts:222` 把 `cancel` 与 `end` 同样清理触点 |
| 3.5 | 刘海 / 挖孔屏 UI 不被遮 | **缺口** | 见 §2.1：安全区**一个消费者都没有** |

### 1.4 文件系统（5 条）

| # | 条目 | 级 | 依据 |
|---|---|---|---|
| 4.1 | 退出重进存档在 | **A** | 写读回环逐字节 + 临时文件 → rename，各 1 条判据 |
| 4.2 | 强制关闭微信再开 | **A** | 同 4.1（原子写的承诺是「要么旧、要么新」） |
| 4.3 | 清缓存后是干净档、不崩 | **A-** | `FS.NOT_FOUND` 路径已判；「清缓存是否真的清掉 `USER_DATA_PATH`」是宿主语义 ⇒ 半个 B |
| 4.4 | 剩余空间很小写入失败有提示 | **C** | `classify` 只认 `no such file` / `not exist` / `enoent` 三类子串，真机的「空间不足」措辞未采集 |
| 4.5 | 杀进程 1 秒内不要半个存档 | **A** | 「写到一半失败 ⇒ 目标保持旧内容、临时文件清掉」有判据；「rename 不覆盖」的分支也有判据 |

### 1.5 包体与加载（3 条）

| # | 条目 | 级 | 依据 |
|---|---|---|---|
| 5.1 | 首包 ≤ 4MB | **A** | `src/publish/pack-plan.ts:27` 就是 4MB 三重预算，超预算退出非 0；CI 第 11 步跑的就是它 |
| 5.2 | 首次进入耗时记录基线 | **B** | 只能真机取数 |
| 5.3 | 无 `Unexpected token 'export'` / 无 `require is not defined` | **A** | CI 第 11 步：IIFE、零 ESM、零 node 内置、禁用 API 0 处 |

**合计：A/A- 12 · B 5 · C 3 · 缺口 1 · 误记 1 = 22。**

## 2 · 四处分类错误（附证据）

### 2.1 3.5「刘海屏」不是待验，是没接线

清单写「不一致时先看 `toCanvasPoint`（含 `safeArea` / `devicePixelRatio`）」。实际：

- `src/host/wx/env.ts:148-162` 的 `readViewport` 只返回 `{ width, height, pixelRatio }` —— **没有 `safeArea`**；
- `src/host/wx/input.ts:79-86` 的 `toCanvasPoint` 只做 `canvas/window` 的比例换算，**一个安全区字段都没读**；
- `src/extensions/ui/viewport.ts:97` 有 `setSafeArea`，但**全仓库 0 处调用**。

所以这条的准确描述是：**宿主从未把安全区交给任何消费者**。UI 会不会被遮，取决于布局的偶然留白
（键位是 0.06 短边边距），不是设计保证。它不是「无设备验不了」，是**现在就能从代码断定「没有保障」**。

顺带纠正一处定位错误：**安全区不属于坐标换算**。触摸命中与 UI 遮挡在同一个坐标系里，
`toCanvasPoint` 对了，点击就中；「UI 被遮」是布局问题。把 safeArea 挂在 `toCanvasPoint` 上，
会让人去改一个不需要改的函数。

### 2.2 第 0 节把模拟器的能力说反了

原文：「停在模拟器，清单第 1–2 组能看，3–4 组看不了」。实际相反：

| 组 | 模拟器 | 真机 | 理由 |
|---|---|---|---|
| 1 启动 | ★★★ 能看 | 复核 | 启动失败、控制台日志、弹窗文案都在 JS 侧 |
| 2 帧源 | ✗ 不可信 | ★★★ 必须 | 模拟器 rAF 是桌面节拍，不是手机 vsync |
| 3 触摸 | ★★★ 能看 | 复核 | 鼠标点击可验布局命中与安全区（可切 iPhone X 机型） |
| 4 存档 | ✗ 部分 | ★★★ 必须 | 模拟器的文件系统语义与真机不同，持久化不能外推 |
| 5 包体 | ★★★ 能看 | —— | 产物侧，与设备无关 |

这条错误的代价是**方向性的**：照原文，人会拿模拟器去验帧源（得到无意义的 60fps），
而放过触摸布局（唯一能在模拟器上看到偏差的东西）。

### 2.3 4.4「空间不足」的依赖比清单写的更深

清单说「写失败有没有被 toast 接住」。但更前置的一层是：`classify` 靠 `errMsg` 子串判断错误种类，
**真机的「空间不足」措辞如果不在那三类里，它会被归成「其他错误」**——提示会有，但文案可能是
「文件操作失败」而不是「空间不足」。这不是 bug，是**未采集的语料**：拿到真机 errMsg 原文后加进
`classify` 的判据语料即可，成本一条。

### 2.4 1.4 被记成「真机风险」，其实是可以现在验的缺口

`src/wx-entry.ts:218-239` 的 `main()` **没有幂等守卫**：调两次就 `startWxGame` 两次，
两条 rAF 循环会同时跑。真机正常路径不会调两次（切后台不重入），所以这条在设备上大概率永远看不到
——**正因为看不到，它才是「无设备可验、有设备验不到」的那一类**：假 wx 里连调两次 `main` 就能判定。

## 3 · 三种缺失各自封死什么

| 缺什么 | 还能做到 | 做不到 | 这一档的结论可信度 |
|---|---|---|---|
| 只有代码（无开发者工具） | 静态判据、假宿主、构建与产物扫描 | 任何布局与观感判断 | 只对 A 类成立 |
| 有工具（无 appid） | 上述 + 模拟器：启动、触摸布局、安全区、包体、控制台 | 真机预览、帧源、真实持久化 | A 类 + 第 3 组的布局部分 |
| 有工具 + appid（无设备） | 同上（预览要扫码到手机，appid 只是前提） | 同「有工具」 | 同上 |
| 三件齐 | 全部 22 条 | —— | 全部 |

**关键点**：appid 单独不能换来任何新增结论。它的价值只在「设备到手那一刻不用再等审批」。
所以现在为 appid 奔走，收益是 0 —— 该做的是把 A 类钉死、把 B 类留空、把 C 类写成可执行的观察协议。

## 4 · 六种替代手段与强度上限

| 手段 | 能替代哪几条 | 强度上限（诚实标注） |
|---|---|---|
| ① **契约外化**：把「真机必须满足什么」逐条写成前提（`renameSync` 存在性、`clientX` 原点与单位、`readdirSync` 只返名字） | 3.1/3.2/4.1/4.5 | 前提来自官方文档，**文档与实现不一致时失效**，须标「以官方当前版本为准」 |
| ② **对称吸收**：凡「两种真机语义都合法」处，代码写成双分支并各配判据（rename 覆盖/不覆盖已有；`touchcancel` 与 `touchend` 同等已做） | 4.1/4.5/3.4 | 只能吸收**已枚举**的分支；第三种语义出现时失效 |
| ③ **恶劣假宿主**：假 wx 只给 `changedTouches`、rAF 不传时间戳、rename 不覆盖、`statSync` 抛错 | 3.1–3.4、4.1–4.5 | 证明的是「在最坏合法实现下正确」，**不证明**真机属于哪一支 |
| ④ **产物侧扫描**（CI 第 11 步） | 1.2、5.1、5.3 | 只覆盖「真机跑的是不是这份产物」的前半；跑没跑对仍要设备 |
| ⑤ **同一份逻辑换真实事件源**（浏览器端 56 条自检） | 3.1–3.4 | 证明事件→行为正确，不证明宿主 API 语义 |
| ⑥ **模拟器**（需开发者工具，不需 appid） | 1.1/1.2、3.1/3.2/3.5、5.1/5.3 | 帧源与持久化**必须排除在外** |

这六种合起来能把 22 条压到「B 5 条 + C 3 条」需要设备 —— 也就是**8 条**。

## 5 · 分层推进

**P0（无设备，可立即做，2 条缺口）**
- `main()` 加幂等守卫：第二次调用要么拒绝、要么先停旧宿主；配一条「连调两次只有一条循环」的判据（§2.4）。
- 安全区接线：`readViewport` 读 `getSystemInfoSync().safeArea`，交给布局；配一条「刘海机型下 HUD 四角都在安全区内」的判据（§2.1）。
  —— 这两条**不是验证工作，是欠的活**，做完之后清单各少一条。

**P1（无设备，重写清单，1 天）**
- 给 22 条加一列「证据等级（A/B/C/缺口）」与一列「谁能判（CI / 模拟器 / 真机）」。
- 改掉 §2.2 的模拟器能力描述、§1.2 里 2.3 的期望值写法、§2.1 的 safeArea 定位。
- A 类 12 条从「待勾」降级为「回归项」：它们由 CI 守着，每次改 wx 宿主自动重跑，不需要人再勾一遍。

**P2（有开发者工具，无 appid）**
- 模拟器跑第 1、3、5 组，重点是**安全区**（P0 接线之后才有东西可看）与**按钮命中**。
- 结论写「模拟器通过」，**不得**升级成「真机通过」。

**P3（三件齐）**
- 只做 B 5 条 + C 3 条，加 A 类抽检 3 条（抽检是为了防「产物不是那份」）。

## 6 · 有设备后的补测与验收标准

**机型矩阵**：iOS 一台 + Android 一台为最低；两台都记录机型、系统版本、**基础库版本**。
基础库不同的两台，结论不得合并 —— 它们验的不是同一个宿主。

**每条都要记「实测值」，不是「✅」**：

| 项 | 判定规则（可执行） |
|---|---|
| 2.1 帧率 | 连续 5 分钟采样，中位数 ≥ 55；且 `< 30fps` 的**连续**区间不超过 1 秒（「稳定」的可判定化） |
| 2.2 / 2.4 时间 | 切后台 5 分钟回来，tick 增量 ≤ `maxStepsPerFrame`（5 步），不出现「世界瞬移」 |
| 3.1 / 3.2 命中 | 四角各点 10 次，0 次误命中；记录 `clientX` 与命中点的偏差像素（这个数就是契约假设的验证） |
| 3.5 安全区 | HUD 四角与刘海/挖孔的最小间距 ≥ 0（截图 + 像素坐标） |
| 4.4 写失败 | 用工具把剩余空间压到 < 1MB，记录 `errMsg` **原文**；不在三类子串里就补进 `classify` 的语料 |
| 4.5 半份存档 | 存档瞬间杀进程 20 次，0 次出现半份（抽样次数要写死，不能「试了几次」） |
| 5.2 首进耗时 | 记录绝对值作为基线；第二台设备偏差 > 50% 视为异常（相对判据，不拍绝对值） |

**验收的通过条件**（三条同时成立才算这一轮验完）：
1. 22 条每条都有「级 + 实测值/未验 + 判定」；
2. 任一 C 类不一致 ⇒ 在 `docs/BLOCKERS-2026-10-27.md` 加一行（状态先 `🔜`），不就地改代码；
3. B 类**不许留空但也不许填估计**：没取到就写「未取」，下一轮补。

## 7 · 残余风险（不可消除，如实记）

1. **真机 errMsg 未采集**：`classify` 的三类子串是猜的措辞，真机可能全都不匹配 ⇒ 错误被归成「其他」。
   影响的是**提示文案**，不是正确性（写失败仍然会失败、仍然会被报出来）。
2. **rename 的持久化承诺**：`fs.ts` 文件头已写明「原子性管的是要么旧要么新，不管是否已落到闪存」
   —— wx 没有 `fsync`。断电瞬间丢最后一份存档是**设计内**的，不是 bug。
3. **「模拟器通过」与「真机通过」之间没有推理桥**：前者只是把范围缩到 JS 侧，任何一条都不能外推。
4. **B 类永远只能取数，不能推理**：帧率是设备 × 基础库 × 场景的函数，换机型就得重取，没有「已验过」的永久状态。

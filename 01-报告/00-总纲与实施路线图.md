## 概述 / TL;DR

《饥荒联机版》（Don't Starve Together, DST）是一个**用 Lua 写全部玩法、用 C++ 只做基础设施**的生存游戏。它的架构可以一句话概括：

> **C++ 的 Sim 层提供渲染、物理、网络、帧时钟这四样基础设施；其余全部——实体、组件、AI、世界生成、物品、合成、UI——都是Lua 写的，通过 `TheSim` 这一个全局对象与底层对话。**

这带来一个对仿写者极其友好的性质：**游戏逻辑与引擎实现是解耦的**。你可以用任何引擎重写全部玩法，只要提供同等语义的 `TheSim` 接口。反过来说，你也能从中学到一整套"生存游戏该怎么组织"的完整答案。

三个最值得先记住的事实：

1. **生存压力最终汇入一次 `health:DoDelta(负值)` 调用。** 饥饿度、理智值、体温、湿度都只是"生成伤害的方式"加上非致命副作用（影子生物、屏幕特效、工具打滑）。理解这一点，整个玩法层的结构就通了。
2. **组件是 ECS-lite。** 821 个组件、1594 个预制体，没有继承体系，行为全靠组合。新增一种生物 = 写一个预制体工厂函数 + 挑几个已有组件。
3. **`SourceModifierList` 是整个模组生态的骨架。** 游戏里几乎所有"×倍率"都是这个带来源追踪、能自动清理的修饰器袋。**先抄这个模式。**

## 一、执行摘要（一页版）

**架构本质**：Lua 玩法 + C++ 基础设施的混合架构。

```
┌─────────────────────────────────────────────────────┐
│  Lua 玩法层（占代码量 99%）                          │
│  实体 · 组件 · 预制体 · AI · 世界生成 · 玩法规则 · UI  │
└───────────────────────┬─────────────────────────────┘
                        │ 通过 TheSim / TheNet / TheAudio 等
                        │ 全局对象调用（367 条绑定）
┌───────────────────────▼─────────────────────────────┐
│  C++ Sim 层（7.4MB stripped）                │
│  渲染 · 物理步进 · 网络收发 · 帧时钟 · 资源加载        │
└─────────────────────────────────────────────────────┘
```

**五种核心抽象**：

| 抽象 | 是什么 | 数量 | 代码位置 |
|---|---|---|---|
| **Class** | 单一 metatable 实现的 OOP，支持单继承 + 属性setter | 1 套| `class.lua`（258 行） |
| **Entity** | 世界的统一载体，原生实体 + Lua 包装 | 数万实例 | `entityscript.lua`（2177 行） |
| **Prefab** | 命名工厂函数 + 资源/依赖清单 | 1,594 | `prefabs/*.lua` |
| **Component** | 挂在实体上的行为单元，`inst.components.xxx` | 821 | `components/*.lua` |
| **StateGraph** | AI 动画状态机 | 261 | `stategraphs/*.lua` |

**一句话概括每个子系统**：
- 生存循环 = 四条数值条 → 一个血条
- 物品与合成 = 标签匹配 + 优先级分层的约束求解
- 世界生成 = 离线 Lua 状态机 + C++ Voronoi 图分割
- AI = Brain（行为树，决策）+ StateGraph（状态机，表现）
- 多人同步 = 服务器权威 + 意图 RPC + 类型化网络变量

```
                    ┌───────────────────────────────┐
                    │      Lua 玩法世界              │
                    │                               │
                    │  prefabs/  (1594 实体工厂)     │
                    │      │                        │
                    │      ├── components/ (821)    │
                    │      │      行为组合            │
                    │      ├── replica/  (客户端镜像) │
                    │      └── EntityScript 生命周期 │
                    │                               │
                    │  stategraphs/(261) + brains/(191)│
                    │  map/ (444) worldgen          │
                    │  widgets/(272) + screens/(135) │
                    └───────────┬───────────────────┘
                                │
        ════════════════════════▼════════════════════════
              TheSim / TheNet / TheAudio / TheInput /
              TheWorld / TheInventory / TheShard ...
                        （367 条 Lua→C++ 绑定）
        ════════════════════════╤════════════════════════
                                │
        ┌───────────────────────▼───────────────────────┐
        │           C++ Sim 层（基础设施）              │
        │  Simulation(帧循环) · Renderer · Physics      │
        │  Network(收发) · Audio · ResourceLoader       │
        └───────────────────────────────────────────────┘
```

**关键设计特征**：

1. **单一信任边界。** Lua 不能直接碰内存，所有操作经`TheSim` 全局对象。这既是性能考虑，也是安全考虑（模组沙箱的基础）。
2. **`SetPristine()` 划分主从。** 预制体工厂里，`inst.entity:SetPristine()` 之后的代码只在服务端执行。这是整个联机模型的基石。
3. **标签即查询语言。** `inst:HasTag("HASHEATER")`、`TheSim:FindEntities(x,y,z,r,must,cant)`。游戏里**没有**"这是不是食物"的类继承体系。
4. **事件驱动解耦。** 组件 `PushEvent("healthdelta")`，任何人可订阅。`healthtrigger.lua` 是一个 41 行的通用阈值响应器。

## 四、九大子系统精华

### 4.1 类系统（`class.lua`，258 行 metatable 魔法）

整个游戏唯一的 OOP 实现。三个能力：

```lua
local c = Class(BaseClass, function(self, arg) self.value = arg end,
                { name = function(self, v) self._name = v; self:PushEvent("namechanged") end })

local inst = c("hello")          -- 因为 c 的元表定义了 __call
inst.name = "world"              -- 触发 setter，PushEvent 被调用
```

- **单继承**：`Class(base)` 把 base 的成员**浅拷贝**进新类，同时 `c._base = base` 供 `is_a()` 回溯
- **属性 setter**：传第三个参数 `props` 后，实例获得隐藏表 `_`，`__newindex` 钩子拦截写入
- **只读属性**：`makereadonly(t, k)` 把值锁死，任何改写断言失败

**移植难度**：低。C# 用 `Class<T>` + `Property<T>`，Godot 用 `setget`，Unity C# 也一样。

### 4.2 Prefab = 命名工厂 + 资源清单

```lua
return Prefab("torch", fn, assets, deps)
```

工厂函数做四件事：
1. `CreateEntity()` + `AddTransform` + `AddAnimState` + `AddPhysics` + `AddNetwork`（底层组件）
2. `inst.entity:SetPristine()` —— **分界线，之后的代码只跑服务端**
3. 添加标签（`CLASSIFIED`、`NO_QUERY`，等等）
4. `AddComponent(inst, "inventory", ...)` 等挂载行为

**SpawnPrefab 有两种：**
- `SpawnPrefab("torch")` —— 工厂每次新建实例
- `TheWorld:FindEntity(guid)` —— 通过 GUID 找已有实例

### 4.3 组件（ECS-lite）

```lua
inst.components.sanity:SetPercent(50)
```

- 组件是 `Class` 对象，挂在 `inst.components[name]`
- **没有继承**，行为靠组合
- 钩子是一组约定俗成的生命周期回调：`OnSave` / `OnLoad` / `OnUpdate` / `LongUpdate` / `OnEntitySleep` / `OnEntityWake` / `OnRemoveFromEntity`
- `StartUpdatingComponent(1)` 开启每 tick 更新

**每个玩法组件都有一个 `*_replica.lua` 镜像**，客户端侧只持有可同步的标量。

### 4.4 生存循环 = 四量表 → 一个血条

```
hunger（饥饿） ──┐
sanity （理智） ──┤
temperature 体温 ─┼──→ health:DoDelta(负值) ──→ death
moisture 湿度 ──┘
```

- 每条都是**速率 × dt 积分**，不是计时器
- 健康值归零 → 死因由最后一条归零的数值决定
- 副作用：饥饿 → 无法采集；理智 → 影子生物；体温 → 失温/中暑；湿度 → 落火熄灭

### 4.5 `SourceModifierList` —— DST 最重要的模式

```lua
local list = SourceModifierList(class)
list:SetModifier(source, "damage", {multiply = 0.5})
list:RemoveModifier(source)          -- 按来源自动清理，防止泄漏
list:GetMultiplier(source, "damage") -- 只算该来源的
list:GetTotal("damage")             -- 全局汇总
```

**为什么重要**：这是模组生态的骨架。所有"×倍率"都走它，且**按来源追踪**——模组卸载时能干净移除自己的影响，不会留下幽灵加成。

**必抄。** 见 [02报告](./02-游戏玩法系统.md) 的深度扩写 E-2。

### 4.6 世界生成（离线 Lua VM + C++ Voronoi）

```
PlaceSpecialPoint→ Voronoi/Triangulation (C++)
    → PlaceItems → PlaceTasks → PlaceCharacters → PostProcess
```

世界生成在**离线的 Lua 虚拟机**中跑，产出一个世界快照。随机数用 `math.randomseed(seed)`，同种子必得同世界。

### 4.7 时间系统

- 主 tick：**30 Hz**（固定步长 1/30 秒）
- 游戏内 1 天 = 8 分钟真实时间 = 16 段 × 30 秒
- 六条独立时间线：`sim`（tick）、`wall`（真实时间）、`long`（大跳跃）、`anim`、`anim_multiplier`、`real_wallclock`

### 4.8 AI = Brain（行为树）+ StateGraph（动画状态机）

**两套 AI 框架并存，各管一层：**

| | Brain（行为树） | StateGraph（状态图） |
|---|---|---|
| 文件位置 | `brains/`（191 个） | `stategraphs/`（261 个） |
| 管什么 | **决策**：我要去哪、要不要攻击 | **表现**：我现在走路还是挥拳 |
| 机制 | 思考周期 + 节点树（Sequence/Condition/Event） | 状态 + 转换条件（FSM） |
| 典型周期 | 每数秒思考一次 | 每帧更新 |

两者通过**共享状态名**耦合：Brain 设 `self.sg:GoToState("walk")`，StateGraph 里就得有 `walk` 这个状态。

### 4.9 多人同步 = 服务器权威 + 意图 RPC + 类型化网络变量

- **服务器权威**：`if not TheWorld.ismastersim then return inst end`
- **意图 RPC**：客户端发送"我想做什么"（`RPC_*`），服务器验证后执行
- **类型化网络变量**：`net_bytearray(guid, name, dirtyevent)` 声明式注册，**声明顺序即线格式**，不可乱改
- **兴趣管理**：按距离裁剪客户端可见实体

### 6.3 架构决策清单

开弓前必须定下的选择。每条给出推荐 + 理由 + 何时该选备选。

| 决策点 | 推荐 | 理由 | 何时选备选 |
|---|---|---|---|
| **引擎选型** | Godot 4 | 开源、无授权费、2D 上手快、导出方便、单人可维护 | 团队已有 Unity 经验 / 需要成熟的商业化发行渠道 → Unity |
| **脚本语言** | Lua 或 C#（跟随引擎） | 原版用 Lua 是为了热重载与模组；跟随引擎可省掉一层 FFI | 要做模组生态 → 必须 Lua |
| **渲染方案** | 2D 手绘风格优先 | 原版是 2D 手绘，3D 化会大幅增加美术成本 | 明确要做 3D 视角 → 同步改 UI 与交互设计 |
| **是否用 ECS** | 早期不用，用组件组合 | 原版是 ECS-lite（组合优于继承），不是真ECS。硬套 ECS 会增加调试难度 | 实体数 > 5000 且出现明显性能瓶颈 → 考虑 |
| **存档格式** | JSON 或自定义二进制 + 版本号 | 必须带版本号与迁移钩子，这是原版踩过的坑 | 存档 > 100MB → 二进制 |
| **是否支持联机** | **先不做，M6 再加** | 联机工作量占 25-35%，且会倒逼架构改动。先跑通单机再联机，成本远低于一开始就做 | 核心玩法依赖多人 → 架构阶段就要定 |
| **美术资源** | 用现成素材包 | 风格化 2D 素材可采购，成本远低于自研 | 有美术团队 → 自研以保证统一风格 |
| **物理** | 用引擎自带 2D 物理 | 原版物理需求简单（移动、碰撞、掉落） | 需要复杂物理沙盒 → 换Box2D |
| **音频** | 引擎自带 + 简单总线 | 原版用 FMOD 做自适应音乐，自研引擎替代方案有限 | 需要动态配乐 → 引入 FMOD/Wwise |

### 6.4 风险登记册

| 风险 | 症状 | 预防措施 | 补救方案 |
|---|---|---|---|
| **过早引入联机** | 架构被网络倒逼，单机玩法进展停滞 | 明确 M1-M4 不做联机，但架构上预留 `if not isAuthority then return` 的门禁习惯 | 若已陷入：抽出一个纯单机分支，把联机层隔离为独立模块 |
| **协程泄漏** | 运行数小时后内存持续增长、后期卡顿 | 所有协程归属于某个实体，实体销毁时强制取消；用泄漏检测脚本监控协程计数 | 用泄漏监控脚本定位未清理的协程创建点，补 `Cancel` |
| **存档不兼容** | 老存档读入后崩溃或数据错乱 | 从第一天就加版本号 + 迁移钩子；每次字段改动都写迁移 | 写存档迁移脚本批量修复；存档格式尽量只增不改 |
| **世界生成不可达** | 玩家出生在封闭区域/ 拿不到必需资源 | 生成后必做洪水填充可达性检查；关键资源放置前验证连通 | 重新生成；或加入传送/挖掘兜底机制 |
| **数值失衡** | 游戏太难或太无聊，但难以定位原因 | 数值集中管理为配置表，记录每次调整与玩家反馈 | 回到"速率×dt"模型，分别调整各数值条的下限与衰减速率 |

## 七、最小可行版本的范围裁剪

> **【深度扩写】** 以下为原版未覆盖的内容。

### 7.1 功能优先级矩阵

按「必要性 × 实现成本」分四象限：

| | **低成本** | **高成本** |
|---|---|---|
| **必须有** | ✅ 主循环与固定步长<br>✅ 角色移动与碰撞<br>✅ 物品栏与拾取<br>✅ 事件总线<br>✅ 组件系统<br>✅ 数值条框架<br>✅ 存档<br>✅ 昼夜与光照 | ✅ 状态机 AI<br>✅ 合成系统<br>✅ 世界生成（基础地形） |
| **应该有** | ⚠️ 战斗系统<br>⚠️ 掉落与拾取反馈<br>⚠️ UI 完整度 | ⚠️ 行为树 AI（可用简单 FSM 替代）<br>⚠️ 烹饪系统<br>⚠️ 可玩性校验（可达性/资源充足） |

### 7.2 明确砍掉清单

以下系统"看着重要但可以后做"，砍掉不影响核心体验：

| 系统 | 为什么可以砍 | 什么时候必须补 |
|---|---|---|

| **驯化/养殖** | 是 AI + 圈养的组合，锦上添花 | 有了稳定 AI 后 |

## 八、不要照抄的地方（Anti-patterns）

原版有些设计是历史包袱或特定约束下的选择，新项目不应照搬。

| 原版做法 | 问题 | 建议 |
|---|---|---|
| `Class` 用**浅拷贝**继承 | 父类后续新增的方法，子类看不到；热重载时要靠 `ClassRegistry` 打补丁 | 用原型链或组合；至少让继承关系显式可查 |
| netvar **声明顺序即线格式** | 改顺序不报错，但两端静默错位 | 用显式字段 ID 或版本号 |
| `set_local` 会永久抬高带宽 | 一旦调用永不恢复 | 提供明确的恢复接口 |
| `GLOBAL = _G` | 模组沙箱形同虚设 | 用真正的环境隔离（独立 `_ENV`） |
| 模组可无限抬高 RPC 限流 | 一个模组能拖垮服务器 | 限流上界不可被模组修改 |
| RPC 代码槽位固定且无边界检查 | 槽位耗尽后行为未定义 | 用注册表 + 运行时检查 |
| 遍历用 `pairs` 且顺序不稳定 | 多端可能算出不同结果（如烹饪产物） | 需要确定性时用 `ipairs` 或先排序 |
| `DoPeriodicTask` 回调里可 `yield` | 周期漂移 + 协程泄漏 | 周期任务禁止 yield，或明确文档化 |
| 时间分母 `seg_time`/`day_time`/`total_day_time` 三种混用 | 调数值时容易用错，行为不符合预期 | 统一为一个，并提供语义清晰的命名 |
| Lua `and/or` 做三元 | 值为 `false`/`nil` 时静默出错 | 用显式 if/else |

## 九、【深度扩写】通用设计模式速查

把原版中可复用的设计抽象成独立模式，脱离具体游戏语境。

### 1. 组件化实体（Composition over Inheritance）

- **问题**：实体种类爆炸，继承树会变成灾难
- **解法**：实体是空壳，行为挂在组件上，按需组合
- **原版体现**：`components/`（821 个），无继承体系
- **适用场景**：几乎所有游戏。内容越扩展越划算
- **跨语言注意**：C# 用组合 + 接口；Go 用嵌入；注意组件间的依赖方向

### 2. 标签系统作为查询语言

- **问题**：类型系统表达不了"所有能加热的""所有可食用的"
- **解法**：多标签 + 空间查询，而不是类继承
- **原版体现**：`inst:HasTag()`、`TheSim:FindEntities(x,y,z,r,must,cant)`
- **适用场景**：开放世界、生存建造类游戏
- **跨语言注意**：**强烈建议用 `int` 枚举或位掩码代替字符串标签**，字符串比较开销大且易错拼

### 3. 事件驱动的系统解耦

- **问题**：系统 A 改了状态，系统 B 也要跟着改 → 循环依赖
- **解法**：A 只发事件，不认识 B；B 订阅事件
- **原版体现**：`PushEvent("healthdelta")`、`ListenForEvent`
- **适用场景**：所有解耦需求
- **跨语言注意**：**必须防泄漏** —— 订阅后不注销是 C# 事件最常见的内存泄漏源

### 4. 速率 × dt 积分（而非计时器）

- **问题**：计时器实现难以支持暂停、快进、离线追赶
- **解法**：数值条存"当前值"，每帧 `值 += 速率 × dt`
- **原版体现**：`hunger.lua`（1 秒周期）、`sanity.lua`（每帧）
- **适用场景**：任何随时间变化的连续量
- **跨语言注意**：固定步长下 `dt` 是常数；变步长时必须限制最大 dt，否则卡顿后数值会"跳跃"

### 5. 带来源追踪的修饰器袋

- **问题**：多个系统都给同一个数值加倍率，卸载时无法干净撤销
- **解法**：修饰器按来源记账，移除时按来源删
- **原版体现**：`util/sourcemodifierlist.lua`
- **适用场景**： buff/debuff、装备加成、模组影响
- **跨语言注意**：**必抄**。这是模组生态的地基

### 6. 权威服务器 + 客户端预测 + 服务器纠正

- **问题**：联机游戏如果不预测，操作会有明显延迟
- **解法**：客户端立即应用并上报意图，服务器校验后广播纠正
- **原版体现**：`ismastersim` 门禁、`RPC_*` 意图、`remote_vector` 纠正
- **适用场景**：任何联机动作游戏
- **跨语言注意**：只有"可预测的操作"能预测（如移动、开箱），伤害结算必须等服务端

### 7. 兴趣管理（按距离裁剪同步）

- **问题**：实体多了全量同步带宽爆炸
- **解法**：每个客户端只同步视野附近的实体
- **原版体现**：`network.lua` 的可见性管理、`sleeping` / `limbo` 语义
- **适用场景**：大世界联机游戏
- **跨语言注意**：需要处理"实体进出视野时状态如何补全"——通常靠全量快照 + 增量

### 8. 代码驱动的 UI（无布局引擎）

- **问题**：编辑器拖拽的 UI 在运行时难以动态调整
- **解法**：UI 是一棵代码构造的控件树，用锚点定位
- **原版体现**：`frontend.lua` + `widgets/`（272 个），**原版确实没有布局引擎**
- **适用场景**：需要动态 UI（如物品栏随内容变化）
- **跨语言注意**：如果用 Unity/Godot，建议仍用其布局系统，除非需要高度动态

### 9. 状态机的共享状态库

- **问题**：每种生物都写一遍"走路/受惊/攻击"状态，重复且难维护
- **解法**：抽出通用状态（`SGidle`、`SGwalk`），各生物复用
- **原版体现**：`stategraphs/SG*.lua` 的共享状态
- **适用场景**：同类行为多的游戏
- **跨语言注意**：共享状态必须参数化，不能硬编码具体生物

### 10. 空间哈希 / 网格索引

- **问题**：每帧遍历所有实体找附近目标，O(N²)
- **解法**：按网格分桶，只查相邻 9 格
- **原版体现**：C++ Sim 层内置
- **适用场景**：实体数 > 1000 的场景
- **跨语言注意**：实体移动时必须更新桶归属，否则查询会漏

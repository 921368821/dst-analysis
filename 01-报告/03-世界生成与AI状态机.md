## 概述 / TL;DR

《饥荒联机版》（Don't Starve Together, DST）这一代重构把「世界」和「角色行为」两件事各自做成了一套**可序列化的数据系统**：

- 世界生成跑在一个**独立的离线 Lua VM** 里。`worldgen_main.lua` 搭一套精简环境，从任务（Task）/房间（Room）数据构造一张**剧情图**（story graph），调用 C++ 的 `WorldSim`（Voronoi 撒点 + 地块烘焙），最后吐出一个序列化 `savedata` blob（地块字符串 + 实体清单 + 种子）。游戏 VM 之后在 `gamelogic.lua` 里读这个 blob。**世界生成期间不运行任何模拟。**
- 进程推进是一条**锁—钥匙图**。任务声明 `locks`（必须已存在什么）和 `keys_given`（本任务提供什么）。`Story:LinkNodesByKeys()` 把各生物群系团簇缝成一张连通的地图，使得猪村只在玩家先通过一个发放 `KEYS.MEAT` 的任务之后才出现。这保证了难度梯度是长在**地图地理**上的，而不是靠脚本门控的。
- 房间是**纯数据**。`AddRoom("SpiderCity", { value = WORLD_TILES.FOREST, contents = { countprefabs = {...}, distributeprefabs = {...}, distributepercent = 0.3 } })` —— 一块地面地块 + 随机预制体散布规则，**没有任何逐房间代码**。
- 地块是**注册出来的，不是硬编码的**。`constants.lua` 里的旧 `GROUND` 表已废弃；`tiledefs.lua` 调 `TileManager.AddTile(name, range, data, ground_def, minimap_def, turf_def)`，由它分配 ID、绑定贴图/噪声/音效，并打上 `flooring` / `hard` / `roadways` / `cannotbedug` 标志。
- TheWorld 是一个**带约 100 个组件的实体**。`prefabs/world.lua`（`MakeWorld`）装引擎件（Map、Pathfinder、GroundCreep）；`prefabs/forest.lua` / `prefabs/cave.lua` 装玩法管理器（时钟、季节、天气、猎犬、 wildfire、巨鹿生成器……）。每一个全局"系统"都只是 `TheWorld` 上的一个组件。
- 一天 = **16 段 × 30 秒 = 8 分钟**，分白天/黄昏/夜晚；季节会重塑这个划分（冬 5/5/6，夏 11/1/4），并在季中平滑过渡。月亮走 20 天的盈亏循环。
- 天气是一个**湿度桶模拟**。湿度按每季速率累积，越过每季上限就开始降水；雨还是雪由温度阈值决定；闪电走一个周期随雨强收缩的计时器。
- AI = **可组合节点组成的行为树**，按周期（0.25–1 秒）重新求值，用 `EventNode` 做即时唤醒。脑只输出**意图**（`BufferedAction` + 移动调用），**从不碰动画**。
- 状态图 = **动画驱动的有限状态机**。每个 `State` 有 tags、`onenter/onupdate/ontimeout/onexit`、一份按时间排序的 `timeline`（`TimeEvent(frame*FRAMES, fn)`，用于帧精确的声音/伤害/干活帧），以及逐状态的 `EventHandler`。`ActionHandler(ACTIONS.CHOP, "chop_start")` 是脑意图 → 动画状态的桥。
- 脑与状态图会随实体**入睡/醒来被销毁重建**（`SetBrain`/`SetStateGraph` + `BrainManager`/`SGManager` 的休眠名单）——这是让几千个实体跑在一个服务器线程上的核心手段。

被分析的规模：**131 个 `AddTask` 定义**、**255 个 `AddRoom` 定义**、**191 个脑**、**261 个状态图**、**29 个可复用行为节点**、**50 个剧本脚本**。

> 本仓库快照实测（`grep` 复核）：`map/` 下 444 个 `.lua` 文件；`AddTask(` 出现在 135 处（去重后定义约 131 个）；`AddRoom(` 出现在 258 处；`brains/` 191 个；`stategraphs/` 261 个；`behaviours/` 29 个；`scenarios/` 50 个。原文给出的数字以此为准。

### 1.2 流水线：`GenerateNew()` → savedata → 实体

世界生成入口，`worldgen_main.lua:379`：

```lua
function GenerateNew(debug, world_gen_data)
    local level = Level(world_gen_data.level_data)   -- 例如 SURVIVAL_TOGETHER 预设
    PrefabSwaps.SelectPrefabSwaps(prefab, level.overrides)

    level:ChooseTasks()          -- 解析 task_set -> 具体任务清单（+可选任务）
    AddSetPeices(level)         -- boons、traps、POI、touchstones
    level:ChooseSetPieces()      -- 把必需/随机场景件分发到任务上

    local choose_tasks = level:GetTasksForLevel()
    local savedata = forest_map.Generate(prefab, max_map_width, max_map_height,
                                         choose_tasks, level, world_gen_data.level_type)
    ...
    savedata.meta = { seed = SEED, level_id = level.id, saveversion = ... }
    require("worldentities").AddWorldEntities(savedata)
    return data  -- DataDumper 出来的字符串
end
```

关键事实：

- 世界生成跑在一个**裸 Lua VM** 里（`worldgen_main.lua` 自建 `package.loaders`，只 require `constants`、`tuning`、`prefabs`、`map/*`）。**没有 TheWorld，没有模拟**——只有表和一个 `WorldSim` C++ 对象。
- 生成**最多重试 5 次**（`maxtries = 5`，每次之间 `collectgarbage("collect")` + `WorldSim:ResetAll()`），因为约束求解可能失败。
- 输出是一个存档文件：`savedata.map.tiles`（压缩地块串）、`savedata.map.topology`（带 id/节点/边的节点图）、`savedata.ents`（prefab → `{x, z, data}` 列表）。

`map/forest_map.lua Generate()`（第 381 行）把关卡 overrides 翻译成剧情参数，并驱动 C++ 侧：

```lua
local sizes = { ["tiny"]=1, ["small"]=50, ["medium"]=400, ["default"]=425, ["large"]=425, ["huge"]=450 }
map_width = min_size; map_height = min_size
WorldSim:SetWorldSize(map_width, map_height)

require("map/storygen")
local topology_save, storygen = BuildStory(tasks, story_gen_params, level)

WorldSim:WorldGen_InitializeNodePoints();   -- 每个图节点一个点云
WorldSim:WorldGen_VoronoiPass(100)          -- Lloyd 松弛 -> 有机的区域形状
storygen:AddRegionsToMainland(on_region_added_fn)  -- 月岛/洞穴区域 + 更多 Voronoi
```

于是每个图节点变成地图点上的一格 **Voronoi 单元**；该单元继承其房间的 `value`（地面地块），房间 `contents` 在单元内按 `TERRAIN_FILTER` 约束散布。

补充（原文未展开，但是这条流水线的后半段）：`Generate()` 在 `VoronoiPass` 之后还有一长串后处理，顺序即执行顺序：

1. `WorldSim:WorldGen_Commit()` —— 提交，失败直接 `return nil`（触发重试）。
2. `topology_save.root:ApplyPoisonTag()` —— 把带 `ForceDisconnected` 标签的节点从链接图中摘掉，并给节点打 `ForceConnected(0x2)` / `RoadPoison(0x4)` 标志位。
3. `WorldSim:ConvertToTileMap(min_size)` —— 点云转地块网格。
4. `WorldSim:SeparateIslands()` —— 分离岛屿。
5. `WorldSim:ForceConnectivity(join_islands, false, WORLD_TILES.ROCKY)` —— **强制连通**，这一步同时会生成陆地地块。
6. `WorldSim:SetRoadParameters(...)` + `WorldSim:DrawRoads(join_islands, WORLD_TILES.DIRT)` —— 道路（非 cave，且 `roads ~= "never"`）。
7. 逐节点 `node:SetTilesViaFunction(...)`；带 `SafeFromDisconnect` 的节点逐点 `WorldSim:MakeSafeFromDisconnect(x, y)`。
8. `SaveEncode` + `CreateNodeIdTileMap` —— 序列化拓扑。
9. **面积校验**：任何（非 `LOOP_BLANK_SUB`）站点 `WorldSim:GetSiteArea(id) < 8` 即判失败返回 `nil`（`SKIP_GEN_CHECKS == false` 时）。
10. `GlobalTags["Labyrinth"]` / `GlobalTags["Maze"]` 分支——`WorldSim:RunMaze()` / `GetPointsForMetaMaze()` 现场造迷宫，并在迷宫入口处补画 `DrawCellLine(..., WORLD_TILES.BRICK)` 把迷宫接回地面。
11. `ConvertGround`（静态布局落位）→ `WorldSim:ReplaceSingleNonLandTiles()`。
12. `WorldSim:DetectDisconnect()` —— 统计孤立地块；**超过全图 5% 即判失败**。
13. `WorldSim:ClearSafeFromDisconnect()`。
14. `PopulateVoronoi(...)` —— 主散布循环。
15. 海洋（`has_ocean` 时）：`Ocean_SetWorldForOceanGen` → `Ocean_PlaceSetPieces` → `Ocean_ConvertImpassibleToWater` → `PopulateOcean` → `MonkeyIsland_GenerateDocks`。
16. **最终清理**：遍历所有实体坐标，`WorldSim:GetVisualTileAtPosition(x,y)` 判不可通行则删除该实体。
17. **世界生成设置减量**：对 `mult < 1` 的 prefab，`shuffleArray` 后按比例裁剪数量。
18. `BunchSpawnerInit` / `BunchSpawnerRun` —— 成簇资源（海草堆、鱼群等）。
19. **必需预制体校验**（三重来源求和）：`level.required_prefabs` + `topology_save.root:GetRequiredPrefabs()`（任务/房间的 `required_prefabs` 累加）+ 海洋房间的 `required_prefabs`。任何一个数量不足即 `return nil`。
20. 起始点校验：`spawnpoint_multiplayer` / `multiplayer_portal` / `quagmire_portal` / `lavaarena_portal` 全空即 `return nil`。
21. `WorldSim:GetEncodedMap(join_islands)` 拿到 `tiles / tiledata / nav / adj / nodeidtilemap`；`GetWorldTileMap()` 存进 `save.map.world_tile_map`。

`map/storygen.lua` —— 图构建器：

```lua
function Story:GenerationPipeline()
    self:GenerateNodesFromTasks()      -- 逐任务：选房间、建节点子图、按钥匙连边
    self:AddBGNodes(min_bg, max_bg)    -- 生物群系之间的填充背景节点

    self:InsertAdditionalSetPieces()   -- 关卡场景件 -> 带标签的节点

```

`Story:GenerateNodesForRegion`（第 864 行）挑一个 `locks == LOCKS.NONE` 的任务作**起始任务**，然后调 `LinkNodesByKeys(startingTask, task_nodes)`（第 493 行），后者迭代地把已解锁的任务子图挂到持有相应钥匙的节点上（用 `story_depth` 追踪，让更难的内容落在离出生点更远处），并可选通过 `SeperateStoryByBlanks` 把地图闭合成一个**环**。

关于 `story_depth`：它是一个**单调递增的全局计数器**（`story_depth = story_depth + 1`，第 601–602 行），不是图上的最短距离。它的用途在 `Story:PlaceTeleportatoParts` 里写得很直白——按 `story_depth` 把有序场景件均匀铺到难度梯度上。**推断**：因为是 BFS 式逐个挂接，计数器顺序大致等于"插入顺序上的深度"，因此可以作为难度的代理指标，但它并不保证是真正的图距离。

分支策略由 `story_gen_params.branching` 控制（`map/forest_map.lua:420`）：`default`（等价 random）/ `random` / `most`（挂到 `story_depth` 最低的持钥节点）/ `least`（挂到最高的）/ `never`（永远挂到链尾，形成一条直线）。

## 4. 昼夜循环 —— `components/clock.lua`

一天 = **`NUM_SEGS = 16` 段**，每段 **`TUNING.SEG_TIME = 30` 秒**（`tuning.lua:19`，实际是 `SEG_TIME = seg_time` 的一处默认赋值）→ **8 分钟一天**。阶段：`day`、`dusk`、`night`；每个阶段拥有整数个段（`_segs[phase]`）。

状态存在网络变量里（每阶段段数一个 `net_smallbyte`，外加 `_cycles`、`_phase`、`_remainingtimeinphase`、`_moonphase`、`_mooniswaxing`）。整个 tick（`OnUpdate`，第 322 行）就是一个倒计时：

```lua
local remainingtimeinphase = _remainingtimeinphase:value() - dt
if remainingtimeinphase > 0 then
    ... -- 客户端 set_local()（预测），服务器只在段边界 set()
elseif _ismastershard then
    while _remainingtimeinphase:value() <= 0 do
        _phase:set((_phase:value() % #PHASE_NAMES) + 1)          -- day→dusk→night→day
        _totaltimeinphase:set(_segs[_phase:value()] * TUNING.SEG_TIME)
        _remainingtimeinphase:set(_totaltimeinphase:value())
        if _phase:value() == 1 then                              -- 回绕到 "day"
            _cycles:set(_cycles:value() + 1)                     -- 天数 +1
            _world:PushEvent("ms_cyclecomplete", _cycles:value())
            -- "真正调整白天/黄昏/夜晚段数的是 seasons 组件"
            _mooomphasecycle = (_mooomphasecycle % #MOON_PHASE_CYCLES) + 1
        end
    end
end
```

脏标记事件推给其它所有系统：`clocksegschanged`、`cycleschanged`、`phasechanged`、`moonphasechanged2`，以及连续的 `clocktick { phase, timeinphase, time = elapsedsegs/16 }`（第 422 行）。`worldstate` 组件把这些翻译成每个脑都读的 `TheWorld.state.isday / isdusk / isnight / cycles`。

**月相**：一张 20 项的周期表——盈 `new(1) quarter(3) half(3) threequarter(3) full(1)`，然后亏镜像——每天推进一格，可被事件锁定（`ms_lockmoonphase`）。

**客户端/服务端模型**：客户端在**段内**本地模拟时间，但在段/阶段边界钳住并等待服务端同步（`set` 与 `set_local` 的区别）；主分片把 `master_clockupdate` 广播给次分片（洞穴），后者整体套用（`OnClockUpdate`）。洞穴分片跑自己的 `nightmareclock`，但通过 `shard_clock` 保持同步。

## 5. 季节与天气

### 5.1 季节 —— `components/seasons.lua`

季节顺序 `autumn → winter → spring → summer`；长度在 `tuning.lua:2218–2221`：**AUTUMN=20、WINTER=15、SPRING=20、SUMMER=15 天**（可用 `SEASON_LENGTH_*` 预设自定义，或 `"noseason"` = 长度 0）。

模式：`cycle`（常规）、`endless`（只用一个季节，前面 10 天铺垫 + 10 天爬坡）、`always`。推进挂在时钟上：`inst:ListenForEvent("ms_cyclecomplete", OnAdvanceSeason)`（第 466 行）→ `_remainingdaysinseason` 减一，归 1 时转到 `GetNextSeason()`（跳过零长度季节），然后 `PushSeasonClockSegs()`。

每个季节重塑一天的结构（第 35 行）：

```lua
local DEFAULT_CLOCK_SEGS = {
    autumn = { day = 8,  dusk = 6, night = 2 },
    winter = { day = 5,  dusk = 5, night = 6 },
    spring = { day = 5,  dusk = 8, night = 3 },
    summer = { day = 11, dusk = 1, night = 4 },
}
```

`PushSeasonClockSegs` **在季节之间做缓动**：用季节进度 `p`，过了季中之后向下一季线性插值白天/夜晚段数（`dusk = 16 - day - night`），所以光照曲线是渐变的，而不是第一天突变。`GetModifiedSegs` 会重新归一到恰好 16 段，优先从"最不重要的阶段"里偷/加。

一个值得照抄的细节：春/秋**从"人为的中间"开始**（`_totaldaysinseason = length*2, _remaining = length`），于是温度/降水曲线（它们是进度的正弦）从温和点起步，而不是从上一季的极端值开始爬。

对外事件：`seasontick { season, progress, elapseddaysinseason, remainingdaysinseason }`（被天气、温度、生成器消费），以及世界状态标志 `iswinter / isspring / ...`。

### 5.2 天气 —— `components/weather.lua`

一切都由一个累加器派生：**湿度**（`OnUpdate`，第 879 行）：


逐季数值（第 42–125 行）：

| 季节 | 湿度速率 MIN–MAX | ceiling × | floor × | 开始/停止下雪温度 |
|---|---|---|---|---|
| autumn | 0.25–1.0 | 8 | 1.0 | −5 / 0 |
| winter | 0.25–1.0 | 3（常下雨！） | 1.0 | **5 / 10** |
| spring | 3.0–3.75 | 5.5 | 0.25 | −5 / 0 |
| summer | 0.1–0.5 | 13（罕见） | 1.5 | −5 / 0 |

- 速率本身受季节进度调制：`_moisturerateval = MIN + (1−sin(π·progress))·(MAX−MIN)` —— **季初/季末最易下雨**。特例：**冬季第 2 天**强制把 `_moisturerateoffset = 50`（源码注释：*"we really want it to snow in early winter"*，为了地表积雪）。
- 降水率（0–1）通过 `PEAK_PRECIPITATION_RANGES` 把湿度在 floor 与 ceiling 之间映射（春季峰值 0.5–1.0；夏季只要下雨就恒为 1.0）。
- **雨 vs 雪**纯粹由温度驱动，且带**迟滞**（`START_SNOW_THRESHOLDS` / `STOP_SNOW_THRESHOLDS`，第 1087–1092 行）：温度 < 开始阈值且当前是雨 → 转雪；温度 > 停止阈值且当前是雪 → 转雨。温度来自监听 `OnTemperatureTick` 的 `worldtemperature.lua`。
- **积雪**：`_snowlevel` 以 `1/300`/秒累积、以 `1/20`/秒融化；超过 `SNOW_COVERED_THRESHOLD` 会切换地面覆盖贴图（`levels/textures/snow.tex`）并置 `_snowcovered`（实体雪帽）。非冬季的湿润则改画 `mud.tex` 的水洼。
- **湿度**（0–100）追踪玩家暴露：下雨时上升（按降水率缩放），干燥速率随温度缩放（`OPTIMAL_DRYING_TEMPERATURE = 70`）；越过 `WET_THRESHOLD` 置 `TheWorld.state.iswet`（驱动理智流失、打滑、物品浸湿）。
- **闪电**（第 1094 行附近）：一个倒计时器，间隔随雨强收缩（`easing.linear(preciprate, 30, 10, 1)`）。当 `preciprate > 0.75` 且已注册 `_lightningtargets`（玩家、避雷针）时，用 `inQuint` 偏置挑一个（通常挑**第一个**——所以会反复劈同一个目标，这就是避雷针/闪电羊角有用的原因），在其周围 2–10 单位内取点，推 `ms_sendlightningstrike`；否则只播 `thunder_close/thunder_far` 环境音。
- 雨的特效实体**挂在当前活跃玩家身上**（`OnPlayerActivated`）——粒子只在摄像机所在处出现。

森林还另有一套读同一 tick 的事件系统：`frograin` 组件（春季蛙雨）、`wildfires`（夏季）、`sandstorms`，以及洞穴分片的 `caveweather` / `caveacidrain` / `caverain`。

## 6. 行为树 AI（`brain.lua`、`behaviourtree.lua`、`behaviours/`）

### 6.1 调度：`BrainManager`

`brain.lua` 定义了 `BrainWrangler`，持有三张名单：`updaters`、`tickwaiters[tick]`、`hibernaters`。每个 tick 它先把到点的脑从 `tickwaiters` 挪回 `updaters`，然后对每个**清醒且有效**的实体跑 `brain:OnUpdate()`，接着问 `bt:GetSleepTime()`：若树想睡，就把它停放到目标 tick 的 `tickwaiters`；若返回 nil，就让它进入冬眠。这是一个**协作式调度器**——一只乱跑的兔子每秒可能只被访问两次。

`Brain` 本身极小：`self.bt`、`OnUpdate → bt:Update()`、`PushEvent → self.events[event]`、`Pause/Resume`，以及 `_Start_Internal`（调 `OnStart()`——子类在这里建树——并应用模组后置函数）。

挂载（`entityscript.lua:1103`）：

```lua
function EntityScript:SetBrain(brainfn)
    self.brainfn = brainfn
    self._braindisabled = brainfn and (self.sleepstatepending or self:IsInLimbo() or self:IsAsleep()) or nil
    ...
    self.brain = brainfn and not self._braindisabled and brainfn() or nil
```

脑是一个**工厂函数，在实体唤醒时重新调用**（`_EnableBrain_Internal`），入睡/进 limbo 时销毁（`_DisableBrain_Internal`）。预制体用法：

```lua

-- prefabs/pigman.lua:310/421/512
inst:SetBrain(normalbrain) / inst:SetBrain(guardbrain) / inst:SetBrain(werepigbrain)
```

### 6.2 节点词汇（`behaviourtree.lua`）

状态：`SUCCESS / FAILED / READY / RUNNING`。`BT:Update()` = `root:Visit(); root:SaveStatus(); root:Step()` —— `Step` 会重置已结束的子树，使下一次 `Visit` 从干净状态开始，而 `RUNNING` 子树保留其内部 `idx`/状态。

| 节点 | 语义 |
|---|---|
| `ConditionNode(fn)` | 即时 SUCCESS/FAILED，每次访问都重测（永不睡眠） |
| `MultiConditionNode(start, continue)` | 首次检查谓词与持续检查谓词分离 |
| `ConditionWaitNode(fn)` | 直到 fn 为真之前一直 RUNNING（阻塞等待） |
| `ActionNode(fn)` | 跑 fn，永远 SUCCESS |
| `WaitNode(t)` | RUNNING t 秒（精确睡眠） |
| `SequenceNode` | AND —— 遇到第一个 FAILED/RUNNING 子节点就停 |
| `SelectorNode` | OR —— 遇到第一个 SUCCESS/RUNNING 子节点就停 |
| `PriorityNode(children, period)` | **主力节点**。每 `period` 秒重评所有子节点（带随机相位散布，让 100 只蜘蛛不会齐步思考）；两次重评之间它继续跑当前胜者。`EventNode` 子节点可以强制立即重评并按优先级抢占。 |
| `ParallelNode` / `ParallelNodeAny` | 并行跑子节点；前者快速失败，后者任一完成即停 |
| `EventNode(inst, event, child, priority)` | 监听实体事件；触发时置 `triggered`、调 `brain:ForceUpdate()` 并把祖先 `PriorityNode.lasttime` 清空 → 即时唤醒 |
| `LoopNode`、`RandomNode`、`NotDecorator`、`FailIfRunning/SuccessDecorator`、`LatchNode` | 流程控制 |
| 语法糖：`WhileNode(cond,name,node)` = `Parallel{Condition, node}`（**可打断**）· `IfNode` = `Sequence{Condition, node}`（只检查一次）· `IfThenDoWhileNode` |

睡眠是**逐节点**的：`BehaviourNode:Sleep(t)` 设 `nextupdatetime`；`GetTreeSleepTime()` 取**所有 RUNNING 分支上的最小值**，于是树恰好在最紧的那个活动节点需要时被唤醒。

`behaviours/` 下的 29 个文件是可复用库：`wander, runaway, chaseandattack (+andavoid/+andram), follow, leash (+leashandavoid), doaction, faceentity, findlight, avoidlight, findclosest, panic (+panicandavoid), standstill, standandattack, attackwall, useshield, chattynode, controlminions, minperiod, runtodist, beargeroffscreen, approach, findfarmplant, findflower, stalkerchaseandattack, ...`。

三个定义架构的节点：

**`Wander`**（`behaviours/wander.lua`）：按计时器交替走/停；每一步挑一个随机角度，用 `FindWalkableOffset(pt, angle, radius, attempts, ...)` 转成可达点（绕开墙），然后 `locomotor:GoToPoint`。若超出 `max_dist`（相对 `homelocation`）就改为走回家——一个内建的软牵引。默认参数：`wander_dist = 12`、`offest_attempts = 8`、`times = {minwalktime=2, randwalktime=3, minwaittime=1, randwaittime=3}`。

**`ChaseAndAttack`**（`behaviours/chaseandattack.lua`）：驱动 `components.combat.target`；在攻击范围外时用 `locomotor:GoToPoint(target_pos)`，进入范围后 `combat:TryAttack()`；在 `max_chase_time`、`give_up_dist` 或 `max_attacks` 次命中后放弃（监听 `onattackother` 与 `onmissother` 来重置追击计时器）。它以 `self:Sleep(.125)` 轮询——**8 Hz 战斗转向**，几百只怪也扛得住。

**`DoAction`**（`behaviours/doaction.lua`）：**通向动作系统的桥**。`getactionfn(inst)` 返回一个 `BufferedAction`（doer、target、action、position）；该节点把它压入 `locomotor:PushAction(action)` 并进入 RUNNING，直到动作的成功/失败回调触发。locomotor 走到目标后，把 `BufferedAction` 交给实体的**状态图** `StartAction`，后者经由 `ActionHandler` 映射成一个动画状态，其 timeline 最终调用 `inst:PerformBufferedAction()`（施加真实游戏效果）。**脑 → 动作 → 动画 → 效果**，完全解耦。

## 7. 状态图 —— 动画状态机

### 7.1 核心模型（`stategraph.lua`）

四个类：

- **`State`** —— `{ name, tags, onenter(inst, params), onupdate(inst, dt), ontimeout(inst), onexit(inst, nextstate), events = {EventHandler...}, timeline = {TimeEvent...} }`。timeline 在构造时按时间排序。`FrameEvent(f, fn)` = `TimeEvent(f * FRAMES, fn)`（`FRAMES = 1/30` 秒，动画按 30 fps 跑）。
- **`EventHandler(name, fn)`** —— 图级或逐状态对一个被推送事件的反应。
- **`ActionHandler(action, deststate, condition)`** —— 把某个 `BufferedAction` 的动词映射到一个状态名，**或一个返回状态名的函数**（函数形式可以检查装备——这就是 CHOP 对海狸-Woodie 变成"啃"的方式）。
- **`StateGraph(name, states, events, defaultstate, actionhandlers)`** —— 共享的、不可变的蓝图；模组钩子在构造时合并进来（`ModManager:GetPostInitData("StategraphState", name)` 等）。

逐实体的 **`StateGraphInstance`** 持有 `currentstate`、`timeinstate`、`timelineindex`、`bufferedevents`、`tags`、`statemem`（逐状态的临时数据，切换时清空）、`mem`（跨状态保留）。由 `EntityScript:SetStateGraph(name)`（`entityscript.lua:1148`）创建：加载/缓存图、实例化、注册进 `SGManager`（与脑同款的休眠/唤醒管夹模式），并进入 `defaultstate`。

**状态转换** —— `GoToState(statename, params)`：

```lua
self.currentstate.onexit(self.inst, statename)
self.statemem = {}                    -- 每个状态一份干净的临时数据
self.tags = {} ; copy state.tags      -- 并同步到实体标签（SGTagsToEntTags）
self.timeout = nil ; self.timelineindex = 1 (if timeline)
self.currentstate.onenter(self.inst, params)
self.inst:PushEvent("newstate", {statename = statename})
SGManager:OnEnterNewState(self)       -- 确保自己回到更新名单
```

`SGTagsToEntTags`（`attack, autopredict, busy, dirt, doing, fishing, flight, hiding, idle, invisible, lure, moving, nibble, noattack, nopredict, pausepredict, sleeping, working, boathopping, shouldautopausecontrollerinventory`）里的状态标签会**镜像到实体**——这就是脑能做 `inst.sg:HasStateTag("busy")` 廉价判断、别的系统能问 `inst:HasTag("attack")` 的机制。

**更新循环**（`UpdateState(dt)`，第 646 行）：累加 `timeinstate`；`timeout` 倒数到 0 → `ontimeout`；然后触发所有 `time <= timeinstate` 的 timeline 事件（若某个事件在中途改了状态，用 `extra_time` 递归处理）；最后 `onupdate`。`Update()` 返回一个**睡眠时间** = min(下一个 timeline 事件, timeout)，若状态有 `onupdate` 则返回 `0`（需要每帧），返回 `nil` 则冬眠——与脑同样的省电契约。

**事件**：`inst.sg:PushEvent(name, data)` *缓冲* `{name, data(+当前状态名)}`；管夹在更新之后统一处理（`HandleEvents`）。派发顺序：**当前状态的 handler 优先**，然后才是图级 `events`。于是状态 handler 可以覆盖全局反应（例如招架状态吞掉 `attacked`）。逐状态 handler 还会忽略带有不同来源状态的事件，避免处理陈旧的缓冲事件（`State:HandleEvent` 检查 `data.state == self.name`）。

**客户端预测**：状态携带 `server_states` / `forward_server_states` / `no_predict_fastforward` 以及 `RemotePausePrediction(frames)`，客户端本地跑同一张图（`SGwilson_client`）并与服务端的状态哈希对账。单机游戏可以完全忽略这套。

### 7.3 SGrabbit —— 最小模板（320 行，完整）

```lua

    ActionHandler(ACTIONS.GOHOME, "action"),

    CommonHandlers.OnSleep(), CommonHandlers.OnFreeze(), CommonHandlers.OnElectrocute(),

        if inst.components.health and not inst.components.health:IsDead() then
            ... inst.sg:GoToState("hit")
        end
    end),
    EventHandler("locomote", function(inst)          -- 来自脑/locomotor 的移动意图
        if not inst.sg:HasStateTag("idle") and not inst.sg:HasStateTag("moving") then return
        elseif not inst.components.locomotor:WantsToMoveForward() then → "idle"
```

### 7.5 SGwilson —— 玩家状态图（28,601 行）

结构：约 1200 行辅助函数，然后 `actionhandlers`（第 850 行）、`events`（第 1745 行）、各状态，最后 `return StateGraph("wilson", states, events, "init", actionhandlers)`（第 28,601 行）。所有可玩角色共用它（`prefabs/player_common.lua:2894: inst:SetStateGraph("SGwilson")`）；角色差异来自标签/覆写。

**ActionHandler 把动词路由到带上下文的状态**：

```lua
ActionHandler(ACTIONS.CHOP, function(inst)
    if inst:HasTag("beaver") then
        return not inst.sg:HasStateTag("gnawing") and "gnaw" or nil
    elseif inst.GetModuleTypeCount and inst:GetModuleTypeCount("spin") > 0 then
        ... "wx_spin_start" ...                        -- WX-78 模块
    end
    return not inst.sg:HasStateTag("prechop")
        and (inst.sg:HasStateTag("chopping") and "chop" or "chop_start")  -- 续砍 vs 起手
        or nil
end),
```

返回 `nil` 就是拒绝这个动作；`prechop`/`chopping` 这套标签舞蹈，就是**按住按钮**能实现 `chop_start → chop → chop → ...` 而不重播起手动画的机制。

**`locomote` 事件**（第 1747 行）是移动路由器：若非 `busy`，比较 `HasStateTag("moving")` 与 `locomotor:WantsToMoveForward()` 并转换 `run_stop` / `run_start`（带 `data.dir` 做 8 向朝向）。值得注意的是 **DST 玩家没有走路状态**——人类移动是 `run_start → run → run_stop`，另有仅用于特殊情况的类 walk 状态（小心/虚弱/沙暴动画藏在 `run` 内部）。

**攻击**（第 10,666 行）：一个状态，约 15 个按物品标签选择的装备分支（`whip`、`book`、`pocketwatch`、`jab`、`lancejab`、`toolpunch`、`rangedweapon` + `projectiledelay`、伐木工的 `chop_attack`、骑乘变体……）。每个分支挑动画并抬高冷却下限（`cooldown = math.max(cooldown, 13*FRAMES)`）。真正发生玩法行为的地方在共享 timeline 里：

```lua
timeline = {
    TimeEvent(5*FRAMES, ...驼鹿拳击音...),
    TimeEvent(6*FRAMES, function(inst)
        if inst.sg.statemem.isbeaver then inst:PerformBufferedAction() ... end),
    TimeEvent(8*FRAMES, function(inst)             -- 普通武器：第 8 帧命中
        if not (beaver/moose/whip/pocketwatch/book) and projectiledelay == nil then
            inst.sg.statemem.recoilstate = "attack_recoil"
            inst:PerformBufferedAction()           -- → 经由动作触发 combat:DoAttack
            inst.sg:RemoveStateTag("abouttoattack")
        end),
    TimeEvent(10*FRAMES, ...whip/book/watch 更晚命中...),
},
ontimeout = function(inst) inst.sg:RemoveStateTag("attack"); inst.sg:AddStateTag("idle") end,
onexit = function(inst)
    inst.components.combat:SetTarget(nil)
    if inst.sg:HasStateTag("abouttoattack") then inst.components.combat:CancelAttack() end
end,
```

也就是说：`onenter` 里 `StartAttack()`（冷却）、挥击帧上 `PerformBufferedAction()`（伤害）、若中途被打断则 `onexit` 里 `CancelAttack()` —— **玩家可以在命中帧之前被打断**，`abouttoattack` 标签则让 HUD 与网络层知道"有一击待落"。远程武器用 `projectiledelay` 让投射物略微早于视觉帧生成，这样它出现时已经在玩家身前。

## 8. 剧本与生成器（Part D）

**剧本**（scenario）是一小段挂在已生成实体上的生命周期脚本——供场景件与战利品箱添加不属于预制体的行为。

机制（`components/scenariorunner.lua` + `mainfunctions.lua:469`）：

```lua

if saved.scenario or (saved.data and saved.data.scenariorunner) then
    if inst.components.scenariorunner == nil then inst:AddComponent("scenariorunner") end
    if saved.scenario then inst.components.scenariorunner:SetScript(saved.scenario) end
end
-- ScenarioRunner:SetScript(name) → require("scenarios/"..name)  （必须导出 OnCreate/OnLoad）
-- :Run() 调 OnCreate 一次（hasrunonce 会被存档）；OnLoad 每次加载都跑；
-- Run() 由 maputil.lua:478 在实体被（重新）激活时调用。
```

`scenarios/` 里的例子：

- **`newgameplus.lua`**（15 行）：在 `OnCreate` 里遍历所有 `spiderden` 实体，把 `growable` 阶段提到 2–3 —— **一个挂在单个场景件实体上的全局难度修饰器**。

## 9. 打造同类游戏的关键模式

1. **把世界生成与游戏 VM 分开。** 生成 → 序列化（地块 + 实体位置 + 种子 + meta）→ 加载。好处：失败重试很便宜；生成对种子完全确定；载入界面只是回放一个数据块；可以无头生成世界（服务器、预览图）。（`worldgen_main.lua`、`gamelogic.lua`）
2. **用锁—钥匙进度图做地图布局。** 任务声明 `locks`/`keys_given`；连接算法从一个 `LOCKS.NONE` 的种子任务开始长地图，只在钥匙存在的地方挂生物群系，并跟踪 `story_depth` 让危险随距出生点距离增长。**为什么**：这保证每个种子都是*公平的* —— 资源先于守卫，守卫先于 Boss —— 而完全不需要手绘地图。（`map/lockandkey.lua`、`Story:LinkNodesByKeys`）
3. **两层内容描述：图（任务）vs 像素（房间）。** 任务决定*哪些*房间存在以及生物群系如何连接；房间是声明式散布规则（`value` 地块 + `countprefabs`/`distributeprefabs` 权重 + `distributepercent` 密度 + `prefabdata`）。**为什么**：设计师能以数据的方式写 255 个房间；平衡性 = 改数字。只在几何本身就是内容的地方，保留手写的 `static_layouts`（Tiled 导出）。
4. **Voronoi + 松弛得到有机区域。** 每个图节点播一个点云；Lloyd 松弛（`WorldGen_VoronoiPass(100)`，加区域时再 50 次）产生团块状的群系形状；噪声混合地块（`*_NOISE` id + 解析函数）柔化边界。**为什么**：图上的邻接 = 地图上的邻接，**免费获得**。
5. **注册地块，而不是枚举地块。** `TileManager.AddTile` 在保留区段（LAND/NOISE/OCEAN/IMPASSABLE，各 ≥256 宽）里分配 ID，并在一处挂上所有与地块相关的东西：贴图、噪声、走/跑/雪音效、小地图美术、`flooring/hard/roadways/cannotbedug` 标志、颜色。在存档里存一份 `world_tile_map`，加载时重映射 ID 以保持向前兼容（`DoDynamicTileConversion`）。
6. **世界是实体，系统是组件。** 时钟、季节、天气、Boss 生成器、野外火 —— 全都是 `TheWorld` 上的组件，通过世界事件（`ms_cyclecomplete`、`seasontick`、`phasechanged`、`weathertick`）和派生出的 `TheWorld.state` 表通信。**为什么**：任何系统都能按世界类型替换（森林 vs 洞穴 vs 泥沼 = 不同的组件列表），而且一切都可以统一地暂停/存档。
7. **时钟 = 整数段 + 脏标记事件，并随季节缓动。** 每阶段整数段让 UI（钟面）与逻辑（是否夜晚）天然同步；季节在季中逐渐修改段数，而不是突变。天气来自单个湿度累加器，配逐季的速率/上限表与温度迟滞的降雪切换。**为什么**：tuning 文件里的十来个数字就产生了整年的节奏。
8. **带睡眠语义 + 优先级周期抖动的行为树。** `PriorityNode(children, period)` 加随机初始相位把 AI 开销摊到时间轴上；节点级 `Sleep()`/`GetTreeSleepTime()` 让闲置怪物成本≈0；`EventNode` 提供即时反应（被攻击、回家）而不必抬高全局 tick 频率。实体离开模拟范围时脑被销毁，唤醒时由工厂重建。
9. **意图 → 动作 → 动画 → 效果。** 脑从不调用伤害函数；它们压入 `BufferedAction`（`DoAction` 节点 → `locomotor:PushAction`）。状态图的 `ActionHandler` 把动词转成状态，效果从某个 timeline 帧触发（`PerformBufferedAction`）。**为什么**：同一个"吃"对兔子和玩家都成立；打断（受击/冰冻/死亡）能统一取消待执行的动作；**动画本身就是玩法的时间源**。
10. **把关键帧写在动画帧上。** `TimeEvent(25*FRAMES, DoAttack)`、脚步声在第 7/15 帧、按钮仍按住时第 14 帧重复干活。起手冷却放在 `onenter`（这样起手不会被连点刷掉），但伤害在挥击中段施加，若被打断则在 `onexit` 里 `CancelAttack`。**为什么**：无需引擎侧关键帧工具，就能得到可读、可调的战斗手感。
11. **状态标签镜像到实体标签。** `busy`、`attack`、`moving`、`canrotate`、`sleeping`、`trapped` 从状态图状态流到 `inst` 标签，于是脑、战斗和其它实体都能做 O(1) 查询（`HasStateTag("busy")`、`inst:HasTag("attack")`），而不必理解彼此的状态机。**到处加迟滞**（逃跑起停带、牵引内外半径）以防振荡。
12. **复杂度放置规则。** trivial 怪给 20 行的脑；Boss 给 3 行的脑和巨大的状态图；村民给大号脑（作息、工作）和适中的状态图。剧本（通过存档数据挂载的 `OnCreate/OnLoad` 脚本）处理一次性场景件行为，不需要新预制体。**为什么**：把逻辑放在"你已经拥有所需计时模型"的地方 —— 树负责决策，状态图负责帧，剧本负责编排。

## 【深度扩写 E-1】世界生成的可运行实现：从零写出一张地图

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原版报告把世界生成描述为"调用 C++ WorldSim"，但没有说清**在没有 C++ 的情况下，怎么用纯数据结构复现这个结果**。这一节把整条链路拆成六个可独立实现的阶段，并给出伪代码。所有引用均已回到源码核实。

### E-1.1 原版的实际阶段划分

从 `map/forest_map.lua Generate()` 的执行顺序可以反推出六个阶段：

| 阶段 | 输入 | 输出 | 承担者 |
|---|---|---|---|
| S1 任务解析 | Level + TaskSet | Task 列表 | `Level:ChooseTasks()` / `ChooseSetPieces()` |
| S2 图构建 | Task 列表 | 节点/边图 | `Story:GenerationPipeline()` |
| S3 空间化 | 节点图 | 坐标 + Voronoi 归属 | `WorldSim`（C++） |
| S4 地块烘焙 | 坐标 + 节点 value | 地块网格 | `WorldSim:WorldGen_Commit` / `ConvertToTileMap` |
| S5 连通性修复 | 地块网格 | 陆地 + 道路 | `SeparateIslands` / `ForceConnectivity` / `DrawRoads` |
| S6 散布与校验 | 节点图 + 地块网格 | 实体清单 + savedata | `Node:PopulateVoronoi` 等 + 5 道校验 |

**这个划分本身就是可移植性的关键**：S2 是纯图的，与空间无关；S3/S4 需要几何算法；S5/S6 需要地块查询。仿写时可以逐段替换。

### E-1.2 S2 复现：锁—钥匙图的完整伪代码

原版的 `Story:LinkNodesByKeys`（`map/storygen.lua:493`）有一个容易被忽略的细节：它维护的 `availableKeys` 是**"钥匙 → 提供该钥匙的节点列表"**的映射，节点加入后把自己的所有 `keys_given` 塞进去。所以这个图是**逐步生长**的，每一步挂进去的任务都会扩大后续可选集合。

```
function LinkNodesByKeys(startTask, remainingTasks):
    lastNode   = startTask
    availableKeys = {}                       # KEYS.* -> [node]
    usedTasks  = {}
    startTask.story_depth = 0
    story_depth = 1

    for key in startTask.keys_given:
        availableKeys[key].append(startTask)

    while remainingTasks is not empty:
        effectiveLastNode = lastNode
        currentNode = nil

        # ---- 关键：按 pairs() 遍历剩余任务，谁先满足锁就选谁 ----
        for taskid, node in remainingTasks:
            locks = {}
            for lockid in tasks[taskid].locks:
                locks[lockid] = { keys = LOCKS_KEYS[lockid], unlocked = false }

            unlockingNodes = {}
            for lockid, lockData in locks:
                for key, keyNodes in availableKeys:
                    if key in lockData.keys:              # 任一钥匙即可开此锁
                        lockData.unlocked = true
                        for n in keyNodes:
                            unlockingNodes[n.id] = n     # 这些节点都能当父节点

            if all locks unlocked:
                currentNode = node
                # ---- 分支策略决定挂到哪个父节点 ----
                effectiveLastNode =
                    case branching:
                      default/random -> random(unlockingNodes)
                      most           -> argmin(parent.story_depth)
                      least          -> argmax(parent.story_depth)
                      never          -> lastNode            # 永远链尾 = 直线
                break                                      # 一轮只挂一个

        if currentNode == null:
            # 没有任何任务满足锁 —— 强制随机挂一个（可能是不可达内容）
            currentNode = random_remaining(remainingTasks)

        currentNode.story_depth = story_depth
        story_depth += 1

        exitNode = effectiveLastNode.GetRandomNodeForExit()
        entryNode = currentNode.entrancenode or currentNode.GetRandomNodeForEntrance()

        if island_percent != nil and rand() < island_percent and entryNode.entrance != true:
            SeparateStoryByBlanks(exitNode, entryNode)     # 插一段"断连"做孤岛
        else:
            rootNode.LockGraph(exitNode, entryNode, key = currentTask.locks)

        for key in currentNode.keys_given:
            availableKeys[key].append(currentNode)

        remove currentNode from remainingTasks
        usedTasks[currentNode.id] = currentNode
        lastNode = currentNode

    return lastNode.GetRandomNodeForExit()
```

**三个必须照抄的细节：**

1. **"全部锁都开"是 AND，"每个锁任一钥匙"是 OR。** 这条规则在 `map/lockandkey.lua:171-172` 的注释里，也直接写在 `LinkNodesByKeys` 的双重循环结构里。
2. **兜底分支。** 原版在没有任何任务可挂时会**强行随机挂一个**（`map/storygen.lua:596-599`），而不是放弃。这保证了"131 个任务一个不落"。代价是可能出现**逻辑上不可达**的任务（锁没满足却被挂上）。原版接受了这个代价 —— 因为它的锁主要用来*排序*难度，而不是真的做可达性验证。
3. **`branching` 策略。** `most` / `least` 直接影响地图形态：`most` 会把所有新内容挂到最浅的节点上（地图聚成一坨，中心密集），`least` 会挂到最深的（地图拉成长链），`never` 强制成一条直线。**这是原版唯一的"布局形状"控制旋钮**，非常值得在自己的实现里保留。

### E-1.3 S3 复现：Voronoi + Lloyd 松弛的完整伪代码

原版：`WorldSim:WorldGen_InitializeNodePoints()` → `WorldSim:WorldGen_VoronoiPass(100)`；每加一个新区（比如月岛）就 `WorldGen_AddNewPositions()` + `WorldGen_VoronoiPass(50)`（`map/forest_map.lua:501-506`）。

**Lloyd 松弛的纯实现**（不需要 Delaunay 三角剖分也能做，用"最近点归属"暴力版就够，复杂度 O(P × S)）：

```
function VoronoiPass(iterations):
    sites = 所有节点的位置        # 每个图节点一个 site，初始位置由 WorldSim 决定

    for iter in 1..iterations:
        # 1) 撒点：每个 site 周围按当前 Voronoi 胞元面积投 N 个点
        new_points = {}
        for site in sites:
            cell = compute_voronoi_cell(site, sites)     # 或直接采样整张图求最近归属
            n = max(1, round(cell.area * POINT_DENSITY))
            for k in 1..n:
                p = uniform_sample_in(cell)
                p.site = site.id
                new_points.append(p)

        # 2) 重心：把每个点的位置挪到它所属胞元的质心
        for site in sites:
            pts = [p for p in new_points if p.site == site.id]
            site.position = centroid(pts)                # 这就是 Lloyd 的一步

    # 3) 最终归属：每个图网格点归给最近的 site
    for each tile (x, y):
        tile.node_id = argmin over sites of dist((x,y), site.position)
```

**为什么 Lloyd 松弛值得实现**：它把初始的"随机圆点 Voronoi"（形状像蜂窝，很不自然）逐步变成"面积大致均匀、边界平滑"的胞元——**这正是生物群系该有的形状**。10 次迭代就能看出差别，100 次几乎完全均匀。生物群系越均匀，房间内的 `distributepercent` 密度就越可控（因为 `Node:PopulateVoronoi` 用的 `#points_x` 就是胞元点数）。

**关于 Voronoi 边界的软化**：原版不靠后处理柔化边界，而是靠 **`*_NOISE` 过渡地块**。`constants.lua` 里有 `DIRT_NOISE=123`、`GROUND_NOISE=125`、`CAVE_NOISE=126`、`FUNGUS_NOISE=127`、`ABYSS_NOISE=124`、`METEORMINE_NOISE=121`。机制是：`WorldSim:SetResolveNoiseFunction(GetTileForNoiseTile)`（`forest_map.lua:383`），在两个不同地块交界处，采样噪声决定最终取哪一侧的地块 id。`GetTileForNoiseTile` 查 `noisetilefunctions` 表，表里没有就用 `NoiseTileFunctions.default(noise)`。

所以边界软化的实现是：

```
for each tile (x, y):
    neighbors = 8 邻域的不同地块类型集合
    if len(neighbors) > 1:
        n = sample_perlin_noise(x * FREQ, y * FREQ)      # 0..1
        tile.value = resolve(noise_tile_id, n)            # 例如 GRASS_NOISE -> GRASS or DIRT
    else:
        tile.value = 该节点的 value
```

这块**完全可以在自己的引擎里先跳过**，直接硬边界，视觉效果只差一点，玩法完全不受影响。等核心跑通了再补。

### E-1.4 连通性：需不需要洪水填充？

**需要的，但不是在图层面，而是在地块层面。** 这是本节最重要的一个区分。

- **图层面（节点图）不需要。** `LockGraph` / `AddEdge` 保证的是"任务子图之间有边"。这层没有洪水填充的必要。
- **地块层面必须做洪水填充。** 原版做了两次相关工作，两次性质不同：

**（1）`WorldSim:ForceConnectivity(join_islands, false, WORLD_TILES.ROCKY)`（`forest_map.lua:536`）** —— 这是一次**强制连通**，把分离的陆地用 `ROCKY` 地块连起来。原版特意注明 `join_islands = not current_gen_params.no_joining_islands`（用户可控），并且注释说这一步"同时也会生成陆地地块"。源码里还有一句注释解释了为什么临时关闭了虫洞功能：

```lua
-- turning this off for now because its conflicting with the island tech and
-- disconnected node stripping, causing wormholes in the atrium
if false and not current_gen_params.no_wormholes_to_disconnected_tiles then
```

**（2）`WorldSim:DetectDisconnect()`（`forest_map.lua:855`）** —— 这是一次**孤立地块审计**，不是修复：

```lua
local replace_count = WorldSim:DetectDisconnect()
-- 允许最多 5% 的地块是断连的
if replace_count > math.floor(map_width * map_height * 0.05) then
    print("PANIC: Too many disconnected tiles...", replace_count)
    if SKIP_GEN_CHECKS == false then return nil end   # 整个生成重来
end
```

**洪水填充的标准实现**（4 邻域或 8 邻域），以及原版"孤立"判定的一个细节：

```
function DetectDisconnect(isLandTile, seedTile):
    # 1) 从"出生点"或地图中心开始 BFS
    visited = flood_fill(seed = 出生点 tile, 邻居 = 8 邻域,
                         谓词 = isLandTile)

    # 2) 全图扫描，找出所有"是陆地但没被访问到"的格子
    orphans = []
    for each tile where isLandTile(tile) and not visited[tile]:
        orphans.append(tile)

    # 3) 原版容忍 5%
    if len(orphans) > total_tiles * 0.05: return FAIL
    return orphans_count
```

原版的 `ForceConnectivity` 在做修复（挖通道），`DetectDisconnect` 在做验收（不够就重生成）。**自己实现时必须两者都有**：只有修复没有验收，会生成玩家永远走不到的"食物洞穴"；只有验收没有修复，会大量重试。

**为什么 5% 是合理的阈值**（推断）：孤岛本身是 DST 的合法内容（月岛、猴岛、废墟岛都是 `region_id ~= "mainland"`），所以不能要求 100% 连通。5% 的地块在 425×425 的图里是 9032 格，足够放几个小岛，又不至于多到玩家觉得"生成有问题"。

### E-1.5 资源分布权重：三套机制的叠加

原版有**三种完全不同的资源密度机制**，容易混淆。分清楚：

**（1）`distributeprefabs` + `distributepercent` —— 房间内的相对密度。**

`Node:PopulateVoronoi`（`map/graphnode.lua:330`）的实际执行：

```
points = WorldSim:GetPointsForSite(node.id)        # 该胞元的所有格点
current_pos_idx = 1

# a) countprefabs 先行：从第 1 个点开始逐个占用
for prefab, count in terrain_contents.countprefabs:
    if count is function: count = count(area, prefab, scratchpad)
    for k in 1..count:
        AddEntity(prefab, points[current_pos_idx], ...)
        current_pos_idx += 1
# 前置校验：#points_x < floor(pos_needed) 直接放弃整个节点
if #points_x < floor(pos_needed): return

# b) distributeprefabs：剩下的点，按 distributepercent 概率决定是否放
for i = current_pos_idx, #points_x:
    if rand() < distributepercent:
        prefab = pickspawnprefab(distributeprefabs, points_type[i])
        if prefab != nil: AddEntity(prefab, points[i], ...)
        else:              idx_left.append(i)         # 这个点被地形过滤掉了
    else:
        idx_left.append(i)
```

**`pickspawnprefab`（`forest_map.lua:16`）就是加权随机**，实现非常朴素：

```
function pickspawnprefab(items_in, ground_type):
    items = {}
    for name, weight in items_in:
        items[name] = weight
        if TERRAIN_FILTER[name] != nil:
            for blocked_tile in TERRAIN_FILTER[name]:
                if blocked_tile == ground_type:
                    items[name] = nil                 # 该地块上不能长 -> 剔除
    total = sum(items.values())
    if total > 0:
        r = rand() * total
        for name, weight in items:
            r -= weight
            if r <= 0: return name
```

注意这里的两点：**（a）过滤发生在抽样之前，不是之后；**（b）**权重是相对值，不是概率**——`{evergreen_sparse = 3, spiderden = 0.3}` 意味着蜘蛛巢穴只有常青树的 1/10 常见。

**（2）`MULTIPLY` + `PopulateExtra` —— 世界生成设置控制的"加量"。**

用户在前端选"更多/更少"，转成倍率（`forest_map.lua:86`）：

```lua
local MULTIPLY = { ["never"]=0, ["rare"]=0.5, ["uncommon"]=0.75, ["default"]=1,
                   ["often"]=1.5, ["mostly"]=2.2, ["always"]=3, ["insane"]=6,
                   ["ocean_never"]=0, ... ["ocean_insane"]=4 }
```

这些倍率**不修改房间定义**，而是在 `Node:PopulateExtra`（`graphnode.lua:567`）里用"上一轮没用掉的点"（`idx_left`）加量：

```
for prefab, amt in world_gen_choices:
    if amt is number:
        if data.prefab_list[prefab]:          # 本节点已经放过
            amount_to_generate[prefab] = floor(data.prefab_list[prefab] * amt) - data.prefab_list[prefab]

for idx in data.idx_left:                     # 遍历剩余空位
    prefab = pickspawnprefab(amount_to_generate, ...)
    if prefab: AddEntity(...); amount_to_generate[prefab] -= 1
```

**（3）`mult < 1` 的减量 —— 生成后的裁剪。** 这是**唯一**会真正减少数量的路径（`forest_map.lua:904-919`）：先 `shuffleArray`，再 `table.remove` 到 `floor(总数 * mult)`。也就是说"更少"是**随机砍**，不是"一开始就少放"。这会造成一个玩家能察觉的偏斜：减量后的实体在空间上仍是随机的，但砍掉的比例对所有同类实体一致。

**（4）`CLUMP` / `CLUMPSIZE` —— 成簇。** 只有国际象棋棋子用了（`TRANSLATE_TO_CLUMP`），但机制值得抄：`{clumpcount = 15, clumpsize = {2,3}}` 意思是"最多 15 簇，每簇 2–3 个"，判定是 `if amt.clumpcount > 0 and 0.25 > rand()`（25% 概率每生成一个点就开一簇）。

**（5）`required_prefabs` —— 硬性下限校验。** 三处来源求和（`forest_map.lua:926-974`）：

```

for prefab, count in rootNode.GetRequiredPrefabs(): # 任务/房间累加
    double_check[prefab] += count

```

**这是"保证地图有可玩性"的核心机制**，下一节展开。

### E-1.6 任务点位选择：场景件怎么落到格子上

原版有**两条**落位路径，对应两种内容性质。

**路径 A：动态房间 + 权重散布**（上一节的 `distributeprefabs`）。适合"这一片都应该长点草"这类内容。

**路径 B：静态布局 `countstaticlayouts` —— 手工几何落位。** 走 `Node:ConvertGround`（`graphnode.lua:247`）→ `obj_layout.Convert(node.id, k, add_fn)` → `map/object_layout.lua` 的 `ReserveAndPlaceLayout`：

```
function ReserveAndPlaceLayout(node_id, layout, prefabs, add_entity, position):
    # 1) 算包围盒
    extents = MinBoundingBox(prefabs 的位置)
    size = max(extents.xmax-xmin, extents.ymax-ymin) / 2 * layout.scale

    # 2) 随机变换（除非 disable_transform）
    switch_xy = rand_bool()            # 转置
    flip_x    = ±1                     # 镜像
    flip_y    = ±1

    # 3) 要用到的地块类型矩阵（如果 layout.ground 存在）
    for column in 1..size, row in 1..size:
        apply switch_xy / flip 变换
        tiles.append(layout.ground_types[layout.ground[row][col]])   # 0 表示不铺

    # 4) 向 C++ 申请一块矩形空地
    rcx, rcy = world:ReserveSpace(node_id, size, start_mask, fill_mask, layout_position, tiles)
    if rcx == nil: return               # 塞不下 -> 放弃这个布局（不报错）

    # 5) 把预制体按变换后的坐标写进去
    for prefab in prefabs:
        x, y = apply_transform(prefab.x, prefab.y)
        add_entity(prefab.name, rcx + x, rcy + y)
```

三个值得抄的点：

- **`ReserveSpace` 失败就静默放弃**，不报错、不重试。这解释了为什么原版需要 `SafeFromDisconnect` 和 `countstaticlayouts` 的配额控制——配额太满时静默丢失配额。
- **`layout.areas` —— 区域化布局。** `ConvertLayoutToEntitylist`（`object_layout.lua`）支持 `areas = { 某个预制体 = function(area_size, prefab_data) ... end }`，即**按区域的面积决定塞多少东西**。这是"小房间里放 1 个，大房间里放 3 个"的自适应做法。
- **`layout.defs` —— 一对多的替换。** `defs[current_prefab]` 是一个候选列表，随机挑一个替换。这让同一份布局能生成"石头阵 / 铁柱阵 / 骨头阵"三种变体。

### E-1.7 迷宫：静态布局搞不定的情况

原版对"几何必须是迷宫"的情况走专门通道（`forest_map.lua:645-838`），分两种：

**`WorldSim:RunMaze(MAZE_TYPE.MAZE_GROWINGTREE_4WAY, val, IMPASSABLE, BRICK, nodes)`** —— 生成"长树迷宫"，返回格点数组 + `types`（每格的开口方向编码，1/2/4/8 表示四个方向的开口，绝对值 = 房间类型，负号 = boss 房）。原版在迷宫里塞 `pandoraschest`，并带 `scenario = "chest_labyrinth"`。

**`WorldSim:GetPointsForMetaMaze(maze_tile_size, nodes)`** —— 生成"元迷宫"（缩放版），然后原版按 `MAZE_CELL_EXITS_INV[types[idx]]` 的出口方向表挑房间类型：`types > 0` 放 `choices.rooms`，`types < 0` 放 `choices.bosses`。distances 数组按到入口质心的距离排序，用于"起在最远端、终在最近端"。

**迷宫接回地面的补丁**（这段代码很能说明问题）：

```lua
-- 迷宫可能在地图边缘把自己和陆地切断，所以画一小段路把它接回来
for node in GlobalTags["MazeEntrance"][task]:
    entrance_node = rootNode:GetNodeById(node)
```

**`FAKE_GROUND` 是个很妙的技巧**，源码注释解释了它（`forest_map.lua:846-852`）：

> *" sigh，`ForceDisconnected` 标签实际上并不能让某物（比如 Atrium）真正与大陆断开连。它反而依赖这个 `FAKE_GROUND` 地块在生成期间把它连上主陆，然后事后清理掉。…… 现在你可以给房间或静态布局设置 `SafeFromDisconnect`，把它们的格子排除在断连清理之外。"*

## 【深度扩写 E-2】AI 状态机的可运行实现

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原版报告把 DST 的 AI 讲成了"行为树 + 动画状态机"两层，但对**如何从零写出一个生物的 AI**着墨不多。这一节给出可直接照抄的骨架。

### E-2.1 两层为什么必须分开

先把分工讲透，这是所有仿写最容易做错的地方：

```
┌──────────────────────────────────────────────────────────────────┐
│ 决策层（行为树 / 脑）                          频率：0.25–1 Hz  │
│   "我现在该去哪儿？该打谁？该回家吗？"                            │
│   输出：意图（BufferedAction / 移动目标点）                       │
│   不知道：动画长什么样、动作要多久、什么时候真的生效              │
└───────────────────────────┬──────────────────────────────────────┘
                            │ locomotor:PushAction / GoToPoint
                            ▼
┌──────────────────────────────────────────────────────────────────┐
│ 执行层（状态图）                              频率：每帧 / 睡眠   │
│   "我现在处于哪个动画状态，第几帧，该做什么"                      │
│   包含：动画、音效、位移、伤害帧、打断点                          │
└──────────────────────────────────────────────────────────────────┘
```

**分开带来的三个好处**（原版第 9 条模式已经说了，这里补上"为什么")：

1. **同一份决策代码复用于任何身体。** 兔子的"吃"和玩家的"吃"是两个状态图的 `eat` 状态，但 `DoAction(EatFoodAction)` 这个脑节点完全一样。
2. **打断是统一处理的。** 任何状态只要带 `busy` 标签并实现 `onexit`，就能被统一取消。`ClearBufferedAction()` 一调用，整条"意图 → 动画 → 效果"链就断了。
3. **动画就是时间源。** 伤害在第 25 帧、开火在第 8 帧——这些数字写在 timeline 里，不在引擎的关键帧系统里。改手感就是改一个数字。

### E-2.2 决策层骨架代码：最小可用行为树

下面是**完整可跑**的行为树最小实现（对应原版 `behaviourtree.lua` 的核心，约 200 行，去掉了调试字符串）：

```python
# ─────────────────────────────────────────────────────────────
# 最小行为树（对应 DST behaviourtree.lua）
# 状态：SUCCESS / FAILED / READY / RUNNING
# ─────────────────────────────────────────────────────────────
from enum import Enum

class Status(Enum):
    SUCCESS = "SUCCESS"
    FAILED  = "FAILED"
    READY   = "READY"
    RUNNING = "RUNNING"


class Node:
    def __init__(self, name=""):
        self.name    = name
        self.children = []
        self.status   = Status.READY
        self.lastresult = Status.READY
        self.next_wake_time = None      # 对应 nextupdatetime
        self.parent  = None
        for c in self.children:
            c.parent = self

    # ---- 三个核心钩子，子类覆写 ----
    def visit(self):                   # 计算 status
        self.status = Status.FAILED

    def step(self):                    # 在整棵树 visit+save 之后调用
        if self.status != Status.RUNNING:
            self.reset()
        else:
            for c in self.children:
                c.step()

    def reset(self):
        if self.status != Status.READY:
            self.status = Status.READY
            for c in self.children:
                c.reset()

    # ---- 睡眠契约 ----
    def sleep(self, seconds):
        self.next_wake_time = now() + seconds

    def get_sleep_time(self):
        """只在「叶子 + RUNNING + 非 Condition」时才有睡眠值。"""
        if self.status == Status.RUNNING and not self.children \
           and not isinstance(self, Condition):
            if self.next_wake_time is not None:
                return max(0.0, self.next_wake_time - now())
            return 0.0
        return None

    def get_tree_sleep_time(self):
        """取所有 RUNNING 分支上的最小睡眠时间。"""
        t = None
        for c in self.children:
            if c.status == Status.RUNNING:
                ct = c.get_tree_sleep_time()
                if ct is not None and (t is None or t > ct):
                    t = ct
        mine = self.get_sleep_time()
        if mine is not None and (t is None or t > mine):
            t = mine
        return t


class Condition(Node):
    """每次访问都重测，永不睡眠。"""
    def __init__(self, fn, name="Condition"):
        super().__init__(name)
        self.fn = fn

    def visit(self):
        self.status = Status.SUCCESS if self.fn() else Status.FAILED


class WaitNode(Node):
    def __init__(self, seconds):
        super().__init__("Wait")
        self.seconds = seconds
        self.wake_time = None

    def visit(self):
        if self.status != Status.RUNNING:
            self.wake_time = now() + self.seconds
            self.status = Status.RUNNING
        if now() >= self.wake_time:
            self.status = Status.SUCCESS
        else:
            # 注意：DST 这里传的是负值（current_time - self.wake_time），是个笔误，
            # 效果是 nextupdatetime 立刻过期 → 每帧唤醒。自己实现时写对的。
            self.sleep(self.wake_time - now())


class Sequence(Node):
    """AND：第一个 FAILED 或 RUNNING 就停。"""
    def __init__(self, children):
        super().__init__("Sequence")
        self.children = children
        self.idx = 1

    def visit(self):
        if self.status != Status.RUNNING:
            self.idx = 1
        while self.idx <= len(self.children):
            child = self.children[self.idx - 1]
            child.visit()
            if child.status in (Status.RUNNING, Status.FAILED):
                self.status = child.status
                return
            self.idx += 1
        self.status = Status.SUCCESS

    def reset(self):
        super().reset()
        self.idx = 1


class Selector(Node):
    """OR：第一个 SUCCESS 或 RUNNING 就停。"""
    def __init__(self, children):
        super().__init__("Selector")
        self.children = children
        self.idx = 1

    def visit(self):
        if self.status != Status.RUNNING:
            self.idx = 1
        while self.idx <= len(self.children):
            child = self.children[self.idx - 1]
            child.visit()
            if child.status in (Status.RUNNING, Status.SUCCESS):
                self.status = child.status
                return
            self.idx += 1
        self.status = Status.FAILED

    def reset(self):
        super().reset()
        self.idx = 1


class Priority(Node):
    """DST 的主力节点：每 period 秒重评一次，其余时间沿用上次赢家。

    period 末尾的随机相位是整个系统能扛住几千只怪的关键。
    """
    def __init__(self, children, period=1.0, no_scatter=False):
        super().__init__("Priority")
        self.children = children
        self.period = period
        self.idx = None
        if not no_scatter:
            # 原版：self.lasttime = period*0.5 + period*rand()
            # 效果：首评时刻在 [0.5*period, 1.5*period] 之间均匀分布
            self.next_eval_time = now() + period * (0.5 + random())

    def visit(self):
        t = now()
        do_eval = self.next_eval_time is None or t >= self.next_eval_time
        old_event = None
        if self.idx and isinstance(self.children[self.idx - 1], EventNode):
            old_event = self.children[self.idx - 1]

        if do_eval:
            self.next_eval_time = t + self.period
            found = False
            for i, child in enumerate(self.children):
                # EventNode 抢占：优先级更高的事件节点即使排在后面也要试
                should_test = (not found) or \
                              (old_event and isinstance(child, EventNode)
                               and old_event.priority <= child.priority)
                if should_test:
                    if child.status in (Status.FAILED, Status.SUCCESS):
                        child.reset()
                    child.visit()
                    if child.status in (Status.SUCCESS, Status.RUNNING):
                        if should_test and self.idx != i:
                            self.children[self.idx - 1].reset()
                        self.status = child.status
                        found = True
                        self.idx = i
                else:
                    child.reset()
            if not found:
                self.status = Status.FAILED
        else:
            # 未到重评时间：只让当前赢家继续跑
            if self.idx:
                child = self.children[self.idx - 1]
                if child.status == Status.RUNNING:
                    child.visit()
                    self.status = child.status
                    if self.status != Status.RUNNING:
                        self.next_eval_time = None      # 赢家结束了 → 立即重评

    def reset(self):
        super().reset()
        self.idx = None

    def get_sleep_time(self):
        if self.status == Status.RUNNING:
            if self.next_eval_time is None:
                return 0.0
            return max(0.0, self.next_eval_time - now())
        elif self.status == Status.READY:
            return 0.0
        return None


class EventNode(Node):
    """监听实体事件 → 强制唤醒整棵树。这是「即时反应」的实现方式。"""
    def __init__(self, inst, event, child, priority=0):
        super().__init__(f"Event({event})")
        self.inst = inst
        self.event = event
        self.child = child
        self.children = [child]
        self.priority = priority
        self.triggered = False

    def on_event(self, data):
        if self.status == Status.RUNNING:
            self.child.reset()
        self.triggered = True
        self.data = data
        self.inst.brain.force_update()          # 立刻唤醒，不等 period
        # 向上把祖先 Priority 的重评计时清空
        n = self.parent
        while n:
            if isinstance(n, Priority):
                n.next_eval_time = None
            n = n.parent

    def visit(self):
        if self.status == Status.READY and self.triggered:
            self.status = Status.RUNNING
        if self.status == Status.RUNNING:
            self.child.visit()
            self.status = self.child.status

    def reset(self):
        self.triggered = False
        super().reset()

    def step(self):
        super().step()
        self.triggered = False


class Parallel(Node):
    """DST 的 WhileNode = Parallel{Condition, node}，可打断。"""
    def __init__(self, children):
        super().__init__("Parallel")
        self.children = children

    def visit(self):
        done = True
        for child in self.children:
            if isinstance(child, Condition):
                child.reset()                     # ← 每帧重测，这是可打断的来源
            if child.status != Status.SUCCESS:
                child.visit()
                if child.status == Status.FAILED:
                    self.status = Status.FAILED
                    return
            if child.status == Status.RUNNING:
                done = False
        self.status = Status.SUCCESS if done else Status.RUNNING


# ---- 语法糖 ----
def WhileNode(cond, name, node):
    """条件每帧检查 → 条件一变，node 立刻被打断。"""
    return Parallel([Condition(cond, name), node])

def IfNode(cond, name, node):
    """条件只检查一次 → 直到 node 成功/失败都不再复查。"""
    return Sequence([Condition(cond, name), node])
```

**行为树的执行入口**（对应 `BT:Update()`）：

```python
class BT:
    def __init__(self, inst, root):
        self.inst = inst
        self.root = root
        self.force_update = False

    def update(self):
        self.root.visit()        # 1. 自顶向下算状态
        # （原版还有 SaveStatus，这里只用于调试字符串，省略）
        self.root.step()         # 2. 清理已结束的分支
        self.force_update = False

    def get_sleep_time(self):
        if self.force_update:
            return 0.0           # 强制更新 → 下一刻就醒
        return self.root.get_tree_sleep_time()   # None = 冬眠
```

**为什么 `step()` 与 `visit()` 要分开**（这是原版的一个精妙设计，很容易看漏）：

- `visit()` 沿树往下走，**不重置**任何东西——RUNNING 节点保留 `idx` 和内部状态，所以 `Sequence` 能从上次停的地方继续。
- `step()` 在 `visit()` 之后跑，**把非 RUNNING 的子树整体重置**。于是下一帧的 `visit()` 从干净状态重新开始。
- 分开的直接好处：**RUNNING 子树的内部状态天然保留**，不需要额外的"记忆"机制。

### E-2.3 思考周期（Think Period）的正确设置

原版的周期值不是随手填的，它们有明确的语义分工（已从源码核实）：

| 生物 | period | 为什么是这个值 |
|---|---|---|
| 兔子 | **0.25 s** | 猎物。逃跑判定必须快，否则玩家贴脸了兔子还在原地评估 |
| 猪（白天） | 0.5 s | 村民。半秒一次足够跟得上玩家走动 |
| 猪（夜晚） | 1 s | 夜晚行为更简单（回家/找光/恐慌） |
| 蜘蛛 | 1 s | 战斗怪但决策简单；`ChaseAndAttack` 内部 8 Hz 已经够 |
| 巨鹿 | 1 s | Boss 的决策只有"打或闲逛" |
| `ChaseAndAttack` 内部 | `Sleep(.125)` | **8 Hz 转向**，独立于脑的 period |
| `RunAway` 内部 | `Sleep(.25)` | 4 Hz 转向 |
| `Follow` 内部 | `Sleep(.25)` | 4 Hz |

**分层原则（这是可以直接照抄的规则）**：

```
顶层 PriorityNode.period      = 决策频率（换目标、换行为）
    └── ChaseAndAttack / RunAway / Follow 的 self:Sleep(x)
                              = 转向频率（在已选定的行为内持续微调）
```

**转向频率应该 ≥ 决策频率的 3–8 倍**。1 Hz 的脑配 8 Hz 的转向，看起来才跟手。

**随机相位散布**（`PriorityNode` 构造函数）：

```python
self.next_eval_time = now() + period * (0.5 + random())
```

这一行是整个系统能扛住几千只怪的关键。100 只蜘蛛各有 0.5–1.5 s 的初始相位，于是它们的重评在时间轴上**均匀铺开**，而不是同一刻全部触发形成尖峰。没有这一行，1 Hz × 1000 只怪 = 每秒 1000 次集中重评，直接掉帧。

### E-2.4 脑参数：好奇心与愤怒的建模

> **注意**：原版**没有**通用的"好奇心 / 愤怒"参数体系——这是本节的**设计建议**，基于原版已有的分散机制归纳，标注为**推断**。

原版把"情绪"拆散在了各个具体机制里：

| `Wander` 的 `wander_dist` + `WanderFromSaltlickDistFn` | `brains/braincommon.lua` | 好奇半径（盐lick 越近，逛得越远——反直觉但源码如此） |

**如果要做一套通用的性格参数**，可行的最小设计（**推断**）：

```python
class Personality:
    """
    把分散在原版各处的东西显式化。取值 0..1，全部可被 prefab 数据覆写。
    """
    def __init__(self, curiosity=0.5, aggression=0.5, courage=0.5,
                 sociability=0.5, attachment=0.5):
        self.curiosity   = curiosity   # 影响 FaceEntity 触发距离、闲逛半径
        self.aggression  = aggression  # 影响 ChaseAndAttack 的 max_chase_time / max_attacks
        self.courage     = courage     # 影响 RunAway 的 see_dist（越低越早逃）
        self.sociability = sociability # 影响 Follow 的 min_dist（越低越贴近）
        self.attachment  = attachment  # 影响 Leash 的 max_dist（越低越恋家）
```

各参数到原版既有参数的映射（**全部可在源码中找到对应的具名字段**）：

| 参数 | 低值时的效果 | 高值时的效果 | 对应原版参数 |
|---|---|---|---|
| `courage` | `RunAway(inst, p, 3, 6)`（3 距离就逃） | `RunAway(inst, p, 8, 20)`（贴脸才逃） | `behaviours/runaway.lua` 的 `see_dist` / `safe_dist` |
| `aggression` | `ChaseAndAttack(inst, 2)`（2 秒放弃） | `ChaseAndAttack(inst, 30, 40)`（追 30 秒 / 40 距离） | `behaviours/chaseandattack.lua` 的 `max_chase_time` / `give_up_dist` |
| `sociability` | `Follow(inst, t, 5, 10, 20)`（保持距离） | `Follow(inst, t, 1, 3, 8)`（紧贴） | `behaviours/follow.lua` 的 `min_dist` / `target_dist` / `max_dist` |
| `attachment` | `Leash(inst, home, 10, 3)`（恋家） | `Leash(inst, home, 60, 20)`（到处跑） | `behaviours/leash.lua` 的 `maxdist` / `returndist` |
| `curiosity` | 不放 `FaceEntity` | `FaceEntity(inst, nearest_player, 20)` | `behaviours/faceentity.lua` |

**迟滞是硬性要求，不是优化。** 原版所有距离判断都是"双带"或"内外半径"：

- `RunAway`：3 触发 / 6 停止
- `Leash`：>30 启动回家 / <10 才算到家
- `Follow`：`max_dist` 触发 APPROACH / `min_dist` 触发 BACKOFF / `target_dist` 算成功
- `Wander`：超出 `max_dist` 时**改为回家**，回到范围内恢复闲逛

单阈值会导致生物在边界上抖动（A→B→A→B），视觉上非常明显，而且每帧都触发一次寻路请求，直接拖垮 CPU。

### E-2.5 执行层骨架代码：最小状态图

```python
# ─────────────────────────────────────────────────────────────
# 最小状态图（对应 DST stategraph.lua）
# ─────────────────────────────────────────────────────────────
FRAMES = 1.0 / 30.0

class TimeEvent:
    """对应 TimeEvent / FrameEvent。构造函数时按时间排序。"""
    def __init__(self, time, fn):
        self.time = time
        self.fn = fn

    @staticmethod
    def frame(f, fn):
        return TimeEvent(f * FRAMES, fn)


class EventHandler:
    def __init__(self, name, fn):
        self.name = name.lower()
        self.fn = fn


class ActionHandler:
    """动作动词 → 状态名。可以是字符串，也可以是函数（检查装备等上下文）。"""
    def __init__(self, action, dest_state, condition=None):
        self.action = action
        self.dest_state = dest_state if callable(dest_state) else (lambda inst, ba: dest_state)
        self.condition = condition


class State:
    def __init__(self, name, tags=(), onenter=None, onupdate=None,
                 ontimeout=None, onexit=None, events=(), timeline=()):
        self.name = name
        self.tags = set(tags)
        self.onenter, self.onupdate = onenter, onupdate
        self.ontimeout, self.onexit = ontimeout, onexit
        self.events = {e.name: e for e in events}
        self.timeline = sorted(timeline, key=lambda e: e.time)   # ← 构造时排序


class StateGraph:
    """共享不可变蓝图：一个 SG 定义 + N 个 StateGraphInstance。"""
    def __init__(self, name, states, events, default_state, action_handlers):
        self.name = name
        self.states = {s.name: s for s in states}
        self.events = {e.name: e for e in events}
        self.default_state = default_state
        self.action_handlers = {ah.action: ah for ah in action_handlers}


# 状态标签 → 实体标签的镜像白名单（对应 SGTagsToEntTags）
SG_TAGS_TO_ENT_TAGS = {"attack", "busy", "moving", "sleeping", "doing",
                       "noattack", "idle", "hiding", "flight", "working"}


class StateGraphInstance:
    def __init__(self, sg, inst):
        self.sg = sg
        self.inst = inst
        self.current = None
        self.time_in_state = 0.0
        self.timeline_index = None
        self.timeout = None
        self.tags = set()
        self.state_mem = {}       # 逐状态临时数据，切换时清空
        self.mem = {}             # 跨状态保留
        self.buffered_events = []

    # ---- 转换：对应 GoToState ----
    def go_to(self, state_name, params=None):
        state = self.sg.states.get(state_name)
        if state is None:
            warn(f"实体 {self.inst} 试图进入不存在的状态 {state_name}")
            return

        if self.current and self.current.onexit:
            self.current.onexit(self.inst, state_name)

        self.state_mem = {}                     # 清空临时数据
        old_tags = self.tags
        self.tags = set(state.tags)
        # ← 状态标签镜像到实体标签，脑和别的系统就能做 O(1) 查询
        for tag in SG_TAGS_TO_ENT_TAGS:
            if tag in self.tags and tag not in old_tags:
                self.inst.add_tag(tag)
            elif tag not in self.tags and tag in old_tags:
                self.inst.remove_tag(tag)

        self.timeout = None
        self.timeline_index = 0 if state.timeline else None
        self.time_in_state = 0.0
        self.current = state

        if state.onenter:
            state.onenter(self.inst, params)
        self.inst.push_event("newstate", {"statename": state_name})

    def set_timeout(self, t):
        self.timeout = t

    def has_tag(self, tag):
        return tag in self.tags

    # ---- 事件 ----
    def push_event(self, name, data=None):
        data = data if data is not None else {}
        data["state"] = self.current.name       # 打上来源状态，避免陈旧事件
        self.buffered_events.append((name, data))

    def handle_events(self):
        for name, data in self.buffered_events:
            # 1) 当前状态的 handler 优先
            if data.get("state") is None or data["state"] == self.current.name:
                h = self.current.events.get(name)
                if h:
                    h.fn(self.inst, data)
                    continue
            # 2) 图级 handler 兜底
            h = self.sg.events.get(name)
            if h:
                h.fn(self.inst, data)
        self.buffered_events.clear()

    # ---- 更新 ----
    def update_state(self, dt):
        self.time_in_state += dt
        start_state = self.current

        if self.timeout is not None:
            self.timeout -= dt
            if self.timeout < 1e-4:             # epsilon，浮点误差
                self.timeout = None
                if self.current.ontimeout:
                    self.current.ontimeout(self.inst)
                    if start_state is not self.current:
                        return                   # ontimeout 改了状态，直接返回

        # 触发所有到点的 timeline 事件
        while (self.timeline_index is not None
               and self.timeline_index < len(self.current.timeline)
               and self.current.timeline[self.timeline_index].time <= self.time_in_state):
            idx = self.timeline_index
            self.timeline_index += 1
            extra_time = self.time_in_state - self.current.timeline[idx].time
            self.current.timeline[idx].fn(self.inst)
            if start_state is not self.current:
                # timeline 中途改了状态 → 递归推进新状态
                self.update(extra_time)
                return

        if self.current.onupdate:
            self.current.onupdate(self.inst, dt)

    def update(self, dt=None):
        if dt is None:
            dt = FRAMES
        self.update_state(dt)

        time_to_sleep = None
        if self.timeline_index is not None and self.timeline_index < len(self.current.timeline):
            time_to_sleep = self.current.timeline[self.timeline_index].time - self.time_in_state
        if self.timeout is not None and (time_to_sleep is None or time_to_sleep > self.timeout):
            time_to_sleep = self.timeout

        if self.current.onupdate:
            return 0.0                # 需要每帧
        elif time_to_sleep is not None:
            return time_to_sleep       # 睡到下一个关键点
        else:
            return None                # 冬眠

    # ---- 动作入口：对应 StartAction ----
    def start_action(self, buffered_action):
        handler = self.sg.action_handlers.get(buffered_action.action)
        if handler is None:
            return False
        if handler.condition and not handler.condition(self.inst):
            return False
        dest = handler.dest_state(self.inst, buffered_action)
        if dest is None:
            return False                          # 返回 nil = 拒绝动作
        self.go_to(dest)
        return True
```

**`update()` 返回三种值的语义**（这是整个节能体系的核心，必须精确实现）：

| 返回值 | 含义 | 调度器动作 |
|---|---|---|
| `0.0` | 需要每帧（状态有 `onupdate`） | 留在 `updaters` 名单，下一帧继续 |
| 正数 | 可以睡 N 秒 | 停到 `tickwaiters[当前 tick + N]` |
| `None` | 冬眠 | 移出所有活跃名单，只有事件或唤醒能叫醒 |

```python
        return
    loco = inst.components.locomotor
    if not loco.wants_to_move_forward():
        inst.sg.go_to("idle")
    elif loco.wants_to_run():
```

**完整的意图 → 效果链路**（一次 `DoAction` 调用的完整展开）：

```
1. 脑：ChaseAndAttack 发现目标在攻击范围内 → combat:TryAttack()
        → 触发 combat 的 "tryattack" → inst.sg:StartAction(BufferedAction{action=ATTACK})
2. 状态图：start_action() 查到 ActionHandler("ATTACK") → dest = "attack"
        → go_to("attack")
3. attack.onenter：Physics:Stop()、combat:StartAttack()（冷却起算）、PlayAnimation("atk")
4. tick N：timeline 第 25 帧触发 → combat:DoAttack(target) → 扣血
5. 期间若被打：hit 状态 → clear_buffered_action() → attack.onexit → combat:CancelAttack()
```

**第 5 步是整套设计里最优雅的地方**：打断不是特殊分支，而是"任何带 `busy` 标签的状态在 `onexit` 时统一撤销自己的未完成意图"。

### E-3.2 隐式保证 1：难度梯度由 story_depth 保证

原版第 9 条模式说了原理，这里补上"怎么落地"。

**`story_depth` 的实际用途**（源码核实）：`PlaceTeleportatoParts`（`map/storygen.lua:118`）用它决定有序场景件放在哪：

```lua
local function InsertPartnumIntoATask(partnum, partSpread, part, tasks)
    for id, task in pairs(tasks) do
        if task.story_depth == math.ceil(partnum * partSpread) then
            return AddPartToTask(part, task)
        end
    end
end

local maxdepth = max(node.story_depth for node in rootNode:GetChildren())
local partSpread = maxdepth / #parts
```

**玩家的实际体验**：从出生点出发，沿路解锁的任务越来越"后期"（`KEYS.TIER4` / `TIER5` 这类），而这些任务在图上被挂得越来越远。所以**地图的地理距离 ≈ 进度**。这是"难度梯度长在地图上"的精确含义。

**仿写时的实现建议（推断）**：比 `story_depth` 计数器更好的做法是记录**图上的真实 BFS 距离**：

```
# 更好的方案：记录真实最短路距离
dist[startNode] = 0
queue = [startNode]
while queue:
    n = queue.pop()
    for m in neighbors(n):
        if m not in dist:
            dist[m] = dist[n] + 1
            queue.append(m)
```

`story_depth` 计数器在 `branching = "most"` 模式下会严重失真（所有新内容都挂到最浅节点，深度增长极慢）。真实 BFS 距离不受分支策略影响。

```
□ 没有"必须绕整个图才能过"的死锁
□ 难度梯度单调：越远的节点 story_depth 越大
```

**D 组的可解性检查是原版的缺口，值得补**。原版的兜底逻辑（`storygen.lua:596`）是：

```lua
if currentNode == nil then
    currentNode = self:GetRandomNodeFromTasks(unusedTasks)
    print_lockandkey("\t\tAttaching random node "..currentNode.id.." to last node", ...)
end
```

这保证了"任务不会丢"，但也意味着**可能存在锁没满足就被挂上去的任务**。结果就是玩家能走到一个本该后期才能进的地方（例如直接摸到巨鹿）。补上 BFS 可解性检查，只需要改一行：

```
# 在 LinkNodesByKeys 的兜底分支里：
if currentNode == null:
    # 原版：随机挂一个
    # 改进：只从"可解锁"集合里挂；若为空则报错而非静默
    candidates = [t for t in remainingTasks if locks_satisfiable(t, availableKeys)]
    if not candidates:
        return FAIL                  # ← 让外层重试，而不是产出坏图
    currentNode = random(candidates)
```

### E-4.1 数字的真实构成

先把这几个"看起来很大"的数字拆开，避免误判复杂度：

### E-4.2 生成期性能：原版的四个设计

**（1）世界生成不在游戏主循环里。** 它跑在独立的离线 VM（`worldgen_main.lua` 自建 `package.loaders`），既没有 TheWorld 也没有模拟。失败重来时 `collectgarbage("collect")` + `WorldSim:ResetAll()`，代价可控。

**（2）数据表深拷贝而非共享。** `Story:GetRoom`（`map/storygen.lua:107`）每次都 `deepcopy(Rooms.GetRoomByName(roomname))`。这是为了允许模组在 `RoomPreInit` 钩子里改房间而不污染全局。**代价是内存换时间**——131 个任务 × 平均 8 个房间 = 约 1000 次深拷贝。对一次性生成完全可以接受。

**（3）散布是 O(胞元点数) 的，不是 O(面积)。** `Node:PopulateVoronoi` 遍历的是 `WorldSim:GetPointsForSite(node.id)` 返回的点，而不是遍历整块区域的每个格子。每个胞元的点数由 Lloyd 松弛后的密度决定，是被显式控制的。

**（4）静态布局的 `ReserveSpace` 失败即放弃，不回溯。** 这避免了"布局放不下 → 换个位置重试 → 又放不下"的指数级搜索。代价是配额可能静默丢失（E-1.6 提到）。

**自研实现时的性能预算（推断）**：

```
阶段                    目标耗时        主要开销
─────────────────────────────────────────────────────
任务解析 + 图构建        < 50 ms        纯表操作，约 1000 次深拷贝
Voronoi + Lloyd ×100     2–8 s          O(P × S)，P=格点数 S=站点数
                            ↑ 这是唯一的大头
地块烘焙                 0.5–2 s        O(W × H)，425² ≈ 18 万格
连通性修复 + 洪水填充      0.3–1 s        O(W × H)
散布                      1–3 s          O(P) 加上权重抽样的 O(N) 预处理
校验                      < 100 ms       几次数组扫描
────────────────────��─────────────
合计                     4–15 s
```

**Lloyd 松弛的优化**：暴力版是 O(P × S)（每点找最近站点）。用**网格空间哈希**把最近站点查询降到 O(1) 附近，整体可降到 O(P + S)，100 次迭代从 8 秒降到 1 秒以内。实现很简单：把地图分成 32×32 的桶，每桶预存其覆盖范围内的候选站点列表。

### E-4.3 运行期性能：三张休眠名单

原版的三张名单（`BrainWrangler` / `StateGraphWrangler` 各一套）是同一个模式：

```
instances[inst] = 当前在哪张名单（指针，不是拷贝）
updaters         = 每帧/每刻都要访问
tickwaiters[t]   = 睡到第 t 刻再唤醒（按目标 tick 分桶，不是按实体）
hibernaters      = 完全不访问，只有事件/唤醒能叫醒
```

**`tickwaiters` 按 tick 分桶**这个设计很值得抄：它避免了"每次唤醒都要扫一遍实体列表找谁该醒了"的 O(N) 开销，唤醒操作退化成 O(该桶大小)。

**调度器的核心循环**（`brain.lua:106`，已核实）：

```lua
function BrainWrangler:Update(current_tick)
    -- 1) 唤醒到点的脑
    local waiters = self.tickwaiters[current_tick]
    if waiters then
        for k in waiters: do
            self.updaters[k] = true
            self.instances[k] = self.updaters
        end
        self.tickwaiters[current_tick] = nil       -- ← 立刻清空，避免重复唤醒
    end

    -- 2) 快照 updaters（因为遍历期间脑会互相增删）
    local count = 0
    for k in self.updaters:
        if k.inst.entity:IsValid() and not k.inst:IsAsleep():
            count = count + 1
            self._safe_updaters[count] = k
    -- 3) 逐个更新并决定下一站
    for i = 1, count:
        k = self._safe_updaters[i]
        self._safe_updaters[i] = nil
        k:OnUpdate()
        local sleep_amount = k:GetSleepTime()
        if sleep_amount then
            if sleep_amount > GetTickTime(): self:Sleep(k, sleep_amount)
            else: pass                                  # 本刻还要更新，留着
        else:
            self:Hibernate(k)
end
```

**第 2 步的快照是必须的**，源码注释明确写了原因（`NOTES(JBK)`）：*"We need to make a copy of the keys to safely iterate over the table because brains will remove and add onto the self.updaters table during iteration."* —— 遍历期间，一个脑的攻击行为可能杀死另一个脑，导致它的 `_Stop_Internal()` 修改 `updaters`。

`StateGraphWrangler:Update`（`stategraph.lua:109`）用了更狠的手法：

```lua
local updaters = self.updaters
self.updaters = {}          -- ← 直接换表，而不是边遍历边删
```

以及 `TheSim:ProfilerPush(k.inst.prefab)` 的逐预制体性能打点——这说明官方自己也需要 profile 才能定位性能问题。

### E-4.4 睡眠生命周期：整个系统的性能基石

`entityscript.lua` 的四个关键函数（行号已核实）：

| 行号 | 函数 | 作用 |
|---|---|---|
| 1103 | `SetBrain(brainfn)` | 设置工厂函数；**注意它会先 `_Stop_Internal()` 掉旧的脑** |
| 1120 | `_DisableBrain_Internal()` | `brain:_Stop_Internal()` 后 `self.brain = nil`（**丢弃实例**） |
| 1135 | `_EnableBrain_Internal()` | `self.brain = self.brainfn()`（**重新调用工厂**） |
| 1148 | `SetStateGraph(name)` | `LoadStateGraph(name)` 加载/缓存 → `StateGraphInstance(sg, self)` → `SGManager:AddInstance(self.sg, self:IsAsleep())` |

**"销毁 + 工厂重建"而不是"停用 + 恢复"，是有意的**：

- 一个正在追玩家的蜘蛛离开模拟范围时，它的脑里保存着 `combat.target`、各种 `idx`、事件监听。恢复这些状态的正确性远难于重建。
- 重建的成本 = `brainfn()` + `OnStart()` 建树 + 一堆 `ListenForEvent`。对 191 个脑模板来说很便宜。
- `Brain:_Start_Internal` 里还有一个额外收益：`self.modpostinitfns` 会在重建时重新应用，模组对脑的修改不会因为睡眠而丢失。

**`SetBrain` 里的一个细节**：

```lua
self._braindisabled = brainfn and (self.sleepstatepending or self:IsInLimbo() or self:IsAsleep()) or nil
```

`sleepstatepending` 是为了处理构造期的竞态——`entityscript.lua:221` 有 `self.sleepstatepending = true -- haven't received initial sleep state from engine yet`，注释里 V2C 写得很清楚：*"sleepstatepending check to prevent brain starting at construction when `:IsAsleep()` always returns false"*。**在自己引擎里移植时要小心这个时序问题。**

**性能账**（推断）：一个 425×425 的世界里可能有 3000 个实体，但同时活跃的通常只有玩家附近的 100–200 个。睡眠机制把这个数字砍掉了 90% 以上。每个活跃脑的 tick 成本 ≈ 0.25–1 次节点访问 + 若干状态查询，微秒级。**结论：AI 的规模问题从来不是"节点太多"，而是"不该跑的还在跑"。**

### E-4.5 261 个状态图的组织：不失控的六条规则

从 `SGwilson.lua`（28,601 行）和 `commonstates.lua`（2,974 行）的组织方式里，可以提炼出六条规则：

**规则 1：状态图是数据，不是代码路径。** 一个 `State` 是一张表，`GoToState` 是字符串跳转。没有 `goto`，没有状态变量，没有 switch。**加一个新状态不影响任何其它状态。**

**规则 2：用生成器而不是复制粘贴。** `commonstates.lua` 提供 `AddIdle / AddRunStates / AddWalkStates / AddCombatStates / AddDeathState / AddSleepStates / AddFrozenStates / AddElectrocuteStates / AddSinkAndWashAshoreStates / AddVoidFallStates / AddCorpseStates / AddInitState / AddFossilizedStates / AddRowStates ...`。

**一个具体的例子**：`SGrabbit.lua` 320 行能覆盖 init/idle/hop/eat/stunned/death/sleep/frozen/electrocute/sink，是因为它只**手写了 6 个非通用状态**，其余全部来自 `CommonStates` + `CommonHandlers`。

**规则 3：状态标签是唯一的对外接口。** 26 个标签（`SGTagsToEntTags`）构成了状态图与外部世界之间的全部契约：

```lua
local SGTagsToEntTags = {
    ["attack"]=true, ["autopredict"]=true, ["busy"]=true, ["dirt"]=true,
    ["doing"]=true, ["fishing"]=true, ["flight"]=true, ["hiding"]=true,
    ["idle"]=true, ["invisible"]=true, ["lure"]=true, ["moving"]=true,
    ["nibble"]=true, ["noattack"]=true, ["nopredict"]=true,
    ["pausepredict"]=true, ["sleeping"]=true, ["working"]=true,
    ["boathopping"]=true, ["shouldautopausecontrollerinventory"]=true,
}
```

**别的系统只通过标签提问**：`inst:HasTag("busy")`（不能被打断）、`HasStateTag("attack")`（正在攻击）、`HasStateTag("canrotate")`（能不能转向）。**新加一个状态不需要改任何外部代码，只要挂对标签。**

**规则 4：动作路由集中在一张表。** `actionhandlers` 是"动词 → 状态"的唯一映射点：

```lua
local actionhandlers = {
    ActionHandler(ACTIONS.CHOP, function(inst) ... end),   -- 函数形式 = 带上下文
    ActionHandler(ACTIONS.EAT, "eat"),
    ...
}
```

`StartAction` 只有一行查找 + 一次跳转。**加一种新动词 = 加一行。**

**规则 5：打断是标签驱动的，不是代码驱动的。** 一个状态被打断时：`onexit` 跑 → `busy` 标签移除 → `ClearBufferedAction()` 清空待执行动作 → `SGManager:OnEnterNewState` 把新状态放回 updaters。**没有"中断处理函数"这种集中式的东西。**

**规则 6：帧精确的东西写进 timeline，逻辑写进 onenter/onexit。**

```
onenter   → 状态开始的瞬间（起冷却、播动画、设目标）
timeline  → 过程中的具体帧（音效、伤害帧、位移帧、重复触发帧）
onupdate  → 需要连续判断的（升级到冲刺、判断距离）
ontimeout → 固定时长后（换状态）
onexit    → 离开的瞬间（清理、撤销未完成意图）
```

**判断标准**：`onenter` / `onexit` / `ontimeout` 是"点"，`timeline` 是"帧"，`onupdate` 是"每帧"。**能写成时间点的一律不要写成 `onupdate` 里的时间比较**——因为 `onupdate` 会让状态图无法休眠（`Update()` 返回 0 → 每帧都要跑）。

最后这一条是性能的关键：**一个有 `onupdate` 的状态，每帧都在跑，哪怕它只做一件微不足道的事。** 原版 `Update()` 的判断是：

```lua
if self.currentstate.onupdate then
    return 0.0                    # ← 每帧
elseif time_to_sleep then
    return time_to_sleep           # ← 睡到下一个 timeline 点
else
    return None                    # ← 冬眠
```

**一个 `idle` 状态如果写了空的 `onupdate = function(inst, dt) end`，性能立刻掉一个数量级。**

### E-4.6 规模化的实际风险点

**（1）`GetTreeSleepTime` 是递归的。** 每个活跃脑每刻都要算一次树上所有 RUNNING 分支的最小睡眠时间。`pigbrain` 那种 8 层嵌套 + 每层 5 个子节点的结构，单次 `GetTreeSleepTime` 要访问 30–40 个节点。300 个活跃猪 × 30 节点 × 30 Hz = 27 万次节点访问/秒。

**缓解（推断）**：给 `Node` 加一个 `sleep_time_dirty` 标记，只在 `status` 或 `next_wake_time` 变化时重算，否则返回缓存值。

**（2）`PriorityNode` 的 `pairs()` 遍历顺序不确定。** `LinkNodesByKeys` 里 `for taskid, node in pairs(unusedTasks)` 的遍历顺序依赖 Lua 的哈希布局，导致"谁先满足锁就选谁"这一行为**在同样的种子下也可能不同**（如果 Lua 的 `pairs` 顺序依赖插入历史和哈希种子）。这不是 bug（世界生成本来就靠 `collectgarbage` 重置），但**做确定性回放时要小心**。

**（3）`EventNode` 的 `DoToParents` 也是递归。** 每个事件触发都要向上走到根，把所有祖先 `PriorityNode` 的计时清空。深层嵌套时事件触发会变贵。

**（4）`SGManager:Update` 里的 `ProfilerPush` 在正式构建里应该关闭。** `TheSim:ProfilerPush("updaters")` + 每预制体一次 push/pop，在几百个实体下是纯粹的浪费。

## 【深度扩写 E-5】移植陷阱：实际开发会踩的坑

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

以下每一条都对应源码里可验证的事实（注释、代码路径、或明显的逻辑漏洞），不是泛泛的经验之谈。

### E-5.1 世界生成侧

**坑 1：`terrain_filter` 是"黑名单"语义，新增地块默认安全。**
`map/terrain.lua` 的 `TERRAIN_FILTER` 是逐预制体的**排除列表**，不是规则系统。这意味着：
- 你新加一种地块（比如"雪原"），**所有预制体默认可以在上面长**，除非你显式加进每个相关预制体的黑名单。
- 原版为此打了一个补丁（`terrain.lua:150-154`）把 `ARCHIVE` / `VAULT` / `VAULT_CLEAN` 加进**所有**条目。
- **移植建议**：改成"白名单 + 默认拒绝"，或者引入地块属性位（可种植 / 可建造 / 可通行 / 水），让规则由地块自己声明而不是由预制体列举。

**坑 2：`lockandkey.lua` 里的同名覆盖。**
`LOCKS.TREES` 在 `LOCKS_KEYS` 里**定义了两次**：

```lua
[LOCKS.TREES] = { KEYS.AXE, KEYS.FIRE },     -- 第 219 行
...
[LOCKS.TREES] = { KEYS.AXE, KEYS.PIGS },     -- 第 254 行 ← 后者生效
```

第一组定义被静默覆盖。源码自己在 486 行留了注释承认这类校验有盲区：*"NOTE: This wil **NOT** catch it if the typo is in the last key in the list. ... But it's better than nothing..."* 而且 498–510 行有一个 `SKIP_THESE_MISSING_KEYS_AND_LOCKS` 白名单，承认有若干 key/lock 引用了但从未声明（`SILK`、`ROCKS`、`TALLBIRDS`、`SWAMP` 等），只在 `BRANCH == "dev"` 时才会在元表 `__index` 里报错。

**移植建议**：用显式的声明式配置 + 启动期严格校验（缺一个就崩溃），而不是容错跳过。原版的容错策略是历史包袱——注释明说是"怕改变世界生成结果、影响玩家体验"。

**坑 3：静默失败比崩溃更难查。**
原版至少有三处静默失败：
- `Node:PopulateVoronoi` 的 `if #points_x < pos_needed then return end` —— 整个节点的内容物丢失
- `object_layout.ReserveAndPlaceLayout` 的 `if rcx == nil then return` —— 场景件丢失
- `InsertAdditionalSetPieces` 的 `if choice == nil then print("Warning!..."); break end` —— 场景件没地方放

它们只打 `print`，不计入校验。**结果是一张"少了几个洞穴"的世界，玩家不会报错，但会遇到"我要找 XX 资源但地图上没有"的困惑。**

**移植建议**：静默失败必须留下可查询的痕迹（统计表、调试面板），并在验收阶段作为警告输出。

**坑 4：`FAKE_GROUND` 这类"临时连通"必须有清理路径。**
源码注释自己都在叹气：*"Sigh, so the `ForceDisconnected` tag does not actually keep something in the void disconnected from the mainland (e.g. Atrium)"*。这个临时地块靠 `DetectDisconnect` 事后清理。**如果你的清理逻辑漏了，玩家就能走进设计上是虚空的地方。**

**坑 5：`VoronoiPass` 的迭代次数与"区域面积均衡"直接挂钩。**
100 次迭代（Lloyd）vs 1 次（纯 Voronoi）产生的形状差异极大。如果你的生物群系大小不均，`Node:PopulateVoronoi` 里的 `#points_x` 会剧烈波动，`distributepercent` 的实际密度就会跟着波动——某些群系会明显稀疏或拥挤。

**坑 6：`mult < 1` 的减量是随机砍，不是重新分布。**
`forest_map.lua:904-919` 先 `shuffleArray` 再 `table.remove`。后果是：被砍掉的和保留的空间上是均匀的，但**同类实体之间的相对关系被破坏了**（比如原本三只一组的洞穴虫群，现在可能只剩散兵）。如果你有"资源必须成组"的设计，这个减量会破坏它。

**坑 7：任务 ID 与房间 ID 是字符串拼接的，容易撞。**
`new_room.id = task.id..":BG_"..bg_idx..":"..new_room.name`（`storygen.lua:1015`）、`task.id..":"..roomID..":"..next_room.name`（第 1307 行）。`roomID` 是任务内自增的，`bg_idx` 是**全局**自增的（第 1052 行 `bg_idx = bg_idx + 1`，注意它在 `AddBGNodes` 的最外层循环里）。**如果你在同一个 task 里生成两个同名的房间**（`room_choices` 里写了两次同一个名字），`roomID` 不同所以不撞；但如果你在 `AddBGNodes` 和 `AddCoveNodes` 之间复用了 `bg_idx`（`AddCoveNodes` 里 `bg_idx = 0` 在外层循环末尾重置，`AddBGNodes` 里不重置），就可能撞。原版靠前缀区分（`:BG_` vs `:COVE_`）规避了这个问题。

**坑 8：坐标精度与地块对齐。**
所有实体坐标的转换都是：

```lua
local x = (tile_x - width/2.0) * TILE_SCALE      -- TILE_SCALE = 4
x = math.floor(x * 100) / 100.0                    # 保留 2 位小数
```

迷宫部分还有一条注释说明了坐标系统的历史包袱：*"gjans: note the +1.5 instead of +0.5... RunMaze points are in a strange position."* —— 迷宫返回的格点中心定义与普通格点差半格。**移植时如果自己写路径系统，务必统一"格点索引 → 世界坐标"的转换，不要让两套系统各写各的。**

**坑 9：`FAKE_GROUND` 和 `IMPASSABLE` 的判定不一致。**
`forest_map.lua:896` 有一条重要的警告注释：

```lua
local tiletype = WorldSim:GetVisualTileAtPosition(x, y)
-- Warning: This does not quite work as expected. It thinks the ground type id is in
-- rendering order, which it totally is not!
if TileGroupManager:IsImpassableTile(tiletype) then
    -- 删掉这个实体
```

**渲染顺序 ≠ 逻辑顺序**。原版用一个"按渲染顺序编号的地块 id"去查按逻辑顺序分组的 `TileGroups`，这是靠巧合能工作。**移植时一定要用逻辑地块类型做判定，不要混用渲染层索引。**

### E-5.2 AI 侧

**坑 10：`WaitNode` 里的一个笔误。**
`behaviourtree.lua:295`：

```lua
else
    self:Sleep(current_time - self.wake_time)      -- ← 负值！
end
```

`Sleep(t)` 做的是 `nextupdatetime = GetTime() + t`，传负值等于"立刻过期"，所以效果是**每帧都唤醒**。这是 bug 还是刻意？注释说 `WaitNode` 的语义是"RUNNING for t seconds (sleeps exactly)"，但这个写法让它每帧醒来。**它不产生正确性问题（因为 status 仍会等到 `current_time >= wake_time`），但完全失去了节能效果。** 自己实现时直接写对的版本。

**坑 11：`PriorityNode` 的 `EventNode` 抢占会重置已经在跑的子节点。**
`behaviourtree.lua:609-611`：

```lua
if should_test_anyway and self.idx ~= idx then
    self.children[self.idx]:Reset()       -- ← 把当前赢家重置了
end
```

如果一个高优先级的 `EventNode` 触发并抢占了位置，而它的子节点立刻返回 FAILED，那么**原本在跑的那个子节点已经被 Reset 了**，它的内部状态丢失。结果是行为被打断而不是抢占。**在移植时如果发现"AI 莫名其妙地停下了"，先查这里。**

**坑 12：`ChaseAndAttack` 的 `onmissother` 也算"命中"。**

```lua
self.inst:ListenForEvent("onattackother", self.onattackfn)
self.inst:ListenForEvent("onmissother", self.onattackfn)     -- ← 落空也算

function ChaseAndAttack:OnAttackOther()
    self.numattacks = self.numattacks + 1
    self.startruntime = nil       -- reset max chase time timer
end
```

**落空也算一次攻击，并重置追击计时器。** 这意味着一个打不中的目标可以让狼永远追下去（只要它一直在挥爪）。这不是 bug —— 它保证了"追不上就不放弃"的玩法手感 —— 但移植时如果觉得怪物太黏人，这里是可调参数。

**坑 13：`EventNode` 监听的是实体事件，不是全局事件。**
`EventNode.__init__` 里直接 `self.inst:ListenForEvent(self.event, self.eventfn)`。事件必须 `PushEvent` 到**这个实体**上。想让所有生物都响应某个世界级事件（比如"月食开始"），得用 `WhileNode(fn→TheWorld.state.xxx)` 而不是 `EventNode`。

**坑 14：`Brain:PushEvent` 和 `inst.sg:PushEvent` 是两套完全不同的机制。**

| | `Brain:PushEvent(name, data)` | `inst.sg:PushEvent(name, data)` |
|---|---|---|
| 实现 | `self.events[event](data)` —— 查表直接调 | 塞进 `bufferedevents` 队列 |
| 时机 | **同步立即** | 更新循环之后统一 `HandleEvents` |
| 注册 | `brain:AddEventHandler(name, fn)` | `EventHandler` 对象进图或状态 |
| 来源标记 | 无 | 带上 `data.state = currentstate.name` |

**两者的时序差异会导致难以复现的 bug**：脑的事件立即改变状态，状态图的事件排队到本刻末尾。一个动作在"排队期间"被另一个事件取消，就是很难查的问题。

**坑 15：`state_mem` 在 `GoToState` 时被清空。**
`self.statemem = {}`（`stategraph.lua:550`）。如果你的 timeline 事件在 20 帧后触发，而期间有**任何**其他 `GoToState` 调用（包括被打断、被事件驱动的跳转），`statemem` 里的数据就没了。**原版对攻击目标的处理是把它塞进 `statemem` 并在同一个状态的 timeline 里用**——只在"从 attack 跳到别的状态"时才丢，安全。但如果你的设计是"attack 状态中途可能切到 chase，chase 还要用 target"，就必须用 `sg.mem`（跨状态保留）而不是 `sg.statemem`。

**坑 16：`ClearBufferedAction` 只在特定状态下被调用。**
`hit` 状态做了这件事，所以"受击打断一切"成立。但**其它可打断状态没做**。如果你新增了一个"可以被打断的挖掘状态"，忘记加 `inst:ClearBufferedAction()`，玩家受击后挖掘动画会继续跑完并产出资源——这是玩家最容易发现的 bug 类型。

**坑 17：客户端预测是可选的双刃剑。**
`stategraph.lua` 里的 `server_states` / `forward_server_states` / `no_predict_fastforward` / `RemotePausePrediction` 整套机制，在 `SGwilson_client.lua` 里实现。**单机游戏应该完全关掉它**（`TheWorld.ismastersim` 为 true 时走的是另一条分支）。移植时如果沿用了这些字段但没实现对账逻辑，会出现"客户端和服务端状态永久分叉"。

**坑 18：`ActionHandler` 的 `condition` 字段被静默忽略。**
`StartAction`（`stategraph.lua:430`）里：

```lua
if handler then
    if not handler.condition or handler.condition(self.inst) then
        ...
    end
    # ← 如果 condition 为假，这里什么都不做，直接返回 nil
end
```

返回 nil 的含义是"这个动作没被接受"，但调用方（locomotor）已经走到了目标位置。**结果：AI 会走到某个东西面前，然后什么都不做地站一会儿。** 这是 AI 卡住的常见原因。

### E-5.3 综合坑

**坑 19：重试机制的代价被低估了。**
`maxtries = 5`，每次失败都 `collectgarbage("collect")` + `WorldSim:ResetAll()`。如果生成要 10 秒，最坏情况是 **50 秒**才给玩家一个错误。**而且错误信息极差**——玩家只看到"生成失败"，开发者要靠 `print` 里的 `PANIC: missing required prefab [X]! Expected N, got M` 反查。

**移植建议**：把失败原因结构化返回（`return nil, {reason="missing_required_prefab", prefab="X", expected=3, got=0}`），前端据此给出可操作的提示（"你的世界设置禁用了必需资源 XX，请调整设置"）。

**坑 20：世界生成确定性的三大破坏者。**

1. **`pairs()` 的遍历顺序。** `LinkNodesByKeys` 里 `for taskid, node in pairs(unusedTasks)` 的顺序依赖 Lua 表的哈希布局。同一份数据、同一个种子，不同的 Lua 版本可能给出不同的结果。
2. **`WorldSim:ResetAll()` 不完全重置 RNG。** 每次重试 `math.random` 的状态已经前进了，所以"第 3 次尝试"和"第 1 次尝试"在同样的逻辑下会得到不同的随机数。
3. **`GetRandomItem` 对表长度敏感。** `for k,v in pairs(t)` 数个数——如果表在遍历中被修改，计数会错。

**移植建议**：用自己的 PRNG（不是 `math.random`），把种子显式传入每一个随机调用点；遍历用有序数组而不是哈希表。

**坑 21：模组钩子的执行时机。**
`Story:GetRoom` 每次调用都跑一遍 `ModManager:GetPostInitFns("RoomPreInit", roomname)`（`storygen.lua:99`）。`StateGraph` 构造函数跑 `GetPostInitData("StategraphState", ...)` / `("StategraphActionHandler", ...)` / `("StategraphEvent", ...)` + `GetPostInitFns("StategraphPostInit", ...)`。**这意味着一个 131 任务 × 8 房间的世界会跑约 1000 次模组钩子查询。** 模组多的时候这本身就是可观开销。

**坑 22：`MapTags` 是一个硬编码的字符串分发表。**
`map/maptags.lua` 把 `"Maze"` / `"Labyrinth"` / `"ExitPiece"` / `"Chester_Eyebone"` 等标签映射到 `STATIC` / `ITEM` / `TAG` / `GLOBALTAG` 四类行为。`Story:GetExtrasForRoom` 会遍历房间的每个 tag 调 `self.map_tags.Tag[tag](...)`。**新增一个标签必须同步改 `maptags.lua`，否则 `self.map_tags.Tag[tag]` 是 nil 直接崩溃。**

|---|---|---|
| `FRAMES` | `1/30` 秒 | 动画与逻辑的基准帧率；与固定 tick 率解耦 |
| `GetTickTime()` | 固定 tick 步长 | 你的引擎的固定步长 |
| `TILE_SCALE` | `4`（1 格 = 4 世界单位） | 保留这个比例，AI 的所有距离参数都以它为基准 |
| `SEG_TIME` | `30` 秒 | 一个"段" |
| `NUM_SEGS` | `16` | 一天 = 8 分钟 |
| 坐标转换 | `(tile - size/2) * TILE_SCALE` | **统一一个函数**，见坑 8 |
| 实体坐标精度 | 2 位小数（`floor(x*100)/100`） | 存档与网络同步需要 |

### P-5 建议的模块边界

```
┌─ WorldGen 模块（离线）──────────────────────────────┐
│  LevelConfig      ← 设计师编辑的关卡数据            │
│  TaskSet / Task   ← 生物群系 + 锁钥匙              │
│  Room             ← 地块 + 散布规则                 │
│  GraphBuilder     ← 锁钥匙图（纯图，无空间）        │
│  VoronoiBaker     ← 点云 → 胞元 → 地块（纯几何）    │
│  ConnectivityFix  ← 洪水填充 + 通道开凿             │
│  Scatter          ← 逐胞元的加权散布                │
│  LayoutPlacer     ← 静态布局落位                    │
│  Validator        ← 5 道硬校验 → 结构化错误         │
│  Serializer       ← 二进制编码                      │
└──────────────────────────────────────────────────────┘
                         │ savedata
                         ▼
┌─ Runtime 模块 ──────────────────────────────────────┐
│  MapLoader        ← 解码 + 地块 id 重映射            │
│  Spawner          ← 实体清单 → 实例                  │
│  WorldEntity      ← 时钟/季节/天气/生成器组件         │
│  BrainSystem      ← 行为树 + 调度器 + 睡眠生命周期    │
│  StateGraphSystem ← 状态图 + 调度器                  │
│  Locomotor        ← 寻路 + 移动 + 动作派发            │
│  ActionSystem     ← 动作定义 + 效果                  │
└──────────────────────────────────────────────────────┘
```

**关键边界原则**：WorldGen 侧**不引用**任何 Runtime 侧的类型；两侧只通过 `savedata` 这个数据契约通信。原版做到了这一点（世界生成 VM 里没有 `TheWorld`），这是它能做无头生成和快速重试的前提。

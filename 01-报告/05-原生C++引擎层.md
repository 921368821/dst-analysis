## 概述 / TL;DR

- **引擎形态**：手写 C++ 引擎（MSVC 2008 / VC9，x64），采用**基于组件的实体系统**，而几乎全部游戏逻辑由 **Lua 5.1.4** 驱动。原生 C++ 负责模拟（simulation）、渲染、物理、音频、网络与文件系统；Lua 负责几乎全部玩法。原生单例（`TheSim`、`TheNet`、`TheInput` …）在 `scripts/main.lua` 运行之前被注入为 Lua 全局变量。
- **整个游戏逻辑都是 Lua。** `main.lua` 引导约 100 个模块、注册预制体、装好逐帧的 `Update(dt)`。C++ 每个 tick 回调 Lua；Lua 通过约 **367 个恢复出的原生绑定**（方法名字符串 → C 函数指针表）向下调用 C++。
- **渲染**：通过 **ANGLE** 的 OpenGL ES 2.0（`libEGL.dll` + `libGLESv2.dll`，转译到 Direct3D）。**没有 SDL** —— 窗口是裸 Win32（USER32）。此外还有场景图渲染器、从 XML 加载的纹理图集、位图字体、可选的**线程化渲染器**、纹理流式加载，以及一层 ImGui 调试/控制台叠加层。
- **网络是 RakNet**（静态链接），不是 enet：`RakNet::UNASSIGNED_RAKNET_GUID`、`ReplicaManager3`、`RakPeerSocket`，UDP + `GameSessionToken` 鉴权，Steam NAT 打洞（`cSteamPunchthrough`）、LAN 搜索，以及基于快照的**回滚**（`IncrementSnapshot`/`TruncateSnapshots`）。HTTP 走 **libcurl 7.42.0** + **OpenSSL**（均为静态链接）。
- **音频是 FMOD**（动态链接 `fmodex64.dll` 低层 DSP + `fmod_event64.dll` 数据驱动 Event System），音效包通过 Klei 自家文件系统读取（`fmod_fs_read`）。
- **固定 30 Hz 模拟。** `TheSim:GetTickTime()` 字面返回常量 `0.03333333`（1/30）。`Simulation::Update(dt)` 推进模拟、调用 Lua `Update(dt)`、递增步数计数器；`Sim Time = step * (1/30)`。
- **资源管线**：全部打包进 `databundles/*.zip`（`scripts.zip`、`images.zip`、`shaders.zip`、`fonts.zip`、`anim_dynamic.zip`、`klump.zip`、`bigportraits.zip`），挂载进虚拟文件系统（`zipfilesystem.cpp`，minizip）。存档走 `SetPersistentString` → zlib + Klei 编码步骤，带 cluster/shard 槽位与禁用路径沙箱检查。
- **确定性与基础设施**：导出 **PCG32** PRNG（`pcg32_rand`/`pcg32_srand`）用于带种子、可复现的随机；专用**世界生成线程**（`WorldSim::SimThread::Main()` 运行 `scripts/worldgen_main.lua`）；崩溃处理用 `dbghelp!MiniDumpWriteDump`；逐更新的**卡死看门狗**，超时调用 `exit(6)`。
- **专用服务器是同一份代码库**，`CONSOLE` 子系统，**渲染器与输入 DLL 被剥离**（`libEGL`、`libGLESv2`、`XINPUT1_3`、`DINPUT8`、`GDI32`、`SETUPAPI` 全部不存在）—— 模拟 + 网络 + FMOD + Steam 保留。
- **来源**：构建于 Jenkins（`c:\jenkins\workspace\DST_BuildGame_Windows_x64\...`），构建产物上传至 `https://s3.amazonaws.com/dstbuilds/`；第三方依赖位于 `foreign/build/` 下。

## 方法论说明

REA 的 `inspect-binary-layout` 只支持 ELF，因此 PE 布局来自 `inspect-pe-resources`（REA）加 `pefile`。深度分析通过 Ghidra 的一个**常驻** REA `GhidraClient` 桥接完成（打开一次，然后通过经过认证的 loopback TCP socket 查询），因为一次性 CLI 每次调用都会重新导入并重新分析这个 7.4 MB 映像（每次约 3 分钟）。二进制**被剥离了函数名**（17,725 个过程里有 16,129 个是 `FUN_xxxxx`），但保留了丰富的**字符串字面量、内嵌源码路径、断言消息与 Lua 注册表**——正是这些让架构得以复原。没有任何编造：凡是无法证明的名字，都标注为 *inferred*（推断）或 *unknown*（未知）。

## 客户端 vs 专用服务器差异

专用服务器（`dontstarve_dedicated_server_nullrenderer_x64.exe`，7,109,632 字节，`CONSOLE` 子系统）是同一个引擎，但**表示层与输入层被移除**。它的 `.text` 小了约 418 KB（4,899,822 对 5,318,494）。

**客户端有、服务器没有的 DLL（全是渲染/输入）：**

| 被移除的 DLL | 子系统 |
|---|---|
| `libEGL.dll`、`libGLESv2.dll` | ANGLE / OpenGL ES 渲染器 |
| `XINPUT1_3.dll`、`DINPUT8.dll`、`SETUPAPI.dll` | 手柄 / 摇杆 / 设备枚举 |
| `GDI32.dll` | 2D GDI（窗口 blit） |

**服务器独有 DLL**：无。服务器**保留** `fmodex64.dll` + `fmod_event64.dll`（FMOD 仍然链接着——运行时音频实际上是个空后端，但依赖留着）、`steam_api64.dll`、Winsock、`WINMM`、`dbghelp` 和完整的 VC9 运行时。服务器由一个独立的 Jenkins 任务构建（`DST_BuildServer_Windows_x64`）。两者导出同样的三个符号（`pcg32_*`）。

> 本机复核（`bin64/` 目录清单）：`dontstarve_dedicated_server_nullrenderer_x64.exe` 实测 7,109,632 字节，与原文一致。

**要点**：引擎干净地把*模拟 + 网络 + 音频 + 平台*（共享部分）与*渲染 + 输入*（仅客户端）分开。"nullrenderer" 这个名字是字面意思：服务器把 GL/ANGLE 渲染器和输入设备栈编译掉了，以无头控制台进程运行。**这是这里最值得复用的架构思想——让 sim/render/input 的切分成为一次编译/链接期的减法，而不是另一个程序。**

## 帧循环分析

每帧的核心是 `Simulation::Update(dt)` = `FUN_1401058c0`（出自 `..\source\simlib\simulation.cpp`）。它以一个 float 增量时间和一个 bool 被调用，由 `RenderOneFrame` 驱动。关键结构（节选，已裁剪）：

```c
bool FUN_1401058c0(longlong *sim, float dt, undefined1 flag) {
```

## Lua 绑定面

**绑定如何工作（由反编译证明）。** 每个原生子系统都由一个 `*LuaProxy` C++ 类暴露。一个 proxy 在堆上分配，被包成一个 Lua **full userdata**，挂上元表，然后安装为一个全局变量。`SimLuaProxy` 的注册（`FUN_140133970`）：

```c

  PreRegister(L, 0);
  void *mem = operator_new(0x80);                    // SimLuaProxy 是 128 字节
  void *proxy = (mem==0) ? 0 : SimLuaProxy_ctor(mem, arg);
  BindProxy(L, proxy);                                // FUN_14012a3a0
  lua_setfield(L, LUA_GLOBALSINDEX /*0xffffd8ee*/, "TheSim");   // TheSim = proxy
  PostRegister(L);
}
```

方法是从 **`.data` 段里的 `luaL_Reg` 风格表** 注册的，每项 **24 字节** `{ const char* name; lua_CFunction fn; int64 userdata; }`。读取例如 `0x1406249e0` 处的原始字节，恰好解出：

```
08 f8 52 40 01 00 00 00 -> 0x14052f808  "GetTickTime"   (name, .rdata)
70 6e 12 40 01 00 00 00 -> 0x140126e70  FUN_140126e70    (C function, .text)
00 00 00 00 00 00 00 00 -> 0                             (userdata/aux)
```

跨 `.data` 解码这些表，恢复了 **367 个名字→函数的绑定**。每一个 Lua C 函数都是同样的形状：一次有效性守卫、通过 Lua C API 做的参数封送、调用 `*(self+8)` 处的 C++ 对象，然后 `return <nresults>`。组件方法全部以同一个存活性检查 `FUN_140066690()`（就是那个 "Stale Component Reference: GUID %d" 守卫）开头，而字符串键由 `FUN_14042f020` 散列成 `uint32`（Klei 的 `StringHash`，用于标签、动画名、音效实例名）。

## 值得复用的关键模式

1. **玩法写脚本，机械留 C++。** 把模拟、渲染、物理、音频、网络、文件系统放进 C++；把**其余一切**放进 Lua。在第一段脚本运行前注入少量原生单例作为全局（`TheSim`、`TheNet`、`TheInput`），然后让 `main.lua` 引导游戏。这样既拿到可模组性与快速迭代，又不牺牲性能关键的控制力。
2. **基于组件的实体，原生内核 + Lua 包装。** 一个原生 `Entity`（以 GUID 标识）持有 C++ 组件（`Transform`、`AnimState`、`Physics`、`Light`、`SoundEmitter`、`Network`……）；一个 Lua `EntityScript` 包装它并持有玩法组件。`entity:AddXxx()` 返回一个原生组件 userdata。每个组件方法开头都有对陈旧引用的存活性守卫。
3. **用注册表绑定，不要临时黏合。** 用 `{name, fnptr, userdata}` 数组（`luaL_Reg` 风格）让整个接口面成为**数据**。它可内省、廉价，而且——正如这次分析所展示的——**可被逆向复原**。标签/动画/音效标识优先用散列字符串键（`StringHash`），让运行时查找保持 O(1) 且对网络友好。
4. **定步长模拟 + 挂钟驱动渲染。** 硬性 30 Hz 刻（`GetTickTime == 1/30`）、`simStep` 计数器，以及与渲染解耦的 `Update(dt)`，让多人游戏具备"近似确定性"且可回放。再加一个**卡死看门狗**（超时 `exit(6)`）—— 对无人值守的专用服务器极有价值。
5. **把服务器设计成一次减法。** 模拟/网络/音频/平台走同一条代码路径；把渲染器 + 输入在编译/链接期剔掉，得到一个无头的 `nullrenderer` 控制台构建。这比维护一份独立的服务端代码库便宜得多。
6. **把资源打进挂载的 zip VFS。** `databundles/*.zip` + 一个虚拟文件系统（带内存与本地后端）带来快速、可打补丁、抗篡改的资源加载，以及一个可以挂接流式加载与清单的单一入口。
7. **边界处一切异步。** 文件读写、HTTP（curl）、世界生成（独立线程 + 独立 Lua state）、纹理加载，全都是异步且回调寄存在 Lua registry（`luaL_ref`）里。**绝不要在模拟线程上阻塞等 I/O 或世界生成。**
8. **复用久经考验的库；核心部分静态链接。** RakNet（复制 + NAT 打洞 + 可靠传输）、libcurl+OpenSSL（HTTPS）、zlib（压缩）、Lua、ImGui（调试 UI）、PCG（RNG）。只有必须匹配操作系统/硬件的厂商 SDK 才动态链接（FMOD、Steam、ANGLE）。
9. **在可移植后端之上铺一层薄渲染抽象。** `renderlib`（渲染器、纹理/缓冲管理器、场景图）架在 `OpenGL/`（ANGLE→D3D）后端之上，让同一份代码在任何平台上跑 GL ES；线程化渲染器开关与纹理流式加载让同一构建能从上网本扩展到高性能机。
10. **沙箱化并加固脚本边界。** `SetPersistentString` 上的禁用路径检查、会话令牌、签名校验（`ValidateWithSignature`）与 Steam 鉴权表明：一旦玩法是用户可编写/可模组的，原生层必须强制规定脚本能碰什么。

## 未知项 / 局限

- **函数名被剥离。** 17,725 个过程里有 16,129 个是 `FUN_xxxxx`。这里所有名字都是间接恢复的：内嵌的 `..\source\*.cpp` 路径、`Class::Method` 形式的日志/断言字符串、Lua 注册表，以及 726 个 DLL 导入。像"`FUN_1401058c0` = `Simulation::Update`"这样的归属是**强推断**（依据是它内部来自 `simulation.cpp` 的剖析作用域字符串），而非符号证明。
- **外层主循环未能隔离。** WinMain 是一整块约 60 KB 的反编译产物；反复调用 `Simulation::Update` + `RenderOneFrame` 的帧/消息泵要么被内联、要么间接抵达（`FUN_1403d9fb0` 被反编译成一个空壳 `return 0`）。帧更新的**内容**是已证实的；确切的循环骨架不是。
- **Lua C API 辅助函数身份是推断的**，来自跨多个绑定的一致使用模式（例如 `FUN_1404e9540`=`lua_pushnumber`），而非符号。Lua 5.1 的伪索引常量（`0xffffd8ee`、`0xffffd8f0`）与行为有力地佐证了它们。
- **注册项里的 `userdata` 字段**（第三个 qword，在抽样到的所有 TheSim 条目里都是 `0`）含义未明；可能是某些 proxy 用的闭包/辅助槽位。
- **RakNet vs Steam 传输的分工未完全理清**：RakNet（UDP）与 Steam 网络同时存在；哪种托管模式（LAN / 在线 / Steam）下由谁承载玩法包，未做端到端追踪。
- **FMOD 事件包的确切格式与 `.tex`/`.anim`/Spriter 容器布局**在此未解码（那属于资源管线报告的领域）；这里只恢复了播放 API 面。
- **没有做动态分析。** 这是 100% 静态的（Ghidra headless，只读）。只在运行时才出现的行为（实际线程调度、真实网络包字节、GPU 调用）是从代码结构推断的，不是观测到的。
- **服务器二进制未单独反编译。** 客户端/服务器差异来自 PE 导入表/节区；服务器的内部代码差异（除剥离的渲染器/输入之外）没有逐函数分析。

## 【深度扩写 1】C++ 引擎层的职责边界：Sim 层到底负责什么、不负责什么

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原文说清了 Sim 层"拥有"哪些系统，但没有说清它**不**拥有什么。而恰恰是这条边界决定了你能不能用现成引擎（Unity/Godot/Unreal）拼出来。

### 1.1 用证据划定边界

判断一条能力属于 Sim 层还是 Lua 层，最可靠的判据是：**它是否影响其他客户端看到的结果**。如果一个决策必须在所有客户端一致，就必须下沉；如果它只影响本地表现，就可以留在 Lua。

按这个判据分类（括号内为证据来源）：

| 归 Sim 层（原生） | 理由 | 证据 |
|---|---|---|
| **实体身份与生命周期** | GUID 必须全局一致 | `CreateEntity` 压入 `e->guid`（`0x14012a660`） |
| **变换与物理** | 位置必须一致，否则穿模 | `Transform::SetPosition`（`0x140087ad0`）、`Physics::SetCapsule/SetMotorVel` |
| **网络序列化与复制** | 带宽与顺序 | `ReplicaManager3`、`SaveDataBuffer.cpp`/`reader.h` |
| **RPC 收发与分帧** | 包顺序 | `SendRPCToServer`（`0x140287280`）、`HandleRPCQueue`（`networkclientrpc.lua:1724`） |
| **确定性刻推进** | 模拟必须定步长 | `GetTickTime` 返回 `0.03333333507180214` |
| **世界生成** | 世界是共享状态 | `WorldSim::SimThread::Main()`（`0x140123540`） |
| **存档的字节级写入** | 沙箱与云同步 | `SetPersistentString` 的禁用路径检查（`0x14012f0c0`） |

| 归 Lua 层（脚本） | 理由 | 证据 |
|---|---|---|
| **预制体的工厂函数** | 纯数据构造 | `prefabs.lua:6-19` 的 `Prefab` 类只存 `name/fn/assets/deps` |
| **组件的 `OnUpdate` 逻辑** | 只影响该实体的本地决策 | `update.lua:255-284` 遍历 821 个组件调 `OnUpdate` |
| **状态图与脑** | AI 决策必须在服务器跑，客户端只跑镜像 | `SGManager:Update(i)` / `BrainManager:Update(i)`（`update.lua:286-294`） |
| **物品栏、配方、合成** | 玩法规则 | `components/inventory.lua` 等 |
| **UI 与界面** | 纯表现 | `TheFrontEnd:Update(dt)`（`update.lua:95`） |
| **存档的语义内容** | Lua 生成字符串，原生只写字节 | `mainfunctions.lua:1068-1274` 的 `SaveGame` 全部在 Lua |

**最关键的一条边界**：**"Lua 决定内容，C++ 决定字节"**。看 `SaveGame` 的分工就明白了——遍历实体、调 `GetSaveRecord()`、拼 `DataDumper` 字符串、检测 NaN，全部在 Lua（`mainfunctions.lua:1087-1238`）；原生只提供一个异步的、带沙箱的"把这段字符串写到指定路径"原语（`SetPersistentString`）。你的自研引擎应该照抄这个切分，而不是把存档序列化也做成引擎功能。

### 1.2 第二条边界：本地表现 vs 共享状态

原文没有明确点出，但代码里非常清楚。`update.lua` 里有两个独立的更新入口：

- **`Update(dt)`（第 224 行）** —— 刻驱动，服务端权威。`assert(not TheNet:IsServerPaused(), "Update() called on paused server!")`（第 229 行）说明它只在模拟线程上跑。
- **`WallUpdate(dt)`（第 33 行）** —— 挂钟驱动，**每个客户端独立跑**。它做的工作：排空 RPC 队列、设置兴趣管理中心点、跑墙钟组件、`TheMixer:Update`、`TheCamera:Update`、`TheInput:OnUpdate`、`TheFrontEnd:Update`、光照效果。

**这就是术语表里 `WallUpdate` = "实时更新"的准确含义**：它与逻辑刻无关，是本地表现层的心跳。凡是"每个客户端必须自己做一遍"的事，都该走这条路，而不是塞进 `Update`。

### 1.3 自研引擎的模块划分建议

把上面的边界翻译成你项目里的模块：

```
┌─────────────────────────────────────────────────────────────┐
│  脚本层（你的 Lua / Lua-like / 数据驱动层）                  │
│  ├── prefab 工厂   ├── 组件 OnUpdate   ├── 状态图/脑       │
│  ├── 配方/合成     ├── UI 界面         └── 存档语义内容    │
└─────────────────────────────────────────────────────────────┘
              ↑ 仅通过下表的窄接口通信（无直调引擎对象）
┌─────────────────────────────────────────────────────────────┐
│  绑定层（Lua C API / FFI 生成的绑定，见【深度扩写 2】）      │
└─────────────────────────────────────────────────────────────┘
              ↓
┌─────────────────────────────────────────────────────────────┐
│  Sim 层（原生，服务端权威）                                   │
│  ├── Entity/GUID/EntityManager      ├── 定步长 Simulation │
│  ├── Transform / Physics            ├── WorldSim          │
│  ├── Network (RPC + 复制)           ├── SaveIO（字节级）  │
└─────────────────────────────────────────────────────────────┘
              ↓ （客户端构建时剔除）
┌─────────────────────────────────────────────────────────────┐
│  表现层（客户端独有）                                         │
│  Renderer / SceneGraph / Atlas / Font / Input / UI           │
└─────────────────────────────────────────────────────────────┘
```

**划分时的三个判据**：

1. **能不能在服务器构建里删掉？** 能删掉的东西必须只被表现层引用。原文的验证方式是导入表对比（`libEGL.dll`/`libGLESv2.dll`/`XINPUT1_3.dll`/`DINPUT8.dll`/`SETUPAPI.dll`/`GDI32.dll` 六个 DLL 在服务器里消失）。你可以用同样方法自查：服务器构建的导入表不应该出现任何图形/音频设备相关的 DLL。
2. **能不能单独跑一个进程？** 世界生成跑在独立线程 + 独立 Lua state 上（`WorldSim::SimThread::Main`），这说明它天然可提取。注意它返回的是一个**字符串**（`error = [[...]]return error` 或生成的世界串）——这条边界要划在"能序列化成字符串"的地方。
3. **改了会不会需要同步更新服务器？** 需要 → 下沉；不需要 → 上浮。净变量（netvar）的注释说得很直接（`netvars.lua:30-31`）：*"netvars must exist and be declared identically on server and clients for each entity, otherwise entity deserialization will fail"*。

### 1.4 三条不该照抄的设计

原文列了 10 条"值得复用的模式"，但也有几处**不该照抄**的地方（原文没提）：

1. **`TheSim` 是一个 194 方法的巨型单例**（本仓库实测唯一方法数）。这是历史包袱，不是好设计。它把时间、实体、渲染控制、音频混音、存档、模组、工作坊、Steam 平台服务全塞在一个对象里。原文反编译出的 `FUN_14011caf0(sim[0x14], dt)` 这种"某个子系统"的模糊身份，以及 `*(sim+0xe0)+0x180` 这种"从 sim 里挖出一个偏移再当对象用"的模式，都是这个巨型单例的症状。你的引擎应该拆成 `Sim`、`Clock`、`EntityRegistry`、`SaveIO`、`Platform` 五个独立绑定对象。
2. **`SetPersistentString` 用"禁用子串黑名单"做沙箱**（`0x14012f0c0` 里遍历 `forbiddenSubstrings` 做 `std::string::find`）。这是**弱策略**：黑名单永远补不全。更好的做法是白名单 + 路径规范化（消除 `..`、绝对路径、符号链接）。DST 实际还有一层更严格的 `unsafedata/` 目录约定（见资源报告），但那靠的是路径前缀而非黑名单。
3. **数值精度陷阱被事后修补**。`mainfunctions.lua:1201-1222` 搜 `nan`/`inf` 字符串、`entityscript.lua:274-296` 用 `isbadnumber` 逐个检查——说明**游戏曾经因为 NaN 污染存档而崩过**。根因是 Lua number 是 double、C++ float 是单精度，跨边界转换会产生 NaN，且 NaN 一旦进网络或存档就永久污染。你的引擎应该在跨语言边界上直接禁止 NaN/Inf（或者干脆全程用 float32 并在序列化前统一检查），而不是等它出问题。

## 【深度扩写 2】可运行实现：用 Unity/Godot/Unreal 时，Lua 逻辑层如何与引擎通信

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原文假设的是"自己写引擎"。如果你用现成引擎，这套 Lua↔C++ 绑定要重新实现。下面是三条可行路径。

### 2.1 方案对比

| | **方案 A：Lua 解释器嵌入**（最接近原版） | **方案 B：Unity + MoonSharp/UniLua** | **方案 C：引擎只跑数据** |
|---|---|---|---|
| 代表 | XTEN + 自己的 C++ 引擎 | MoonSharp（纯 C#）、UniLua（LuaJIT + C API） | 自定义 VM / 脚本引擎 |
| 调用开销 | 最低（栈式 API，无装箱） | 中（Lua→C# 有装箱；MoonSharp 更高） | 取决于实现 |
| 热重载 | 直接替换 `.lua` | 同左 | 需要自己设计 |
| 服务端复用 | 天然复用（同一份 Lua） | 需要把 Unity 的模拟部分剥离 | 天然 |
| 移植成本 | 要自己写引擎 | 低 | 中 |
| **推荐场景** | 有 C++ 团队、要复刻 DST 架构 | **绝大多数团队** | 玩法重度依赖自定义 VM |

**对绝大多数团队，方案 B（Unity + MoonSharp/UniLua）是最优解**：拿不到 Lua 的全部性能，但能拿到 90% 的架构收益。

### 2.2 绑定层的具体设计

关键是把 DST 那 367 个绑定的**形状**复刻出来。原文第 6 节已经证明了这个形状有多重要——它让整个接口面成为可内省、可枚举的数据。方案 B 也应该这么设计：

```lua
-- 绑定注册表：由代码生成或由数据表驱动
local TheSim = Proxy.new("SimLuaProxy")

TheSim:Bind({
    -- 时间与刻（对应原生 0x140126de0 / 0x140126e10 / 0x140126e70）
    { name = "GetTick",         impl = function() return native_sim_get_tick() end },
    { name = "GetStaticTick",  impl = function() return native_sim_get_static_tick() end },
    -- 注意：这里硬编码 1/30，而不是从引擎的时间设置读。
    -- 原文证明 TheSim:GetTickTime() 字面返回常量 0.03333333507180214，
    -- 说明 DST 把刻长做成了编译期常量而非运行时配置。
    { name = "GetTickTime",    impl = function() return 1.0 / 30.0 end },

    -- 实体
    { name = "CreateEntity",   impl = function() return PushEntityUserdata(entity_manager_create()) end },
    { name = "SpawnPrefab",    impl = function(name, skin, skin_id, creator, custom)
                                    return entity_manager_spawn(name, skin, skin_id, creator, custom)
                                end },
    { name = "FindEntities",   impl = function(x,y,z,radius,must,cant,mustoneof)
                                    return entity_manager_find(x,y,z,radius,must,cant,mustoneof)
                                end },
    -- ... 共 194 个（按本仓库实测的唯一方法数）
})
```

**必须复刻的三个机制**（它们不是优化，是正确性保障）：

**（1）陈旧引用守卫。** 原文明确每个组件方法开头都有 `FUN_140066690()`，对应断言消息 `"Stale Component Reference: GUID %d"`。Lua 的 GC 不会通知 C++ "我刚把实体销毁了"，所以每个 userdata 包装里必须带一个句柄，并在每次调用时验证：

```lua
-- 伪代码：底层组件 userdata 的统一入口
local function MakeComponentProxy(nativeHandle, guid, compName)
    return setmetatable({ __h = nativeHandle, __guid = guid, __name = compName }, {
        __index = function(t, k)
            local fn = ComponentMethods[k]
            if not fn then return nil end
            -- 守卫：句柄是否还有效（实体是否已销毁）
            if not Native_IsValid(t.__h) then
                error(string.format("Stale Component Reference: GUID %d (%s)",
                                    t.__guid, t.__name))
            end
            return function(_, ...)
                return fn(t.__h, ...)
            end
        end
    })
end
```

这一条是 DST 能安全地让 Lua 到处持有组件引用的前提。没有它，Lua 侧的 `local cmp = inst.components.foo` 跨帧存着就会变成悬垂指针。

**（2）散列字符串键。** 原文第 6 节：`StringHash`（`FUN_14042f020`）把字符串键散列成 `uint32`，用于标签、动画名、音效实例名。`AnimState::PlayAnimation`（`0x140083ef0`）明确支持"传字符串或直接传数字散列值"两条路径：

```c
if (lua_type(L,1)==LUA_TSTRING){ anim = lua_tostring(L,1); hash = StringHash(anim); }
else { hash = (int)lua_tonumber(L,1); }
```

Lua 侧大量代码直接传预计算的整数（因为 `TUNING`/`constants` 里有大量常量）。你的实现应该：

```lua
-- 在 Lua 侧预散列，常量化
local ANIM_HASH = HashString("idle_1")   -- 编译期算一次
inst.AnimState:PlayAnimation(ANIM_HASH)  -- 每帧零字符串查找
```

**（3）回调寄存。** 原文反复出现 `luaL_ref(L, LUA_REGISTRYINDEX)` 把异步回调寄存。方案 B 的等价物：

```lua
-- 引擎回调进 Lua：把 Lua 闭包压进引擎侧的对象池
local CallbackPool = {}
local CallbackSeq  = 0

local function DeferToLua(fn)
    CallbackSeq = CallbackSeq + 1
    local id = CallbackSeq
    CallbackPool[id] = fn
    return id     -- 交给引擎做句柄
end

local function ResumeCallback(id, ...)
    local fn = CallbackPool[id]
    CallbackPool[id] = nil      -- 一次性：取出即销毁
    if fn then fn(...) end
end
```

DST 里这个模式被用在 `GetPersistentString`/`SetPersistentString`（`0x14012ecf0`/`0x14012f0c0`）、`CurlRequestManager` 的异步 HTTP、`AddBatchVerifyFileExists` 上。Lua 侧也能看到对应物：`fileutil.lua:1-83` 的 `EraseFiles` 用一个 `res` 剩余计数器收敛 N 个异步回调。

### 2.3 调用开销：哪些调用在热路径上

原文的反编译给出了 Profiler 作用域名，可以据此排优先级。`update.lua` 里有 30 处 `TheSim:ProfilerPush`，直接告诉你哪些是热路径：

```lua
function Update(dt)
    TheSim:ProfilerPush("scheduler")           -- update.lua:238
    TheSim:ProfilerPush("static components")   -- update.lua:249
    TheSim:ProfilerPush("updating components") -- update.lua:255  ← 最热
    TheSim:ProfilerPush("LuaSG")               -- update.lua:287
    TheSim:ProfilerPush("LuaBrain")            -- update.lua:291
end
```

按本仓库实测的调用频次排序，最热的绑定是：

| 绑定 | 全树出现次数 | 位置 | 每次调用开销 |
|---|---:|---|---|
| `inst.AnimState:` | 26,830 | 动画播放/混合 | 中（要查动画表） |
| `inst.Transform:` | 9,453 | `GetWorldPosition`/`SetPosition` | **低**（纯字段） |
| `inst.SoundEmitter:` | 7,977 | `PlaySound`/`KillSound` | 高（FMOD 事件查找） |
| `inst.Physics:` | 3,559 | 碰撞/速度 | **低** |
| `inst.Light:` | 1,497 | 光照 | 低 |

**优化取舍的实测依据**：DST 把 `Transform`/`Physics` 做成纯字段访问（`Transform::SetPosition` 就是三个 `lua_tonumber` + 一次结构体赋值，`0x140087ad0`），把重活（声音、动画）做成需要查表的调用。这正是你该抄的分层：

- **必须走"极轻路径"的**：`Transform:GetWorldPosition`（每帧被调用上万次）。在绑定里直接返回三个 float，不要构造临时 table。
- **可以付出代价的**：`SoundEmitter:PlaySound`（每次要散列事件路径、查 FMOD、启动实例）。
- **应该批量的**：连续设置 4 个 `Transform` 参数（位置+旋转+缩放）应该是**一次**绑定调用传一个结构体，而不是 4 次。原版是分开的三元组，你可以合并。

**Unity 特有的开销点**：C# 侧不要用 `object[]` 返回值数组。每个 `Transform:GetWorldPosition()` 返回一个 `Vector3`（值类型，无装箱）；但如果返回 `float[]` 或 `object[]`，每次调用都会在托管堆分配。MoonSharp 的装箱更严重——如果热路径上绑定调用密集，考虑把 `Transform`/`Physics` 改成一组 `GetXxx()`/`SetXxx(float)` 的标量方法。

### 2.5 Lua 侧的自定义加载器

原文恢复的 `main.lua:133-158` 是一段**必须在你的移植项目里保留**的机制：

```lua
--install our crazy loader!
local manifest_paths = {}
local loadfn = function(modulename)
    local modulepath = string.gsub(modulename, "[%.\\]", "/")
    for path in string.gmatch(package.path, "([^;]+)") do
        local filename = string.gsub(string.gsub(path, "%?", modulepath), "\\", "/")
        local result = kleiloadlua(filename, pathdata.manifest, "scripts/"..modulepath..".lua")
        if result then
            local filetime = TheSim:GetFileModificationTime(filename)
            RequiredFilesForReload[filename] = filetime
            return result
        end
    end
    return errmsg
end
table.insert(package.loaders, 2, loadfn)
```

它在 `package.loaders` 的第 2 位插入自己的加载器，做两件事：**(a)** 走 `kleiloadlua` 而不是裸 `loadfile`（模组目录有独立的路径规则）；**(b)** 记录每个加载文件的修改时间到 `RequiredFilesForReload`，供热重载使用。这是 Lua 里做"资源管线接入"的标准手法，方案 B 里同样要写。

## 【深度扩写 3】移植陷阱：跨语言边界的常见坑

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

DST 用了 15 年（2016 至今），把跨语言边界的坑几乎踩了个遍。下面 9 条每一条都能在源码里找到证据。

### 陷阱 1：GC 与原生句柄的生命周期错配

**症状**：Lua GC 回收了一个 userdata，但它持有的原生实体还在跑；或者反过来，原生实体销毁了，Lua 侧还拿着 userdata。

**DST 的解法**：原文第 6 节的 `ComponentValid` 守卫 + `"Stale Component Reference: GUID %d"`。关键在于**每次调用都验证**，而不是依赖 GC 时机。

**你的坑**：Lua 5.1 的 userdata 在被 GC 前没有任何通知钩子（除非写 `__gc`，但 `__gc` 只在**真正不可达且 GC 那一轮**才跑，时机不可控）。如果你的绑定里 `userdata` 只是一个裸指针（`lightuserdata` 或打包进 `userdata` 的整数），就会产生悬垂指针。

**正确做法**：句柄 + 世代号（generation counter）。

```cpp
// 句柄表：slot + generation，防止 ABA 问题
struct HandleTable {
    std::vector<void*>   slots;
    std::vector<uint32_t> generations;   // slot 复用时 +1
    std::vector<bool>    alive;
    uint32_t freeListHead = UINT32_MAX;
};

// 每次解引用都校验
void* Resolve(uint32_t handle) {
    uint32_t slot = handle >> 8, gen = handle & 0xFF;
    if (slot >= slots.size()) return nullptr;
    if (!alive[slot] || generations[slot] != gen) return nullptr;
    return slots[slot];
}
```

只校验"非空"是不够的——槽位复用会让旧句柄指向新对象（ABA 问题）。必须带世代号。

### 陷阱 2：整数被截断成浮点

**症状**：`net_uint`（32 位无符号）传一个大于 2^31 的值，Lua 侧看到的是负数。预制体哈希、GUID、资产 ID 全都可能超 31 位。

**证据**：`netvars.lua:8-11` 的类型表明确列了 `net_uint 32-bit unsigned integer [0..4294967295]`、`net_ushortint 16-bit unsigned integer [0..65535]`。而 Lua 5.1 只有 double 一种数。`Entity:AddTag` 用 `uint32 hash`（`0x1401227b0`）、`AnimState::PlayAnimation` 接受 `(int)lua_tonumber(L,1)`（`0x140083ef0`）——都依赖 Lua 的 double 精确表示 32 位整数这一事实（IEEE754 double 有 53 位尾数，做得到）。

**你的坑**：Lua 5.1/LuaJIT 的 double 没问题，但 **Lua 5.3+ 变成了整数/浮点双类型**，`tonumber("4294967295")` 返回的是整数子类型而不是浮点——如果你的绑定代码假设"所有数都是 double"，行为会变。另外 Unity 的 `MonoBehaviour` 侧 `float` 只有 24 位尾数，传大整数会掉精度。

**正确做法**：绑定里显式声明宽度，`static uint32_t`、`static uint64_t`，不要图省事全用 `double` 或 `float`。

### 陷阱 3：异常穿透脚本边界

**症状**：C++ 抛出的异常穿过 Lua 的 C 调用栈，导致 Lua 状态不一致（栈上残留半压入的值），后续所有调用都错位。

**证据**：原文提到二进制里有 **568 个具名的 `Catch$...` 处理器**，且 `.pdata` 节很大——说明大量 C++ 代码用了异常。反编译出的绑定函数里，`ComponentValid` 失败时是 `return 0`（正常返回）而不是抛异常。

**DST 的策略很清楚**：**绑定函数不抛 C++ 异常穿越边界**。错误处理用两种方式：返回 0/nil + 日志，或调 Lua 的 `error()`。

**你的坑**：Unity 的 Mono/C# 侧没有真正的 C++ 异常（用的是受管的 SEH），但 **Lua 的 `error()` 在 pcall 边界外会直接终止整个 VM**。`mainfunctions.lua:1602-1616` 展示了正确处理：

```lua
local fn = loadstring(str)
known_assert(fn ~= nil, "CUSTOM_COMMANDS_ERROR")
xpcall(fn, debug.traceback)   -- 用 xpcall 兜住用户代码
```

**正确做法**：每一个可能被用户代码污染的入口（自定义命令、热重载的脚本、模组）都用 `xpcall(fn, debug.traceback)` 包住。C++ 侧则统一约定：绑定函数返回错误码，绝不 throw。

### 陷阱 4：每帧的隐式分配

**症状**：绑定函数每次调用都 new 一个临时对象，GC 压力把帧率打穿。

**证据**：`mainfunctions.lua:487-496` 的 `CreateEntity` 是在**创建时**分配一次并常驻的；`util.lua:553-572` 的 `distsq` 处理"2D 向量当数字传"的特殊情况并做了 `# V2C: disabling asserts. crash is fine` 的降级——这些都是热路径被反复优化过的痕迹。

**特别要注意的**：`simutil.lua:35/48/229/235/241/482` 都在调 `TheSim:FindEntities(x, y, z, radius, tags...)`——这个函数返回**一个实体数组**。在 Lua 侧这意味着每次调用都创建一个 table 数组并填充。遍历邻近实体做标签筛选时，很容易写出"每个实体每帧调一次 FindEntities"的 O(n²) 代码。

**正确做法**：
- 绑定层提供**迭代器式**接口而非返回数组：`for e in Sim:EachEntityNear(x, y, z, r) do ... end`，把遍历在原生侧完成。
- 或者至少用对象池复用返回的 table。

### 陷阱 5：浮点精度在跨边界时被静默改变

**症状**：位置数据在 C++ float（24 位尾数）和 Lua double（53 位）之间来回转换，反复累积误差；或者读档后位置漂移。

**证据**：`entityscript.lua:264-296` 的 `GetSaveRecord` 里，所有坐标在存盘前都被量化：

```lua
record.rx = rx and math.floor(rx * 1000 + 0.5) * 0.001 or 0
record.rz = rz and math.floor(rz * 1000 + 0.5) * 0.001 or 0
```

即**保留 3 位小数、毫米级精度**，且用 `math.floor(x*1000+0.5)*0.001` 而不是 `x`，避免浮点表示误差累积进存档格式。

同一处还有 NaN 猎捕（`isbadnumber(rx)`），命中时开发版 `error()`、发布版降级为 0。

**正确做法**：存档/网络序列化前统一量化，格式用定点而非浮点。

### 陷阱 6：字符串生命期

**症状**：`const char*` 指向引擎内部的临时缓冲区，脚本保存了这个指针，下次调用就悬垂。

**证据**：`RegisterPrefab`（`0x140132b00`）在循环里把 Lua 字符串传给 `Prefab_AddAsset(p, type, name, param)`——这是立即消费。但 `StringHash` 的存在说明设计倾向是**尽早转成整数**：散列之后就不再需要原字符串了。

**你的坑**：Lua 的 string 是不可变且驻留的（interned），传给 C++ 时 `lua_tolstring` 返回的指针在 GC 前都有效——但如果你的绑定把这个指针**存进引擎对象**，Lua 侧那个变量出了作用域被 GC，引擎对象就悬垂了。

**正确做法**：存进引擎的字符串一律 `strdup` 或转成 interned ID。参考 `TheSim:SetResolveNoiseFunction`（`0x140139020`）这类"注册 Lua 函数指针到原生"的调用——注册的应该是 Lua 在 registry 里的 ref，不是栈指针。

### 陷阱 7：热路径上的错误检查反而更慢

**症状**：你加了完善的参数检查，结果热路径调用成本翻倍。

**原文的做法**：`ComponentValid` 守卫在**每个**绑定函数开头都跑，但它必须极简（一次句柄查表）。它不是"防御性编程"，是**正确性前提**（陷阱 1）。两者不能混。

**正确做法**：区分三类检查——
- **必须每次做**：句柄有效性（否则就是崩溃）。
- **可以 debug 构建做**：参数类型/数量检查。用 `luaL_checkstring` / `luaL_optnumber`（这些只在出错时才抛，编译进 release 后开销很小）。
- **可以省略**：业务逻辑校验（比如"这个 prefab 存不存在"）——放到注册期一次性做完。`mainfunctions.lua:121-122` 就是这么干的：

```lua
local resolvedpath = resolvefilepath(asset.file, prefab.force_path_search, prefab.search_asset_first_path)
assert(resolvedpath, "Could not find "..asset.file.." required by "..prefab.name)
```

**预制体资源解析在注册时一次性做完并 assert**，运行时 `resolvefilepath` 就走 `memoizedFilePaths` 缓存（`util.lua:636-643`）。

### 陷阱 8：服务端/客户端构建的差异会泄漏到脚本

**症状**：开发时在客户端测通了，上服务器发现某个组件不存在。

**证据**：`ShouldIgnoreResolve`（`mainfunctions.lua:69-98`）是一个**在 Lua 侧**实现的服务器资源过滤：

```lua
function ShouldIgnoreResolve( filename, assettype )
    if assettype == "INV_IMAGE" then return true end
    if assettype == "MINIMAP_IMAGE" then return true end
    if filename:find(".dyn") and assettype == "PKGREF" then return true end
    if TheNet:IsDedicated() then
        if assettype == "SOUNDPACKAGE" then return true end
        if assettype == "SOUND" then return true end
        if filename:find(".ogv") then return true end
        if filename:find(".fev") and assettype == "PKGREF" then return true end
        if filename:find("fsb") then return true end
    end
    return false
end
```

注意几个细节：
- `INV_IMAGE` 和 `MINIMAP_IMAGE` 是**永远**跳过的（纯客户端资源），不只是服务器。
- 音频资源有**三道**过滤：`SOUNDPACKAGE` 类型、`.fev` 扩展名、`fsb` 扩展名——因为 `SOUND` 类型既可能指向 `.fsb` 也可能指向别的东西。
- 这段函数在**注册预制体时**（`RegisterPrefabsImpl`，`mainfunctions.lua:107-111`）被调用，不是运行时。

**你的坑**：如果你的资源解析在运行时才做过滤，服务器会白读几百 MB 的音频（991 MB 的 `.fsb`/`.fev`）。而且 `Assert(resolvedpath, ...)` 在服务器上会因为资源被过滤而炸。

**正确做法**：像 DST 一样，把"这个资源在这个平台上要不要"做成**注册期**决策，且**默认值偏向"要"**（宁可多加载也不要缺）。

### 陷阱 9：异步回调的生命周期跨越场景重置

**症状**：玩家退出关卡时，一个还在飞的 HTTP 请求回调触发了，操作的是已被销毁的世界。

**证据**：`mainfunctions.lua:14-16` 有一组明确的拆除标志：

```lua
SimTearingDown = false
SimShuttingDown = false
PerformingRestart = false
```

`update.lua:81-85` 在 `WallUpdate` 里检查它：

```lua
if not SimTearingDown then
    TheSim:ProfilerPush("input")
    TheInput:OnUpdate()
    TheSim:ProfilerPop()
end
```

`update.lua:244-247` 在 `Update` 里检查 `SimShuttingDown` 提前返回。

同时 `mainfunctions.lua:1578` 有一段很坦诚的注释：

```lua
-- warning, we don't want to run much code here. We're in a strange mix of loaded assets and mapped paths
-- as a bonus, the fonts are unloaded, so no asserting...
```

**你的坑**：这是所有"脚本驱动 + 异步引擎"的通病。回调必须检查场景世代号（generation），且拆除路径要极度克制。

**正确做法**：维护一个单调递增的 `worldGeneration` 计数器，所有异步闭包捕获创建时的值；回调触发时 `if gen ~= currentGen then return end`。DST 的等价物是三个布尔标志（更弱，但足够）。

## 【实现清单】

按依赖顺序排列。每项都是可勾选的独立任务。

### 阶段一：模拟内核（无渲染、无网络）

- [ ] **实体句柄表**：slot + generation 的双数组，支持 slot 复用；解引用返回 `nullptr` 而非崩溃
- [ ] **实体管理器**：创建/销毁/遍历；维护 `GUID` 唯一分配器
- [ ] **标签位集**：`TagSet: Add(uint32 hash) / Contains / Count`，用位图实现
- [ ] **字符串散列**：`HashString(s) -> uint32`，全局唯一的散列函数（Lua 与 C++ 共用）
- [ ] **变换组件**：`SetPosition/GetWorldPosition/SetRotation/WorldToLocalSpace`，零分配路径
- [ ] **预制体注册表**：名字 → 工厂函数 + 资源清单 + 标签 + 依赖；支持 `Register/Unregister/Load/Unload`
- [ ] **定步长时钟**：`TickLength` 硬编码 1/30（不是可配置项）；`Tick/StaticTick/RealTimeMs/TimeScale/Step`
- [ ] **模拟步进**：`Step(dt)` = 调脚本 `Update(dt)` → 推进子系统 → `StepCount++` → 调脚本 `PostUpdate`/`StaticUpdate`
- [ ] **脚本 VM 宿主**：嵌入 Lua 5.1（或 UniLua），创建 VM、设置 `package.path`、注册全局
- [ ] **绑定注册框架**：`{name, fnptr, userdata}` 表驱动的注册，让接口面成为可枚举的数据
- [ ] **组件绑定**：每个组件方法入口带句柄有效性检查（`"Stale Component Reference: GUID %d"`）
- [ ] **回调寄存**：Lua 闭包 ↔ 引擎句柄的双向映射，一次性取出即销毁

### 阶段二：确定性与持久化

- [ ] **PCG32 随机数**：`pcg32_srand(seed)` / `pcg32_rand()`，**导出为 C ABI 符号**（原文如此，方便第三方替换）
- [ ] **存档量化辅助**：所有浮点入档前 `floor(x*1000+0.5)*0.001`
- [ ] **NaN/Inf 拦截**：序列化前扫描，开发构建 `error()`，发布构建降级为 0 并记日志
- [ ] **异步保存 IO**：`Put/Get/Erase`，回调模型；路径**白名单**（不是黑名单）+ 路径规范化
- [ ] **槽位路由**：`InClusterSlot(slot, shard, ...)`，支持按世界分槽
- [ ] **压缩 + 编码**：zlib + 一层自定义编码；开发构建关闭编码（对应 `ENCODE_SAVES = BRANCH ~= "dev"`）
- [ ] **世界快照**：环形缓冲，`Increment/List/SetCurrent/Truncate`
- [ ] **Lua 存档序列化**：表 → 文本；分段落盘（避免单文件过大）

### 阶段三：网络

- [ ] **传输层**：UDP + 可靠通道（可用 Netcode/GameNetworkingSockets 替代 RakNet）
- [ ] **实体复制**：GUID 标识 + 组件状态同步 + 兴趣管理
- [ ] **RPC 派发**：`SendRPC(scope, code, ...)`，scope ∈ {Server, Client, Shard, ModServer}
- [ ] **RPC 队列**：`HandleRPC` 入队；`PumpRPCQueue(limitPerSender)` 在刻边界按发送者串行化
- [ ] **RPC 时间线**：`Timeline[sender] == tick` 才执行，否则留到下一刻；刻边界清空
- [ ] **限流**：每发送者每刻上限（建议 20），超限打警告
- [ ] **Shard（分片）**：主/从分片的数据路由与玩家迁移；`ID_SHD_*` 式包 id
- [ ] **异步 HTTP**：主服务器请求（ matchmaking / 鉴权 / 版本检查）
- [ ] **会话令牌**：`GameSessionToken` 式鉴权 + 签名校验

### 阶段四：世界生成

- [ ] **独立生成 VM**：独立线程 + 独立 Lua state（或独立进程）
- [ ] **字符串边界**：返回序列化字符串，失败返回 `error = [[...]]return error`
- [ ] **种子可复现**：同一个种子 → 同一个世界（依赖 PCG32 + 无浮点累积）
- [ ] **生成期不跑模拟**：生成期间主循环只加载进度

### 阶段五：客户端表现层（服务器构建时全部剔除）

- [ ] **虚拟文件系统**：zip 挂载 + 内存后端 + 本地后端；路径解析带缓存
- [ ] **纹理加载**：KTEX 或引擎原生格式；图集（XML 或自定义描述符）
- [ ] **字体**：BMFont 或引擎原生字体；字距微调 + fallback 链
- [ ] **着色器**：源码内嵌容器（见资源报告【深度扩写 1】）；uniform block 注册表
- [ ] **动画**：bank/build 分离的编译格式；`SetBank`/`SetBuild` 支持运行时换皮
- [ ] **音频**：事件路径驱动；DSP 效果；设备热插拔；混音快照栈
- [ ] **渲染器**：场景图 + 视锥剔除 + 后处理 + 粒子批处理
- [ ] **纹理流式加载**：分组 + 优先级 + 异步
- [ ] **线程化渲染**（可选）：mutex+semaphore 同步；同线程快路径
- [ ] **输入**：键鼠 + 手柄 + 震动
- [ ] **调试叠加层**：ImGui 控制台 + 性能图 + 统计 HUD

### 阶段六：构建与运维

- [ ] **服务器构建做减法**：链接期剔除渲染器 + 输入；用导入表差异验证
- [ ] **卡死看门狗**：逐帧倒计时，超时 `exit(6)`（专用服务器必备）
- [ ] **崩溃转储**：`MiniDumpWriteDump` 或等价方案
- [ ] **定时器精度**：`timeBeginPeriod(1)` / `timeEndPeriod(1)`
- [ ] **调试开关矩阵**：`引擎支持 && 非主机 && 非生产 && 非专用服务器`（照抄 `main.lua:88`）
- [ ] **Lua 调试器挂载**：可开关，发布构建强制关闭
- [ ] **自定义包加载器**：`package.loaders[2]` 插入，记录文件 mtime 供热重载
- [ ] **热重载**：基于 `RequiredFilesForReload` 的时间戳比对
- [ ] **栈追踪**：脚本异常时输出完整 traceback

### 阶段七：质量保障（照抄 DST 的实战教训）

- [ ] **构建期断言**：预制体资源解析在注册期 assert，不留到运行时
- [ ] **组件重名检测**：`AddComponent` 重复添加要打印警告（照抄 `entityscript.lua:612-613`）
- [ ] **平台资源过滤**：照抄 `ShouldIgnoreResolve` 的三层过滤（类型 + 扩展名 × 2 + 专用服务器）
- [ ] **场景世代号**：所有异步回调检查世代，防止跨场景误触发
- [ ] **拆除路径克制**：`Shutdown()` 里只做最少的事（照抄 `mainfunctions.lua:1578` 的注释态度）
- [ ] **热路径剖析**：脚本侧可用的 `ProfilerPush/Pop`，覆盖最热的 5 个循环

## 概述 / TL;DR

- **DST 是严格的服务器权威（server-authoritative）架构。** 主分片跑真实模拟，客户端只跑一层*预测*。几乎每个玩法文件都被 `if TheWorld.ismastersim then ... end` 门控。**同一套 Lua 跑在服务器和客户端上**——行为由运行时的角色标志决定，而不是由两份代码决定。
- **客户端从不直接改世界。** 它通过 **RPC** 表达意图（`SendRPCToServer(RPC.LeftClick, ...)`），由服务器校验并施加。三条内置通道：客户端→服务器（`RPC`）、服务器→客户端（`CLIENT_RPC`）、分片→分片（`SHARD_RPC`），外加每一类各自的模组可寻址版本。
- **实体状态通过类型化的网络变量（netvar）同步**（`net_bool`、`net_byte`、`net_entityref`……），这些变量在服务器与客户端上必须**逐字段一致地声明**；再加上组件的**副本组件（replica）**（`health_replica.lua`），它给客户端提供一份服务器组件的只读视图。
- **房主玩家是一个真正的服务器。** 客户端开的世界里 `TheNet:GetIsServer()` 为真**且** `ismastersim` 为真，于是在同一个进程里同时扮演两个角色。
- **存档就是 Lua 源码文本**，由 `DataDumper`（一个打印 Lua 源码的序列化器）产出，按预制体分块，异步落盘（`TheNet:SerializeWorldSession`）。每个实体贡献自己的 `OnSave()`，每个组件也贡献自己的 `OnSave()`；重建流程是 `SpawnSaveRecord` → `SetPersistData` → `LoadPostPass`（后者负责解析跨实体引用）。
- **模组系统是一个沙箱环境。** 每个模组拿到一张全新的 Lua `env` 表（`CreateEnvironment`）和一套精选 API（`AddPrefabPostInit`、`AddClassPostConstruct`、`AddAction`……）。模组从不直接触碰全局 `_G`，而是通过 `env.GLOBAL` 绕进去。所有钩子都是**延迟表（deferred tables）**，在引擎的正确时刻被回放。
- **模组注册自己的 RPC 处理器**：`AddModRPCHandler(namespace, name, fn)`，调用时用 `SendModRPCToServer(GetModRPC(namespace, name), ...)`。命名空间把每个模组隔离开。
- **前端是一个屏幕栈。** `TheFrontEnd:PushScreen(screen)` / `PopScreen()` 管理一个 `screenstack`；`Screen` 继承自 `Widget`，而 `Widget` 包装着一个真实（不可见）的实体并带一个 `UITransform`。焦点与输入沿着控件树向下流动。
- **HUD 本身就是一个 Screen**（`screens/playerhud.lua`，类名 `"HUD"`），在本地玩家激活时被压栈；它持有 `Controls`（状态徽章、物品栏、合成、地图）以及几十个全屏浮层。
- **资源按预制体声明**，通过 `Asset("ANIM"|"IMAGE"|"SOUND"|"ATLAS"|...)` 写在预制体里，再由 `resolvefilepath()` 解析成真实路径——它会搜索 `package.assetpath`（先模组目录，再本体 data 目录）。图集（atlas）由一份 `.xml` 描述文件配若干 `.tex` 图像。

## 一、网络架构——服务器权威模型

### 1.1 三个角色标志

DST 用三个布尔量区分进程角色，它们在世界实体创建时被设定（`prefabs/world.lua:426`）：

```lua
inst.ismastersim   = TheNet:GetIsMasterSimulation()
inst.ismastershard = inst.ismastersim and not TheShard:IsSecondary()
```

| 标志 | 含义 | 在哪里为真 |
|---|---|---|
| `TheNet:GetIsServer()` | 本进程托管着*某个*模拟 | 专用服务器；房主玩家；次级（Caves）分片 |
| `TheNet:GetIsClient()` | 本进程为真人渲染并接收复制 | 每一个非专用实例，包括房主玩家 |
| `TheWorld.ismastersim` | 本进程是这个世界的**权威**模拟 | 仅主分片（Forest） |
| `TheWorld.ismastershard` | 既是主模拟又是集群主（拥有全局状态） | 集群中的 Forest 分片 |

```
        ┌──────────────────────── CLUSTER ────────────────────────┐
        │                                                          │
   主分片 ("Forest")                次级分片 ("Caves")
   ismastersim = true                  ismastersim = true
   ismastershard = true                ismastershard = false
   TheNet:GetIsServer() = true         TheNet:GetIsServer() = true
        │  ▲                                   │  ▲
        │  │  SHARD_RPC (服务器↔服务器)         │  │
        │  └───────────────────────────────────┘  │
        │ 实体复制 (netvars)                         │
   ┌────┴─────┬─────────────┐                      │
   ▼          ▼             ▼                      ▼
[房主PC] [远程PC]      [远程PC]                [远程PC]
ismastersim 客户端      仅客户端              仅客户端
= true       只         只                    只
(服务器+     (RPC↑ /     (RPC↑ /               (通过传送门
 客户端)     netvars↓)   netvars↓)              迁移到这里)
```

**各角色具体跑什么：**

- **仅服务器**（`TheWorld.ismastersim` / `TheNet:GetIsServer()`）：世界 tick、生成、伤害结算、物品栏权威、存档（`SaveGame` 在客户端上直接早退——见 `mainfunctions.lua:1068`）、玩家加入/离开事件（`ms_playerjoined`）、分片迁移。
- **仅客户端**（`not TheWorld.ismastersim`）：输入采集 → 发 RPC、移动*预测*、HUD 更新、本地小地图序列化、`net_event` 反应（音效/特效）。
- **房主玩家（两者兼具）**：客户端开的世界既跑权威模拟，又为房主渲染；`SerializeUserSession` 显式允许 `player == ThePlayer or TheNet:GetIsServer()`（`networking.lua:303`）。

`SaveGame` 是最清晰的「仅服务器」守卫：

```lua
-- mainfunctions.lua:1068
function SaveGame(isshutdown, cb)
    if not TheNet:GetIsServer() then
        print("SaveGame disabled for Clients in Don't Starve Together")
        if cb ~= nil then cb(true) end
        return
    end
    TheNet:StartWorldSave()
    ...
```

### 1.2 专用服务器

**不存在**独立的 `dedicated_server.lua`；**同一套**脚本启动成服务器模式。`gamelogic.lua:1322` 展示了那个分支：

```lua
-- Online servers call StartDedicatedServer after authentication
if TheNet:IsDedicated() and not TheNet:GetIsServer() and TheNet:IsDedicatedOfflineCluster() then
	StartDedicatedServer()
end
```

`StartDedicatedServer()`（`networking.lua:849`）调用 `TheNet:StartServer(online_mode)`，然后 `StartNextInstance({ reset_action = RESET_ACTION.LOAD_SLOT, save_slot = slot })`。专用进程没有 `ThePlayer`，鼠标输入被禁用（`input.lua:22`：`self.mouse_enabled = IsNotConsole() and not TheNet:IsDedicated()`），前端/输入系统被短路。所谓「空渲染器」是 C++ 层面的事——Lua 侧完全一样，它只是**永远不会成为客户端**。`SpawnSecondInstance()`（`networking.lua:12`）甚至会再启动第二个 `.exe`，好让房主能加入自己开的专用服务器。

## 二、RPC 系统——客户端↔服务器消息

所有 RPC 管线都在 **`networkclientrpc.lua`** 里。引擎（C++）负责投递字节；这个文件定义处理函���表、代码→数字的映射、限流，以及发送函数。

### 2.1 三条内置通道

每条通道都是一个 `name = function(player, ...)` 处理器的 Lua 表。加载时引擎按 `orderedPairs` 顺序给每个 name 分配一个整数代码，然后把表按代码重新建键：

```lua
-- networkclientrpc.lua:1388
RPC = {}
local i = 1
for k, v in orderedPairs(RPC_HANDLERS) do RPC[k] = i; i = i + 1 end
for k, v in orderedPairs(RPC) do RPC_HANDLERS[v] = RPC_HANDLERS[k]; RPC_HANDLERS[k] = nil end
```

| 通道 | 方向 | 发送函数 | 处理表 | 信任级别 |
|---|---|---|---|---|
| `RPC` | 客户端 → 服务器 | `SendRPCToServer(code, ...)` | `RPC_HANDLERS` | **不可信**——必须校验 + 限流 |
| `CLIENT_RPC` | 服务器 → 客户端 | `SendRPCToClient(code, users, ...)` | `CLIENT_RPC_HANDLERS` | 可信 |
| `SHARD_RPC` | 分片 → 分片 | `SendRPCToShard(code, shards, ...)` | `SHARD_RPC_HANDLERS` | 可信 |

```lua
-- networkclientrpc.lua:1636
function SendRPCToServer(code, ...)
    assert(RPC_HANDLERS[code] ~= nil)
    TheNet:SendRPCToServer(code, ...)
end
```

### 2.2 校验与限流（为什么客户端→服务器方向是特殊的）

每一个发往服务器的 RPC **都要重新校验自己的参数**，因为恶意客户端可以发任何东西。`LeftClick` 是最有代表性的例子：

```lua
-- networkclientrpc.lua:61
LeftClick = function(player, action, x, z, target, isreleased, controlmods, noforce, mod_name, platform, platform_relative, spellbook, spell_id)
    if not ( (action == nil and x == nil and ...) -- 全 nil
          or (checknumber(action) and checknumber(x) and checknumber(z)
              and optentity(target) and optbool(isreleased) and ...) ) -- 或全部合法
    then
        printinvalid("LeftClick", player)  -- 推送 "invalidrpc" 事件，供反作弊模组使用
        return
    end
    local playercontroller = player.components.playercontroller
    if playercontroller ~= nil then
        x, z = ConvertPlatformRelativePositionToAbsolutePosition(x, z, platform, platform_relative)
        if IsPointInRange(player, x, z) then   -- 拒绝距离平方 > 4096 的点击
            playercontroller:OnRemoteLeftClick(action, Vector3(x,0,z), target, ...)
        end
    end
end,
```

`HandleRPC`（`networkclientrpc.lua:1675`）不立即执行，而是**入队**，同时施加按发送者的限流，并在每帧一次的 `HandleRPCQueue` 中排空（由 `update.lua:42` 的 `WallUpdate` 调用）：

```lua
local RPC_QUEUE_RATE_LIMIT = 20          -- 每个逻辑刻
local RPC_QUEUE_RATE_LIMIT_PER_MOD = 5   -- 每注册一个模组 RPC +5
...
if limit < RPC_QUEUE_RATE_LIMIT then
    RPC_Queue_Limiter[sender] = limit + 1
    table.insert(RPC_Queue, { fn, sender, data, tick })
else
    print("Rate limiting RPCs from", sender, userid, ...)
end
```

### 2.3 内置 RPC 列表（节选）

**客户端→服务器（`RPC_HANDLERS`）**——移动、动作、物品栏、合成：

- 鼠标/点位：`LeftClick`、`RightClick`、`ActionButton`、`AttackButton`、`InspectButton`、`ResurrectButton`、`DoWidgetButtonAction`、`DoActionOnMap`。
- 移动/预测：`DirectWalking`、`DragWalking`、`PredictWalking`、`PredictOverrideLocomote`、`StrafeFacing`、`StartHop`、`SteerBoat`、`StopWalking`、`SetMovementPredictionEnabled`。
- 手柄：`ControllerActionButton`、`ControllerActionButtonPoint`、`ControllerActionButtonDeploy`、`ControllerAttackButton`、`ControllerAltActionButton(Point)`。
- 物品栏：`PutOneOfActiveItemInSlot`、`TakeActiveItemFromAllOfSlot`、`SwapActiveItemWithSlot`、`MoveItemFromAllOfSlot`、`EquipActiveItem`、`DropItemFromInvTile`、`ReturnActiveItem`。
- 合成/建造：`MakeRecipeFromMenu`、`MakeRecipeAtPoint`、`BufferBuild`、`CannotBuild`。
- 杂项：`SetWriteableText`、`WakeUp`、`GetChatHistory`、`SetClientAuthoritativeSetting`、`ClosePopup`、`RecievePopupMessage`、`AddSkillXP`。

**服务器→客户端（`CLIENT_RPC_HANDLERS`）**——向特定玩家推送状态/知识：

- `LearnRecipe`、`LearnFoodStats`、`LearnPlantStage`、`LearnFertilizerStage`、`LearnBuilderRecipe`、`TakeOversizedPicture`（填充客户端本地的 Cookbook/植物登记表）。
- `RecieveChatHistory`、`ShowPopup`、`RecievePopupMessage`、`UpdateAccomplishment`、`SetSkillActivatedState`、`AddSkillXP`、`PostActivateHandshake`。

**分片→分片（`SHARD_RPC_HANDLERS`）**——跨世界同步：

- `ShardTransactionSteps` / `PruneShardTransactionSteps`（迁移期间的两阶段物品转移）。
- `SyncWorldSettings`、`ResyncWorldSettings`、`SyncWorldStateTag`、`SyncBossDefeated`、`ReskinWorldMigrator`、`SyncMermKing*`。

### 2.4 移动的实际流程

1. 客户端 `playercontroller:OnUpdate` 读取输入，构建一个 `BufferedAction`。
2. 客户端发送 `SendRPCToServer(RPC.DirectWalking, x, z)`（或 `PredictWalking`），**同时**乐观地移动本地化身（预测）。
3. 服务器的 `RPC_HANDLERS.DirectWalking` 校验 `x*x + z*z < 1.01`，调用 `playercontroller:OnRemoteDirectWalking(x, z)` 驱动权威的 locomotor。
4. 服务器 netvar（`Transform`、`net_float` 位置）复制回客户端；客户端做纠正（reconciliation）。

对于在地面上的左键点击：`playercontroller.lua:4857` 的
`SendRPCToServer(RPC.LeftClick, act.action.code, pos_x, pos_z, mouseover, ...)`。

## 三、实体复制——网络变量

### 3.1 `entity:AddNetwork()` + 类型化 netvar

任何需要被客户端看到的实体都要调用 `inst.entity:AddNetwork()`（在 `prefabs/` 下共出现 **1905 次**，分布在 1400 个文件里）。之后，字段用类型化 netvar 声明。`netvars.lua` 文档化了完整集合：

```
net_bool         1-bit boolean
net_tinybyte     3-bit unsigned   [0..7]
net_smallbyte    6-bit unsigned   [0..63]
net_byte         8-bit unsigned   [0..255]
net_shortint     16-bit signed
net_ushortint    16-bit unsigned
net_int/uint     32-bit
net_float        32-bit float
net_hash         32-bit hash of a string
net_string       variable length
net_entity       entity reference (net_entityref)
net_bytearray / net_smallbytearray / net_ushortarray  (max 31, "expensive")
```

`netvars.lua` 头部的关键规则：

> *"netvars must exist and be declared identically on server and clients for each entity, otherwise entity deserialization will fail. Note that this means if a MOD uses netvars, then server and clients must all have the same MOD active."*
>
> （netvar 必须在服务器与客户端上为每个实体都存在且**声明完全一致**，否则实体的反序列化会失败。这意味着：**只要模组用了 netvar，服务器和所有客户端就必须都装上这个模组。**）

构造签名是 `net_bool(GUID, "path.name", "dirtyeventname")`。真实例子——玩家的每客户端「私密」实体（`prefabs/player_classified.lua:1335` 起）：

```lua
inst.entity:AddNetwork()
...
inst.healthpenalty   = net_byte(inst.GUID, "health.penalty", "healthdirty")
inst.istakingfiredamage = net_bool(inst.GUID, "health.takingfiredamage", "istakingfiredamagedirty")
inst.currenttemperaturedata = net_byte(inst.GUID, "temperature.current", "temperaturedirty")
inst.sanitypenalty   = net_byte(inst.GUID, "sanity.penalty", "sanitydirty")
```

### 3.2 set / value / set_local / 脏事件

```lua
netvar:set(x)       -- 仅服务器；同步到客户端，两边都会触发脏事件
netvar:value()      -- 在服务器或客户端上读取
netvar:set_local(x) -- 不触发同步的写入（客户端在本地平滑外推计时器）
```

`net_event`（`netvars.lua:85`）是包在 `net_bool` 外面的「一次性触发器」封装（一个音效、一次脉冲）：

```lua
net_event = Class(function(self, guid, event)
    self._bool = net_bool(guid, event, event)
end)
function net_event:push()
    self._bool:set_local(true)
    self._bool:set(true)
end
```

`GetIdealUnsignedNetVarForCount(count)`（`netvars.lua:97`）会挑一个装得下的最小类型——例如 7 个取值 → `net_tinybyte`，255 个 → `net_byte`。用它来压带宽。

### 3.3 「classified」实体模式

与其把*一切*都复制在玩家身上，DST 会生成一个**隐藏的伴生实体** `player_classified`，它**只复制给那一个玩家**（通过 `Network:SetClassifiedTarget`），承载该玩家所有的私密 netvar（生命百分比、理智值、体温、灵感、技能状态）。见 `prefabs/player_classified.lua`（服务器接口）以及读取它的那些副本组件。绑定发生在 `prefabs/player_common.lua:1016`：

```lua
inst.player_classified.Network:SetClassifiedTarget(inst)
```

### 3.4 组件副本（replica）

`entityreplica.lua` 列出了哪些组件有客户端侧镜像：

```lua
local REPLICATABLE_COMPONENTS = {
    builder=true, combat=true, container=true, constructionsite=true, equippable=true,
    fishingrod=true, follower=true, health=true, hunger=true, inventory=true,
    inventoryitem=true, moisture=true, named=true, oceanfishingrod=true, rider=true,
    sanity=true, sheltered=true, stackable=true, writeable=true,
}
```

在主模拟上，添加这些组件之一会给实体打上 `_<name>` 标签（预复制的情况下是 `__<name>`）；客户端在反序列化标签之后读到这个标签，就实例化 `<name>_replica.lua`（见 `EntityScript:ReplicateEntity`，`entityreplica.lua:75`）。副本会挂上 classified 实体并暴露只读 getter。例子——`components/health_replica.lua`：

```lua
local function MaxWithPenalty_Client(self)
    return self.classified.maxhealth:value() * (1 - GetPenaltyPercent_Client(self))
end
function Health:SetMax(max)                    -- 服务器路径
    if self.classified ~= nil then self.classified:SetValue("maxhealth", max) end
end
function Health:Max()
    if self.inst.components.health ~= nil then -- 权威模拟
        return self.inst.components.health.maxhealth
    elseif self.classified ~= nil then         -- 客户端读 netvar
        return self.classified.maxhealth:value()
    else return 100 end
end
```

所以游戏代码在客户端上调 `inst.replica.health:GetPercent()`，在服务器上调 `inst.components.health:GetPercent()`——概念上是同一套 API，两份实现。模组可以用暴露出来的 `AddReplicableComponent(name)`（`entityreplica.lua:98`）添加可复制的组件。

## 四、玩家生命周期——加入 → 游玩 → 迁移 → 离开

### 4.1 加入流程

1. 客户端连接；C++ 的 `NetworkManager` 完成鉴权，并在新生成时于主分片上调用 **`SpawnNewPlayerOnServerFromSim`**（`networking.lua:249`）：

```lua
function SpawnNewPlayerOnServerFromSim(player_guid, skin_base, ..., skillselection, skinoverrides)
    local player = Ents[player_guid]
    if player ~= nil then
        local skinner = player.components.skinner
        skinner:SetClothing(clothing_body) ... skinner:SetSkinName(skin_base)
        if player.OnNewSpawn ~= nil then player:OnNewSpawn(starting_item_skins) ... end
        player.components.skilltreeupdater:SetPlayerSkillSelection(skillselection)
        TheWorld.components.playerspawner:SpawnAtNextLocation(TheWorld, player)
        SerializeUserSession(player, true)
    end
end
```

角色/皮肤的选择会先由 `ValidateSpawnPrefabRequest`（`networking.lua:194`）在服务器侧校验——它检查所有权（`TheInventory:CheckClientOwnership`）和白名单，因此客户端无法冒领它并不拥有的皮肤/角色。

2. 玩家实体激活。`OnPlayerActivated`（`prefabs/player_common.lua:826` 附近）会推送 `playeractivated`，在客户端通过 `ActivateHUD` 构建 HUD，并对客户端立即调用 `SerializeUserSession(inst)`，这样崩溃后还能重连。
3. 晚一帧，`OnPlayerJoined`（`player_common.lua:843`）触发**加入事件**：

```lua
local function OnPlayerJoined(inst)
    inst.jointask = nil
    TheWorld:PushEvent("playerentered", inst)   -- 服务器和客户端都会触发
    if TheWorld.ismastersim then
        TheWorld:PushEvent("ms_playerjoined", inst)  -- 仅服务器
        inst:ListenForEvent("gotnewattunement", OnGotNewAttunement)
        ...
    end
end
```

`ms_` 前缀是**仅主模拟事件**的约定。几十个世界组件订阅它们（`hounded`、`birdspawner`、`deerclopsspawner`……）来根据玩家数量缩放难度/氛围：

```lua
-- components/hounded.lua:680
inst:ListenForEvent("ms_playerjoined", OnPlayerJoined)
inst:ListenForEvent("ms_playerleft",  OnPlayerLeft)
```

### 4.2 游玩

游玩期间客户端发送意图 RPC；服务器复制 netvar；调度器 tick（`update.lua`）：`WallUpdate`（RPC 队列、相机、前端）跑在真实时间上，`Update`（组件、状态图、大脑）只在未暂停时跑，`StaticUpdate`（控件动画）即使暂停也跑。

### 4.3 离开流程

`OnDespawn`（`player_common.lua:1417`）做清理（叫醒、下坐骑、掉落不可替代物、移除跟随物）。随后 `PlayerRemove`（`components/playerspawner.lua:81`）要么删除会话，要么——对于迁移——保留它。`ms_playerleft`（`player_common.lua:1195`）通知所有服务器侧监听者。

### 4.4 迁移（见下一节）

迁移是一种*特殊的*离开：玩家被序列化，C++ 把他们的连接转到目标分片，实体在那里被重建。

## 五、分片系统——Forest ↔ Caves

DST 把一个「集群」拆成若干独立的服务器进程（「分片」），每个都是自己的权威模拟，通过服务器到服务器的网络相连。Forest 是**主分片**（`TheWorld.ismastershard == true`）；Caves 是**次级分片**。

### 5.1 分片账目

- `shardnetworking.lua`——运行时分片连通性。`Shard_IsMaster()`、`Shard_IsWorldAvailable(id)`、`Shard_UpdateWorldState(world_id, state, tags, world_data, shard_name)`（由 C++ 的 `ShardManager` 在连接/断开时调用），以及 `Shard_SyncWorldSettings`，它通过 `SendRPCToShard(SHARD_RPC.SyncWorldSettings, ...)` 把主分片的世界选项推给次级分片。
- `shardindex.lua`（`ShardIndex`）——每分片的持久记录（世界选项、服务器数据、`session_id`、启用的模组），版本号 `SHARDINDEX_VERSION = 5`，通过 `TheSim:SetPersistentStringInClusterSlot(slot, shard, ...)` 保存。
- `shardsaveindex.lua`（`ShardSaveIndex`）——把集群槽位映射到分片名。默认 `SHARD_NAMES = { "Master", "Caves" }`。

### 5.2 传送门绑定

当一个分片连上时，`Shard_UpdateWorldState` 把空闲的迁移传送门绑定到它（`shardnetworking.lua:101`）：

```lua
for k, v in pairs(ShardPortals) do
    if ready and (v.components.worldmigrator.linkedWorld == nil or v.components.worldmigrator.auto == true) then
        if v.components.worldmigrator.shard_name == nil or v.components.worldmigrator.shard_name == shard_name then
            v.components.worldmigrator:ClearDisabledWithReason("MISSINGSHARD")
            v.components.worldmigrator:SetDestinationWorld(world_id)   -- Forest 传送门 → "Caves"
        end
    elseif v.components.worldmigrator.linkedWorld == world_id then
        v.components.worldmigrator:ValidateAndPushEvents()             -- Caves 传送门 → "Master"
    end
end
```

### 5.3 迁移握手

1. 玩家踏入传送门 → `WorldMigrator:Activate(doer)`（`components/worldmigrator.lua:198`）：

```lua
TheWorld:PushEvent("ms_playerdespawnandmigrate",
    { player = doer, portalid = self.id, worldid = self.linkedWorld, fxoverride = fxoverride })
```

2. `playerspawner` 捕获它（`components/playerspawner.lua:213`）→ `OnPlayerDespawnAndMigrate` → `PlayerRemove(player, false, migrationdata)`——**`deletesession = false`**，于是会话被*保留*：

```lua
-- playerspawner.lua:81
if deletesession then
    DeleteUserSession(player)
else
    player.migration = migrationdata ~= nil and {
        worldid = TheShard:GetShardId(),
        portalid = migrationdata.portalid,
        sessionid = TheWorld.meta.session_identifier,
        dest_x = migrationdata.x, dest_y = migrationdata.y, dest_z = migrationdata.z,
    } or nil
    SerializeUserSession(player)      -- 把完整存档记录送到新分片
end
player:Remove()
if migrationdata ~= nil then
    TheShard:StartMigration(migrationdata.player.userid, migrationdata.worldid)  -- C++ 重路由连接
end
```

3. **目标分片**收到序列化会话，重建玩家，`SpawnAtLocation`（`playerspawner.lua:238`）解析出口传送门：

```lua
if player.migration ~= nil then
    if player.migration.worldid ~= TheShard:GetShardId() then
        x, y, z = GetMigrationPortalLocation(player, player.migration)   -- componentutil.lua:1069
        -- 也把迁移宠物传送过去
    end
    player.migration = nil
end
player.Physics:Teleport(x, y, z)
```

不该跨分片的物品（「不可替代物」、配对的宠物）会先被丢弃（`WorldMigrator:DropThingsThatShouldNotMigrate`、`CanInventoryItemMigrate`）。两阶段的 `ShardTransactionSteps` RPC 协调跨分片的物品一致性。

**为什么这样设计：** 每个分片都是一台完整的权威服务器，所以一个分片可以是**另一台机器上的另一个进程**——Caves 可以卡顿或重启而不影响 Forest。玩家「迁移」的方式就是被序列化、被搬走、被反序列化，跟一次作用域限定到单个实体的存档/读档完全一样。

## 六、存档 / 读档

### 6.1 序列化格式

存档是 **Lua 源码文本**，由 `DataDumper`（`dumper.lua`）产出——一个打印出 `return { ... }` 代码块的 table 打印器，之后用 `RunInSandboxSafe` 重新加载。非 dev 构建会把字符串 zip + 编码（`ENCODE_SAVES = BRANCH ~= "dev"`，`main.lua`）。

`SaveGame`（`mainfunctions.lua:1068`）构建记录：

```lua
local save = {}
local savedata_entities = {}          -- 以预制体名为键
for k, v in pairs(Ents) do
    if v.persists and v.prefab ~= nil and v.Transform ~= nil
       and v.entity:GetParent() == nil and v:IsValid() then
        local record, new_references = v:GetSaveRecord()
        record.prefab = nil
        savedata_entities[v.prefab] = savedata_entities[v.prefab] or {}
        table.insert(savedata_entities[v.prefab], record)
    end
end

save.map = {
    prefab = ground.worldprefab,
    tiles  = ground.Map:GetStringEncode(),      -- 二进制地块网格
    tiledata = ground.Map:GetDataStringEncode(),
    nav    = ground.Map:GetNavStringEncode(),
    width, height = ground.Map:GetSize(),
    topology = ground.topology, generated = ground.generated,
    persistdata, new_refs = ground:GetPersistData(),
}
save.meta = ground.meta
save.mods = ModManager:GetModRecords()
save.super = WasSuUsed()
```

然后是按预制体分块、损坏守卫（NaN/inf 检测）、异步写盘：

```lua
data.ents = {}
for key, value in pairs(savedata_entities) do
    data.ents[key] = DataDumper(value, nil, not PRETTY_PRINT)
    -- 扫描 "=-1.#IND"、"=1.#QNAN"、"=1.#INF" …… 发现损坏就 error 退出
end
...
SerializeWorldSession(data, save.meta.session_identifier, callback, metadataStr)
```

`SerializeWorldSession`（`networking.lua:328`）把活交给 `TheNet:SerializeWorldSession`，后者写入集群槽位并驱动**快照/回滚**（`TheNet:IncrementSnapshot`、`TheNet:TruncateSnapshots`）——这就是 `c_rollback()` 背后的机制。

### 6.2 一个实体贡献什么

`EntityScript:GetSaveRecord`（`entityscript.lua:248`）记录 `prefab`、位置（x/z 总是记，y 只在非零时记）、移动平台的平台相对坐标、皮肤名，然后委派给 `GetPersistData`：

```lua
-- entityscript.lua:1903
function EntityScript:GetPersistData()
    local references, data = {}, {}
    for k, v in pairs(self.components) do
        if v.OnSave then
            local t, refs = v:OnSave()          -- 每个组件自己序列化自己
            if type(t) == "table" and not IsTableEmpty(t) then data[k] = t end
            if refs then for _,v1 in pairs(refs) do table.insert(references, v1) end end
        end
    end
    if self.OnSave then self.OnSave(self, data) end   -- 预制体级 OnSave
    return data, references
end
```

组件只返回「和默认值不同」的小表。`Health:OnSave`（`components/health.lua:154`）：

```lua
return { health = self.currenthealth,
         penalty = self.penalty > 0 and self.penalty or nil,
         maxhealth = self.save_maxhealth and self.maxhealth or nil }
```

跨实体链接以 **GUID 引用**保存（就是 `references` 返回值）。读档时它们通过在 `newents` 表里匹配 GUID 被解析。

### 6.3 玩家存档是独立的「用户会话」

玩家不在 `save.ents` 里。每个玩家通过 `SerializeUserSession`（`networking.lua:303`）序列化成一份按用户存储的 blob → `TheNet:SerializeUserSession(userid, data, ...)`。这正是玩家能在分片之间迁移、以及崩溃后重连的原因。`player_common.lua:1213`（`OnSave`）存储 `is_ghost`、`migration`、死亡位置/分片、wormlight 等。

### 6.4 槽位系统

`SaveIndex`（`saveindex.lua`）管理 `NUM_SAVE_SLOTS` 个槽位；每个 `NewSlotData()` 是 `{ world={}, server={}, session_id=nil, enabled_mods={} }`，`SAVEDATA_VERSION = 4`。它还会从集群目录读取用户可编辑的覆盖文件：

- `../leveldataoverride.lua`（`GetLevelDataOverride`）
- `../worldgenoverride.lua`（`GetWorldgenOverride`）——针对合法的 customize 选项做合法性检查，并覆盖到预设之上。

对集群来说，`ShardGameIndex`/`ShardSaveIndex` 把存档限定到 `(slot, shard)`，通过 `TheSim:GetPersistentStringInClusterSlot(slot, shard, filename, onload)`。

### 6.5 读档 / 重建流程

`LoadSlot`（`gamelogic.lua:1112`）根据世界文件是否存在来分支：

```lua
local function LoadSlot()
    TheFrontEnd:ClearScreens()
    if ShardGameIndex:CheckWorldFile() then
        DoLoadWorld()     -- 读档
    else
        DoGenerateWorld() -- 世界生成
    end
end
```

`DoLoadWorld` → `ShardGameIndex:GetSaveData(onload)`：

```lua
local function onload(savedata)
    UpgradeSaveFile(savedata)     -- 把存档跑到当前版本
    LoadAssets("BACKEND", savedata)
    DoInitGame(savedata, Profile)
end
```

`UpgradeSaveFile`（`gamelogic.lua:1031`）走一串带版本号的升级函数：

```lua
for i, upgrade in ipairs(require("savefileupgrades").upgrades) do
    if savedata.meta.saveversion == nil or savedata.meta.saveversion < upgrade.version then
        upgrade.fn(savedata); savedata.meta.saveversion = upgrade.version
    end
end
```

`PopulateWorld`（`gamelogic.lua:368`）重建世界：生成世界预制体、恢复地块/寻路网格（`map:SetFromString`、`map:SetNavFromString`），然后以**两趟**重建实体：

```lua
-- gamelogic.lua:623
local newents = {}
for prefab, ents in pairs(savedata.ents) do
    prefab = replace[prefab] or prefab
    for i, v in ipairs(ents) do
        v.prefab = v.prefab or prefab
        SpawnSaveRecord(v, newents)      -- 第 1 趟：实例化 + SetPersistData，按 GUID 建索引
    end
end
-- 第 2 趟：现在所有 GUID 都存在了，把跨实体引用接上
for k, v in pairs(newents) do
    v.entity:LoadPostPass(newents, v.data)
end
world:LoadPostPass(newents, savedata.map.persistdata)
```

`SpawnSaveRecord`（`mainfunctions.lua:438`）调用 `SpawnPrefab(saved.prefab, saved.skinname, ...)`，定位它（解析平台相对坐标），然后 `inst:SetPersistData(data, newents)`。组件实现 `OnLoad(data)`（例如 `Health:OnLoad` 恢复生命/惩罚并强制 HUD 刷新）和 `LoadPostPass(newents, data)` 来把存档里的 GUID 引用解析成活实体。最后 `ModManager:SetModRecords(savedata.mods)` 和 `ModManager:StartVersionChecking()` 重新绑定模组状态。

## 七、模组系统架构

文件：`mods.lua`（`ModWrangler` = `ModManager`）、`modindex.lua`（`KnownModIndex`）、`modutil.lua`（注入到每个模组的 `env` API）。

### 7.1 加载流程

`main.lua:392` 调用 `ModManager:LoadMods()`。`ModWrangler:LoadMods`（`mods.lua:470`）：

1. 在专用服务器上，`LoadServerModsFile()` 会运行 `dedicated_server_mods_setup.lua`（它调用 `ServerModSetup(product_id)` / `ServerModCollectionSetup`），然后 `TheNet:DownloadServerMods()`。
2. `KnownModIndex:GetModsToLoad(worldgen)` 返回启用的模组目录（区分 worldgen 与游戏模式）。
3. 对每个模组：加载配置选项、读取 `modinfo`，并 **`CreateEnvironment(modname, worldgen)`** 建立沙箱。
4. **按 `priority` 排序**（高的在前），让「库」模组先于依赖它的模组加载（`modPrioritySort`）。
5. 向 C++ 注册（`kleiregistermods`），把模组根目录加进 `package.path` 与 `package.assetpath`，然后对 `modworldgenmain.lua` 和 `modmain.lua` 各跑一次 `InitializeModMain`。

### 7.2 沙箱环境（`CreateEnvironment`，`mods.lua:297`）

每个模组都以 `setfenv(fn, env)` 运行，其中 `env` 是一张**全新的表**，只暴露白名单里的全局量：

```lua
local env = {
    pairs=pairs, ipairs=ipairs, print=print, math=math, table=table, type=type,
    string=string, tostring=tostring, require=require, Class=Class,
    TUNING=TUNING,
    GROUND=GROUND, WORLD_TILES=WORLD_TILES, LOCKS=LOCKS, KEYS=KEYS, LEVELTYPE=LEVELTYPE,
    GLOBAL = _G,                       -- 通向真实全局表的逃生舱
    modname = modname,
    MODROOT = MODS_ROOT..modname.."/",
}
env.env = env
env.modimport = function(modulename) ... setfenv(result, env.env); result() end   -- 模组相对的 require
modutil.InsertPostInitFunctions(env, isworldgen, isfrontend)   -- 安装整套钩子 API
```

需要核心游戏对象的模组写 `local X = GLOBAL.X` 或 `GLOBAL.require(...)`。`modimport` 让模组在留在沙箱内的前提下拉取自己的子文件。

### 7.3 `InitializeModMain`（`mods.lua:589`）

```lua
local fn = kleiloadlua(MODS_ROOT..modname.."/"..mainfile)   -- "modmain.lua"
...
local status, r = RunInEnvironment(fn, env)   -- 在沙箱里跑 modmain
if status == false then table.insert(self.failedmods, {name=modname, error=r}) end
```

### 7.4 模组预制体注册（`ModWrangler:RegisterPrefabs`，`mods.lua:677`）

模组在 `modinfo`/`env` 里列出预制体文件；wrangler 用 `LoadPrefabFile` 加载每个文件，把返回的 `Prefab` 对象收集进全局 `Prefabs` 表，并把它们包进一个合成的 `Prefab("MOD_"..modname, ...)`，好让引擎能批量加载它们的资源：


## 八、模组钩子模式——5 个具体例子

### 8.1 后初始化一个预制体（加组件 / 改数值）

```lua

    inst:AddComponent("myflavor")           -- 自定义组件
    if GLOBAL.TheWorld.ismastersim then
        inst.components.workable.workleft = 5   -- 仅服务器端调整
    end
end)
```

它在 `SpawnPrefabFromSim`（`mainfunctions.lua:368`）里、在预制体自己的 `fn` 跑完之后应用，所以此时实体已经完整构建好了。

### 8.2 后初始化*每一个*玩家（`AddPlayerPostInit`）

```lua
AddPlayerPostInit(function(inst)
    inst:AddTag("my_mod_player")
    if not GLOBAL.TheWorld.ismastersim then return end   -- 为服务器逻辑加守卫
    inst.components.health.maxhealth = inst.components.health.maxhealth + 20
end)
```

这就是 `AddPrefabPostInitAny` 按 `inst:HasTag("player")` 过滤后的结果（`modutil.lua:586`）。

### 8.3 替换/扩展一个类方法（`AddClassPostConstruct`）

```lua
AddClassPostConstruct("components/health", function(self)
    local old_DoDelta = self.DoDelta
    function self:DoDelta(delta, overtime, cause, ignore_invincible, afflicter, ignore_absorb)
        local ret = old_DoDelta(self, delta, overtime, cause, ignore_invincible, afflicter, ignore_absorb)
        if delta < 0 then self.inst:PushEvent("my_mod_took_damage", {amount = -delta}) end
        return ret
    end
end)
```

机制上，这是在包装类构造器（`modutil.lua:153`）：

```lua
local function DoAddClassPostConstruct(classdef, postfn)
    local constructor = classdef._ctor
    classdef._ctor = function(self, ...) constructor(self, ...); postfn(self, ...) end
end
```

因为它打的是**类表本身**，所以此后构造的**每一个**实例（包括别的模组构造的）都会带上你的改动。`AddGlobalClassPostConstruct(package, classname, fn)` 对全局量做同样的事。

### 8.4 加一个自定义 Action 并绑定到组件

```lua
local MYACTION = AddAction("MYMOD_PICK", "Pick", function(act)
    if act.target and act.target.components.mypickable then
        return act.target.components.mypickable:Pick(act.doer)
    end
    return false
end)
-- 让这个 action 在指向带该组件的实体时出现：
AddComponentAction("SCENE", "mypickable", function(inst, doer, actions, right)
    if inst.components.mypickable:CanBePicked(doer) then
        table.insert(actions, GLOBAL.ACTIONS.MYMOD_PICK)
    end
end)
```

`client_only_mod` 与 `all_clients_require_mod` **互斥**（在 `modindex.lua:679` 打印警告）。由此浮现出三种实用模组类型：

- **客户端模组**（`client_only_mod = true`）：UI/HUD/QoL，只在本地客户端跑，绝不发送到服务器，不得使用 netvar 或共享预制体。
- **服务器模组**（默认，`all_clients_require_mod = false`）：只在房主上跑；客户端不必拥有（它们只会看到复制过去的结果）。
- **「全员需要」模组**（`all_clients_require_mod = true`）：必须同时存在于服务器*和*每个客户端——只要模组加了 netvar、所有人都要生成的新预制体、或共享玩法逻辑，就需要这种。加入流程会自动订阅/下载它们（`DownloadMods`，`networking.lua:347`）。

分片模组：在集群上，`ShardIndex` 按分片存储 `enabled_mods`，每个分片的 `modmain` 在该分片的进程里运行，因此一个模组可以通过 `TheShard:IsMaster()` 在 Forest 与 Caves 上表现不同。

## 十、控件基类与 UI 层级

`widgets/widget.lua`。每个 `Widget` 都**创建一个真实实体**并带一个 UI 变换——UI 和玩法共用同一套实体/组件世界：

```lua
local Widget = Class(function(self, name)
	name = name or "widget"
    self.children = {}
    self.callbacks = {}
    self.name = name
    self.inst = CreateEntity()
    -- 如果你的控件效果依赖玩法状态，请用下面这两个而不是默认的，这样暂停会冻结效果。
    self.inst.DoSimPeriodicTask = self.inst.DoPeriodicTask

    self.inst:AddTag("widget"); self.inst:AddTag("UI")

    self.inst.entity:CallPrefabConstructionComplete()
    self.inst:AddComponent("uianim")   -- 补间：MoveTo/ScaleTo/RotateTo/TintTo

    self.focus_flow_args = {}
end)

function Widget:AddChild(child)
    if child.parent then child.parent.children[child] = nil end
    self.children[child] = child
    child.parent = self
    child.inst.entity:SetParent(self.inst.entity)   -- C++ 场景图父子关系
```

## 十二、输入处理

`input.lua` 定义了 `Input`（`TheInput`）。C++ 喂进原始事件；`Input` 分发给两层——先是**前端/UI**，然后才是**玩法处理器**：

```lua
-- input.lua:163
function Input:OnControl(control, digitalvalue, analogvalue)
    if (self.mouse_enabled or (control ~= CONTROL_PRIMARY and control ~= CONTROL_SECONDARY))
        and not TheFrontEnd:OnControl(control, digitalvalue) then   -- UI 先吃
        self.oncontrol:HandleEvent(control, digitalvalue, analogvalue)          -- 按 control 分发的处理器
        self.oncontrol:HandleEvent("oncontrol", control, digitalvalue, analogvalue)  -- 通用处理器
    end
end
```

处理器是 `EventProcessor` 表（`events.lua`）。注册 API（`input.lua:115-153`）：

```lua
TheInput:AddKeyDownHandler(key, fn)          -- 指定原始按键按下
TheInput:AddKeyUpHandler(key, fn)
TheInput:AddKeyHandler(fn)                    -- 所有按键 (key, down)
TheInput:AddControlHandler(control, fn)       -- 一个抽象 control（CONTROL_MAP, ...）
TheInput:AddGeneralControlHandler(fn)         -- 所有 control (control, value)
TheInput:AddMouseButtonHandler(fn)
TheInput:AddMoveHandler(fn)
TheInput:AddTextInputHandler(fn)
TheInput:AddGestureHandler(gesture, fn)
```

**按键 vs Control 抽象层。** 原始按键（`KEY_TAB=9`、`KEY_F1=282`……在 `constants.lua`）由 C++（`DontStarveInputHandler`）映射到抽象 **control**（`CONTROL_PRIMARY=0`、`CONTROL_SECONDARY`、`CONTROL_ATTACK`、`CONTROL_MAP`、`CONTROL_PAUSE`、`CONTROL_INV_1..15`……在 `constants.lua:109` 起）。游戏代码绑定的是 *control*，所以重绑按键/手柄是透明的。`debugkeys.lua` 展示了原始绑定表的写法：

```lua
GLOBAL_KEY_BINDINGS = {
    { binding = { key = KEY_F1 },              fn = function() ... end },
    { binding = { key = KEY_HOME, CTRL = true }, fn = ... },
    { binding = { key = KEY_A, CTRL = true },  fn = ... },
}
```
它的分发器会检查 `TheInput:IsKeyDown(KEY_CTRL/KEY_SHIFT/KEY_ALT)` 来处理修饰键。

**玩家控制器**注册一个通用处理器，把 control 转换成缓存动作和 RPC（`components/playercontroller.lua:319`）：

```lua
self.handler = TheInput:AddGeneralControlHandler(function(control, value) self:OnControl(control, value) end)
```
之后才会 `SendRPCToServer(RPC.LeftClick/RightClick/DirectWalking/AttackButton/...)`。在房主玩家（主模拟）上，同一个处理器直接驱动模拟而不是发 RPC。

**焦点 vs 玩法。** `TheFrontEnd:OnControl`（`frontend.lua:419`）把 `CONTROL_PRIMARY` 映射到 `CONTROL_ACCEPT` 并喂给栈顶屏幕的控件树；如果任何控件消费了它，玩法处理器就被跳过。这就是为什么打开一个菜单能干净地禁掉世界交互。

### 13.3 路径解析

`resolvefilepath(filepath, force_path_search, search_first_path)`（`util.lua:636`，带记忆化）→ `softresolvefilepath_internal`（`util.lua:585`）：

```lua
-- 主机平台上路径已经是绝对的
if IsConsole() and not force_path_search then return filepath end
filepath = string.gsub(filepath, "^/", "")
if search_first_path then                     -- 模组资源的快路径
    local filename = search_first_path..filepath
    if kleifileexists(filename) then return filename end
end
local searchpaths = package.assetpath         -- 先模组，再 data（main.lua 建立）
for i, pathdata in ipairs_reverse(searchpaths) do
    local filename = string.gsub(pathdata.path..filepath, "\\", "/")
    if kleifileexists(filename, pathdata.manifest, filepath) then return filename end
end
if kleifileexists(filepath) then return filepath end   -- 已经是解析过的绝对路径
return nil
```

`package.assetpath` 在 `LoadMods`（`mods.lua:576`）里逐模组扩展：
`table.insert(package.assetpath, {path = MODS_ROOT..mod.modname.."\\", manifest = manifest})`。这就是一个模组的 `images/foo.xml` 能在不与本体游戏冲突的情况下被解析到的方式，也是**模组可以覆盖本体资源**的原因（模组路径先被搜索）。`resolvefilepath` 在失败时断言；`softresolvefilepath` 返回 nil（用于测试可选资源，例如 `modindex.lua:539` 处的模组图标）。

## 十四、构建联机生存游戏的 15 条关键模式（附「为什么」）

1. **服务器权威内核，单套代码库，角色标志驱动。** 在服务器和客户端跑**完全相同**的 Lua，在 `TheWorld.ismastersim` / `TheNet:GetIsServer()` 上分支。*为什么：* 这消除了客户端/服务器分歧类 bug，让房主玩家就是「一个顺便还渲染的普通服务器」，并让模组保持简单（只有一套脚本）。

2. **只发意图 RPC，绝不让客户端改状态。** 客户端发送*它想要什么*（`RPC.LeftClick` 带一个动作代码 + 点位），服务器校验并施加。*为什么：* 防作弊；服务器是伤害/物品栏/生成的唯一真相来源。

3. **对每一条发往服务器的消息做校验 + 限流。** 每个 RPC 重新检查参数类型与范围、拒绝超距点位、丢弃超出每刻预算的发送者。*为什么：* 网络是敌对的；永远不要信任载荷。发出 `invalidrpc` 事件也让反作弊模组得以响应。

4. **按数据大小选类型化的网络变量。** 7 状态枚举用 `net_tinybyte`（3 位），0–255 用 `net_byte`，字符串 ID 用 `net_hash`。提供 `set`/`value`/`set_local` 与脏事件。*为什么：* 生存游戏有成百上千个实体；位级类型化和 `set_local`（客户端本地平滑外推，无需往返）让带宽可控。

5. **组件「副本」+ 每玩家「classified」实体。** 给客户端提供服务器组件的只读镜像，并把私有的每玩家状态走一个只复制给一个客户端的隐藏实体。*为什么：* API 对称干净（`replica.health` vs `components.health`），而且隐私可控（你的理智值不会广播给所有人）。

6. **移动预测 + 服务器纠正。** 让客户端在 RPC 还在路上时就移动化身，然后从复制来的变换里纠正。*为什么：* 掩盖延迟；对动作生存游戏的响应手感是必需的。

7. **读档时两趟实体重建。** 先实例化所有实体（按 GUID 建索引），再用 `LoadPostPass` 解析交叉引用。*为什么：* 存档数据里含有指向第一趟时尚不存在的实体的 GUID 链接。

8. **组件各自负责序列化。** 每个组件实现 `OnSave`/`OnLoad`/`LoadPostPass`；实体只做聚合，且只存与默认值不同的差量。*为什么：* 模块化，且模组可以给任何组件加持久化而不用碰核心存档代码。

9. **按预制体分块存档 + 损坏守卫 + 异步写 + 快照。** 把实体 blob 按预制体切开、扫描 NaN/inf、把写盘挪出主线程、保留快照以支持回滚。*为什么：* 大世界存档快且安全，回滚（`c_rollback`）也变成顺手的事。

10. **沙箱模组环境 + 延迟钩子。** 给每个模组一张干净的 `env`（精选全局量 + `GLOBAL` 逃生舱），把钩子存成数据，在精确的引擎时刻回放（`SpawnPrefabFromSim`、`AddComponent`、状态图构建）。*为什么：* 隔离防止模组互相踩踏或踩到内核；延迟回放让模组可以安全地扩展那些加载时还不存在的东西。

11. **包装类构造器以实现「修补任意类」。** `AddClassPostConstruct` 重新绑定 `_ctor`，让所有未来实例都带上改动；方法包装（`local old = self.DoDelta; self.DoDelta = ...`）实现非破坏性覆写。*为什么：* 这是最强大也最常用的模组原语——不改源码就能深度扩展。

12. **分片世界 + 实体序列化迁移。** 每个区域都是一台完整的权威服务器；玩家通过「被序列化、连接被重路由、在链接传送门处被反序列化」跨界。*为什么：* 水平扩展与故障隔离——一个分片打嗝或重置不会拖垮整个集群。

13. **建立在与玩法同一套实体/控件系统之上的屏幕栈前端。** UI = 由 UI 实体支撑的控件；`PushScreen`/`PopScreen` 带焦点记忆；输入先走 UI 再走玩法。*为什么：* 单一渲染/场景图、焦点与手柄导航一致、菜单自动暂停世界交互。

14. **抽象 Control 之上的原始按键。** 玩法绑定 `CONTROL_*`，让 C++ 映射按键/手柄；前端把 `CONTROL_PRIMARY` 映射到 `CONTROL_ACCEPT`。*为什么：* 免费的重绑定、手柄支持，以及干净的 UI vs 玩法输入仲裁。

15. **资源声明与预制体同处 + 搜索路径解析。** 每个预制体列出自己的资源；`resolvefilepath` 先搜模组再搜 data。*为什么：* 自动流式加载/预加载，且模组只要附带同名文件就能覆盖任何本体资源。

## 【深度扩写】一、实体状态同步的可运行实现

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原报告只说了「netvar 会同步」「脏事件会触发」，没有给出协议设计层面的可运行方案。这一节把 DST 的做法拆成一套可以照抄的同步管线。

### 1.1 DST 的同步模型：引擎持有真值，Lua 只声明字段

关键前提：**Lua 侧没有任何序列化代码**。`net_bool(...)`、`net_byte(...)` 这些不是 Lua 函数，而是 **C++ 引擎注入的全局构造器**。它们返回一个 netvar 对象，这个对象上的 `:set()` / `:value()` / `:set_local()` 三个方法最终调用到 `TheSim` 的底层网络写入。整个状态同步由 C++ 完成，Lua 只负责**声明字段**与**响应脏事件**。

这一点决定了你仿写时的架构选择：

| 方案 | 谁持有真值 | 带宽效率 | 实现难度 |
|---|---|---|---|
| 状态由 Lua 每帧算好、整表序列化下发（DST 早期思路） | 脚本层 | 极差（每实体每帧一次） | 低 |
| **netvar 声明式增量同步（DST）** | 引擎层 | 好（仅脏字段） | 中（需要引擎侧支持） |
| 完整状态复制 + 客户端插值（Unity 传统做法） | 引擎层 | 差（每实体持续流） | 低 |

DST 选的是中间那条。伪代码表达它的完整形状：

```c
// ---- 引擎侧伪代码：NetVar 声明 ----
// GUID + 字段路径 "health.currenthealth" + 脏事件名 "healthdirty"
// 三元组在服务器与客户端上以相同顺序注册成一张全局表。
void NetVar_Declare(int guid, const char* path, const char* dirtyevent, NetVarType type);

// 服务器写入：置脏位，排队等本刻末尾统一 flush
void NetVar_Set(NetVarRef* nv, Value v) {
    if (nv->cached == v) return;        // 值没变就不产生任何流量
    nv->cached = v;
    nv->dirtybit = 1;
    PushEvent(nv->owner, nv->dirtyevent);   // 脏事件在服务器本地也触发
}

// 每刻末：把本刻所有脏 netvar 按实体分组，打包成 [entity_guid][field_index][value]
// 只发给对该实体「可见」的客户端（见 1.4 兴趣管理）
void FlushDirtyNetVars() {
    for (Entity* e : dirty_entities) {
        ByteBuffer buf;
        buf.WriteEntityID(e->network_id);
        for (NetVarRef* nv : e->dirty_nvars) {
            buf.WriteBitField(nv->bit_width);   // 1/3/6/8/16/32 位
            buf.WriteValue(nv->type, nv->cached);
        }
        SendToSubscribers(e, buf);
    }
}

// 客户端反序列化：按字段路径查表写入本地缓存 + 触发脏事件（事件早于 Lua update 触发）
```

`netvars.lua:34-37` 的注释确认了两个关键时序事实，值得原样抄进你自己的设计文档：

```
* Server and clients may register different listeners for dirty events.
* netvar dirty events are triggered before lua update.
```

「脏事件早于 update 触发」意味着：**你在脏事件回调里读到的其他 netvar 已经是本刻新值**，不会出现「半新半旧」的读状态。这是自研引擎里最容易搞错的一点。

### 1.2 脏标记（dirty bit）的两级设计

DST 的脏标记有**两层**，原报告没有点破：

**第一层：字段级脏标记**（Lua 可见）。`netvar:set(x)` 内部比较旧值，值真变了才置脏。这是 `netvars.lua:44-47` 承诺的语义：*"Dirty event is triggered on server and clients (only if value has actually changed)"*。

**第二层：强制脏**（Lua 主动触发）。`prefabs/player_classified.lua:16` 有一个工具函数专门做这件事：

```lua
local function SetDirty(netvar, val)
    --Forces a netvar to be dirty regardless of value
    netvar:set_local(val)
    netvar:set(val)
end
```

先 `set_local` 再 `set` 的组合拳，绕过了「值相同就不置脏」的短路。它的用途是**把状态变更变成一个事件**（`healthdirty` 的监听者会重新计算 HUD），而不只是传递数据。文件里大量注释确认了这个意图：

```lua
--V2C: Don't clear: it's redundant as player_classified shouldn't
--parent.player_classified.ishealthpulseup:set_local(false)
```

**陷阱**：`set_local` 会**污染**下一次 `set` 的脏判定。`netvars.lua:55-57` 明确警告：

> *"NOTE: this results in the next server set(x) to be dirty regardless of whether the value changed, since we assume the client may have set_local(x) to any arbitrary value."*

也就是说：**你只要在客户端调用过一次 `set_local`，该字段的带宽开销就会退化成「每次服务器 set 都发」**。正确用法是严格限定 `set_local` 只用于「客户端本来就能自己算出来」的值（比如平滑计时器），用完最好配合一次强制 `set` 归位。

### 1.3 增量同步：快照 + 脏量的组合

DST **不是**纯增量，也不是纯快照，而是「**初次全量快照 + 之后纯增量**」：

```
[实体首次进入客户端视野]
   ├─ 服务器发：实体元信息（network_id、prefab 哈希、初始 Transform、初始 tag 集合）
   ├─ 服务器发：全部 netvar 当前值（全量快照，一次性）
   └─ 服务器发：全部 REPLICATABLE_COMPONENTS 对应的副本组件集合

[此后每一刻]
   └─ 服务器只发：脏 netvar（增量），且仅发给对该实体可见的客户端
```

这个设计有两个隐含约束，仿写时必须正面处理：

**约束一：客户端首次见到实体时必须能拿到全量。** 这就是为什么 `AddNetwork()` 必须在 `SetPristine()` **之前**调用——`SetPristine()` 是给网络同步状态拍快照的时刻。DST 里 1905 处 `entity:AddNetwork()` 全部遵守这个顺序，典型写法见 `prefabs/player_classified.lua`：

```lua
inst.entity:AddNetwork()
...  -- 所有 netvar 声明
inst:DoStaticTaskInTime(0, RegisterNetListeners)   -- 延迟注册脏事件监听器
inst.entity:SetPristine()
```

注意 `RegisterNetListeners` 是**延迟到 0 刻**才执行的，文件内注释说明原因是 *"Delay net listeners until after initial values are deserialized"*。这是必需的：初始快照里的脏事件风暴会和监听器注册打架。

**约束二：字段顺序必须两侧一致。** 这正是 `netvars.lua` 那段警告的根因——C++ 侧用「按声明顺序的第 N 个字段」作为 wire format 的隐式索引。DST 靠「服务器和客户端跑同一套脚本」来保证一致，一旦有模组单边启用 netvar，索引就会错位，反序列化直接失败。

**如果你的引擎不能保证两侧跑同一套脚本**，就必须引入**显式 schema**：给每个 netvar 一个稳定的字符串 ID 或哈希，wire format 里带 ID 而非序号。代价是每字段多 2-4 字节，收益是彻底摆脱顺序耦合。**这是移植时最该改的一处**（详见移植陷阱一节）。

### 1.4 兴趣管理（interest management）

原报告没有提到兴趣管理在 Lua 侧的样子，这里补上。DST 的兴趣管理**完全在 C++ 侧**，Lua 只提供了一个「兴趣中心点」的输入：

```lua
-- update.lua:46-51（WallUpdate 内，每帧）
if TheFocalPoint ~= nil then
    TheSim:SetActiveAreaCenterpoint(TheFocalPoint.Transform:GetWorldPosition())
else
    TheSim:SetActiveAreaCenterpoint(0, 0, 0)
end
```

`TheFocalPoint` 通常是本地玩家的化身。这意味着：**只要实体进入以本地玩家为中心的某个半径，就会被自动复制进来**。实体首次进入视野时触发 `EntityScript:ReplicateEntity`（`entityreplica.lua:74`），其注释直白地说明了这个时机：

```lua
--Triggered on clients immediately after initial deserialization of tags from construction
function EntityScript:ReplicateEntity()
```

对应的 Lua 侧证据链是 `prefabs/player_common.lua:844-849` 的注释——`playerentered` 事件在客户端的语义就是「有玩家实体进入了你的网络视野」：

```lua
    -- "playerentered" is available on both server and client.
    -- - On clients, this is pushed whenever a player entity is added
    --   locally because it has come into range of your network view.
```

**DST 的兴趣管理其实非常粗粒度**（单一中心点 + 半径），这是「小规模生存游戏 + 开放地形」的合理取舍：玩家数量少（≤8），地图虽大但实体在视野外不需要精确剔除。**如果你要扩到 100 人 MMO 或大规模战场，必须自己实现分层方案**：

```
粗粒度（DST 现状）：
    单一中心点 → 单一半径

分层（大规模场景的标准做法）：
    L1 空间网格：世界切成 cell，客户端订阅自己所在 cell + 8 邻域
    L2 静态分级：静态实体（建筑/地形）走独立的低频通道，不参与动态剔除
    L3 显式订阅：关键实体（BOSS、任务目标）无视距离强制复制给所有人
    L4 优先级队列：带宽紧张时先丢 L4，再丢 L3，最后收缩 L1 半径
```

兴趣管理的数据结构骨架（伪代码）：

```lua
-- 服务器每刻维护
InterestManager = {
  subscribers = { [userid] = { cells = {...}, radius = 64 } },
  cell_entities = { [cellkey] = { [network_id] = true } },
}
-- 实体进入新 cell 时，计算「新增订阅者集合」，对新人发全量快照，对老人无操作
-- 实体离开 cell 时，把实体标记为「无订阅者」，此时它变成休眠实体（OnEntitySleep）
```

### 1.5 存档快照（snapshot）与回滚

DST 的 `TheNet:IncrementSnapshot` / `TheNet:TruncateSnapshots` 驱动的是**运行时状态快照**，服务于 `c_rollback()`（管理员指令）和崩溃恢复。核心生命周期在 `mainfunctions.lua` 的 `SaveGame` 回调里：

```lua
local function callback()
    if isshutdown or #AllPlayers <= 0 then
        TheNet:TruncateSnapshots(save.meta.session_identifier)
    end
    TheNet:IncrementSnapshot()
    ...
end
```

以及读档侧（`gamelogic.lua:970-973`）：

```lua
if TheNet:GetIsServer() then
    TheNet:TruncateSnapshots(savedata.meta.session_identifier)
    local players_to_restore = savedata.snapshot ~= nil and savedata.snapshot.players or nil
```

以及 `mainfunctions.lua:1162-1168` 保存的快照玩家名单：

```lua
if not isshutdown and #AllPlayers > 0 then
    save.snapshot = { players = {} }
end
for i, player in ipairs(AllPlayers) do
    if player.userid ~= nil and userid:len() > 0 then
        if save.snapshot ~= nil then
            table.insert(save.snapshot.players, player.userid)
        end
        SerializeUserSession(player)
    end
end
```

**仿写要点**：快照保留策略是「**世界存档写完且所有玩家离线时截断历史快照**」。这样磁盘上始终有一份「玩家刚离线时的完整世界状态」，`c_rollback` 只需回到那个点，而不必保留每刻的历史。这是「省磁盘」与「能回滚」的折中，值得直接采用。

### 1.6 协议设计的具体方案（可直接落地的最小实现）

综合上面几点，一套可运行的最小网络协议：

```
消息类型：
  MSG_JOIN_REQ   { client_version, player_name, mod_hash, last_seen_snapshot_id }
  MSG_JOIN_ACC   { your_net_id, world_time, snapshot_id, player_net_id }
  MSG_SPAWN      { net_id, prefab_hash, x,y,z, rotation, tags[], netvars[] }   -- 全量
  MSG_DESPAWN    { net_id, reason }                                            -- 离开视野
  MSG_DIRTY      { net_id, [(field_id, bit_width, value_bytes)]... }           -- 增量
  MSG_RPC        { code, [args...] }
  MSG_SNAPSHOT   { snapshot_id, world_time }

编码：
  - field_id 显式（2 字节），不依赖声明顺序      ← 对原设计的改进
  - netvar 值按声明位宽打包：1/3/6/8/16/32 位
  - net_entity 引用存 2 字节 net_id，不存 GUID 字符串
  - MSG_DIRTY 单条消息承载同一实体同刻的多个字段（批量打包，摊薄 per-message 开销）

可靠 vs 不可靠：
  MSG_RPC / MSG_SPAWN / MSG_DESPAWN  → 可靠有序（TCP 式或带 ACK 的 UDP）
  MSG_DIRTY                         → 不可靠（UDP 乱序丢弃即可，丢失一拍的脏包不值得重传）
```

**为什么 netvar 引用要存数字 net_id 而不是 GUID**：GUID 在 DST 里是形如 `1234567890` 的长整数（`inst.GUID`），直接上 wire 太宽。引擎内部维护一张 GUID→net_id 的表，net_id 随实体生命周期复用。仿写时建议用 16 位递增 ID + 连接期唯一性保证。

## 【深度扩写】二、权威服务器模型：为什么必须由服务器裁决

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

### 2.1 为什么「服务器说了算」不是可选项

DST 里最直白的证据是 `SaveGame` 的守卫（`mainfunctions.lua:1069`）——客户端连存档都写不了。但真正的理由要更深一层：**客户端上跑的是玩家自己机器上的代码**。

```
若允许客户端裁决伤害：
  客户端 A 声称「我用剑砍了 B，造成 37 伤害」 → 服务器照单全收
  → 改一行客户端代码就能秒杀全服

若允许客户端裁决生成：
  客户端声称「这里应该生成一只猎犬」 → 服务器生成
  → 客户端可以凭空造出无限资源

若允许客户端裁决物品栏：
  客户端声称「我有 999 个铱矿石」→ 服务器接受
  → 经济系统崩盘

DST 的选择：客户端只发「意图」，所有裁决在服务器
  SendRPCToServer(RPC.LeftClick, act.action.code, pos_x, pos_z, mouseover, ...)
  → 服务器重新校验参数类型、校验点位距离（IsPointInRange）、校验组件状态
  → 服务器执行 OnRemoteLeftClick
```

`IsPointInRange`（`networkclientrpc.lua:43`）是一个很值得学的防御细节：

```lua
local function IsPointInRange(player, x, z)
    local px, py, pz = player.Transform:GetWorldPosition()
    return distsq(x, z, px, pz) <= 4096
end
```

**4096 = 64²**。它挡住的是一类具体攻击：客户端发一个坐标在地图极远处的 `LeftClick`，如果服务器直接拿去查找目标，可能会命中本不该命中的东西（或者触发远处的连锁逻辑）。**任何「客户端提供了世界坐标」的 RPC 都需要这一层检查**。

### 2.2 参数校验的正确姿势：白名单 + 联合断言

`LeftClick` 的校验写法（`networkclientrpc.lua:61-76`）值得原样学习。它的形态是「**要么全 nil（取消操作），要么全部合法**」，用 `and` 串成一条长链：

```lua
if not ( (action == nil and x == nil and ...)        -- 分支 A：全空 = 取消
      or (checknumber(action) and checknumber(x) and checknumber(z)
          and optentity(target) and optbool(isreleased) and ...) )   -- 分支 B：全对
then
    printinvalid("LeftClick", player)
    return
end
```

`networkclientrpc.lua:3-14` 定义了这一整套校验原语，注意它们是**全局的，模组也能用**：

```lua
function checkbool(val) return val == nil or type(val) == "boolean" end
function checknumber(val) return type(val) == "number" end
function checkuint(val) return type(val) == "number" and tostring(val):find("%D") == nil end
function checkstring(val) return type(val) == "string" end
function checkentity(val) return type(val) == "table" end
optbool = checkbool
function optnumber(val) return val == nil or type(val) == "number" end
function optuint(val) return val == nil or (type(val) == "number" and tostring(val):find("%D") == nil) end
function optstring(val) return val == nil or type(val) == "string" end
function optentity(val) return val == nil or type(val) == "table" end
```

注释里还给了一条重要的实战经验：

```lua
--NOTE: checkuint since non-integer inventory slots are not handled gracefully
--      checknumber is generally enough for other cases
```

**这是「用最弱的校验换取兼容性」**——物品栏槽位本该用 `checkuint`，但因为非整数槽位没有被优雅处理，改用宽松的 `checknumber` 保证不崩。**这类「刻意放松」必须在注释里写清楚**，否则后来者会以为它是 bug 并"修好"它。

`checkentity` 只检查 `type(val) == "table"`，这是**必要但不充分**的——它无法防止客户端伪造一个长得像实体的 table。真正的防线是：**RPC 处理器绝不能信任 `target` 参数指向的对象**，必须重新从服务器自己的世界里按 ID 查找。**推断**：DST 在此处的安全性依赖 C++ 侧对实体引用的反序列化（收到的引用只会被映射为服务器上真实存在的实体，无法凭空构造）。

`printinvalid` 里的一个细节同样值得学（`networkclientrpc.lua:18-29`，其中事件推送在 `:22`）：

```lua
local function printinvalid(rpcname, player)
    print(string.format("Invalid %s RPC from (%s) %s", rpcname, player.userid or "", player.name or ""))
    --This event is for MODs that want to handle players sending invalid rpcs
    TheWorld:PushEvent("invalidrpc", { player = player, rpcname = rpcname })
    if BRANCH == "dev" then
        --Internal testing
        assert(false, string.format("Invalid %s RPC from (%s) %s", rpcname, player.userid or "", player.name or ""))
    end
end
```

它做了三件事：① 打日志；② **推事件给反作弊模组**（这是给第三方工具的正式接口）；③ 在 dev 分支直接 assert 崩溃（便于内测时立刻发现客户端 bug）。生产环境不崩、但留下证据链——这是成熟的处理方式。

### 2.3 限流：按发送者、按逻辑刻，且可被模组"买通"

限流实现在 `HandleRPC`（`networkclientrpc.lua:1675-1703`），其额度模型是：

```lua
local RPC_QUEUE_RATE_LIMIT = 20          -- Per logic tick.
local RPC_QUEUE_RATE_LIMIT_PER_MOD = 5   -- +this for every mod RPC added.
```

两个设计细节：

**其一：额度是「入队」额度，不是「执行」额度。** `RPC_Queue_Limiter[sender]` 在 `HandleRPC` 里自增，在 `HandleRPCQueue`（`networkclientrpc.lua:1724`）排空时自减：

```lua
local limit = (RPC_Queue_Limiter[sender] or 1) - 1
if limit == 0 then
    RPC_Queue_Limiter[sender] = nil      -- 归零后清表，避免无界增长
    RPC_Queue_Warned[sender] = nil
else
    RPC_Queue_Limiter[sender] = limit
end
```

清表这一行是**防内存泄漏的关键**——一个攻击者可以用无限多个伪造 sender 把这张表撑爆。仿写时务必照做。

**其二：模组可以增加全局额度。** `AddModRPCHandler`（`networkclientrpc.lua:1848`）执行：

```lua
RPC_QUEUE_RATE_LIMIT = RPC_QUEUE_RATE_LIMIT + RPC_QUEUE_RATE_LIMIT_PER_MOD
```

这**没有上限**。一个恶意模组可以注册上万个 RPC 处理器，把全局限流抬到天上，让真正的攻击流量畅通无阻。**这是原版设计的一个真实缺口**，你的引擎里应该改成：`每模组独立配额 + 全局硬上限`（下面给出方案）。

**其三：告警只打一次。** `RPC_Queue_Warned[sender]` 保证同一个发送者超限只打印一次日志——否则一个持续攻击的客户端能把服务器控制台刷爆。**推断**：这也意味着日志本身不会告诉你「攻击持续了多久」，生产环境应把这张表接入监控而非只看日志。

### 2.4 同刻重入保护：`RPC_Timeline`

这是原报告完全没提、但极其重要的一条规则。`HandleRPCQueue`（`networkclientrpc.lua:1741-1750`）：

```lua
elseif RPC_Timeline[sender] == nil or RPC_Timeline[sender] == tick then
    -- Invoke.
    if TheNet:CallRPC(fn, sender, data) then
        RPC_Timeline[sender] = tick
    end
else
    -- Pending.
    table.insert(RPC_Queue_new, rpcdata)
    RPC_Timeline[sender] = 0
end
```

含义：**同一个发送者的 RPC，在同一逻辑刻内最多执行一个**。如果本刻已经执行过这个发送者的一条 RPC，后续的会被重新入队（`Pending`）推迟到下一刻。

为什么要这样？因为 RPC 处理器会改世界状态（移动、受伤、生成）。如果同一刻内执行 20 条来自同一客户端的移动 RPC，玩家会在一帧内「瞬移」20 次距离，并且这 20 次状态变更会在同一次网络 flush 里产生 20 组脏数据。**限制成每刻一条，等于把客户端输入天然降采样到模拟频率**——客户端发得再快也不会获得超越模拟的分辨率。

而 `TickRPCQueue`（`networkclientrpc.lua:1798`，由 `update.lua:182` 的 `StaticUpdate` 调用）每刻重置时间线：

```lua
function TickRPCQueue()
    RPC_Timeline = {}
    RPC_Client_Timeline = nil
    RPC_Shard_Timeline = {}
end
```

**分片方向还有一个更硬的限制**（`networkclientrpc.lua:1786-1788`）：

```lua
if RPC_Shard_Queue[RPC_Shard_Queue_len + 1] then
    print("Shard RPC invoked another RPC in the same frame and will be dropped! Delay shard RPCs sending more shard RPCs to itself by a frame minimally or try handling shard RPCs in a different way.")
end
```

**同一个分片在一帧内发出的第二条分片 RPC 会被直接丢弃**。原因是分片 RPC 可能触发迁移，进而在目标分片引起连锁同步，同帧递归会造成状态不一致。**这是原版用"丢弃"换正确性的地方**——你的引擎里做同类设计时，要确保「丢弃」这件事对发送方可见（至少要有统计），否则会出现难以复现的数据不一致。

### 2.5 客户端预测 + 服务器纠正：完整链路

DST 的移动预测是一条完整的客户端预测 → 服务器裁决 → 客户端纠正链。原报告只说了"客户端乐观移动"，下面展开。

**第一步：客户端挂载预测 locomotor。** `prefabs/player_common.lua:877`：


注意三个要点：
1. **locomotor 组件只在客户端挂**（`not TheWorld.ismastersim`）。服务器不挂，所以客户端本地移动**不会**驱动服务器世界。
2. **必须先建 locomotor 再建状态图**（注释明写），因为状态图会查询 locomotor。
3. **`DoTaskInTime(0, ...)` 延迟发第一个 RPC**——生成那一帧引擎不允许发 RPC。这是个真实踩过的坑，注释里留着。

**第二步：客户端每刻把「预测位置」当目标发给服务器。** `PlayerController:DoPredictWalking`（`components/playercontroller.lua:4003`）的客户端分支：

`RemotePredictWalking`（`playercontroller.lua:3922`）最终发出：

**第三步：服务器收到后驱动权威 locomotor，并把客户端意图编码进 `remote_vector`。** `OnRemotePredictWalking`（`playercontroller.lua:3785`）里：

`remote_vector.y` 被**复用成一个标签字段**（`playercontroller.lua:3694` 注释：`--remote_vector.y is used as a flag for stop/direct/drag walking`）：

| 1 | 直接行走 | `GetRemotePredictDirectVector` |
| 2 | 拖拽行走 | `GetRemotePredictDragVector` |
| 3 | 预测行走（客户端认为是 direct） | `GetRemotePredictVector` |

**这是一个非常值得学的省带宽技巧**：用浮点数的 `y` 分量当枚举，省掉一个独立的整数字段。DST 还在代码里到处用 `pt.y == 3` / `pt.y == 4` 判断（`playercontroller.lua:4050-4075`）。**但它同时是个陷阱**——`y` 还要承载真实的预测高度（`net_float` 的第三个用途），所以这套编码只在「没有平台相对高度」时成立。**推断**：这是历史演进的产物，现代引擎里应该把 flag 和坐标拆成两个字段。

**第四步：服务器按客户端目标位置驱动 locomotor，并处理纠正。** 同函数的服务器分支（`playercontroller.lua:4013-4085`）：


**`pt.y == 5` 是一个额外的语义**（注意它和上面 flag 表里的 3/4/5 不同——5 表示「正在执行动作，忽略预测移动」）。服务器在玩家做动作（挖矿、攻击、开门）期间**完全忽略移动预测**，因为动作期间的位置由动作决定。

**回滚带（rubber band）纠正**（`playercontroller.lua:4075-4085`）：

```lua
--Detect stop, teleport, or prediction errors
--Cancel the cached prediction vector and force resync if necessary
if distancetotargetsq <= stopdistancesq then
    self.remote_vector.y = 0
    self.remote_predict_stop_tick = GetTick()
elseif distancetotargetsq > RUBBER_BAND_DISTANCE_SQ then
    self.remote_vector.y = 0
    --V2C: don't override rubberband, otherwise server teleports will also get stomped by client prediction
    self.inst.Physics:Teleport(self.inst.Transform:GetWorldPosition())
end
```

**`RUBBER_BAND_DISTANCE_SQ` 是「预测误差容忍上限」**：当服务器位置与客户端预测目标点距离超过它时，判定为预测错误，**放弃预测、清空 remote_vector，让服务器权威位置胜出**。参数定义在 `playercontroller.lua:10`：

```lua
local RUBBER_BAND_DISTANCE_SQ = RUBBER_BAND_DISTANCE * RUBBER_BAND_DISTANCE
local PREDICT_STOP_ERROR_DISTANCE_SQ = 0.25
```

**代码里那条注释是本节最重要的经验**：

> `V2C: don't override rubberband, otherwise server teleports will also get stomped by client prediction`

翻译过来是一个经典陷阱：**如果纠正逻辑足够"聪明"，它会试图用客户端预测去"修正"服务器传送**——服务器把玩家传送走（传送门、指令、剧情），客户端却因为还有预测目标点而把玩家拉回去，导致传送被撤销。**解决办法是：回滚带必须是无条件的、优先于一切其他纠正逻辑的最高优先级通道。**

`remote_authority` 那个分支还有一层考虑（`playercontroller.lua:4036`）：只有当**服务器确实认为该玩家处于自己管辖的移动模式**（`remote_authority`）且方向偏差超过 90° 时才做瞬移纠正，否则走温和的 `SetMoveDir`。注释写着 `FIXME(JBK): Boat handling.` 和 `FIXED(V2C): Remote predict position now resolves platform relative positions from clients.` ——**推测**：船只（Boat）场景下的预测纠正至今仍有已知问题（FIXME 标记未被清除），这提示我们**移动预测在载具/平台上是出了名难做的部分**。

### 3.2 依赖解析

DST 的依赖系统分「正向依赖」和「反向依赖（被依赖计数）」两套。

**正向依赖解析**（`modindex.lua:571-589`，在 `LoadModInfo` 里）：


`BuildModPriorityList`（`modindex.lua:492-508`）实现了**多版本候选的优先级排序**：

```lua
local function BuildModPriorityList(self, v, is_workshop)
    local workshop = v.workshop
	local mods = {}
    for modname, isfancy in pairs(v) do
        if modname ~= "workshop" then
            modname = not isfancy and modname or self:GetModActualName(modname)
            if self:DoesModExistAnyVersion(modname) then
                table.insert(mods, modname)
            end
        end
	end
	if workshop then
		--prioritize workshop mods if the mod is_workshop, otherwise its the last resort
		table.insert(mods, is_workshop and 1 or #mods+1, workshop)
	end
	return mods
end
```

`mod_dependencies` 的语法是一个「候选版本列表」表：本地已启用的版本排最前，创意工坊版本排中间/末尾。**这解决了"用户装了 2.0 但依赖方要求 1.5"这类真实问题**——不硬失败，而是给出一个有序候选集让 UI 去提示。

**递归依赖解析与环检测**（`modindex.lua:1143-1167`）：

```lua
function ModIndex:GetModDependencies(modname, recursive, rec_deps)
	...
	local dependencies = self.savedata.known_mods[modname] and self.savedata.known_mods[modname].dependencies
	if not dependencies then return end
	local deps = rec_deps or {}
	local new_deps = {}
	--add our modname to the deps to prevent circular dependency loops
	deps[modname] = true
	for i, mods_dep in ipairs(dependencies) do
		if not IsModAlreadyDepended(deps, mods_dep) then
			deps[mods_dep[1]] = true
			new_deps[mods_dep[1]] = true
		end
	end
	if recursive then
		for _modname, _ in pairs(new_deps) do
			self:GetModDependencies(_modname, recursive, deps)
		end
	end
	if rec_deps == nil then
		deps[modname] = nil          -- 顶层调用时把自己摘掉
		return table.getkeys(deps)
	end
end
```

**环检测靠「把当前 modname 先塞进结果集」**——如果递归时再次遇到它，说明成环，直接跳过（注释写得很直白：`--add our modname to the deps to prevent circular dependency loops`）。这是一个廉价但有效的做法。**推断**：这种检测不会报出「哪里成环」，只会静默截断；用户会看到"依赖没生效"而不是"你的依赖图有环"。更好的实现应该做一次 DFS 并记录路径。

**反向依赖用引用计数**（`modindex.lua:1199-1225`）：

```lua

        self.mod_dependencies.server_dependency_list = {}
        self.mod_dependencies.dependency_list = {}
    else
        for i, v in ipairs(self.mod_dependencies.dependency_list[modname] or {}) do
            self.mod_dependencies.server_dependency_list[v] = (self.mod_dependencies.server_dependency_list[v] or 0) - 1
        end
        self.mod_dependencies.dependency_list[modname] = nil
    end
```

**`IsModDependedOn` 是"不能禁用这个模组"的守卫**——如果 X 被 Y 依赖且 Y 启用，那么 X 不能单独禁用。这就是为什么需要引用计数而不是布尔标记：多个模组可能依赖同一个 X，禁用其中一个不该让 X 的计数归零。

### 3.3 加载顺序：priority 排序与稳定排序

`ModWrangler:LoadMods`（`mods.lua:470`）的关键序列：

```
1. 专用服务器 → LoadServerModsFile()
2. 前端上下文 → ClearAllTempModFlags() + DisableAllServerMods()
3. KnownModIndex:UpdateModInfo() → LoadModOverides() → ApplyEnabledOverrides()
4. moddirs = KnownModIndex:GetModsToLoad(worldgen)
5. 对每个 moddir：加载配置 → CreateEnvironment → env.modinfo = initenv → table.insert(self.mods, env)
6. ApplyConfigOptionOverride()
7. 按 priority 排序
8. kleiregistermods(self.mods)          ← 一次性向 C++ 注册
9. 逐个：扩展 package.path / package.assetpath → InitializeModMain(modworldgenmain.lua)
                                              → InitializeModMain(modmain.lua)
```

排序函数（`mods.lua:530-561`）有三个精心处理的细节：

```lua
local function sanitizepriority(priority)
    local prioritytype = type(priority)
    if prioritytype == "string" then
        return tonumber(priority) or 0        -- 容忍字符串形式的数字
    elseif prioritytype == "number" then
        return priority
    end
    return 0
end
local function modPrioritySort(a, b)
	-- NOTES(JBK): Mac OS changed locale sorting so we have to do this using stringidsorter to avoid locale issues.
	if a.modinfo and b.modinfo then
        local apriority = sanitizepriority(a.modinfo.priority)
        local bpriority = sanitizepriority(b.modinfo.priority)
        if apriority == bpriority then
            local aname = a.modinfo.name
            if type(aname) ~= "string" then aname = a.modname end     -- 名字缺失时退回 modname
            local bname = b.modinfo.name
            if type(bname) ~= "string" then bname = b.modname end
            return stringidsorter(aname, bname)                     -- 稳定的二级排序键
        end
        return apriority > bpriority                                  -- 降序
	end
	return stringidsorter(a.modname, b.modname)
end
table.sort(self.mods, modPrioritySort)
```

三个值得学的点：
1. **`sanitizepriority` 做类型防御**——模组作者会写 `priority = "10"`，不该崩溃。
2. **`stringidsorter` 替代 `<`**——注释说明了原因（macOS 改了 locale 排序行为）。**同一 priority 时必须给出确定性顺序**，否则不同机器上加载顺序不同 → 行为不一致。这在有全局状态（钩子顺序）的系统里是致命的。
3. **降序（高的先加载）**。

### 3.4 沙箱环境：Lua 5.1 的 `setfenv` 与它的局限

DST 用的是 **Lua 5.1 的 `setfenv`**，这是本报告需要特别点出的一处「原文没提但很关键」的技术前提。

```lua

	setfenv(fn, fnenv)
	return xpcall(fn, debug.traceback)
end

function RunInEnvironmentSafe(fn, fnenv)
	setfenv(fn, fnenv)
	return xpcall(fn, function(msg) print(msg) StackTraceToLog() print(debugstack()) return "" end )
end

function RunInSandbox(untrusted_code)
	if untrusted_code:byte(1) == 27 then return nil, "binary bytecode prohibited" end
	local untrusted_function, message = loadstring(untrusted_code)
	if not untrusted_function then return nil, message end
	return RunInEnvironment(untrusted_function, env)
end
```

**`setfenv` 的沙箱强度边界（必须理解，否则会误以为"沙箱=安全"）：**

| 能做到 | 做不到 |
|---|---|
| 隐藏全局量（模组看不到 `_G`，只有白名单） | **阻止 `GLOBAL` 逃生舱**——`env.GLOBAL = _G` 是明文给的 |
| 限制模组能 `require` 什么 | 阻止模组调用 `debug.getregistry()` / `debug.setupvalue`（若未隐藏 `debug`，但 DST 也没给 `debug`） |
| 捕获错误（xpcall） | 阻止无限循环（`RunInSandboxSafeCatchInfiniteLoops` 用 `debug.sethook` 做了，但见下） |
| 阻止二进制字节码 | — |

**结论：DST 的 `env` 是「API 规约」而不是「安全边界」。** `GLOBAL = _G` 这一行就决定了：模组可以做任何事。Klei 的立场是「模组代码来自创意工坊，用户自愿安装」，安全靠 Steam Workshop 的审核与用户信任，不靠运行时隔离。

**你的引擎该怎么选：**

| 方案 | 隔离强度 | 兼容性 | 成本 |
|---|---|---|---|
| `setfenv` 白名单（DST 现状） | 弱（有逃生舱） | 高（Lua 5.1 模组零改动） | 极低 |
| 白名单 + 移除 `GLOBAL` 逃生舱 | 中 | 高（改一行模组代码） | 极低 |
| 独立 Lua state（per-mod） | 强（内存/CPU 隔离） | 高（需处理跨 state 调用） | 中 |
| WASM 沙箱 | 强（可 seccomp） | 中（需重新编译模组） | 高 |

**推荐**：至少做到「白名单 + 无 `GLOBAL` 逃生舱 + 独立的 per-mod 限流配额」，这三条加起来成本极低但堵住了原版最大的两个缺口。

**没有专门的 "PlayerPostInit" 钩子**——它就是 `PrefabPostInitAny` 加一个 `HasTag` 过滤。**这是扩展点设计的通用手法**：绝大多数"专用钩子"都是"通用钩子 + 过滤条件"的糖。

`GetPostInitFns` 的聚合实现（`mods.lua:857-877`）有一个关键动作 —— **`runmodfn` 包装**：

```lua
function ModWrangler:GetPostInitFns(type, id)
	local retfns = {}
```

`runmodfn`（`mods.lua:192-206`）是**每个模组钩子的独立错误隔离器**：

```lua
local runmodfn = function(fn,mod,modtype)
	return (function(...)
		if fn then
			local status, r = xpcall( function() return fn(unpack(arg)) end, debug.traceback)
			if not status then
				print("error calling "..modtype.." in mod "..ModInfoname(mod.modname)..": \n"..(r or ""))

			else
				return r
			end
		end

```

**一个模组的钩子抛错 → 整个模组被 `DisableBecauseBad` 禁用 + 弹出错误界面**，其他模组不受影响。这是模组生态能长期运转的关键工程投入。`DisplayBadMods`（`mods.lua:629`）还会构造一个带"退出游戏 / 禁用所有模组 / 访问论坛"三个按钮的错误对话框。

**循环顺序 = 模组启用顺序**（`GetPostInitFns` 遍历 `self.enabledmods`，而 `enabledmods` 是在 `mods.lua:565-586` 按 priority 排好后依次 `table.insert` 进去的）。**这意味着高 priority 模组的钩子先执行。** 如果两个模组都要改同一个值，后加载的覆盖先加载的——**这个覆盖顺序必须写进你的模组文档**，否则模组作者会写出无法诊断的 bug。

### 3.6 模组间通信

DST 的模组间通信有三条通道，从松到紧：

**通道一：共享全局命名空间（最松，无保证）。** 模组通过 `GLOBAL` 表通信：`GLOBAL.MyModSharedState = ...`。因为所有模组共享同一个 `_G`，这在技术上可行，但**没有任何加载顺序保证**（谁先初始化取决于 priority）。**推断**：这在实践中被大量使用，也是"两个模组互相污染"类 bug 的根源。

**通道二：钩子协作（中等，隐式契约）。** 一个模组注册 `AddPrefabPostInit("rock", fn)` 改属性，另一个模组也注册同样的钩子，两者的执行顺序由 priority 决定。**没有显式的"依赖"关系**，只有隐式的时序契约。

**通道三：模组 RPC（最紧，显式命名空间）。** `AddModRPCHandler(namespace, name, fn)`。namespace 是字符串，id 按注册顺序分配：

```lua
-- networkclientrpc.lua:1834
function AddModRPCHandler(namespace, name, fn)
    if MOD_RPC[namespace] == nil then
        MOD_RPC[namespace] = {}
		MOD_RPC_HANDLERS[namespace] = {}
        setmetadata(MOD_RPC[namespace])
        setmetadata(MOD_RPC_HANDLERS[namespace])
    end
    table.insert(MOD_RPC_HANDLERS[namespace], fn)
    MOD_RPC[namespace][name] = { namespace = namespace, id = #MOD_RPC_HANDLERS[namespace] }
    setmetadata(MOD_RPC[namespace][name])
    RPC_QUEUE_RATE_LIMIT = RPC_QUEUE_RATE_LIMIT + RPC_QUEUE_RATE_LIMIT_PER_MOD
end
```

`setmetadata`（`networkclientrpc.lua:1804-1814`）给这些表挂了**大小写不敏感的元表**：

```lua
local function __index_lower(t, k)
    return rawget(t, string.lower(k))
end
local function __newindex_lower(t, k, v)
    rawset(t, string.lower(k), v)
end
local function setmetadata( tab )
    setmetatable(tab, { __index = __index_lower, __newindex = __newindex_lower })
end
```

**这意味着 `MOD_RPC["MyMod"]["RequestHeal"]` 和 `MOD_RPC["mymod"]["requestheal"]` 是同一个条目。** 极大降低了模组作者的心智负担（大小写风格差异不再导致"RPC 不存在"）。**这是个非常实用的设计**，强烈建议照抄。

**通道三的关键限制：命名空间是全局的，没有所有权检查。** `AddModRPCHandler("MyMod", "A", fn)` 会覆盖任何已注册的 `MyMod.A`（`MOD_RPC[namespace][name] = {...}` 直接赋值）。**模组 A 可以劫持模组 B 的 RPC 命名空间**。你的实现里应该加：`if MOD_RPC[namespace][name] ~= nil then error("RPC already registered") end`，并把 namespace 强制为模组名（或 `modname..":"..namespace`）。

### 3.7 模组资源与路径覆盖

模组加载时把根目录插进两条搜索路径（`mods.lua:563-586`）：

```lua
	kleiregistermods(self.mods)

	for i,mod in ipairs(self.mods) do
		table.insert(self.enabledmods, mod.modname)
		package.path = MODS_ROOT..mod.modname.."\\scripts\\?.lua;"..package.path
		local manifest
		--manifests are on by default for workshop mods, off by default for local mods.
		--manifests can be toggled on and off in modinfo with forcemanifest = false or forcemanifest = true
		if((mod.modinfo.forcemanifest == nil and IsWorkshopMod(mod.modname)) or
			(mod.modinfo.forcemanifest ~= nil and mod.modinfo.forcemanifest)) then
			ManifestManager:LoadModManifest(mod.modname, mod.modinfo.version)
			manifest = mod.modname
		end

        self.currentlyloadingmod = mod.modname

			self:InitializeModMain(mod.modname, mod, "modmain.lua")
		end
        self.currentlyloadingmod = nil

```

三个关键点：

1. **`package.path` 前插**（`MODS_ROOT..mod.."/scripts/?.lua;"..`）——模组可以 `require` 同目录下 `scripts/` 里的文件，**且后加载的模组排在前面**（因为每次前插）。所以靠 `require("common")` 找到的到底是哪个模组的文件，取决于 priority 顺序。**这是个隐式的模块冲突面**。

2. **`package.assetpath` 前插 + manifest**。manifest 是创意工坊的文件清单机制（`ManifestManager`），用于校验/下载完整性。`forcemanifest` 让本地模组也能开启。`resolvefilepath` 查找时会带上 manifest 参数（`kleifileexists(filename, pathdata.manifest, filepath)`）。

3. **`modworldgenmain.lua` 总是执行，`modmain.lua` 只在非 worldgen 时执行**。注释说明了原因：`-- worldgen has to always run (for customization screen) but modmain can be skipped for worldgen. This reduces a lot of issues with missing globals.` ——**这是"世界生成"与"运行时"两个阶段的分离**：世界生成进程只需要知道模组提供了哪些自定义项（角色、地形、预设），不需要完整初始化模组逻辑。

`resolvefilepath` 的搜索顺序是 `ipairs_reverse(package.assetpath)`——**倒序遍历，也就是后插入的（priority 低的）先被搜到**。这与 `package.path` 的行为一致：**priority 高的模组最后插入、先被搜索，所以 priority 低的模组资源优先。** **推断**：这个方向可能是无意的（对称性考虑），但如果你的引擎想保持"高 priority 模组覆盖低 priority 模组"的直觉语义，需要显式处理顺序。

### 3.8 一个可运行的模组加载器骨架

综合以上，最小可用模组加载器的完整流程（伪代码）：

```lua
-- ============ 阶段 1：发现与校验 ============
function LoadAllMods(slot_config)
    local manifests = ScanModDirectories()          -- 每个 modinfo.lua 一个沙箱执行
    local valid = {}
    for _, m in ipairs(manifests) do
        local ok, err = ValidateManifest(m)         -- 必填字段 + API 版本双向闸门
        if ok then valid[#valid+1] = m
        else LogError("mod "..m.name.." rejected: "..err) end
    end

    -- ============ 阶段 2：依赖解析（拓扑排序 + 环检测） ============
    local resolved, cycles = ResolveDependencies(valid, slot_config.enabled)
    -- ResolveDependencies: DFS，输出拓扑序；发现环时按 priority 强行截断并记录到 cycles
    if #cycles > 0 then LogWarn("dependency cycles: "..table.concat(cycles, ", ")) end

    -- ============ 阶段 3：构建沙箱 + 排序 ============
    for _, m in ipairs(resolved) do
        m.env = CreateSandboxEnv(m)                  -- 白名单，无 GLOBAL 逃生舱
        m.env.__per_mod_cpu_quota = 1000000         -- 指令配额，防死循环
    end
    table.sort(resolved, ByPriorityThenNameStable)  -- 必须有稳定二级排序键

    -- ============ 阶段 4：注册资源搜索路径 ============
    for _, m in ipairs(resolved) do
        InsertAssetPath(m.root)                     -- 注意：决定覆盖优先级
        InsertScriptPath(m.root .. "/scripts/?.lua")
    end
    RegisterPrefabsToEngine(resolved)               -- 收集 Prefab + Asset，批量加载

    -- ============ 阶段 5：执行入口（带错误隔离） ============
    for _, m in ipairs(resolved) do
        local ok, err = RunInSandbox(m.main_file, m.env, m.__per_mod_cpu_quota)
        if not ok then
            DisableMod(m, err)                       -- 连带把它的依赖者一起禁用
            ShowModErrorDialog(m, err)
        end
    end

    -- ============ 阶段 6：回放延迟钩子 ============
    -- 由引擎在精确时机调用 GetHooks("PrefabPostInit", name) 等
end
```

**与 DST 的差异，都是有意为之**：

| 环节 | DST | 建议实现 | 理由 |
|---|---|---|---|
| 依赖排序 | 无拓扑排序，只有 priority | 加拓扑排序 | priority 是"提示"，依赖是"硬约束"，两者混用会加载失败 |
| 环检测 | 静默截断 | 记录路径并警告 | 让模组作者能诊断 |
| 沙箱 | 有 `GLOBAL` 逃生舱 | 移除 | 至少堵住"模组互相踩踏" |
| CPU | 无配额 | 每模组指令配额 | 防 `while true do end` |
| RPC 命名空间 | 无所有权检查 | 加冲突检测 | 防命名空间劫持 |
| 限流 | 全局上限可被模组无限抬高 | 每模组独立配额 + 全局硬上限 | 防恶意模组 |
| 资源覆盖顺序 | 隐式（倒序搜索） | 显式声明 priority 语义 | 消除直觉与行为的不一致 |

## 【深度扩写】四、UI 系统的可运行实现：代码驱动的 UI

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原报告说了「HUD 是 Screen」「Widget 是实体」，但没给出一个「怎么用代码搭 UI」的完整方法论。这一节给出框架设计。

### 4.1 核心决策：UI 是场景图节点，还是独立树？

DST 选了**混合**：Widget 是 Lua 对象树，**同时**每个 Widget 背后有一个 C++ 实体，二者双向绑定：

```lua
-- widgets/widget.lua:1
self.inst = CreateEntity()          -- C++ 实体（Widget 节点的载体）
self.inst.widget = self             -- 反向指针：实体 → Widget
self.inst.entity:SetName(name)      -- 给调试器/性能分析用
self.inst.entity:AddUITransform()   -- 变换组件：位置/缩放/锚点
self.inst.entity:CallPrefabConstructionComplete()
```

```lua
function Widget:AddChild(child)
    if child.parent then
        child.parent.children[child] = nil
    end
    self.children[child] = child
    child.parent = self
    child.inst.entity:SetParent(self.inst.entity)   -- 双向：Lua 树 + C++ 场景图
    return child
end
```

**这个选择的收益：**

1. **世界坐标可用。** `Widget:GetWorldPosition()`（`widget.lua:336`）走的是 `self.inst.UITransform:GetWorldPosition()`——UI 元素能参与世界空间的命中测试与跟随（`FollowText` 飘在实体头顶就是靠这个）。原版 `widgets/followtext.lua` 是这个能力的直接受益者。
2. **继承游戏的变换与动画系统。** `UIAnim` 组件（`components/uianim.lua`）用的是同一个 `easing.lua` 与同一套 `DoPeriodicTask`。
3. **调试友好。** `entity:SetName(name)` 让引擎侧的性能分析器/实体列表能按名字筛选。

**代价（必须正视）：**

1. **每个控件 = 一个实体 = 一份 Transform 组件内存。** HUD 有几百个控件，等于几百个实体。这是可接受的（DST 的实体本身很轻），但如果你有上万个 UI 元素（比如滚动列表里塞满物品图标），会成为内存瓶颈。
2. **实体系统的所有开销都被继承。** 标签查找、事件总线注册、`DoPeriodicTask` 调度……对一个"只是显示一行文字"的控件来说太重了。

**仿写决策树：**

```
需要 UI 元素参与世界空间（跟随、命中测试、与 3D 物体交互）？
  ├─ 是 → 用 DST 模式（实体支撑的控件树）
  └─ 否 → 用轻量模式（纯 UI 节点树，无实体）

UI 元素规模？
  ├─ < 1000 且动态 → DST 模式可接受
  ├─ < 1000 且静态 → 批渲染的静态图集（一张 mesh）
  └─ > 1000 → 必须虚拟化（ScrollableList 只实例化可见项）
```

DST 的 `widgets/scrollablelist.lua` 就是**虚拟化的实例**——它的注释直接说明了设计意图：

```lua
-- ScrollableList expects a table of pre-constructed items to be handed in as the "items" param OR
-- for the "items" table to be a normalized table of data where each table entry is the data that will be handed as the parameters to the supplied function for "updatefn"
```

两种模式：**预构造 item**（元素少，直接全部建）与 **`updatefn` 复用**（元素多，复用同一批控件改内容）。后者是标准的列表虚拟化。

### 4.2 布局引擎：DST 的答案是「没有布局引擎」

这是一个必须说清楚的事实：**DST 的 UI 没有约束求解、没有自动布局、没有测量-布局两趟。** 全部布局是**绝对坐标 + 锚点**手工计算。

**仿写建议（按推荐度排序）：**

| 方案 | 描述 | 适用 |

### 4.3 事件绑定：DST 的"焦点链"模型

DST 的输入分发是**递归下降 + 焦点标记**，不是命中测试：

```lua
-- widgets/widget.lua:124

    if not self.focus then return false end
    for k,v in pairs (self.children) do
        if v.focus and v:OnControl(control, down) then return true end
    end
    if self.parent_scroll_list and (control == CONTROL_SCROLLBACK or control == CONTROL_SCROLLFWD) then
        return self.parent_scroll_list:OnControl(control, down, true)
    end
    return false
end
```

**关键点：只有带 `focus` 标记的子控件才会收到事件。** `focus` 不是"鼠标悬停"，而是"键盘/手柄焦点链上的一员"。鼠标事件的处理略有不同（`OnMouseButton` 同样看 `v.focus`），但 `TheFrontEnd.isprimary` 标记用于区分。

**焦点链的维护**（`widget.lua:632-687`）：

```lua
    if focus_forward then focus_forward:SetFocus(); return end    -- ③ 焦点代理

    if not self.focus then
        self.focus = true
        if self.OnGainFocus then self:OnGainFocus() end
        if self.ongainfocusfn then self.ongainfocusfn() end
        if self.parent then self.parent:SetFocusFromChild(self) end
    end
    for k,v in pairs(self.children) do
        v:ClearFocus()                          -- ④ 清空所有子焦点
    end
end
```

**这套机制保证了"恰好一个叶子持有焦点"这个不变量**（`IsDeepestFocus`，`widget.lua:46`）：

```lua
function Widget:IsDeepestFocus()
    if self.focus then
        for k,v in pairs(self.children) do
            if v.focus then return false end
        end
    end
    return true
end
```

**手柄导航**用 `focus_flow` 图（`widget.lua:72-99`）：

```lua
function Widget:OnFocusMove(dir, down)
    if not self.focus then return false end
    for k,v in pairs (self.children) do
        if v.focus and v:OnFocusMove(dir, down) then return true end
    end
    if down and self.focus_flow[dir] then
        local dest = FunctionOrValue(self.focus_flow[dir], self)
        -- Can we pass the focus down the chain if we are disabled/hidden?
        if dest and dest:IsVisible() and dest.enabled then
            if self.focus_flow_args[dir] then
                dest:SetFocus(unpack(self.focus_flow_args[dir]))
            else
                dest:SetFocus()
            end
            return true
        end
    end
    if self.parent_scroll_list then
        return self.parent_scroll_list:OnFocusMove(dir, down)   -- ④ 滚动列表接管
    end
    return false
end
```

**三个值得学的设计：**

1. **`focus_flow[dir]` 可以是一个函数**（`FunctionOrValue`），允许动态计算目标（比如"下一个可用的空槽位"）。
2. **`dest:IsVisible() and dest.enabled` 检查**——跳过隐藏/禁用的目标，防止焦点"掉进黑洞"。
3. **`parent_scroll_list` 逃生舱**——控件在滚动列表里时，滚轮事件向上委托给列表。这是"控件不知道自己在容器里"的经典解法。

### 4.5 动画与"暂停时仍刷新"

`Widget` 构造函数里有一个容易被忽略但很重要的机制：

```lua

```

```lua
-- widgets/widget.lua:34

        --widgets run all their tasks on StaticUpdate instead of Update so pausing the server doesn't pause widget tasks.
        self.inst.DoPeriodicTask = self.inst.DoStaticPeriodicTask
        self.inst.DoTaskInTime = self.inst.DoStaticTaskInTime
    else
        self.inst.DoPeriodicTask = self.inst.DoSimPeriodicTask
        self.inst.DoTaskInTime = self.inst.DoSimTaskInTime
    end
    self.inst.components.uianim:UpdateWhilePaused(update_while_paused)

```

**原名（`DoSimPeriodicTask`）已经把意图说清楚了：默认是"模拟期任务"（会随暂停冻结），改名后的 `DoPeriodicTask` 是"无论暂停与否都跑"（走 `StaticUpdate`）。** 所以第 8-9 行是在构造时**先把 sim 版本存到另一个名字上做备份**，然后 `UpdateWhilePaused(true)` 把 `DoPeriodicTask` 换成 static 版本。

`update.lua` 侧的对应实现（`update.lua:169`）：

```lua

    local static_tick = TheSim:GetStaticTick()
    if static_tick <= last_static_tick_seen then
        print("Saw this before")
        return
    end
    ...
    for i = last_static_tick_seen + 1, static_tick do
        RunStaticScheduler(i)
    end
    ...
    TickRPCQueue()
    if TheNet:IsServerPaused() then --only update static components when paused.
```

**注意最后那行注释：`only update static components when paused`** —— 即 `StaticUpdate` 里的组件更新**只在暂停时执行**（`cmp:OnStaticUpdate(0)`，DT 恒为 0）。但 `RunStaticScheduler` 和 `TickRPCQueue` 是**无条件**执行的。也就是说：

```
未暂停时：  Update(dt)          → 模拟（组件、状态图、大脑）
            WallUpdate(dt)     → RPC 队列、相机、输入、前端
暂停时：    StaticUpdate(dt)   → 静态组件（dt=0）+ 静态调度器 + TickRPCQueue
            WallUpdate(dt)     → 同上（仍然跑！）
```

**`WallUpdate` 在暂停时仍然跑**，这正是 UI 动画能在暂停菜单里继续动的原因 —— UI 的每帧更新走 `TheFrontEnd:Update(dt)`（在 `WallUpdate` 里，`update.lua:86-93`）：

```lua

```

**推论**：你的引擎如果有"暂停"语义，必须保证 **UI 更新循环与模拟更新循环分离**。否则暂停菜单会卡住不动。

### 4.6 资源路径与图集

UI 图像的加载路径（`widgets/image.lua:84`）：

```lua

    assert( atlas ~= nil )
    assert( tex ~= nil )
	self.atlas = type(atlas) == "string" and resolvefilepath(atlas) or atlas
	self.texture = tex
    self.inst.ImageWidget:SetTexture(self.atlas, self.texture, default_tex)

```

两个细节：
1. **`default_tex` 参数**——纹理缺失时的占位图。这是"资源加载失败"必须优雅降级的体现。
2. **`UpdateTransform()`**——换纹理后必须重算变换（尺寸变了）。**这是所有"图片控件"实现都要记得的一步**，忘了会导致布局错位。

`resolvefilepath`（`util.lua:636`）带记忆化并在失败时 assert：

```lua
function resolvefilepath(filepath, force_path_search, search_first_path)
    if memoizedFilePaths[filepath] then
        return memoizedFilePaths[filepath]
    end
    local resolved = resolvefilepath_internal(filepath, force_path_search, search_first_path)
    assert(resolved ~= nil, "Could not find an asset matching "..filepath.." in any of the search paths.")
    return resolved
end
```

**记忆化表 `memoizedFilePaths` 是全局的、无上限的**。UI 里如果用动态生成的路径（`"images/skin_"..player_skin..".xml"`），这张表会无限增长。**原版没有处理这个问题**（推断：游戏里 UI 路径都是编译期常量，所以不构成问题）。你的引擎里如果支持运行时换皮肤，必须给这张表加 LRU 或在皮肤切换时清空。

## 【深度扩写】五、移植陷阱清单

> **【深度扩写】** 以下为原版未覆盖、但实际开发会踩的坑。

以下每一条要么是原版里的已知缺陷，要么是从代码里能直接读出的隐患。**所有标注「推断」的条目是基于代码阅读的合理推断，未经运行时验证。**

### 陷阱 1：netvar 的「声明顺序即 wire format」隐式契约

**症状**：任何单边启用 netvar 的改动，会让所有客户端的实体反序列化错位——不是报错，是**静默的数据错乱**（A 的血量显示成 B 的体温）。

**根因**：`netvars.lua:29-32` 那条警告描述的正是这个约束。DST 靠「服务器与客户端跑同一套 Lua」来保证顺序一致，这在**模组只能服务器安装**的场景下必然崩。

**规避**：用**显式字段 ID** 而非声明序号做 wire format。代价是每字段多 2-4 字节；收益是彻底摆脱顺序耦合，且能支持「服务器有的客户端没有」的渐进式扩展。**这是本清单里最值得优先改动的一条。**

### 陷阱 2：`set_local` 永久性抬高带宽

**症状**：某个字段的流量莫名变大，且日志里没有异常。

**根因**：`netvars.lua:55-57` 明确警告——客户端调用过 `set_local` 后，服务器的每一次 `set` 都会变成脏。`player_classified.lua:16-20` 的 `SetDirty` 工具函数说明这是被有意使用的模式（把状态变更变成事件），所以在原版里这个问题是"可控的"。但**如果你自己给某个字段加了 `set_local` 却忘了它会被强制同步，带宽就永久性上升**。

**规避**：为每个 netvar 标注「是否允许 `set_local`」；在开发构建里统计每字段的实际发送次数。

### 陷阱 3：模组可以无限抬高全局 RPC 限流

**症状**：服务器被一个模组的流量压垮，而所有诊断都显示"没有攻击者"。

**根因**：`networkclientrpc.lua:1848` 的 `RPC_QUEUE_RATE_LIMIT = RPC_QUEUE_RATE_LIMIT + RPC_QUEUE_RATE_LIMIT_PER_MOD` 无上限。

**规避**：每模组独立配额 + 全局硬上限（不因模组数量而增长）。

### 陷阱 4：模组死循环挂起整个服务器

**症状**：某个模组更新后，服务器 CPU 100% 但无响应，重启后正常。

**根因**：`util.lua:817` 的 `RunInSandboxSafeCatchInfiniteLoops` 需要 `debug.sethook`，而它和调试器冲突（注释明写），且默认路径根本没用它——`InitializeModMain` 走的是普通 `RunInEnvironment`。

**规避**：每个模组入口配指令配额（`debug.sethook` 计数 + 超时抛错），或把每个模组跑在独立 Lua state 里（可被独立中断）。

### 陷阱 5：沙箱的 `GLOBAL = _G` 让一切隔离形同虚设

**症状**：模组 A 意外改坏了本体游戏的状态，堆栈里完全看不出是谁干的。

**根因**：`mods.lua:328` 的 `GLOBAL = _G` 是明示的逃生舱。所有防护都只在这一行之前有效。

**规避**：至少移除 `GLOBAL`，改用**显式的白名单 API 门面**（`env.MyModReadOnlyTable` 而不是 `env.GLOBAL.STRINGS`）。如果必须保留 `GLOBAL`，则应加一层**写保护代理**（metatable 拦截 `__newindex`，只允许读已声明字段）。

### 陷阱 6：模组 RPC 命名空间可被劫持

**症状**：模组 B 的功能莫名触发/失效，日志无异常。

**根因**：`networkclientrpc.lua:1844` 的 `MOD_RPC[namespace][name] = {...}` 是无条件赋值。同 namespace 同 name 后注册者覆盖先注册者。

**规避**：`if MOD_RPC[namespace][name] then error(...) end`；namespace 强制为 `modname..":"..namespace`。

### 陷阱 7：priority 决定钩子执行顺序，但这个语义没写在文档里

**症状**：两个模组都改同一个属性，效果与预期相反，且在不同机器上表现不同。

**根因**：`mods.lua:561` 的排序决定了 `GetPostInitFns` 的遍历顺序（`mods.lua:857`）。**后加载的覆盖先加载的**。DST 用了 `stringidsorter` 做稳定的二级排序保证跨机器一致，但**「谁覆盖谁」的规则本身没有对外声明**。

**规避**：在你的文档里明确写死「priority 高 = 先执行 = 被后执行者覆盖」，或者反过来（推荐：priority 高 = 后执行 = 覆盖别人，符合"高优先级模组理应赢"的直觉）。

### 陷阱 8：`remote_vector.y` 一个字段承担三种语义

**症状**：处理移动平台/船只时的位置错乱，且难以复现。

**根因**：`playercontroller.lua:3694` 的 `remote_vector.y` 同时用作 flag（0/1/2/3/4）和真实高度坐标。`playercontroller.lua` 里至少两处 `FIXME(JBK): Boat handling.` 标记说明这条路径至今有已知问题。

**规避**：把「移动意图标签」和「坐标」拆成两个独立字段（一个枚举 + 一个 vec3）。多花 4 字节，换来可调试性。

### 陷阱 9：平台相对坐标的补丁是后期加的

**症状**：做移动平台时，客户端与服务器坐标差一个平台的偏移量。

**根因**：`platform` / `platform_relative` 这对参数是后加的（见 `FIXED(V2C)` 注释），代码里到处是补丁。`printinvalidplatform` 里那个 `Playform` 拼写错误说明这段是紧急加入的。

**规避**：从第一天就设计成「所有位置消息都是 (平台句柄, 局部坐标) 二元组」，或明确声明不支持移动平台。不要中途加。

### 陷阱 10：同帧分片 RPC 重入被静默丢弃

**症状**：跨分片物品偶发不同步，且日志里只有一行 `print`。

**根因**：`networkclientrpc.lua:1786-1788` 检测到同帧第二条分片 RPC 就丢弃，只打印警告。

**规避**：改成"排队到下一帧"而不是"丢弃"，并把丢弃计数上报到监控。

### 陷阱 11：存档按预制体分块，但 NaN 检测只扫字符串

**症状**：极端情况下存档损坏，且损坏点在字符串里找不到 NaN 模式。

**根因**：`mainfunctions.lua:1202-1236` 对每个 `DataDumper` 产物做 `string.find(..., 1, true)`（纯文本匹配）扫描，dev 与非 dev 分支用不同的模式串（`"=nan"/"=inf"` vs `"=-1.#IND"/"=1.#QNAN"`）。数值已经被序列化成字符串了，所以扫字符串是可行的；但如果某个表结构让 NaN 走了别的序列化路径（比如以 key 形式出现），就漏了。

**规避**：在 `DataDumper` 里加一个类型检查钩子，遇到 NaN/inf 直接抛错（比事后扫字符串更可靠）。

### 陷阱 12：`memoizedFilePaths` 无上限

**症状**：长时间运行后内存缓慢增长；换皮肤后用到了旧的（已删除的）路径。

**根因**：`util.lua:622` 的记忆化表只写不清。**推断**：原版 UI 路径都是编译期常量，所以不构成问题；但支持运行时换皮肤/换语言包时就是泄漏源。

**规避**：加 LRU 或在资源组切换时 `table.clear(memoizedFilePaths)`。

### 陷阱 13：每控件一实体 = 每控件一份 Transform 内存

**症状**：超长列表滚动时内存峰值过高、GC 抖动。

**根因**：`widget.lua:1` 每个控件都 `CreateEntity()`。这是有意的设计选择（换取世界坐标能力），但代价明确。

**规避**：静态内容用图集合批；动态长列表虚拟化（参考 `scrollablelist.lua` 的 `updatefn` 复用模式）。

### 陷阱 14：假 Image 吃焦点

**症状**：为了响应鼠标 hover 而创建了一个全透明 `Image`，多了一次 draw call，且屏幕阅读器/无障碍工具会把它当成真实元素。

**根因**：`scrollablelist.lua:44` 的 `self.bg = self:AddChild(Image(...)) -- so that we have focus whenever the mouse is over this thing`。

**规避**：在框架层提供独立的"命中区域"概念（一个矩形描述符），不要用假图元。

### 陷阱 15：焦点记忆的对象可能已被销毁

**症状**：关闭一个弹窗后再打开，焦点落到了无人处理的控件上，所有按键无声失效。

**根因**：`screen.lua:35` 有 `self.last_focus.inst.entity:IsValid()` 检查——说明这个坑被踩过。但**模组自定义的 Screen 若忘了这个检查就会复现**。

**规避**：把焦点记忆做成框架能力（在 `Screen` 基类的 `OnBecomeActive` 里统一处理并校验有效性），不要让每个屏幕自己写。

### 陷阱 16：RPC 代码只有 127 个可用槽位

**症状**：新增内建 RPC 时分配到重复的 code，行为错乱。

**根因**：`networkclientrpc.lua:1386` 的注释：`-- NOTES(JBK): RPC limit is at 128, with 1-127 usable.` 而 `RPC` 的分配循环（`networkclientrpc.lua:1391-1396`）**没有边界检查**。

**规避**：分配时断言 `< 128`，超限直接报错；模组的 RPC 走独立的 namespace 空间（这正是 `AddModRPCHandler` 的价值——不占用 127 个内建槽位）。

### 陷阱 17：`all_clients_require_mod` 与 netvar 强耦合

**症状**：给服务器装一个"服务器专属"模组后，所有客户端被要求安装它，理由是它用了 netvar。

**根因**：`netvars.lua:29-32` 那条警告的实际后果。netvar 要求两侧声明一致 → 无法做成服务器专属。

**规避**：区分「只读 netvar（可做服务器专属，客户端不发就行）」与「写 netvar（必须全员）」。DST 没有这个区分（**推断**：这可能是它把 `all_clients_require_mod` 用得如此保守的原因之一）。

### 陷阱 18：分片状态是 C++ 侧管理的

**症状**：想加一个"第三个区域"时，发现 Lua 侧完全没有插拔点。

**根因**：`shardnetworking.lua` 里的 `Shard_UpdateWorldState` 是被 C++ `ShardManager` 调用的**回调**，不是 Lua 侧能主动驱动的流程。分片列表来自引擎。

**规避**：如果要自研，做成"Lua 侧维护分片注册表 + 引擎按注册表连接"，而不是反过来。

## 【移植指引】面向自研引擎的抽象映射

### 6.1 Lua 概念 → 自研引擎对应物

| Lua / DST 概念 | 在 DST 里的实现 | 自研引擎对应物 | 迁移注意 |
|---|---|---|---|
| `Class(base, ctor, props)`（`class.lua`） | 元表 + `__call` 的元类系统 | 标准 OOP（类 / 结构体 + 组合） | 保留「浅拷贝继承 + `is_a`」的语义，别用组合替代继承（钩子机制依赖 `is_a`） |
| `EntityScript`（`entityscript.lua`） | 实体上的 Lua 包装器 | 实体对象 / Actor 的脚本绑定 | 保留 `inst.components` 的索引式访问，它比方法派发快 |
| `Prefab`（`prefabs.lua:6`） | 具名工厂函数 + 资源表 + 依赖表 | 工厂 + 资源声明 + 加载依赖 | 资源必须**与预制体同处声明**，不要集中到单独的资源清单文件 |
| `Asset(type, file, param)` | 四字段记录 | 同 | `type` 决定加载器；`param` 用于同类型差异化（如动画的 bank 名） |
| `Component` | 挂在 `inst.components[name]` 的 Class 对象 | 组合式组件 | **保持 `OnSave/OnLoad/OnComponentUpdate` 的鸭子类型契约**，不要要求继承基类 |
| `TheWorld` / `ThePlayer` 等全局单例（`main.lua:308-371`） | 引擎注入或 `global()` 声明的全局 | 服务定位器 / 全局上下文对象 | 用 `strict.lua` 那样的未声明全局守卫（`main.lua:120` 的 `require("strict")`） |
| `ismastersim` / `ismastershard` | 三个布尔标志 | 角色枚举（Client/Server/Host+Server/Shard） | **用枚举而非多个布尔**——三个布尔会产生 8 种非法组合 |
| `net_bool` / `net_byte` / … | C++ 注入的全局构造器 | 引擎的 `Replicated[T]` 声明 | **改成显式字段 ID**，见陷阱 1 |
| `netvar:set / value / set_local` | 三个方法 | `ReplicatedProperty.Set/ Get/ SetLocal` | `SetLocal` 必须有明确的"不保证下次 Set 幂等"文档 |
| 脏事件（`"healthdirty"`） | 引擎触发的事件名字符串 | `OnRep()` 回调 或 属性变更委托 | 触发时机必须在游戏逻辑更新**之前**（`netvars.lua:36`） |
| `net_event`（`netvars.lua:85`） | 包在 net_bool 外面的一次性触发器 | `ReplicatedEvent` | 单独提供，不要让作者手写 `set_local(true); set(true)` |
| `player_classified` + `SetClassifiedTarget` | 只对一个客户端可见的隐藏实体 | 「私有复制通道」/ per-client channel | 这个抽象非常值得抄：**隐私需求比「只读」需求更常见** |
| `<name>_replica` 组件（`entityreplica.lua`） | 客户端只读镜像组件 | `IReadOnlyMirror<T>` 接口 | 保持「同一方法名、两份实现」的 API 对称（`replica.health` vs `components.health`） |
| `RPC` / `CLIENT_RPC` / `SHARD_RPC` | 三张 name→fn 表 + 自动编号 | 消息注册表 + 编译器生成 ID | **注意 127 槽上限**（陷阱 16）；用字符串/哈希 ID 可完全避免 |
| `HandleRPCQueue` + `RPC_QUEUE_RATE_LIMIT` | 入队 + 每刻配额 + 同刻一条 | 同 | `TickRPCQueue` 里**必须清空 limiter 表**（防泄漏） |
| `SpawnPrefabFromSim` | 生成 + 立即跑 PostInit 钩子 | 工厂调用 + 后处理钩子 | 钩子必须在「工厂返回之后、子树建立之后」 |
| `modenv` / `setfenv` | Lua 5.1 全局环境替换 | 模块沙箱 / 独立 VM / WASM | 至少移除 `GLOBAL` 逃生舱（陷阱 5） |
| `postinitfns` / `postinitdata` | 延迟钩子表 | 钩子注册表 | 区分「数据型钩子（贡献对象）」与「函数型钩子（执行行为）」 |
| `ModManager:GetPostInitFns(type, id)` | 跨模组聚合 | 钩子总线 | **必须按模组优先级排序**，且逐个用 `runmodfn` 包装（错误隔离） |
| `AddClassPostConstruct` | 包装 `_ctor` | 装饰器 / 中间件 | 用 `__init_subclass__` 或构造后回调，不要改类表本身（污染全局） |
| `package.assetpath` + `resolvefilepath` | 逆序搜索的记忆化路径解析 | 虚拟文件系统 + 挂载点 | 加 LRU；模组挂载点的优先级要显式定义 |
| `TheFrontEnd:PushScreen/PopScreen` | 屏幕栈 | 视图栈 / 场景栈 | 必须有 `OnBecomeActive/Inactive` 成对钩子（焦点记忆依赖它） |
| `Widget`（实体支撑的控件） | Lua 对象 + C++ 实体双向绑定 | UI 节点 | **仅在需要世界坐标时用**；否则用轻量节点 |
| `focus` / `focus_flow` | 焦点链 + 导航图 | 焦点管理 + 焦点组 | 「恰好一个叶子持有焦点」是不变量，别破坏它 |
| `OnControl(control, down)` 返回 true = 消费 | 输入仲裁 | 输入路由 / 消费标记 | **按下与抬起必须一起仲裁**（陷阱 4 里的 UI 攻击 bug） |
| `CONTROL_*` 抽象层 | 物理按键 → 抽象控件的映射 | 输入动作（Input Action） | 抽象层要在**引擎侧**做，重绑定才透明 |
| `WallUpdate` / `Update` / `StaticUpdate` | 真实时间 / 模拟时间 / 暂停期 | 三条更新循环 | **UI 更新必须挂"真实时间"那条**，否则暂停时 UI 冻结 |
| `uianim` 补间组件 | `StartWallUpdatingComponent` + easing | 动画系统 | 补间完成回调要检查宿主是否已销毁 |
| `DataDumper`（`dumper.lua`） | 打印成 Lua 源码 | 序列化库 | 换成二进制格式（msgpack/protobuf）能小 3-5 倍 |
| `GetSaveRecord` / `GetPersistData` | 每个实体/组件贡献表 | 序列化 | 保持「组件自序列化 + 只存差量」，这是存档大小的关键 |
| `LoadPostPass`（两趟重建） | 第二趟解析 GUID 引用 | 反序列化第二阶段 | 参考表（ID → 对象）必须在第一趟建立 |
| `ShardIndex` / `ShardSaveIndex` | 每分片存档索引 | 分区存档路由 | 存档键用 `(slot, shard)` 复合键，别用路径嵌套 |
| `migration`（序列化 → 换连接 → 反序列化） | 玩家跨界 | 会话迁移 | 迁移必须是「序列化 + 路由 + 反序列化」，不是「传送」 |

### 6.2 模块边界与单向依赖

DST 的依赖方向（从 `main.lua` 的 `require` 顺序与各文件的引用关系可推出）：

```
        ┌──────────────┐
        │  引擎 (C++)  │  TheSim / TheNet / TheShard / TheInput (原生)
        └──────┬───────┘
               │ 注入全局
        ┌──────▼───────────────────────────────────────┐
        │  核心框架 (class/util/scheduler/entityscript) │
        └──────┬───────────────────────────────────────┘
               │
     ┌─────────┼──────────┬────────────┬─────────────┐
     ▼         ▼          ▼            ▼             ▼
 ┌───────┐ ┌────────┐ ┌────────┐ ┌──────────┐ ┌─────────┐
 │netvars│ │frontend│ │ prefabs│ │   mods   │ │ assets  │
 │net*rpc│ │widgets │ │entity  │ │ modutil  │ │ util    │
 └───┬───┘ └───┬────┘ └───┬────┘ └────┬─────┘ └────┬────┘
     │         │         │           │            │
     └─────────┴────┬────┴───────────┘            │
                    ▼                              │
             ┌─────────────┐                      │
             │ components/ │──────────────────────┘
             │ prefabs/*   │
             └─────────────┘
```

**必须遵守的三条单向依赖规则**（DST 基本遵守）：

1. **`components/` 不依赖 `widgets/`。** 玩法组件要显示 UI，必须通过 `TheFrontEnd:PushScreen` 或事件，让前端去拉。反向依赖（组件直接 `require "widgets/button"`）会把玩法层绑死在 UI 上。
2. **`prefabs/` 不依赖 `prefabs/`（跨文件）。** 预制体之间通过 `Prefab` 的 `deps` 参数声明，由引擎加载器解决顺序。这样 `LoadPrefabFile` 才能独立加载单个文件。
3. **`mods/` 只允许通过 `GLOBAL` 和注入的 `env` API 触碰核心。** 这是唯一的越界通道，也是所有不稳定性从这里来。

### 6.3 推荐的引擎侧模块划分

如果要自研，按这个顺序实现，每层可独立测试：

```
第 0 层：确定性基础
  - 固定步长模拟循环（tick = 1/30）+ 真实时间循环分离
  - 事件总线（带 source/target 过滤）
  - 序列化库（二进制，支持 GUID 引用表）

第 1 层：实体框架
  - 实体 / 组件 / 生命周期钩子（OnSave/OnLoad/OnUpdate）
  - 预制体工厂 + 资源声明 + 加载依赖

第 2 层：网络
  - 消息注册表（字符串或哈希 ID，不用序号）
  - 权威模拟 + 角色标志
  - 输入仲裁（UI 优先）
  - 复制层：Replicated 属性 + 脏位 + 兴趣管理

第 3 层：客户端体验
  - 客户端预测 + 服务器纠正（带回滚带）
  - 插值缓冲（远端实体位置平滑）

第 4 层：前端
  - 控件树 + 焦点链 + 输入路由
  - 屏幕栈 + 淡入淡出
  - 资源（图集 + 字体 + 本地化）

第 5 层：模组
  - 清单校验 + 版本闸门
  - 沙箱（独立 state 或字节码配额）
  - 依赖拓扑排序
  - 钩子总线（数据型 + 函数型）
  - 模组 RPC 命名空间（带所有权校验）

第 6 层：持久化
  - 组件自序列化 + 差量存储
  - 两趟重建（引用解析）
  - 快照保留策略（支持回滚）
```

**关键顺序约束**：第 2 层必须在第 1 层之后（复制的是实体状态）；第 4 层的输入仲裁必须在第 2 层的输入分发之前定义好接口；第 5 层的钩子总线必须在第 1 层的工厂/组件注册处埋点。**如果先做模组系统再改实体框架，所有钩子点都要返工。**

## 【实现清单】

要做出一个 DST 级别的联机生存 + 模组生态系统，按此顺序推进。

### A. 联机同步基础设施

- [ ] 固定步长模拟循环（tick = 1/30），与真实时间循环（WallUpdate）**物理分离**
- [ ] 角色抽象：`Client` / `Server` / `Host`（同时是两者）/ `Shard`，用**枚举**而非多个布尔
- [ ] 消息注册表：按字符串或哈希 ID 注册（**不要用序号**，见陷阱 1 / 16）
- [ ] 输入仲裁层：UI 优先，按下与抬起**一起**仲裁，消费后写"已吞掉"标记（见陷阱 4 里的 UI 攻击 bug）
- [ ] 输入动作抽象（`CONTROL_*`），物理按键映射在引擎侧完成，支持运行时重绑定
- [ ] 服务器权威：`SaveGame` 类操作有客户端守卫；所有状态变更只在服务器路径可达
- [ ] RPC 校验原语库：`checknumber/checkbool/checkuint/checkstring/checkentity` + `opt*` 可选版本（照抄 `networkclientrpc.lua:3-14`）
- [ ] 点位距离守卫：任何客户端提供的世界坐标都要过 `distsq <= LIMIT`（照抄 `IsPointInRange`）
- [ ] 限流：每发送者每刻配额 + **limiter 表每刻清空**（防泄漏）+ 超限只告警一次
- [ ] 同刻重入保护：同一发送者每刻最多执行一条 RPC（照抄 `RPC_Timeline`）
- [ ] 错误隔离：非法 RPC 推 `invalidrpc` 事件给反作弊工具；dev 构建 assert，生产不崩（照抄 `printinvalid`）
- [ ] **每模组独立 RPC 配额 + 全局硬上限**（原版缺口，见陷阱 3）

### B. 实体复制

- [ ] 类型化复制属性：`bool / tiny(3b) / small(6b) / byte / short / ushort / int / uint / float / hash / string / entityref / bytearray(≤31)`
- [ ] **显式字段 ID** 的 wire format（不是声明序号）
- [ ] 三方法语义：`Set`（服务器，同步 + 触发脏事件）/ `Get`（两侧可读）/ `SetLocal`（不同步，**文档写明会抬高带宽**）
- [ ] 脏事件：值真变才触发；提供"强制脏"工具函数（`set_local(v); set(v)`）
- [ ] 脏事件触发时机在游戏逻辑更新**之前**
- [ ] 首次进入视野 = 全量快照（实体元信息 + 全部复制字段 + 组件集合）
- [ ] 之后 = 纯增量，只发给对该实体可见的客户端
- [ ] 初始脏事件风暴的规避：脏监听器**延迟注册**（照抄 `DoStaticTaskInTime(0, RegisterNetListeners)`）
- [ ] 兴趣管理：中心点 + 半径起步；预留空间网格接口
- [ ] `AddNetwork()` 必须在 `SetPristine()` 之前调用
- [ ] 休眠/唤醒：离开视野的实体进入休眠（`OnEntitySleep`），回到视野唤醒
- [ ] 「classified」等价物：私有复制通道（只对一个客户端可见的隐藏实体）
- [ ] 副本组件机制：`IReadOnlyMirror` 列表 + 客户端自动实例化；提供"注册新可复制组件"的 API
- [ ] 客户端预测：locomotor 逻辑只在客户端挂载；`EnableMovementPrediction` 时机在组件与状态图都就绪之后
- [ ] 第一个 RPC 延迟一帧发送（引擎不允许生成帧发 RPC）
- [ ] 回滚带（rubber band）：预测误差超过阈值时**无条件**放弃预测、让服务器位置胜出，优先级高于一切其他纠正
- [ ] 停止时专门补发一帧 `isstop` RPC
- [ ] 客户端预测目标用「预测位置」而非「当前模拟位置」

### C. 存档与持久化

- [ ] 组件自序列化：`OnSave()` 返回**只含差量**的小表 + 可选引用表
- [ ] 预制体级 `OnSave` 作为补充钩子
- [ ] 跨实体引用存 GUID，加载时映射为对象引用
- [ ] **两趟重建**：第 1 趟实例化 + 建 GUID 索引，第 2 趟 `LoadPostPass` 解析引用
- [ ] 存档分块：按预制体分组 dump，便于局部重载与压缩
- [ ] 损坏检测：在序列化器里检测 NaN/inf（比事后扫字符串可靠，见陷阱 11）
- [ ] 异步写盘 + 回调链（写世界存档 → 写索引 → 更新时间戳文件）
- [ ] 版本化升级链：`upgrades[]` 数组按 `saveversion` 顺序执行
- [ ] 存档版本号与槽位数据分离（`SAVEDATA_VERSION`）
- [ ] 玩家独立存档（user session），支持崩溃后重连
- [ ] 快照保留策略：世界存档写完且全员离线时截断历史快照（支撑 `rollback`）
- [ ] **用二进制序列化**（msgpack/protobuf）替代 Lua 源码文本，体积小 3-5 倍

### D. 模组系统

- [ ] 清单文件（`modinfo` 等价物）在**最小沙箱**中执行（连 `print` 都不给）
- [ ] API 版本**双向闸门**：太旧警告仍加载，太新硬失败（照抄 `modindex.lua:620-627`）
- [ ] 必填字段校验，分「硬失败」与「仅警告」两级（照抄 `checkinfo` 表的分级处理）
- [ ] 兼容性字段缺省兜底 + `*_specified` 影子标记（区分"用户没设"与"用户设了 false"）
- [ ] 互斥标志检测并警告（如 `client_only_mod` vs `all_clients_require_mod`）
- [ ] **依赖拓扑排序**（不只是 priority）+ 环检测并**记录路径**（静默截断不够）
- [ ] 多版本候选依赖：优先本地已启用版本，创意工坊版本次之（照抄 `BuildModPriorityList`）
- [ ] 反向依赖用**引用计数**（`IsModDependedOn`），不是布尔标记

## 概述 / TL;DR

- **`.tex` 就是 "KTEX"** —— 一个 8 字节头 + 每 mip 10 字节的表 + 依次拼接的 BC1/BC3/RGB888 mip 数据。行是**自底向上**存储的。整个格式约 60 行代码就能解码；参考解码器在 `assets-work/ktex_decode.py`。
- **实际出现的像素格式**：BC3/DXT5（1381 个文件）、BC1/DXT1（105 个）、未压缩 RGB888（33 个，全部是色彩立方 LUT）。没有别的。
- **图集描述符**是极小的 XML（`<Atlas><Texture/><Elements><Element u1 u2 v1 v2 [variant]/>`），带**归一化 UV、半纹素内缩、整个发布版本里没有任何旋转标志**。
- **动画包**就是普通 ZIP，内含 `anim.bin`（魔数 `ANIM`）、`build.bin`（魔数 `BILD`）与 `atlas-N.tex`。没有随包发布的 `.scml`/`.xml` —— 这些是**编译后**的 Spriter 工程。
- **`anim_dynamic.zip`** 是"zip 套 zip"（3346 个按皮肤分的嵌套包）；散落的 `anim/dynamic/*.dyn` 文件是**加密数据块**（熵 7.97 比特/字节，无魔数，不是 zip，也不是简单 XOR）。
- **着色器**（`.ksh`）是*包裹明文 GLSL ES 源码的二进制容器*，按 stage 分文件（`name.vs`、`name.ps`），外加 uniform block / sampler 名字表。
- **字体**是嵌套 zip 里的 **AngelCode BMFont** 对：`font.fnt`（XML）+ `font.tex`（KTEX 图集）。
- **声音** = FMOD：`.fsb` 音效包（魔数 `FSB5`）+ `.fev` 事件工程（RIFF/`FEV `）。触感反馈（haptics）是普通的 882 Hz 单声道 PCM WAV。
- **影片** = 一个 103 MB 的 `.ogv`（Ogg 容器，`fishead` 骨架 → Theora/Vorbis）。
- **Lua 就是资源清单**：每个预制体声明 `Asset("ANIM"|"IMAGE"|"ATLAS"|"ATLAS_BUILD"|"SOUND"|"SOUNDPACKAGE"|"SHADER"|"FONT"|"DYNAMIC_ANIM"|"PKGREF"|...)`。

## 2. `.tex` —— KTEX 容器

### 2.1 魔数与头部

```
$ xxd -l 64 data/fx/pixel.tex
00000000: 4b54 4558 20a2 fcff 1000 1000 4000 0001  KTEX .......@...
00000010: 0000 0800 0800 2000 4000 0000 0400 0400  ...... .@.......
00000020: 1000 1000 0000 0200 0200 1000 1000 0000  ................
00000030: 0100 0100 1000 1000 0000 00ff 4992 2449  ............I.$I
```

| 偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| `0x00` | 4 | magic | ASCII `KTEX`（`4B 54 45 58`） |
| `0x04` | 4 | flags 位域 | LE uint32；见 2.2 |
| `0x08` | 10·N | mip 表 | N = 由 flags 推出的 mipmap 数；每个 mip 一条 10 字节记录 |
| `0x08+10N` | … | mip 数据 | 依次拼接，**最大的 mip 在前** |

mip 记录（10 字节）：

| 偏移 | 大小 | 字段 | 已验证语义 |
|---|---|---|---|
| +0 | 2 | `width` | uint16 |
| +2 | 2 | `height` | uint16 |
| +4 | 2 | `pitch` | uint16，每编码行的字节数：BC3 = `ceil(w/4)*16`，BC1 = `ceil(w/4)*8`，RGB888 = `w*3` |
| +6 | 4 | `data_size` | uint32，本 mip 载荷字节数：BC3/BC1 = `pitch*ceil(h/4)`，RGB888 = `pitch*h` |

**尺寸不变量（解码器的单元测试）**：`8 + 10*N + Σ data_size == 文件大小`。对 1519/1519 个散装 `.tex` 成立。

算例，`fx/pixel.tex`（426 字节，BC3，5 个 mip）：mip 为 16×16/256 B、8×8/64、4×4/16、2×2/16、1×1/16 → 8+50+368 = 426 ✓。
`fx/rain.tex`（1460 字节，BC3，6 个 mip）：32×32/1024 … 1×1/16 → 8+60+1392 = 1460 ✓。

> **本版复核（2026-10-11）**：用 `struct.unpack('<HHHI', ...)` 逐 mip 解析本机全部 1519 个 `.tex`，结果：
> ```
> scanned 1519  formats {'BC3': 1381, 'RGB888': 33, 'BC1': 105}  bad 0
> fx/pixel.tex  size 426  flags=fffca220  N 5  inv 426  [(16,16,64,256),(8,8,32,64),(4,4,16,16),(2,2,16,16),(1,1,16,16)]
> fx/rain.tex   size 1460 flags=fffcc220  N 6  inv 1460 [(32,32,128,1024),(16,16,64,256),(8,8,32,64),(4,4,16,16),(2,2,16,16),(1,1,16,16)]
> ```
> 不变量 1519/1519 成立，像素格式分布与原文完全一致。

### 2.2 `0x04` 处的 flags 位域

在 1519 个文件里观察到的取值（共 15 个不同值），以及置位的比特位：

```
0xfffd6220  n= 702  bpp= 8  mips=11   bits=[5, 9, 13, 14, 16, 18..31]
0xfffd2220  n= 243  bpp= 8  mips= 9   bits=[5, 9, 13, 16, 18..31]
0xfffd8220  n= 194  bpp= 8  mips=12   bits=[5, 9, 15, 16, 18..31]
0xfffd4220  n= 163  bpp= 8  mips=10   bits=[5, 9, 14, 16, 18..31]
0xfffce220  n=  69  bpp=24  mips= 7   bits=[5, 9, 13, 14, 15, 18..31]
0xfffd2200  n=  45  bpp= 4  mips= 9   bits=[9, 13, 16, 18..31]
0xfffd6200  n=  44  bpp= 4  mips=11   bits=[9, 13, 14, 16, 18..31]
0xfffc2250  n=  33  bpp=24  mips= 1   bits=[4, 6, 9, 13, 18..31]
```

* **比特 13–16 = mipmap 数量** —— 已验证：`(flags>>13)&0xF` 等于 mip 表长度，**并且**能让尺寸不变量对每个文件成立（出现过的值：1,3,5,6,7,8,9,10,11,12）。
* **比特 5** 恰好在 8-bpp（BC3）纹理上置位、在 4-bpp（BC1）上清零；**比特 4+6** 恰好在 24-bpp 的 RGB888 色彩立方上置位。等价地，`(flags>>3)&0x1F` 给出 `{0: BC1, 4: BC3, 10: RGB888}`，`(flags>>5)&0x1F` 给出 `{16: BC1, 17: BC3, 18: RGB888}` —— 两种分解都成立；写解码器时把*格式 id* 当作住在低字节里的小枚举，并以 `pitch` 做交叉验证。
* **比特 9** 与 **比特 18–31** 在本 PC 版本的*每个*文件里都置位；**比特 17** 与比特 0–3、7–8、10–12 在这里恒为清零。含义未知 —— 很可能是只在主机版本上才有差异的平台/画质标志。**不要依赖它们。**

> **本版复核**：`fx/pixel.tex` 实测 flags = `0xfffca220`，mips = 5；`fx/rain.tex` = `0xfffcc220`，mips = 6。两者都不在原文列出的那 8 个高频取值里（原文只列了 15 个不同值中的前 8 个），进一步印证了"不要依赖未列出的比特"这条告诫。

### 2.3 像素数据

* BC3/DXT5 块 = 16 字节：`[a0,a1,6×3-bit alpha 索引][color0 u16, color1 u16, 4×2-bit 索引]`。
* BC1/DXT1 块 = 8 字节：`[color0, color1, 4×2-bit 索引]`。
* RGB888 = 3 字节/像素，只用于被展平为 2D 的 3D 调色 LUT（`images/colour_cubes/*.tex`，例如 1024×32 = 32×32×32 的立方）。
* **行序是自底向上**（v = 0 先存）。按自顶向下解码会得到上下翻转的图像 —— 已通过把 `bigportraits/random_none.tex` 与 `images/anr_silhouettes.tex` 渲染成 PNG（`assets-work/decoded/*.png`）验证：精灵图在 V 翻转前是倒的。这与图集 XML 一致，后者的 `v1/v2` 是从底部量起的。

### 2.4 解码配方

1. 检查魔数 `KTEX`；读 flags；`N = (flags>>13)&0xF`。
2. 读 N 条 mip 记录；从 `0x08+10N` 起按累加方式算出各 mip 的载荷偏移。
3. 用 `pitch` 对 `width` 的关系挑编解码器（`ceil(w/4)*16` → BC3，`*8` → BC1，`w*3` → RGB888）。
4. 解 mip 0（或任意 mip），按块行主序：块 `(bx,by)` 从 `by*pitch + bx*blocksize` 开始。
5. 为得到左上原点的输出，对结果做 V 翻转。

## 3. `.xml` 图集描述符

存在两种形态。UI/精灵图集：

```xml
<Atlas><Texture filename="anr_silhouettes.tex" /><Elements>
<Element name="silhouette_beta_8.tex" u1="0.000244140625" u2="0.124755859375"
         v1="0.25048828125" v2="0.49951171875" />
<Element name="silhouette_beta_5.tex" u1="0.000244140625" u2="0.124755859375"
         v1="0.50048828125" v2="0.74951171875" />
</Elements></Atlas>
```

地块图集多一个 `variant` 属性（地形地块的 a/b/c 重着色变体）：

```xml
<Atlas><Texture filename="data/levels/tiles/grass.tex" /><Elements>
<Element name="03" u1="0.126953125" u2="0.185546875" v1="0.37890625" v2="0.49609375" variant="b" />
<Element name="06" u1="0.314453125" u2="0.373046875" v1="0.50390625" v2="0.62109375" variant="a" />
</Elements></Atlas>
```

注解：
- `u1,u2,v1,v2` 是元素矩形的**归一化** UV；`v` 向上增长（与 KTEX 行序一致）。
- 0.000244140625 这样的偏移是**半纹素内缩**（0.5/2048；`grass.xml` 里 0.00048828125 = 0.5/1024），用来防止 mip 渗色 —— 你写任何打包器时都要复刻这一点。
- 元素的 `name` 保留一个假的 `.tex`/`.png` 扩展名；它只是一个查找键。
- **不存在旋转属性。** 对全部随包发布的图集做属性普查：`name/u1/u2/v1/v2` 各 3843 次，`variant` 1128 次，`filename` 375 次；`rotat*` 出现 **0** 次。

> **本版复核**：`data/images/anr_silhouettes.tex` 的实际 XML 首元素为 `name="silhouette_beta_8b_reveal.tex" u1="0.125244140625" u2="0.249755859375" v1="0.25048828125" v2="0.49951171875"`（原文示例中的 `silhouette_beta_8.tex` 也在同文件里，UV 完全相同）。`data/levels/tiles/grass.xml` 的 `Texture filename` 实测为 `data/levels/tiles/grass.tex`（带 `data/` 前缀的绝对相对路径），而 `anr_silhouettes.xml` 用的是裸文件名 `anr_silhouettes.tex` —— **两种写法在同一套资源里混用**，这正好说明描述符里的路径是走统一解析器（见第 12 节的 `resolvefilepath()`）而非简单的前缀拼接。

### 4.1 `anim.bin`（魔数 `ANIM`）

```
00000000: 414e 494d 0400 0000 c603 0000 6000 0000  ANIM........`...
00000010: 0000 0000 0500 0000 0600 0000 6964 6c65  ............idle
00000020: 5f31 ffd5 ff1f 4800 00f0 4105 0000 00d0  _1....H..A.....
```

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0x00 | magic `ANIM` | |
| 0x04 | uint32 = 4 | 版本（每个样本里都是常量） |
| 0x08 | uint32 | 未知；在单元素动画库上等于帧数，在多符号动画库上远大于此（很可能是元素-帧总数） |
| 0x0C | uint32 | 未知；行为上像"跨所有动画的总帧数" |
| 0x10 | uint32 | 每个样本里都是 0 |
| 0x14 | uint32 | **动画数量** —— 已验证：`abigail_flower` = 5，且确实存在五个动画名（`idle_1, idle_2, haunted_pre, idle_haunted_loop, haunted_pst`）；另有 16 个 zip 交叉验证通过 |
| 0x18 | 每动画：uint32 `name_len` + ASCII 名，然后是时间线载荷 | 这里第一个名字是 `idle_1` |
| 载荷 | 含 fps 的浮点数（`00 00 f0 41` = 30.0）与关键帧数据 | 关键帧的精确语法未在此逆向 |
| 尾部 | 符号/动画库名表：带长度前缀的字符串（`petalback1…petal4, shdw, flower1, flower2`，然后是动画库名 `abigail_flower`） | 与 `build.bin` 的符号列表呼应 |

> **本版复核**：`abigail_flower` 的 `anim.bin` 头 8 个 uint32 实测为 `4 / 966 / 96 / 0 / 5`，与上表逐项对应（版本 4、`0x08`=966、`0x0C`=96、`0x10`=0、`0x14`=5）。`0x08`=966 对 `0x0C`=96 的比值印证了"元素-帧总数 vs 动画总帧数"的推断——该库有 10 个符号（见 `build.bin`），966/96 ≈ 10。

### 4.2 `build.bin`（魔数 `BILD`）

```
00000000: 4249 4c44 0600 0000 0a00 0000 0b00 0000  BILD............
00000010: 0e00 0000 6162 6967 6169 6c5f 666c 6f77  ....abigail_flow
00000020: 6572 0100 0000 0b00 0000 6174 6c61 732d  er........atlas-
00000030: 302e 7465 7820 72db 1601 0000 0000 0000  0.tex r.........
```

魔数 `BILD`；`0x04` 处 uint32 = 6；`0x08` 处 = 10（= 本样本的符号数）；`0x0C` 处 = 11；`0x10` 处 = 14 = 动画库名长度；随后是动画库名 `abigail_flower`；图集数量 uint32 = 1；每个图集是 uint32 长度 + 名字（`atlas-0.tex`）+ 图集元数据浮点数；然后是符号表 —— 10 个带长度前缀的名字（`petalback1…flower2`），每个后面跟若干浮点数（UV 矩形 / 轴心 / 尺寸）。`0x04`/`0x0C` 处的字段未确认。

> **本版复核**：`build.bin` 前 96 字节实测：
> ```
> 42 49 4c 44 | 06 00 00 00 | 0a 00 00 00 | 0b 00 00 00 | 0e 00 00 00
> 61 62 69 67 61 69 6c 5f 66 6c 6f 77 65 72        ("abigail_flower")
> 01 00 00 00 | 0b 00 00 00 | 61 74 6c 61 73 2d 30 2e 74 65 78   ("atlas-0.tex")
> 20 72 db 16 | 01 00 00 00 00 00 00 00 | 01 00 00 00 08 00 20 3f ...
> ```
> 名字**没有** NUL 终止（长度 14 之后紧跟 `01 00 00 00`），这一点在写解析器时要注意。图集元数据里的 `08 00 20 3f` = float `0.62890625`，对应 174,908 字节的 atlas-0.tex —— 这个值恰好等于它在图集中的某个归一化尺寸，后续可用于确认"图集元数据浮点数"的语义（**推断**）。

### 4.3 动态皮肤

* `databundles/anim_dynamic.zip` = **3346 个嵌套 zip**，位于 `anim/dynamic/` 下（同样的 `anim.bin`/`build.bin`/`atlas-N.tex` 布局；只含皮肤数据的包只有 `build.bin`）。

## 5. 着色器包（`databundles/shaders.zip`）

68 个 `.ksh` 文件。**不是纯文本** —— 是一个内嵌 GLSL ES 源码的二进制容器：

```
00000000: 0600 0000 7370 7269 7465 0300 0000 0d00  ....sprite......
00000010: 0000 5343 5245 454e 5f50 4152 414d 5300  ..SCREEN_PARAMS.
...
00000080: 0700 0000 5341 4d50 4c45 5200 0000 002b  ....SAMPLER....+
00000090: 0000 0001 0000 0009 0000 0073 7072 6974  ...........sprit
000000a0: 652e 7673 e001 0000 6174 7472 6962 7574  e.vs....attribut
```

布局：uint32 长度 + 着色器名（`sprite`）；uint32 计数 + uniform block 描述符（带长度前缀的名字 `SCREEN_PARAMS`、`SPRITE_PARAMS`、`SAMPLER`……，每个带定长元数据）；然后每个 stage 是 uint32 长度 + 文件名（`sprite.vs` / `sprite.ps`）+ uint32 src_len + **GLSL 源码文本**（NUL 结尾）。

提取出的 `sprite.vs`（逐字）：

```glsl
attribute vec3 POSITION;
attribute vec2 TEXCOORD0;
varying vec2 PS_TEXCOORD0;
uniform vec4 SCREEN_PARAMS;
uniform vec4 SPRITE_PARAMS;
void main()
{
    vec3 screen_pos = POSITION.xyz;
    screen_pos.x = screen_pos.x * SCREEN_PARAMS.z * SCREEN_PARAMS.y;
    screen_pos.xy = screen_pos.xy * SPRITE_PARAMS.xy;
    screen_pos.xy = screen_pos.xy + SPRITE_PARAMS.zw;
    gl_Position = vec4( screen_pos.xyz, 1.0 );
    PS_TEXCOORD0.xy = TEXCOORD0.xy;
}
```

约定：GLSL ES 1.00 风格（`attribute`/`varying`/`texture2D`、`#if defined(GL_ES) precision highp float;`）；sampler 声明为数组（`uniform sampler2D SAMPLER[1]; #define SPRITE_IMAGE SAMPLER[0]`）；Klei 预处理器开关 `SKINNED`、`HOLO`、`FADE_OUT`、`HAUNT`、`BLOOM`、`TRIPLE_ATLAS`、`UI_CC`、`UI_HOLO`；uniform 词汇表 `MatrixW/V/P`、`MatrixPVW`、`pv`、`TIMEPARAMS`、`FLOAT_PARAMS`、`fastanim_bones`、`fastanim_xform`、`LIGHTMAP_WORLD_EXTENTS`、`COLOURCUBE`。骨骼矩阵每根骨头打包成 2×vec4，采样器索引被塞在 `POS2D_UV.z` 里 —— 这是一个值得在 ES2 硬件上照抄来做 GPU 蒙皮的好模式。

> **【深度扩写】本版新增：`.ksh` 的完整字段布局已逐字节逆向。**
>
> 原文只说"每个 uniform block 带定长元数据"。本版对全部 68 个文件做了锚点扫描与结构解析，结果如下（**已在本机验证 68/68 文件按此布局可完整解析**）：
>
> ```
> ┌─────────────────────────────────────────────────────────────────┐
> │ u32 nameLen; char name[nameLen];            // 着色器名，如 "sprite"
> │ u32 blockCount;
> │ repeat blockCount:
> │     u32 blkNameLen; char blkName[blkNameLen];
> │     u32 binding;        // 0 = 普通 uniform；0x2b = sampler 类
> │     u32 arrayLen;       // sampler 时为数组长度；uniform 时为槽位数
> │     u32 elemCount;      // 仅 uniform：初值 float 的个数
> │     float defaults[elemCount];   // 仅 uniform，elemCount*4 字节
> │ u32 stageCount（隐含 2）;
> │ repeat 2:
> │     u32 fnLen; char fn[fnLen];      // "sprite.vs" / "sprite.ps"
> │     u32 srcLen; char src[srcLen];   // NUL 结尾的 GLSL 源码
> │ u32 attribCountVs; u32 attribCountPs; u32 reserved0; u32 reserved1;
> └─────────────────────────────────────────────────────────────────┘
> ```
>
> **关键判别规则**（`shaders/sprite.ksh` 与 `shaders/anim.ksh` 上实测）：
> - 若 `binding == 0x2b`，该 block 是 sampler，**没有** `elemCount` 与初值数组 —— 记录在名字后 12 字节处结束。
> - 否则 `binding == 0`，记录在名字后 `12 + 4*elemCount` 字节处结束。
>
> 实测数据（`sprite.ksh`，953 字节，逐字节偏移）：
> ```
> 偏移   0: u32 6              → "sprite"（4..9）
> 偏移  10: u32 3              → blockCount = 3
> 偏移  14: u32 13             → "SCREEN_PARAMS"（18..30）
>        31: u32 binding=0, 35: u32 arrayLen=4, 39: u32 elemCount=4,
>        43: float[4] = {0,0,0,0}（47..62 全零） → 下一 block 在 63
> 偏移  63: u32 13             → "SPRITE_PARAMS"（67..79）
>        80: u32 binding=0, 84: u32 arrayLen=4, 88: u32 elemCount=4,
>        92: float[4] = {0,0,0,0} → 下一 block 在 112
> 偏移 112: u32 7              → "SAMPLER"（116..122）
>       123: u32 binding=0x2b, 127: u32 arrayLen=1     → 下一个 token 在 135
> 偏移 135: u32 9              → "sprite.vs"（139..147）
 *       148: u32 480           → 源码 152..631（末尾 \r\n\r\n\0）
 * 偏移 632: u32 9              → "sprite.ps"（636..644）
 *       645: u32 284           → 源码 649..932
 * 偏移 933: u32 0, u32 1, u32 1, u32 2    ← 尾部四元组
> ```
> `sprite.vs` 里恰好有 **2** 条 `attribute` 声明（`POSITION`、`TEXCOORD0`），尾部四元组的第三个值恰为 **2**；`sprite.ps` 有 **0** 条 `attribute`，对应值 **1**。**推断**：尾部是 `{reserved, psAttrCount, vsAttrCount, …}` 或类似的属性/常量槽位计数，用于在不改 GLSL 文本的前提下驱动顶点布局绑定。68 个文件的尾部取值互不相同（普查到的前 10 种），与各文件顶点属性数量吻合。**这一段的字段语义标注为「推断」**；但**结构本身（偏移与长度）已在本机对全部 68 个文件验证通过**。

00000010: 388b 0000 0001 3701 0f00 0000 0100 0000  8.....7.........

FMOD **FSB5** 包。对三个包（`wanda1` 7 个采样/172 字节头/248 字节名字表，`rabbit` 12/240/276，`music` 84/25720/2636）做文件大小交叉验证，可得到公开布局：`0x00` 魔数 `FSB5`、`0x04` 版本（此处 =1）、`0x08` 采样数、`0x0C` 采样头大小、`0x10` 名字表大小、`0x14` 数据大小、`0x18` 模式，然后是 `0x24` 处的 16 字节 MD5 与一个 CRC。采样头/名字表是 varint 编码并按 FMOD 规范做 XOR 扰动的 —— **请用现成的解包器，不要自己手写。**

> **触感 WAV 实测参数**（`haptics/vibration/vibration/` 抽样）：
> ```
> 0_puzzle_grotto_DST.wav   4692 B   1 ch   882 Hz   16 bit   2324 帧
> 1manband_kickdrum_1.wav    352 B   1 ch   882 Hz   16 bit    154 帧

> ```

>         local filename = string.gsub(pathdata.path..filepath, "\\", "/")
>         if kleifileexists(filename, pathdata.manifest, filepath) then return filename end
>     end
>     if kleifileexists(filepath) then return filepath end   -- 最后兜底
>     return nil
> end
> ```
> 三个设计要点，每一个都值得照抄：
> 1. **`ipairs_reverse`** —— 搜索路径**逆序**遍历。`package.assetpath` 在 `main.lua:3-4` 初始化为 `{path = ""}`（游戏自身），模组加载时 `mods.lua:576` 用 `table.insert(package.assetpath, {path = MODS_ROOT..mod.modname.."\\", manifest = manifest})` **追加**。逆序遍历 ⇒ **最后加载的模组优先**，这正是模组覆盖的标准语义。
> 2. **三级缓存** —— `memoizedFilePaths`（`util.lua:574`）在 `resolvefilepath` / `resolvefilepath_soft` / `softresolvefilepath` 三个入口都先查表；未命中才走 `resolvefilepath_internal` 并写回。游戏启动时要解析上万条路径（4417 条 `PKGREF` + 3606 条 `ANIM` + …），没有缓存会退化成 O(路径数 × 搜索路径数) 次文件系统探测。
> 3. **强/软两种语义** —— `resolvefilepath` 失败会 `assert`（`util.lua:641`："Could not find an asset matching ... in any of the search paths."），`softresolvefilepath` 失败返回 nil。注册期用强版本（`mainfunctions.lua:121-122`），模组可选内容用软版本（`modindex.lua:539`）。
>
> 另外 `GetMemoizedFilePaths`/`SetMemoizedFilePaths`（`util.lua:576-581`）会把这张缓存表用 `ZipAndEncodeSaveData` 序列化后跨启动携带 —— 即**路径解析结果可以持久化**，避免每次启动重跑上万次文件探测。

## 14. 类似游戏中值得借鉴的关键模式

1. **一个动画集一个 zip**（anim + build + atlas）让流式加载单元极小，并让加载器能把一个包挂载成虚拟目录；空占位 zip 保持挂载表稳定。
2. **把"build"（骨架/符号/UV）与"anim"（时间线）分开**，这样皮肤可以只发 build 包，运行时用 `SetBuild` 换装而不动动画数据。
3. **图集描述符是数据不是代码**：具名 UV 矩形 + `variant` 标签让美术改铺砌/自动铺砌时不需要改引擎；半纹素内缩烘进 UV 里避免 mip 渗色。
4. **mip 表里显式记录每级的 pitch 与 size**，让容器与编解码器无关（BC1/BC3/RGB888 都能装），并且能用一条算术不变量校验整个文件。
5. **调色 LUT 就当普通纹理发**（`colour_cubes/`、RGB888 KTEX）—— 不需要特殊资源类型。
6. **着色器即"容器内的源码"**：元数据用二进制包裹 + GLSL 用明文文本，意味着着色器可热重载、可 diff、可跨平台编译，还自带一份 uniform block 注册表。
7. **Lua 即资源清单**（每个预制体一份 `Asset(type, path)`），白送依赖图驱动的加载、可模组性，以及可被垃圾回收的资源生命周期。
8. **databundle（zip）叠在散装文件之上**，用 `resolvefilepath()` 汇合：可打补丁、可缓存，并通过一个极小的 `hashes.txt` 清单做校验。
9. **事件图音频**（FSB 包 + FEV 工程，按字符串路径播放）把混音器与代码解耦。
10. **只加密真正必须保护的东西**（`.dyn` 皮肤），其余一律明文 —— 把"可模组友好"当特性来做，并用 `unsafedata/` 作为被认可的写入沙箱。

## 【深度扩写 1】自定义格式的读写实现：如何设计自己的资源格式

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原文详细描述了 KTEX 的字段，但没有回答"我该怎么做自己的格式"。下面用 KTEX 与 `.ksh` 作为真实样本，抽出可迁移的设计原则，并给出可直接使用的读写器。

### 1.1 KTEX 的三个设计决策（值得照抄）

**决策一：头极小，索引紧贴头。**

```
[4B magic][4B flags][10B × N mip 记录][mip 载荷依次拼接]
```

`8 + 10N + Σ data_size == 文件大小` —— **整个文件可以用一次线性扫描校验完毕，不需要任何查找结构**。这是原文称之为"解码器的单元测试"的那条不变量，也是 KTEX 最优雅的地方。

**决策二：每级 mip 记录显式携带 pitch 与 size，让容器与编解码器解耦。**

如果只存 `width/height`，加载器就得先知道格式才能算出行大小。有了 `pitch`，BC1/BC3/RGB888 全都装得下同一个容器，加载器可以先读表、后选解码器（原文第 2.4 节的第 3 步就是这个用途：`ceil(w/4)*16` → BC3，`*8` → BC1，`w*3` → RGB888）。代价是每个 mip 多 6 字节——完全值得。

**决策三：格式标识用"冗余编码"而非单一字段。**

原文指出 `(flags>>3)&0x1F` 与 `(flags>>5)&0x1F` 两种分解都能映射到 {BC1, BC3, RGB888}，而 `pitch` 与 `width` 的关系是第三重冗余。三条独立路径给出一致的答案 —— 这意味着**即使某条路径在某个平台上有差异，加载器仍然能正确判别**。这是给未来格式演进留的余量。

> 反面教训：`flags` 的比特 18–31 与比特 9 在**每个文件**里都置位（`0xfffd6220` 这种值的高 14 位全是 1）。这看起来像是**签名/魔数位**，而不是语义位。如果你的格式也这么做，务必确保它不与格式语义冲突 —— 原文明确警告"不要依赖它们"。

### 1.2 `.ksh` 的三个设计决策

**决策一：元数据与源码分离。** 见上文【深度扩写】给出的完整布局。核心是"uniform 的初值用裸 float 数组内联，sampler 不带初值"，用 `binding == 0x2b` 一个常数区分两类记录。

**决策二：源码明文内嵌。** `sprite.vs` 的 480 字节就是纯 ASCII GLSL。这让着色器可 diff、可热重载、可跨平台编译（换 `#version` 就能给不同后端用同一份源）。代价是文件比纯二进制大 —— 对 68 个文件（合计不到 1 MB）来说完全可以接受。

**决策三：块名表 + 显式数组长度。** `SAMPLER[1]`、`sampler2D SPRITE_IMAGE[]` 这种数组式 sampler 声明，靠的就是"元数据里记了数组长度"，渲染器才能按索引绑定正确的纹理槽，而不必去解析 GLSL 源码。

### 1.3 通用格式骨架：头 + 索引 + 数据块

综合两个真实样本，加上工程实践，给出一个推荐的容器骨架：

```
┌──────────────────────────────────────────────────────────────┐
│ 固定头（32~64 字节，永远在 offset 0，CPU 可一次性读入缓存）    │
│   u32 magic           // 4B ASCII，如 "KTEX"                  │
│   u16 versionMajor    // 不兼容变更 ++                        │
│   u16 versionMinor    // 兼容变更 ++                          │
│   u32 flags           // 位域；预留 16 位给未来，高 16 位可   │
│                       // 用作格式签名的冗余校验                │
│   u32 indexOffset     // 索引表在文件中的绝对偏移              │
│   u32 indexCount      // 索引条目数                            │
│   u64 contentHash     // 内容散列，用于缓存失效判定            │
│   … 保留字段（必须补零，保证固定长度）                         │
├──────────────────────────────────────────────────────────────┤
│ 索引表：indexCount × 固定大小记录（16~32 字节，可 mmap 直读）  │
│   u32 key             // 资源键（散列值，或指向字符串表的下标） │
│   u32 dataOffset      // 数据块绝对偏移                        │
│   u32 dataSize        // 数据块字节数                          │
│   u32 flags           // 该条目的私有标志（压缩/加密/mips）    │
│   u32 aux             // 备用：格���尺寸、采样数等               │
├──────────────────────────────────────────────────────────────┤
│ 字符串表（可选）：长度前缀的 UTF-8，供索引表引用              │
├──────────────────────────────────────────────────────────────┤
│ 数据块：按 16 字节对齐；大块可独立压缩/独立 mmap              │
└──────────────────────────────────────────────────────────────┘
```

**为什么索引项要定长？** 因为这样才能对索引表做 `mmap` + 二分查找，不需要反序列化。KTEX 的 10 字节 mip 记录、`build.bin` 的符号表都是这个思路的简化版。代价是浪费一点空间（短字符串也占定长槽位），但换来 O(log n) 随机访问。

### 1.4 快速随机访问：三级索引

要同时支持"按名字查"和"按 id 查"，用两级：

```
L0: 名字 → key      （启动时建一次 hash 表；或用排序数组 + 二分）
L1: key  → indexIdx （索引表下标，二分或直接散列）
L2: indexIdx → (dataOffset, dataSize)  （定长记录，O(1)）
```

DST 实际的做法更简单粗暴但同样有效：**`StringHash` 把字符串直接变成 `uint32`，然后用这个整数当键**（引擎报告第 6 节）。Lua 侧还可以预散列（`constants`/`TUNING` 里的常量），运行时零字符串查找。

**三条具体的性能实践**（都能在 DST 里找到依据）：

1. **索引项定长 + 按 key 排序** → 二分查找，缓存友好。避免散列表的指针跳转。
2. **数据块 16 字节（或 64 字节）对齐** → 可直接 `mmap` 后按对齐地址解释，省掉一次 memcpy。KTEX 的 mip 载荷是从 `0x08+10N` 开始的自然偏移，不对齐 —— 如果你的格式要支持 mmap 零拷贝，这个对齐必须从一开始就定好。
3. **小资源内联进索引项**（inline）→ 一个 8 字节的向量参数、一个小图标，如果小于 32 字节就直接放在索引记录里，省一次间接。这对应 `.ksh` 把 `float[4]` 初值直接内联在 block 记录里的做法。

### 1.5 完整的读写器实现

下面给出一个真实可用的 KTEX 读写器，以及一个通用的"头+索引+数据块"读写器骨架。两者都只用标准库。

#### KTEX 读取器（对照本文档第 2 节验证过的格式）

```python
# ktex.py —— KTEX 容器的读写。结构依据：本报告第 2 节的字段表，
# 已对本机全部 1519 个 .tex 验证（8 + 10N + Σdata_size == filesize）。

import struct

KTEX_MAGIC   = b"KTEX"
BLOCK_BC1    = 8      # 4x4 块字节数
BLOCK_BC3    = 16     # 4x4 块字节数

def _blocks(w):        # ceil(w / 4)
    return (w + 3) // 4

def pixel_format_from_pitch(width, pitch):
    """用 pitch 反推像素格式 —— 这是 KTEX 冗余编码设计的关键。"""
    if pitch == _blocks(width) * BLOCK_BC3:
        return "BC3"
    if pitch == _blocks(width) * BLOCK_BC1:
        return "BC1"
    if pitch == width * 3:
        return "RGB888"
    raise ValueError("无法识别的 pitch=%d（width=%d）" % (pitch, width))

class Mip:
    __slots__ = ("width", "height", "pitch", "size", "offset")
    def __init__(self, width, height, pitch, size, offset):
        self.width, self.height, self.pitch, self.size, self.offset = \
            width, height, pitch, size, offset

class Ktex:
    def __init__(self, flags, mips):
        self.flags  = flags
        self.mips   = mips

    # ---- 读 --------------------------------------------------------
    @classmethod
    def load(cls, data: bytes) -> "Ktex":
        if len(data) < 8 or data[:4] != KTEX_MAGIC:
            raise ValueError("不是 KTEX 文件")
        (flags,) = struct.unpack_from("<I", data, 4)
        n = (flags >> 13) & 0xF          # 已验证：bits 13–16 = mipmap 数

        mips, off, total = [], 8 + 10 * n, 0
        for _ in range(n):
            if off + 10 > len(data):
                raise ValueError("mip 表越界")
            w, h, pitch, size = struct.unpack_from("<HHHI", data, off)
            off += 10
            mips.append(Mip(w, h, pitch, size, 8 + 10 * n + total))
            total += size

        # ★ 核心不变量：一条算术就能验证整个文件
        if 8 + 10 * n + total != len(data):
            raise ValueError("尺寸不变量失败：头部声明 %d 字节，实际 %d 字节"
                             % (8 + 10 * n + total, len(data)))
        return cls(flags, mips)

    def format(self):
        """像素格式由最大 mip 的 pitch 决定。"""
        return pixel_format_from_pitch(self.mips[0].width, self.mips[0].pitch)

    def mip_data(self, data: bytes, level: int = 0) -> bytes:
        m = self.mips[level]
        return data[m.offset : m.offset + m.size]

    # ---- 写 --------------------------------------------------------
    @staticmethod
    def save(pixels, flags_extra: int = 0) -> bytes:
        """pixels: 按 mip 从大到小排列的 (width, height, pitch, bytes) 列表。
        调用方负责先编好 BC1/BC3/RGB888 数据（建议用 DirectXTex/texconv）。"""
        n = len(pixels)
        if not 1 <= n <= 15:              # bits 13–16 只有 4 位
            raise ValueError("mip 数量必须在 1..15")
        flags = ((n & 0xF) << 13) | flags_extra

        out = bytearray(KTEX_MAGIC + struct.pack("<I", flags))
        for (w, h, pitch, payload) in pixels:
            out += struct.pack("<HHHI", w, h, pitch, len(payload))
        for (_, _, _, payload) in pixels:
            out += payload
        return bytes(out)

# 自检：对着真实文件跑一遍不变量
if __name__ == "__main__":
    import sys, os, collections
    root = sys.argv[1] if len(sys.argv) > 1 else "."
    tally, bad, count = collections.Counter(), [], 0
    for dirpath, _, files in os.walk(root):
        for f in files:
            if not f.lower().endswith(".tex"):
                continue
            count += 1
            p = os.path.join(dirpath, f)
            raw = open(p, "rb").read()
            try:
                t = Ktex.load(raw)
                tally[t.format()] += 1
            except Exception as e:
                bad.append("%s: %s" % (p, e))
    print("扫描 %d 个文件，格式分布 %s，失败 %d" % (count, dict(tally), len(bad)))
    for b in bad[:5]:
        print("  ", b)
```

对照本机实测输出：`扫描 1519 个文件，格式分布 {'BC3': 1381, 'RGB888': 33, 'BC1': 105}，失败 0`。

#### 通用"头 + 索引 + 数据块"读写器骨架

```python
# container.py —— 自定义资源容器的推荐骨架。
# 与 KTEX 的差异：增加了「按 key 的 O(log n) 随机访问」与「对齐」，
# 因为通用资源容器通常要支持 mmap 零拷贝与热重载。

import struct, mmap, os, bisect

MAGIC   = b"MYAS"
VER_MAJ, VER_MIN = 1, 0
HDR_FMT = "<4sHHIIIIQ8x"          # 4+2+2+4+4+4+4+8+8 = 40 字节
HDR_SIZE = struct.calcsize(HDR_FMT)
IDX_FMT = "<IIIII"                # key, dataOffset, dataSize, flags, aux = 20 字节
IDX_SIZE = struct.calcsize(IDX_FMT)
ALIGN    = 64                     # 数据块对齐，保证 mmap 后可直接按对齐地址解释

KEY_INVALID = 0xFFFFFFFF

def align_up(x, a=ALIGN):
    return (x + a - 1) & ~(a - 1)

class Entry:
    __slots__ = ("key", "offset", "size", "flags", "aux")
    def __init__(self, key, offset, size, flags, aux):
        self.key, self.offset, self.size, self.flags, self.aux = \
            key, offset, size, flags, aux

class Container:
    def __init__(self):
        self.flags    = 0
        self.entries  = {}       # key -> Entry
        self.blobs    = {}       # key -> bytes
        self._sorted  = []       # [(key, Entry)] 按 key 排序，供二分

    # ---- 写入 ------------------------------------------------------
    def put(self, key: int, payload: bytes, flags: int = 0, aux: int = 0):
        if key in self.entries:
            raise KeyError("key 0x%08X 已存在" % key)
        self.entries[key] = Entry(key, 0, len(payload), flags, aux)
        self.blobs[key]    = payload
        self._sorted       = []          # 标脏，最后统一重建

    # ---- 序列化 ----------------------------------------------------
    def to_bytes(self) -> bytes:
        items = sorted(self.entries.items(), key=lambda kv: kv[0])
        n = len(items)

        # 两趟：先算偏移，再填内容
        cursor = align_up(HDR_SIZE + IDX_SIZE * n)
        index  = bytearray()
        body   = bytearray()
        for key, e in items:
            pad = align_up(cursor + len(body)) - (cursor + len(body))
            body += b"\0" * pad
            e.offset = cursor + len(body)
            index += struct.pack(IDX_FMT, key, e.offset, e.size, e.flags, e.aux)
            body  += self.blobs[key]

        hdr = struct.pack(HDR_FMT, MAGIC, VER_MAJ, VER_MIN, self.flags,
                          HDR_SIZE, n, 0, 0)
        return bytes(hdr) + bytes(index) + bytes(body)

    @classmethod
    def from_file(cls, path: str, mmap_it: bool = False):
        self = cls()
        raw = open(path, "rb")
        try:
            data = raw.read(HDR_SIZE)
            magic, vmaj, vmin, flags, idx_off, idx_cnt, _, _ = \
                struct.unpack(HDR_FMT, data)
            if magic != MAGIC:
                raise ValueError("魔数不匹配")
            if vmaj != VER_MAJ:
                raise ValueError("主版本不兼容：文件 %d，本库 %d" % (vmaj, VER_MAJ))
            # 小版本不同只记警告 —— 兼容变更不该让老读取器崩掉
            raw.seek(idx_off)
            idx = raw.read(IDX_SIZE * idx_cnt)
            for i in range(idx_cnt):
                key, off, size, eflags, aux = struct.unpack_from(IDX_FMT, idx, i * IDX_SIZE)
                e = Entry(key, off, size, eflags, aux)
                self.entries[key] = e
                if mmap_it:
                    e._buf = mmap.mmap(raw.fileno(), 0, access=mmap.ACCESS_READ)
                self._sorted.append((key, e))
        finally:
            raw.close()
        return self

    # ---- O(log n) 随机访问 ------------------------------------------
    def find(self, key: int):
        if not self._sorted:
            self._sorted = sorted(self.entries.items(), key=lambda kv: kv[0])
        i = bisect.bisect_left(self._sorted, key, key=lambda t: t[0])
        if i < len(self._sorted) and self._sorted[i][0] == key:
            return self._sorted[i][1]
        return None

    def read(self, key: int) -> bytes:
        e = self.find(key)
        if e is None:
            raise KeyError("找不到 key 0x%08X" % key)
        buf = getattr(e, "_buf", None)
        if buf is not None:              # mmap 路径：零拷贝切片
            return buf[e.offset : e.offset + e.size]
        return self.blobs[key]

    def iter_entries(self):
        for key, e in sorted(self.entries.items(), key=lambda kv: kv[0]):
            yield key, e
```

### 1.6 三个容易踩的坑

**坑一：整数溢出。** KTEX 的 `data_size` 是 `uint32`，`Σ data_size` 用 32 位累加在超过 4 GB 的容器上会静默回绕。你的容器索引项如果用 `uint32` 存偏移，**单文件上限就是 4 GB**。用 `uint64` 或保证单文件不超 4 GB。

**坑二：对齐与 mmap 的相互作用。** `mmap` 返回的页对齐地址，加上 `dataOffset` 后如果不对齐，你无法直接 `reinterpret_cast` 成结构体指针（C++ 里是未定义行为，虽然 x86 上碰巧能工作）。**索引项对齐到 4/8 字节，数据块对齐到 16/64 字节** —— 这不是性能优化，是正确性要求。

**坑三：版本演进时不要复用旧字段。** `.ksh` 的 flags 里有一堆"本 PC 版本恒定"的比特（引擎报告侧还有 KTEX 的 bits 18–31），这些位置一旦被赋予语义，将来发现有平台差异时就无处安放新语义了。**预留位就让它永远预留**，新增语义用新偏移。

## 【深度扩写 2】资源管线搭建：从美术资源到游戏内可用资产的完整流程

> **【深度扩写】** 以下为原版未覆盖、对仿写实现关键的内容。

原文第 14 节列了 10 条模式，但没有把它们串成一条**流水线**。下面把 DST 的实际流程拆成 7 个阶段，每个阶段给出输入/输出/失败模式，并指出原版特有、值得抄的机制。

### 2.1 流水线总览

```
① 美术产出          PNG/PSD/TGA 源文件（通常在引擎外）
        │
② 导入 + 压缩       → KTEX（BC1/BC3）+ mip 链
        │           决策点：哪些图要 BC3（带 alpha）、哪些 BC1、哪些不压缩（LUT）
        │
③ 打包进图集        → 单张 KTEX + XML 描述符（具名 UV 矩形 + variant + 半纹素内缩）
        │           决策点：图集切分粒度（UI 一张？物品栏一张？）
        │
④ 声明依赖          → Lua 里的 Asset(type, path) 列表（挂在预制体上）
        │           决策点：粒度是"每个预制体"还是"每类资源"
        │
⑤ 路径解析          → resolvefilepath()：散装目录 ∪ databundle ∪ 模组目录
        │           带 memoizedFilePaths 缓存；强/软两种语义
        │
⑥ 注册到引擎        → TheSim:RegisterPrefab(name, assets, deps)
        │           原生侧据此建立资源→预制体的反向索引
        │
⑦ 加载/卸载         → TheSim:LoadPrefabs(names) / UnloadPrefabs(names)
                    资源在预制体引用计数归零时释放
```

### 2.2 阶段一至三：美术到图集

**导入压缩的决策规则**（从实测的 1519 个文件的分布反推）：

| 用途 | 格式 | 实测占比 | 理由 |
|---|---|---|---|
| 带 alpha 的精灵（角色、大部分 UI） | BC3/DXT5 | 1381/1519 = 91% | BC3 用 16 B/块换 4 bpp alpha，是"几乎所有图都要 alpha"这一现实的最优解 |
| 无 alpha 的遮罩（噪声、UI 底） | BC1/DXT1 | 105/1519 = 7% | 8 B/块，省一半空间 |
| 3D 调色 LUT | RGB888 不压缩 | 33/1519 = 2% | **LUT 必须无损**：它是逐像素查表数据，BC 块的插值误差会直接变成色偏 |

**LUT 用不压缩纹理**这一条（第 14 节第 5 条模式）值得单独强调：它是"资源类型系统不需要特殊分支"的典范。`images/colour_cubes/*.tex` 就是普通 KTEX + RGB888，只是被 `postprocesseffects.lua` 用 `SetColourCubeData` 当作 3D 纹理采样。你的引擎如果打算区分"纹理资源"和"数据资源"，就会多出一整套加载/生命周期/序列化路径 —— 而 DST 靠"不区分"省掉了这些。

**图集打包的三个硬性要求**（原文第 3 节已给出，此处补充为什么）：

1. **半纹素内缩（0.5/texW）。** 不做的话，在 mip level ≥ 1 时相邻图块的像素会被双线性插值混进来，表现为图块边缘的"彩色描边"。这是 2D 游戏最常见的美术 bug。DST 把内缩**烘进 UV 数值里**（`u1 = 0.000244140625` 而不是 `0.0`），而不是靠着色器的 `clamp to edge` 技巧 —— 前者对美术工具透明，后者要求每个采样点都记得开采样器状态。
2. **底原点 V（v 向上增长）。** 因为 KTEX 行序是自底向上（原文第 2.3 节），图集描述符必须与之匹配。混用会导致整个图集上下颠倒。
3. **不支持旋转。** DST 的所有打包器都关掉了旋转。这不是能力缺失，而是**有意的约束**：一旦允许旋转，描述符就要多一个旋转角度字段、渲染器要多一次分支、美术工具的自动布局质量也会下降。DST 的图集元素数是 3843，尺寸都很小（很多是单个 UI 图标），不值得为此付复杂度。

### 2.3 阶段四：Lua 资源 DSL

DST 的 `Asset(type, path)` 是一个**只有三个字段的值对象**（`prefabs.lua:25-29`），声明在预制体的 `assets` 列表里：

```lua
Prefab = Class( function(self, name, fn, assets, deps, force_path_search)
    self.name = string.sub(name, string.find(name, "[^/]*$"))
    self.desc = ""
    self.fn = fn
    self.assets = assets or {}
    self.deps = deps or {}
    self.force_path_search = force_path_search or false
    ...
end)
```

**这个设计的三个优点**：

1. **零执行语义。** 解析 `Asset(...)` 不需要跑任何代码，所以工具链（打包、校验、分析依赖）可以直接用文本解析处理 Lua 源码，不需要嵌入解释器。
2. **依赖图是免费得到的。** `TheSim:RegisterPrefab(name, assets, deps)`（`0x140132b00`）拿到的就是完整依赖边。原生侧据此建立"哪些预制体需要哪些资源"的反向索引，于是 `LoadPrefabs(["player_wilson"])` 能自动把它的所有 ANIM/SOUND/ATLAS 拉进来。
3. **模组可以用同一套语法。** 模组作者的 prefab 里写 `Asset("ANIM", "mods/mymod/anim/hero.zip")`，走完全相同的路径解析。

**14 种类型的语义分组**（按实测数量从大到小）：

```
"包裹型"（指向整个 zip/包）
  PKGREF         4417   通用包引用（动画包、皮肤包、未分类的 zip）
  ANIM           3606   动画包 zip
  DYNAMIC_ANIM   3392   动态皮肤包 zip
  DYNAMIC_ATLAS   870   动态皮肤图集
  SOUND           210   FMOD .fsb
  SOUNDPACKAGE     56   FMOD .fev 事件工程

"元素型"（指向图集里的一个具名元素）
  INV_IMAGE       454   物品栏图标
  MINIMAP_IMAGE   304   小地图图集元素

"文件型"（指向单个文件）
  IMAGE           368   单张 .tex
  ATLAS           211   图集 XML
  ATLAS_BUILD     307   图集 XML + 格子尺寸（param）
  SHADER          140   .ksh
  SCRIPT          158   Lua 模块（不是文件资源，是加载顺序依赖）
  FILE             88   原始文件
  FONT              2   BMFont zip（数量少，因为字体是全局的）
```

**关键设计点：`PKGREF` 承担了 4417 条（占全部声明的 34%）的"兜底"职责。** 这是一个务实的选择：当开发者不确定某资源属于哪一类、或者需要绕过类型检查时，用 `PKGREF`。代价是失去了类型安全（`ShouldIgnoreResolve` 里就得靠 `filename:find(".dyn")` 这种字符串匹配来判断，见引擎报告陷阱 8）。你的引擎如果想更严格，可以只保留具名类型，把 `PKGREF` 拆成具体类型 —— 但要准备好迁移 4000 多条声明的工作量。

### 2.4 阶段五：路径解析（本管线最精妙的一环）

见第 12 节【本版复核】引用的 `util.lua:585-650` 实现。这里补上它在整个管线中的位置与取舍：

**为什么路径解析要有缓存？** 启动时要解析的路径总数 = 4417(PKGREF) + 3606(ANIM) + 3392 + 870 + 454 + 368 + 307 + 304 + 211 + 210 + 158 + 140 + 88 + 56 ≈ **15,481 条**（去重后更少）。每条要遍历 `package.assetpath`（基础 1 条 + 每个启用的模组 1 条）。一个装了 50 个模组的玩家 → 15,481 × 51 ≈ **79 万次文件系统探测**。`memoizedFilePaths`（`util.lua:574`）把这个降到接近 0。

**为什么缓存能跨启动持久化？** `GetMemoizedFilePaths()`（`util.lua:576-578`）用 `ZipAndEncodeSaveData` 序列化整张表，随 `Settings.memoizedFilePaths` 存进用户配置；`main.lua:495-500` 在启动时 `SetMemoizedFilePaths(Settings.memoizedFilePaths)` 恢复。这是一次**典型的"用序列化绕过昂贵重建"**优化。

**逆序搜索 = 模组覆盖**（`ipairs_reverse`）。这是模组系统的基石，值得在自己的项目里直接采用：

```lua
-- util.lua:607 —— 后插入的路径先被搜索
for i, pathdata in ipairs_reverse(searchpaths) do
```

由于 `mods.lua:576` 按模组加载顺序 `table.insert` 追加，逆序遍历 ⇒ **最后加载的模组覆盖先加载的**。这与 Steam Workshop 的加载顺序语义一致，用户能预期"我最后装的模组赢"。

**`search_first_path` 优化**（`util.lua:599-604`）：某些预制体能从上下文推断出资源最可能所在的目录（`Prefab` 的 `force_path_search` / `search_asset_first_path` 字段就是这个的载体，见 `mainfunctions.lua:168`）。先试这一条，命中就省掉整个遍历。

### 2.5 阶段六至七：注册与生命周期

**注册期做全部验证，运行期零失败。** `mainfunctions.lua:107-125`：

```lua
function RegisterPrefabsImpl(prefab, resolve_fn)
    for i,asset in ipairs(prefab.assets) do
        if not ShouldIgnoreResolve(asset.file, asset.type) then
       		resolve_fn(prefab, asset)
        end
    end
    modprefabinitfns[prefab.name] = ModManager:GetPostInitFns("PrefabPostInit", prefab.name)
    Prefabs[prefab.name] = prefab
    TheSim:RegisterPrefab(prefab.name, prefab.assets, prefab.deps)
end

local function RegisterPrefabsResolveAssets(prefab, asset)
    local resolvedpath = resolvefilepath(asset.file, prefab.force_path_search, prefab.search_asset_first_path)
    assert(resolvedpath, "Could not find "..asset.file.." required by "..prefab.name)  -- ★
    TheSim:OnAssetPathResolve(asset.file, resolvedpath)      -- ★ 通知引擎：原始路径 → 解析后路径
    asset.file = resolvedpath
end
```

两处关键：
- **`assert(resolvedpath, ...)` 在注册期** —— 资源缺失在加载阶段就炸，而不是在玩家用到时才炸。
- **`TheSim:OnAssetPathResolve(asset.file, resolvedpath)`** —— 引擎侧维护一张"逻辑路径 → 物理路径"的映射表。这张表就是 `resolvefilepath()` 在运行期能被缓存的依据，也是调试工具（"这个资源到底从哪加载的"）的数据源。

**异步批量预热**（`mainfunctions.lua:127-131`）：

```lua
local function VerifyPrefabAssetExistsAsync(prefab, asset)
	-- this is being done to prime the HDD's file cache and ensure all the assets exist before going into game
	TheSim:AddBatchVerifyFileExists(asset.file)
end
```

用 `RUN_GLOBAL_INIT` 决定走同步还是异步路径（`main.lua:401-403`）。**这里的意图值得注意**：这些 `VerifyFileExists` 调用不是为了检查资源存在（注册期的 `resolvefilepath` 已经检查过了），而是为了**预热磁盘页缓存** —— 让首次进游戏时的资源读取不触发物理 I/O。这是"启动时间优化"里最容易被忽略的一招。

**加载/卸载的粒度是预制体**（`gamelogic.lua:205-284` 的 `TheSim:LoadPrefabs(...)` / `TheSim:UnloadPrefabs(...)`），不是单个资源：

```lua
TheSim:UnloadPrefabs(Settings.loaded_characters)           -- 退出游戏时卸载角色
TheSim:UnloadPrefabs(RECIPE_PREFABS)                      -- 退出配方界面时卸载
TheSim:UnloadPrefabs({ special_event.."_event_backend" })  -- 事件后端
TheSim:UnloadPrefabs({ Settings.last_world_asset })         -- 上一个世界的资源
TheSim:LoadPrefabs(FRONTEND_PREFABS)                      -- 主菜单资源
TheSim:LoadPrefabs(SPECIAL_EVENT_FRONTEND_PREFABS)
TheSim:LoadPrefabs(FESTIVAL_EVENT_FRONTEND_PREFABS)
```

**资源生命周期因此挂在预制体上** —— 引用计数归零即释放。这就是原文第 14 节第 7 条"可被垃圾回收的资源生命周期"的实现机制。

### 2.6 模组的热重载

DST 的模组资产重载走一个专门的路径（`mainfunctions.lua:198-214`）：

```lua
function ModReloadFrontEndAssets(assets, modname)
    assert(KnownModIndex:DoesModExistAnyVersion(modname), ...)
    if assets then
        ModUnloadFrontEndAssets(modname)             -- ① 先卸载
        assets = shallowcopy(assets)                -- ② 浅拷贝，避免模组代码后续改动影响
        for i, v in ipairs(assets) do
            local modroot = MODS_ROOT..modname.."/"
            resolvefilepath_soft(v.file, nil, modroot)   -- ③ 用模组根目录做软解析
        end
        local prefab = Prefab("MODFRONTEND_"..modname, nil, assets, nil)
        table.insert(MOD_FRONTEND_PREFABS, prefab.name)
        RegisterSinglePrefab(prefab)                -- ④ 重新注册
        TheSim:LoadPrefabs({prefab.name})           -- ⑤ 重新加载
    end
end
```

四个值得抄的细节：
1. **卸载 → 改路径 → 注册 → 加载** 的四步固定顺序。
2. **`shallowcopy(assets)`** —— 拷贝一份，防止模组代码在热重载之后修改了原表导致状态不一致。
3. **`resolvefilepath_soft(v.file, nil, modroot)`** —— 用软版本（失败返回 nil 不 assert），因为模组资源本来就可能缺失。
4. **伪预制体命名 `MODFRONTEND_<modname>` / `MODPRELOAD_<modname>`**（`mainfunctions.lua:209`、`242`）—— 把"模组的资源包"包装成一个虚拟预制体，从而**复用同一套加载/卸载/引用计数机制**，不需要为模组单开一条代码路径。这是很典型的"用已有抽象吃掉新需求"。

## 【移植指引】面向自研引擎的抽象映射

把上述每一项资源能力映射到与引擎无关的接口。目标是：**这套接口能在没有图形设备的环境（专用服务器、构建机）里也存在**，只是返回空实现。

| `TheSim:RegisterPrefab(name, assets, deps)` | `IPrefabRegistry.Register(name, assetList, deps)` | Sim | 建反向索引 |
| `TheSim:LoadPrefabs(names)` | `IPrefabRegistry.Load(names)` | Sim | 按依赖图闭包加载 |
| `TheSim:UnloadPrefabs(names)` | `IPrefabRegistry.Unload(names)` | Sim | 引用计数归零释放 |
| `ShouldIgnoreResolve` | `IAssetPolicy.ShouldLoad(type, path, platform)` | Sim | 注册期决策，三层过滤 |
| `AddBatchVerifyFileExists` | `IVFS.Prefetch(paths[])` | Sim | 异步预热页缓存 |
| `ManifestManager` | `IManifest.Seen(path) -> mtime` | Sim | 支撑热重载 |
| `hashes.txt` | `IManifest.Verify(bundleName) -> bool` | Sim | 校验和 + 版本标记 |

| 模组写入沙箱 | `ISaveIO` 的路径白名单（见引擎报告） | Sim | 目录 + 扩展名双白名单 |

### 四条必须遵守的约束

1. **资源路径解析必须存在于服务器构建里。** 服务器不渲染，但它仍然要解析预制体的资源声明（为了 `ShouldIgnoreResolve` 的过滤决策与依赖图计算）。这一条决定了 `IVFS` 不能被划进"表现层"。

2. **打包期的不变式必须在打包器里断言，不能留到运行时。** DST 的 `8 + 10N + Σ data_size == filesize` 之所以能对 1519/1519 成立，是因为打包工具保证了它。同理，空 zip 要放占位文件（`klump.zip`）。

3. **资源声明保持"零执行语义"。** `Asset(...)` 是纯数据对象（`prefabs.lua:25-29`），这样打包工具、依赖分析器、模组校验器都能用文本解析处理 Lua 源码而不必嵌入解释器。一旦你让 `Asset(...)` 可以调用函数，这条管线就断了。

4. **模组资源必须走与本体完全相同的加载路径。** DST 靠 `package.assetpath` 的层列表 + `ipairs_reverse` 逆序实现覆盖（`util.lua:607`），并用伪预制体 `MODFRONTEND_<modname>` 复用加载/卸载机制（`mainfunctions.lua:209`）。**不要给模组单开一条代码路径** —— 那是所有资源管理 bug 的温床。

## 【实现清单】

按流水线阶段排列。工具侧（①②③）可以独立于引擎先做完。

### 阶段一：纹理格式（工具侧）

- [ ] **定义容器格式**：4B magic + 4B flags + 每 mip 10B 记录 + 拼接载荷
- [ ] **确定 flags 位分配**：mip 数占 bits 13-16；格式 id 分配在低字节；bits 18-31 留作签名冗余
- [ ] **写读取器**：读头 → 读 mip 表 → 用 `pitch` 反推格式 → 返回 mip 链
- [ ] **写写入器**：接受已编码的 mip 数据，包头输出
- [ ] **实现尺寸不变量断言**：`hdr + Σ record + Σ payload == filesize`，在**打包器**里就检查
- [ ] **实现格式判别的三重冗余**：flags 位、`pitch` vs `width` 关系、以及你额外加的一路；至少两路一致才接受
- [ ] **决定 BC1/BC3/未压缩的分配规则**：带 alpha → BC3；无 alpha 遮罩 → BC1；LUT/数据类 → 不压缩
- [ ] **mip 生成**：完整 mip 链（KTEX 实测出现过 1、3、5、6、7、8、9、10、11、12 级）
- [ ] **行序决策**：显式记录"自底向上"或"自顶向下"，并在解码器与图集描述符之间保持一致
- [ ] **端到端验证脚本**：遍历全量资源，输出格式分布与失败列表（本次实测：1519 文件 / BC3 1381、BC1 105、RGB888 33 / 失败 0）

### 阶段二：图集打包（工具侧）

- [ ] **打包器**：maxrects 或类似算法；输出单张图 + XML 描述符
- [ ] **半纹素内缩**：`u1 += 0.5/w`、`u2 -= 0.5/w`、`v1 += 0.5/h`、`v2 -= 0.5/h`
- [ ] **V 轴方向**：与纹理行序一致；打包器与运行期必须一致
- [ ] **不做旋转**：显式关闭并断言输出里不含旋转字段
- [ ] **变体标签**：支持 `variant="a|b|c|"`（注意空串是合法值，表示"不需要重着色"）
- [ ] **元素名规范**：允许保留假扩展名（`.tex`）作为查找键，或强制纯名 —— 选定一种并贯彻
- [ ] **元素完整性校验**：同一图集内所有元素不得重叠；重叠会导致 mip 渗色

### 阶段三：动画格式（工具侧）

- [ ] **定义 bank 格式**：符号表（名字 + UV 矩形 + 轴心 + 尺寸）
- [ ] **定义 timeline 格式**：动画名 + fps + 关键帧序列（按符号索引）
- [ ] **bank 与 build 分离**：允许只发 build 包（皮肤换装依赖于此）
- [ ] **写出为 zip**：`anim.bin` + `build.bin` + `atlas-N.tex` 三条目约定
- [ ] **空包占位策略**：拒绝产出零条目 zip，或强制写入占位条目（照抄 `klump.zip` 的做法）
- [ ] **确定性输出**：同一输入两次打包产出的字节完全一致（便于校验和）

### 阶段四：着色器容器（工具侧）

- [ ] **定义容器**：块名表（含 sampler 数组长度）+ 每个 stage 的明文源码
- [ ] **uniform 初值内联**：`float defaults[elemCount]` 直接放在记录里
- [ ] **sampler 判别标志**：用一个常量（如 `0x2b`）区分"带初值的 uniform"与"sampler"
- [ ] **源码 NUL 结尾**：`srcLen` 是否含 NUL 必须在格式文档里写死（本版实测：含）
- [ ] **尾部元数据**：属性/常量槽位计数（本版推断为 `{reserved, psAttrCount, vsAttrCount, …}`）
- [ ] **往返测试**：写出的文件能被自己的读取器解析，且全部 68 个样本文件都能按同一布局解析
- [ ] **预处理器**：支持平台宏（对应 Klei 的 `SKINNED`/`HOLO`/`BLOOM`/`TRIPLE_ATLAS` 等 8 个开关）

### 阶段五：字体（工具侧）

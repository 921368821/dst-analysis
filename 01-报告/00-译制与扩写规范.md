# 报告译制与扩写规范

本规范用于将已有的 7 份英文拆解报告译制为中文，并在此基础上深度扩写。

---

## 一、译制原则

### 1. 忠于原意，但不做直译
英文报告是高度技术化的分析文本，直译成中文会晦涩难读。要求：
- **保留全部技术判断与结论**，不弱化、不含糊
- **重写表达方式**：拆解长句、补充主语、用中文技术写作习惯重组
- **保留全部代码引用、文件路径、行号**，这些是可验证的事实，一个都不能丢

### 2. 扩写方向（原版未覆盖但对仿写有价值的内容）
在忠实译制的基础上，补充以下内容。补充部分要**明确标记**，与译文区分：

```markdown
> **【深度扩写】** 以下内容为原版报告未覆盖、但对仿写实现关键的部分。
```

扩写选题（按优先级）：
1. **可运行的实现路径**：这段代码要移植到自己的引擎里，该怎么写
2. **调用链的完整展开**：原版只说了 A 调B，补出 A→B→C 的完整链路
3. **数据结构的具象化**：用伪代码/结构体/表结构把抽象描述落地
4. **边界与陷阱**：作者原版没提但实际开发会踩的坑
5. **与其它系统的耦合关系**：这个模块如何被别的模块依赖

### 3. 禁止事项
- ❌ 不得编造原版没有的结论。扩写内容必须基于实际源码，且标注引用文件与行号
- ❌ 不得删减原版的分析细节
- ❌ 不得把「已验证事实」与「推断」混为一谈 —— 推断必须标注「推断」
- ❌ 代码块内的代码保持原样（可加中文注释行，但不改动代码本身）

---

## 二、术语处理

统一使用 `00-注释规范与术语表.md` 中的译名。补充约定：

| 情况 | 处理方式 |
|---|---|
| 已有固定中文译名 | 直接用（见术语表） |
| 无固定译名 | **首次出现时**给出「英文（中文）」，之后用中文 |
| API / 函数名 | 保留英文原名，用反引号包裹，如 `SpawnPrefab()` |
| 文件路径 | 保留原样并用反引号包裹 |
| 代码变量 | 保留英文原名 |

---

## 三、章节结构标准

每份报告统一采用以下结构：

```markdown
# 《饥荒联机版》<主题>（中文详尽版）

> **原文对应**：<原英文文件名>
> **本版说明**：译制 + 深度扩写。扩写部分以>【深度扩写】标注。

## 概述 / TL;DR
（先给结论，再展开）

## <正文章节>
（对应原文结构，逐节译制，保留原文的层级与引用）

## 【深度扩写】<新增主题>
（补充的实现指导、调用链、代码骨架）

## 【移植指引】<引擎相关>
（面向自研引擎的抽象与映射）

## 【实现清单】
（要做出这个系统，需要做什么——可勾选的任务列表）
```

---

## 四、质量要求

每份报告交付前自查：
- [ ] 原文所有代码引用、文件路径、行号均已保留
- [ ] 原文所有技术结论均已译出，无遗漏
- [ ] 扩写部分已标注，且基于实际源码
- [ ] 术语与术语表一致
- [ ] 有「实现清单」章节
- [ ] 中文表达通顺，无直译腔

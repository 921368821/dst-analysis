## 概述 / TL;DR

- **一切都是跑在 C++ "Sim" 之上的 Lua。** 原生侧（以全局对象 `TheSim`、`TheNet`、`TheAudio`、`TheGameService`、`TheSystemService`、`TheShard`、`TheInventory` 等形式暴露）掌管渲染、物理步进、网络与帧时钟；Lua 掌管**全部**玩法逻辑。
- **面向对象只有一个约 250 行的元表技巧**（`class.lua`）。`Class(base, ctor, props)` 返回一个既当类、又当实例元表的 table；像调用函数一样调用它就构造实例。它支持单继承，以及通过隐藏的 `_` 表实现的属性 **setter** 和 **只读属性**。
- **实体是原生实体对象外面一层很薄的 Lua 包装（`EntityScript`）。** 预制体（prefab）只是一个具名工厂函数（`fn`）加上资产/依赖清单。`SpawnPrefab("x")` 调用工厂，工厂先 `CreateEntity()`，挂上原生"底层组件"（`Transform`、`AnimState`、`Physics`、`Network`……）、打标签，然后挂 Lua **组件**。
- **组件是普通的 `Class` 对象**，存放在 `inst.components[name]` 里。它们挂接一组约定俗成的生命周期回调（`OnSave`/`OnLoad`/`OnUpdate`/`LongUpdate`/`OnEntitySleep`/`OnEntityWake`/`OnRemoveFromEntity`）。这里没有任何继承——行为是按实体**组合**出来的。
- **事件总线是按实体粒度**的，内建在 `EntityScript:PushEvent` / `:ListenForEvent` 里。不存在全局总线对象；取而代之的做法是把 `TheWorld` 当作约定俗成的"全局"事件源（`TheWorld:PushEvent("ms_playerjoined", inst)`）。
- **时间是协程调度器，以刻（tick）为单位驱动的。** `DoTaskInTime` / `DoPeriodicTask` 往 `scheduler.attime[tick]` 里注册 `Periodic` 记录；`StartThread` 跑协程任务。原生循环依次调用 `Update(dt)`（模拟时间）、`WallUpdate(dt)`（真实时间，永远执行）和 `LongUpdate(dt)`（大时间步长跳跃）。
- **主从（服务端/客户端）切分被烙进了每一个预制体。** `inst.entity:SetPristine()` 会给网络同步状态拍快照；写在 `if not TheWorld.ismastersim then return inst end` 之后的代码**只在权威服务端执行**。客户端则拿到"副本"（replica）组件。
- **世界本身也是一个预制体。** `SpawnPrefab(savedata.map.prefab)` 创建出 `TheWorld` 实体，它持有地图、寻路器、世界状态，以及几十个管理型组件（刷怪器、时钟、天气等等）。

## 一、类系统

文件：`class.lua`（整个文件约 259 行）。

### 1.1 构造与继承

`Class(base, _ctor, props)` 构造出一个 table `c`，它同时充当**类本身**和它所有实例的**元表**。如果 `base` 是 table，它的字段会被**浅拷贝**进 `c`（所以方法是通过拷贝继承的，而不是靠原型链），同时 `c._base` 记录父类，供 `is_a` 检查使用：

```lua
-- class.lua:83
function Class(base, _ctor, props)
    local c = {}    -- a new class instance
    local c_inherited = {}
    if not _ctor and type(base) == 'function' then
        _ctor = base
        base = nil
    elseif type(base) == 'table' then
        for i,v in pairs(base) do      -- shallow copy of the base class
            c[i] = v
            c_inherited[i] = v
        end
        c._base = base
    end

    if props ~= nil then
        c.__index = __index            -- setter-aware lookup
        c.__newindex = __newindex
    else
        c.__index = c                  -- plain method lookup
    end
    ...
    c._ctor = _ctor
    c.is_a = _is_a
    c.is_class = _is_class
    c.is_instance = function(obj) return type(obj)=="table" and _is_a(obj, c) end
    setmetatable(c, mt)                -- mt.__call makes ClassName(...) construct
    ClassRegistry[c] = c_inherited
    return c
end
```

`mt` 上挂了一个 `__call`（class.lua:165/181），于是**调用类就等于构造实例**：

```lua
mt.__call = function(class_tbl, ...)
    local obj = {}
    if props ~= nil then obj._ = {} ... end   -- per-instance property table
    setmetatable(obj, c)
    if c._ctor then c._ctor(obj, ...) end      -- run constructor
    return obj
end
```

`is_a` 通过元表逐级上溯 `_base` 链（class.lua:15-22）。注意：由于继承是浅拷贝，子类覆写某个方法只是在 `c` 里重新赋值那个 key。

### 1.2 属性 setter 与只读

当第三个参数 `props` 被传入时，每个列出的 key 都会被存进一张隐藏的 `obj._[k] = {value, setterfn}` 表里，而原本的裸 key 被移除（`rawset(t, k, nil)`）。此后 `__newindex` 拦截写入，并以 `(实例, 新值, 旧值)` 调用 setter：

```lua
-- class.lua:36
local function __newindex(t, k, v)
    local p = rawget(t, "_")[k]
    if p == nil then rawset(t, k, v)           -- normal field
    else local old = p[1]; p[1] = v; p[2](t, v, old) end   -- setter
end
```

`makereadonly(t,k)`（class.lua:51）把 setter 换成 `onreadonly`，断言该值永不改变。`addsetter` / `removesetter` 可以在运行期增删 setter。

**这对游戏为什么重要：** 组件用 `props` setter 来让*被同步的*（网络化的）状态与副作用自动保持一致。见 `components/health.lua:62-114`，在那里给 `self.currenthealth` 赋值会透明地触发 `oncurrenthealth`，后者把值推到 `inst.replica.health` 并重算 HUD/可修复状态：

```lua
-- components/health.lua:18
local function oncurrenthealth(self, currenthealth)
    self.inst.replica.health:SetCurrent(currenthealth)
    self.inst.replica.health:SetIsDead(currenthealth <= 0)
    ...
end
local Health = Class(function(self, inst) self.inst = inst; self.maxhealth = 100; ... end,
    nil,                              -- no base class
    { maxhealth = onmaxhealth, currenthealth = oncurrenthealth, penalty = onpenalty, ... })
```

于是一句普通赋值 `self.currenthealth = 42` 就同时触发了网络同步与 HUD 更新。这是最值得照搬的一个模式：**带透明副作用的属性**。

## 二、启动流程

启动分两个阶段：`main.lua` 在每个 VM 实例里执行一次，之后原生引擎不断调用各个更新入口。

### 2.1 阶段一 —— `main.lua`（VM 创建时自上而下执行）

1. 设置 `package.path`，给 `math.random` 播种，定义平台判定（`IsConsole`、`IsSteam`……）与编译期开关（`CHEATS_ENABLED`、`ENCODE_SAVES`、`DEBUG_MENU_ENABLED`）——main.lua:1-82。
2. 向 `package.loaders[2]` 装入一个**自定义模块加载器**（main.lua:134-158），把 `require` 路由到原生的 `kleiloadlua`（支持模组感知），并把每个文件记进 `RequiredFilesForReload`（供热重载使用）。
3. `require("strict")` —— 装上全局变量声明守卫（见第八章）。
4. 一长串按顺序的 `require` 建立起引擎骨架：`config`、`vector3`、`mainfunctions`、`mods`、`json`、`tuning`、profile/language/strings，然后是 `class`、`util`、`actions`、`scheduler`、`stategraph`、`behaviourtree`、`prefabs`、`entityscript`、`recipes`、`brain`、`input`、`frontend`、`netvars`、`networking`、`physics`、`componentutil`……——main.lua:177-260。
5. 创建音频混音器 `TheMixer` 并压入 `"start"` 声音混合集（main.lua:280-283）。
6. **初始化更新循环要用的全局注册表**（main.lua:288-301）：
   ```lua
   Prefabs = {}; Ents = {}; AwakeEnts = {}
   UpdatingEnts = {}; NewUpdatingEnts = {}; StopUpdatingEnts = {}
   StaticUpdatingEnts = {}; WallUpdatingEnts = {}; num_updating_ents = 0
   ```
7. **通过 `global(...)` 声明每一个全局单例**，随后把它们置 nil（main.lua:308-371）：
   `TheCamera`、`TheFrontEnd`、`TheWorld`、`ThePlayer`、`AllPlayers`、`TheFocalPoint`、`TheRecipeBook`、`TheSkillTree`、`SaveGameIndex`……（`TheSim`/`TheNet`/`TheAudio` 由原生注入，这里*不*声明。）
8. `require` 地图/关卡/任务/房间定义（main.lua:374-378）。
9. 运行 `ModSafeStartup()`（main.lua:382-484），直接运行或在模组索引加载完毕后运行。它会：
   - `ModManager:LoadMods()`，重新翻译字符串；
   - `LoadPrefabFile("prefabs/global")` 与 `prefabs/event_deps`（注册常驻预制体）；
   - 加载成就、配方书、食谱图、技能树、剪贴册等；
   - 创建 `TheCamera = FollowCamera()`；
   - 创建 **`TheGlobalInstance`** 这个非网络实体，并挂上原生管理器（`ShadowManager`、`RoadManager`、`EnvelopeManager`、`PostProcessor`、`FontManager`、`MapLayerManager`）；
   - 调用一次 `GlobalInit()`（mainfunctions.lua:1447），后者执行 `TheSim:LoadPrefabs({"global"})` 与 `LoadFonts()`。
10. 应用实例参数/设置，然后 `require` `consolecommands`，若开启作弊再加载 `debugcommands`/`debugkeys`。

`main.lua` **不会**创建世界。它只注册预制体并启动前端这条路径。

### 2.2 阶段二 —— `Start()` 与「前端 → 世界」流程

`mainfunctions.lua:1410 Start()` 由引擎调用：它创建 `TheFrontEnd = FrontEnd()`、`require("gamelogic")`、检查磁盘权限、加载 `customcommands.lua`，并执行 `CheckControllers()`。

随后 `gamelogic.lua` 在自己被 require 时（文件底部）驱动"该加载哪个世界"的决策：它构造 `SaveGameIndex`、`ShardGameIndex`、`Morgue` 等，并启动一条异步链 `Profile:Load → SaveGameIndex:Load → ShardSaveGameIndex:Load → ShardGameIndex:Load(OnFilesLoaded)`（gamelogic.lua:1297-1303）。`OnFilesLoaded → OnUpdatePurchaseStateComplete → DoResetAction`。

`DoResetAction()`（gamelogic.lua:1135）读取 `Settings.reset_action`，然后二选一：
- `LOAD_FRONTEND` → `LoadAssets("FRONTEND")` + `TheFrontEnd:ShowScreen(MainScreen(Profile))`（主菜单）；
- `LOAD_SLOT`/`LOAD_FILE`/`JOIN_SERVER`/`DO_DEMO` → 加载或生成一个世界（`LoadSlot` → `DoGenerateWorld`/`DoInitGame`）。

`DoInitGame(savedata, profile)`（gamelogic.lua:821）校验存档、重建道路，然后调用 `PopulateWorld`（gamelogic.lua:368），后者执行关键一步：

```lua
-- gamelogic.lua:400
local world = SpawnPrefab(savedata.map.prefab)   -- e.g. "forest" -> creates TheWorld
world.worldprefab = savedata.map.prefab
assert(TheWorld == world)                        -- world.lua sets TheWorld = inst inside its fn()
```

`PopulateWorld` 接着设置地图尺寸、加载地块与导航数据、生成 `*_network` 与 `shard_network` 实体（仅服务端），并**实例化每一个被保存的实体**：

```lua
-- gamelogic.lua:623
local newents = {}
for prefab, ents in pairs(savedata.ents) do
    for i, v in ipairs(ents) do
        v.prefab = v.prefab or prefab
        SpawnSaveRecord(v, newents)              -- mainfunctions.lua:438
    end
end
-- second pass hooks up cross-entity references:
for k, v in pairs(newents) do v.entity:LoadPostPass(newents, v.data) end
```

`SpawnSaveRecord` 调用 `SpawnPrefab`、设置位置，然后调用 `inst:SetPersistData(saved.data, newents)`，后者把数据派发给每个组件的 `OnLoad`。

### 2.3 阶段三 —— 帧循环（原生 → Lua）

C++ 引擎每帧调用下列 Lua 全局函数，它们定义在 `update.lua`：

- `WallUpdate(dt)`（update.lua:33）—— **真实时间，永远执行**（即使暂停）：排空 RPC 队列、依据 `TheFocalPoint` 设置活动区域中心点、更新 wall-time 组件、`TheMixer`、`TheCamera`、`TheInput`、`TheFrontEnd`。
- `Update(dt)`（update.lua:224）—— **模拟时间，暂停期间不会被调用**（它会对此 assert）。逐刻推进调度器直到 `TheSim:GetTick()`，然后对 `UpdatingEnts` 里每个实体执行 `OnUpdate`，接着推进状态图（`SGManager:Update`）与脑（`BrainManager:Update`）。
- `StaticUpdate(dt)`（update.lua:169）—— 运行 `staticScheduler`，并在暂停期间运行静态组件。
- `PostUpdate(dt)`、`PostPhysicsWallUpdate(dt)` —— 发射器、平台后置更新。
- `LongUpdate(dt, ignore_player)`（update.lua:301）—— 一次性快进大量实体（用于跳过夜晚、从洞穴返回等）：对每个实体调用 `v:LongUpdate(dt)`，再扇出到每个组件的 `LongUpdate`。

## 三、预制体解剖

**预制体**由 `prefabs/` 下的文件返回一个 `Prefab(name, fn, assets, deps)` 对象完成注册。`Prefab` 与 `Asset` 都是极小的 `Class`（prefabs.lua:6 与 :25）：

```lua
-- prefabs.lua:6
Prefab = Class( function(self, name, fn, assets, deps, force_path_search)
    self.name = string.sub(name, string.find(name, "[^/]*$"))
    self.fn = fn                 -- the factory
    self.assets = assets or {}   -- list of Asset(type, file)
    self.deps = deps or {}       -- names of prefabs this one may spawn (so they get loaded)
end)
Asset = Class( function(self, type, file, param) self.type=type; self.file=file; self.param=param end)
```

文件通过 `LoadPrefabFile`（mainfunctions.lua:145）加载：它 `loadfile` 脚本、执行它，并对每一个满足 `:is_a(Prefab)` 的返回值调用 `RegisterPrefabs` → `TheSim:RegisterPrefab`。`deps` 很重要，因为引擎只*加载*那些可达的预制体；把某个会生成的预制体列进 `deps`，就能保证它的资产常驻内存。

### 3.1 工厂 `fn` 注解示例：`prefabs/twigs.lua`（一个简单物品）

```lua
-- prefabs/twigs.lua:1
local assets = { Asset("ANIM", "anim/twigs.zip"), Asset("SOUND", "sound/common.fsb") }
local prefabs = { "oceanfishingbobber_twig_projectile" }   -- deps

local function fn()
    local inst = CreateEntity()             -- EntityScript wrapper + native entity (mainfunctions.lua:486)

    inst.entity:AddTransform()              -- native "lower components":
    inst.entity:AddAnimState()              --   Transform, AnimState, Network, SoundEmitter,
    inst.entity:AddNetwork()                --   Physics, Light, DynamicShadow, MiniMapEntity ...

    MakeInventoryPhysics(inst)              -- adds native Physics with item collision (standardcomponents.lua:371)

    inst.AnimState:SetBank("twigs")         -- animation: bank = skeleton/state set, build = skin
    inst.AnimState:SetBuild("twigs")
    inst.AnimState:PlayAnimation("idle")

    inst:AddTag("cattoy"); inst:AddTag("renewable"); inst:AddTag("twigs")  -- string tags for queries

    MakeInventoryFloatable(inst, "med", nil, 0.68)

    inst.entity:SetPristine()               -- FREEZE the networked snapshot that clients replicate

    if not TheWorld.ismastersim then
        return inst                          -- CLIENTS STOP HERE (no authoritative components)
    end

    -- ===== server-only authoritative setup =====
    inst:AddComponent("inventoryitem")
    inst:AddComponent("stackable"); inst.components.stackable.maxsize = TUNING.STACK_SIZE_SMALLITEM
    inst:AddComponent("fuel");      inst.components.fuel.fuelvalue = TUNING.SMALL_FUEL
    inst:AddComponent("edible");    inst.components.edible.foodtype = FOODTYPE.ROUGHAGE
    MakeSmallBurnable(inst, TUNING.SMALL_BURNTIME)   -- adds 'burnable' + config
    MakeSmallPropagator(inst)
    MakeHauntableLaunchAndIgnite(inst)
    inst:AddComponent("inspectable")
    ...
    return inst
end

return Prefab("twigs", fn, assets, prefabs)
```

这里能看到几个关键概念：

- **原生"底层组件"**（`Transform`、`AnimState`、`Physics`、`Network`、`SoundEmitter`、`Light`、`DynamicShadow`、`MiniMapEntity`、`LightWatcher`、`Map`、`Pathfinder`……）通过 `inst.entity:AddXxx()` 添加。它们是 C++ 对象，在 Lua 包装上暴露为 `inst.Transform`、`inst.AnimState` 等。它们**不是** Lua 组件。
- **标签**是引擎侧的字符串标志，用于快速空间查询（`TheSim:FindEntities(x,y,z,r, mustTags, cantTags)`），也到处被 `HasTag` 检查。
- **`SetPristine()`** 标记了"被同步/被复制的状态"与"仅服务端状态"之间的分界线。它之前添加的一切都会镜像给客户端；`if not TheWorld.ismastersim then return inst end` 这道闸门保证权威组件只在服务端存在。
- **`Make*` 辅助函数**（`MakeInventoryPhysics`、`MakeSmallBurnable`、`MakeHauntableLaunchAndIgnite`、`MakeFeedableSmallLivestock`……）是一次性添加并配置多个组件的可复用打包。定义在 `standardcomponents.lua` 与 `componentutil.lua` 中。

### 3.2 一个结构物：`prefabs/campfire.lua`

骨架相同，外加一个 `MakePlacer`（建造时用的幽灵预览实体）和若干事件监听。该文件返回**多个**值：

```lua
-- prefabs/campfire.lua:231
return Prefab("campfire", fn, assets, prefabs),
    MakePlacer("campfire_placer", "campfire", "campfire", "preview"),
    Prefab("quagmire_campfire", quagmire_fn, assets, prefabs)
```

在 `fn` 内部，营火把组件接到回调与实体事件上：

```lua
-- prefabs/campfire.lua:176
inst:AddComponent("fueled")
inst.components.fueled.maxfuel = TUNING.CAMPFIRE_FUEL_MAX
inst.components.fueled:SetSections(4)
inst.components.fueled:SetSectionCallback(onfuelchange)   -- fired when fuel crosses a section
inst.components.fueled:InitializeFuelLevel(TUNING.CAMPFIRE_FUEL_START)

inst:ListenForEvent("onbuilt", onbuilt)                   -- entity event bus
inst.OnSave = OnSave                                       -- per-entity save/load hooks
```

`MakePlacer`（prefabutil.lua:1）创建一个不联网、不持久化、带 `placer` 标签的实体，外加一个 `placer` 组件，负责渲染建造幽灵并校验放置合法性。

### 3.4 一个玩家角色：`prefabs/wilson.lua` → `player_common.lua`

角色不自己手写 `fn`；它们调用共享工厂 `MakePlayerCharacter`：

```lua
-- prefabs/wilson.lua:171
return MakePlayerCharacter("wilson", prefabs, assets, common_postinit, master_postinit)
```

`MakePlayerCharacter(name, customprefabs, customassets, common_postinit, master_postinit, starting_inventory)`（player_common.lua:1980）构建出一大份公共资产清单，然后定义 `fn`（player_common.lua:2411）：先加所有原生组件，调用 `common_postinit(inst)`（**服务端与客户端都会执行**，在 `SetPristine` 之前），然后在 `ismastersim` 闸门之后添加权威组件（`locomotor`、`combat`、`inventory`、`health`、`hunger`、`sanity`……），最后调用 `master_postinit(inst)`。顺序如下：

```lua
-- player_common.lua:2547  (common_postinit runs for everyone)
if common_postinit ~= nil then common_postinit(inst) end
...
-- player_common.lua:2623
inst.entity:SetPristine()
if not TheWorld.ismastersim then return inst end   -- clients stop
...
-- player_common.lua:2693+  (server-only)
inst:AddComponent("locomotor"); inst:AddComponent("combat"); inst:AddComponent("inventory")
inst:AddComponent("health"); inst:AddComponent("hunger"); inst:AddComponent("sanity")
...
if master_postinit ~= nil then master_postinit(inst) end   -- player_common.lua:2936
...
TheWorld:PushEvent("ms_playerspawn", inst)                 -- player_common.lua:2977
return Prefab(name, fn, assets, prefabs)
```

于是这套 DSL 的词汇表就是：`assets`（要流式加载什么）、`prefabs`/`deps`（要预载什么）、`fn`（工厂）、`common_postinit`（客户端+服务端微调）、`master_postinit`（服务端微调）。对角色来说这些是作为参数传入的；对简单预制体来说它们直接内联在 `fn` 里。

## 四、组件解剖

**组件**就是一个 `Class`，其构造函数接收所属实体（`inst`），并返回类表。文件位于 `components/<name>.lua`，由 `AddComponent` 惰性加载。

### 4.1 `AddComponent` 如何工作 —— `entityscript.lua:610`

```lua
function EntityScript:AddComponent(name)
    local lower_name = string.lower(name)
    if self.lower_components_shadow[lower_name] ~= nil then ... return existing end   -- idempotent
    local cmp = LoadComponent(name)                    -- require("components/"..name), cached
    self:ReplicateComponent(name)                      -- create client replica if networked
    local loadedcmp = cmp(self)                        -- construct: Class __call -> _ctor(self, inst)
    self.components[name] = loadedcmp                  -- attach to inst.components
    self.lower_components_shadow[lower_name] = true
    local postinitfns = ModManager:GetPostInitFns("ComponentPostInit", name)
    for _, fn in ipairs(postinitfns) do fn(loadedcmp, self) end   -- mod hooks
    self:RegisterComponentActions(name)                -- register interactive actions
    return loadedcmp
end
```

`LoadComponent`（entityscript.lua:52）把类缓存在模块局部的 `Components` 表里，并向其注入 `WatchWorldState`/`StopWatchingWorldState` 辅助函数。`RemoveComponent`（entityscript.lua:648）会调用 `OnRemoveFromEntity`、取消复制并注销动作。

### 4.2 标准组件形态 —— `components/health.lua`

一个典型组件会声明：

1. **构造函数**（`Class(function(self, inst) ... end, base, props)`）—— 保存 `self.inst`、设置默认值、可选地注册属性 setter 并启动一个更新任务。
2. **属性 setter**，把值同步到 `inst.replica.<name>`（客户端可见镜像）。
3. **公共方法**，供游戏其余部分调用（`DoDelta`、`SetPercent`、`Kill`、`IsDead`……）。
4. **生命周期回调**，由引擎/实体派发：
   - `OnUpdate(dt)` —— 仅当调用过 `inst:StartUpdatingComponent(self)` 才会执行。
   - `LongUpdate(dt)` —— 批量时间跳跃的追赶。
   - `OnSave()` → 返回一个 table（以及可选的引用列表）；`OnLoad(data, newents)`。
   - `OnEntitySleep()` / `OnEntityWake()` —— 实体进入/离开活动模拟区域。
   - `OnRemoveFromEntity()` / `OnRemoveEntity()` —— 清理。

health 的 `DoDelta` → `SetVal` 展示了典范的"变更 → 钳制 → 派发事件"流程（components/health.lua:565）：

```lua
function Health:SetVal(val, cause, afflicter)
    local old_health = self.currenthealth
    self.inst:PushEvent("pre_health_setval", {val=val, old_health=old_health})
    ... clamp to max/min ...
    if old_health > 0 and self.currenthealth <= 0 then
        TheWorld:PushEvent("entity_death", { inst=self.inst, cause=cause, afflicter=afflicter, ... })
        self.inst:PushEvent("death", { cause=cause, afflicter=afflicter, ... })
        if self:CanFadeOut() then
            self.inst.persists = false
            self.inst.erode_task = self.inst:DoTaskInTime(self.destroytime or 2, ErodeAway)
        end
    end
end
```

health 只有在着火期间才逐帧更新（`DoFireDamage` 调用 `inst:StartUpdatingComponent(self)`，而 `OnUpdate` 在火焰超时时调用 `StopUpdatingComponent`）——这是**按需更新**而非永远 tick 的例子。

### 4.3 两种更新范式

- **周期任务**（components/hunger.lua:38）：组件自己排定 tick，绝不出现在 `UpdatingEnts` 里：
  ```lua
  local Hunger = Class(function(self, inst)
      self.inst = inst; self.max = 100; self.current = self.max
      self.burnratemodifiers = SourceModifierList(self.inst)
      self.updatetask = self.inst:DoPeriodicTask(UPDATE_PERIOD, OnTaskTick, nil, self)
  end, nil, { max = onmax, current = oncurrent })
  ```
  `Hunger:OnRemoveFromEntity()` 会取消该任务。
- **帧更新**（components/sanity.lua:122）：构造函数里调用 `self.inst:StartUpdatingComponent(self)`，于是 `Sanity:OnUpdate(dt)` 每个模拟帧都会跑。

### 4.4 带引用的存读档 —— `components/inventory.lua:192`

持有其他实体的组件会返回第二个值，列出被引用的实体，以便加载器在所有实体都生成之后解析 GUID：

```lua
function Inventory:OnSave()
    local data = {items={}, equip={}}; local references = {}; local refs = {}
    for k,v in pairs(self.itemslots) do
        if v.persists then data.items[k], refs = v:GetSaveRecord() ... end
    end
    ...
    return data, references
end
```

`EntityScript:GetPersistData`（entityscript.lua:1903）遍历组件逐个调用 `OnSave`；`EntityScript:SetPersistData`（entityscript.lua:1954）调用每个组件的 `OnLoad`。此外还有第二阶段的 `LoadPostPass`（entityscript.lua:1939），用于在所有实体都存在之后接上引用。

### 4.5 组件驱动的交互动作 —— `componentactions.lua`

交互动词（"PICK"、"CHOP"、"EAT"……）不是按实体硬编码的。一张大表 `COMPONENT_ACTIONS`（componentactions.lua:138）把 `actiontype → componentName → collector 函数` 映射起来。当一个组件被添加时，`RegisterComponentActions` 把它的数字 id 记录到实体上；之后 `CollectActions(actiontype, ...)`（componentactions.lua:3174）对实体的组件运行对应的 collector，构建出合法动作列表。collector 示例：

```lua
-- componentactions.lua:228 (SCENE actions)
book = function(inst, doer, actions)
    if doer:HasTag("reader") and not inst:HasTag("fire") then
        table.insert(actions, ACTIONS.READ)
    end
end,
```

正是这套机制让游戏能够纯粹依据对象的组件集合来回答"玩家能对这个物体做什么？"——一种干净的、数据驱动的替代方案，取代了巨型 switch 语句。

## 五、实体生命周期

1. **创建。** `SpawnPrefab(name)`（mainfunctions.lua:403）→ `TheSim:SpawnPrefab` → 引擎回调 Lua 的 `SpawnPrefabFromSim(name)`（mainfunctions.lua:347），后者运行 `prefab.fn(TheSim)`、设置预制体名、运行模组 post-init，然后 `TheWorld:PushEvent("entity_spawned", inst)`。`EntityScript` 包装是在 `fn` 内部由 `CreateEntity()`（mainfunctions.lua:486）创建的，它会把实体登记进 `Ents[guid]`。
2. **Pristine/网络。** `SetPristine()` 快照被同步状态；客户端构建 `replica` 组件而非权威组件。`ReplicateEntity`（mainfunctions.lua:814）在实体进入网络范围时于客户端运行。
3. **睡眠/唤醒。** 引擎决定哪些实体处于活动区域。状态切换时它调用 `OnEntitySleep(guid)` / `OnEntityWake(guid)`（mainfunctions.lua:670/699），它们推 `"entitysleep"`/`"entitywake"` 事件、启停脑、让状态图与发射器冬眠/唤醒，并调用每个组件的 `OnEntitySleep`/`OnEntityWake`。脑在睡眠时被拆除、唤醒时重建（`_DisableBrain_Internal`/`_EnableBrain_Internal`，entityscript.lua:1120/1135）。睡着的实体停止思考，但依然存在。
4. **保存。** `SaveGame`（mainfunctions.lua:1068）遍历 `Ents`；对每个满足 `v.persists and v.prefab and v.Transform and no parent and IsValid()` 的实体调用 `v:GetSaveRecord()`（entityscript.lua:248）→ 位置 + `GetPersistData()`（所有组件的 `OnSave`）。记录按预制体分组，用 `DataDumper`（一个 table→Lua 源码序列化器）导出。玩家会话单独保存。
5. **加载。** `SpawnSaveRecord`（mainfunctions.lua:438）重新生成每条记录、设置位置，然后 `SetPersistData`（派发各 `OnLoad`），最后由一次全局 `LoadPostPass` 解析跨实体引用。
6. **销毁。** `inst:Remove()`（entityscript.lua:1705）从父实体/平台脱离，调用 `OnRemoveEntity(GUID)`（mainfunctions.lua:501 —— 杀掉任务、移除脑与状态图、从更新列表摘除），推 `"onremove"`，停止世界状态监听，移除所有事件回调，取消挂起任务，调用每个组件的 `OnRemoveEntity`，递归移除子实体，最后 `self.entity:Retire()`。设置 `inst.persists = false` 会把它排除在下一次存档之外。

`LongUpdate(dt)`（entityscript.lua:2026）是一条独立的"大时间跳跃后追赶"路径，调用 `OnLongUpdate` 与每个组件的 `LongUpdate`。

## 六、事件系统

**不存在单一的全局事件对象。** 总线活在每个 `EntityScript` 上。

### 6.1 核心原语 —— `entityscript.lua`

```lua
-- entityscript.lua:1188
function EntityScript:ListenForEvent(event, fn, source)
    source = source or self                      -- default: listen to self
    AddListener(source.event_listeners, event, self, fn)   -- source records "who listens to me"
    AddListener(self.event_listening, event, source, fn)   -- self records "who I listen to"
end

-- entityscript.lua:1286
function EntityScript:PushEvent_Internal(event, data, immediate)
    if self.event_listeners then
        local listeners = self.event_listeners[event]
        if listeners then
            local tocall = {}                     -- copy first: handlers may mutate listener tables
            for entity, fns in pairs(listeners) do for i, fn in ipairs(fns) do tocall[#tocall+1]=fn end end
            for i, fn in ipairs(tocall) do fn(self, data) end   -- handler(source, data)
        end
    end
    if self.sg then ... self.sg:PushEvent(event, data) end       -- forward to state graph
    if self.brain then self.brain:PushEvent(event, data) end     -- forward to behaviour tree
end
```

双向记账（数据源上的 `event_listeners`，监听者上的 `event_listening`）使得 `RemoveAllEventCallbacks`（entityscript.lua:1232）能把一个实体干净地从"它监听的一切"以及"监听它的一切"上摘下来——这对避免 `Remove` 后出现悬空引用至关重要。

`PushEvent` 会缓冲状态图事件；`PushEventImmediate` 则同步派发（entityscript.lua:1317/1321）。

### 6.2 "全局"总线就是 `TheWorld`

因为每个实体都有一条总线，游戏就把世界实体当作事实上的全局频道。`ms_*`（master sim）事件被推到 `TheWorld` 上，并且只存在于服务端：

```lua
-- prefabs/player_common.lua:851 (OnPlayerJoined)
TheWorld:PushEvent("playerentered", inst)          -- server AND client
if TheWorld.ismastersim then
    TheWorld:PushEvent("ms_playerjoined", inst)     -- server only
    ...
end
-- prefabs/player_common.lua:1195 (OnRemoveEntity)
TheWorld:PushEvent("ms_playerleft", inst)
```

消费者以 `TheWorld` 作为显式数据源来订阅：

```lua
-- components/birdspawner.lua:411
inst:ListenForEvent("ms_playerjoined", OnPlayerJoined, TheWorld)
inst:ListenForEvent("ms_playerleft",   OnPlayerLeft,   TheWorld)
```

`OnPlayerLeave`（mainfunctions.lua:1761）类似地在 `TheWorld` 上推 `ms_playerdisconnected` 与 `ms_playerdespawn`。

`events.lua` 里还有一套**独立的、更简单的 `EventProcessor`/`EventHandler` 总线**（供 UI/界面使用，而非玩法实体）—— `AddEventHandler(event, fn)` / `HandleEvent(event, ...)`。

### 6.3 值得知道的事件

## 七、任务 / 更新系统

文件：`scheduler.lua`。时间被量化成**刻**；`GetTime() = TheSim:GetTick()*ticktime`（mainfunctions.lua:565）。存在两个调度器：`scheduler`（模拟时间）与 `staticScheduler`（真实/"静态"时间，暂停时仍运行）—— scheduler.lua:324。

### 7.1 数据结构

- `Task`（scheduler.lua:20）包装一个**协程**（`co`）。用于 `StartThread` 风格的脚本。
- `Periodic`（scheduler.lua:45）是一个普通记录 `{fn, period, limit, nexttick, arg, onfinish}` —— 用于定时器。`limit=1` → 一次性；`limit=nil` → 永久。
- `Scheduler` 持有 `tasks`、`running`、`waitingfortick`、`waking`、`hibernating`，以及 `attime`（一个 `tick → {Periodic=true}` 映射）。

### 7.2 调度 API

```lua
-- scheduler.lua:276
function Scheduler:ExecuteInTime(timefromnow, fn, id, ...)      -- one-shot
    return self:ExecutePeriodic(timefromnow, fn, 1, nil, id, ...)
end
function Scheduler:ExecutePeriodic(period, fn, limit, initialdelay, id, ...)  -- recurring
    local list, nexttick = self:GetListForTimeFromNow(initialdelay or period)
    local periodic = Periodic(fn, period, limit, id, nexttick, ...)
    list[periodic] = true; periodic.list = list
    return periodic
end
```

`GetListForTimeFromNow(dt)` 把 `now+dt` 秒换算成绝对的唤醒**刻**，并返回 `attime[tick]` 里的桶（scheduler.lua:280）。

### 7.3 刻 —— `Scheduler:OnTick(tick)`（scheduler.lua:164）

每个刻：把等待这一刻的协程移入 `waking`，然后对 `attime[tick]` 里的每个 `Periodic` 调用 `fn(unpack(arg))`、递减 `limit`，然后要么重新排进下一个桶（`GetListForTimeFromNow(period)`），要么触发 `onfinish` 并 `Cleanup`。`Scheduler:Run`（scheduler.lua:218）随后恢复协程任务，并解释它们的 yield 值：`Sleep(t)` yield `(SLEEP, desttick)`、`Hibernate()` yield `HIBERNATE`（停放到 `Wake()` 被调用）、裸 `Yield()` 则下一帧重跑。

### 7.4 面向实体的包装 —— `entityscript.lua`

```lua
function EntityScript:DoTaskInTime(time, fn, ...)          -- one-shot, auto-cancelled on Remove
    local periodic = scheduler:ExecuteInTime(time, fn, self.GUID, self, ...)
    self.pendingtasks = self.pendingtasks or {}
    self.pendingtasks[periodic] = true
    periodic.onfinish = task_finish                         -- cleans up pendingtasks entry
    return periodic
end
function EntityScript:DoPeriodicTask(time, fn, initialdelay, ...)   -- recurring
    local periodic = scheduler:ExecutePeriodic(time, fn, nil, initialdelay, self.GUID, self, ...)
    ...
end
```

注意 `fn` 总是把 `inst` 收到**第一个**参数（实体通过调度器的 `arg` 绑定），随后才是额外的 `...`。`self.GUID` 是任务 `id`，因此实体被移除时调用 `KillThreadsWithID(guid)` 就会取消该实体安排的一切。`DoStaticTaskInTime`/`DoStaticPeriodicTask` 使用 `staticScheduler`（暂停时仍运行 —— 用于菜单、存档流程、数据迁移）。

`DoPeriodicTask` 返回的 `Periodic` 对象带 `:Cancel()`（scheduler.lua:56）——组件正是靠它停掉自己的定时器（见 `Hunger:Pause`）。

**周期 vs 一次性 vs 帧更新小结：**
- `DoTaskInTime(t, fn)` —— 一次性延迟调用（limit 1）。
- `DoPeriodicTask(t, fn)` —— 固定周期的重复定时器（便宜；两次触发之间没有每帧开销）。
- `StartUpdatingComponent(cmp)` —— 每个模拟帧执行 `cmp:OnUpdate(dt)`（用于平滑/连续逻辑）。
- `StartThread(fn)` —— 可 `Sleep`/`Hibernate`/`Yield` 的协程（用于有序列的脚本、脑）。

## 九、值得照搬的关键模式

1. **玩法层用组合而非继承（轻量 ECS）。** 实体是笨容器；行为活在按名字添加的独立组件里（`AddComponent("health")`）。两个共享 `health`+`combat` 的实体行为相似，却不需要共同的基类。**为什么有效：** 你可以按预制体自由混搭能力、在运行时增删（`RemoveComponent`），且每个组件都小而可测。`Make*` 辅助打包（例如 `MakeSmallBurnable`）提供了可复用的"原型"，而没有僵硬的类树。

2. **带透明 setter 的属性。** `class.lua` 的 `props` 机制让 `self.currenthealth = x` 自动复制给客户端并刷新 HUD。**为什么有效：** 玩法代码读起来就是普通字段赋值，而网络同步与副作用依然正确——不存在被遗忘的"脏"标志。这是保持权威状态与复制状态同步的最干净方式。

3. **pristine / `ismastersim` 切分。** 一个工厂函数同时描述服务端与客户端的实体；`SetPristine()` + `if not TheWorld.ismastersim then return inst end` 干净地把被同步状态与权威逻辑分开。**为什么有效：** 实体的形状有了单一事实来源，且服务端专用代码有一条显眼的、可 grep 的分界线。客户端构建的是轻量的 `replica` 组件。

4. **预制体 = 数据 + 工厂，按名注册。** `Prefab(name, fn, assets, deps)` 把"实体是什么"与"它何时被创建"解耦，`assets`/`deps` 驱动内容流式加载。**为什么有效：** 任何地方都能 `SpawnPrefab("campfire")`；引擎可以预载/卸载资产集；模组可以通过 `PrefabPostInit` 钩子注入行为而无需改动工厂。

5. **按实体的��件总线 + 双向监听记账。** `PushEvent`/`ListenForEvent(event, fn, source)` 配合 `event_listeners` + `event_listening` 两张表。**为什么有效：** 生产者与消费者解耦（health 不知道谁在监听 `death`），而 `RemoveAllEventCallbacks` 保证销毁时没有悬空引用。用 `TheWorld` 作为约定俗成的全局频道，避免了再造一个单例总线。

6. **刻量化的调度器，协程 + 定时器并存。** 绝对刻桶（`attime`）管定时器，协程任务管有序列逻辑，配上 `Sleep/Hibernate/Yield`。**为什么有效：** 确定性、对存档友好（时间是整数刻）、廉价（定时器只在自己的触发刻产生开销），协程脚本读起来线性（对脑/AI 极友好）。绑定到实体的任务 id（`self.GUID`）让"死亡即取消"变得自动。

7. **按需逐帧更新。** 只有当组件调用 `StartUpdatingComponent` 时实体才进入 `UpdatingEnts`；`NewUpdatingEnts`/`StopUpdatingComponents` 把增删延后，以避免在遍历中修改列表。**为什么有效：** 你永远不会为上万个闲置实体支付每帧代价；组件只在相关时才打开 tick（health 只在燃烧时 tick）。

8. **存档 = 每组件 `OnSave`/`OnLoad` + 一趟引用解析。** `GetPersistData` 收集每个组件的表；`LoadPostPass`/`newents` 在所有实体存在之后解析 GUID 引用。**为什么有效：** 组件自己拥有序列化（没有中心 schema），两趟加载能安全处理任意跨实体链接（物品栏物品、跟随物）。

9. **严格全局纪律。** `strict.lua` 对未声明的全局读写报错；每个单例都显式 `global("X")` 声明。**为什么有效：** 笔误变成即时的、响亮的错误，而不是静默的 `nil`——在这样规模的 Lua 代码库里价值极高。

10. **数据驱动的交互动词。** `COMPONENT_ACTIONS` 把组件映射到动作收集器，于是"我能对它做什么？"是从实体组件算出来的。**为什么有效：** 增加一种新的可交互行为意味着加一个组件 + 一个收集器，而不是到处改输入/动词代码。

## 【深度扩写】一、类系统移植：从元表技巧到自研语言

`class.lua` 只有 259 行，但它是整个代码库的地基。下面给出三套可运行实现。

### 1.1 语义等价性分析（先看清 Lua 版本到底做了什么）

在动手翻译之前，必须先确认 Lua 版本的实际语义，否则很容易翻译错。

```lua
-- class.lua:83
if not _ctor and type(base) == 'function' then
    _ctor = base
    base = nil
elseif type(base) == 'table' then
    for i,v in pairs(base) do      -- shallow copy of the base class
        c[i] = v
        c_inherited[i] = v
    end
    c._base = base
end
```

**关键点 1（`Class(fn)` 的重载）**：`Health = Class(function(self, inst) ... end, nil, {...})` 里，`base` 位置收到的是函数，`_ctor` 是 `nil`，于是第一个分支成立，把 `base` 提升为 `_ctor`。而当 `Health = Class(function() ... end)` 时同样成立。所以"第一个参数是函数就意味着这是构造函数"。

**关键点 2（继承是浅拷贝）**：`c[i] = v` 直接把基类的成员值拷进子类表。这意味着：
- 运行时**修改基类**不会影响已创建的子类（Lua 里的类表是"编译期快照"）。
- 子类里 `c[i] = v` 的赋值是纯粹的覆盖，与原型链无关。

**关键点 3（`is_a` 靠元表而非 `_base` 字段）**：

```lua
-- class.lua:15
local function _is_a(self, klass)
	local m = getmetatable(self)
	while m do
		if m == klass then return true end
		m = m._base
	end
	return false
end
```

它从实例的元表（= 类表 `c`）出发，**读的是元表对象的 `_base` 字段**。子类 `c._base = base`，基类如果没有父类则 `base._base == nil`，循环自然终止。

**关键点 4（`props` 改变的是整个类的元表行为）**：一旦有 `props`，`c.__index = __index`、`c.__newindex = __newindex`。此时：
- 读取 `obj.k`：若 `rawget(obj,"_")[k]` 命中返回属性值，否则 `return getmetatable(t)[k]`（即 `c[k]`，方法走这条路）。
- 写入 `obj.k`：若 `rawget(obj,"_")[k]` 命中则走 setter，否则 `rawset(obj, k, v)`。

**这里有一个真实的坑（原文未提）**：`__index` 第一行是 `rawget(t, "_")[k]`。如果实例的 `_` 表不存在（比如某个类**没**传 `props`，但有人在其子类上传了 `props`），`rawget(t,"_")` 返回 `nil`，索引 `nil[k]` 会直接报错。实际上由于 `mt.__call` 里 `if props ~= nil then obj._ = {} end` 与 `c.__index = __index` 是同步的（同一个闭包捕获的 `props`），所以正常路径不会触发。但如果自研实现把这两处解耦（比如属性表延迟创建），就会踩到。

### 1.2 实现路径 A：继续用 Lua，但换成标准 `__index` 查表（更安全的变体）

```lua
-- myclass.lua —— 面向自研 Lua 引擎的等价实现
local ClassRegistry = {}

local function make_meta(props)
    local mt = {}
    mt.__index = function(t, k)
        local d = rawget(t, "_")
        if d ~= nil then
            local p = d[k]
            if p ~= nil then return p[1] end
        end
        local cls = getmetatable(t)
        -- 原版是 getmetatable(t)[k]；这里做原型链上溯，修复浅拷贝的缺陷
        while cls do
            local v = cls[k]
            if v ~= nil then return v end
            cls = rawget(cls, "_base")
        end
        return nil
    end
    mt.__newindex = function(t, k, v)
        local d = rawget(t, "_")
        local p = d and d[k]
        if p == nil then
            rawset(t, k, v)
        else
            local old = p[1]; p[1] = v; p[2](t, v, old)
        end
    end
    mt.__call = function(cls, ...)
        local obj = {}
        if props ~= nil then
            obj._ = {}
            for k, fn in pairs(props) do obj._[k] = { nil, fn } end
        end
        setmetatable(obj, cls)
        if cls._ctor then cls._ctor(obj, ...) end
        return obj
    end
    return mt
end

function Class(base, _ctor, props)
    if not _ctor and type(base) == 'function' then
        _ctor, base = base, nil
    end
    local c = {}
    local c_inherited = {}
    if type(base) == 'table' then
        for i, v in pairs(base) do
            c[i] = v; c_inherited[i] = v
        end
        c._base = base
    end
    setmetatable(c, make_meta(props))
    c._ctor = _ctor
    c.is_a = function(self, klass)
        local m = getmetatable(self)
        while m do
            if m == klass then return true end
            m = rawget(m, "_base")
        end
        return false
    end
    c.is_class = function(self) return rawget(self, "is_instance") ~= nil end
    c.is_instance = function(self, obj) return type(obj) == "table" and self.is_a(obj, self) end
    ClassRegistry[c] = c_inherited
    return c
end
```

差异只有两处，都是修正而非破坏：原型链上溯取代 `getmetatable(t)[k]`；`rawget(m,"_base")` 取代 `m._base`。**如果你要严格 1:1 复刻原版行为（包括热重载对浅拷贝的依赖），请保留原版写法。**

### 1.3 实现路径 B：C# / Unity

```csharp
// ClassRegistry.cs —— 把"类即元表"翻译成"类即 Type"
using System;
using System.Collections.Generic;
using System.Reflection;

public interface IClass { }

public class ClassBase
{
    // 模拟 obj._ —— 每实例的属性槽
    internal Dictionary<string, PropertySlot> Slots;

    internal class PropertySlot { public object Value; public Action<object, object, object> Setter; }

    protected virtual void OnConstruct() { }

    public T As<T>() where T : class => this as T;
    public bool IsA(Type t) => t.IsInstanceOfType(this);
}

public class Class<T> where T : ClassBase, new()
{
    public delegate void PropSetter(object inst, object v, object old);

    public Class() { }

    public T Create(params object[] args)
    {
        var inst = new T { Slots = new Dictionary<string, PropertySlot>() };
        typeof(Class<T>).GetField("_slots", BindingFlags.Static | BindingFlags.NonPublic)
              ?.SetValue(null, null);
        // 按声明顺序执行 setter 初始化，等价于原版 obj._[k] = {nil, v}
        foreach (var kv in RegisteredSetters) inst.Slots[kv.Key] = new PropertySlot { Setter = kv.Value };
        inst.OnConstruct();   // 注意：原版是 c._ctor(obj, ...)，构造器与实例创建是同一个动作
        return inst;
    }

    static readonly List<KeyValuePair<string, PropSetter>> RegisteredSetters = new();

    public static Class<T> Setter(string name, PropSetter setter)
    {
        RegisteredSetters.Add(new(name, setter));
        return this;
    }

    /// <summary>属性包装：赋值时透明触发 setter。</summary>
    public class Property<TV>
    {
        readonly string key; readonly ClassBase owner;
        public Property(ClassBase owner, string key) { this.owner = owner; this.key = key; }
        public TV Value
        {
            get => owner.Slots.TryGetValue(key, out var s) ? (TV)s.Value : default;
            set {
                if (!owner.Slots.TryGetValue(key, out var s)) { s = new PropertySlot(); owner.Slots[key] = s; }
                var old = s.Value; s.Value = value; s.Setter?.Invoke(owner, value, old);
            }
        }
    }
}

// 使用
public class Health : ClassBase
{
    private readonly Property<float> _current = new(this, "currenthealth");
    public float currenthealth { get => _current.Value; set => _current.Value = value; }

    public override void OnConstruct()
    {
        _current.Setter = (inst, v, o) =>
        {
            var h = (Health)inst;
            h.replica.SetCurrent((float)v);
            h.replica.SetIsDead((float)v <= 0f);
            h.repairable?.SetHealthRepairable((float)v < h.maxhealth);
        };
        maxhealth = 100f;   // 注意：赋值会触发 setter，与原版一致
    }
}
```

**C# 移植的三个真实差异：**
1. **构造顺序**。Lua 里 `c._ctor(obj, ...)` 在 `obj` 建好、`setmetatable` 之后执行，所以构造器里可以直接写 `self.maxhealth = 100`（会触发 setter）。C# 里 `new T()` 先跑字段初始化器再跑构造函数，如果你把默认值写在字段初始化器里，setter 还没注册 → 不会触发网络同步。**必须在 `OnConstruct` 里注册 setter 之后再赋默认值。**
2. **`props` 是编译期表**。Lua 的 `props` 是运行时 table，模组可以往里加 key。Unity C# 若要支持模组热插拔，需要把 `RegisteredSetters` 改成 `Dictionary` 并允许运行时 `Add`。
3. **`ClassRegistry` 的热重载用途**。原版把 `c_inherited`（继承来的成员快照）存进 `ClassRegistry`，配合 `ReloadedClass(mt)`（class.lua:216）让模组重载后能"删掉"旧类记录。这是**唯一用到拷贝语义的地方**——热重载补丁靠它区分"自己定义的"和"继承来的"。C# 版本要复刻热重载，必须同样保存 inherited 快照。

### 1.4 实现路径 C：C++ / 自研引擎（Godot GDScript 亦可照搬）

```cpp
// class.hpp
#pragma once
#include <unordered_map>
#include <vector>
#include <functional>
#include <memory>
#include <cassert>

namespace dst {

class Object {
public:
    virtual ~Object() = default;

    template <class T>
    T* As() { return dynamic_cast<T*>(this); }

    bool IsA(const Class* c) const {
        for (const Class* k = c; k; k = k->base) if (k == this->klass) return true;
        return false;
    }
    const Class* klass = nullptr;

protected:
    // 模拟 obj._ —— 属性槽表
    std::unordered_map<std::string, PropertySlot> slots_;
    friend class Class;
};

struct PropertySlot {
    std::any            value;
    std::function<void(Object*, const std::any&, const std::any&)> setter;
};

class Class {
public:
    std::string                 name;
    const Class*                base = nullptr;
    std::function<void(Object*, const std::vector<std::any>&)> ctor;

    // 方法表：等价于 Lua 里把基类成员浅拷贝进 c
    std::unordered_map<std::string, std::function<void(Object*, const std::vector<std::any>&)>> methods;
    std::unordered_map<std::string, std::function<void(Object*, const std::any&, const std::any&)>> setters;
    // 热重载用：继承来的成员快照，等价于 Lua 的 c_inherited
    std::unordered_map<std::string, int> inherited_keys;

    Object* Create(const std::vector<std::any>& args = {}) const {
        auto* obj = new Object();
        obj->klass = this;
        for (auto& kv : setters) obj->slots_[kv.first] = PropertySlot{ {}, kv.second };
        if (ctor) ctor(obj, args);
        return obj;
    }

    bool is_class = true;
};

// 单例注册表
inline std::vector<const Class*>& ClassRegistry() {
    static std::vector<const Class*> r; return r;
}

// Class 声明宏 —— 使用体验贴近 Lua 的 Class(ctor, base, props)
#define DST_CLASS(Name, Base, ...)                                          \
    class Name : public Base {                                              \
    public:                                                                 \
        static const dst::Class* ClassRef() {                               \
            static const dst::Class* c = MakeClass(#Name, &Base::ClassRef()); \
            RegisterProps(c, __VA_ARGS__);                                  \
            return c;                                                       \
        }                                                                   \
        static dst::Object* Create() { return ClassRef()->Create(); }      \
        void __Construct();                                                 \
    };                                                                      \

}
```

对应的 Lua 语义要点：
- `MakeClass` 负责把基类 `methods` 全量拷贝进子类（复刻浅拷贝），并把 key 记进 `inherited_keys`。
- `RegisterProps` 把 `__VA_ARGS__` 里每个 `Prop(name, setter)` 注册到 `setters`。
- 属性的读取/写入走 `Object::Get<T>(name)` / `Object::Set(name, value)`，后者查 `slots_` 并调用 setter —— 也就是 `__newindex` 的直译。

### 2.2 这条链路上真正值得抄的四个设计

**（1）`Ents[guid]` 是唯一的实体真相表。** `CreateEntity`（mainfunctions.lua:486）里 `Ents[guid] = scr` 这一行意味着：任何拿到 GUID 的地方都能反查到 Lua 包装。`SaveGame`、`OnEntitySleep`、`OnEntityWake`、`OnRemoveEntity`、`SpawnPrefab` 的返回值、`ReplicateEntity` 全部走这张表。

**（2）`ReplicateComponent` 用标签编码"需要复制什么"。** 这是整份代码里最巧妙的一处：

```lua
-- entityreplica.lua:34
```

**（1）刻追赶而非逐帧。** `Update` 里是：

**（2）`last_tick_seen` 的去重保护。**

### 4.2 调度器移植（C++ 伪代码）

```cpp
// scheduler.cpp —— TickScheduler
class TickScheduler {
    std::unordered_map<int64_t, std::vector<PeriodicPtr>> attime_;
    std::vector<TaskPtr>    running_, waking_, hibernating_;
    std::unordered_map<int64_t, std::vector<TaskPtr>> waitingfortick_;
    std::unordered_map<void*, TaskPtr> tasks_;   // key = 协程句柄
    bool is_static_;
    int64_t last_tick_ = -1;

public:
    /// 返回持有绝对刻号的句柄。period<=0 且 limit==1 → 一次性。
    Handle ExecuteInTime(float dt, std::function<void()> fn, uint32_t id);
    Handle ExecutePeriodic(float period, int limit, float initial_delay,
                           std::function<void()> fn, uint32_t id);

    void OnTick(int64_t tick) {
        // 1) 唤醒等待这一刻的协程
        if (auto it = waitingfortick_.find(tick); it != waitingfortick_.end()) {
            for (auto& t : it->second) t->list = &waking_;
            waitingfortick_.erase(it);
        }
        // 2) 跑定时器
        auto it = attime_.find(tick);
        if (it != attime_.end()) {
            for (auto& p : it->second) {
                bool already_dead = p->limit == 0;
                if (!already_dead && p->fn) p->fn();
                if (p->limit) p->limit--;
                if (p->limit <= 0) {
                    if (p->onfinish && !already_dead) p->onfinish(p, true);
                    p->Cleanup();
                } else {
                    auto [list, next] = GetListForTimeFromNow(p->period);
                    list->push_back(p); p->list = list; p->nexttick = next;
                }
            }
            attime_.erase(it);
        }
    }

    void Run() {
        for (auto& t : waking_) t->list = &running_;
        waking_.clear();
        for (auto& t : running_) {
            if (t->co->dead()) { KillTask(t); continue; }
            YieldValue y = t->co->Resume();
            if (y.type == YieldType::Hibernate) t->list = &hibernating_;
            else if (y.type == YieldType::Sleep)   t->list = BucketForTick(y.tick);
            else if (y.type == YieldType::Error)   { LogTraceback(t); KillTask(t); }
        }
    }

private:
    int64_t GetTick() const { return is_static_ ? sim_->GetStaticTick() : sim_->GetTick(); }
    float   GetTime() const { return is_static_ ? sim_->GetStaticTime() : sim_->GetTime(); }

    std::pair<std::vector<PeriodicPtr>*, int64_t> GetListForTimeFromNow(float dt) {
        int64_t now    = GetTick();
        // 关键：-0.0001 的 epsilon，避免浮点误差导致 ceil 多跳一格
        int64_t wakeup = (int64_t)std::ceil((GetTime() + dt) / kTickTime - 0.0001);
        if (wakeup <= now) wakeup = now + 1;
        auto& list = attime_[wakeup];
        return { &list, wakeup };
    }
};
```

**移植时最容易漏的两点：**

1. **那个 `-0.0001` 的 epsilon。** 原版注释写得很清楚：`--epsilon for floating point error when used with FRAMES`。例如 `DoTaskInTime(1.0, fn)`，若 `GetTime()` 恰好是 10.0 而 `kTickTime` 是 1/30，`11.0 * 30 = 329.9999...` 或 `330.0000001`，`ceil` 结果会差一整格。这会让"1 秒后"的任务变成"1.0333 秒后"或"0.9667 秒后"。**照抄这个 epsilon。**

2. **`Periodic:Cancel()` 与 `Cleanup()` 的区别**（scheduler.lua:56 / :81）：
   - `Cancel()`：`limit = 0`、从桶里摘除、**调用 `onfinish(self, false, ...)`**、清空字段。
   - `Cleanup()`：`limit = 0`、从桶里摘除、**不调用 onfinish**、清空字段。
   
   `OnTick` 里先算 `already_dead`（`k.limit == 0`），若为真则跳过 `onfinish`——所以"在回调里取消自己"不会重复触发 `onfinish`。这个细节在 C++ 里如果用 `shared_ptr` 实现，很容易写出双重释放或漏掉 `onfinish`。

### 4.3 `PendingTasks` 与自动取消

```lua
-- entityscript.lua:1469

        for k in pairs(self.pendingtasks) do
            k:Cancel()
        end
        self.pendingtasks = nil

```

`Remove()` 里 `self:CancelAllPendingTasks()`（entityscript.lua:1721）与 `OnRemoveEntity` 里的 `ent:KillTasks()` → `KillThreadsWithID(self.GUID)`（entityscript.lua:1065、scheduler.lua:427）是**两条互补的路径**：
- `CancelAllPendingTasks` 精确取消这个实体通过 `DoTaskInTime`/`DoPeriodicTask` 排的**定时器**。
- `KillThreadsWithID` 粗粒度杀掉所有 `id == GUID` 的**协程任务**——包括通过 `inst:StartThread(fn)` 起的（`StartThread(fn, self.GUID)`，entityscript.lua:1069），以及**在实体自己的线程里 `StartThread` 派生出来的子线程**（`StartThread` 在 `id == nil` 时会继承当前任务的 id，scheduler.lua:387-393）。

**移植陷阱：** 如果你的引擎里协程任务的归属不是显式 id 继承的，那么"实体死亡时连带杀掉它派生的所有协程"这件事就做不到。原文没有强调这一点，但它是从 Lua `coroutine` 语义里**免费**得来的能力。

## 【深度扩写】五、事件系统的四个陷阱与两个扩展点

### 5.1 陷阱一：`PushEvent` 的重入安全性

```lua
-- entityscript.lua:1290
--make a copy list of all callbacks first in case
--listener tables become altered in some handlers
local tocall = {}
for entity, fns in pairs(listeners) do
    for i, fn in ipairs(fns) do table.insert(tocall, fn) end
end
for i, fn in ipairs(tocall) do fn(self, data) end
```

必须先复制。典型场景：`Health:SetVal` 推 `"death"`，某个监听者响应时调用 `inst:Remove()`，而 `Remove()` 会调 `RemoveAllEventCallbacks()` → 把 `self.event_listeners` 整个置 nil。如果不复制，`pairs(listeners)` 正在遍历的表被置 nil 后行为未定义。

### 5.2 陷阱二：处理器签名是 `(source, data)`，不是 `(data)`

```lua
for i, fn in ipairs(tocall) do fn(self, data) end
```

第一个参数是**推事件的那个实体**（即 `self`）。这正是 `inst:ListenForEvent("attacked", OnAttacked)` 里 `OnAttacked(inst, data)` 的 `inst` 来源。**注意这个 `inst` 是事件源，不一定是被监听的那个**——因为 `ListenForEvent(event, fn, source)` 允许你监听别人。

### 5.3 陷阱三：`RemoveAllEventCallbacks` 的双向解绑必须成对

```lua
-- entityscript.lua:1232
function EntityScript:RemoveAllEventCallbacks()
    --tell others that we are no longer listening for them
    if self.event_listening then
        for event, sources  in pairs(self.event_listening) do
            for source, fns in pairs(sources) do
                if source.event_listeners then
                    local listeners = source.event_listeners[event]
                    if listeners then listeners[self] = nil end
                end
            end
        end
        self.event_listening = nil
    end
    --tell others who are listening to us to stop
    if self.event_listeners then
        for event, listeners in pairs(self.event_listeners) do
            for listener, fns in pairs(listeners) do
                if listener.event_listening then
                    local sources = listener.event_listening[event]
                    if sources then sources[self] = nil end
                end
            end
        end
        self.event_listeners = nil
    end
end
```

这个 O(监听数) 的解绑是 `Remove()` 能安全执行的前提。**Lua 的 GC 不会帮你解决这个问题**——因为 Lua 的 table 是强引用，`TheWorld:PushEvent("entity_death", { inst = ... })` 的 data 会被监听者闭包捕获，实体即使逻辑上已死也会被拖住不回收。

**自研引擎里这条特别重要：** C++/C# 的 GC 不会自动断开 Lua↔引擎的双向引用。你需要：
- 事件注册表用 `weak_ptr` 或显式生命周期管理；
- 或者强制"实体死亡时必须调用解绑"，并在 `Remove` 里断言无残留监听。

### 5.4 陷阱四：`PushEvent` 与 `PushEventImmediate` 对状态图的影响不同

```lua
-- entityscript.lua:1286
function EntityScript:PushEvent_Internal(event, data, immediate)
    ... -- Lua 监听者：两种模式都是立即同步调用
    if self.sg then
        if immediate then
            self.sg:HandleEvent(event, data)                   -- 立刻处理
        elseif self.sg:IsListeningForEvent(event) and SGManager:OnPushEvent(self.sg) then
            self.sg:PushEvent(event, data)                     -- 缓冲，刻末统一处理
        end
    end
    if self.brain then self.brain:PushEvent(event, data) end    -- 脑总是缓冲
end
```

状态图的事件是**刻末批处理**的（`SGManager:Update` 最后调 `self:UpdateEvents()`，stategraph.lua:147）：

```lua
-- stategraph.lua:148
function StateGraphWrangler:UpdateEvents()
    local evs = self.haveEvents
    self.haveEvents = {}
    TheSim:ProfilerPush("events")
    for k,v in pairs(evs) do k:HandleEvents() end
    TheSim:ProfilerPop()
end
```

**为什么这么设计（推断）**：状态图的 `EventHandler` 里通常会做状态转移，而状态转移又会触发新的事件。批处理让一个刻内的多次 `PushEvent` 合并成一次转移计算，避免"边遍历边改状态图结构"。`PushEventImmediate` 提供给那些"必须在当前调用栈内完成状态转移"的场景——比如 `Health:SetVal` 里推 `"forcecorpsereplace"` 时同时 `sg:GoToState("corpse")`（health.lua:559-562）。

**移植建议：** 状态机也采用"事件入队 → 帧末统一 drain"，并且**入队期间禁止修改队列容器**（原版用 `local evs = self.haveEvents; self.haveEvents = {}` 的"换表法"实现，比迭代中删除安全得多）。

### 7.1 保存端：从 `GetSaveRecord` 到磁盘

```lua
-- entityscript.lua:248
function EntityScript:GetSaveRecord()
	local record = { prefab = self.prefab }
	local x, y, z = self.Transform:GetWorldPosition()
	if self.temp_save_platform_pos or self.entity:HasTag("player") then
		record.age = self.Network:GetPlayerAge()
		local platform = self:GetCurrentPlatform()
		if platform then
			local rx, ry, rz = platform.entity:WorldToLocalSpace(x, y, z)
			if isbadnumber(rx) or isbadnumber(ry) or isbadnumber(rz) then ... end   -- NaN 猎捕
			record.puid = platform.components.walkableplatform:GetUID()
			record.rx = ...; record.rz = ...; record.ry = ...
		end
	end
	if isbadnumber(x) or isbadnumber(y) or isbadnumber(z) then ... end             -- NaN 猎捕
	record.x = x and math.floor(x * 1000 + 0.5) * 0.001 or 0   -- 保留 3 位小数
	record.z = ...
	if y and y ~= 0 then record.y = ... end                 -- y 常常是 0，从省
	record.skinname = self.skinname
	record.skin_id = self.skin_id
	record.alt_skin_ids = self.alt_skin_ids

	local references
	record.data, references = self:GetPersistData()
	return record, references
end
```

**值得学的四个细节：**

1. **站在平台上的实体用"平台局部坐标"存档**。`record.puid`（platform UID）+ `record.rx/rz/ry` 而不是世界坐标。加载时通过 `ResolveSaveRecordPosition`（mainfunctions.lua:424）换算回世界坐标。移动平台（船）因此能带着货物一起动。
2. **`isbadnumber` NaN/Inf 猎捕**。坐标一旦变成 NaN，存档会被污染且**永久**（NaN 传播）。生产环境只打印、开发环境直接 `error`。
3. **坐标量化到 3 位小数**：`math.floor(x * 1000 + 0.5) * 0.001`。这是典型的"存档体积 vs 精度"权衡——1594 个预制体、数千个实体，每条记录省几个字节就有意义。
4. **`y` 为 0 时不写**。`if y and y ~= 0 then`。字段缺失比写 0 更省，且加载端 `record.y or 0` 已经处理了。

**`newents` 用实体本身作 key 的设计很聪明**：没有 id 的实体也能被引用（引用时直接传实体），有 id 的实体则通过 `newents[saved.id]` 查到。两趟之后 `LoadPostPass(newents, savedata)` 让组件把 GUID 换成真实实体引用：

```lua
-- entityscript.lua:1939
function EntityScript:LoadPostPass(newents, savedata)
    if savedata ~= nil then
        for k, v in pairs(savedata) do
            local cmp = self.components[k]
            if cmp ~= nil and cmp.LoadPostPass ~= nil then cmp:LoadPostPass(newents, v) end
        end
    end
    if self.OnLoadPostPass ~= nil then self:OnLoadPostPass(newents, savedata) end
end
```

**注意 `newents[saved.id] = {entity=..., data=...}` 存的是一个二元组**，`data` 是给 `LoadPostPass` 用的原始数据。很多组件在 `OnLoad` 里只记 GUID，`LoadPostPass` 才真正查表：

```lua
function SomeComponent:OnLoad(data, newents)

function SomeComponent:LoadPostPass(newents, data)
    local rec = newents[data.target]
    self.target = rec and rec.entity or nil
end
```

### 7.5 存档的输出格式与损坏检测

```lua
-- mainfunctions.lua:1201
local PRETTY_PRINT = BRANCH == "dev"
local patterns
if BRANCH == "dev" then patterns = {"=nan", "=-nan", "=inf", "=-inf"}
else                      patterns = {"=-1.#IND", "=1.#QNAN", "=1.#INF", "=-1.#INF"} end

for key,value in pairs(save) do
    data[key] = DataDumper(value, nil, not PRETTY_PRINT)
    for i, corrupt_pattern in ipairs(patterns) do
        local found = string.find(data[key], corrupt_pattern, 1, true)
        if found ~= nil then
            local bad_data = string.sub(data[key], found - 100, found + 50)
            print(bad_data)
            error("Error saving game, corruption detected.")
        end
    end
end
```

`DataDumper` 把 table 序列化成 **Lua 源码文本**（不是二进制），存档文件本质上是可读的 Lua。开发分支扫描字符串形式的 `=nan`，发布分支扫描 MSVC 的 `1.#QNAN` 等形式（Windows 的浮点打印差异）。

**移植建议：** 二进制格式（protobuf / flatbuffers）能显著减小体积并加速加载，但代价是存档不可 diff、不可手工修复。饥荒选 Lua 源码，最大好处是**模组可以理解并修改存档格式**——这对长生命周期的游戏是值得的取舍。

### 8.2 `CollectActions` 的 id → name 映射是性能关键

```lua
-- componentactions.lua:3174
function EntityScript:CollectActions(actiontype, ...)
    local t = COMPONENT_ACTIONS[actiontype]
    if t == nil then
        print("Action type", actiontype, "doesn't exist ...")
        return
    end
    for i, v in ipairs(self.actioncomponents) do
        local collector = t[ACTION_COMPONENT_NAMES[v]]     -- 两次查表：id→name→fn
        if collector ~= nil then collector(self, ...) end
    end
    -- 之后是同样结构的模组循环
end
```

一个实体有 N 个组件，`CollectActions` 就是 N 次双层查表 + 可能的函数调用。玩家移动时每个被指向的实体都会跑一遍。**这是典型的"每帧 × 每实体"热点**，原版没有做缓存——因为 N 很小（通常 5~20 个组件），且查表是 O(1)。

`IsActionValid`（componentactions.lua:3202）走 `COMPONENT_ACTIONS.ISVALID` 这一组，用于"动作预校验"。

### 8.3 移植建议：数据驱动交互的三种形态

| 形态 | 做法 | 优缺点 |
|---|---|---|
| **饥荒式（收集器）** | `actiontype → component → collector(inst, ctx, actions)` | 组合性最好；调用有开销；顺序由 `actioncomponents` 插入序决定，不稳定 |
| **Unity 式（接口查询）** | 组件实现 `IInteractable`，`GetActions(ctx)` 虚方法 | 类型安全；仍是每帧接口调用；需维护组件类型列表 |
| **ECS 式（标签驱动）** | 动作由 `(操作键, 实体标签组合)` 决定，如 `(PICK, has:workable)` | 最快；组合爆炸难维护；失去"组件自己决定"的能力 |

**推荐做法**：借鉴饥荒的"组件自注册 + 集中收集"，但用**编译期位掩码**替代字符串查表：

```cpp
enum class CompBit : uint32_t { Health=1u<<0, Workable=1u<<1, Fueled=1u<<2, Container=1u<<3, /*...*/ };

struct Entity {
    uint32_t comp_mask;   // O(1) 判定"有没有某组件"
    std::vector<IInteractCollector*> collectors;  // 按注册序
};

// 收集
void CollectActions(uint32_t mask, const InteractCtx& ctx, ActionList& out) {
    for (auto* c : collectors) {
        if (mask & c->required_mask) c->Collect(ctx, out);
    }
}
```

这样既保留了"组件自己决定"的组合性，又把最内层查表降到一次位与。

### 9.2 "脑被销毁重建"是刻意的设计

```lua
-- entityscript.lua:1135
function EntityScript:_EnableBrain_Internal()
	if self._braindisabled then
		self._braindisabled = nil
		self.brain = self.brainfn()          -- 重新调用工厂，而不是恢复旧对象
		if self.brain then
			self.brain.inst = self
			if not self._brainstopped then self.brain:_Start_Internal() end
		end
	end
end
```

**为什么要销毁而不是挂起？**（推断，依据脑内部持有协程任务）脑（`Brain`）内部持有调度器协程与一堆运行期状态（当前思考目标、黑板数据、临时表）。销毁重建保证所有内部缓存干净，避免"睡了三天醒来还记得自己在盯着什么"。代价是分配开销——但只有玩家附近的实体会被唤醒。

```lua
-- entityscript.lua:1103
function EntityScript:SetBrain(brainfn)
    self.brainfn = brainfn
	--V2C: -sleepstatepending check to prevent brain starting at construction when :IsAsleep() always returns false
	self._braindisabled = brainfn and (self.sleepstatepending or self:IsInLimbo() or self:IsAsleep()) or nil
	if self.brain then self.brain:_Stop_Internal() end
	self.brain = brainfn and not self._braindisabled and brainfn() or nil
	...
end
```

`sleepstatepending` 这个标志的存在是为了解决一个时序问题：`SetStateGraph`/`SetBrain` 在 `fn` 里被调用，此时引擎还没告诉这个实体"你初始是不是睡着的"（`IsAsleep()` 依赖原生状态）。`sleepstatepending` 在构造器里被设为 `true`（entityscript.lua:221），在第一次 `OnEntitySleep`/`OnEntityWake` 时被清空（mainfunctions.lua:685、719）。**这是"原生状态尚未同步"这一类问题的通用解法**，自研引擎如果有类似的"属性要等第一次同步才知道"的场景，可以照抄。

### 9.3 limbo：另一种"假死"

```lua
-- entityscript.lua:348
function EntityScript:RemoveFromScene()
    self.entity:AddTag("INLIMBO")
    self.entity:SetInLimbo(not self.forcedoutoflimbo)
    self.inlimbo = true
    self.entity:Hide()
	self:_DisableBrain_Internal()
    if self.sg then self.sg:Stop() end
    if self.Physics then self.Physics:SetActive(false) end
    if self.Light and self.Light:GetDisableOnSceneRemoval() then self.Light:Enable(false) end
    if self.AnimState then self.AnimState:Pause() end
    if self.DynamicShadow then self.DynamicShadow:Enable(false) end
    if self.MiniMapEntity then self.MiniMapEntity:SetEnabled(false) end
    self:PushEvent("enterlimbo")
end
```

limbo 与 sleep 的区别：

| | sleep | limbo |
|---|---|---|
| 谁决定 | 引擎（距离/兴趣管理） | 游戏逻辑显式调用 `RemoveFromScene` |
| 物理 | 不变 | `Physics:SetActive(false)` |
| 脑 | 销毁 | 销毁 |
| 状态图 | Hibernate（可唤醒） | `Stop()`（需显式 `ReturnToScene`） |
| 可见性 | 不变 | `entity:Hide()` |
| 事件 | `entitysleep` / `entitywake` | `enterlimbo` / `exitlimbo` |
| `IsInLimbo()` | — | `self.inlimbo`（注释说"比查 tag 快，但只在 mastersim 有效"） |

**关键约束**：`OnEntityWake` 里有 `if not inst:IsInLimbo() then` 的守卫（mainfunctions.lua:712），注释明确写着：

```lua
--V2C: Note that if this needs to work properly for networked
--     entities on clients, then should use the slower check
--     :HasTag("INLIMBO").  But there should be no networked
--     entities on clients that can go to sleep.
```

**即：客户端的实体永远不会 sleep，也不会 wake，因此客户端不需要维护 `inlimbo` 字段的正确性。** 客户端用 `HasTag("INLIMBO")` 查询。这是把"状态放在哪"这个问题想清楚后的取舍。

## 【深度扩写】十、移植陷阱清单（原文未提但实际会踩）

以下每一条都基于源码核实。

1. **`AddComponent` 的大小写陷阱**。`lower_components_shadow` 用小写去重，`self.components` 用原样存。`AddComponent("Health")` 后再 `AddComponent("health")` 会走幂等分支并返回已存在的组件（entityscript.lua:612-623 有兜底查找），但如果两次都用不同大小写且**第一次用了混合大小写**，`self.components["Health"]` 与 `lower_components_shadow["health"]` 存在，而 `SaveGame`/`GetPersistData` 是用 `self.components` 的 key 做存档字段名的 → 存档里会出现 `"Health"` 字段。老存档读回时会因 key 不匹配而丢数据。**自研实现请统一小写。**

2. **`is_a` 与 `ReplicateComponent` 的白名单是两张独立的表**。`is_a(Component)` 判断类型继承；`REPLICATABLE_COMPONENTS`（entityreplica.lua:5）决定是否创建副本。两者不联动。写了新组件忘了加白名单 → 服务端有 `health` 客户端没有 → UI 永远显示满血。

3. **`props` 与浅拷贝继承的交互**。子类 `Class(Base, ctor, props)` 会把基类的**所有成员**浅拷贝进 `c`，包括基类的 `__index`/`__newindex`（如果基类有 props）。子类再传 `props` 时会用新的 `__index`/`__newindex` 覆盖，行为正常。但**属性表 `obj._` 是每次构造时新建的**，所以父类 props 与子类 props 都生效（`__index` 只查 `obj._` 一层，靠的是 `mt.__call` 把合并后的 props 都填进同一个 `obj._`）。如果你在自研版本里改成"每个类一个 props 表"，就必须显式合并，否则子类会丢掉父类的 setter。

4. **`props` 表在构造时被 `pairs` 遍历初始化**，所以**顺序不确定**。`obj._[k] = { nil, v }` 全部先设为 nil，之后构造器才跑。如果构造器里 `self.a = 1; self.b = 2` 且 `a` 的 setter 依赖 `b` 已存在，就会读到 nil。原版的 `health` 构造器里 `self.currenthealth = self.maxhealth` 依赖 `self.maxhealth = 100` 在前一行——**依赖关系必须由代码顺序保证，不能指望 props 顺序**。

5. **`DoTaskInTime` 的 `fn` 第一个参数永远是实体**。`scheduler:ExecuteInTime(timefromnow, fn, id, self, ...)`（entityscript.lua:1522），`Periodic` 把 `self` 存进 `arg[1]`。但 `PushEventInTime`（entityscript.lua:1532）是个例外——它的内部 `event_function(inst)` 也遵守这个约定，可外部传入的 `data` 会排在 `inst` 之后。

6. **`Periodic` 是以 table 为键存在 `attime[tick]` 里的**（`list[periodic] = true`）。这意味着**遍历顺序不确定**。同一刻到期的多个定时器，执行顺序随机。对有依赖关系的定时器（例如"先扣血再检查死亡"），必须用不同的时间或显式串行化。**自研实现若改用数组/向量会"意外地"变成确定性的插队顺序，这反而可能掩盖 bug。**

7. **`Sleep(t)` 在 `t` 不足一格时不会 yield SLEEP**：
   ```lua
   -- scheduler.lua:356
   function Sleep(time)
       local schedule = GetCurrentScheduler()
       local desttick = math.ceil((GetSchedulerTime(schedule.isstatic) + time)/GetTickTime())
       if GetSchedulerTick(schedule.isstatic) < desttick then
           coroutine.yield(SLEEP, desttick)
       else
           coroutine.yield()          -- 空 yield → 下一帧继续
       end
   end
   ```
   `Sleep(0.001)` 会变成"下一帧"，不是"这一帧末尾"。协程脚本里写 `Sleep(0)` 以为会立即继续，会得到一帧延迟。

8. **`OnTick` 里的 `assert(k >= tick)`**（scheduler.lua:166）会对 `waitingfortick` 里所有等待中的协程断言。这意味着 `Sleep` 到过去的刻会立刻触发断言失败。时间回拨（服务器校时）会导致这个炸。

9. **`Remove()` 的组件遍历中组件可能反过来 `Remove` 自己**：
   ```lua
   -- entityscript.lua:1723
   for k, v in pairs(self.components) do
       if v and type(v) == "table" and v.OnRemoveEntity then
           v:OnRemoveEntity()
       end
   end
   ```
   某个组件的 `OnRemoveEntity` 里调用 `inst:Remove()` → 重入。虽然 Lua 允许遍历中删 key，但会跳过元素。**自研实现要加 `is_removing` 标志位。**

10. **`Self:Remove()` 里的 `erode_task` 与 `DoTaskInTime` 的自引用**。`Health:SetVal` 里 `self.inst.erode_task = self.inst:DoTaskInTime(...)`，而 `DoTaskInTime` 把任务加进 `inst.pendingtasks`。`Remove()` 会 `CancelAllPendingTasks()`。如果 `ErodeAway` 内部调 `Remove()`，此时它自己正在 `pendingtasks` 里被迭代取消——`for k in pairs(self.pendingtasks) do k:Cancel() end`（entityscript.lua:1470）中 `k:Cancel()` 内部会置 `k.list = nil` 但不修改 `pendingtasks`，遍历安全。**但如果 `Cancel()` 的 `onfinish` 回调（`task_finish`）去改 `pendingtasks` 就有问题**——看 `task_finish`（entityscript.lua:1476），它确实改 `inst.pendingtasks[task] = nil`。所以 `for k in pairs(self.pendingtasks) do k:Cancel() end` 中，第二次迭代时 `self.pendingtasks` 可能已经被改。原版能跑是因为 Lua 的 `pairs` 对"当前 key 被置 nil"是安全的，但如果 `onfinish` 往表里**新增** key 就会跳过。**自研实现务必先快照再取消。**

11. **`componentactions.lua` 的 255 上限**（componentactions.lua:3084）。新增组件类型时如果它注册了 `COMPONENT_ACTIONS` 里的任何一项，`ACTION_COMPONENT_NAMES` 就会增长，超过 255 直接 assert 失败。**这是硬上限，不是性能提示。**

12. **`ENTITY_ACTIONS` 的 id 是位置敏感的**：`ACTION_COMPONENT_IDS[cmp] = #ACTION_COMPONENT_NAMES`，顺序由 `orderedPairs(COMPONENT_ACTIONS)` 决定。`orderedPairs` 保证了确定性排序——这是刻意的，因为 id 会进网络包。**自研实现若用无序遍历，会导致服务端与客户端的 id 不一致。**

13. **`inst.entity:HasTag("player")` vs `inst:HasTag("player")`**。`inst:HasTag` 是 `EntityScript:HasTag`（entityscript.lua:572）转发给 `self.entity:HasTag`。两者等价，但源码里 GetSaveRecord（entityscript.lua:256）用的是 `self.entity:HasTag`。**统一用 `inst:HasTag`。**

14. **`TheWorld` 在 `PopulateWorld` 之前是 nil**。任何在 `SpawnPrefab(savedata.map.prefab)` 之前调用 `TheWorld.something` 的代码都会崩。`SpawnPrefabFromSim` 里有 `if TheWorld then` 的守卫（mainfunctions.lua:387），但 `PushEvent_Internal` 里的 `self.sg`/`self.brain` 检查没有 `TheWorld` 依赖。自研引擎要保证"世界实体最先创建"或对 nil 全面防御。

15. **`spawntime` 用 `GetTime()` 而非真实时间**。`EntityScript` 构造器里 `self.spawntime = GetTime()`（entityscript.lua:220）。服务器暂停时 `GetTime()` 停走，`GetTimeAlive()` 返回的值会"冻结"。这是刻意的（游戏内时间），但如果拿它做网络超时判断会出错。

## 【实现清单】

面向"要做一个类饥荒生存游戏"的目标。以下每项都可以独立勾选。

### 阶段 1：地基（无它寸步难行）

- [ ] **实现刻（tick）驱动的固定步长循环**，并区分「模拟时间」与「真实时间」两条线（对应 `Update` / `WallUpdate`）
- [ ] **刻追赶逻辑**：一帧跨多个刻时逐刻补跑，含 `last_tick_seen` 去重保护
- [ ] **刻量化调度器**：绝对刻桶（`attime`）+ 一次性/周期性定时器 + `Cancel`/`onfinish` 语义
- [ ] **协程调度器**：`Sleep(t)` / `Hibernate()` / `Yield()`，任务归属 id 继承
- [ ] **类系统**：构造函数 + 单继承 + 属性 setter + 只读属性
- [ ] **属性 setter 必须能在赋值瞬间触发副作用**（这是网络同步与 UI 刷新的唯一收口）
- [ ] **全局变量纪律**：未声明即报错；每个单例显式注册

### 阶段 2：实体与组件

- [ ] **实体注册表** `Ents[guid]`，创建即入表，销毁即出表
- [ ] **组件系统**：按名添加、按名查找、大小写归一、幂等去重
- [ ] **组件生命周期钩子**：`OnSave`/`OnLoad`/`OnUpdate`/`LongUpdate`/`OnEntitySleep`/`OnEntityWake`/`OnRemoveFromEntity`/`OnRemoveEntity`
- [ ] **按需逐帧更新**：双缓冲的 `UpdatingEnts`/`NewUpdatingEnts`/`StopUpdatingComponents`
- [ ] **原生底层组件抽象**：`Transform`/`AnimState`/`Physics`/`Network`/`Light`/`Shadow`，且与 Lua 组件**物理隔离**
- [ ] **标签系统**：用 int/enum 而非字符串；空间查询支持 mustTags/cantTags 过滤
- [ ] **`Make*` 原型打包**：把"可组合的组件集合"封装成可复用构造函数

### 阶段 3：预制体与工厂

- [ ] **预制体 = 工厂函数 + 资产清单 + 依赖清单**
- [ ] **资产依赖图**：引擎只加载可达预制体的资源
- [ ] **`deps` 机制**：声明式保证子预制体资源常驻
- [ ] **预制体哈希/ID**：网络用数值 id 标识，名称仅在加载期使用
- [ ] **角色工厂**（对应 `MakePlayerCharacter`）：`common_postinit` / `master_postinit` 两段式扩展点

### 阶段 4：事件

- [ ] **按实体的事件总线**（不要做成全局单例）
- [ ] **双向监听记账**：`listeners` + `listening`，销毁时统一解绑
- [ ] **派发前快照回调列表**，容忍处理器增删监听
- [ ] **用"世界实体"充当全局总线**，`ms_*` 事件只在服务端存在
- [ ] **批量事件队列**：状态机事件帧末统一 drain（换表法）
- [ ] **轻量观察者通道**（`WatchWorldState`）：世界状态变量的观察者

### 阶段 5：存档

- [ ] **组件自持序列化**：`OnSave` 返回 table，`OnLoad` 消费
- [ ] **两趟加载**：第一趟生成实体 + `OnLoad`，第二趟 `LoadPostPass` 解析引用
- [ ] **引用表机制**：只有被引用的实体才写入 id
- [ ] **坐标量化**（如 3 位小数）+ **NaN/Inf 猎捕**
- [ ] **移动平台存档**：局部坐标 + 平台 UID
- [ ] **存档迁移**：`add_component_if_missing` / `OnPreLoad` / 预制体重命名表
- [ ] **数据驱动交互动作**：`actiontype → component → collector`，含 id→name 的有序映射

### 阶段 6：主从分离（联机版才需要）

- [ ] **`SetPristine()` 冻结点**：之前添加的进网络，之后的仅服务端
- [ ] **`ismastersim` 门禁**：一个工厂函数同时描述两端
- [ ] **副本组件机制**：服务端写、客户端只读；**白名单显式注册**
- [ ] **用标签编码"需要复制什么"**，避免额外同步清单
- [ ] **网络变量 + 脏事件**：赋值自动发事件，客户端自动收到
- [ ] **服务器广播实体生成**：`TheWorld:PushEvent("entity_spawned", inst)`

### 阶段 7：性能与规模化

- [ ] **兴趣管理**：远处实体休眠（停脑、停状态图、停发射器）
- [ ] **脑的销毁-重建**语义（而非挂起），保证唤醒后内部状态干净
- [ ] **limbo 机制**：移出场景但不销毁（关物理、隐藏、停脑）
- [ ] **性能剖析打点**：`ProfilerPush`/`ProfilerPop` 逐子系统包裹（见 update.lua 全篇）
- [ ] **`LongUpdate` 批量补偿**：跳过夜晚/返回洞穴时批量快进，且能跳过玩家及其背包
- [ ] **无障碍的弱实体查询**：大量闲置实体零每帧开销

### 阶段 8：可扩展性

- [ ] **后置钩子系统**：`PrefabPostInit` / `PrefabPostInitAny` / `ComponentPostInit` / `SimPostInit`
- [ ] **模组资产隔离**：模组预制体的加载与卸载成对（参考 `ModPreloadAssets` / `ModUnloadPreloadAssets`）
- [ ] **热重载支持**：`ClassRegistry` 保存继承成员快照、`ReloadedClass` 注销
- [ ] **数值配置外置**：策划可调的 `TUNING` 等价物
- [ ] **本地化与重翻译**：模组加载后重新翻译字符串

### 阶段 9：验收标准

- [ ] 地上 5000 个实体、活跃区 50 个实体时，**非活跃实体每帧开销为零**
- [ ] 一个实体从生成到销毁，其所有定时器、协程、事件监听**全部自动清理**（无泄漏）
- [ ] 存档往返 10 次后世界状态**完全一致**（含移动平台上的物品）
- [ ] 客户端与服务端在相同输入下**产生相同的确定性结果**（刻调度器保证）
- [ ] 新增一种可交互行为 = **加一个组件 + 一个收集器**，不改任何动词/输入代码

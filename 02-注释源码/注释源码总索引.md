## 深度注释的阅读顺序建议

要理解一个类饥荒游戏的核心机制，按此顺序读注释源码：

**第三组：AI 系统（做生物必读）**

## behaviours 节点库（29 个文件，2026-10-12 新增）

> 本节为 behaviours/ 目录**逐行深度注释**后的说明。该目录是 DST 行为树（Brain）
> 的标准叶子节点库 —— `brain.lua` 与 `behaviourtree.lua` 是框架，这 29 个文件是实现。
> 全部 29 个文件均已精读并加注，源行 2,800 行 → 注释版 7,737 行（含 5,058 行注释）。
>
> **⚠️ 先纠正一个常见误解**：这些节点**不是** `ShouldRun`/`OnEnter`/`OnUpdate`/`OnExit`
> 四段式，也不是 `DoBehaviour` 返回值协议（已 grep 全目录确认出现次数均为 0）。
> 真实协议是 **构造器 + `Visit()` 两段式**，靠 `self.status`（READY/RUNNING/终态）驱动。

### 节点协议（移植必读）

```
Class(BehaviourNode, function(self, ...)   -- 建树时跑一次：存参数、注册事件，不做决策
  function X:Visit()                      -- 每帧/每次唤醒被调用，全部分支在此
      if self.status == READY   then ...  end   -- ① 能否进入 + 决定动作
      if self.status == RUNNING then ...  end   -- ② 执行 + 判断终止（多数用顺序双 if）
  function X:OnStop()                     -- 可选：仅 bt:Stop() 时调用，释放事件监听
```

| 要素 | 结论 |
|---|---|
| **终态语义** | `SUCCESS` = 行为**意图已达成**；`FAILED` = 本行为**不适用**（不是"出错"） |
| | 写终态后必须 `return`/`Stop`，否则会污染后续逻辑 |
| **终态是谁写的** | 只有 `Visit` 可以改 `self.status`。异步回调只写自己的数据字段 |
| **参数化** | 阈值普遍支持"值或函数"：`FunctionOrValue(self.x, inst)`，在**消费点**求值 |
| **休眠协作** | 唯一接口是 `self:Sleep(t)` → `GetSleepTime` → `brain.lua` 排 Sleep 或 Hibernate |
| **节拍** | 与行为类型强相关：逃跑 .1s / 战斗 .125s / 移动 .25s / 转身 .5s / 单次动作 1s |
| **共享黑板** | 目标可存节点私有字段（`self.targ`）、组件（`pollinator.target`）、或实体（`inst.planttarget`）|
| **朝向控制权** | `if sg:HasStateTag("canrotate")` —— 全目录出现 6 次的铁律 |

### 本目录提炼出的可复用范式（移植到自研 AI）

1. **三段距离带滞回**：进入阈值在外圈（易触发）、退出阈值在内圈（难退出）——
   `follow` 的 min/target/max、`leash` 的 max/return、`useshield` 的静默超时。
   **任何"维持在某范围内"的行为缺了内圈退出条件就一定会抖。**
2. **`SUCCESS`/`FAILED` 只由行为意图决定**，不看过程是否有进展。
   正反例：`approach` 已在范围内→SUCCESS（意图=抵达）；
   `follow` 已在范围内→FAILED（意图=持续跟随，静止不构成动作）。
   同一几何条件（`runtodist` 第 104 行 vs `faceentity` 第 43 行）终态可以相反。
3. **异步结果只能写数据字段，由 `Visit` 搬进 `status`**（`doaction`）。
   回调直接改 `node.status` 会破坏行为树遍历假设，产生极难复现的时序 bug。
4. **节拍 = 行为对延迟的敏感度**：逃生 .1 / 战斗 .125 / 移动 .25 / 转身 .5 / 单次动作 1。
   降开销有三条独立路径：Sleep 节流、内部降频（`findlight`）、跳过调用（`minperiod`）。
5. **休眠必须有事件唤醒通道**：状态由外部驱动时（被电击/冻结），
   必须有 `brain:ForceUpdate()`（`useshield` 第 28 行、`avoidelectricfence` 第 15 行），
   否则沉睡中的大脑看不到状态结束 → 永久卡死。**这条最容易漏。**
6. **可见性决定模拟精度**：`beargeroffscreen` 对离屏单位直接 `SetPosition` 瞬移 +
   沿途补算摧毁/掉落事件，省掉寻路与状态机。海量单位场景就该这么分级。
7. **群体 AI 分调度层与执行层**：`controlminions` 只派活不执行；
   `findflower`/`findfarmplant` 的「资源被抢就退出」避免踩踏。
8. **装饰器只做两件事：转发子节点 + 同步状态**，且状态同步必须存在
   （`chattynode` 透明型 / `minperiod` 约束型）；`enter_delay` 解决周期台词聒噪。
9. **`canrotate` 状态标签是朝向控制权的仲裁点**（全目录 6 处铁律）——
   行为树绝不与状态图争夺何时可转向。
10. **给随机行为加扰动与惯性**：`+45°` 抖动、`avoid_angle` 1s 锁定 ——
    群体同步行为会显得极假，扰动是廉价解法。

### ⚠️ 职责纠正（两处与直觉不符）

1. **`templates.lua` 不是「UI 模板基类」**。
   全库 `grep -rn ":Template("` **零命中** —— DST 没有 `Widget:Template()` 这个机制。
   真正的继承体系在 `class.lua:83` 的 `Class(base, _ctor, props)`
   （`widget.lua:1` 用它建 Widget 基类，`ImageButton = Class(Button, ...)` 做浅拷贝继承）。
   `templates.lua` 走的是**完全另一条路**：一张扁平的**工厂函数表**，
   每个 entry 是 `function(...) -> 新实例`，不参与继承体系。
   → 两条路的取舍：工厂适合「一次性零件」，Class 适合「有状态的长生命周期控件」。

2. **`inventorybar.lua` 的类名是 `Inv`，不是 `InventoryBar`**（第 33 行）。
   且它**只负责手柄/主机模式**：鼠标玩家的背包交互由 `invslot.lua`/`itemtile.lua`
   自行处理悬停与拖拽。手柄版用 `cursor`/`active_slot` 取代鼠标 hover，
   是**并列的第二套实现**，两者不共用逻辑。

### 对自研游戏最有价值的 6 个模式

1. **「空对象占位」防崩溃**（`templates.lua:66,70`、`inventorybar.lua:66,70`）
   lavaarena/quagmire 模式没有 `inventory_bg_cover` 美术资源，
   于是 `self.bgcover = AddChild(Widget("dummy"))` 塞一个**空 Widget 顶替**。
   后续 RebuildLayout 无条件对 bgcover 调 SetScale/SetPosition 也不会崩。
   → 「某分支没创建这个字段」会让通用代码炸掉；正确解法就是补空对象占位。

2. **延迟重建（脏标记 + 下帧消费）**（`inventorybar.lua:150-155,522`）
   `AddEquipSlot` **只登记不建控件**，置 `rebuild_pending`；
   实际重建推迟到 `OnUpdate` 的安全时机。
   → 「批量修改请求」的正确姿势是置脏标记 + 统一处理。
   若每加一个槽就重建一次，中间态算出的底板宽度是错的。

3. **差分更新：预览/权威双轨**（`itemtile.lua:86,239-281,350-379`）
   客户端先本地改堆叠数做即时预览（`ispreviewing`），
   服务端回包再校正；用 `movinganim.isolddata` 标记让**过期动画自然消亡**，
   只有最后一次生效 —— 否则数字会「弹两下」。
   → 任何有本地预测的 UI（倒计时、读条、进度）都需要这套协议。

4. **多来源更新计数**（`itemtile.lua:751-763`）
   一个 tile 可能同时因「蓄力」和「暗影燃料」需要每帧更新。
   用 `updatingflags` 标志表 + `next(...) == nil` 判断，
   「第一个进来启动、最后一个离开停止」。
   若用单一布尔，蓄力结束会把暗影燃料的更新也停掉。
   （与 `inventorybar.lua:1417` 的 SourceModifierList 是同思路两形态：一个做「或」，一个做「计数」。）

5. **配置驱动布局：把变化提升为常量表**（`statusdisplays.lua:295-308`）
   分屏只需 5 个 `columnN` 常量**反转符号**，其余 5 个徽章的定位代码
   一行分支都不用写。若不这么做，5 徽章 × 5 位置 = 25 个 if。

6. **运行时方法包装（猴子补丁）**（`statusdisplays.lua:769-800,805-822`）
   缓存原方法 `_OnFlagsChanged = badge.OnFlagsChanged`，
   换成新函数内部先调原方法再追加行为 —— **不改被扩展方源码**而扩展其行为。
   移植自研游戏的 mod/plugin 系统可直接借鉴。

### 无布局引擎的纯算术（值得整段抄）

- **槽位网格总宽**（`inventorybar.lua:247-249`）：
  `total_w = 槽数×W + (槽数-1)×SEP + ceil(槽数/5)×INTERSEP`。
  先算总宽 → 据此把内容居中、把底板拉伸到刚好匹配（`bg:Flow(total_w+60, ...)`）。
- **像素图缩放到虚拟分辨率**（`templates.lua:105-110` 等三处同构）：
  `plate:SetScale(RESOLUTION_X / plate:GetSize())`。
  写死 `SetScale(1.5)` 换 16:10 就错位；`SetScale(1)` 高分辨率下露边。
- **几何焦点导航**（`inventorybar.lua:760-788`）：
  点积 > 0 过滤方向、距离平方最小者胜。**必须用世界坐标**，
  因为各列表挂在不同父节点下、缩放不同 —— 这样容器整体缩放时导航依然正确。
- **光环 / 环绕步进的安全阀**（`inventorybar.lua:619-630`）：
  `repeat ... until start_idx == idx`，若所有槽无效则最多绕一圈，不死循环。

### ★ 温度系统的核心提炼（本轮重点）

**1. 保暖不改变「目标温度」，只封顶「速率」——这是最反直觉的一点**

`temperature.lua:367` 的目标温度公式：

```
delta = (环境温度 + totalmodifiers + 湿度惩罚) - 当前温度
```

**公式里根本没有保暖**。保暖只出现在 `:493` / `:502`，作为 rate 的**上限**：

```
rate = min(delta, SEG_TIME / (SEG_TIME + 夏季保暖))     -- 升温时
rate = max(delta, -SEG_TIME / (SEG_TIME + 冬季保暖))    -- 降温时
```

所以静止不动时，**穿多少毛毯最终都会趋近环境温度**，保暖只决定「多久到」。
这个选择让「换装备」变成「过渡速度」的选择而非「最终状态」的选择。
移植时若把保暖写成「目标温度 + 保暖」，玩家就永远不会真正回暖。

**2. 保暖是不对称的：只挡「变坏」的方向**

`:488-506` 的四个分支，规律是：

| 环境 | 自身方向 | 行为 |
|---|---|---|
| 暖 | 升温 | 用**夏装**封顶 |
| 暖 | 降温 | **全速**，已过热则 5 度/秒 ★保暖不参与 |
| 冷 | 降温 | 用**冬装**封顶 |
| 冷 | 升温 | **全速**，已结冰则 5 度/秒 ★保暖不参与 |

推论：穿顶级毛毯的玩家在暴风雪里，**归零后仍会以 `THAW_DEGREES_PER_SEC = 5`
的速度回温**，因为那时已进「升温」分支。保暖救不了已经冻僵的人，但能让你不走到那一步。

**3. 跨阈值自动加速回温（软墙）**
`THAW_DEGREES_PER_SEC = 5` vs `WARM_DEGREES_PER_SEC = 1`，
在 `:496`（解暑）与 `:505`（回温）形成 5 倍差。玩家在边界附近会感到「推不过去」的软墙。

**4. 伤害与偏离幅度脱钩——这才是「不会瞬间冻死」的真正答案**
`:519` `DoDelta(-hurtrate * dt, true, "cold")`，`hurtrate = WILSON_HEALTH / FREEZING_KILL_TIME = 1.25`。
体温可以是 -0.1 也可以是 -20（差 200 倍），**受到的伤害完全相同**。
若伤害随深度增长，玩家在最冷处会瞬间暴毙；DST 选择了恒定速率 + 120 秒缓冲。
注意 `FREEZING_KILL_TIME` 这个写法：调平衡只需改一个旋钮，实际掉血速率自动跟随。

**5. 保护分三层，职责分离**
| 层 | 位置 | 职责 |
|---|---|---|
| 值域夹取 | `:168` `clamp([-20, 90])` | 温度本身有界 |
| 上下文值域 | `:338` 冰箱、`:514` 局部 clamp | 本次计算允许的更严范围 |
| 速率不对称 | `:488-506` | 演化过程有界 |
| 血量底线 | `health.lua:616-621` `nonlethal_*` | 结果不为负（默认 false，仅特定规则开启） |

`:514` 的**双层夹取不是冗余**：外层用局部 `mintemp`（冰箱可抬高），内层用 `self.mintemp`（固有）。
删掉任何一层都会丢功能（冰箱失效，或温度跑出合理显示范围）。

**6. 为什么温度用每帧 `OnUpdate` 而饥饿用 1 秒定时器**

- `hunger.lua:38` `DoPeriodicTask(UPDATE_PERIOD=1, ...)`，而温度/湿度/理智都是每帧 `StartUpdatingComponent`。
- 三个结构性差异：① 积分步长——每秒一跳的量化噪声在温度计上肉眼可见，在饥饿条上看不出；
  ② 环境是**连续空间量**——`GetTemperatureAtXZ` 随坐标平滑变化，1 秒采样会跳过沿途冷热区；
  ③ 伤害是速率积分 `-hurtrate * dt`，固定 1 秒 tick 在掉帧时会算错，逐帧积分天然免疫帧率波动。
- 代价是真实的：温度每帧要 `GetInsulation()`（遍历装备槽）+ `FindEntities()`（空间查询）。
  代码因此要精心挑 FindEntities 的标签策略（`:350-351`：玩家用 ONEOF、其余用 MUST）。

**7. ⚠️ 关于「阈值迟滞」：本文件没有**
`:170` 与 `:174` 用的是 `(新) ~= (旧)` 的**边沿触发**，只为避免每帧重复 `PushEvent`；
状态本身在阈值附近仍会逐帧抖动。全库唯一的**真迟滞**在 `playercontroller.lua:3519`
（同目标加成 1.5 倍）。移植时若需要真迟滞带，得自己加。

**8. 双向调节量需要两套坐标系**
放热型 `warmingtemp = heat * heatfactor`（基准 0 度，heat=0 即无效）；
吸热型 `coolingtemp = (heat - overheattemp) * heatfactor + overheattemp`（基准过热线，heat=0 才等于「无效」）。
`:465-478` 必须用两套公式，否则「heat=0」的语义在两者间冲突。
同理，**双向系统每个方向都需要自己的「到达即停」阈值**：`:418-421` 的热食 62 度 / 冷食 12 度。

**9. ⚠️ 隐式耦合的常数**
`SEG_TIME/(SEG_TIME+insulation)` 的零保暖取值恰好是 1，与 `WARM_DEGREES_PER_SEC = 1` 巧合相等。
改后者不改前者，「零保暖升温上限」就静默失去联动。移植时建议显式拆开。

**10. 冻结是另一种性质，别套同一骨架**
`freezable.lua` 管的是离散状态机，用定时器而非每帧积分；且 `IsFrozen()` **包含 THAWING**
（`:116`），误用会导致「明明在化冻却还被当作冻结」。
冻结时必须同时停**大脑 + 攻击目标 + 移动**（`:265/268/272`），漏一项就出「被冻住的怪物还在追你」。

### 双向耦合：温度 ↔ 湿度（值得单独记一笔）

- `moisture.lua:293` 读 `temperature.externalheaterpower` → 站火边烘干更快（温度→湿度）
- `temperature.lua:306` 读 `moisture:GetMoisturePercent()` → 湿身体感 -0 到 -30 度（湿度→温度）
- **两个组件都不能单独理解**。`MOISTURE_TEMP_PENALTY = 30` 意味着「全身湿透 ≈ 环境温度降 30 度」，
  这就是 DST 雨季危险的根源。

`moisture.lua` 的骨架是**累加型**（多速率直接相加），比温度的**趋近型**（先求目标再求差）简单一整层。
选骨架的第一个依据：**这个状态是「趋近某目标」还是「多源累加」**。

### 三分支回退：镜像组件范式（combat_replica.lua）

几乎每个查询函数都是这个形状：

```lua
if self.inst.components.combat ~= nil then   -- 服务端：转发给真组件
elseif self.classified ~= nil then            -- 客户端：用镜像数据本地估算

**接口不区分端，只有实现区分**——这是 DST 镜像模式最值得学的地方。
对照 `container_replica`：后者管背包（高频增删改）需细粒度脏标记，字段众多；
前者管攻击意图（低频整体态）只需 4 个 net 变量。**镜像数据量由状态复杂度决定，不由原组件大小决定。**

客户端预测的两个关键细节：
- `:178` **误差补偿 -.5**——客户端有位置预测，不补偿就会「刀明明碰到却砍空」。代价是有效距离真短了 0.5 码。
- `:136-141` **只记账不执行**——`StartAttack` 在客户端仅记时间戳用于算冷却，真正攻击仍由服务端驱动。

- `CanHitTarget`（`:263-266`）：整体弃用 + `assert(BRANCH ~= "dev")` 硬拦截（客户端根本不需要）
- `CanLightTarget`（`:253-261`）：保留函数但简化实现（精度足够时）
`assert(BRANCH ~= "dev")` 是「开发期严格、生产期宽容」的双模式断言，比无条件 assert 或默默注释都好。

### 对自研游戏最有价值的 8 个模式

1. **列表虚拟化 = 复用池 + `updatefn(控件, 数据)` 重新绑定**
   （`scrollablelist.lua:36-65`、`serverlistingscreen.lua:1125`）
   DST 的 `ScrollableList` 有两种互斥模式，**选型判据是「项数是否会无界增长」**：
   - 模式 A（自带子控件）：控件数 = 数据项数。用于 modstab、筛选器列表等项数固定的场合
   - 模式 B（静态池）：只造 N 个控件，滚动时把「池内第 k 个」重新绑定到「第 i 项数据」。
     `serverlistingscreen` 用 **13 个行控件显示任意数量服务器**（`listings_per_view = 13`）

   **关键设计**：`always_show_static = true` 让「池 > 数据」时也对多余控件调用
   `updatefn(widget, nil)`，由绑定函数自己复位。这是池化与普通列表的本质差异。

   ⚠️ **暴露的缺陷**：`item_height = 20`（`serverlistingscreen:1125`）与实际行高
   （约 100）严重不符，但 `widgets_per_view = ceil(385/(20+10)) = 13` **恰好等于池大小**——
   即「用错误的数字凑出正确的结果」。根因是 `item_height` 同时承担
   「布局高度」与「视口计数」两个语义。移植时应把两者拆开。

2. **稳定标识 vs 位置：选中态绝不能用下标**
   （`serverlistingscreen.lua:1565` `actualindex = i`）
   `viewed_servers` 会被 `DoSorting` **原地 table.sort**，下标随排序变化。
   所以每项都携带 `actualindex`（过滤前的原始位置），选中态、高亮、双击检测全靠它。

   → 反例对照：`tradescreen.selected_items` 用下标做 key，那里侥幸正确
   仅因列表不排序。**判据是「这个列表会不会重排」。**

3. **「不可加入」与「被过滤」是两回事**（`serverlistingscreen.lua:1377-1379`）
   `IsValidWithFilters` 先排除「无论选什么过滤器都进不去」的服务器
   （friends_only 且非好友、ping 不可达…），**并单独计数**，
   于是「显示 100 / 共 87」中的「87」是有意义的。
   混为一谈会导致「显示一堆但一个都进不去」。

   ⚠️ 该计数器有副作用（`unjoinable_servers + 1`），且 `SearchForServers:763`
   清空 `self.servers` 时**忘记清零它**，靠 767 行的负数兜底。

4. **选中/搜索态的自动失效**（三处同构实现）
   - `mapscreen.lua:212` `ValidateMapTarget` —— 目标实体失效或归属条件不再满足
   - `serverlistingscreen.lua:1576` —— 选中的服务器不再符合新过滤条件则取消选中
   - `modstab.lua:212` `ValidateMapTarget` —— 与 mapscreen 同款

   → ★★★★ 这就是用户所说「焦点链：控件销毁时焦点如何失效」的答案：
   **DST 没有「对象销毁自动撤销焦点」的反向通知机制**
   （`Widget:Kill` 只摘父子关系，不通知祖先清焦点），
   所以「持有焦点的对象失效」必须由**持有者自己轮询检测**。

5. **不可信输入必须沙箱执行**（`serverlistingscreen.lua:1332`）
   `RunInSandboxSafe(data)` 执行服务器上报的玩家数据。
   服务器可上报 mod 列表/角色等结构化信息，而这些是 **Lua 片段**——
   直接 `eval` 等于给恶意主机一个客户端后门。
   且结果被缓存在 `session_mapping` 中，**避免重复执行同一段不可信代码**
   （既省性能，也减少风险暴露面）。

   缓存用 `nil / false / table` 三态表示「未处理 / 解析失败 / 成功」，
   下游 `charInvalid` 完全依赖这个区分——若失败时存 nil，过滤结果会反过来。

6. **屏幕栈只有三个操作，却足以表达模态层级**
   （`frontend.lua:959-1143` + `playerhud.lua:460`）
   ```lua
   function PlayerHud:OpenScreenUnderPause(screen)
       if self:IsPauseScreenOpen() then
           TheFrontEnd:InsertScreenUnderTop(screen)   -- 插到暂停屏「下面」
       else
           TheFrontEnd:PushScreen(screen)            -- 正常压栈
       end
   end
   ```
   → ★★ 这是「模态层」与「内容层」分离的最小实现：暂停屏必须留在栈顶，
   否则玩家在暂停时打开衣柜会「看起来像暂停结束了」。
   代价是用「栈顶屏名是不是 PauseScreen」做特判，加一个模态屏就要改这里。

7. **输入独占的四种粒度（按代价从低到高）**
   - **文本编辑态**（`serverlistingscreen.lua:2244`）：在 `OnControl` 最前面
     把事件转交 textbox 并 `return true`。零成本
   - **控件可用性**（`modstab.lua:92-146` `Enable/DisableConfigButton`）：
     视觉（Select/Unselect）+ 逻辑（字段拦截）+ **重建焦点链**三件套
   - **动画期间锁定**（`scrollablelist.lua:144` `LockFocus(true)`、
     `serverlistingscreen:1617` `self:Disable()`、`tradescreen:641` `machine_in_use`）
   - **模拟冻结**（`mapscreen.lua:59` `SetAutopaused(true)`、
     `playerhud.lua:1373` 指令轮盘自动暂停）

   → ★★★ `modstab` 的「禁用按钮必须重建焦点链」最容易被漏：
   不重建的话手柄导航会跳到一个点不动的按钮上，玩家会以为「手柄失灵」。

8. **脏标记 + 统一刷新点（三种粒度）**
   - `mapscreen.lua:1180` —— 五路 or 汇成一个刷新点（拖动/缩放/位置/左右动作类型）
   - `playerhud.lua:155` —— 去抖：`DoSimTaskInTime(3)` + 先 Cancel 旧的再建新的
     （湿度是连续 netvar，每帧都变，不去抖计时器永远推不到 3 秒）
   - `serverlistingscreen.lua:837` —— **两级过滤：先廉价后昂贵**：
     引擎脏标志 `GetServerListingReadDirty()`（O(1)）→ 再 `CompareTable` 深比较（O(字段数)）

   → ★★★★ 「数据变了才重建 UI」是所有轮询型界面的核心性能策略。
   `CompareTable`（递归深比较）承担了这个角色，使得每秒轮询一次服务器列表
   不会造成每秒重建 260 个控件。

| ② 开始 | `StartUsingItem()` | `StartUsingItem(target, doer)` |
| ③ 状态 | `inuse` 字段 + `inuse` 标签 | `inuse_targeted` 字段 + 标签 |
| ④ 停止 | `StopUsingItem()` | `StopUsingItem()` |

**这不是基类+子类，而是两个平行实现**，靠 `actions.lua:3299-3309` 与
`:3338-3350` 分别调度。二者共享协议却**无任何继承关系**。

**1. 目标合法性判定链 = 标签 or 回调（`useabletargeteditem.lua:3013-3017`）**

```
目标合法  <=>  inst.UseableTargetedItem_ValidTarget(target, doer)      -- 回调式
               或  target.prefab 且 inst:HasTag(target.prefab.."_targeter")  -- 声明式
```

**or 而非 and**：prefab 级声明一次生效零开销；回调式可读任意状态但每次都调。
多数物品只需前者。★ 自研游戏建议把这对 or 结构做成统一的 `TargetFilter` 配置项。

**2. 「用一次」与「使用中」的分离靠 `SetUsingItemDoesNotToggleUseability`（`:105`）**

一次性道具（挤奶器、肥料袋）不该闪「停止」按钮，该布尔让 `StartUsingItem`
成功但不置 `inuse_targeted`。这是统一抽象**必须**提供的扩展点：
协议只有「开始/停止」两态时，一次性道具只能假装自己在使用中。

**3. ★ 置位时机为何不同 —— 这是「不应强行合并」的实证**

| | 置位时机 | 为何 |
|---|---|---|
| `useableitem.lua:38-40` | 先置 `true`，再用回调返回值**覆盖** | 回调只是「做点事」，物品本体还在 |
| `useabletargeteditem.lua:122-125` | **回调成功且 `IsValid()` 后**才置 | 回调**极可能销毁自己**（挤奶器用完消失） |

`useableitem.lua:40` 用 `self.onusefn(...) ~= false` 而非 `if 返回值 then`，
正确处理了「回调没写 `return`」这一 Lua 常见写法 —— 换成 `if` 就会把
绝大多数正常回调误判为失败。而 `useabletargeteditem.lua:134` 的 `onstopusefn`
**只传 `self.inst`，拿不到 `target`/`doer`**，且构造函数也没有 `last_target` 缓存
（已逐行核实 `:39-52`），是当前设计的真实限制。

### ★ 二、长耗时动作的打断机制：workable 的进度条其实不在组件里

**`workable.lua` 不含任何进度条、计时器或协程。** 真正的驱动是
`actions.lua:1690-1730` 的 `DoToolWork` + stategraph 的 `dolongaction`，
每结算一次调一次 `WorkedBy_Internal`。

★ **最值得移植的一条设计：把进度建模为「剩余量」而非「已用时间」。**
`workleft` 是唯一的持久化字段，于是「打断」退化为「不再被调用」——
**无需任何中断代码、无需保存进度**，因为进度本身就是存下来的。

**浮点 epsilon 是必需品，不是洁癖**（`:140-142`，源码注释署名 NOTES(JBK)）：
`workmultiplierfn` 会产生 0.3/1.5 这类倍率，`workleft` 被减成 `0.0000001` 后，
若严格判 `<= 0`，玩家会看到进度条 99.99% **永远敲不完**。
`:136` 的 `workleft <= 1 直接归零` 是另一套收尾（针对「本来就只设 1 点」）。

**`workleft` 的两个特殊值语义相反**：`0` = 已完成（`OnSave` 里 `-1` 才是「无限耐久」）。
判「完成」必须写 `== 0`，不能写 `not workleft`。

⚠️ **`maxwork` 初值 `-1`（`:32`）而 `workleft` 初值 `10`（`:31`）是一对矛盾默认值**：
prefab 若忘了 `SetMaxWork`，实体会变成「永远敲不完但每次扣 1」的软锁死。

⚠️ **`savestate` 初值 `false`（`:34`）→ 绝大多数实体的进度不进存档**（`:106-113`）。
只有显式设 `savestate = true` 的（多半是玩家建造物）才持久化。

的每个 `Prefab` 对象被登记进一张全局表；此后 `SpawnPrefab("pighouse")` 就是查表拿 `fn` 调用。
⇒ **推论**：★ 一个 Lua 文件 = 一族预制体。`boat.lua` 末尾 `return` 了 23 个实体，
`treasurechest.lua` 8 个。读 `return` 语句要把它读成「注册表」而非「一堆独立定义」。

★ **2. 组件装配顺序是硬约束，不是风格问题**
`fn()` 被 `SetPristine()` 切成三段，6 个文件无一例外：

```
A 段  entity:Add* 实体组件 + 纯表现 + 纯客户端子实体   （两端都跑）
      ★ AddNetwork() 必须排在实体组件之后、AddComponent 之前
──── inst.entity:SetPristine()  ← 网络快照点 ────
      ★ 客户端在此 return（拿到的是「只有表现的壳」）
C 段  inst:AddComponent(...) 纯 Lua 组件            （仅服务端）
```

两种端判定**必须分清**：
- `not TheNet:IsDedicated()` —— 本机有没有画面（要不要造纯装饰/纯音频）
- `not TheWorld.ismastersim` —— 本端是不是服务端（要不要造逻辑组件）

监听服务器两者皆真；专服只有 `ismastersim` 为真。

★ **3. 资源清单与降级**
`Asset("ANIM", "anim/x.zip")` 交给资源打包器按需预加载。三种降级方式：
① 没声明的资源不加载（`boat_ice` 无 `MINIMAP_IMAGE` → 不画小地图）；
② 音效字段显式写 `nil` 并注释原因（`sounds_grass.creak = nil`，比留空字符串更可维护）；
③ 映射表查不到给合理默认值（`DECOR_SYMBOL_LOOKUP[...] or "gems_blue"`）。
★ 依赖清单（第 4 参数）等于「运行时零件清单」，比读代码里的 `SpawnPrefab` 更快摸清结构；
只 `SpawnPrefab` 不写进清单 ⇒ 正式构建可能被裁掉，运行时空 Prefab。

★ **4. 变体派生的三条路线**
| 路线 | 代表 | 适用 |
|---|---|---|
| 工厂 + 钩子 | `MakeChest`（9 参数 / 双钩子）| 变体多、差异正交 |
| 数据表 + pre/post 两段 | `create_common_pre` + `XXX_BOAT_DATA` | 同族多形态、共性重 |
| 变体调变体 + 覆盖 | `ice_crabking_fn` 调 `ice_fn()` 再打补丁 | 变体少、高度相似 |

★ 工厂参数数量应与「变体差异的维度数」成正比，不是越少越好 ——
`umbrella.lua` 的 `common_fn` 只有 1 个参数（bank/build 名），因为两个变体只差外观与消耗模式。

★ **5. 预制体名 = 玩家身份认知，外观 = 运行时状态**（★ 最重要的一条）
`deciduoustrees.lua:1310` 用一行 `SetPrefabName("deciduoustree")` 声明：
6 种颜色系（红/橙/黄/绿/光秃/毒）**不是 6 个预制体**，而是 `inst.build` 字段的取值。
⇒ 想做一个「红色的树」：若它是新东西 → 新增预制体；若只是这棵树变红 → 改 `build` 字段。
混用会导致存档、图鉴、配方全部分裂。

同理 `umbrella.lua` 里函数名 `pigskin`、预制体名 `umbrella`、模型名 `parasol`
**三者各不相同**且都是对的 —— 读源码时不能假设它们对应。

★ **6. 跨预制体协作：Lua 对象挂函数 = 公开接口**
预制体是闭包，模块级函数拿不到 `inst`。`crabking.lua:1637-1676` 把 30+ 个内部函数
挂到 `inst` 上（分「外部 / 内部 / 事件适配」三组），任何预制体都能调用。
`boat.lua:463` 定义的 `InstantlyBreakBoat` 就是被 `crabking.lua:1039` 跨文件调用的。
⇒ ★ 等价于「类的 public 方法」，但**没有类、没有继承表、没有元编程**。

★ 配套技巧（`crabking.lua:1683-1686`）：事件回调的「适配包装」
`inst.onkeystoneremoved = function(stone) OnKeyStoneRemoved(inst, stone) end`
同时解决两个问题：适配签名 + ★ **保证注册与解除是同一个函数对象**
（否则 `RemoveEventCallback` 静默失败，回调累积）。

★ **跨系统事件优于公共函数**：`umbrellaranout` 被三件不同的伞
（`umbrella.lua:81` / `hats.lua:1321` / `voidcloth_umbrella.lua:133`）共同发出，
玩家与 AI（`player_common.lua:667`、`SGhermitcrab.lua:435`）各自监听。
函数复用只解决代码重复，事件复用才解决响应一致性。

### ★ 一个值得单独记录的技术：标签「偷渡」过网络快照

★ **问题**：Lua 组件不参与网络同步，但客户端有时也需要知道组件的属性。
★ **解法**：在 `SetPristine()` **之前**手动 `AddTag()`，让标签随快照过去。

- `umbrella.lua:105-106` —— 原注释：`waterproofer (from waterproofer component)
  added to pristine state for optimization`
  （已核实 `components/waterproofer.lua:5` 有 Klei 官方 `V2C` 注释
  `Recommended to explicitly add tag to prefab pristine state`）
- `deciduoustrees.lua:1320-1331` —— 同一手法，但更精细：
  `AddTag("__combat")` → `SetPristine` → `RemoveTag("__combat")` → `PrereplicateComponent("combat")`
  ★ 连标签都会摘掉（临时协议，用完即弃），再用 `PrereplicateComponent` 让客户端提前建好空壳。

两个相隔万行的文件用同一手法 ⇒ 这是 DST 的既定约定，不是个人风格。

### 「组合优于继承」的三档证据（按说服力排序）

1. ★ **`deciduoustrees.lua:482` `make_stump`** —— 树与树桩**没有任何继承关系**，
   就是同一个 Lua 对象 `RemoveComponent` + `AddComponent` + 改几个字段：

   每个系统只管自己的输入输出（hauntable 输出「被闹鬼」、workable 输出「被砍到零」、

3. `crabking.lua:1719-1722` —— ★ 「宝石插槽」这个玩法是 trader 组件的现成能力，

   「玩家走近 → 提示 → 点击 → 接收 → 改变 Boss 强度」。

### 休眠优化：预制体层最重要的性能手段

★ `deciduoustrees.lua:909/926` —— `OnEntitySleep` 卸载 `burnable` / `propagator` /
`inspectable`（+ 火里的话连 `growable` 也卸），`OnEntityWake` 严格镜像重建。

### 存档：只存「跨组件的复合语义」

★ 统一规律：**单一组件的内部状态由组件自己存，预制体只存组件管不到的东西**。

| 文件 | 预制体存的 | 例子 |
|---|---|---|
| `pighouse.lua:272` | 1 个布尔 | `data.burnt` |
| `umbrella.lua` | 无 | 全交给 perishable / fueled |
| `treasurechest.lua:85` | 1 个布尔 | `data.burnt` |
| `deciduoustrees.lua:1028` | 8 个字段 | 状态描述 + **相对时间** |
| `crabking.lua:537` | 4 类子实体集群 | ★ 手写 GUID 表 |
| `boat.lua:165` | 碰撞体朝向 | `OnLoadPostPass` 重算 |

★ **时间绝不能存绝对值**：`deciduoustrees.lua:1043` 存
`monster_start_time - GetTime()`（相对差值）而非 `GetTime()` 本身。
所有带计时器的系统都适用。

★ **子实体集群存档的三种方案**（`crabking.lua:537-711` vs `deciduoustrees.lua:1224`）：
① 数量少且固定（5~15 个）→ 手写 GUID 表；② 数量不定 → `entitytracker` 组件；
③ 存的其实不是实体而是「配置」（如插槽里的宝石）→ 存字符串、读档时重新 `SpawnPrefab`。
★ 读档时 **每一个跨实体引用都必须判空**（`crabking.lua:621`、`deciduoustrees.lua:1120`）。

★ **`OnLoadPostPass` 是唯一安全的还原点**：只有它能拿到 `newents`
（GUID → 实体映射表），因为其它阶段其它实体可能还没被创建出来。

### 概率系统：必须走统一入口

★ `deciduoustrees.lua:556` 用
`TryLuckRoll(chopper, chance * chance_mod, LuckFormulas.DeciduousMonsterSpawn)`，
而非 `math.random()`。
⇒ ★ 直接用 `math.random()` 会**绕过玩家的 luck 影响**（饱食度、装备、雕像都会改 luck），
玩家会觉得「概率不对」。自研游戏若要做概率玩法，务必留一个统一的 roll 入口。

同类分层（`deciduoustrees.lua:532-553`）：季节概率 × 存活天数档位 × 砍伐者身份，三层修正。

### 二、★ 联机架构提炼（自研引擎移植用）

#### 1. netvar：声明顺序即 wire format
- `netvars.lua` 的 13 个 `net_*` **全部是 C++ 内建函数，Lua 侧零实现**（已 grep 全库核实）。
  它是一份**类型契约**，且是「Lua 与 C++ 双份真相」之一（首行注释指向 `luanetworkvariable.cpp`）。
- 三条硬规则：位宽必须与值域严格匹配 / 数组类型限量 31 且昂贵 / `net_hash` 写入可给字符串、
  读出只有哈希（**单向门**）。
- `GetIdealUnsignedNetVarForCount`（第 97 行）提供「值域上界 → 最窄类型」查表。
  真实用例见 `player_classified.lua:1535`（`craftinglimit_net_enum`，遵循 `_net_enum` 命名约定）。
- **★最容易踩的坑**：wire format 的一致性不仅约束「写了几行代码」，
  还约束**数据表的遍历顺序**。`player_classified.lua:1509/1515` 用 `ipairs` 而非 `pairs`
  遍历 `TechTree.BONUS_TECH`，否则两端展开顺序不同 → 立即错位。

#### 2. replica 分发：靠标签，不靠网络消息
- `entityreplica.lua` 回答「服务端如何决定谁能看到什么」，答案是**实体标签**而非逐客户端消息。
- **★两段式标签协议**（增量同步的关键技巧）：
  - `_inventory` = 需要同步；`__inventory` = 显式声明不要
  - 用「双下划线否定项」表达删除，是因为标签集合同步只发增量；
    没有否定项就无法表达删除，只能整表重发 —— 即分布式系统的「墓碑（tombstone）」思路。
- 白名单（19 个组件）是**安全边界**而非优化：组件的 netvar 自动同步，
  纳入白名单等于把服务端内部状态（配方解锁表、真实血量）主动送给客户端。
- 完整链路：服务端 `AddComponent` → `entityscript.lua:631` 自动调 `ReplicateComponent` →
  打标签 → C++ 随实体元数据下发 → 客户端实体构造完成 → 回调 `ReplicateEntity` →
  `require(name.."_replica")` → 新建副本挂到 `self.replica._`。
- **★同一份代码两端走**：客户端复用服务端同一个创建函数，由 `ismastersim` 自然分岔。
  另写一套「客户端简化版」是本层最典型的腐化来源。

#### 3. 脏值检测：只同步变化的部分
- `set`（权威写）/ `value`（读）/ `set_local`（本地写，不触发同步与脏事件）。
- `set` 仅在**值真的变了**时触发脏事件 —— 这是带宽命门，代价是 C++ 侧为每个 netvar 存上一帧值。
- **★`set_local` 的代价（netvars.lua:55-57 明确警告）**：服务端无法知道客户端预测成了什么，
  只能作废比较影子 ⇒ **下一次服务端 `set` 必定重发**。用得越频繁，无效重发越多。
- **★官方解法 = `ForceResync`**：`set_local(v)` + `set(v)` 强行使其变脏。
  真实用例：`clock.lua:161`（暂停恢复时纠正时间预测）、`player_classified.lua:16`
  的 `SetDirty`（全文件 18 次，用于「只想触发客户端事件」的场景）。
- **★净脏事件的两条合并策略**：`player_classified` 靠**命名复用**
  （health 的 5 个字段共用 `healthdirty`）；`clock` 靠**标志位中转**
  （脏回调只置 flag，`OnUpdate` 末尾统一派发 —— 保证「先推进状态再通知下游」的顺序）。

#### 4. `ismastersim` / `ismastershard` 的正交性
三个维度必须分清，源码三处经典判别：

| 判据 | 维度 | 典型用例 |
|---|---|---|
| `ismastersim` | 我是这个**模拟端**的权威？ | `entityreplica.lua:39`（只有权威能定同步策略） |
| `ismastershard` | 我是这个 **shard** 的权威？ | `clock.lua:342`（只有 shard 权威能自行推进时段） |
| `TheNet:IsDedicated()` | 本进程有**本地玩家窗口**？ | `world_network.lua:28` |

四象限（主 shard 服务端 / 主 shard 客户端 / 次 shard 服务端 / 次 shard 客户端）全部存在。
**★最典型的一处**：`clock.lua:259` 的 `ismastersim and not ismastershard`
= 「主 shard 的服务端」—— 它在链路上是**中转**（收上游、发给下游），
所以既不能自行推进时段（第 342 行只给 shard 权威），也不注册上游监听（否则形成反馈环自我激励而发散）。

#### 5. `SetPristine`：构造期的分界线
- 之前：构造代码在两端都执行；之后：**只有服务端执行**。不是 `if`，是引擎层代码路径分叉。
- **★所有含 netvar 的组件必须在分界线之前装配**，否则两端字段序列长度不同 →
  反序列化整体错位，且报错点与出错点相距很远。
  正确实例：`world_network.lua:54`、`player_classified.lua:1637`（123 处 netvar 全在其前）。
- 常见误解：`SetPristine` 之后**仍可**写双端代码（`player_classified.lua:1639` 就判了
  `not ismastersim`），因为引擎只是「默认只跑服务端」。

#### 6. classified：把数据切成共享与私有两半
- 服务端只生成 **1 份** classified，全客户端都收到，但各客户端只渲染属于自己的那份。
  实体数与带宽不随人数增长。
- `player_classified.lua` 就是这套机制的最大实例（123 处 netvar 的宿主）。
- **★dirty 事件三段式分发**（跨端只能走序列化通道，事件总线是进程内的）：
  玩家实体本地事件 → 服务端压进布尔 netvar（`SetDirty`）→ 客户端脏事件消费 → `PushEvent` 给玩家实体。

#### 7. 两条易被忽略的初始化铁律
- **★「先填数据，后接回调」**：`player_classified.lua:1634` 用 `DoStaticTaskInTime(0)`
  延后注册监听。否则初值反序列化本身会触发一批脏事件，表现为「刚进游戏就闪一串动画」。
- **★增量同步必须配「强制全量重算」**：`fns.OnInitialDirtyStates`。
  因为初值若恰好等于默认值，引擎判定「没变」不触发事件，客户端会漏掉初始化（偶发 UI 不刷新）。
- **★一次性网络事件要「收到即消费」**：不能在发送端预复位。
  `player_classified.lua:38-43` 有被刻意注释掉的复位代码，V2C 注释解释了原因：
  网络尚未 tick 时复位会**丢失脉冲**。

WhileNode(条件, 名字, 子树)   →  DISTANCE 段：每帧求值条件，决定子树是否继续
PriorityNode({...}, 间隔)     →  SCHEDULE 段：按数组顺序逐个试，第一个成功的赢
                               →  ★ 排列顺序即优先级，这是 DST AI 唯一的"控制流"
ChattyNode / DoAction / ...   →  HEALTH 段：真正产生位移与动作
```

`IfThenDoWhileNode(if, while, name, do)`（`braincommon:440`）是三段式的一次性表达。

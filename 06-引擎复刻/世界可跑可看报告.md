### 11.1 ★ 引擎字符串哈希被实证为 sdbm（67/67）

`host/03_globals.lua` 的 `hash()` 原本是个自造的多项式哈希，注释写着
「不追求与引擎一致」。**那个注释是错的** —— 引擎哈希值确实会被跨文件比较：

```lua
-- clothing.lua:11765
CLOTHING_SFX = { [0x7BB765F7] = { -- feet_horseshoe
    footstep_layered = "dontstarve/movement/run_horseshoes", } }
-- player_common_extensions.lua:1277
local skin_sfx = CLOTHING_SFX[inst.AnimState and inst.AnimState:GetSymbolOverride("foot")]
```

实证过程（探针已删，结论可复现）：

1. 拿 `_out/json/*.json` 里 **67 组「符号名 → 哈希」**当已知样本
   （这些哈希是 build.bin 里真实存的，不是猜的）
2. 试 fnv1a / fnv1 / djb2 / djb2x / **sdbm** / joaat / crc32 / murmur3 / jenkins
3. **只有 sdbm 全中：67/67**
   唯一看着不命中的 `SWAP_ICON`，是导出侧把显示名写成大写 ——
   `sdbm("swap_icon")` 才等于真实哈希 `0xF6AADF05`，反而印证了算法
4. `sdbm("feet_horseshoe") == 0x7BB765F7`，与 `CLOTHING_SFX` 的键分毫不差

sdbm 的经典写法用移位 `(c + (h<<6) + (h<<16) - h) & M`，而 Lua 5.1 没有位运算符
—— 这正是当初退化成多项式哈希的原因。但 `(h<<6)+(h<<16)-h == h*65599`，
可纯算术表达，两种写法已在 Python 侧交叉验证一致。顺带补了 `smallhash`
（用完整哈希而非截断，避免命令因低 16 位相同而静默合并）。

### 11.2 AnimState 符号覆盖（换装/皮肤）系统 —— 278 次调用

`host/10_animstate.lua` 实现了整套契约，逐行对齐真实源码：

| 方法 | 语义 | 实证来源 |
|---|---|---|
| `OverrideSymbol(sym, build, repl)` | 换符号；build 传 nil = 撤销 | skinner.lua:307 / mightygym.lua:144 / oceanfishingrod.lua:185 |
| `GetSymbolOverride(sym)` → **(哈希, 哈希)** | 无覆盖返 nil | 见 11.1 的两处；`balloon_held_child.lua:46` 塞 netvar 回退写 0 |
| `ClearOverrideSymbol` / `ClearAllOverrideSymbols` | 撤销 | skinner.lua:54 |
| `AddOverrideBuild` / `ClearOverrideBuild` | 登记/注销可用 build；注销连带撤覆盖 | beefalo.lua:283 |
| `ShowSymbol` / `HideSymbol` | 符号显隐，与覆盖正交 | skinner.lua:283/306 |
| `BuildHasSymbol(sym)` | 当前 build（含登记 build）有没有这符号 | skinner.lua:69 |
| `SetSkin` / `IsSkinBuild` | 皮肤模式 | skinner.lua:51 / wx78_backupbody.lua:1114 |

**★ 两个不显然的设计决定**：

1. **`GetSymbolOverride` 返回哈希而不是名字。** 两条独立证据逼出来的：
   ① `CLOTHING_SFX` 用数字键；② `balloon_held_child.lua:46` 的
   `inst._swap_build:set(swap_build or 0)` 塞的是 netvar、回退值写 0。
   反过来 `OverrideSymbol` 却收名字（skinner 传 `"wonkey"`）——
   所以两边都必须容得下两种形态。
2. **`SetBuild` 不清覆盖。** 反证：`ClearOverrideBuild` 与
   `ClearAllOverrideSymbols` 作为独立方法存在，若 `SetBuild` 已经清了就冗余。
   （这也保住 beefalo：先 `AddOverrideBuild` 登记 tendency build，
   之后 world.lua 再 `SetBuild` 换图集，覆盖不该丢。）

**★ 还补了一个此前漏掉的真实语义**：`AddOverrideBuild` 的真正用途是让
「base build 里**没有**的符号」能被动画引用到。全量统计发现 wilson 的动画引用了
**12 个**不在 wilson build 里的符号哈希（`swap_hat` / `SWAP_BODY` / `skirt` /
`swap_object` / `BEARD` / `tail` … 全是装备槽），beefalo 有 4 个。
旧实现把它们**静默丢弃** —— 画面缺件但不报错，正是最难发现的那类 bug。

**端到端验证（三组探针，全绿）**：

| 探针 | 验什么 | 结果 |
|---|---|---|
| CLOTHING_SFX 查表 | 穿马蹄铁后脚步声该变 | `CLOTHING_SFX[GetSymbolOverride("foot")]` **✔ 命中**，返回 `dontstarve/movement/run_horseshoes` |
| 几何替换 | wilson 的 foot 换成 rabbit_build 的 foot | `bld` 切到 `rabbit_build`、UV 从 0.5547 → 0.6094、撤销后回落、覆盖到不存在的 build 时保留原符号 |
| 牛鞍（真实数据） | `AddOverrideBuild` 让 base build 没有的符号可解析 | 不登记时 DrawList 14 元素、鞍符号被丢；登记 `saddle_basic` 后 **15 元素**、`bld=saddle_basic`；`GetSymbolOverride("swap_saddle")` 返回 `hash("saddle_basic")` |

牛鞍这条是**完整走通真实链路**的证据：全库扫描发现 beefalo 动画引用的
`0x653942B3` 正是 `sdbm("swap_saddle")`，由 `saddle_basic.zip` 提供，
而 `rideable.lua:157` / `rider.lua:109` 做的就是
`OverrideSymbol("swap_saddle", saddle_build, ...)`。

### 11.3 BufferedAction 体系 —— 91 次调用

`host/06_entityscript.lua` 实现了 `GetBufferedAction` / `PushBufferedAction` /
`PreviewBufferedAction` / `PerformPreviewBufferedAction` /
`PerformBufferedAction` / `ClearBufferedAction` / `InterruptBufferedAction`。

**为什么必须真实实现**：全库 216 处读它，几乎全是 brain 的守卫条件
（`dragonflybrain.lua:39`、`dustmothbrain.lua:125` 的 `WhileNode`、
`oceanfishbrain.lua:222` 的 `ConditionWaitNode`、`monkeybrain.lua:407` …）。
语义是「这个实体正忙着做某个动作吗」—— 桩返 nil 等于**永远不忙**，
于是「等它忙完」类节点立刻穿透、「它在忙」类分支永不进入。

`GetBufferedAction` 本体就一行（`entityscript.lua:4179`）：
`self.bufferedaction or (locomotor and locomotor.bufferedaction) or nil`。

**11 项探针验证全过**：常规动作挂上 / `ClearBufferedAction` 先 Fail 再置 nil /
`TestForStart` 失败发 `actionfailed` 且不挂上 / `WALKTO` 直接 Succeed 并清空 /
`instant` 与 `options.instant` 都走立即路径 / `PerformBufferedAction` 只清自己的 /
去重守卫比的是**对象同一性**（真实 DST 里动作是 `ACTIONS` 单例，测试必须复用同一张表）。

### 11.4 Physics 碰撞体/材质属性 —— 76 次调用

`host/11_physics.lua` 修了一个**真实的字段名错配**：

```lua
-- 00_stubs.lua 泛化桩：所有 setter 统一存成 "_"..方法名小写
rawset(self, "_" .. m:lower(), first)     -- SetMass(5) → _setmass = 5
-- 而 OVERRIDES 表里的 getter 读的是另一个键
GetMass = function(self) return self._mass end   -- 读 _mass（初值 1）
```

存的和读的完全不是同一个键 —— `SetMass(5)` 之后 `GetMass()` 永远返回 1。
实测 world.lua 2400 tick 里这组 setter 被调 76 次，全部落进这个黑洞，
谁也没发现，因为没人断言过它。

修复后（探针实测）：

```
wilson   radius=0.5 mass=75  group=1024 mask=224 friction=0 damping=5
rabbit   radius=0.5 mass=1   group=1024 mask=224 friction=0 damping=5
beefalo  radius=0.5 mass=100 group=1024 mask=224 friction=0 damping=5
poop     radius=0.5 mass=1   group=256  mask=224 friction=0.1 damping=0
```

**半径真的进了碰撞判定**：此前 `_integrate` 只用**中心点**判可通行，
于是 `SetRadius` 设了个寂寞 —— world.lua 自己就调了 `SetRadius(0.5)` 却被忽略，
一个半径 0.5 的生物可以脸贴进不可通行瓦片。现在沿运动方向前后各采一个半径
（等价于「用长 2r 的线段代替点」），`r=0` 时两点重合、行为与旧版一致。

⚠️ **诚实边界**：mass / friction / damping / restitution / collision-group
在本宿主里**只存不用**。`11_physics.lua` 文件头已声明 —— 宿主只做
「motor velocity 积分 + 瓦片可通行判定」，**不建模**实体间碰撞、推挤、摩擦耗散。
喂进积分器就是伪造一套宿主并没有的物理。补了 `GetFriction`/`GetDamping`/
`GetRestitution`（原先不在方法清单里，会是**真缺口**）。

### 11.5 修好 `render_frame.py` 的光栅化（两个真 bug）

此前它对 pig / wilson 都输出噪点/残件，而 `build_world_player.py` 的仿射四边形
路径却正确。逐字节比对两条路径取到的顶点数据**完全一致**后，确认 bug 纯在光栅化：

1. **顶点池是三角形列表，旧代码只画前 2 个三角形**
   ```python
   if len(pts2) >= 6:
       draw_tri(pts2[0], pts2[1], pts2[2], tex)   # 就这两个
       draw_tri(pts2[3], pts2[4], pts2[5], tex)
   ```
   nv 越大丢得越多：`pig_head` nv=24 → 8 个三角形只画 2 个；
   `face` nv=12 → 4 个只画 2 个（所以只有眼睛清楚）；
   `hair` nv=114 → 38 个只画 2 个（所以头发是一条条条纹）。
   **数据是对的，光栅化漏画** —— 这正是「渲染出来是噪点」的根因。
2. **`tex = texs[0]` 恒用第一张图集** —— 多图集 build（pig_build 有
   atlas-0 2048² + atlas-1 1024×512）里属于 atlas-1 的符号会拿 atlas-0 的纹理采样。

修复后 pig / wilson 都渲出**可辨认的完整形象**（猪人：头/耳/身/臂/腿/草裙；
wilson：标志性尖发 + 红衣服），可见像素 23943 → **59752**（2.5 倍）。

### 11.6 ⚠️ 一个方法论教训：A/B 结论被方差混淆过

排查「性能是否回退」时，我先后把 radius、`ov_by_hash`、BufferedAction、
整个 11_physics 都回退过，每次都「看起来有效」，一度得出错误结论。

**真相**：world.lua 的运行时间有 **1-in-5 的长尾**（`pairs(Core.Spawned)`
遍历顺序不确定 → 生物行为不同 → 成本不同）。恢复干净实现后连测 10 次：
**7 次在 800~840ms（≈2950 tick/s，即基线）**，2 次 1.8~3.3s。

**教训**：这个工程的 A/B 必须**多次采样取分布**，单次或 3 次采样会把人带歪。
纯 Lua 基准（27ms，10 次零方差）证明机器本身是稳的 —— 波动来自工作量，不是环境。

#### 17.1 两个「加了却看不见」的坑

1. **景物必须注册进 `watched`。** 它们不参与 AI（不进 `ents`），
   但若不进采样列表就**不进轨迹**，播放器里还是空的。
   这是「加了树却看不见」的唯一原因 —— 与渲染无关。
2. **景物只采第 1 帧。** 它们是静止的，逐采样点重采没有信息量，
   却要为 90 个景物 × 1200 个采样点跑 10.8 万次
   `draw_sig → AnimState:GetDrawList()`。
   改成「只在 `i <= SAMPLE_EVERY` 时采一次」，播放器侧
   `frameAt()` 会沿用最近一帧，画面完全一致。

#### 17.2 顺带修掉的两个缺口

- **`SpawnPrefab("evergreen")` 失败 20 次** —— `evergreens.lua` 末尾是一串
  `tree("evergreen", ...)`，而 `tree()` **内部**才调 `Prefab(name, ...)`，
  名字是变量，文本索引扫不到。加进「动态家族文件」列表
  （与 `fx` / `preparedfoods` 同类，见 16.3）。
- **`EntityScript:SetDeploySmartRadius` x70** —— 每个景物都调一次。
  原版实现是「存值 + 转告 Map 更新一个全局间距常量」
  （`entityscript.lua:835` → `components/map.lua:21`），
  语义是「放置时与旁边实体留多远」。已按原版实现，并把
  `SetDeployExtraSpacing` / `SetTerraformExtraSpacing` /
  `SetGroundTargetBlockerRadius` 一并补上。

#### 17.3 ★ 石头：**诚实放弃**

`rock.zip` / `rock2.zip` 各自带 `build.bin`，但它们里面的 `anim.bin`
**解析出 0 个动画**；全库扫描也没有任何一个包提供「命中 rock 符号的 `idle`」。
石头只需要一个静止的 idle，但没有可解码的动画数据 ⇒ **不放进来**。

**这是一个取舍，不是遗漏**：放进去就是一块**看不见的占位**
（玩家会以为那里有东西却什么也没有），比「干脆不放」更糟。
所以报告里明确写出来，而不是让它变成缺口清单里的一行。

#### 17.4 性能

加上景物后帧率 1285 → **711 tick/s**（两天 30000 tick 约 42 s）。
开销主要不在采样，而在**景物自身的组件更新**
（burnable / workable / pickable 等每 tick 都在跑）——
这与真实 DST 一致（它同样更新这些组件，只是靠 C++ 更快）。
真实引擎靠「远离玩家就休眠」省这笔开销。**本轮把这一环补上了**（见第 18 节）。

### 27. ★★ WebGL 渲染后端（`?renderer=gl`）

按 P2-1 执行。播放器现在有**两个渲染后端**：默认仍是 canvas 2D，
`?renderer=gl` 走 WebGL2。

#### 27.1 架构：分层 + 顺序段

- **分层**：地形仍由 canvas 2D 画（`terr` 是预渲染 canvas），
  上面叠一块透明的 `#cvgl` 专画精灵。为什么不把地形也搬进 WebGL：
  那要另写一套瓦片着色器，收益低风险高。
- **顺序段**：`emitQuad` 把 quad 收进「段」，**图集一换就开新段**，
  段间严格保序。实测 957 quad/帧 → 70 段 → 70 次 `drawArrays`。
  （对比 canvas 2D：957 次 `setTransform` + `drawImage`。）

#### 27.2 三个坑（都不是「算错了」，但都会让 GL 静默不工作）

1. **headless Edge 要 `--enable-unsafe-swiftshader`**。
   不加这个 flag 时 `getContext('webgl2')` 返回 null，
   日志只有一句 `Automatic fallback to software WebGL has been deprecated`。
2. **不能复用已经 `getContext('2d')` 的 canvas**。
   `#cv` 早在脚本开头就当了 2D 画布，再向它要 webgl 只会拿到 null
   （**无任何报错**）⇒ 必须用独立的 `#cvgl`。
   这一条的迷惑性最强：日志显示 `canvas=found`，只是 context 拿不到，
   很容易误判成「环境不支持 WebGL」。
   （对照实验：`document.createElement('canvas')` 的独立测试页在同样 flag 下
   `webgl2=yes` ⇒ 环境是好的，是画布被占用了。）
3. **按图集分桶会破坏叠加顺序**。
   第一版用 `Map<img, 顶点数组>`，而 Map 的遍历顺序是**插入顺序**，
   不是「实体间按 z、实体内按 layer」的绘制顺序 ⇒ 该压在上面的被盖住。
   实测两个后端差 11.82%，且 flush 统计 `skipped=0`（**一个都没漏画**）
   —— 纯粹是顺序错了。改成顺序段后段数 15 → 70。

#### 27.3 A/B 结论：差异是**光栅化器固有的**，不是 bug

同一帧、同一轨迹，两种后端对比：

| scale / zoom | 差异像素 |
|---|---|
| 2 / 100 | **0.95%** |
| 2 / 200 | 3.10% |
| 6 / 150 | 11.82% |

**差异随缩放增大而增大**，且 53~71% 的差异是**小幅**（≤60/765 ≈ 8% 色差）
⇒ 归因于 canvas 2D 与 WebGL 在缩放采样上的核不同（边缘/半透明 AA 处最明显）。
scale=2/zoom=100 时已基本一致，说明结构与 UV 都对。

**没有测帧率** —— 无头环境跑的是 SwiftShader（软件渲染），
测出来的数不代表真实 GPU。要做这个对比必须有真机，
所以这里只报「能跑通、结构等价」，**不报性能数字**。

#### 27.4 用法

```
world_day_player.html?renderer=gl&scale=2&zoom=100&tick=6000&play=0&ui=0
```

默认（不带 `renderer`）仍是 canvas 2D —— 保留它是为了**能 A/B**：
没有对照就无法证明新后端是对的还是错的。

### 26. ★ 腐烂 / 饥饿链路（新入口 `perish.lua`）

按 P1-2 执行。两条链路都通了。

```

饥饿：hunger 5 → 第 31 tick IsStarving() 首次为真 → current = 0                 ✔
```

#### 26.1 一个「我以为它每 tick 动」的误解

第一版跑 200 tick（6.7 s）就看到「剩余从 2 掉到 0.56 就再也不动」，
一度怀疑组件没更新。真相是**我的测试时长不够**：

`Perishable` **不用 `OnUpdate`**，而是
`DoPeriodicTask(dt, Update)`，其中 `dt = 10 + math.random()*FRAMES*8`（秒）
—— **每约 10+ 秒才推进一次**，每次按 dt 秒扣。
所以「2 → 0.56」是**一次** Update 的结果，之后停住只是在等下一个周期。
跑到 1200 tick（40 s，约 3 个周期）才变质。

**教训**：同样是「慢速推进」的组件，推进的**节拍**各不相同
（perishable 按周期、hunger 每 tick）。写验证前得先看清它靠什么驱动，
否则会把「还没到下一次触发」误判成「没在工作」。

（顺带：`hunger` 默认速率很慢，20 秒只掉 2.65，从 5 掉到 0 要 37 秒以上；
所以要 `SetRate` 调高再验。）

#### 39.3 修法：一个**代理工厂**补掉全部 12 个

```lua
local function proxy_child(name)
    local rec = { _name = name, _calls = {} }
    return setmetatable(rec, { __index = function(t, k)
        local m = function(self, ...) self._calls[k] = (self._calls[k] or 0) + 1
                                      return self end
        rawset(t, k, m); return m
    end })
end
```

### 32. ★★★ 一个 bug 类连续出现三次：`G.X` 与 `_G.X` 是两套绑定

#### 32.1 机制

`host/03_globals.lua` 用一张**暂存表** `local G = {}` 收集全局，
再由 `05_bootstrap.lua:26-27` **一次性拷贝**进真全局：

```lua
for k, v in pairs(G) do
    if k ~= "TheSim" then _G[k] = v end
end
```

所以 **bootstrap 之后，`G.X` 与 `_G.X` 是两个互不相干的绑定**。
之后写 `G.X = v` **不会**更新 `_G.X`；而游戏代码读的是 `X`
（也就是 `_G.X`）⇒ 永远是旧值。

**关键：这类 bug 全部静默。** 不报错、不进桩清单，
而「赋值语句写得好好的」——所以肉眼与 grep 都不会发现。

#### 32.2 三次出现（一次比一次隐蔽）

| # | 位置 | 写法 | 后果 | 怎么发现的 |
|---|---|---|---|---|
| 1 | `PrefabExists` | 读 `G.Prefabs`（暂存表**没有**这个字段） | **自打加上起就永远返回 false**，被一个通过的测试盖住 | `tests.lua` 的 T2 直接断言它的行为 |
| 2 | `SetFocalPoint` | 写 `G.TheFocalPoint` | 绑定「返回成功」但 `_G.TheFocalPoint` 从没变 ⇒ **游戏永远读到 nil** | T12 第三条断言：`rawget(_G,...) == p` |
| 3 | `20_map.lua` | 写 `G.Map`（在**函数体内**，晚于拷贝） | `components/map.lua:3` 的 `local _SetTile = Map.SetTile` 会拿到 nil | 静态清扫「函数体内写 G.X」 |

第 3 例值得单说：它**在函数体内**，所以连启动期的拷贝都覆盖不到；
而且 `map.lua` 目前没有任何场景加载，所以**至今没暴露**——
属于「还没被触发」的定时炸弹。

#### 32.3 统一判据（已写进三处代码注释）

> **凡是运行时才被赋值的全局，一律要写 `_G`。**
> 只有「启动期一次性定义」的全局才可以用 `G.*` 了事。

三处都按此改了（`SetFocalPoint` 同时写两处、`Map` 同时写两处，
`PrefabExists` 直接改读 `Core.Prefabs`）。

#### 32.4 清扫方法（可复跑）

静态扫「**函数体内**对 `G.X` 的赋值」（缩进/函数深度 > 0）——
启动期赋值不需要写 `_G`，运行时赋值必须写。
本次扫出 1 处（`20_map.lua` 的 `Map`），已修。

> 附带一条方法论：**同一 bug 类出现第二次，就不要再靠「小心」——
> 要做的是把判据写下来 + 做一次系统性清扫。**

```lua
-- host/03_globals.lua
local G = {}                                    -- 第 15 行：往 _G 灌全局的**暂存表**
function G.PrefabExists(name)
    ...
    if G.Prefabs ~= nil and G.Prefabs[name] ~= nil then return true end
```

2. `burn.lua` 当时**照样通过** —— 因为树的掉落路径压根不调它

3. 「不报错 + 测试通过」看起来像正常

- 用 `Core.Prefabs` 而不是 `G.Prefabs`
- `meats` 加进 `DYNAMIC_FAMILY_FILES` —— `fishmeat_small_cooked` 这类名字
  是用 `common(...)` **批量注册**的，文件里没有字面量 `Prefab("xxx")`，

### 26. ★★★ WebGL 渲染后端：证明「画的是同一幅图」，然后比速度

播放器本来就有两个后端（`?renderer=2d` / `?renderer=gl`），

#### 26.1 正确性：scale=1 时两后端**逐字节完全一致**

|---|---|---|---|---:|---:|
| 2000 | 66.7 | 白天 | 无 | **100.0000%** | 100.000% |
| 6000 | 200 | 白天 | 无 | **100.0000%** | 100.000% |
| 10800 | 360 | 黄昏 | 有 | 6.774% | **100.000%** |
| 13200 | 440 | 夜晚 | 有 | 6.774% | **100.000%** |

**558000/558000 像素逐字节相同** ⇒ GL 侧的符号解析、UV、分段顺序、
纹理选择**全部正确**。

#### 26.2 两个差点被当成 bug 的现象

1. **放大 6 倍后差异 10.95%。** 我先怀疑是 alpha 管线
   （`UNPACK_PREMULTIPLY_ALPHA_WEBGL` + `blendFunc`），改成预乘管线后
   差异 10.85% → 10.95%，**没有改善**（是量化噪声）。
   而两条管线在 scale=1 下**都是 0.00%** ⇒ alpha 管线根本不影响结果。
   **真正的解释是插值实现不同**：canvas `drawImage` 的平滑插值
   vs WebGL `texture2D` 的双线性采样，两者都是合法实现，不该「修」到一致。
   我为此做过三个排除实验，都记录在工具注释里，避免下次再绕：
   - 差异方向：GL 更亮 52% / 更暗 48%，**平均偏差 +0.1 ≈ 零** ⇒ 不是合成问题
   - 平移假设：dx/dy 各取 -2~+2，**dx=0,dy=0 最优** ⇒ 无几何偏移
   - 幅度分布：20~200 各档均匀 ⇒ 不是只有边缘
2. **黄昏/夜晚帧只有 6.774% 逐字节。** 看着像错，其实是**色调叠色的舍入差**：
   canvas 2D 走逐 quad 全局乘法，GL 走 `uTint` uniform，
   舍入位置不同 ⇒ 差在 ±24 以内（阈值近似 100%）。
   ⇒ 判据必须**按「这一帧有没有叠色」分开**，否则要么放过真错、
   要么把正常舍入当 bug 反复修。

### 24. ★★★ 卸下装备不生效：`OverrideSymbol` 的单边登记（新入口 `equip.lua`）

按 `后续任务清单.md` 的 P1-3 执行 —— 验「已实现功能的反向路径」。
结果是：**正向能画，反向清不掉。**

#### 24.1 新入口 `equip.lua`：不只验正向

此前只验过「装备 → 覆盖 → 画面上多一块」（`tools/verify_override.py`，像素级
133 像素 / 1 个连通块）。但**卸下**那条路从没走过 —— 而「半边实现」正是这类功能
最常见的坏法。所以新增入口 `equip.lua`，在**数据层**验往返：

| 阶段 | `_overrides` | `_ov_builds` | `GetDrawList` 的 bld 条目 |
|---|---:|---:|---:|
| 装备前 | 5 | 22 | 0 |
| 装备后 | 6 | 23（+hat_football） | 1 ✔ |
| **卸下后（修复前）** | **5** ✔ | **23** ✘ | **1** ✘ |
| **卸下后（修复后）** | **5** ✔ | **22** ✔ | **0** ✔ |

`_overrides` 干净了，但 `_ov_builds` 里 `hat_football` **留着没撤** ——
`GetDrawList` 的回退路径（base build 没有 `swap_hat` 时去 `_ov_builds` 里找）
于是继续输出 `bld=hat_football` ⇒ **帽子留在画面上**。

#### 24.2 根因：宿主单边登记

`host/10_animstate.lua` 的 `OverrideSymbol` 会**顺手**把 build 登记进 `_ov_builds`：

```lua
-- OverrideSymbol 会自动把 build 登记为可用覆盖 build
-- （skinner.lua:307 的 "wonkey" 就没先 AddOverrideBuild）
if bname and not self._ov_builds[bname] then self._ov_builds[bname] = true end
```

这个「自动登记」本身有依据（`skinner.lua:300` 确实直接
`anim_state:OverrideSymbol(sym, "wonkey", sym)` 而没先 `AddOverrideBuild`，**已核实**）。

但原版 `prefabs/hats.lua:76` 的 `_onunequip` **只调 `ClearOverrideSymbol`**：

```lua
owner.AnimState:ClearOverrideSymbol("headbase_hat")
owner.AnimState:ClearOverrideSymbol("swap_hat")
```

⇒ 单边登记 + 单边清除 ⇒ **`_ov_builds` 里的 build 永远不会被撤掉**。

#### 24.3 修法：记一本「自动登记」账，成对撤销

新增 `as._ov_auto[build] = { [符号名] = true }` 记录「谁把它带进来的」。
`ClearOverrideSymbol(sym)` 先查这个账：

- 该 build 只被这个符号引用 ⇒ 随覆盖一起撤（并让哈希缓存失效）
- 还有别的符号在用，或它是**显式** `AddOverrideBuild` 登记的（不在账上）⇒ 保留

`ClearAllOverrideSymbols` 同样对每个被清的符号走一遍成对撤销，
**不能只把表清空** —— 否则剩下的自动登记 build 还是清不掉。

#### 24.4 度量口径上的一个自查

第一版验证里我查的是 `GetSymbolOverride("headbase_hat")`，而实际被覆盖的是
**`swap_hat`**（hash 1690368943）—— 查错了符号名，导致「装备后也应非 nil」的判据
一直失败。修正后才看到真实图景。
另外 `bld` 有**两个**来源（`_overrides` 与 `_ov_builds`），
正则里必须分开看，否则会把「`_onunequip` 没清 `_ov_builds`」误判成
「`ClearAllOverrideSymbols` 根本没生效」。

### 23. ★★★ 纠正一个测量错误：帧率是双峰分布，此前报的是幸运样本

这一轮本打算继续审计，结果在复测帧率时**发现之前报的数字不可信**。

#### 23.1 发现过程

改完两处 instrumentation 后复测，world.lua 从「~1000 tick/s」掉到「~500」。
先按惯例做了两次检查：

1. **对照实验** —— `seasons.lua`（无实体，纯世界状态）三次采样稳定在
   91000~93000 tick/s，与历史持平 ⇒ **不是系统负载**。
2. **A/B 还原** —— 临时还原 `14_replica.lua` 的改动，三次采样 395~619
   ⇒ **不是我的改动**。

两次都排除后，按项目规范（「A/B 必须多次采样」）采了 10 次：

```
371  354  376  389  341  333  340  526  999  1020     （tick/s）
排序：333 340 341 354 371 376 389 526 999 1020
min=333  max=1020  中位数=374  极差 3.1 倍
```

**双峰分布**：8 个样本聚在 330~390，2 个在 ~1000。

#### 23.2 ★ 这意味着什么

回看历史记录，我先后报过：
- 「帧率 552 → **1212** tick/s（休眠生效）」
- 「**1046** tick/s」「**1127** tick/s」「**939** tick/s」
- 「528 tick/s」

**这些全是单次采样**，而且不幸（或者说幸运地）大多落在快尾。
真实的中位数是 **~374 tick/s**，不是 1000+。

`seasons.lua` 之所以稳定，是因为它**没有任何实体**；
`world.lua` 的波动来自 `pairs()` 遍历顺序不同 ⇒ 实体处理顺序不同
⇒ 休眠/唤醒的时机不同 ⇒ 每 tick 实际工作量不同。

#### 23.3 纠正

| 指标 | 此前报的 | 10 次采样后 |
|---|---|---|
| world.lua 帧率 | 1000+ （单次，快尾） | **中位数 ~374**，双峰 330~390 / ~1000 |
| 休眠的收益 | 「552 → 1212」 | **无法用单点数字量化**，需同样多次采样对比 |

休眠**确实有效**（机制验证过：57/89 入睡、状态图进 hibernaters 桶），
但「翻倍」这个说法建立在不可靠的采样上，不应保留。

**教训（第二次踩同一个坑）**：项目记忆里早就写了「world.lua 有长尾，
单次/3 次采样会得出错误结论」，我这次又报了好几个单点数字。
**凡是波动的量，报数字必须带样本数与分布形态**，不能报一个「代表性」值——
因为没有哪个单值是代表性的。

#### 23.4 顺着这条查了其他指标：方差大小与「离纯几何多远」成正比

既然帧率不可信，其他单点数字呢？同样采 10 次：

| 指标 | min | max | 中位数 | 极差 | 性质 |
|---|---:|---:|---:|---:|---|
| 物理撞墙次数 | 314 | 332 | **314** | 1.06x | 纯几何（固定圆周 × 固定种子地形） |
| 状态图状态种类 | 75 | 90 | **83** | 1.20x | 半行为 |
| 战斗事件次数 | 40 | 58 | **50** | 1.45x | 行为（受 `pairs()` 顺序影响） |
| 帧率 | 333 | 1020 | **374** | 3.1x | 涌现量 |

**规律很干净：越靠近纯几何越确定，越依赖「实际发生了多少事」越不确定。**

- 撞墙 9/10 都是 314 —— 它只由「玩家走固定圆周」和「固定种子的地形」决定，
  与生物怎么动无关，所以可以当单次采样用。
- 战斗事件取决于生物 AI 的决策序列，而 AI 的更新顺序受 `pairs()` 影响 ⇒ 必然波动。
- 帧率是「这段时间里实际发生了多少事」的涌现量，波动最大。

**实用结论**：报数字前先问「这个量离纯几何有多远」。
撞墙次数可以直接报；战斗事件和帧率必须带样本数和分布。

#### 22.2 ★ 一个自己造成的假警报（值得记下来）

审计 `StopBrain` 时，我用 `tostring(E.StopBrain):find("_brainstopped")` 判断它是不是真实实现，
结果显示 false，于是判定「空实现生效了」。

**但这是测量方法错误**：Lua 里 `tostring(function)` 返回的是

改用**行为测试**后真相是：

```
_brainstopped 初始        = nil
StopBrain('test') 之后    = table: 0x...     ← 真实实现，正确置位
RestartBrain('test') 之后 = nil              ← 正确清除
```

`13_update.lua` 装得更晚（bootstrap 766 行 vs 741 行）且用直接赋值，所以覆盖成功。

**教训**：判断「某个实现是不是真的」不能靠读函数对象的字符串表示，
只能靠**可观测的行为**。这与本工程一贯的做法一致——但它以「我自己犯错」的形式
又演示了一遍，所以记下来。

#### 22.3 修正：把限制输出到演示报告里

### 20. ★★ 休眠补全：状态图也要进 hibernaters 桶

第 18 节的休眠只做了一半。这一轮查出另一半。

#### 20.1 缺口：`sg.Start` 不传 hibernate

原版 `entityscript.lua:404-408`：

```lua
if self.brainfn or self.sg then
    local asleep = self:IsAsleep()
    if self.brainfn and not (asleep or self.sleepstatepending) then
        self:_EnableBrain_Internal()
    end
    if self.sg then
        self.sg:Start(asleep)      -- ← 传 IsAsleep()
    end
end
```

宿主首次启动状态图时调的是 `sg.Start` **不传参** ⇒ `hibernate` 恒为 nil
⇒ `SGManager:AddInstance` 永远把它塞进 **`updaters`（热桶）**。

而 `stategraph.lua:118-119` 的 `StateGraphWrangler:Update` 只遍历 `updaters`：

```lua
local updaters = self.updaters
self.updaters = {}          -- ← 每 tick 清空重建
for k, v in pairs(updaters) do ... k:Update() ... end
```

**后果：休眠实体省了组件更新，却没省状态图更新** —— 每 tick 还在跑 `sg:Update()`。
这正是「休眠只做了一半」的由来。

#### 20.2 修法（两处，都是原版已有的 API）

1. `sg.Start(inst:IsAsleep())` —— 首次启动就把状态图放进对的桶
   （`02_sim.lua` 的 SG 启动段）。
2. 睡/醒时搬桶 —— 原版 `stategraph.lua:47/53` 就提供了
   `SGManager:Hibernate(inst)` 与 `SGManager:Wake(inst)`，
   在 `UpdateSleepStates` 里跟着 `_asleep` 一起切。

#### 20.3 验证

```
· 实体休眠：57/89 个实体已入睡（入睡半径 40 格，以玩家为中心）
  本 tick 因休眠被跳过的组件更新：3 个
  状态图调度桶：updaters=1  hibernaters=8（后者不跑 Update）
```

> ⚠️ 上面这段是**当时的输出**（89 个实体 / 10 种生物）。
> 2026-10-15 加到 14 种生物后重测为 **57/98 个实体已入睡**
> —— 入睡**数量**基本不变（睡的都是远处的生物），
> 但**分母从 89 变成 98**，所以引用时要用新值。

`hibernaters=8` 证明状态图真的进了休眠桶（`updaters` 每 tick 被清空重建，
所以收尾时读到的计数不代表稳态，不用它做判据）。

**注意**：TUNING 里**没有**休眠半径常量 —— 原版的休眠完全在 C++ 侧
（`entity:IsAwake()` 由引擎按玩家距离设置），Lua 只负责响应。
所以「按玩家距离 + 单一半径」已经贴近真实行为；
真正的分级（按视线/同屏）属于 C++ 那一层，宿主用 Lua 等价实现到这一步为止。

### 18. ★★ 实体休眠：补上「远离玩家就睡着」，帧率翻倍

上一节留下的性能差距，根源是：宿主**从来没有把实体设为休眠**。
`_asleep` 字段存在、`EntityScript:IsAsleep()` 也有（`entityscript.lua:1465`），
但**没有任何一处写它** —— 一个「声明了却没生效」的机制。

#### 18.1 按原版实现三环

1. **`UpdateSleepStates(cx, cz, sleep_radius, wake_radius)`**（`host/13_update.lua`）

   如 `boattrail.lua:25-26`）。
   **唤醒时要把脑和状态图拉起来**（`_EnableBrain_Internal` / `sg:Start(false)`）——
   否则实体醒了却不动，比不睡更糟。
2. **组件泵跳过休眠实体**（`StepComponents`）—— 真实引擎的做法就是把休眠实体
   从 `UpdatingEnts` 里摘掉。
3. **`Sim.SleepCenter` 钩子** —— 宿主不知道「玩家在哪」，由场景提供；
   这里返回玩家位置 + 半径 40。

#### 18.2 ★ 一个只能靠计数器才发现的静默失效

实现完第一版，诊断显示 `SleepCenter 非 nil = 2550/2550`、钩子明明在，

根因是 Lua 作用域经典坑：

```lua

...

```

闭包定义在 `local player` **之前 150 行**，函数体里的 `player` 解析成
**全局** `player`（恒为 nil）。症状极其隐蔽：钩子本身确实存在、条件也确实通过，
只是每次调用都返回 nil。修法是把实现挪到玩家声明之后。

#### 16.2 ★★ 一个「让所有无组件实体变成地雷」的真 bug：`replica` 惰性创建


崩溃是「索引 nil」，说明 `target.replica` 是 nil。**但那是 `target` 的，不是 `self` 的。**

#### 16.3 ★★ 预制体名 ≠ 文件名：惰性索引

宿主按「文件名 = 预制体名」懒加载，但实际有大量文件注册**别的名字**：

| 文件 | 注册的预制体 |
|---|---|
| `prefabs/fx.lua` | `die_fx` 等 ~200 个特效 |
| `prefabs/hats.lua` | 83 个帽子（`footballhat` …） |
| `prefabs/shallow_grave.lua` | `shallow_grave_player` |
| `prefabs/spoiledfood.lua` | `spoiled_food` / `spoiled_fish` … |
| `prefabs/preparedfoods.lua` | 全部料理（名字来自数据表） |

真实引擎没这个问题：启动时把 prefablist 里**全部**文件跑一遍。
宿主做成**惰性构建的索引**（只在真的缺预制体时才付这个代价，约 1~2 s）：

1. 先按「文件名 = 预制体名」直接试（绝大多数命中，零额外成本）
2. 扫描 `prefabs/*.lua` 建 `预制体名 → {候选文件}` 索引，逐个试加载
3. 文本扫不到的**动态注册**文件（`fx` / `preparedfoods`）单独列一张表，跑一遍即全注册

**★ 索引踩的两个坑（都靠实测抓到）**：

- 正则 `Prefab%(%s*"(%w+)"` 会把 **`SpawnPrefab("spoiled_food")`** 也算上
  （`SpawnPrefab(` 的尾巴就是 `Prefab(`）—— 于是 `spoiled_food` 被错指到
  `yotr_rabbitshrine.lua`。修法：前导加 `[^%w_]`。
- 加了前导后，模式**只有一个捕获**，写成 `for _, pname in ...` 会让
  `pname` 恒为 nil，报 `table index is nil`。修法：`for pname in ...`。
- 索引存**候选列表**而不是单个文件：文本扫描只是启发式，最终以
  「加载后 `Core.Prefabs` 里真的出现了」为准。

### 15. KTEX 的「像素格式字段」：**它不存在**，格式由 pitch 隐含

原任务写的是「解 KTEX 的像素格式字段 —— 目前靠体积与 alpha 块结构反推 DXT5」。
逐个字节解完之后结论是：**没有这个字段。**

#### 15.1 全库扫描：文件里没有留给格式枚举的字节

`tools/scan_ktex.py` 扫了全部 **3522 个包、3242 个 KTEX 样本**：

| 检查项 | 结果 |
|---|---|
| 每像素字节比 `mip0.size/(w*h)` | **3242/3242 都是 1.0000**（无一例外） |
| 每块字节数 `pitch/(w/4)` | **3242/3242 都是 16.00**（DXT1 会是 8） |
| 体积守恒（头长 + Σmip.size == 文件大小） | **3242/3242 成立** |

体积守恒全库成立意味着：**magic + 尺寸级 + mip 表**已经把文件里每一个字节都解释完了，
没有剩余空间放「格式」。
格式是由 **pitch 字段隐含**的：`pitch = (w/4) × 16` ⇒ 每 4×4 块 16 字节 ⇒ DXT3/DXT5 系。

#### 15.2 顺带修正了 `flag` 的公式（小图那几项原文档是错的）

原文档写的是 `byte1 = 0x02 | (0x20 × (log2(长边) − 7))`。
这个写法在 `log2 < 7`（边长 < 128）时**根本算不出来**，而实测确实存在小图：

```
16×16 → 0xFFFCA220    32×32 → 0xFFFCC220    64×64 → 0xFFFCE220
128   → 0xFFFD0220   256   → 0xFFFD2220  2048  → 0xFFFD8220
```

正确形式是**有符号偏移 + 借位**：

```python
flag = 0xFFFD0220 + ((log2(longside) - 7) << 13)
```

（小图时负数偏移会**借位到 byte2**，`byte2` 从 0xFD 变成 0xFC —— 不是逐字节 OR。）
8 个实测取值**全部命中**。

#### 15.3 怎么把 DXT3 排除掉（两者体积完全相同）

这只能从**数据本身**判别。用「解码后 alpha 的干净度」做可证伪判据 ——
精灵图集的 alpha 绝大多数是完全透明 0 或完全不透明 255，只有边缘一圈抗锯齿：

| 按哪种格式解 | 非 {0,255} 的 alpha 占比 |
|---|---:|
| **DXT5**（前 2 字节 = 8 位端点，后 6 字节 = 3 bit 索引） | **2.36%** ✔ |
| DXT3（前 8 字节 = 16 个 4 bit 显式 alpha） | 78.58% ✘（把索引当 alpha，全是噪点） |

2.36% 正是 AA 边缘该有的比例。两项旁证：首个块的 alpha 段是
`01 00 49 92 24 49 92 24`（a0/a1 + 梯度索引，DXT5 编码）；
解出来的图**看着就是原精灵**（pig/wilson 可辨认）—— 若格式错，画面会是垃圾。

复现脚本 `tools/probe/ktex_format.py`。

**★ 方法论提醒（踩过）**：第一版只抽每张图的**前 16 个块**做统计，
得到「DXT5 100.0% 干净」的假象 —— 因为精灵图集开头常整块透明。
改成**全图均匀撒 64 个块**后才看到真实的 2.36%。

### 11.8 ★★★ 一个「静默了很久」的深层宿主 bug：`GetParent()` 返回错类型

这是本阶段最有价值的发现，且**只有把静态调度器接线才会暴露**。

**症状**：接线 `RunStaticScheduler` 后，每 tick 报
`player_classified.lua:817: attempt to index field 'components' (a function value)`
（`components` 是**函数**）。

**追查过程**：
1. 报错行号对不上 —— 读的是 `02-注释源码/scripts/`，而宿主实际加载
   `.qwenworkcn/.../scripts/`，**两份文件行号不同**。换成真文件后是：
   `inst._parent.components.playervision:SetGhostVision(...)`
2. `inst._parent` 是**实体句柄**而不是 EntityScript —— 读它的未知字段会命中
   句柄的兜底 `__index`，返回「一个记录缺口的函数」，于是 `.components` 是函数。
3. 全库搜 `_parent =` 只找到 `= nil`，说明 Lua 侧从不显式赋值 → 由 C++ 的
   `SetParent` 维护。于是去读原版 classified 预制体：
   ```lua
   container_classified.lua:69        inst._parent = inst.entity:GetParent()
   constructionsite_classified.lua:36 inst._parent = inst.entity:GetParent()
   attunable_classified.lua:8          inst._parent = inst.entity:GetParent()
   container_opener.lua:8              inst._parent = inst.entity:GetParent()
   ```
   **⇒ `entity:GetParent()` 返回的必须是父实体的 EntityScript**（Klei 的 C++
   会 push 父实体的 Lua 表），而宿主返回的是实体句柄。

**修复**（`host/01_core.lua`）：
```lua
h._inst = inst
function h:SetParent(parent)
    if parent == nil then
        inst._parent, inst._parententity = nil, nil
    else
        inst._parententity = parent              -- 句柄（引擎内部指针）
        inst._parent = rawget(parent, "_inst")    -- ★ EntityScript
    end
end
function h:GetParent() return inst._parent end
function h:GetParentEntity() return inst._parententity end
```

**影响面**：整条 classified 实体的父子链此前都是错的
（`player_classified` / `inventory_classified` / `container_classified` …）。
修完之后静态任务的 attime 桶从 `[1×3, 2×1]` 缩到 `[2×1]` —— 那些原本报错的任务
现在正常完成。桩调用从 23 类 / 58 次降到 14 类 / 17 次。

### 11.9 ★ 静态调度器从来没被驱动过

`Sim.Step` 此前只调 `RunScheduler(tick)`，而真实 `scheduler.lua` 提供**两个独立入口**：

| 入口 | 内容 | 原版调用点 |
|---|---|---|
| `RunScheduler(tick)` | `scheduler:OnTick` + `scheduler:Run` | update.lua:247 |
| `RunStaticScheduler(tick)` | `staticScheduler:OnTick` + `staticScheduler:Run` | update.lua:185 |

宿主漏了第二个 → **`staticScheduler` 从来没被推进过**，所有走它的机制全是死的。
其中一个就是我们刚实现的 `DoStaticTaskInTime`（entityscript.lua:3775
`staticScheduler:ExecuteInTime`）：任务能登记、永远不执行，`pendingtasks` 也永远摘不掉。
另一个更隐蔽：`player_classified.lua:2104` `inst:DoStaticTaskInTime(0, RegisterNetListeners)`
—— **整个 classified 的网络监听注册一直是静默跳过的**。

接线时还缺两个真实全局（都是 C++ 侧）：
- **`GetStaticTick` / `GetStaticTime`** —— scheduler.lua:21/30 立刻调用，缺了直接崩
  `scheduler.lua:7: attempt to call global 'GetStaticTick'`。
  真实差别是「静态时钟不受暂停/加速影响」；宿主无暂停无加速，两者按定义重合。
- **`toarrayornil(...)`** —— scheduler.lua:95 `self.arg = toarrayornil(...)`。
  它的存在是为了绕开 Lua 的经典陷阱：**无参时 `{...}` 得到空表 `{}`，而 `{}` 是 truthy**，
  于是 `if args then unpack(args) end` 会被空表骗过。所以必须是「无参返 nil，否则返数组」。
  widget.lua:1833-1836 的注释把这个理由写得很清楚。

## 三、★ 本阶段最重要的引擎语义修复：AnimState 动画队列

**这是复刻侧第一次「修出了一个真实引擎级 bug」，而不是补桩。**

### 3.1 症状

蜘蛛在真实地形上位移约 40 世界单位，动画却**永久冻结在 `walk_pre` 第 6 帧**；
`state=moving` 但 `anim` 从未变成 `walk_loop`。

### 3.2 根因（三层叠加）

1. **`SGspider.lua:184` 的 `moving` 状态用的是 `PushAnimation("walk_loop")`**
   （排队，不打断当前动画），不是 `PlayAnimation`。
2. **状态图切状态是刻末批处理**：`stategraph.lua:1506` 把事件塞进
   `bufferedevents`，由 `SGManager:UpdateEvents` 在本帧最后统一处理
   （`host/02_sim.lua` 的 Step 尾部，对齐原版）。
3. 而宿主 `_tick` 写成了：

```lua
self._frame = self._nframe
if self._fired then return end      -- ← 闸门：动画播完后永久短路
self._fired = true
local played = self._curName
fire("animover")                     -- SG 是刻末批处理，状态切换要等本帧末
if self._curName ~= played then return end
local q = self._queue               -- ← 此刻队列还是空的！
```

时序：

```
tick N   ：walk_pre 播完 → animover 入队（此刻 _queue 仍是空的）→ 补发 animqueueover
tick N 末：SG 才把 premoving → moving，onenter 里 PushAnimation("walk_loop")
            → 队列到这时候才有了东西
tick N+1：_tick 再来，`if self._fired then return end` → 直接返回
            → 那个 walk_loop 永远排不上
```

### 3.3 修复（`host/10_animstate.lua`）

三段式，队列消费**独立于 `_fired`**：

```lua
-- ① 首次播完 → 补发 animover（只发一次）
if not self._fired then
    self._fired = true
    local played = self._curName
    fire("animover")
    if self._curName ~= played then return end
end
-- ② ★★ 队列消费：必须在每一次「动画已播完」时检查，绝不能放在 _fired 之后
local q = self._queue
if q ~= nil and #q > 0 then
    local nxt = table.remove(q, 1)
    applyAnim(self, nxt.name, nxt.loop)
    return
end
-- ③ 队列确实空了 → 补发 animqueueover（也只发一次，否则会每 tick 刷屏）
if not self._queuefired then
    self._queuefired = true
    fire("animqueueover")
end
```

配套：`applyAnim` 重置 `_queuefired = false`（新动画开始 → 允许下一次事件）。

### 3.4 隔离探针验证（4 场景全绿）

| 场景 | 结果 |
|---|---|
| Play 播完**之后**才 Push（= SGspider 的真实时序） | 修复前永久卡 `walk_pre`；修复后 ✔ 队列被消费 → `walk_loop` |
| 常规 Play + 同帧 Push | ✔ 正常切换（无回归） |
| `animqueueover` 重复发？ | 触发 **1** 次（期望 1） |
| `animover` 重复发？ | 触发 **1** 次（期望 1） |

### 3.5 效果（轨迹帧序列对比）

```
修复前：idle → walk_pre(fr6 冻结 42 tick) → walk_pst      ← walk_loop 永远缺席
修复后：idle → walk_pre → walk_loop → walk_pst            ← 干净的走/跑循环
```

并带来一个直接收益：**pigman 追逐时真的用跑的动画**（`run_loop/run_pre/run_pst`）。

### 4.2 玩家驱动的量纲修正（实测 0.076 → 0.198 单位/tick）

把「按固定 12 tick 重设目标」改成「**到达才推进路点**」：

- 若目标点绕圆周走，线速度只有 `2π·26/2400 ≈ 0.068` 单位/tick，

  目标比玩家**慢 3 倍** → 每 12 tick 玩家总是「提前到达」
  （`arrive_dist = 0.15`）→ 走 4 tick → `run_stop` → 空等 8 tick → 再 `run_start`，
  状态序列每 12 tick 抖一次。
- 改法：路点夹角 `WP_STEP = 0.62 rad`（弦长 ≈ 16 世界单位 ≈ 80 tick 连续跑动），
  且只在 `loco.dest == nil`（= 到达/被清）时才设下一个。
- 结果：位移恢复到 **0.198 单位/tick（≈ 满跑速）**，状态序列变成干净的
  `run_start → run → run_stop`。

## 五、朝向语义实证 → billboard 设计

**AnimatedSprite 是固定朝向 billboard，DST 不做平面旋转**；转向只体现为左右镜像。
两条独立证据：

1. 真实 `locomotor.lua:1411` 注释明确写了角度约定「+X 为 0°、顺时针为正」，
   而贴图只有一套朝向的画。
2. 用 `world.json` 的轨迹反推：对 862 个「方向稳定的位移样本」做圆统计，
   `rotation` 与移动方向角 `atan2(dz,dx)` 的圆均值偏差只有 **3.8°**（r = θ 拟合），
   而任何「贴图旋转」模型都对不上。

所以播放器：贴图不旋转，仅当朝向朝西（`cos r < 0`）时水平镜像；
真实的 rotation 用一根短线段画出来，避免丢失信息。

#### 8.5.3 规律与实用判据

**方差大小与「离纯几何多远」成正比**：

- 撞墙 **±0** —— 玩家沿固定圆周走，是**纯几何量**，与生物数量、行为、随机性都无关
- 状态名 ±6 —— 依赖生物各自的 `pairs()` 顺序
- 战斗事件 37~64（**1.7x**）—— 依赖「实际发生了多少次打斗」
- 帧率 670~887 —— 依赖实际发生的事最多

**实用判据：报数字前先问「这个量离纯几何有多远」**。
越接近纯几何越能单次引用；越依赖「实际发生了多少事」越必须带样本数和分布。

#### 8.5.4 ★ 两条元规则（本轮踩出来的）

1. **指标的名字必须说清口径**。「状态种类」曾被用来指「每实体状态数求和」，

   **它压根不测多样性**。测多样性只能用**全局去重**（25 → 34 种）。
2. **场景一改，这张表就作废**。加 7 只生物让五项数字全部变化，
   而这五项当时都还写着旧值 —— 包括被当成「可单次引用」的那一项。
3. **这张表由机器核对，不靠人记得**：`tools/verify_report.py`

### 43.1 一个此前被忽略的事实

`reachability.lua` 的抽样是**无放回**的（部分 Fisher-Yates）：

```lua
local want = math.min(n, #list)
for i = 1, want do
    local j = i + (rnd() % (#list - i + 1))
    idx[i], idx[j] = idx[j], idx[i]
    out[i] = list[idx[i]]
end
```

⇒ 令 `REACH_N` 等于**注册表总数**（6081），就是**全域覆盖**，

```bash
REACH_N=6081 REACH_LIST=1 "…/python.exe" "…/_run_lua.py" 5.1 "…/reachability.lua"
```

## 44. 一条**反向判据**抓到的真 bug：影子闸门一直是空转（2026-10-15 17:45，`date` 实读）

### 44.1 怎么发现的

T23 任务要求给「三条此前零断言覆盖的静默失效机制」补**反向判据**
（`grep` 计数：`DropDeathLoot` 0 条、`PushEvent` 0 条、`ListenForEvent` 0 条）。
其中一条是：

> `AddComponent` 影子闸门：重复添加必须返回**同一个**实例

断言一跑就红：**两次 `AddComponent("health")` 返回了两个不同实例。**

### 44.2 真因

原版 `entityscript.lua` 里影子表是**两处**配合的：

```
:218  self.lower_components_shadow = {}                    ← 建表
:612  if self.lower_components_shadow[lower_name] ~= nil then ← 查（闸门）
          ... return existingcmp
:635  self.lower_components_shadow[lower_name] = true       ← ★ 成功添加后**登记**
:654  self.lower_components_shadow[string.lower(name)] = nil ← 移除时**清掉**
```

宿主**只实现了 `:612` 的查**，从来没写 `:635` 的登记
（唯一一处 `= true` 是 `knownlocations` 那行硬编码）。

⇒ **闸门对所有普通组件都是死的**：第二次 `AddComponent("health")`
既查不到影子标记、也就不会返回旧实例，直接 `cmp(self)` **造出第二个活实例**。

## 45. 最后一个未解问题**已定论**：引擎不向预制体工厂传参（2026-10-15 18:03，`date` 实读）

### 45.1 它为什么是最后一个

第三轮追溯 `carnivaldecor_figure` 时曝出一个**脚本内部无法回答**的问题：

> `Prefab("carnivaldecor_figure", fn_season1, ...)` 而 `fn_season1(data)`
> —— 引擎到底往工厂里传参数吗？

两种假设都自洽，且**在脚本内部无法区分**：
- **不传** ⇒ `data` 恒 nil ⇒ `data.physics_radius` 崩 ⇒ 这是**原版自身的缺陷**
- **传 `(name, skin)`** ⇒ `data` 是**字符串** ⇒ 索引字符串只得到 nil、不崩
  ⇒ 正好解释「雕像在游戏里是正常的」⇒ 那是**宿主缺口**

本工程当时按规矩**没写成定论**，挂在「待定」并留下残余不确定性。
内部实证只到「27 个同类工厂里 23 个在无参调用下正常生成」。

### 45.2 外部证据（WebSearch，三处独立来源一致）

| 来源 | 关键表述 |
|---|---|
| **Klei 官方论坛**《[Documentation] Understanding Prefabs》 | 构造器**一律**写成 `local function fn()` —— **无参**；全文没有提到任何转发给 `fn` 的参数 |
| **DST 模组 API 文档**（`Prefab` 类） | `fn (function) — Factory function that creates the entity instance (inst) and returns it.` 参数表里**没有** name / skin |
| **entity 系统架构文档** | `SpawnPrefab(prefabname)` → 「查 `Prefabs` 表 → **调用构造器** → 返回实体」，**没有向构造器转发参数**这一步 |

⇒ **三处一致：引擎不向工厂传参。**

### 45.3 定论与证据级别（如实标注）

`carnivaldecor_figure / _season2 / _season3 / carnivaldecor_lamp`
= **原版缺陷（工厂声明了参数，但没有任何无参调用点会提供它）**

**证据级别：外部文档 + 本工程实证（23/27）双重支持**，
但**不是引擎二进制反汇编**。所以：
- 分类**从「待定」升级为「原版缺陷」**（不再是待查项）；
- 仍不写「已证实」—— 如果将来有反汇编或行为实验反驳，这条要改。

### 45.4 顺带说明：这 4 个**不是**宿主缺口，无需修

宿主的 `Core.SpawnPrefab` 忠实复刻了「无参调用」这一侧 —— **和原版一致**。
要让它「不崩」就得**替原版打补丁**（补 wrapper），那属于改原版代码，

## 48. P43：建造落地链路上的两个真缺陷 + 两个「判据错」

这一节记的是 **宿主侧**（`host/` 与入口脚本）的问题。07 侧的两条跨实现守卫见
`07-通用引擎/开发计划.md` §9ao，不在这里重复。

### 48.1 `GetDistanceSqToPoint` 漏了「只传一个 Vector3」分支（真缺陷）

原版 `entityscript.lua:3526-3537` 第二行就是 `if x and not y and not z then x, y, z = x:Get() end`，
宿主**整条漏掉**。于是 `map.lua:484` 的 `other:GetDistanceSqToPoint(pt)`（`pt` 是 Vector3）
把表当 `x` 传下去，接着触发 `number - Vector3`，报
`attempt to index local 'a' (a number value)`。

后果不是「放置判定不准」，而是**整条 `deployable` / 建造落地链路直接抛错**：
`deployable:CanDeploy()` 一调就崩。实测见 `mech.lua` 第 10 段。

配套修 `host/03_globals.lua` 的 `Vector3Meta.__add/__sub`：原来只处理「两侧都是表」，
`1 - v` 这种调用会把错误抛在**元方法里**，栈指向元方法而不是调用点 —— 排查成本极高。
原版 `Vector3` 是 C++ 类、标量加减是支持的，这里对齐。

### 48.2 `render.lua` 挑动画的判据是**恒真**的（判据错）

原来：

```lua
as:PlayAnimation(n, true)
if as._nframe and as._nframe > 0 then return n end
```

`host/10_animstate.lua:689-696`：动画**不存在**时宿主会投影一条**合成动画**
（`FALLBACK_FRAMES=15`、`_cur = nil`、`_synthetic = true`），好让 `_tick`/`AnimDone`/`animover`
照常工作（否则生物进这类状态就永久卡死）。副作用是 **`_nframe` 恒 > 0** ⇒
判据**恒为真** ⇒ `pick_anim` 永远返回候选表第一项 `"idle_loop"`，**从没按生物挑过动画**。

实测后果：`rabbit_build` / `spider_build` 没有 `idle_loop`（它们叫 `idle`）
⇒ 拿到合成动画 ⇒ `GetDrawList()` 空 ⇒ `drawlist.txt` 里这两个 build **0 个 QUAD**。
而 `07` 的 DrawCmd 一致性判据只能把它们**跳过** —— 汇总行里「跳过」长得跟「通过」很像。

修法：判据改成「真的绑上了动画数据」（`as._cur ~= nil and not as._synthetic`），
`spawned` 的入口条件同样改看 `_cur`（原来 `info.nframe` 也会被合成动画填成 15，
把「一条动画都没绑上」的生物也放进去，导出成空 BUNDLE 污染下游判据）。

### 48.3 `player.lua` 状态机判据的**采样时刻**错了（判据错）

`onenter 驱动动画` 这一条原来只在 `GoToState` 之后**跑 10 tick** 才读动画。
但 `go("run")` 进 `run` 后，状态机在 10 tick 内自己切回 `idle` ⇒ 采到 `idle_loop`
⇒ **恒为 ✘**。加一个「转移瞬间」的采样点后实测：`idle_loop → run_loop`，
`onenter` 确实在驱动动画，原来的 ✘ 是**判据的采样时刻错了**。

同时按 `mech.lua` 的教训（§43 那条「打印 ✘ 却从不 error = 假绿」）补了文末 `error` 收尾，
这条判据从此**真的会红**（已做反向测试：把判据退回旧写法，`player.lua` 立刻 FAIL）。

### 48.4 为什么这三个都要写进 `audit_fixes.py`

本工程的规矩是「修了就得有特征串守着，否则下次文件恢复会静默丢修复」。
本轮往清单里加了 6 条（建造链路 2 条 + 判据错 4 条），清单从 146 条涨到 152 条。
特征串一律指向**那句判定本身**（如 `if x and not y and not z and type(x) ~= "number" then`），
不指向注释 —— 注释写得再详细也不代表分支还在。

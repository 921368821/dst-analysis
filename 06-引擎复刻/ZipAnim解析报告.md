# ZipAnim 解析器 · 阶段报告

> 目标：解开 DST 的 `data/anim/*.zip` 里的三个私有二进制格式，
> 好让契约复刻宿主的 `AnimState` 桩能换成真实帧数据 —— 这是接渲染层唯一缺的一块。
>
> 报告时间：2026-10-13

## 一、为什么这活儿不轻松

DST 的动画资源是 Klei 自家格式，**没有官方文档**：

| 文件 | 作用 | 格式 |
|---|---|---|
| `atlas-N.tex` | 纹理图集（一张大图，所有精灵排列其上） | KTEX（Klei 私有） |
| `build.bin` | 符号/图层 → 图集矩形 + 变换 | 私有二进制 |
| `anim.bin` | 动画名 → 帧 → 每帧各符号的变换 | 私有二进制 |

`data/anim/` 下共 **3522 个 zip**，其中约 80% 同时含 `anim.bin` 与 `build.bin`
（其余是纯 build 或纯动画）。

本报告里每个字段都标注了 **[已解码] / [部分] / [未解码]** —— 这些格式是
逐字节观测推导的，不是从任何文档或泄漏源码来的，**不该假装全都懂了**。

## 二、[已解码] KTEX 图集头

```
+0   char[4]  magic "KTEX"
+4   u32      平台/格式标志（打包方式未定，见下）
+8   u16      width    ★
+10  u16      height   ★
+12  起       mipmap 链的尺寸表
```

**关键：宽高在 +8，不在经典布局的 +12。** 这是踩出来的 —— 按经典布局读会得到
「512×16384」这种荒谬值。

### ★ 怎么确认宽高读对了：用文件体积反推
以 `abigail_attack_fx.zip` 为例：

```
实测宽高      : 128 × 128
全 mip 链字节 : 128² + 64² + 32² + 16² + 8² + 4²   (DXT5 = 1 字节/像素)
              = 16384 + 4096 + 1024 + 256 + 64 + 16 = 21840
文件总大小    : 21960
差值          : 120 字节  ≈  头部(16) + 对齐
```

体积对得上 → 宽高解读正确。这个断言**可证伪**，所以是有力的。

## 三、[已解码] build.bin 头

```
+0   char[4] magic "BILD"
+4   u32     version（DST 实测为 6）
+8   u32     未知 A
+12  u32     未知 B
+16  u32     build 名字长度      ← 注意不是 +12！
+20  ...     build 名字
...  u32     num_atlases
...  num_atlases × (u32 长度 + 图集名)
...  u32     图集哈希
...  u32     num_symbols
```

### ★ 踩过的坑
一开始把 `+12` 当成名字长度，于是**每个 build 的名字都读歪一个字段**，
连锁导致符号数读成 `1313879758`（那其实是哈希值）。跨 9 个不同 build
对照才看出来 —— 单看一个文件，`1313879758` 这种数字很容易被当成
「某个大 build 的符号数」而放过。

### [未解码] 未知 A / 未知 B
实测取值：

| build | A | B | 名字长 |
|---|---:|---:|---:|
| `abigail_attack_fx` | 2 | 15 | 17 |
| `antlion_build` | 11 | 81 | 13 |
| `archive_centipede_build` | 12 | 56 | 23 |
| `bearger_build` | 13 | 87 | 13 |
| `bee_build` | 7 | 9 | 9 |
| `bee_angry_build` | 7 | 9 | 15 |

同族资源取值相同（`bee_build` 与 `bee_angry_build` 都是 7,9），
但与名字长度、图集数、符号数都**无相关性**。疑为「总帧数」或内容计数。**不猜。**

### [未解码] 符号条目区
每个符号以 u32 hash 开头，随后是一批 f32（实测有 `-6.525` / `93` / `61`
这样像「顶点坐标 + 宽高」的值），但字段边界未定。

## 四、[部分] anim.bin

```
+0   char[4] magic "ANIM"
+4   u32     version（DST 实测为 4）
+8   u32     总元素数（疑为「帧 × 符号」引用总数）
+12  u32     未知
+16  u32     未知（实测恒为 0）
+20  u32     num_anims
+24  起      [ u32 长度 + 动画名 + 该动画的帧数据 ] × num_anims
```

### ★ 重要结构发现：名字与数据是**交织**的
不像 build.bin 能把名字表一次读完，anim.bin 里每段动画的帧数据紧跟在自己名字后面。
想跳到下一个名字，必须知道本段数据多长 —— 而帧数据格式尚未完全解码。

所以本工具列动画名用「扫描全部长度前缀字符串」的方式捞。

### ★ 交叉验证：捞出来的名字数正好等于头部声明
`abigail_attack_fx.zip`：

```
头部声明 num_anims = 18
扫出的名字：
  attack1_pre  attack1_loop  attack1_pst
  attack2_pre  attack2_loop  attack2_pst
  attack3_pre  attack3_loop  attack3_pst
  attack1_ground_pre  attack1_ground_loop  attack1_ground_pst
  attack2_ground_pre  attack2_ground_loop  attack2_ground_pst
  attack3_ground_pre  attack3_ground_loop  attack3_ground_pst
  ── 正好 18 个 ✓
```

名字还是规范的 `_pre / _loop / _pst` 三段式（前摇 / 循环 / 后摇），
与 DST 状态机里 `attack` 状态的写法一致 —— 说明头偏移读对了。

### [未解码] 帧数据区
含大量 f32，语义像「x, y, 缩放, 旋转, alpha」的关键帧变换，字段边界未定。

## 六、工具用法

```bash
# ★ 2026-10-18：PY 由 tools/env.sh 解析；$B 是本机装的原版 DST 资产目录

⚠️ 路径含 `'`（`Don't Starve Together`），在 bash 里要小心引用；
建议先 `cp` 到无单引号的目录再跑（本仓库的 `_animtest/` 就是干这个的）。

# 第二阶段：符号条目区 + 帧数据区 —— **两者都已完全解开**

> 报告时间：2026-10-13
> 结论：BILD v6 与 ANIM v4 的**全部字段**已确定，并经全量样本守恒验证。

## 0. 关键转折：找到了官方字段表

纯靠逐字节猜很慢。转到一条更高效的路：**Klei 自己的 mod 工具脚本**
`mod_tools/tools/scripts/buildanimation.py` 顶部的注释里就有完整字段表。
它不是泄漏物 —— 是随游戏发布的脚本，公开论坛上有原文引用。

拿到字段表后，剩下的工作是**用守恒约束把布局细节钉死**（字段表给了语义，
但没给对齐/计数/池化这类实现细节）。

## 1. BILD v6 符号条目区 —— 已解开

### 最终布局
```
'BILD' | version | total_symbols | total_frames | build_name
num_materials | material_texture_name × n
── 符号区 ──
symbols × total_symbols {
    hash : i32
    num_frames : i32
    frames × num_frames {
        frame_num    : i32
        duration     : i32      -- 该帧重复用的次数
        bbox x,y,w,h : f32 × 4  -- 裁剪框（相对锚点，可为负）
        vb_start_index : i32    -- ★ 全局顶点池下标
        num_verts      : i32
    }                           -- 定长 32 字节
}
── 全局顶点池（只存一份）──
total_vertices : i32
vertices × total_vertices { x, y, z, u, v, w } : f32 × 6   -- 定长 24 字节
── 哈希 → 原始字符串 ──
num_hashed_strings | ( hash : i32, original_string : str ) × n
```

### 破译靠的三个守恒点（都不是猜的）
1. **符号条目定长 32 字节** ← 由「符号长度 = 8 + nframes × 32」在 41 个样本上成立
   （`arm` 40B = 8+32，`inner wing` 72B = 8+2×32，`pinchers` 168B = 8+5×32）
2. **`vb_start_index` 是全局累计下标** ← 由 antlion 符号区的累加序列
   `0, 78, 156, 246, 330, 444, 516, 774, 966, …` 一路加到 **1758**，
   而 1758 **正好等于下一个符号 `pinchers` 的 vb_start**，且各帧 num_verts
   之和 = 1758 —— 两路独立算出的数字吻合
3. **顶点池独立、只存一份** ← 由「`pinchers` 长 168 且不含顶点数据」
   与「最后一个符号后紧跟 total_vertices + 池」共同确认

### 定位手法（本轮最有用的一招）
**用尾部字符串表里的哈希反查符号起点。**
字符串表给的是 `(hash, name)` 对，而符号条目里存的正是同一个哈希。
在符号区里 `find()` 这些哈希的小端字节，就拿到每个符号的**精确起点**，
进而得到**精确长度** —— 不用再猜字段边界。

```
bee_build:   body  arm  inner wing  nose  stinger  face  foot   ← 7 个，与 total_symbols=7 吻合
            长度 32   40   72          40    40       72    1340
```

### 验证结果
```
BILD v6 完整解析: 守恒通过 59，失败 0        ← 59 个含 build.bin 的样本全部「逐字节正好读完」
```

## 2. ANIM v4 帧数据区 —— 已解开

### 最终布局
```
'ANIM' | version | total_num_element_refs | total_num_frames
      | total_num_events | num_anims
anims × num_anims {
    animname         : str
    validfacings     : byte      -- 位掩码 xxxx dlur（下左上右）
    rootsymbolhash   : i32
    frame_rate       : f32
    num_frames       : i32
    frames × num_frames {
        x, y, w, h   : f32 × 4   -- 整帧包围盒
        num_events   : i32 | event_hash × num_events
        num_elements : i32
        elements × num_elements {
            symbol_hash  : i32
            symbol_frame : i32    -- 用该符号的第几帧
            folder_hash  : i32    -- 图层分组
            mat a,b,c,d,tx,ty,tz : f32 × 7
        }                         -- 定长 40 字节
    }
}
num_hashed_strings | ( hash : i32, original_string : str ) × n
```

### ★ UV 在哪：在**顶点**里，不在 bbox 里
顶点元组是 `(x, y, z, u, v, w)`：
- `x, y` —— 相对锚点的像素位置（可为负）
- `z` —— 2D 恒为 0
- **`u, v` —— 归一化 UV，落在 [0,1]** ← 渲染要的就是它
- `w` —— 未使用（恒 0）

6 个顶点组成一个四边形（两个三角形）。

**三重交叉验证**（UV 跨度 × 图集尺寸 应当等于 bbox 的 w/h）：

| 符号 | UV 跨度 | ×256 | bbox w/h |
|---|---|---:|---|
| `body` | 0.2969 | **76.0** | 76 ✓ |
| `arm` | 0.1172 | **30.0** | 30 ✓ |
| `inner wing` | 0.2304 | **59.0** | 59 ✓ |

⚠️ 踩过的坑：一开始拿 `bbox` 当 UV 用，报出 133219 处「超出图集范围」。
真相是 bbox 是**相对锚点的裁剪框**，负数完全正常。改用顶点 UV 后越界降到 **0**。

### 验证结果
```
ANIM v4 完整解析: 守恒通过 72，失败 0
  其中「头部声明数 == 实际解析数」不变式成立: 72，不符 0
```
第二行是更强的自证 —— 文件头声明了总数，文件体里又有逐层计数，
两路数字必须完全一致：

```
abigail_attack_fx: 动画=18  帧=276(声明276 ✓)  事件=0(声明0 ✓)  元素=704(声明704 ✓)
```

# 第三阶段：KTEX 纹理 + DXT5 解码 + 真实动画帧合成 —— **能出图了**

> 报告时间：2026-10-13

## 1. KTEX 头部 —— 完全解开

```
+0   char[4] magic "KTEX"
+4   u32     大小级别标志
             byte0 = 0x20（常量）
             byte1 = 0x02 | (0x20 × (log2(长边) − 7))
                     实测：128→0x02  256→0x22  512→0x42  2048→0x82
             byte2 = 0xFD（常量）
             byte3 = 0xFF（常量）
             实测取值 0xfffd0220 / 0xfffd2220 / 0xfffd4220 / 0xfffd8220
+8   mip 表，每项 **10 字节**:
        u16 width
        u16 height
        u16 row_pitch   -- 每个「块行」的字节数 = (w/4) × 16，最小 16
        u32 size        -- 该 mip 级的压缩字节数
     项数 = 从整图一直降到 1×1（长边 128 → 8 项，2048 → 12 项）
...  压缩纹理数据，**紧接着 mip 表最后一项**，按 mip 顺序排列
```

### ★ 怎么确认「数据从表尾开始」（分毫不差）
```
abigail_attack_fx（128×128）:
  8 项 mip，size 之和 = 16384+4096+1024+256+64+16+16+16 = 21872
  文件总大小 = 21960
  头 = 21960 − 21872 = 88 = 8（magic+标志）+ 8 项 × 10 字节   ✓
```
这个等式在全部样本上成立，所以**头长、项长、数据起点被同时钉死**。

之前我以为头只有 16 字节、mip 表在别处，怎么算都差一截。把「10 字节一项」
和「数据紧接表尾」这两点确定后，一切对齐。

## 2. 像素格式 = DXT5（1 字节/像素）

两条独立证据：
1. **字节/像素 = 1.00**（DXT3/DXT5 都是 1B/px；DXT1 是 0.5B/px）
2. **首个块的 alpha 段结构**：`01 00 49 92 24 49 92 24`
   开头 2 字节是 alpha 端点 a0=1, a1=0，随后 6 字节是插值索引 ——
   这正是 DXT5 的 alpha 编码。若是 DXT3，那 8 字节会是 16 个 4bit
   显式 alpha，精灵图多为 0 或 F，分布不会是这样平滑的梯度。

## 3. DXT5 解码器 + PNG 输出（`tools/ktex.py`）

纯标准库实现，不依赖 Pillow。**解码结果肉眼可验证**：

| 图集 | 结果 |
|---|---|

```

### 变换矩阵已确认
`mat = (a, b, c, d, tx, ty, tz)` 里的 (a,b,c,d) 是标准旋转矩阵
（实测 a=d=cos, b=−c=sin），tx/ty 是平移，tz 是深度排序键。

### ⚠️ 两个踩过的坑
1. **y 轴翻转算错**：画布 y = (offy − y) × scale，`offy` 必须是
   **maxy + pad**（我误写成 −miny + pad），否则 y=maxy 时画布 y 变负，
   整张图被纵向裁掉，表现为「只画出两个小红块」。
2. **UV 不能靠包围盒插值**：顶点里本来就带 (u, v)，按**三角形重心坐标**
   插值才严格正确。早前用「按位置比例在 UV 包围盒里插值」，
   隐含假设了「UV 与位置同向且轴对齐」，一旦有旋转就会错位。

### 诚实说明
- 合成出的画面**纹理与颜色是对的**（与图集逐一对应），
  但**部件摆位是否与原版游戏完全一致，我没有逐帧比对过**。

  ① charlie 本身就是个高瘦的影子生物，或
  ② 我漏了什么（比如部件层级 / 锚点偏移）。

# 第四阶段：部件摆位核实 —— **确认正确（此前是我的 y 方向搞反了）**

> 报告时间：2026-10-13

## 1. 问题的由来

第三阶段我渲染 `charlie_basic` 的 idle 得到一条 238×700 的纵向长条，

## 5. ⚠️ 踩坑记录：文档那句话把我带偏了

`buildanimation.py` 的注释里写着：

> the game engine flips images vertically when drawing.
> This means that yes, the output Y coordinate will be inverted.

我据此以为「数据里 y 向上，渲染时要翻」—— 于是多翻了一次，帽子跑到了脚底下。
**实际是这句话在描述「从 Spriter 导出到 DST」那一步已经做过的翻转，

教训：**文档描述的是转换过程，不是最终格式的约定。**
判断方向时要靠**语义可验证的东西**（帽子在上、裙摆在下），
而不是靠推测文档那句话指的是哪一步。
